    오리엔테이션

    엔진이 무엇으로 이루어져 있는지 큰 그림을 잡고, 아무것도 없는 폴더에서 "창이 뜨고 화면이 지워지는" 상태까지 가는 첫 걸음을 함께 밟습니다.

    0강

    게임 엔진이란 무엇인가

    관련 기록: Plans.md "핵심 결정 (2026-09-29)" · 살펴볼 곳: Projects/Sample/, Engine/Source/
    이 강의를 마치면
    • 게임 엔진, 에디터, 런타임, 게임 프로젝트가 각각 무엇이고 서로 어떻게 연결되는지 설명할 수 있습니다.
    • 엔진을 이루는 주요 시스템(렌더링, 씬, 물리, 스크립트, 네트워크 등)과 그 의존 방향을 그릴 수 있습니다.
    • ProjectE가 "무엇을 직접 만들고 무엇을 가져다 쓸지" 정한 기준과 그 이유를 이해합니다.

    왜 필요한가게임마다 같은 일을 반복하지 않기 위해

    게임을 하나 만든다고 생각해 봅시다. 화면에 3D 모델을 그려야 하고, 키보드와 마우스 입력을 받아야 하고, 물체가 떨어지고 부딪혀야 하고, 소리가 나야 하고, 저장과 불러오기가 되어야 합니다. 그런데 이 목록은 레이싱 게임이든 RPG든 거의 똑같습니다. 다른 것은 "그 위에서 무슨 일이 일어나느냐" — 즉 규칙과 콘텐츠뿐입니다.

    게임 엔진은 이 공통 부분을 한 번 잘 만들어 두고, 게임마다 규칙과 콘텐츠만 바꿔 끼우게 해 주는 소프트웨어입니다. 언리얼과 유니티가 대표적이고, 이 강의에서 다루는 ProjectE도 같은 목표를 가진 엔진입니다.

    비유 엔진은 자동차의 차체·엔진·변속기이고, 게임은 그 위에 얹는 실내 디자인과 운전 경험입니다. 같은 차체로 세단도 SUV도 만들 수 있듯, 같은 엔진으로 장르가 다른 게임을 만듭니다.

    핵심 개념엔진을 구성하는 네 가지 층

    "엔진"이라는 말은 사실 여러 덩어리를 한꺼번에 부르는 말입니다. ProjectE를 기준으로 나누면 네 층이 됩니다.

    ① 플랫폼 추상화

    운영체제와 GPU는 저마다 API가 다릅니다. 창을 만드는 방법은 Windows(Win32)와 macOS가 다르고, GPU에 그리라고 시키는 방법은 DirectX, Vulkan, Metal이 다릅니다. 엔진은 이 차이를 얇은 층으로 감싸서 위층이 신경 쓰지 않게 합니다. ProjectE에서는 이것이 Core(창·입력·타이머)와 RHI(Render Hardware Interface — GPU 명령 추상화)입니다. 지금은 Windows + DirectX 12만 지원하지만, 층이 분리되어 있으므로 나중에 다른 플랫폼을 붙일 자리가 있습니다.

    ② 엔진 런타임

    게임이 실행되는 동안 매 프레임 돌아가는 시스템들입니다. 화면을 그리는 렌더러, 게임 세계의 물체를 담는 씬, 물리 시뮬레이션, 소리, 애니메이션, AI, 스크립트, 네트워크, UI가 여기 있습니다. 중요한 점은 이 코드가 에디터와 게임에서 똑같이 쓰인다는 것입니다. 에디터의 뷰포트에 보이는 장면은 게임에서 보일 장면과 같은 렌더러가 그립니다.

    ③ 실행 파일: 에디터, 런타임, 서버, 도구

    같은 엔진 런타임 위에 서로 다른 "얼굴"을 붙인 프로그램들입니다.

    실행 파일누가 쓰나특징
    ProjectEEditor.exe개발자씬 편집, 에셋 편집기, 플레이 테스트. ImGui로 만든 도구 UI
    ProjectERuntime.exe플레이어출시되는 게임. 패키징할 때 게임 이름·아이콘으로 바뀐다
    ProjectEServer.exe서버 운영창도 GPU도 없이 게임 규칙만 돌리는 전용 서버
    ProjectECook.exe빌드 파이프라인셰이더·모델·텍스처를 게임이 바로 읽을 형식으로 변환(쿠킹)

    ④ 게임 프로젝트

    실제 게임의 내용물입니다. ProjectE에서는 엔진 폴더와 완전히 분리된 프로젝트 폴더에 있고, 그 표식이 .eproject 파일입니다.

    Projects/Sample/
  Sample.eproject      // 프로젝트 정체성: 이름, 엔진 버전, 게임 모듈 DLL 이름
  Content/             // 씬(.escene), 모델, 머티리얼(.emat), Lua 스크립트, UI(.eui) ...
  Config/              // 프로젝트 설정 JSON (입력 매핑, 충돌 레이어, 렌더링 옵션 ...)
  Source/              // 게임 전용 C++ → SampleGame.dll (게임 모듈)
  Saved/               // 로그, 세이브, 캐시 (gitignore)
  Cooked/              // 쿠킹된 에셋 (gitignore)
    왜 엔진과 프로젝트를 나누나 엔진 코드 안에 게임 에셋이 섞이면, 게임을 두 개 만들 때 엔진을 복사해야 합니다. 분리해 두면 엔진 하나로 여러 프로젝트를 열 수 있고, 엔진을 고쳐도 게임 폴더는 그대로입니다. 경로를 얻을 때 항상 FPaths를 거치게 한 것도 이 때문입니다 — 엔진 파일은 "실행 파일 기준", 게임 파일은 "프로젝트 폴더 기준"으로 찾습니다.

    핵심 개념게임은 "아주 빠르게 반복되는 루프"다

    영화는 미리 찍은 사진을 1초에 24장 넘깁니다. 게임은 사진을 매번 새로 계산해서 1초에 60장 이상 만들어 냅니다. 이 한 장을 만드는 과정이 프레임이고, 엔진의 심장은 프레임을 끝없이 반복하는 루프입니다.

    이 그림에서 두 가지를 기억해 두세요. 첫째, 한 바퀴는 예산이 정해져 있습니다. 60fps라면 16.7ms 안에 입력·갱신·그리기를 모두 끝내야 합니다. 4부(성능)는 통째로 이 예산 싸움입니다. 둘째, 세계 갱신은 dt(델타 타임)에 비례해야 합니다. 빠른 PC에서 캐릭터가 더 빨리 달리면 안 되니까요.

    ProjectE에서는무엇을 직접 만들고, 무엇을 가져다 쓰나

    엔진을 처음부터 만든다고 해서 모든 것을 직접 짤 필요는 없습니다. 오히려 그러면 끝나지 않습니다. ProjectE는 첫날(2026-09-29) 다음 기준을 정했습니다.

    직접 구현라이브러리 사용 (CMake FetchContent, 커밋 해시 고정)
    창·입력, 수학, RHI(DirectX 12 래퍼), 렌더러, ECS, 리플렉션
    — 엔진의 성격과 성능을 결정하는 것    		 이미지 디코딩(stb_image), glTF 파싱(cgltf), JSON(nlohmann), 에디터 UI(Dear ImGui), 오디오(miniaudio), 스크립트 VM(Lua + sol2), 물리(Jolt), 네트워크(GameNetworkingSockets), 내비메시(Recast), 프로파일러(Tracy)
    — 잘 만들어진 표준 해법이 있고, 직접 짜도 배울 것보다 시간이 더 드는 것

    판단 기준은 단순합니다. "이걸 직접 만들면 엔진의 핵심을 이해하는 데 도움이 되는가, 그리고 엔진의 구조를 내 마음대로 정해야 하는가?" 렌더러와 ECS는 둘 다 '예'입니다. 반면 PNG 파일 형식을 해독하는 코드는 엔진 설계와 무관하므로 검증된 라이브러리를 씁니다. 물리 엔진은 그 자체로 하나의 거대한 분야라 Jolt를 쓰되, 엔진과 맞닿는 경계(단위 변환, 컴포넌트, 이벤트 전달)는 직접 설계합니다 — 45강에서 다룹니다.

    첫날 함께 정한 다른 결정들
    • DirectX 12, Windows x64, C++20, MSVC — 가장 널리 쓰이는 PC 게임 환경 하나에 집중
    • 좌표계는 언리얼과 같은 왼손 Z-up, 1단위 = 1cm — 4강에서 이유를 다룹니다
    • 소스 에셋은 JSON, 실행할 때는 쿠킹된 바이너리 — 사람이 읽고 git diff 할 수 있게(10강)
    • 스크립트는 하이브리드 — 무거운 시스템은 C++, 콘텐츠 로직은 Lua(47강)
    이런 결정은 나중에 바꾸기 매우 비쌉니다. 좌표계를 중간에 바꾸면 수학, 셰이더, 임포터, 물리, 저장된 씬 전부를 고쳐야 합니다. 그래서 첫날 정했습니다.

    ProjectE에서는모듈과 의존 방향

    엔진 소스는 Engine/Source/ 아래 모듈 단위로 나뉩니다. 모듈 사이에는 한 방향으로만 의존이 흐르도록 규칙을 둡니다.

    왜 이렇게 까다롭게 할까요? 의존이 순환하면(A가 B를 쓰고 B가 A를 쓰면) 둘을 따로 테스트할 수도, 따로 바꿀 수도 없게 됩니다. 예를 들어 Lua 스크립트에서 Physics.Raycast를 부를 수 있어야 하지만, Scripting 모듈이 Physics를 직접 include하면 "물리 없는 서버 테스트" 같은 것이 어려워집니다. 그래서 Scripting은 FScriptPhysicsHooks라는 함수 묶음만 알고, 그 함수를 실제 물리에 연결하는 일은 더 위층인 World가 합니다. 이 "훅으로 잇기" 패턴은 강의 곳곳에서 다시 나옵니다.

    함정과 교훈범용 엔진은 끝이 없다

    ProjectE의 목표는 "에디터를 포함한 범용 3D 게임 엔진"입니다. 범용이라는 말은 끝이 없다는 뜻이기도 합니다. 그래서 이 프로젝트는 처음부터 Plans.md에 Phase 단위로 작업을 나누고, 각 Phase마다 완료 기준(DoD, Definition of Done)을 적었습니다. 예를 들어 Phase 0의 DoD는 이렇습니다.

    ## Phase 0 — 프로젝트 골격
**DoD**: Sandbox.exe 실행 시 창이 열리고 DX12로 배경색이 클리어된다.
리사이즈 / ESC 종료 / F1 VSync 토글이 동작하고, 디버그 레이어 에러 및
종료 시 라이브 오브젝트 누수가 없다.

    "좋은 엔진 만들기"는 끝낼 수 없지만, "창이 뜨고 배경이 지워지며 누수가 없다"는 끝낼 수 있습니다. 확인 가능한 작은 목표를 쌓아 가는 것이 큰 소프트웨어를 만드는 유일한 방법입니다. 이 강의도 그 순서를 따라갑니다.

    정리
    • 엔진 = 게임마다 반복되는 공통 부분(그리기, 입력, 물리, 소리, 저장 …)을 한 번 잘 만든 것.
    • 네 층: 플랫폼 추상화 → 엔진 런타임 → 실행 파일(에디터/런타임/서버/도구) → 게임 프로젝트.
    • 에디터와 게임은 같은 엔진 런타임을 공유하고, 게임 프로젝트는 엔진 폴더와 분리된다.
    • 엔진의 성격을 정하는 것(렌더러, ECS, 리플렉션)은 직접, 표준 해법이 있는 것은 라이브러리.
    • 모듈 의존은 한 방향. 거꾸로 이어야 하면 위층이 훅으로 잇는다.

    생각해 볼 문제

    Q1. 에디터 전용 코드(예: 기즈모)가 엔진 런타임 DLL 안에 있으면 어떤 문제가 생길까요? 출시되는 게임에 쓰지도 않는 코드가 함께 실리고, 런타임이 ImGui 같은 에디터 라이브러리에 의존하게 됩니다. 그래서 ProjectE에서 Editor 모듈은 엔진 DLL 밖에 있고, 엔진 DLL을 쓰기만 합니다. 의존 방향은 "에디터 → 엔진"이지 그 반대가 아닙니다.
    Q2. 위치를 위치 += 속도로 갱신하면 어떤 일이 생길까요? 1프레임마다 "속도"만큼 움직이므로 144fps 모니터에서는 60fps보다 2.4배 빨리 움직입니다. 위치 += 속도 × dt로 쓰면 초당 이동량이 프레임률과 무관해집니다. (물리처럼 정확해야 하는 시뮬레이션은 한 걸음 더 나아가 "고정 스텝"을 씁니다 — 45강.)
    Q3. Lua 스크립트가 AI의 블랙보드를 읽어야 하는데 Scripting과 AI 모듈은 서로 모릅니다. 어떻게 이을까요? Scripting 쪽에 "블랙보드 읽기" 함수 포인터 묶음(FScriptAIHooks)을 두고, 둘을 모두 아는 World(FGameWorld::ConnectScriptsAndAI)가 실제 구현을 꽂아 넣습니다. 의존 방향은 그대로 두고 연결만 위에서 합니다.

    이 강의를 마치면
    • CMake로 여러 모듈과 실행 파일을 가진 C++ 프로젝트를 구성하는 방법을 이해합니다.
    • 엔진이 로그와 어설트를 왜 자체 매크로로 두는지 설명할 수 있습니다.
    • Win32 창과 메시지 루프가 무엇이고, 그것이 게임 루프와 어떻게 맞물리는지 압니다.
    • 입력을 "눌려 있음/이번에 눌림/이번에 뗌"으로 나누는 이유를 압니다.

    왜 필요한가그리기 전에 필요한 것들

    삼각형 하나를 그리기 전에도 준비할 것이 꽤 많습니다. 소스 파일을 어떻게 묶어 빌드할지, 무슨 일이 일어나는지 어떻게 기록할지, 화면을 띄울 창은 어떻게 만들지, 키보드 입력은 어떻게 받을지, 시간은 어떻게 잴지. 이 강의는 Phase 0에서 만든 이 "뼈대"를 하나씩 봅니다. 화려하지 않지만, 이후 모든 강의의 코드가 이 위에서 돌아갑니다.

    핵심 개념CMake: 빌드를 설명하는 언어

    C++ 컴파일러는 ".cpp 파일 하나 → 오브젝트 파일 하나"만 압니다. 수백 개 파일을 모아 라이브러리를 만들고, 라이브러리끼리 링크해 실행 파일을 만들고, 컴파일 옵션을 정하는 일은 빌드 시스템의 몫입니다. CMake는 "이런 타깃이 있고 이렇게 의존한다"를 기술하면 Visual Studio 솔루션이나 Ninja 빌드 파일을 대신 만들어 주는 도구입니다.

    핵심 단어는 타깃(target)입니다. 라이브러리 하나, 실행 파일 하나가 각각 타깃이고, 타깃끼리 target_link_libraries로 의존을 맺습니다. ProjectE의 각 모듈은 하나의 타깃입니다.

    # Core 모듈: 플랫폼 추상화(창/입력), 로그, 타이머, 애플리케이션 루프
file(GLOB_RECURSE CORE_SOURCES CONFIGURE_DEPENDS
    "${CMAKE_CURRENT_SOURCE_DIR}/*.h"
    "${CMAKE_CURRENT_SOURCE_DIR}/*.cpp")

add_library(ECore ${E_ENGINE_MODULE_TYPE} ${CORE_SOURCES})
add_library(ProjectE::Core ALIAS ECore)

# include 경로는 모듈 루트(Engine/Source) 기준: #include "Core/Log.h"
target_include_directories(ECore PUBLIC "${CMAKE_CURRENT_SOURCE_DIR}/..")
target_link_libraries(ECore PRIVATE ThirdParty::nlohmann_json)

e_set_engine_module_defaults(ECore)

    여기서 눈여겨볼 점이 셋 있습니다.

    1. include 경로를 모듈 루트 기준으로 둡니다. 그래서 어디서든 #include "Core/Log.h", #include "RHI/D3D12/D3D12RHI.h"처럼 "어느 모듈의 무엇"인지 드러나게 씁니다.
    2. PUBLIC과 PRIVATE을 구분합니다. JSON 라이브러리는 Core 내부에서만 쓰므로 PRIVATE — Core를 쓰는 쪽에는 전파되지 않습니다. 의존을 최소한으로 퍼뜨리는 습관입니다.
    3. 모든 자체 타깃에 공통 설정 함수 e_set_*_defaults를 부릅니다. 바로 아래에서 봅니다.

    경고 = 에러

    function(e_set_target_defaults TargetName FolderName)
    set_target_properties(${TargetName} PROPERTIES FOLDER "${FolderName}")
    target_compile_options(${TargetName} PRIVATE /W4 /WX) # 경고 레벨 4 + 경고 = 에러 (자체 타깃만, 서드파티는 /W0)
    ...
endfunction()

    /W4는 MSVC의 높은 경고 수준이고, /WX는 "경고가 하나라도 있으면 빌드 실패"입니다. 처음엔 귀찮아 보이지만, 사용하지 않는 변수, 부호 있는/없는 정수 비교, 암시적 축소 변환 같은 경고는 실제 버그의 씨앗인 경우가 많습니다. 경고가 쌓이기 시작하면 진짜 중요한 경고가 묻힙니다. 그래서 이 프로젝트는 "경고를 끄지 말고 원인을 고친다"를 규칙으로 둡니다.

    실제로 겪은 일 처음엔 /W4를 전역 옵션(add_compile_options)에 넣었습니다. 그러자 서드파티 라이브러리에 걸린 /W0(경고 끔)과 충돌해, 파일마다 "D9025: '/W4'을(를) '/W0'(으)로 재정의" 경고가 쏟아졌습니다. 그래서 경고 수준은 자체 타깃에만 함수로 걸도록 바꿨습니다. 전역 옵션에는 모두에게 공통인 것(/utf-8, /permissive- 등)만 둡니다.

    전역 컴파일 옵션과 정의

    add_compile_options(
    /permissive-     # 표준 준수 모드
    /utf-8           # 소스/실행 문자 집합 UTF-8 (한글 주석·로그)
    /Zc:preprocessor # 표준 준수 전처리기 (__VA_OPT__ 지원)
    /EHsc
    /MP              # 병렬 컴파일
)
add_compile_definitions(
    UNICODE _UNICODE
    NOMINMAX            # Windows.h의 min/max 매크로가 std::min을 망가뜨리지 않게
    WIN32_LEAN_AND_MEAN
    $<IF:$<CONFIG:Debug>,E_DEBUG=1,E_DEBUG=0>
)

    /utf-8은 한글 주석과 로그 때문에 필수입니다. 이것이 없으면 MSVC는 소스를 시스템 코드 페이지(한국어 Windows는 CP949)로 읽어 한글이 깨집니다. E_DEBUG는 디버그 전용 코드를 #if E_DEBUG로 감싸기 위한 매크로입니다.

    핵심 개념로그와 어설트 — 엔진의 눈과 경보기

    게임은 1초에 60번 수많은 일을 합니다. 무엇이 잘못됐는지 알려면 기록이 필요하고, "절대 일어나면 안 되는 일"이 일어났을 때 즉시 멈추는 경보기가 필요합니다.

    enum class ELogVerbosity : uint8
{
	Fatal = 0, // 출력 후 프로세스 중단
	Error,
	Warning,
	Display,   // 사용자에게 보여줄 주요 진행 상황
	Log,       // 일반 로그
	Verbose,   // 상세 디버깅용
};

// 사용 예: E_LOG(LogCore, Display, "창 생성 완료: {}x{}", Width, Height);
#define E_LOG(CategoryName, Verbosity, Format, ...)                                              \
	do                                                                                           \
	{                                                                                            \
		if (FLog::ShouldLog(CategoryName, ELogVerbosity::Verbosity))                              \
		{                                                                                        \
			FLog::Write(CategoryName, ELogVerbosity::Verbosity,                                  \
			            std::format(Format __VA_OPT__(,) __VA_ARGS__));                          \
		}                                                                                        \
	} while (0)

    왜 그냥 printf를 쓰지 않고 매크로를 만들었을까요?

    • 카테고리와 상세 수준: LogRenderer, LogPhysics처럼 출처를 붙이고, 카테고리마다 "Verbose는 끄기" 같은 걸러내기를 할 수 있습니다.
    • 걸러질 로그는 문자열을 만들지도 않는다: ShouldLog를 먼저 확인하고, 통과할 때만 std::format을 실행합니다. 매크로이기 때문에 가능한 일입니다 — 함수였다면 인자(포맷된 문자열)가 호출 전에 이미 만들어집니다.
    • std::format 문법: {} 자리표시자는 타입 안전합니다. printf의 %d에 문자열을 넘겨 크래시 나는 종류의 실수가 컴파일 타임에 잡힙니다.
    • 출력 위치를 한곳에서: 콘솔, Visual Studio 출력 창, 로그 파일(<Saved>/Logs/), 에디터의 출력 로그 패널이 모두 이 한 함수에서 나옵니다.
    do { ... } while (0)는 왜? 여러 문장짜리 매크로를 if (x) E_LOG(...); else ...처럼 써도 하나의 문장으로 동작하게 하는 C/C++의 오래된 관용구입니다. 중괄호만 쓰면 뒤의 세미콜론 때문에 else가 짝을 잃습니다.

    어설트는 "이 조건은 반드시 참이어야 한다"를 코드에 적는 방법입니다.

    // 조건 검증. 실패 시 Fatal 로그 후 중단. 모든 빌드 구성에서 활성화
#define E_CHECK(Expression)                                                                 \
	do                                                                                      \
	{                                                                                       \
		if (!(Expression))                                                                  \
		{                                                                                   \
			E_LOG(LogCore, Fatal, "검증 실패: {} ({}:{})", #Expression, __FILE__, __LINE__); \
		}                                                                                   \
	} while (0)

    #Expression은 조건식을 문자열로 바꾸는 전처리기 기능이라, 실패하면 "검증 실패: Index < Count (Scene.cpp:120)"처럼 정확히 무엇이 어디서 깨졌는지 남습니다. 잘못된 상태로 계속 달리면 엉뚱한 곳에서 원인 모를 크래시가 납니다. 문제가 생긴 그 자리에서 멈추는 것이 디버깅 시간을 가장 크게 줄입니다.

    어설트와 오류 처리의 구분 파일이 없거나 GPU가 기능을 지원하지 않는 것은 "일어날 수 있는 일"이므로 오류를 반환하고 처리합니다(예: 초기화 경로의 E_D3D_VERIFY는 Error 로그 후 return false). 반대로 "배열 인덱스가 범위 밖" 같은 것은 프로그래머의 실수이므로 E_CHECK로 즉시 멈춥니다.

    핵심 개념Win32 창과 메시지 루프

    Windows에서 창은 운영체제가 관리하는 객체입니다. 사용자가 키를 누르거나, 창 크기를 바꾸거나, 닫기 버튼을 누르면 운영체제는 그 창에 메시지(WM_KEYDOWN, WM_SIZE, WM_CLOSE …)를 보냅니다. 프로그램은 메시지 대기열을 꺼내 처리하고, 처리 함수를 윈도우 프로시저(WndProc)라고 부릅니다.

    void FWindow::PumpMessages()
{
	MSG Message{};
	while (PeekMessageW(&Message, nullptr, 0, 0, PM_REMOVE))
	{
		TranslateMessage(&Message);
		DispatchMessageW(&Message); // → FWindow::WndProc 호출
	}
}

    메모장 같은 일반 앱은 GetMessage로 메시지가 올 때까지 잠듭니다. CPU를 쓰지 않으니 좋습니다. 하지만 게임은 아무도 키를 누르지 않아도 구름이 흐르고 적이 움직여야 하므로, PeekMessage로 쌓인 메시지만 처리하고 바로 돌아와 프레임을 진행합니다.

    규칙: 공개 헤더에 Windows.h를 넣지 않는다 Windows.h는 거대하고, min/max, CreateWindow 같은 매크로를 잔뜩 정의해 다른 코드를 망가뜨립니다. 그래서 Window.h는 창 핸들을 void* 같은 중립 타입으로 들고, Windows 헤더는 플랫폼 .cpp에서만 Core/Platform/WindowsHeaders.h로 포함합니다. 위 코드에서 WndProc의 인자 타입이 HWND, WPARAM 대신 uint32, uint64 같은 엔진 타입인 이유도 이것입니다.

    핵심 개념입력: 상태와 엣지

    "점프는 스페이스를 누른 순간 한 번", "달리기는 시프트를 누르고 있는 동안". 게임 입력에는 두 종류의 질문이 있습니다. 그래서 FInput은 키마다 이번 프레임과 지난 프레임의 상태를 들고, 그 차이로 엣지를 계산합니다.

    bool IsKeyDown(EKey Key) const;      // 눌려 있음
bool IsKeyPressed(EKey Key) const;   // 이번 프레임에 눌림
bool IsKeyReleased(EKey Key) const;  // 이번 프레임에 떼어짐
int32 GetMouseDeltaX() const { return MouseX - PrevMouseX; }
float GetLookDeltaX() const;          // 원시 마우스(WM_INPUT) 시점 회전량 — 21강

    이 단순한 구조는 나중에 크게 자랍니다. 24강에서는 키 대신 "점프", "이동" 같은 액션을 읽도록 한 층을 더 얹고, 44강에서는 UI가 입력을 가져갔을 때 게임에 "빈 입력"을 주는 입력 모드를 만듭니다. 하지만 바닥에는 항상 이 Down/Pressed/Released가 있습니다.

    핵심 개념시간 재기

    // 프레임 단위 고해상도 타이머
class FTimer
{
public:
	void Tick(); // 프레임마다 한 번 호출. 델타/누적 시간 갱신
	// 고정 델타 (> 0이면 Tick이 실제 경과 대신 이 값을 쓴다 — 자동 검증을 재현 가능하게)
	void SetFixedDelta(float Seconds);
	float  GetDeltaSeconds() const;
	double GetTotalSeconds() const;
private:
	using FClock = std::chrono::steady_clock;
	...
};

    두 가지 설계 포인트가 있습니다. 하나는 steady_clock을 쓴다는 것입니다. 시스템 시계(system_clock)는 사용자가 시간을 바꾸거나 동기화되면 거꾸로 갈 수도 있지만, steady_clock은 항상 앞으로만 갑니다. 다른 하나는 고정 델타입니다. 자동 테스트에서 스크린샷을 비교하려면 실행할 때마다 같은 화면이 나와야 하는데, 실제 시간은 매번 조금씩 다릅니다. --fixed-delta를 주면 "한 프레임 = 정확히 1/60초"로 고정되어 결과가 재현됩니다. 이 "결정성" 이야기는 65강에서 다시 다룹니다.

    ProjectE에서는FApplication — 모든 실행 파일의 공통 루프

    창, 입력, 타이머를 모아 0강의 게임 루프를 실제로 돌리는 것이 FApplication입니다. 에디터, 런타임, Sandbox, 서버가 모두 이 클래스를 상속하고, 바뀌는 부분만 가상 함수로 재정의합니다(템플릿 메서드 패턴).

    class FApplication
{
public:
	int Run(); // 초기화 → 메인 루프 → 종료. 프로세스 종료 코드를 반환
protected:
	virtual bool OnInit() { return true; }
	virtual void OnUpdate(float DeltaSeconds) {}
	virtual void OnRender() {}
	virtual void OnResize(uint32 Width, uint32 Height) {}
	virtual void OnShutdown() {}
};
    while (!bExitRequested)
{
	Window.PumpMessages();                         // ① 운영체제 메시지 → 입력 상태
	if (bExitRequested) break;
	Timer.Tick();                                  // ② dt 계산
	FFrameTime::Advance(Timer.GetDeltaSeconds());
	OnUpdate(Timer.GetDeltaSeconds());             // ③ 세계 갱신 (파생 클래스)

	if (Window.IsMinimized())
	{
		Sleep(10); // 최소화 상태에서는 렌더링을 건너뛰고 CPU 점유를 낮춘다
	}
	else
	{
		OnRender();                                // ④ 그리기 (파생 클래스)
		++FrameIndex;
	}
	Input.EndFrame();                              // ⑤ "이번 프레임" 입력을 "지난 프레임"으로
}

    0강의 그림과 그대로 대응됩니다. 최소화 처리도 눈여겨보세요. 창이 최소화되면 스왑체인(화면 버퍼) 크기가 0이 되어 그리기가 실패할 수 있고, 보이지도 않는데 GPU를 돌릴 이유도 없습니다. Phase 0의 DoD에 "리사이즈·최소화에서 크래시 없음"이 들어간 이유입니다.

    class FSandboxApp final : public FApplication
{
protected:
	bool OnInit() override
	{
		Rhi = std::make_unique<FD3D12RHI>();   // 2강: DirectX 12 초기화
		if (!Rhi->Init(RhiDesc)) { return false; }
		...
	}
};

    Run()은 루프 외에도 공통 일을 많이 합니다. 로그 파일 열기, 프로젝트 경로 찾기(FPaths::Initialize), 명령줄 인자 처리, 크래시 덤프 위치 설정 등입니다. 특히 --exit-after N, --screenshot 경로 같은 자동 검증 인자를 여기서 한 번에 처리하므로, 에디터든 런타임이든 "N프레임 돌리고 스크린샷 찍고 종료"를 똑같이 할 수 있습니다. 이 자동 검증이 이후 모든 렌더링 작업의 안전망이 됩니다.

    함정과 교훈

    • 한글과 인코딩: C++ 소스는 UTF-8(BOM 없음) + /utf-8로 해결됐지만, 셰이더(.hlsl)와 PowerShell 스크립트(.ps1)는 반대로 BOM이 반드시 있어야 했습니다. Windows SDK에 들어 있는 DXC 1.6과 PowerShell 5.1이 BOM 없는 UTF-8 한글을 잘못 읽기 때문입니다. 그래서 .editorconfig에 파일 종류별 인코딩을 적어 두었습니다. 도구마다 기본값이 다르다는 것을 일찍 알아 두면 시간을 많이 아낍니다.
    • Windows 매크로 오염: NOMINMAX를 정의하지 않으면 std::max(a, b)가 max 매크로로 치환되어 이해하기 힘든 컴파일 에러가 납니다.
    • "동작한다"의 기준: Phase 0 DoD에는 "디버그 레이어 에러 없음", "종료 시 라이브 오브젝트 누수 없음"이 있습니다. 화면이 잘 나와도 GPU 객체를 해제하지 않고 종료하면 실패입니다. 기준을 처음부터 엄격하게 잡아 두면 나중에 원인 모를 누수를 쫓을 일이 줄어듭니다.
    정리
    • CMake 타깃 = 모듈. include는 모듈 루트 기준, 의존은 PRIVATE으로 좁게, 경고는 에러로.
    • E_LOG는 카테고리·상세 수준·지연 포맷을, E_CHECK는 "그 자리에서 멈추기"를 제공한다.
    • 게임은 PeekMessage로 메시지를 비우고 바로 프레임을 진행한다.
    • 입력은 Down(상태)과 Pressed/Released(엣지)로 나누고, 프레임 끝에 상태를 넘긴다.
    • FApplication이 루프를 소유하고, 각 실행 파일은 OnInit/OnUpdate/OnRender만 채운다.

    생각해 볼 문제

    Q1. E_LOG를 매크로가 아니라 일반 함수 Log(Category, Verbosity, std::string)로 만들면 성능상 무엇이 달라질까요? 함수 인자는 호출 전에 평가되므로, Verbose 로그가 꺼져 있어도 매번 std::format으로 문자열을 만들고 버리게 됩니다. 매 프레임 불리는 곳이라면 무시할 수 없는 비용입니다. 매크로는 ShouldLog 확인을 문자열 생성보다 앞에 둘 수 있습니다.
    Q2. 키를 아주 빨리 눌렀다 떼서, 한 프레임 안에 WM_KEYDOWN과 WM_KEYUP이 모두 왔습니다. 위 구조에서 IsKeyPressed는 어떻게 될까요? 메시지 처리가 끝난 시점의 상태만 보면 "안 눌림"이므로 그 입력을 놓칠 수 있습니다. 이런 경우를 잡으려면 "이번 프레임에 눌린 적이 있음" 플래그를 별도로 기록해야 합니다. 60fps에서 한 프레임(16ms) 안에 눌렀다 떼는 일은 드물지만, 프레임이 크게 끊길 때는 실제로 생길 수 있는 문제입니다.
    Q3. 전용 서버는 창이 없습니다. 같은 FApplication을 어떻게 쓸까요? FApplicationDesc::bHeadless를 켜면 Run()이 창 대신 고정 간격 틱 루프(RunHeadlessLoop)를 돕니다. OnRender/OnResize는 불리지 않고, --exit-after는 프레임 대신 틱 수로 셉니다. 루프의 "모양"만 바꾸고 나머지(로그, 명령줄, 크래시 처리)는 공유합니다.
