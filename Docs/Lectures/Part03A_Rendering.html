    사실적인 화면 — 렌더링 심화 (전반)

    삼각형을 그릴 줄 알게 되었으니 이제 "그럴듯하게" 그릴 차례입니다. 렌더러의 뼈대에서 출발해 물리 기반 셰이딩, HDR과 톤매핑, 그림자, 환경광, 수많은 광원, 화면 공간 효과를 차례로 쌓고, 마지막으로 이 모든 것이 움직일 때 화면이 지글거리지 않게 만드는 방법까지 다룹니다.

    왜 필요한가"씬을 그려라"와 "GPU에 명령을 보내라" 사이

    1·2부에서 삼각형, 큐브, 텍스처를 그렸습니다. 그때는 그릴 물체가 몇 개뿐이라 "물체마다 상수 올리고 그리기"를 그냥 순서대로 반복해도 충분했습니다. 하지만 실제 게임의 씬에는 수천~수만 개의 메시가 있고, 그중 상당수는 카메라 뒤에 있거나 화면 밖에 있습니다. 또 GPU는 "같은 셰이더·같은 텍스처로 연속해서 그리기"를 좋아하고, 셰이더나 텍스처를 바꿀 때마다(상태 변경) 비용을 치릅니다.

    그래서 씬(ECS의 엔티티와 컴포넌트)과 GPU 명령 사이에 렌더러라는 번역 층을 둡니다. 렌더러는 씬을 직접 그리지 않습니다. 씬을 보고 "이번 프레임에 그려야 할 것의 목록"을 만들고, 필요 없는 것을 버리고, GPU가 좋아하는 순서로 바꾼 다음에야 명령을 기록합니다. 이 강의는 Phase 3에서 처음 만든 이 뼈대와, 그 뼈대가 지금 어떤 모습으로 자랐는지를 봅니다. 3부의 나머지 강의(PBR, 그림자, IBL, 화면 공간 효과…)는 모두 이 뼈대 위에 패스를 하나씩 끼워 넣는 이야기입니다.

    핵심 개념수집 → 컬링 → 정렬 → 드로우

    각 단계가 무엇을 하는지 정리해 봅시다.

    1. 수집(Gather): ECS 뷰로 "트랜스폼과 메시를 가진 엔티티"를 돌며, 그리기에 필요한 정보(어떤 메시, 어떤 머티리얼, 월드 행렬, 월드 공간 경계 상자)를 평평한 배열에 모읍니다. 씬 구조(계층, 컴포넌트 저장 방식)를 렌더러 뒤쪽 단계가 몰라도 되게 하는 경계입니다.
    2. 컬링(Culling): 카메라에 보이지 않는 항목을 버립니다. 가장 기본은 프러스텀 컬링(시야 사각뿔 밖 버리기)이고, 더 나아가면 가려진 것 버리기(오클루전 컬링), 너무 작은 것 버리기(화면 크기 컬링)가 있습니다.
    3. 정렬(Sorting): 남은 항목을 "상태가 같은 것끼리 붙도록", 그리고 같은 상태 안에서는 "가까운 것부터" 늘어놓습니다.
    4. 드로우(Draw): 정렬된 순서대로 상태를 설정하고 그리기 명령을 기록합니다. 상태가 바뀔 때만 바꾸고, 같은 메시·머티리얼이 연속이면 한 번의 인스턴싱 드로우로 묶습니다.
    비유 택배 배송과 비슷합니다. 접수된 상자를 모으고(수집), 이번 경로에 해당 없는 상자를 빼고(컬링), 같은 동네끼리 묶어 가까운 집부터 돌도록 순서를 정한 뒤(정렬), 트럭을 출발시킵니다(드로우). 순서를 정하는 데 드는 시간보다 동네를 왔다 갔다 하지 않아서 아끼는 시간이 훨씬 큽니다.

    핵심 개념프러스텀 컬링 — 평면 6개와 p-vertex

    원근 카메라가 볼 수 있는 공간은 꼭대기가 잘린 사각뿔, 곧 프러스텀(frustum)입니다. 이 공간은 평면 6개(왼쪽·오른쪽·아래·위·근평면·원평면)로 둘러싸여 있고, 어떤 점이 6개 평면 모두의 "안쪽"에 있으면 보이는 점입니다.

    평면은 뷰-투영 행렬에서 바로 나온다

    평면을 카메라 위치·시야각으로 직접 계산할 수도 있지만, 더 간단한 방법이 있습니다(Gribb–Hartmann 방식). 월드 점 p에 뷰-투영 행렬을 곱하면 클립 좌표 (x, y, z, w)가 나오고, 클립 공간에서 보이는 조건은 -w ≤ x ≤ w, -w ≤ y ≤ w, 0 ≤ z ≤ w입니다(ProjectE는 깊이 범위 [0, 1]). 그런데 ProjectE의 행렬은 행벡터 규약(v · M)이라 x = p · (M의 0번 열)입니다. 그러니 "x + w ≥ 0"은 "p · (열0 + 열3) ≥ 0"이라는 평면 방정식 그 자체가 됩니다.

    // 행벡터 규약 ViewProjection에서 추출. 클립 공간: -w<=x<=w, -w<=y<=w, 0<=z<=w
static FFrustum FromViewProjection(const FMatrix4x4& ViewProjection)
{
	...
	Frustum.Planes[Left]   = FPlane(C3.Normal + C0.Normal, C3.D + C0.D).GetNormalized(); // x + w >= 0
	Frustum.Planes[Right]  = FPlane(C3.Normal - C0.Normal, C3.D - C0.D).GetNormalized(); // w - x >= 0
	Frustum.Planes[Bottom] = FPlane(C3.Normal + C1.Normal, C3.D + C1.D).GetNormalized(); // y + w >= 0
	Frustum.Planes[Top]    = FPlane(C3.Normal - C1.Normal, C3.D - C1.D).GetNormalized(); // w - y >= 0
	Frustum.Planes[Near]   = FPlane(C2.Normal, C2.D).GetNormalized();                    // z >= 0
	Frustum.Planes[Far]    = FPlane(C3.Normal - C2.Normal, C3.D - C2.D).GetNormalized(); // w - z >= 0
	return Frustum;
}

    이 방식의 장점은 투영의 종류를 가리지 않는다는 것입니다. 원근이든 직교든, 그림자용 광원 행렬이든 "뷰-투영 행렬만 있으면" 같은 함수로 평면을 얻습니다. 실제로 ProjectE는 같은 FFrustum을 메인 카메라, 그림자 캐스케이드, 점광원 큐브 면 컬링에 모두 씁니다.

    AABB 판정: 꼭짓점 8개를 다 볼 필요는 없다

    물체 하나는 AABB(Axis-Aligned Bounding Box, 축 정렬 경계 상자 — 최소점·최대점 두 개로 표현하는 상자)로 근사합니다. 메시는 로컬 AABB를 미리 갖고 있고, 월드 행렬로 꼭짓점 8개를 변환해 다시 감싸면 월드 AABB가 됩니다(회전하면 조금 커지지만 항상 물체를 포함합니다).

    상자가 프러스텀 밖인지 알려면, 평면 하나에 대해 "상자에서 평면 안쪽 방향으로 가장 멀리 나간 꼭짓점"만 보면 됩니다. 이 꼭짓점을 p-vertex(positive vertex)라고 부릅니다. 평면 법선의 x가 양수면 상자의 max.x, 음수면 min.x를 고르는 식으로 축마다 하나씩 고르면 됩니다. p-vertex조차 평면 바깥이면 상자 전체가 바깥이므로 즉시 버립니다.

    // AABB가 프러스텀과 겹치는지 (보수적: 모서리 근처에서 드물게 참을 반환할 수 있음)
constexpr bool Intersects(const FBox& Box) const
{
	for (const FPlane& Plane : Planes)
	{
		// 평면 법선 방향으로 가장 먼 꼭짓점(p-vertex)이 바깥이면 상자 전체가 바깥
		const FVector3 PositiveVertex(Plane.Normal.X >= 0.0f ? Box.Max.X : Box.Min.X,
		                              Plane.Normal.Y >= 0.0f ? Box.Max.Y : Box.Min.Y,
		                              Plane.Normal.Z >= 0.0f ? Box.Max.Z : Box.Min.Z);
		if (Plane.DistanceTo(PositiveVertex) < 0.0f)
		{
			return false;
		}
	}
	return true;
}

    평면 6개 × (점 하나 고르기 + 내적 하나)뿐이라 아주 쌉니다. 꼭짓점 8개를 모두 평면마다 검사하는 방법(48번의 내적)보다 8배 가깝게 빠르고, 결과도 같습니다. 그림의 D처럼 "평면마다 따로 보면 통과지만 실제로는 바깥"인 경우가 남는데, 이것은 렌더링을 틀리게 만들지 않고 약간의 헛일만 시키므로 대부분의 엔진이 그대로 받아들입니다.

    핵심 개념정렬 키 — 무엇부터 같게 묶을 것인가

    GPU 그리기에서 비용이 큰 상태 변경은 대략 이런 순서입니다: 파이프라인 상태(PSO, 셰이더 조합) > 머티리얼(텍스처 테이블·상수) > 메시(정점·인덱스 버퍼). 그래서 정렬은 비싼 것부터 같게 묶습니다. 같은 상태 안에서는 가까운 것부터 그립니다. 가까운 물체가 먼저 깊이 버퍼를 채우면, 뒤에 그리는 가려진 픽셀은 픽셀 셰이더를 돌리기 전에 깊이 테스트로 버려집니다(초기 깊이 기각, early-Z).

    이 우선순위를 여러 필드의 비교로 짜도 되지만, 엔진은 흔히 필드들을 정수 하나에 비트로 이어 붙인 정렬 키를 만듭니다. 그러면 "키가 작은 순"이라는 정수 비교 한 번이 곧 "PSO → 머티리얼 → 메시 → LOD" 사전식 비교가 되고, 키가 같다는 것은 곧 "한 번의 인스턴싱 드로우로 묶을 수 있다"는 뜻이 됩니다.

    // 일반 키: PSO 종류(3비트) | 머티리얼 슬롯(24비트) | 메시 슬롯(24비트) | LOD(4비트).
// 슬롯 번호는 핸들 Index (같은 프레임 안에서 유일)
constexpr uint64 MakeKey(uint32 Pipeline, uint32 Material, uint32 Mesh, uint32 Lod)
{
	return (static_cast<uint64>(Pipeline & 0x7u) << 52) | (static_cast<uint64>(Material & 0xFFFFFFu) << 28) |
	       (static_cast<uint64>(Mesh & 0xFFFFFFu) << 4) | static_cast<uint64>(Lod & 0xFu);
}
    왜 포인터 대신 "슬롯 번호"인가 머티리얼·메시는 3부 이전에 본 세대 핸들(THandle)로 참조합니다. 핸들의 Index는 리소스 풀 안의 자리 번호라 작은 정수이고, 같은 프레임 안에서는 유일합니다. 포인터 주소를 키에 넣으면 64비트를 통째로 써야 하고 실행할 때마다 순서가 달라지지만, 슬롯 번호는 24비트에 들어가고 결정적입니다.

    반투명 물체는 예외입니다. 반투명은 뒤에 있는 것을 먼저 그려야 섞임(블렌딩)이 맞으므로 먼 것부터 그리고, 키가 같아도 정렬 결과에서 바로 이웃한 것끼리만 묶습니다(BuildBackToFront). 머티리얼 강의(21강)에서 다시 봅니다.

    Q1. 정렬 키에서 머티리얼을 메시보다 상위 비트에 둔 이유는? 반대로 두면 어떤 장면에서 손해일까요? 머티리얼 변경(텍스처 테이블·상수 바인딩, 때로는 PSO까지)이 메시 변경(정점·인덱스 버퍼 바인딩)보다 비싸기 때문입니다. 메시를 상위에 두면 "같은 메시에 머티리얼만 다른 물체"(예: 색만 다른 상자 수백 개)가 메시별로 모였다가 머티리얼이 번갈아 바뀌어 머티리얼 바인딩이 많아집니다. 물론 둘 다 같은 물체끼리는 묶이므로 인스턴싱 묶음 수는 같습니다 — 차이는 묶음과 묶음 사이의 상태 변경 비용입니다.
    Q2. 월드 AABB를 "로컬 AABB의 꼭짓점 8개를 변환해 다시 감싸서" 만들면 회전한 물체는 경계가 커집니다. 컬링 결과에 어떤 영향이 있나요? 경계가 실제보다 커지므로 "보이지 않는데 그리는" 경우가 조금 늘어날 뿐, "보이는데 버리는" 경우는 생기지 않습니다. 컬링은 항상 보수적(포함하는 쪽)이어야 하므로 이 방향의 오차는 허용됩니다. 반대로 경계를 너무 작게 잡으면(예: 애니메이션으로 뼈가 바인드 포즈 밖으로 나가는 스킨 메시) 화면 가장자리에서 물체가 갑자기 사라지는 버그가 됩니다.
    Q3. 병렬 컬링에서 각 스레드가 하나의 공유 배열에 push_back하지 않고 조각마다 따로 목록을 만든 뒤 이어 붙이는 이유는? 공유 배열에 동시에 넣으려면 잠금(또는 원자 연산)이 필요해 느려지고, 무엇보다 넣는 순서가 스레드 실행 순서에 따라 달라집니다. 정렬 키가 같고 깊이도 같은 항목의 상대 순서가 실행마다 바뀌면 그리기 순서가 달라져 결과가 비트 단위로 달라질 수 있습니다. 조각별 목록을 조각 번호 순으로 이어 붙이면 잠금이 없고 결과도 순차 실행과 같습니다.

    왜 필요한가"보기 좋게 맞춘" 조명의 한계

    Phase 2에서 큐브를 비춘 조명은 Blinn-Phong이었습니다. 확산광은 max(n·l, 0), 하이라이트는 (n·h)지수로 계산하는, 수십 년 된 경험적 모델입니다. 간단하고 빠르지만 문제가 있습니다.

    • 에너지가 보존되지 않습니다. 하이라이트 지수를 바꾸면 하이라이트가 좁아지기만 할 뿐 밝기가 그대로라, 거친 면이 빛을 "만들어 내기도" 하고 "잃기도" 합니다.
    • 재질 값이 조명에 묶입니다. 한낮 장면에서 맞춘 금속이 실내 장면에서는 플라스틱처럼 보입니다. 아티스트는 장면마다 값을 다시 만져야 합니다.
    • 스치는 각도의 반사(프레넬)가 없습니다. 물웅덩이를 낮은 각도로 보면 거울처럼 하늘이 비치는 현상이 표현되지 않습니다.

    물리 기반 렌더링(PBR, Physically Based Rendering)은 재질을 "이 표면은 빛을 얼마나, 어느 방향으로 돌려보내는가"라는 물리량으로 기술합니다. 그러면 같은 재질 값이 어떤 조명 아래서도 일관되게 보이고, glTF 같은 표준 형식의 에셋을 그대로 가져와도 만든 사람이 의도한 모습이 나옵니다. Phase 6의 DoD 첫 줄이 "DamagedHelmet이 PBR(금속/거칠기/노멀/AO/발광)로 올바르게 보인다"였던 이유입니다.

    핵심 개념셰이더가 계산하는 "색"의 정체

    먼저 단어 몇 개를 정합니다.

    • 복사 휘도(radiance) L: 한 점에서 한 방향으로 나가는(또는 들어오는) 빛의 세기. 카메라 픽셀 하나가 받는 것이 바로 이것이고, 픽셀 셰이더의 출력값은 그 픽셀 방향의 복사 휘도입니다.
    • 조도(irradiance) E: 표면 한 점에 모든 방향에서 쏟아지는 빛의 총량. 광원 방향이 비스듬할수록 같은 빛이 넓은 면적에 퍼지므로 n·l(코사인)이 곱해집니다.
    • BRDF f(l, v): "l 방향에서 받은 조도 중 얼마가 v 방향 복사 휘도로 나가는가"의 비율. 재질의 본질이 이 함수 하나에 담깁니다.

    그러면 광원 하나(방향광 또는 점광원)에 대한 셰이딩은 이 한 줄입니다.

    광원 하나의 셰이딩 식 Lout(v) = f(l, v) × Llight × (n·l)
    — 광원 여러 개면 더하고, 하늘처럼 모든 방향에서 오는 빛이면 반구 전체에 대해 적분합니다(17강).

    BRDF는 보통 두 부분의 합입니다. 표면 안으로 들어갔다가 사방으로 흩어져 나오는 확산(diffuse)과, 표면에서 바로 튕겨 나가는 정반사(specular)입니다.

    확산: Lambert와 π

    이상적인 확산면은 들어온 빛을 모든 방향으로 똑같은 휘도로 내보냅니다. 이때 BRDF는 상수 albedo / π입니다. 왜 π로 나눌까요? 나가는 휘도를 반구 전체에 대해 코사인 가중으로 적분하면 ∫cosθ dω = π가 나옵니다. 즉 π로 나눠야 "나간 빛의 총량 = albedo × 들어온 빛"이 되어, albedo가 1이어도 빛이 늘어나지 않습니다. 이것이 에너지 보존의 가장 단순한 형태입니다.

    핵심 개념미세면 이론과 Cook-Torrance

    현미경으로 보면 매끈해 보이는 표면도 아주 작은 거울 조각(미세면, microfacet)들이 제각각 기울어진 채 모여 있습니다. 각 조각은 완벽한 거울이라, 빛을 l에서 v로 반사하려면 조각의 법선이 정확히 하프 벡터 h = normalize(l + v)를 향해야 합니다. 그러니 "v 방향으로 얼마나 반사되는가"는 "법선이 h인 조각이 얼마나 많은가"의 문제가 됩니다.

    이 생각을 식으로 옮긴 것이 Cook-Torrance 정반사 BRDF입니다.

    Cook-Torrance 정반사 fspec(l, v) = D(h) · G(l, v) · F(v, h) / (4 · (n·l) · (n·v))
    항의미ProjectE가 쓰는 모델
    D 법선 분포법선이 정확히 h를 향하는 미세면의 비율(밀도). 하이라이트의 모양과 크기를 정한다GGX (Trowbridge-Reitz)
    G 기하 감쇠그 미세면이 이웃 조각에 가려 빛을 못 받거나(그림자), 반사한 빛이 가려 카메라에 못 오는(가림) 비율Smith GGX, height-correlated (Heitz 2014)
    F 프레넬각도에 따라 반사되는 비율. 정면에서는 F0, 스칠수록 1에 가까워진다Schlick 근사

    D — GGX

    α를 거칠기의 제곱(α = roughness²)으로 둘 때 GGX 분포는 D = α² / (π · ((n·h)²(α² − 1) + 1)²)입니다. α가 작으면 n·h ≈ 1 근처에 뾰족하게 몰리고(작은 하이라이트), 크면 넓게 퍼집니다. GGX가 인기 있는 이유는 피크 주변이 빨리 떨어지면서도 "꼬리"가 길어, 실제 금속 하이라이트 둘레의 은은한 번짐을 잘 흉내 내기 때문입니다. 아티스트가 다루는 값(지각적 거칠기)을 제곱해서 α로 쓰는 것은, 그래야 슬라이더를 움직일 때 겉보기 변화가 고르게 느껴지기 때문입니다.

    G — Smith, 높이 상관

    G는 그림자(빛 쪽)와 가림(시선 쪽) 두 효과의 곱입니다. 단순한 Smith 모델은 두 효과를 독립으로 보고 곱하지만, 실제로는 높이 솟은 미세면이 두 방향 모두에 잘 보이므로 둘은 상관이 있습니다. height-correlated 버전은 이를 반영합니다. ProjectE는 분모 4(n·l)(n·v)까지 미리 합친 가시성 항 V = G / (4(n·l)(n·v))를 계산해 나눗셈을 줄입니다.

    F — Schlick 프레넬

    정면(입사각 0°)에서의 반사율을 F0라 하면 Schlick 근사는 F = F0 + (1 − F0)(1 − v·h)5입니다. 대부분의 비금속(유전체)은 F0가 약 0.04(4%)로 거의 같고, 금속은 F0가 크고 색이 있습니다(금이 노란 이유).

    확산과 정반사를 합치기 — 에너지 보존

    표면에서 F만큼이 바로 반사되었다면, 안으로 들어가 확산될 수 있는 빛은 남은 (1 − F)뿐입니다. 그리고 금속은 안으로 들어간 빛을 자유 전자가 흡수해 버려 확산이 없습니다. 그래서 ProjectE의 최종 BRDF는 다음과 같습니다.

    ProjectE의 직접광 BRDF f = D · V · F + (1 − F) · (1 − metallic) · albedo / π
    Lout = f × (색 × 강도) × (n·l) 
    float3 GetF0(FSurface Surface)
{
	return lerp(float3(0.04f, 0.04f, 0.04f), Surface.Albedo, Surface.Metallic);
}

// 한 광원의 기여 (Radiance = 색 * 강도, L = 표면 → 광원)
float3 EvaluateDirectLight(FSurface Surface, float3 L, float3 Radiance)
{
	const float NdotL = saturate(dot(Surface.N, L));
	if (NdotL <= 0.0f) { return 0.0f; }

	const float3 H     = normalize(L + Surface.V);
	const float  NdotV = max(dot(Surface.N, Surface.V), 1.0e-4f);
	const float  NdotH = saturate(dot(Surface.N, H));
	const float  VdotH = saturate(dot(Surface.V, H));
	const float  Alpha = max(Surface.Roughness * Surface.Roughness, 2.0e-3f);

	const float3 F        = F_Schlick(GetF0(Surface), VdotH);
	const float3 Specular = D_GGX(NdotH, Alpha) * V_SmithGGXCorrelated(NdotV, NdotL, Alpha) * F;
	const float3 Diffuse  = (1.0f - F) * (1.0f - Surface.Metallic) * Surface.Albedo / E_PI;

	return (Diffuse + Specular) * Radiance * NdotL;
}

    NdotV를 1e-4 이상으로, α를 2e-3 이상으로 막은 것은 0으로 나누기와, 거울에 가까운 면에서 D가 무한대로 치솟는 것을 막기 위해서입니다.

    핵심 개념금속/거칠기 워크플로

    BRDF의 재료는 albedo(베이스 컬러), F0, 거칠기입니다. 그런데 F0를 아티스트가 직접 고르게 하면 "4% 근처여야 할 비금속에 30%를 넣는" 실수가 쉽습니다. 금속/거칠기(metallic/roughness) 워크플로는 입력을 세 가지로 줄여 이런 실수를 막습니다.

    • 베이스 컬러: 비금속이면 확산 색, 금속이면 반사 색(F0).
    • 금속도 0~1: 0이면 F0 = 0.04에 베이스 컬러가 확산, 1이면 F0 = 베이스 컬러에 확산 없음. 중간 값은 녹·먼지 경계처럼 섞인 픽셀에 씁니다. 위 GetF0의 lerp가 이 규칙 그대로입니다.
    • 거칠기 0~1: 미세면 분포의 폭(α = 거칠기²).

    glTF 2.0이 이 방식을 표준으로 쓰므로, ProjectE도 머티리얼 텍스처를 glTF의 다섯 슬롯과 똑같이 둡니다.

    핵심 개념sRGB와 선형 — 왜 두 가지 색공간이 필요한가

    사람의 눈은 밝기 변화에 선형적이지 않습니다. 어두운 쪽의 작은 차이는 잘 느끼고, 밝은 쪽의 같은 차이는 잘 못 느낍니다. 그래서 8비트(256단계)로 색을 저장할 때는 단계를 어두운 쪽에 촘촘히 배정하는 것이 효율적이고, 이 비선형 인코딩이 sRGB(대략 감마 2.2)입니다. 사진과 텍스처는 거의 모두 sRGB로 저장되어 있습니다.

    반면 빛의 계산은 선형이어야 맞습니다. 전등 두 개를 켜면 밝기가 두 배여야 하는데, sRGB 값 0.5 두 개를 더한 1.0은 물리적으로 두 배가 아니라 약 4.6배입니다. 그래서 규칙은 이렇습니다.

    • 색 텍스처(베이스 컬러, 발광)는 _SRGB 포맷으로 만듭니다. 그러면 GPU가 샘플링할 때 자동으로 선형으로 바꿔 줍니다(필터링도 선형 공간에서 올바르게 됩니다).
    • 데이터 텍스처(노멀, 금속·거칠기, AO)는 UNORM(선형)입니다. 이 값은 "색"이 아니라 숫자이므로 감마 변환을 하면 값이 틀어집니다.
    • 출력 렌더 타깃도 _SRGB 뷰로 씁니다. 셰이더는 선형 값을 쓰고, 하드웨어가 쓸 때 인코딩합니다.
    • CPU에서 사람이 고른 색(예: 광원 색 컴포넌트)은 sRGB로 저장하고, GPU로 보낼 때 LightMath::SrgbToLinear로 바꿉니다.
    규칙 (CLAUDE.md "색공간") 백버퍼 RTV와 색상 텍스처는 sRGB 포맷, 셰이더는 선형 공간에서 계산, 데이터 텍스처는 UNORM. 한 곳이라도 어긋나면 화면이 "물빠진 듯" 밝거나 "탄 듯" 어두워지는데, 어디서 틀렸는지 눈으로 찾기가 매우 어렵습니다.

    핵심 개념노멀 맵과 탄젠트 공간

    노멀 맵은 픽셀마다 "표면이 실제로는 이쪽을 향한다"는 작은 기울기를 저장해, 삼각형을 늘리지 않고 요철을 표현합니다. 그런데 이 기울기를 월드 방향으로 저장하면 물체가 회전하거나, 같은 텍스처를 다른 면에 붙일 때 쓸 수 없습니다. 그래서 탄젠트 공간 — 표면에 붙은 좌표계 (T: UV의 +U 방향, B: 바이탄젠트, N: 정점 법선) — 기준으로 저장합니다. 평평한 곳의 노멀 맵 값이 (0.5, 0.5, 1)인 파란색인 이유가 "탄젠트 공간에서 그냥 +Z(법선 방향)"이기 때문입니다.

    // XY만 사용하고 Z는 재구성 (BC5 노멀 맵은 RG만 저장)
float3 TangentNormal;
TangentNormal.xy = MATERIAL_SAMPLE(NormalTexture, E_MATERIAL_SAMPLER_WRAP, In.UV0).xy * 2.0f - 1.0f;
TangentNormal.z  = sqrt(saturate(1.0f - dot(TangentNormal.xy, TangentNormal.xy)));
TangentNormal.xy *= NormalScale;

float3 MaterialTangentToWorld(float3 WorldNormal, float4 WorldTangent, float3 TangentNormal)
{
	const float3 N = WorldNormal;
	const float3 T = normalize(WorldTangent.xyz - N * dot(N, WorldTangent.xyz)); // 그람-슈미트: N에 수직으로
	const float3 B = cross(N, T) * WorldTangent.w;                               // w = 손잡이(거울 UV) 부호
	return normalize(T * TangentNormal.x + B * TangentNormal.y + N * TangentNormal.z);
}

    두 가지 설계 포인트가 있습니다. 첫째, 노멀은 단위 벡터라 X, Y만 알면 Z = √(1 − X² − Y²)로 복원됩니다. 그래서 노멀 맵은 두 채널 전용 압축 BC5로 쿠킹하고, B 채널에 의존하지 않습니다. 둘째, 바이탄젠트를 저장하지 않고 cross(N, T) × w로 만듭니다. w(±1)는 UV가 좌우 반전된 면(대칭 모델에서 흔함)에서 B를 뒤집기 위한 부호입니다.

    함정과 교훈좌표계 반사와 탄젠트의 w

    glTF 탄젠트는 w를 뒤집어야 한다 glTF는 오른손 Y-up, ProjectE는 왼손 Z-up입니다. 축 하나가 반사되는 변환이라 위치·법선을 변환하면 삼각형 와인딩과 손잡이(handedness)가 바뀝니다. 그래서 glTF의 TANGENT는 FGltfLoader::ConvertTangent가 xyz를 변환할 뿐 아니라 w도 반전합니다. 이것을 빠뜨리면 노멀 맵의 요철이 Y 방향으로만 반대로 보이는데(볼록이 오목으로), 정면 조명에서는 티가 잘 나지 않아 찾기 어렵습니다. 규약은 "B = Cross(N, T) × w = 노멀 맵 +Y = UV 위쪽(−V)"으로 CLAUDE.md에 고정해 두었습니다. 탄젠트가 없는 모델은 FMeshData::ComputeTangents가 UV로 계산합니다.
    거칠기 0은 허용하지 않는다 거칠기가 0에 가까우면 D 항이 픽셀 하나 크기보다 작은 각도에 몰려, 카메라나 물체가 조금만 움직여도 하이라이트가 나타났다 사라지며 반짝입니다(스페큘러 에일리어싱). 0.045 하한은 이를 막는 실용적 타협입니다. 거울 같은 반사는 직접광 하이라이트가 아니라 환경 반사(17강)와 SSR(19강)이 담당합니다.
    정리
    • 픽셀 셰이더 출력 = 카메라 방향 복사 휘도. 광원 하나는 BRDF × 광원 휘도 × (n·l).
    • Cook-Torrance 정반사 = D(GGX 분포) · G(Smith 가림) · F(Schlick 프레넬) / 4(n·l)(n·v).
    • 에너지 보존: 확산은 (1 − F)(1 − metallic) · albedo/π.
    • 금속/거칠기: F0 = lerp(0.04, 베이스 컬러, 금속도), α = 거칠기².
    • 색 텍스처·출력은 sRGB, 데이터 텍스처는 선형, 계산은 항상 선형. 노멀 맵은 탄젠트 공간 XY + Z 복원.

    생각해 볼 문제

    Q1. 금속도 1, 베이스 컬러가 완전한 검정 (0, 0, 0)인 머티리얼은 어떻게 보일까요? 금속이므로 확산이 0이고 F0 = 베이스 컬러 = 0입니다. 하지만 Schlick 프레넬은 스치는 각도에서 1로 가므로 가장자리에만 약한 반사가 남는, 거의 검은 물체가 됩니다. 현실에 F0가 0인 금속은 없으므로, 아티스트 가이드는 보통 금속 베이스 컬러를 밝은 값(대략 0.5 이상)으로 두라고 합니다.
    Q2. 노멀 맵을 실수로 sRGB 포맷으로 만들면 어떤 현상이 생길까요? 샘플링 때 감마 해독이 적용되어 0.5(평평)가 약 0.21로 바뀝니다. × 2 − 1 후 XY가 약 −0.57이 되어 모든 픽셀의 법선이 한쪽으로 크게 기울고, 조명이 전체적으로 비뚤어집니다. 그래서 노멀은 반드시 선형(ProjectE는 BC5 UNORM)입니다.
    Q3. Lambert 확산을 albedo로 두고 π로 나누지 않으면 어떤 문제가 생기나요? 엔진들이 광원 강도에 π를 미리 곱해 두는 경우도 있는데, 그건 무엇을 위한 것일까요? π로 나누지 않으면 나가는 빛의 총량이 들어온 빛의 π배가 되어 에너지가 보존되지 않고, 확산과 정반사의 상대 비율도 틀어집니다. 광원 강도에 π를 미리 곱하는 것은 "흰 면을 정면으로 비춘 강도 1의 광원이 화면 값 1이 되게" 하려는 단위 편의로, BRDF 자체는 여전히 albedo/π입니다.

    HDR과 포스트 프로세싱

    관련 Phase: 6 (기반 + 트랙 J), 49 (HDR 디스플레이) · 살펴볼 곳: Renderer/PostProcess.h/.cpp, PostProcessMath.h, HdrDisplayMath.h, Engine/Shaders/Tonemap.hlsl, Bloom.hlsl, AutoExposure.hlsl
    이 강의를 마치면
    • 씬을 왜 0~1이 아닌 부동소수점(HDR) 타깃에 그리는지 설명할 수 있습니다.
    • 노출(EV)과 톤매핑 곡선(Reinhard, ACES 근사)이 각각 무슨 일을 하는지 구분합니다.
    • 블룸이 13탭 다운샘플·Karis 평균·텐트 업샘플 체인으로 어떻게 넓고 부드러운 번짐을 싸게 만드는지 압니다.
    • 자동 노출의 로그 휘도 히스토그램과 시간 적응, HDR 모니터 출력의 기본 개념을 이해합니다.

    왜 필요한가모니터는 태양을 표현할 수 없다

    현실의 밝기 범위는 엄청납니다. 달 없는 밤의 그림자와 한낮의 태양 표면은 수십억 배 차이가 나고, 같은 장면 안에서도 창밖 하늘과 방 안 구석은 수천 배 차이가 납니다. 반면 일반 모니터가 내는 밝기는 0~1(8비트로 0~255) 사이의 좁은 범위입니다.

    14강의 PBR은 물리량을 계산하므로, 결과도 이 넓은 범위의 값입니다. 태양을 받은 흰 벽은 10, 하늘은 30, 반사된 태양 하이라이트는 1000이 나올 수 있습니다. 이 값을 8비트 타깃에 바로 쓰면 1 이상은 전부 1로 잘려(클리핑) 하늘과 벽과 하이라이트가 똑같은 흰색이 됩니다. 반대로 어두운 실내는 0.01 같은 값이라 8비트 단계 몇 개에 뭉개져 계단(밴딩)이 생깁니다.

    해결은 두 단계입니다. 먼저 계산 결과를 잘리지 않게 담고(HDR 렌더 타깃), 마지막에 사람 눈과 카메라가 하듯 모니터 범위로 눌러 담는 것(노출 + 톤매핑)입니다. 그 사이에서 넓은 범위의 값이 있어야만 가능한 효과 — 블룸, 자동 노출 — 를 처리하는 단계가 포스트 프로세싱입니다.

    핵심 개념노출과 톤매핑

    노출 — 전체를 몇 배로 볼 것인가

    카메라는 조리개와 셔터로 들어오는 빛의 양을 조절합니다. 렌더러의 노출도 같은 일을 곱셈 하나로 합니다. 사진가의 단위인 EV(Exposure Value, 스톱)를 써서 배율 = 2EV로 둡니다. EV +1이면 두 배 밝게, −1이면 절반입니다. 사진에서 "한 스톱"이 빛의 양 두 배인 것과 같은 감각이라, 값을 조절하는 사람이 직관적으로 다룰 수 있습니다.

    무엇을 기준으로 맞출까요? 사진에서는 장면의 평균이 반사율 18%인 회색(미들 그레이)으로 찍히도록 노출을 맞추는 관례가 있습니다. ProjectE의 자동 노출도 장면의 평균 휘도가 0.18이 되도록 EV = log2(0.18 / 평균 휘도)를 고릅니다.

    톤매핑 — 0~∞를 0~1로 부드럽게

    노출을 곱해도 하이라이트는 여전히 1을 넘습니다. 톤매핑은 0~∞의 값을 0~1로 옮기는 곡선으로, 어두운~중간 영역은 거의 그대로 두고 밝은 영역을 점점 눌러 하얗게 포화시킵니다.

    Reinhard(x / (1 + x))는 가장 단순하지만 밝은 것도 끝내 하얗게 되지 않아 화면이 물빠진 듯 보이고, 중간 톤의 대비도 줄어듭니다. 영화 업계의 색 관리 표준인 ACES의 톤 곡선을 유리 함수로 근사한 Narkowicz의 ACES 근사가 게임에서 널리 쓰이는 이유는, 식 하나로 "필름 같은" 대비와 하이라이트 포화를 얻기 때문입니다.

    float3 TonemapAcesApprox(float3 X)
{
	// Krzysztof Narkowicz, "ACES Filmic Tone Mapping Curve"
	const float A = 2.51f, B = 0.03f, C = 2.43f, D = 0.59f, E = 0.14f;
	return saturate((X * (A * X + B)) / (X * (C * X + D) + E));
}

{
	float3 Hdr = SceneColor.SampleLevel(PointSampler, Input.UV, 0.0f).rgb;
	... // (TAA 흐림 보정 샤프닝 — 19강)

	{
		Hdr += BloomColor.SampleLevel(LinearSampler, Input.UV, 0.0f).rgb * BloomIntensity; // ① 블룸은 HDR에서 더한다

    핵심 개념블룸 — 밝은 빛이 번지는 효과

    실제 카메라 렌즈와 사람 눈은 아주 밝은 빛 주변이 뿌옇게 번져 보입니다(렌즈 산란). 블룸은 이것을 흉내 내 "이 부분은 화면이 표현할 수 있는 것보다 훨씬 밝다"는 신호를 줍니다. 톤매핑으로 하얗게 포화된 하늘과 전구가 똑같이 보이는 문제를, 번짐의 크기로 구분해 주는 셈입니다.

    번짐은 결국 큰 흐림(blur)입니다. 그런데 화면 폭의 수십 %에 이르는 넓은 흐림을 원래 해상도에서 직접 하면 픽셀마다 수백 개를 읽어야 합니다. 그래서 밉 체인을 씁니다. 반해상도로 줄이며 조금 흐리고, 또 반으로 줄이며 조금 흐리고 … 를 반복하면 작은 해상도의 픽셀 하나가 원본의 넓은 영역을 대표하게 됩니다. 그다음 거꾸로 올라오며 각 단계를 더해 합칩니다.

    13탭 다운샘플 (Jimenez 2014)

    단순히 2×2 평균으로 줄이면 줄일 때마다 픽셀 격자에 맞춰 덜컥거리는 계단과 깜빡임이 생깁니다. Call of Duty: Advanced Warfare 발표(Jimenez 2014)의 13탭 필터는 원본에서 13곳을 읽어, 겹치는 2×2 상자 다섯 개(가운데 하나 + 네 모서리)의 평균을 가중합합니다.

    첫 다운샘플 단계에는 두 가지가 더 붙습니다.

    • Karis 평균: HDR에서는 픽셀 하나가 주변의 1000배 밝을 수 있습니다(금속 위 태양 반사). 그대로 평균하면 그 한 점이 큰 원형 번짐을 만들고, 그 점이 프레임마다 깜빡이면 번짐 전체가 깜빡입니다("반딧불, firefly"). 상자마다 1/(1 + 휘도) 가중치를 주면 밝은 상자의 영향이 눌립니다.
    • 소프트 니(soft knee) 임계값: 임계값(기본 1.0) 이상만 번지게 하되, 경계에서 뚝 끊기지 않게 임계값 근처를 2차 곡선으로 이어 줍니다. CPU의 FPostProcessMath::ComputeBloomContribution과 셰이더 ApplyThreshold가 같은 식이고, CPU 쪽이 단위 테스트를 받습니다.

    업샘플은 3×3 텐트 필터(가중치 1·2·1 / 2·4·2 / 1·2·1, 합 16)로 한 단계 작은 레벨을 읽어, PSO의 가산 블렌드로 한 단계 큰 레벨에 더합니다. 작은 레벨일수록 넓은 번짐이므로, 이렇게 더해 올라가면 "가까운 곳은 진하고 멀수록 옅은" 자연스러운 번짐 모양이 됩니다.

    핵심 개념자동 노출 — 눈이 어둠에 적응하듯

    동굴에서 밝은 바깥으로 나가면 처음엔 눈이 부시다가 곧 적응합니다. 자동 노출은 화면의 평균 밝기를 재서 EV를 자동으로 고르고, 그 값을 시간에 따라 천천히 따라가게 합니다.

    1. 히스토그램(PSHistogram): 1/4 해상도로 화면을 읽어 픽셀마다 휘도의 log2를 계산하고, [−10, 12] 범위를 256칸으로 나눈 히스토그램에 원자적 덧셈(InterlockedAdd)으로 셉니다. 렌더 타깃 없이 UAV에만 쓰는 픽셀 셰이더입니다.
    2. 평균(CSAverage): 256스레드 그룹 하나가 칸 번호 × 개수를 병렬 합산해 평균 로그 휘도를 구합니다. 0번 칸(거의 검은 픽셀)은 제외합니다 — 하늘 없는 실내 씬에서 검은 배경이 평균을 끌어내려 과노출되는 것을 막습니다.
    3. 시간 적응: 이전 값에서 목표로 1 − e−dt × 속도만큼 다가갑니다. 이 지수 적응은 프레임률이 달라도 같은 시간에 같은 만큼 적응합니다(0강의 dt 이야기).
    // 지수 적응: Speed(1/초)가 클수록 빨리 목표에 도달. DeltaSeconds <= 0이면 이전 값 유지
static float ComputeAdaptedLuminance(float Previous, float Target, float DeltaSeconds, float Speed)
{
	if (!(Previous > 0.0f) || !std::isfinite(Previous))
	{
		return Target; // 첫 프레임 또는 잘못된 이전 값
	}
	const float Alpha = 1.0f - std::exp(-FMath::Max(DeltaSeconds, 0.0f) * FMath::Max(Speed, 0.0f));
	return Previous + (Target - Previous) * Alpha;
}

// 평균 휘도 → 자동 노출 EV (MiddleGray 기준), [MinEV, MaxEV]로 제한
static float ComputeAutoExposureEV(float AverageLuminance, float MinEV, float MaxEV)
{
	const float EV = std::log2(MiddleGray / FMath::Max(AverageLuminance, 1.0e-4f));
	return FMath::Clamp(EV, MinEV, MaxEV);
}
    왜 산술 평균이 아니라 로그 평균인가 화면 1%가 하늘(값 1000)이고 99%가 땅(값 1)이면 산술 평균은 약 11이라 땅이 시커멓게 찍힙니다. 로그 평균(기하 평균)은 약 1.07로, "대부분의 픽셀이 보이는 수준"에 가깝습니다. 사람의 밝기 지각도 대략 로그적입니다.

    ProjectE에서는포스트 프로세서와 HDR 디스플레이 출력

    효과들은 FPostProcessor 한 곳에 모여 있고, 씬 렌더러는 Render를 한 번 부를 뿐입니다. 설정은 FPostProcessSettings(노출 EV, 톤매핑 연산자, 자동 노출 범위 −4~+6 EV와 적응 속도 1.5/초, 블룸 임계값 1.0·니 0.5·세기 0.08 …)로 모으고, 에디터의 "포스트 프로세스" 패널이 이 값을 조절합니다. CPU와 GPU가 같은 식을 쓰는 부분은 PostProcessMath.h에 두고 셰이더와 함께 고친다는 규칙이 있습니다(CLAUDE.md "포스트 프로세싱").

    HDR 모니터로 내보내기 (Phase 49)

    HDR 모니터는 1을 넘는 밝기(예: 1000 nits)를 실제로 낼 수 있습니다. 그렇다고 톤매핑을 빼고 HDR 값을 그대로 보내면 안 됩니다. 장면 값 30이 몇 nits인지 정해 줘야 하기 때문입니다. ProjectE의 방식은 이렇습니다.

    • SDR과 같은 ACES 곡선을 먼저 적용하고, 그 결과 s(0~1)의 무릎(knee, 기본 0.5) 위쪽만 [0, 최대 밝기/종이 흰색) 범위로 펼칩니다(ExpandHighlights). 무릎 아래는 SDR과 같은 값이라 중간톤과 UI 밝기가 SDR 화면과 일치합니다.
    • "종이 흰색(paper white)" = SDR의 1.0을 몇 nits로 볼지. 설정 HdrPaperWhiteNits/HdrMaxNits로 조절합니다.
    • 마지막 합성 패스가 HDR10(BT.2020 색역 + ST.2084 PQ 곡선) 또는 scRGB(선형, 1.0 = 80 nits)로 인코딩합니다. 식은 HdrDisplayMath.h ↔ HdrDisplay.hlsli가 같고 Hdr_* 테스트가 지킵니다.
    // HDR 하이라이트 펼치기: s(SDR 톤매핑 값, 0~1) → [0, PeakRatio). 무릎 아래는 그대로, 무릎에서 기울기 1로 이어진다 (C1 연속, 단조)
inline float ExpandHighlights(float S, float PeakRatio, float Knee = DefaultKnee)
{
	if (PeakRatio <= 1.0f || S <= Knee)
	{
		return S;
	}
	const float U     = FMath::Min(S, 1.0f) - Knee;
	const float Range = 1.0f - Knee;
	const float Gain  = 1.0f - Range / (PeakRatio - Knee);
	return Knee + U / FMath::Max(1.0f - U / Range * Gain, 1.0e-6f);
}
    규칙: 씬 출력과 UI 출력은 다른 문 씬은 반드시 Rhi->GetSceneOutput()으로, UI·오버레이는 GetBackBufferOutput으로 그립니다. HDR 모드에서 UI는 SDR 겹침 층에 그려진 뒤 합성되므로, UI를 씬 출력에 그리면 UI까지 HDR 곡선으로 펼쳐져 눈부시게 밝아집니다. 새 앱도 FHdrOutputController::Update를 BeginFrame 전에 부릅니다.

    함정과 교훈"시간"과 "밝은 점 하나"

    자동 노출이 실행마다 다른 화면을 만든다면 자동 노출 적응은 "지난 프레임 이후 흐른 시간"이 필요합니다. 이 시간을 실제 시계(steady_clock)로 재면, 자동 검증에서 같은 씬을 두 번 찍어도 기계 부하에 따라 노출이 조금씩 달라져 스크린샷이 비트 단위로 일치하지 않습니다. 그래서 ProjectE는 "시간에 따라 바뀌는 화면 상태(자동 노출 적응, 물·구름의 시간, 쿠키 패닝 …)는 실제 시각 대신 FFrameTime(앱 프레임 델타, --fixed-delta면 고정)을 쓴다"는 규칙을 두었습니다. 실제 시각은 측정에만 씁니다.
    자동 검증이 처음 잡아낸 경고들 (2026-10-01) 스크린샷 자동 검증을 처음 붙이고 Phase 6 화면을 돌리자, 눈으로는 멀쩡한 화면에서 D3D12 디버그 레이어 메시지가 나왔습니다. Plans.md에 기록된 수정 중 하나가 HDR 타깃의 "최적 클리어 값"입니다 — 리소스를 만들 때 알려 준 클리어 색과 실제로 지우는 색이 다르면 드라이버의 빠른 클리어 최적화를 못 쓴다고 디버그 레이어가 알립니다. 지금의 EnsureSceneColor가 배경색을 클리어 값으로 미리 넣어 두는 것도 같은 맥락입니다. "화면이 맞다"와 "올바르게 그렸다"는 다르다는 교훈입니다.
    샤프닝도 밝은 점을 조심한다 톤매핑 패스 앞부분의 샤프닝(TAA 흐림 보정)은 4이웃 언샤프 마스크인데, 보정량에 1 / (1 + 최대 성분)을 곱합니다. HDR에서 매우 밝은 픽셀 옆을 그대로 샤프닝하면 검은 테두리(링잉)가 생기기 때문입니다. Karis 평균과 같은 발상 — "HDR에서는 밝기에 반비례하는 가중치" — 입니다.

    생각해 볼 문제

    Q1. 블룸 임계값을 0으로 두면 어떤 화면이 될까요? 임계값 없이도 블룸이 "물리적으로" 맞다는 주장은 무엇일까요? 모든 픽셀이 조금씩 번져 화면 전체가 뿌옇게(글로우) 됩니다. 실제 렌즈 산란은 밝기와 무관하게 모든 빛에 일어나므로 임계값이 없는 것이 물리적으로는 맞고, 대신 세기(BloomIntensity)를 아주 작게 두면 밝은 것만 눈에 띄게 번집니다. 임계값은 예술적 조절 수단이라 볼 수 있습니다.
    Q2. 자동 노출 히스토그램을 1/4 해상도로 만드는 이유와, 그 대가는? 원자적 덧셈은 같은 칸에 많은 스레드가 몰리면 느려지고, 평균을 내는 데는 모든 픽셀이 필요하지 않습니다. 1/4 해상도면 표본이 1/16로 줄어 비용이 크게 줍니다. 대가는 아주 작은 밝은 물체(작은 전구)가 표본에서 빠질 수 있다는 것인데, 평균 노출에는 거의 영향이 없습니다.
    Q3. 톤매핑된 SDR 이미지를 HDR 모니터에 그대로 보내면(종이 흰색 = 모니터 최대 밝기) 어떤 문제가 있을까요? SDR의 1.0이 모니터 최대 밝기(예: 1000 nits)가 되어 UI와 중간톤까지 눈부시게 밝아지고, 하이라이트와 흰 벽의 구분은 여전히 없습니다. HDR의 이점은 "중간톤은 SDR처럼 두고 하이라이트에만 여유 범위를 쓰는 것"이므로, 종이 흰색을 낮게 두고(ProjectE 기본값 HdrPaperWhiteNits = 200) 무릎 위만 펼칩니다.

    14강의 셰이딩 식은 "광원에서 이 점까지 빛이 가려지지 않았다"고 가정합니다. 그 가정을 지키면 모든 물체가 땅 위에 둥둥 떠 보입니다. 그림자는 물체 사이의 위치 관계(얼마나 높이 있나, 어디에 닿아 있나)를 알려 주는 가장 강한 시각 단서입니다.

    정확한 답은 "점에서 광원 방향으로 광선을 쏴서 무언가에 맞는가"입니다(레이 트레이싱, 3부 후반). 하지만 오랫동안 실시간 렌더링의 표준은 래스터라이저만으로 이 질문에 답하는 섀도우 맵이었고, ProjectE도 방향광 그림자의 기본은 섀도우 맵입니다.

    핵심 개념섀도우 맵 — 광원에서 찍은 깊이 사진

    아이디어는 단순합니다. 광원 위치에 카메라를 두고 장면의 깊이만 그립니다. 이 깊이 텍스처의 각 텍셀에는 "광원에서 그 방향으로 가장 가까운 면까지의 거리"가 들어 있습니다. 그다음 실제 카메라로 그릴 때, 픽셀의 월드 위치를 광원 공간으로 변환해 "나와 광원 사이의 거리"를 섀도우 맵의 값과 비교합니다. 내가 더 멀면, 광원과 나 사이에 무언가 있다는 뜻 — 그림자입니다.

    장점은 분명합니다. 그림자를 드리우는 물체(캐스터)가 무엇이든 — 스킨 메시, 지형, 풀 — 그냥 깊이를 그리면 됩니다. 단점도 분명합니다. 섀도우 맵은 유한한 해상도의 이산 표본이라, 화면 픽셀과 섀도우 맵 텍셀이 1:1로 맞지 않는 데서 거의 모든 문제가 생깁니다.

    핵심 개념섀도우 애크니와 피터 패닝

    섀도우 맵 텍셀 하나는 표면의 작은 조각을 대표하는 깊이 하나를 저장합니다. 표면이 광원에 비스듬하면, 텍셀 안에서 실제 표면 깊이는 저장된 값보다 앞이기도 하고 뒤이기도 합니다. 뒤쪽 절반은 "내가 더 머니까 그림자"로 판정되어, 빛을 받아야 할 면에 줄무늬가 생깁니다. 이것이 섀도우 애크니(shadow acne), 자기 그림자 여드름입니다.

    ProjectE는 세 가지 장치를 함께 씁니다. 모두 FShadowSettings에서 조절합니다.

    장치기본값하는 일
    고정 깊이 바이어스 (래스터라이저 DepthBias)1000 (D32 단위)섀도우 맵에 깊이를 쓸 때 일정량 뒤로 민다
    기울기 비례 바이어스 (SlopeScaledDepthBias)2.0광원에 비스듬한 삼각형일수록 더 민다 (애크니는 비스듬한 면에서 심하므로)
    법선 오프셋 (NormalOffset)텍셀 크기 × 1.5받는 쪽(2패스)에서 조회 위치를 표면 법선 방향으로 민다. 빛에 비스듬할수록 더

    법선 오프셋이 특히 효과적인 이유는, 깊이를 미는 대신 조회 위치 자체를 표면 밖으로 옮겨 "다른 텍셀"을 읽게 하기 때문입니다. 미는 거리가 텍셀 크기에 비례하므로 캐스케이드마다(텍셀 크기가 다르므로) 알맞은 양이 자동으로 정해집니다.

    핵심 개념캐스케이드 섀도우 맵 (CSM)

    방향광은 무한히 먼 태양이라 그림자를 그려야 할 범위가 카메라가 보는 모든 곳입니다. 60m 앞까지 그림자를 그리는데 2048×2048 섀도우 맵 한 장으로 그 넓은 영역(가로세로 수십 m)을 덮으면 텍셀 하나가 수 cm가 됩니다. 발밑에서는 너무 거칠고(계단 그림자), 60m 앞에서는 화면 픽셀 하나에 텍셀 여러 개가 들어가 낭비입니다. 원근 투영 때문에 가까울수록 화면에서 크게 보이는데 섀도우 맵은 거리와 무관하게 균일하기 때문입니다(원근 에일리어싱).

    CSM은 카메라 절두체를 거리로 여러 조각(캐스케이드)으로 나누고, 조각마다 섀도우 맵을 한 장씩 씁니다. 가까운 조각은 좁은 범위를 같은 해상도로 덮으니 촘촘하고, 먼 조각은 넓은 범위를 덮으니 성깁니다.

    // 실용 분할(Practical Split Scheme): 로그 분할과 균등 분할을 Lambda로 섞는다.
for (uint32 Index = 0; Index < Count; ++Index)
{
	const float P       = static_cast<float>(Index + 1) / static_cast<float>(Count);
	const float LogPart = NearZ * std::pow(FarZ / NearZ, P);
	const float UniPart = NearZ + (FarZ - NearZ) * P;
	Splits[Index]       = FMath::Lerp(UniPart, LogPart, Lambda);
}

    경계 구와 텍셀 스냅 — 카메라가 돌 때 그림자가 떨리지 않게

    조각마다 광원 방향 직교 투영 상자를 정해야 합니다. 조각의 꼭짓점 8개를 딱 맞게 감싸는 상자를 쓰면 가장 촘촘하지만, 카메라가 회전할 때마다 상자 크기가 바뀌어 텍셀 크기가 바뀌고, 그림자 가장자리가 매 프레임 꿈틀거립니다(shimmering). 그래서 ProjectE는 두 가지를 합니다.

    1. 경계 구: 꼭짓점 8개를 감싸는 구의 반경으로 투영 크기를 정합니다. 구는 회전해도 같으므로 카메라가 돌아도 텍셀 크기가 변하지 않습니다(조금 낭비하는 대신 안정을 삽니다).
    2. 텍셀 스냅: 카메라가 이동하면 구의 중심이 움직입니다. 중심을 광원 공간의 텍셀 격자에 맞춰 내림하면, 섀도우 맵이 정확히 텍셀 단위로만 움직여 같은 물체가 항상 같은 텍셀 경계에 래스터됩니다.
    // 반경을 1/16 단위로 올림 → 프레임 간 투영 크기 고정
Radius *= static_cast<float>(Resolution) / static_cast<float>(Resolution - 2); // 스냅으로 움직일 한 텍셀 여유
Radius = FMath::Ceil(Radius * 16.0f) / 16.0f;
...
// 텍셀 스냅: 원점 기준 광원 뷰에서 중심을 텍셀 격자에 맞춘다
const float      TexelSize  = (Radius * 2.0f) / static_cast<float>(Resolution);
const FMatrix4x4 LightView0 = FMatrix4x4::MakeLookAt(FVector3::ZeroVector, Direction, WorldUp);
FVector3         CenterLS   = LightView0.TransformPosition(Center);
CenterLS.X = FMath::Floor(CenterLS.X / TexelSize) * TexelSize;
CenterLS.Y = FMath::Floor(CenterLS.Y / TexelSize) * TexelSize;
Center     = LightView0.GetInverse().TransformPosition(CenterLS);

// CasterExtension: 조각 앞쪽(광원 쪽)으로 더 확장해 화면 밖 캐스터도 그림자를 드리우게 한다
const FVector3   Eye  = Center - Direction * (Radius + CasterExtension);

    CasterExtension(기본 5000cm)도 중요합니다. 화면 밖 높은 곳의 나무나 절벽이 화면 안으로 그림자를 드리울 수 있으므로, 투영 상자를 광원 쪽으로 길게 늘려 그 캐스터들도 섀도우 맵에 들어가게 합니다.

    PCF — 그림자 가장자리를 부드럽게

    비교 결과는 0 또는 1이라 가장자리가 텍셀 모양 계단으로 보입니다. PCF(Percentage-Closer Filtering)는 주변 여러 텍셀과 비교한 결과(0/1)를 평균해 "몇 %가 빛을 받는가"를 냅니다. 깊이 값을 먼저 평균하면 안 된다는 점에 주의하세요 — 서로 다른 물체의 깊이를 평균한 값은 의미가 없습니다. 비교를 먼저 하고 결과를 평균하는 것이 핵심입니다.

    // 빛에 비스듬한 면일수록 더 밀어 자기 그림자(acne)를 줄인다
const float  NdotL    = saturate(dot(GeometricNormal, L));
const float3 Offset   = GeometricNormal * CascadeTexelWorld[Cascade] * ShadowNormalOffset * (1.0f - 0.5f * NdotL);
const float4 ClipPos  = mul(float4(WorldPosition + Offset, 1.0f), CascadeViewProjection[Cascade]);
const float2 UV       = ClipPos.xy * float2(0.5f, -0.5f) + 0.5f;
...
float Lit = 0.0f;
[unroll] for (int Y = -1; Y <= 1; ++Y)
	[unroll] for (int X = -1; X <= 1; ++X)
		Lit += ShadowMap.SampleCmpLevelZero(ShadowSampler, float3(UV + float2(X, Y) * ShadowTexelSize, Cascade), ClipPos.z);
Lit /= 9.0f;
// 그림자 거리 끝 10%에서 부드럽게 사라지게

    SampleCmpLevelZero는 비교 샘플러로, 하드웨어가 이웃 2×2 텍셀과 각각 비교한 결과를 쌍선형으로 섞어 줍니다. 그래서 3×3번 호출이 실제로는 4×4 텍셀 영역의 부드러운 필터가 됩니다. 픽셀이 어느 캐스케이드인지는 뷰 깊이와 분할 경계를 비교해(SelectCascade) 고르고, 마지막 캐스케이드 끝 10%에서는 그림자를 서서히 1로 페이드해 경계가 뚝 끊기지 않게 합니다.

    ProjectE에서는정적 캐스터 캐시 — Rebuild / Reuse / Direct

    그림자 패스는 장면을 캐스케이드 수만큼(최대 4번) 다시 그리는 셈이라 비쌉니다. 그런데 장면의 대부분 — 건물, 바위, 나무 — 은 움직이지 않습니다. 2026-10-04 작업은 이 점을 이용했습니다. 캐스케이드마다 정적 캐스터만 그린 깊이를 따로 보관해 두고, 다음 프레임에는 그것을 섀도우 맵에 복사한 뒤 움직이는 것만 위에 그립니다.

    • 정적 = 스킨이 아니고 월드 행렬이 30프레임(r.Shadow.Cache.StaticFrames) 연속 비트 단위로 같은 인스턴스, 폴리지(배치 고정), 상태 해시를 알려 주는 추가 캐스터(지형).
    • 캐시 키 = 캐스케이드 뷰-투영 행렬의 비트, 해상도·바이어스, 정적 인스턴스 집합의 해시(순서 무관한 합), 지형 상태 해시, 캐시 세대(셰이더 다시 로드 등)를 섞은 64비트 해시.

    키를 보고 프레임마다 세 가지 중 하나를 고릅니다.

    if (State.bCacheValid && State.CachedKey == Key)
{
	Action = ECacheAction::Reuse;
}
else if ((State.bHasLast && State.LastKey == Key) || (State.bCacheValid && State.ReuseFrames >= ImmediateRebuildReuseFrames))
{
	Action            = ECacheAction::Rebuild;
	State.CachedKey   = Key;
	State.bCacheValid = true;
}
else
{
	State.bCacheValid = false; // 한 프레임 안정될 때까지 캐시를 만들지 않는다
}

    카메라가 움직이는데 어떻게 재사용하나 — 양자화

    문제가 하나 있습니다. 캐스케이드는 카메라를 따라다니므로, 카메라가 걷기만 해도 텍셀 스냅이 한 텍셀 움직일 때마다 뷰-투영 행렬이 바뀌어 키가 바뀝니다. 해결은 더 큰 격자에 스냅하는 것입니다(r.Shadow.Cache.Quantize = 0.125). 반경을 12.5% 넓히고, 중심을 "텍셀의 정수배이면서 넓힌 만큼 이하"인 큰 칸에 반올림합니다. 카메라가 그 칸 안에서 움직이는 동안 행렬은 비트 단위로 같고, 원래 조각은 여전히 넓힌 상자 안에 들어 있습니다. 칸을 넘는 프레임에는 그림 16-4의 6번 프레임처럼 바로 Rebuild합니다. 칸 크기가 텍셀의 정수배라 칸을 넘어도 텍셀 격자는 그대로여서 그림자 가장자리가 튀지 않습니다. 대가는 텍셀이 12.5% 커지는 것뿐입니다.

    측정: 그림자 GPU 2.48ms → 0.35~0.5ms 데모 맵 Hub에서 방향광 그림자 GPU 시간이 2.48ms에서 0.35~0.5ms로 줄었고, 화면은 비트 단위로 같았습니다(Terrain/Materials/GI 검증 씬 MD5 동일). 카메라가 계속 걷는 경우(--hold-keys W, 에디터 팬 8cm/프레임)에도 양자화 덕분에 2.2~2.9ms → 0.65~0.72ms, 캐스케이드 3장 중 평균 2.95장을 재사용했습니다.

    함정과 교훈캐스터를 빠뜨리지 말 것

    규칙: 새 그림자 캐스터 종류는 정적/동적을 알린다 캐시는 "알려 준 것만 정적"으로 봅니다. AddExternal로 넣는 인스턴스는 bShadowStatic을, 추가 캐스터 훅은 상태 해시를 채워야 합니다. 알리지 않으면 동적으로 취급되어 매 프레임 그려지므로 틀린 그림자는 안 생기지만 이득도 없습니다. 반대로 해시에 담기지 않는 변경(같은 핸들로 메시를 다시 로드)은 FShadowRenderer::InvalidateCache()로 직접 무효화해야 낡은 그림자가 남지 않습니다.
    화면 밖 캐릭터의 그림자가 사라진다 (Phase 29) 스킨 메시의 본 팔레트 계산을 "화면에 보이는 것만"으로 줄였더니, 카메라 밖에 서 있는 캐릭터의 그림자가 화면 안 바닥에서 사라졌습니다. 그림자 캐스터는 화면 밖에 있어도 그림자는 화면 안에 떨어질 수 있기 때문입니다. 그래서 팔레트 가시성 = 메인 프러스텀 ∪ 방향광 캐스케이드 캐스터 볼륨 ∪ 로컬 그림자 장이 되었고, 캐스터 볼륨은 팔레트보다 먼저 정합니다. 새 그림자 패스를 추가하면 이 판정에도 넣어야 합니다.
    그림자 LOD 바이어스는 기본 0 먼 캐스케이드에서 더 낮은 LOD 메시로 그림자를 그리는 r.Shadow.LodBias도 만들었지만, 0.5로 두자 Hub의 나무 그림자 모양이 눈에 띄게 바뀌어 기본값을 0으로 두었습니다. 대신 경계 구 지름이 텍셀 하나보다 작은 캐스터를 그 캐스케이드에서 빼는 r.Shadow.MinCasterTexels(기본 1)는 화질 차이가 없어 켜 두었습니다. "눈에 띄는 화질 차이가 없으면 최적화는 기본 켬, 끄는 CVar는 유지"가 이 프로젝트의 원칙입니다.
    정리
    • 섀도우 맵 = 광원 시점 깊이. 픽셀의 광원 깊이가 더 크면 그림자.
    • 이산 표본 때문에 애크니 → 고정·기울기 바이어스 + 법선 오프셋. 과하면 피터 패닝.
    • CSM: 실용 분할로 거리 조각마다 한 장. 경계 구(회전 안정) + 텍셀 스냅(이동 안정).
    • PCF는 "비교 후 평균". 비교 샘플러가 2×2를 섞어 3×3 호출이 넓은 필터가 된다.
    • 정적 캐스터 캐시: 키가 같으면 Reuse, 안정되면 Rebuild, 매번 바뀌면 Direct. 양자화로 이동 중에도 재사용.

    생각해 볼 문제

    왜 필요한가그림자 쪽은 정말 검은가

    14·16강까지 만든 화면에서, 태양 반대쪽 면과 그림자 속은 완전히 검습니다. 현실에서는 그렇지 않습니다. 하늘 전체가 푸른 빛을 내고, 땅과 벽이 빛을 되튕겨 그림자 속을 비춥니다. 금속 공에는 주변 풍경이 비칩니다. 이 "사방에서 오는 빛"을 환경광(ambient/environment lighting)이라 합니다.

    Phase 6 초기의 해결은 하늘색·땅색 두 색을 법선 방향으로 섞는 간이 환경광(EvaluateAmbient)이었습니다. 방향에 따른 변화가 거의 없어 밋밋했고, 금속에 비칠 풍경도 없었습니다. IBL(Image-Based Lighting)은 주변 환경을 큐브맵 이미지로 찍어 두고, 그 이미지의 모든 텍셀을 작은 광원으로 취급합니다. 다만 픽셀마다 수만 개의 광원을 더할 수는 없으니, 적분을 미리 해 두는 것이 이 강의의 핵심입니다.

    핵심 개념반구 적분을 미리 해 두기

    14강의 셰이딩 식을 모든 방향에서 오는 빛으로 확장하면 반구 적분이 됩니다.

    환경광의 렌더링 방정식 Lout(v) = ∫반구 f(l, v) · Lenv(l) · (n·l) dωl
    = (확산 부분) + (정반사 부분)

    확산 → 조도 맵 (irradiance map)

    Lambert 확산은 BRDF가 상수 albedo/π라 적분 밖으로 나옵니다. 남는 것은 E(n) = ∫ Lenv(l)(n·l) dω — 법선 n으로 향한 면이 받는 조도 — 뿐이고, 이것은 n만의 함수입니다. 그러니 모든 방향 n에 대해 미리 계산해 작은 큐브맵(ProjectE는 32×32)에 저장해 두면, 셰이더는 법선 방향으로 한 번 샘플링하면 끝입니다. 확산은 저주파(부드럽게 변함)라 작은 큐브로 충분합니다.

    ProjectE는 E 대신 E/π를 저장합니다. 그러면 확산 = 조도 맵 × albedo로 π가 사라집니다. 계산할 때는 코사인 가중 샘플링(pdf = cosθ/π)을 쓰는데, 이렇게 하면 표본 평균이 정확히 E/π가 되어 식이 깔끔해집니다.

    for (uint I = 0; I < SampleCount; ++I)
{
	float2 Xi = Hammersley(I);
	float Phi = 2 * Pi * Xi.x;
	float R = sqrt(Xi.y);
	float CosTheta = sqrt(1 - Xi.y);
	float3 L = ToWorld(float3(R * cos(Phi), R * sin(Phi), CosTheta), N);

	// 코사인 샘플링 pdf = cos / pi
	float Lod = FilteredSampleLod(CosTheta / Pi, SourceSize);
	Sum += Environment.SampleLevel(LinearSampler, L, Lod).rgb;
}
// 코사인 중요도 샘플링 평균 = irradiance / pi.
CubeOutput[Id] = float4(Sum / float(SampleCount), 1);

    정반사 → 분할 합 근사 (split sum)

    정반사는 BRDF가 l과 v 모두에 의존해서 그대로는 미리 계산할 수 없습니다(입력이 n, v, 거칠기로 너무 많음). Epic Games(Karis 2013)의 분할 합 근사는 적분을 두 개의 곱으로 쪼갭니다.

    분할 합 ∫ Lenv(l) f(l, v) (n·l) dω ≈ [ ∫ Lenv(l) D(h) (n·l) dω 의 정규화 평균 ] × [ ∫ f(l, v) (n·l) dω ]
    = 프리필터 환경 맵(R, 거칠기) × BRDF 적분(n·v, 거칠기)
    • 앞 항(프리필터): "n = v = R"이라고 가정하면 환경을 GGX 로브 모양으로 흐린 값이 되어 R과 거칠기만의 함수가 됩니다. 거칠기 단계마다 하나씩, 큐브맵의 밉 레벨에 저장합니다(밉 0 = 거울, 마지막 밉 = 가장 거침).
    • 뒤 항(BRDF 적분): 환경과 무관합니다. F0를 밖으로 빼면 F0 × A + B 꼴이 되고, A와 B는 (n·v, 거칠기) 두 입력만의 함수라 2D 텍스처(BRDF LUT) 하나에 담깁니다. 어떤 환경에서도 같은 표입니다.
    const float  NdotV = max(saturate(dot(Surface.N, Surface.V)), 1.0e-4f);
const float3 F0 = GetF0(Surface);
// 거칠기를 고려한 프레넬: 거친 면은 스치는 각도에서도 반사가 1까지 가지 않는다
const float3 F = F0 + (max(1.0f - Surface.Roughness, F0) - F0) * pow(1.0f - NdotV, 5.0f);
const float3 Diffuse = IblDiffuse.SampleLevel(IblSampler, Surface.N, 0).rgb * Surface.Albedo;
const float3 R = reflect(-Surface.V, Surface.N);
const float3 Prefiltered = SampleSpecularEnvironment(R, Surface.Roughness, WorldPosition, PixelPosition, (float)MipCount, bScreenReflections);
const float2 Brdf = IblBrdf.SampleLevel(IblSampler, float2(NdotV, Surface.Roughness), 0);
const float3 Specular = Prefiltered * (F0 * Brdf.x + Brdf.y);
...
return ((1.0f - F) * (1.0f - Surface.Metallic) * Diffuse * AmbientIntensity + Specular) * Surface.Occlusion;

    마지막 줄의 Surface.Occlusion이 14강에서 말한 AO(텍스처 AO × 19강의 SSAO)입니다. 환경광에만 곱합니다.

    핵심 개념중요도 샘플링과 점박이 문제

    프리필터·조도 맵을 만드는 적분은 GPU 계산 셰이더가 몬테카를로(무작위 표본 평균)로 합니다. 텍셀마다 256개(IntegrationSampleCount) 방향을 골라 환경을 읽고 평균하는데, 방향을 반구에 고르게 뿌리면 GGX 로브 밖 — 기여가 거의 0인 곳 — 에 표본 대부분이 낭비됩니다. 중요도 샘플링은 표본을 BRDF가 큰 곳에 몰아서 뽑고(GGX 분포를 따르는 방향 생성), 확률 밀도(pdf)로 보정합니다. 표본 순서는 고르게 퍼진 저불일치 수열인 Hammersley를 써서 무작위보다 빨리 수렴하고, 실행마다 결과가 같습니다(결정적).

    HDR 하늘의 해가 점으로 찍히다

    절차적 하늘에서는 문제가 없었는데, Phase 33-7에서 실제 촬영한 .hdr 하늘(태양이 수만 단위로 밝은)을 넣자 금속 구에 비친 반사와 조도가 점박이가 되었습니다. 원인은 표본 수 256개가 하늘 전체에 비해 성기다는 것입니다. 해는 아주 작고 아주 밝아서, 어떤 출력 텍셀의 표본은 우연히 해를 맞히고(엄청 밝음) 옆 텍셀의 표본은 비껴갑니다(어두움). 출력 텍셀마다 같은 Hammersley 패턴을 다른 방향으로 돌려 쓰므로, 해가 표본 패턴 모양 그대로 찍힙니다.

    해결책인 필터드 중요도 샘플링은 표본 하나가 대표하는 입체각 Ωs = 1 / (표본 수 × pdf)을 원본 큐브 텍셀 하나의 입체각 Ωp = 4π / (6 × 크기²)과 비교해, 그 비율만큼 흐린 원본 밉에서 읽습니다. 그러려면 원본 하늘 큐브가 밉 체인을 가져야 하므로, ProjectE는 하늘 큐브를 만들 때 DownsampleCS로 전체 밉을 만듭니다.

    // 필터드 중요도 샘플링 (Ibl.hlsl과 같은 식, Křivánek & Colbert 2008): 표본 하나가 대표하는 입체각 1 / (표본 수 × pdf)를
// 원본 큐브 텍셀 입체각 4π / (6 × 크기²)과 비교해 그만큼 흐린 원본 밉에서 읽는다(+1 = 표본 사이를 겹쳐 덮는 치우침).
// 원본 밉 0만 읽으면 밝고 작은 광원(HDR 하늘의 해)이 표본 방향마다 따로 찍혀 반사/조도가 점박이가 된다
inline float ComputeFilteredSampleLod(float Pdf, uint32 SampleCount, uint32 SourceSize)
{
	const float SampleSolidAngle = 1.0f / FMath::Max(static_cast<float>(SampleCount) * Pdf, 1.0e-8f);
	const float TexelSolidAngle  = 4.0f * FMath::Pi / (6.0f * static_cast<float>(SourceSize) * static_cast<float>(SourceSize));
	return FMath::Max(0.5f * std::log2(SampleSolidAngle / TexelSolidAngle) + 1.0f, 0.0f);
}

    0.5 × log2인 이유는 밉이 하나 올라갈 때 텍셀의 한 변이 2배, 입체각(면적)은 4배가 되기 때문입니다. 프리필터의 pdf는 "n = v 가정에서 반사 방향 pdf = D/4"이고, 거울 밉(거칠기 0)은 출력 텍셀 하나가 덮는 만큼의 원본 밉(512 원본 → 128 출력이면 밉 2)을 읽습니다.

    반사 캡처 — 하늘만 비치는 실내 문제

    하늘 IBL은 "무한히 먼 환경"이라, 방 안의 금속 주전자에도 바깥 하늘이 비칩니다. 반사 캡처는 장면 안 특정 위치에서 큐브를 직접 찍어(도구 → 반사 캡처 굽기) 하늘과 같은 GGX 프리필터를 적용해 둔 것입니다. 픽셀은 우선순위대로 SSR(19강) → 반사 캡처 → 하늘을 섞습니다. 앞의 것이 덮지 못한 "남은 비중"만큼 뒤의 것을 씁니다.

    • 최대 8개, 128px 프리필터 6밉, 큐브 배열 아틀라스(t21) + 프레임 캡처 목록(t20).
    • 구 또는 상자 모양. 상자 캡처는 시차 보정을 합니다 — 반사 광선을 상자 벽과 교차시켜 그 점을 캡처 중심에서 본 방향으로 큐브를 읽어, 방 크기에 맞는 반사가 나옵니다.
    • 굽기 결과는 .ecapture(원본 에셋이 아닌 엔진 바이너리, FReflectionCaptureFile::Version)로 저장합니다.

    함정과 교훈미리 계산한 것은 낡는다

    금속 구의 해 반사가 점박이 (2026-10-02 사용자 보고) Demo_HdrSky의 금속 구와 주황 구에 해가 점점이 찍힌 보고였습니다. 조도/프리필터가 원본 밉 0만, 256개 고정 표본으로 읽어 해가 표본마다 찍힌 것이 원인이었고, 하늘 큐브 밉 체인 + 필터드 중요도 샘플링으로 고쳤습니다(테스트 Ibl_FilteredImportanceSampling). 규칙으로 남긴 것은 "환경 큐브를 새로 적분하는 코드도 원본 밉을 갖춘다"입니다. 반사 캡처의 원본 큐브는 아직 밉이 1개라 밉 0으로 잘리는 것이 알려진 후속 과제입니다.
    하늘을 바꾸면 캡처를 다시 굽는다 반사 캡처는 굽는 순간의 장면과 하늘을 담은 사진입니다. 하늘 환경맵이나 대기를 바꾸면 캡처는 옛 하늘을 계속 비춥니다. 또 캡처 굽기는 3부 후반의 동적 GI(DDGI) 없이 하늘빛만으로 찍히기 때문에, DDGI로 밝힌 실내에 두면 푸른 하늘 반사가 얹혀 보입니다. 그래서 DDGI 실내 데모 맵에는 반사 캡처를 두지 않는다는 규칙이 생겼습니다.
    CPU 참조 식을 두는 이유 IblMath.h는 GPU 셰이더(Ibl.hlsl)와 같은 식(큐브 면 방향, Hammersley, GGX 샘플링, 필터드 LOD)을 C++로 갖고 있고, 단위 테스트가 이것을 검증합니다. GPU 결과는 테스트하기 어렵지만, 식이 같다는 약속을 지키면 CPU에서 경계값(면 경계 방향, 거칠기 0, pdf 0)을 확인할 수 있습니다. 3부 전체에 걸쳐 반복되는 "XxxMath.h ↔ hlsl" 패턴입니다.
    정리
    • IBL = 환경 이미지의 모든 텍셀을 광원으로. 적분은 미리 해서 텍스처에 담는다.
    • 확산 → 조도 큐브(E/π, 법선으로 조회). 정반사 → 분할 합: 프리필터 큐브(R, 거칠기→밉) × BRDF LUT(F0·A + B).
    • 적분은 GGX/코사인 중요도 샘플링 + Hammersley(결정적).
    • HDR 해 같은 작고 밝은 광원은 필터드 중요도 샘플링(표본 입체각만큼 흐린 밉)으로 점박이를 없앤다.
    • 반사 캡처로 국소 반사를 보완: SSR → 캡처 → 하늘 순으로 남은 비중을 채운다.

    생각해 볼 문제

    Q1. 조도 맵이 32×32인데 프리필터 맵의 밉 0은 128×128입니다. 왜 이렇게 크기가 다를까요? 조도는 반구 전체를 코사인으로 평균한 값이라 방향에 따라 아주 천천히 변합니다(저주파). 32×32로도 보간하면 충분히 매끈합니다. 반면 프리필터 밉 0은 거울 반사라 환경의 세부(건물 윤곽, 해)를 그대로 보여야 하므로 더 큰 해상도가 필요합니다. 거칠기가 커질수록 흐려지므로 밉이 작아져도 됩니다.
    Q2. 표본 수를 256에서 4096으로 늘리면 점박이 문제가 해결될까요? 필터드 중요도 샘플링보다 나은가요? 표본이 많으면 해를 맞히는 표본의 비율이 실제 해의 크기에 가까워져 점박이가 줄지만, 해가 매우 작고 밝으면 여전히 남고 비용은 16배입니다. 필터드 중요도 샘플링은 같은 256개로도 각 표본이 넓은 영역을 평균해 읽으므로 훨씬 싸게 매끈해집니다. 대신 약간 더 흐려지는(+1 치우침) 대가가 있습니다.
    Q3. BRDF LUT는 왜 환경이 바뀌어도 다시 만들 필요가 없을까요? 다시 만들어야 하는 경우가 있다면? LUT는 BRDF(GGX + Smith + Schlick) 자체를 (n·v, 거칠기)에 대해 적분한 것이라 환경과 무관합니다. BRDF 모델 자체를 바꾸면(예: 다른 G 항, 천 재질용 BRDF 추가) 다시 만들어야 합니다.

    왜 필요한가횃불 80개가 있는 밤

    지금까지의 조명은 태양(방향광) 하나와 하늘(IBL)뿐이었습니다. 밤의 마을, 지하 던전, 실내 술집에서는 횃불·전구·스포트라이트 수십~수백 개가 장면을 밝힙니다. 이런 광원을 로컬 라이트라고 합니다. 위치가 있고, 영향이 미치는 범위(반경)가 있습니다.

    가장 단순한 구현은 픽셀 셰이더에서 모든 광원을 도는 것입니다. 그러면 비용은 (화면 픽셀 수) × (광원 수)입니다. 1920×1080 화면에 광원 100개면 프레임마다 2억 번의 셰이딩이고, 그중 대부분은 "이 광원은 여기에 닿지도 않는다"는 판정으로 끝나는 낭비입니다. 이 강의의 주제는 각 픽셀이 자기에게 닿는 광원만 보게 하는 법입니다. Phase 23의 DoD는 "수십~수백 개여도 클러스터드 라이트 컬링으로 버틴다"였습니다.

    핵심 개념감쇠 — 빛은 거리의 제곱으로 약해진다

    점광원에서 나온 빛은 구면으로 퍼지고, 구의 넓이는 반지름의 제곱에 비례하므로 단위 면적에 닿는 빛은 1/거리²로 줄어듭니다(역제곱 법칙). 문제는 두 가지입니다. 거리 0에서 무한대가 되고, 아무리 멀어도 0이 되지 않아 "영향 반경"이 없습니다. 반경이 없으면 클러스터에 넣을지 판정할 수 없습니다.

    ProjectE는 언리얼·Frostbite 방식대로 역제곱에 반경 창 함수를 곱합니다.

    거리 감쇠 (LightMath.h ↔ Lighting.hlsli) 감쇠(d) = [ 1 / (max(d, 10cm) / 100cm)² ] × [ saturate(1 − (d/R)4) ]²
    — 1m에서 정확히 1이므로 강도(Intensity) = 1m 거리에서의 밝기, 반경 R에서 정확히 0.

constexpr float MinDistance       = 10.0f;  // cm: 이보다 가까우면 역제곱을 고정 (특이점 방지)

// 반경 창: 1 (d = 0) → 0 (d >= Radius)
inline float DistanceWindow(float Distance, float Radius)

	const float Ratio2 = Ratio * Ratio;

    스포트라이트의 원뿔

    스포트라이트는 점광원에 방향 제한을 더한 것입니다. 광원 방향과 "광원 → 표면" 방향 사이 각의 코사인이 외부 원뿔의 코사인 이하면 0, 내부 원뿔 이상이면 1, 그 사이는 부드럽게 잇습니다. cos × Scale + Offset 형태로 미리 계산해 두면 셰이더는 곱셈·덧셈 한 번(FMA)과 saturate, 제곱만 하면 됩니다. 점광원은 Scale 0, Offset 1을 넣어 같은 코드를 지나가게 합니다(분기 없음).

    단위를 사람이 정하기 쉽게 "강도 = 1m 거리에서의 밝기"라서 레벨 디자이너는 "전구에서 1m 떨어진 탁자가 얼마나 밝아야 하나"로 값을 정할 수 있습니다. 색은 사람이 고르는 값이라 sRGB로 저장하고 GPU로 보낼 때 선형으로 바꿉니다(14강). 엔진 단위가 cm라서 기준 거리는 100입니다.

    점광원 큐브 그림자와 여백

    스포트라이트 그림자는 원근 투영 한 장이면 됩니다(시야각 = 2 × 외부 원뿔). 점광원은 사방을 비추므로 큐브의 여섯 면을 각각 90° 원근으로 그립니다. ProjectE는 큐브맵 대신 Texture2DArray 한 장에 1024×1024 타일을 쌓아(스포트 1장, 점광원 6장, 상한 36장) 모든 로컬 그림자를 담습니다.

inline float CubeFaceTanHalfFov(uint32 Resolution)

    목록에는 항상 상한이 있다 클러스터 하나에 63개, 프레임에 1024개, 그림자 36장. 상한 없이 가변 길이로 만들면 최악의 경우 메모리나 시간이 폭발합니다. 상한을 두고 "넘치면 무엇을 버리는가"를 정해 둡니다. 프레임 목록은 가까운 순이라 먼 광원이 빠지지만, 클러스터 목록은 목록 순서대로 넣고 넘치면 버리므로(LightMath.h 주석) 한 칸에 광원이 63개를 넘게 몰리는 배치는 피해야 합니다.

    정리
    • 거리 감쇠 = 1m 기준 역제곱(10cm 이하 고정) × 반경 창 (1 − (d/R)⁴)². 강도 = 1m에서의 밝기.
    • 스포트 원뿔 = saturate(cos × Scale + Offset)², 점광원은 Scale 0·Offset 1로 같은 코드.
    • 포워드+는 2D 타일, 클러스터드는 타일 × 로그 깊이 조각. ProjectE는 포워드 + 사전 패스 + 16×9×24 클러스터.
    • 클러스터마다 고정 64칸 [개수, 번호 63개]를 계산 셰이더가 채우고, 픽셀은 자기 칸만 돈다.
    • 로컬 그림자는 Texture2DArray 타일(스포트 1, 점광원 6, 최대 36). 큐브 면은 2텍셀 여백으로 조금 넓게.

    왜 필요한가"이미 그린 화면"은 공짜 정보다

    14~18강의 셰이딩은 픽셀 하나가 자기 표면과 광원만 압니다. 그런데 사실적인 화면에는 "주변"이 필요합니다. 구석은 빛이 덜 들어와 어둡고(앰비언트 오클루전), 바닥에는 옆 물체가 비치고(반사), 공기에는 빛줄기가 보이고(안개), 벽에는 낙서가 붙습니다(데칼). 이것을 3D 장면 전체로 정확히 계산하는 것은 비쌉니다(3부 후반의 레이 트레이싱).

    화면 공간(screen-space) 기법은 "이미 화면에 그려진 깊이·법선·색"만으로 이런 효과를 근사합니다. 화면 해상도에 비례하는 비용으로, 장면이 아무리 복잡해도 일정합니다. 대가는 "화면에 보이지 않는 것은 모른다"는 근본 한계입니다. Phase 33(화면 품질)은 이 기법들을 한꺼번에 들여왔고, 그 기반이 깊이 사전 패스입니다.

    핵심 개념깊이 사전 패스 — 모든 화면 효과의 재료

    메인 패스 전에 불투명 물체를 한 번 더 그리되, 비싼 조명 계산 없이 기하 정보만 렌더 타깃 여러 장(MRT)에 씁니다.

    사전 패스의 이점은 두 가지입니다.

    1. 덧칠(overdraw) 제거: 메인 패스를 깊이 테스트 EQUAL로 그리면, 사전 패스가 남긴 "가장 앞 표면"과 정확히 같은 깊이의 픽셀만 비싼 PBR 셰이더를 돌립니다. 가려진 픽셀은 셰이딩되지 않습니다.
    2. 재료 공급: 메인 패스 전에 화면 전체의 깊이·법선이 생기므로, SSAO·데칼·SSR을 메인 패스 전에 계산해 메인 패스가 결과를 읽을 수 있습니다(포워드 렌더러인 ProjectE에서 특히 중요합니다 — 18강).
    규칙: 같은 정점 셰이더 바이트코드 EQUAL 테스트는 두 패스가 계산한 깊이가 비트 단위로 같아야 통과합니다. 정점 셰이더가 조금만 달라도(연산 순서, 컴파일러 최적화) 마지막 비트가 달라져 픽셀이 사라집니다. 그래서 사전 패스는 메인과 같은 VS 바이트코드에 픽셀 셰이더만 PSPrepass로 바꿉니다. 지형 같은 새 메시 경로도 두 PSO에 같은 VS를 쓰고, 사전 패스에 반드시 그려야 합니다.

    법선은 팔면체(octahedral) 인코딩으로 두 채널에 담습니다. 단위 구를 팔면체에 투영해 펼치면 정사각형이 되므로, 3D 방향을 2D 좌표 두 개로 균일한 정밀도로 저장할 수 있습니다. 남는 B 채널에는 SSR이 쓸 거칠기를 넣습니다.

    핵심 개념사전 패스를 재활용하는 효과들

    SSAO — 구석의 어둠

    앰비언트 오클루전(AO)은 "이 점에서 보이는 하늘의 비율"입니다. 구석·틈·물체 아래는 주변 기하에 가려 환경광을 덜 받습니다. SSAO는 픽셀 주변의 깊이 버퍼를 둘러보며 "주변 표면이 얼마나 솟아 이 점의 반구를 가리는가"를 추정합니다. ProjectE는 수평선 각도를 재는 GTAO 방식을 반해상도로 계산하고, 깊이를 고려한 양방향(bilateral) 블러로 노이즈를 없앱니다(Phase 33 측정 0.03~0.046ms). 결과(R = 가시도, G = 뷰 깊이)는 메인 패스가 간접광(IBL)에만 곱합니다. 직접광의 가림은 그림자의 몫이기 때문입니다(14강).

    DBuffer 데칼 — 표면 위에 붙이는 머티리얼

    데칼은 상자 모양 투영기로, 상자 안에 들어온 표면에 텍스처(낙서, 핏자국, 녹)를 덮어씁니다. 표면의 월드 위치는 깊이에서 복원하고, 그 위치를 상자 로컬 좌표로 바꿔 UV로 씁니다. ProjectE는 언리얼 4의 DBuffer 방식을 택했습니다. 사전 패스 뒤 데칼 상자를 그려 베이스 컬러·노멀·거칠기/금속을 RGBA8 세 장(DBuffer A/B/C)에 쓰고, 메인 패스가 이 고정된 세 장을 읽어 자기 표면 값에 섞습니다(0.005ms). 메인 패스 셰이더가 데칼마다 다른 텍스처를 읽어야 하는 클러스터드 데칼은 바인드리스 텍스처가 필요해 택하지 않았습니다(DecalRenderer.h 머리 주석).

    볼류메트릭 안개 — 빛줄기가 보이는 공기

    화면을 160×90 칸 × 깊이 64조각의 3D 격자(froxel, 절두체 복셀)로 나눠, 칸마다 안개 밀도와 그 칸에 닿는 빛(방향광 그림자, 로컬 라이트)을 주입하고, 카메라에서 깊이 방향으로 적분해 "여기까지 오는 동안 쌓인 산란광과 투과율"을 저장합니다. 메인 패스 뒤에 전체 화면 패스가 픽셀 깊이로 이 볼륨을 읽어 색 × 투과율 + 산란으로 합칩니다(0.039 + 0.009ms). 반투명과 파티클은 자기 셰이더에서 같은 식(Fog.hlsli EvaluateFog)을 직접 부릅니다.

    SSR — 화면에서 광선 쏘기

    SSR(Screen-Space Reflections)은 픽셀의 반사 방향으로 광선을 쏘되, 3D 장면 대신 깊이 버퍼를 높이장처럼 따라가며 처음으로 표면 뒤로 들어가는 지점을 찾습니다. 찾으면 그 지점의 화면 색(지난 프레임 결과)이 반사 색입니다. 한 픽셀씩 걸으면 느리므로 Hi-Z(계층 깊이 — 밉마다 칸의 가장 가까운 깊이를 담은 피라미드)를 씁니다. 광선이 칸의 가장 가까운 면보다 앞에 있으면 그 칸 전체를 건너뛰고 더 거친 밉으로 올라가고, 부딪힐 것 같으면 고운 밉으로 내려옵니다. 큰 빈 공간은 몇 걸음에 지나갑니다.

    찾지 못하면(화면 밖, 물체 뒤) 17강의 반사 캡처 → 하늘 순으로 대체합니다. 시간 안정성을 위해 SSR이 어떻게 바뀌었는지는 20강의 주제입니다.

    핵심 개념TAA — 시간으로 안티에일리어싱

    래스터라이저는 픽셀 가운데 한 점만 봅니다. 그래서 가는 선과 대각선 가장자리가 계단(에일리어싱)이 되고, 카메라가 움직이면 계단이 기어갑니다. 픽셀 안을 여러 점으로 보면(MSAA, 슈퍼샘플링) 해결되지만 비쌉니다. TAA(Temporal Anti-Aliasing)는 프레임마다 픽셀 안의 다른 위치를 보도록 투영을 살짝 흔들고(지터), 지난 프레임들의 결과(이력)와 섞어 시간에 걸쳐 여러 점을 평균합니다.

    움직임 벡터 — 이력은 어디에 있었나

    카메라나 물체가 움직이면, 이번 프레임 픽셀 (x, y)에 보이는 표면은 지난 프레임에는 다른 위치에 있었습니다. 사전 패스는 정점마다 지터 없는 현재 클립 위치와 이전 클립 위치(이전 월드 행렬 × 이전 뷰-투영)를 계산해 그 차이(UV 단위, "현재 − 이전")를 씁니다. 스킨 메시는 이전 프레임 본 팔레트를 함께 갖고, 정적 인스턴스는 엔티티별로 이전 월드 행렬을 기록합니다(FInstanceGpuData의 PrevWorld). 물체가 없는 하늘 픽셀은 카메라 움직임만으로 재투영합니다.

    윤곽선 근처에서는 픽셀 하나에 앞 물체와 뒤 배경이 섞여 있습니다. 그 픽셀의 움직임 벡터를 그대로 쓰면 앞 물체 윤곽에 배경 이력이 끌려와 잔상이 생기므로, 3×3 이웃 중 가장 가까운 깊이의 움직임 벡터를 씁니다.

    • 반응형 마스크: 파티클처럼 움직임 벡터가 없는(깊이를 쓰지 않는) 것은 이력이 엉뚱한 곳을 가리킵니다. 그래서 씬 컬러 알파에 "반투명이 덮은 정도"를 쓰고(불투명 0), 알파가 큰 픽셀은 현재 프레임 비중을 0.6까지 올려 잔상을 줄입니다. 15강에서 씬 컬러의 알파를 투명도가 아닌 용도로 쓴다고 한 것이 이것입니다.

    이력이 유효한 조건

    지난 프레임과 이번 프레임이 "같은 화면의 연속"일 때만 이력을 씁니다. ProjectE의 조건은 한 렌더러가 연속 프레임에 뷰 하나만 그리고, 같은 씬, 같은 출력 크기이며, 카메라 컷이 아닐 때입니다. 카메라 컷은 한 프레임에 20m(2000cm) 넘게 이동하거나 60° 넘게 회전한 경우입니다. 하나라도 어기면 이력을 버리고 현재 프레임만 씁니다. 에디터의 에셋 미리보기처럼 한 렌더러로 여러 뷰를 번갈아 그리는 경우나, 픽셀 아트·와이어프레임에서는 TAA가 자동으로 꺼집니다.

    지터는 씬 컬러에 그리는 패스에만 그림자 캐스케이드, 클러스터, 컬링, LOD는 지터 없는 카메라로 계산합니다. 지터 카메라로 그림자 캐스케이드를 만들면 16강의 텍셀 스냅이 매 프레임 흔들려 그림자 가장자리가 떨립니다. 깊이 버퍼에 테스트하는 오버레이(에디터 그리드)가 이 차이 때문에 깜빡였던 이야기는 20강에서 봅니다.

    생각해 볼 문제

    Q1. 사전 패스가 있으면 메인 패스의 깊이 쓰기를 꺼도 될까요? 메인 패스의 깊이 테스트를 LESS_EQUAL로 해도 같은 결과일까요? 깊이는 이미 사전 패스가 다 썼으므로 메인 패스에서 쓰기를 꺼도 됩니다(대역폭 절약). LESS_EQUAL로 해도 정확히 같은 깊이가 통과하므로 결과는 같아 보이지만, EQUAL은 "사전 패스와 다른 깊이가 나오면 아예 안 그려짐"으로 불일치를 즉시 드러내 줍니다. 정점 셰이더가 달라 깊이가 조금 앞으로 나오는 버그를 LESS_EQUAL은 숨깁니다.
    Q2. 화면 공간 반사는 왜 화면 가장자리로 갈수록 반사가 끊기나요? 어떻게 감추나요? 반사 광선이 화면 밖으로 나가면 그 너머의 정보가 없습니다. 위를 보는 바닥 반사는 화면 위쪽으로 갈수록 대상이 화면 밖이 됩니다. 보통 화면 가장자리 근처에서 SSR의 신뢰도를 줄이고 반사 캡처·하늘로 부드럽게 넘깁니다. ProjectE는 남은 비중 방식(SSR → 캡처 → 하늘, 17강)으로 이 전환을 처리하고, 근본 해결은 3부 후반의 레이 트레이싱 반사입니다.
    Q3. 움직임 벡터를 지터가 들어간 위치로 계산하면 어떤 일이 생길까요? 정지한 물체도 프레임마다 지터만큼 "움직인" 것으로 기록되어, TAA가 이력을 엉뚱한 위치에서 읽습니다. 그러면 지터로 얻으려던 서브픽셀 평균이 상쇄되고 화면이 흔들립니다. 그래서 움직임 벡터는 지터 없는 위치(UnjitteredViewProjection) 기준이 규약입니다.

    왜 필요한가스크린샷으로는 보이지 않는 버그

    19강까지의 효과를 모두 켠 화면은 스크린샷 한 장으로 보면 훌륭했습니다. 그런데 2026-10-01 사용자 보고는 "화면이 지글거린다"였습니다. 카메라를 멈춰도 금속 벽의 반사가 방송 없는 TV처럼 자글자글 끓고, 에디터 바닥 그리드 선이 깜빡였습니다. 정지 사진에서는 보이지 않고 연속 프레임 사이의 차이로만 드러나는 문제 — 시간적 불안정(temporal instability)입니다.

    이 강의는 그 보고에서 시작해 며칠에 걸쳐 원인을 하나씩 고친 실제 과정을 따라갑니다. 결론부터 말하면, 고친 방법보다 중요한 것은 두 가지 교훈입니다. "확률적 효과를 TAA가 알아서 평균해 줄 것"이라는 기대가 틀릴 수 있다는 것, 그리고 안정성은 측정해야 고칠 수 있다는 것입니다.

    핵심 개념지수 이동 평균은 노이즈를 얼마나 줄이나

    현대 실시간 렌더링에는 "픽셀마다, 프레임마다 다른 무작위 표본을 하나 쓰고, TAA가 시간에 걸쳐 평균하게 한다"는 기법이 흔합니다. 거친 반사라면 GGX 로브에서 방향 하나를 뽑아 광선 하나만 쏘는 식입니다(확률적 반사, stochastic reflection). 픽셀당 비용은 광선 하나지만 여러 프레임을 평균하면 많은 광선을 쏜 것처럼 보이리라는 기대입니다.

    그런데 TAA의 누적은 19강에서 본 대로 이력 = lerp(이력, 현재, w), 즉 지수 이동 평균(EMA)입니다. 매 프레임 독립인 노이즈(분산 σ²)를 EMA로 평균하면, 수렴한 뒤의 분산은 다음과 같습니다.

    EMA의 정상 상태 분산 Var = σ² · w / (2 − w)   →   w = 0.1이면 표준편차 ≈ 0.23σ, w = 0.05여도 ≈ 0.16σ

    즉 현재 비중 0.1의 TAA는 노이즈를 1/4쯤으로 줄일 뿐 없애지 못합니다. 남은 노이즈는 매 프레임 다른 값이라 "끓는" 것처럼 보입니다. 비중을 더 낮추면 줄지만, 그만큼 움직일 때 잔상이 늘어납니다.

    클립이 노이즈를 더 키운다

    더 나쁜 일이 있습니다. TAA는 이력을 이웃 3×3 색 분산 상자로 자릅니다(19강). 노이즈 효과에서는 이것이 두 방향으로 실패합니다.

    • 노이즈가 이웃끼리 비슷하면(난수가 공간적으로 상관됨) 분산 상자가 좁게 잡혀 이력이 매번 잘려 나가고, 평균 자체가 일어나지 않습니다. 실제로 이 경우 사선 줄무늬가 매 프레임 이동하는 "물결 띠"가 생겼습니다.
    • 노이즈가 이웃끼리 제각각이면 상자가 넓어져 이력이 잘 남지만, 그만큼 진짜 변화(가려짐 해제)도 통과시켜 잔상이 생깁니다.

    ① 결정적 추적 + 반경 출력

    거칠기와 상관없이 거울 반사 방향으로 광선 하나를 쏩니다(19강의 Hi-Z 추적). 같은 장면, 같은 카메라면 매 프레임 같은 결과입니다. 대신 거친 면의 "흐린 반사"는 화면에서 흐려서 만듭니다. 흐림 반경은 GGX 반사 로브를 원뿔로 근사한 반각 θ로 정합니다: 퐁 지수 근사 p = 2/α² − 2, cosθ = 0.2441/(p+1). 화면 반경(픽셀) = 교차 거리 × tanθ × (픽셀 / 거리)인데, 이때 거리는 표면이 아니라 반사된 상의 깊이로 나눕니다. 거울 속 물체는 표면 뒤 교차 거리만큼 더 먼 곳에 있는 것처럼 보이기 때문입니다.

    // 원뿔 반각 = acos(0.244^(1/(p+1))), p = 2/alpha^2 - 2 (alpha = 거칠기^2, 퐁 지수 근사). 반환은 tan(반각)
static float ComputeSpecularConeTangent(float Roughness)
{
	const float Alpha = Roughness * Roughness;
	if (Alpha < 1.0e-3f) { return 0.0f; }
	const float Power    = FMath::Max(2.0f / (Alpha * Alpha) - 2.0f, 0.0f);
	const float CosAngle = std::pow(0.244f, 1.0f / (Power + 1.0f));
	return std::sqrt(FMath::Max(1.0f - CosAngle * CosAngle, 0.0f)) / FMath::Max(CosAngle, 1.0e-4f);
}
// 반사된 상의 뷰 깊이 = 표면 뷰 깊이 × (1 + 교차 거리 / 카메라 → 표면 거리)

static float ComputeSsrBlurRadiusPixels(float Roughness, float HitDistance, float PixelsPerUnit, float MaxRadius);

    ② 원판 흐림 — 왜 분리형이 아닌가

    가우시안 흐림은 보통 가로 한 번, 세로 한 번으로 나눠(분리형) 비용을 줄입니다. 2D 가우시안이 가로·세로 1D 가우시안의 곱이라 결과가 같기 때문입니다. 하지만 이 성질은 모든 픽셀이 같은 반경일 때만 성립합니다. SSR 흐림은 픽셀마다 반경이 다르고, "같은 면(법선 내적 > 0.9)만 섞는다"는 조건까지 있습니다. 가로 패스가 이미 자기 반경으로 흐린 값을 세로 패스가 다른 반경으로 다시 흐리면, 반사가 십자와 막대 모양으로 뭉개집니다.

    [loop] for (int Index = 0; Index < BlurTaps; ++Index)
{
	// 황금각 나선: 원판 면적을 고르게 덮는다 (반경 ∝ sqrt)
	const float  T      = ((float)Index + 0.5f) / (float)BlurTaps;
	const float  Angle  = (float)Index * 2.39996323f;
	const float2 Offset = Radius * sqrt(T) * float2(cos(Angle), sin(Angle));
	const int2   Tap    = clamp(int2(round(float2(Pixel) + Offset)), 0, MaxPix);
	if (dot(LoadBlurNormal(Tap), CenterNormal) > SameSurfaceMinDot)
	{
		const float W = exp(-2.0f * T); // 가우시안 (거리² / 반경² = T)
		Sum       += Premultiply(SsrCurrent.Load(int3(Tap, 0))) * W;
		WeightSum += W;
	}
}

    또 하나의 세부: 반사가 맞은 픽셀에만 반경을 주면, 빗나간 픽셀(캡처·하늘로 대체)은 흐려지지 않아 "맞음/빗나감" 경계가 칼로 자른 다각형이 됩니다. 빗나간 픽셀에도 최대 추적 거리 기준 반경을 줘서 경계까지 함께 흐립니다.

    ③ 반사 움직임으로 시간 누적

    결정적 추적에도 남는 것이 있습니다. 깊이 버퍼는 픽셀 단위라 반사된 물체의 윤곽은 계단 모양이고, 정지 화면에서는 TAA 지터가 이 계단을 평균해 줍니다. 그런데 카메라가 움직이면 다시 지글거렸습니다. SSR 결과를 누적할 때 표면의 움직임 벡터로 이력을 찾았기 때문입니다.

    if (Output.Color.a > 0.0f && HitDistance > 0.0f)
{
	const float3 ViewDirection = bOrthographic != 0 ? float3(0.0f, 0.0f, 1.0f) : normalize(SurfaceView);
	const float3 Virtual       = ScreenFromView(SurfaceView + ViewDirection * HitDistance);
	const float4 PrevClip      = mul(float4(Virtual.x * 2.0f - 1.0f, 1.0f - Virtual.y * 2.0f, Virtual.z, 1.0f), Reprojection);
	if (PrevClip.w > 1.0e-5f)
	{
		const float2 PrevUV = float2(PrevClip.x / PrevClip.w * 0.5f + 0.5f, 0.5f - PrevClip.y / PrevClip.w * 0.5f);
		Output.Motion.xy    = (float2(Pixel) + 0.5f) / ScreenSize - PrevUV;   // 반사 움직임 벡터 (두 번째 출력)
	}
}

    누적(PSResolve)은 반사가 맞은 픽셀은 이 반사 움직임으로, 빗나간 픽셀은 표면 움직임으로 이력을 찾고, TAA처럼 이웃 평균 ± γ·표준편차로 자른 뒤 섞습니다. HDR 밝은 표본이 평균을 지배하지 않게 휘도로 누른 공간에서 섞는 것도 TAA와 같습니다. 반사 색의 원본은 지난 프레임 TAA 결과(이미 안정된 화면)입니다.

    곡률 페이드 — 볼록 거울은 포기한다

    데칼 리벳 같은 작은 곡면은 볼록 거울처럼 넓은 장면을 작은 면적에 압축해 비춥니다. 지터로 반 픽셀만 움직여도 맞는 지점이 크게 바뀌고, 평면 거울 가정의 가상 점 재투영도 맞지 않아 깜빡였습니다. 같은 면 이웃 픽셀과의 법선 각을 픽셀 하나의 월드 크기로 나눠 곡률(1/반경)을 구하고(화면 해상도와 무관), 반경 20cm 이하는 SSR 신뢰도 0 → 60cm 이상은 1로 페이드해 캡처·하늘 반사에 맡깁니다. 75cm 크롬 공은 그대로 SSR을 받습니다.

    ProjectE에서는그리드 깜빡임과 음의 기울기 바이어스

    같은 날 함께 고친 다른 지글거림은 에디터 바닥 그리드였습니다. 씬의 깊이는 TAA 지터(최대 반 픽셀)가 들어간 투영으로 그려지는데, 그리드는 지터 없는 행렬로 그려 씬 깊이와 테스트합니다. Z = 0 바닥 평면과 그리드가 같은 평면에 있으면, 프레임마다 지터 방향에 따라 바닥의 깊이가 그리드보다 아주 조금 앞이기도 뒤이기도 해서 선이 켜졌다 꺼졌다 했습니다. 16강의 섀도우 애크니와 같은 구조 — 거의 같은 두 깊이의 비교 — 입니다.

    Desc.bDepthEnable = true;
Desc.bDepthWrite  = false; // 씬 깊이로 가려지기만 한다
Desc.DepthFunc    = D3D12_COMPARISON_FUNC_LESS_EQUAL;
// 씬 깊이는 TAA 지터(최대 반 픽셀)로 그려지고 그리드는 지터 없이 그리므로, Z=0 바닥과 겹치면 매 프레임 깊이 비교가 뒤집혀 선이 깜빡인다.
// 카메라 쪽으로 기울기 비례 바이어스(반 픽셀 × 두 축 + 여유)를 줘 바닥과 같은 평면에서는 항상 보이게 한다
Desc.DepthBias            = -8;
Desc.SlopeScaledDepthBias = -1.5f;

    반 픽셀 지터가 만드는 깊이 차이는 표면이 화면에서 기울어진 정도(깊이의 픽셀당 변화)에 비례하므로, 기울기 비례 바이어스가 정확히 맞는 도구입니다. 음수로 주면 그리드가 카메라 쪽으로 당겨져 같은 평면에서는 항상 이깁니다. 이 규칙은 "지터 없는 행렬로 씬 깊이에 테스트하는 오버레이는 음의 SlopeScaledDepthBias(+ 작은 DepthBias)를 준다"로 일반화되어 CLAUDE.md에 있습니다.

    화면 안정성을 숫자로 재기

    "덜 지글거린다"를 눈으로 판단하면 사람마다, 날마다 다릅니다. 처음에는 연속 프레임의 화면 전체 평균 차이를 쟀습니다(그리드·SSR 수정에서 0.89 → 0.04). 하지만 2026-10-04 기록은 이 지표가 국소적인 깜빡임과 넓은 얼룩을 놓쳤다고 적고, 더 엄격한 방법을 정했습니다.

    1. 수렴 뒤 연속 프레임: --exit-after 600 이상으로 이력이 충분히 쌓인 뒤 --screenshot-frames 32로 연속 32장을 저장합니다.
    2. 화소별 시간 표준편차 지도: 픽셀마다 32프레임 밝기의 표준편차를 구해 ×64 증폭한 이미지로 봅니다. 어디가 끓는지가 지도로 보입니다.
    3. 분위 지표: 표준편차의 99%·99.9% 분위와 1.0 초과 비율 — 평균에 묻히는 소수의 심한 픽셀을 잡습니다.
    4. 16×16 블록 평균의 시간 표준편차: 넓은 영역이 함께 밝아졌다 어두워지는 저주파 깜빡임 지표(8비트 양자화 경계 효과를 지움).
    5. 대조 실험: 영역 평균 시계열로 2프레임 주기 왕복을 확인하고, TAA를 끈 실행과 비교합니다. TAA와 효과를 모두 끄면 정지 장면의 표준편차는 0이어야 합니다.

    움직이는 경우는 에디터의 --verify-camera-pan <cm/프레임>로 편집 카메라를 일정하게 밀며 찍고, 효과를 끈 같은 경로와의 차이로 효과만 비교합니다. 자동 검증은 결정적이라(13강의 순서 보존, 15강의 프레임 시간) vsync 여부와 무관하게 결과가 같습니다 — 이것이 숫자 비교가 가능한 전제입니다.

    함정과 교훈"노이즈 + 누적"을 경계하라

    같은 함정, 다른 장소: DDGI 깜빡임 (2026-10-04) 3부 후반의 동적 GI(DDGI)에서도 같은 종류의 문제가 다시 나왔습니다. 프로브의 "텍셀 급변 감지" 문턱이 광선 노이즈에 걸려 프로브 단위로 깜빡였고(사용자 보고 "Tests/GI 깜빡임"), 그래서 기본값을 끄고 CPU에서 결정적으로 감지한 조명 변화에만 빠른 적응을 걸었습니다. 벽 옆 프로브를 밀어내는 재배치도 "미는 문턱 = 되돌아가는 문턱"이면 매 프레임 왕복해 깜빡여, 되돌아가는 문턱을 2배로 둔 히스테리시스를 넣었습니다. 노이즈 낀 신호로 이산적인 결정을 내리면, 그 결정이 프레임마다 뒤집힙니다.
    시간 변화가 있는 상태는 "시간"도 결정적으로 물·구름·머티리얼 Time, 자동 노출 적응처럼 시간에 따라 변하는 화면 상태는 실제 시각이 아니라 FFrameTime(앱 프레임 델타)을 씁니다(15강). 그래야 같은 실행이 같은 프레임 시퀀스를 만들어, 위의 연속 프레임 측정이 "효과의 노이즈"만 재게 됩니다.
    설계 순서: 결정적 필터 → 시간 누적 이번 과정의 결론은 "시간 누적은 남은 작은 계단을 다듬는 마지막 단계로 쓰고, 노이즈를 없애는 주 수단으로 쓰지 않는다"입니다. 먼저 같은 입력에 같은 출력을 내는 공간 필터(원판 흐림, 같은 면 조건)로 노이즈의 원천을 없애고, 남은 지터 수준의 차이만 누적이 평균하게 합니다. 3부 후반의 RT 그림자·RTAO도 "고정 패턴 표본(Bayer) → 결정적 공간 필터 → 시간 누적" 순서를 따릅니다.
    정리
    • EMA(현재 비중 w)는 독립 노이즈의 표준편차를 √(w/(2−w))배로만 줄인다. w = 0.1이면 약 0.23배 — 남은 노이즈가 끓어 보인다.
    • TAA의 분산 클립은 공간적으로 상관된 노이즈에서는 이력을 버려 평균조차 막는다.
    • SSR: 거울 방향 결정적 추적 → GGX 원뿔 반경의 48탭 황금각 원판 흐림(같은 면만) → 반사 움직임(가상 점) 재투영 누적 → 작은 곡면은 곡률 페이드.
    • 지터된 씬 깊이와 지터 없는 오버레이의 비교는 음의 기울기 비례 바이어스로 안정시킨다.
    • 안정성은 연속 프레임의 화소별·블록별 시간 표준편차로 재고, TAA·효과를 끈 실행과 대조한다.

    생각해 볼 문제

    Q1. 확률 반사의 노이즈를 TAA로 충분히 줄이려면 표준편차를 0.05σ 이하로 만들어야 한다고 합시다. 필요한 현재 비중 w는? 그때 생기는 부작용은? w/(2−w) ≤ 0.0025 → w ≈ 0.005입니다. 현재 프레임 비중이 0.5%라 새 정보가 이력에 반영되려면 수백 프레임이 걸리고, 물체가 움직이거나 조명이 바뀌면 몇 초 동안 잔상이 남습니다. 그래서 이 방법만으로는 안 되고, 결정적 필터나 공간 노이즈 제거가 필요합니다.
    Q2. 원판 흐림의 표본 위치를 프레임마다 회전시키면(무작위 회전) 표본 수를 줄일 수 있을 텐데, 왜 고정 위치를 썼을까요? 회전시키면 프레임마다 결과가 달라져 다시 시간 노이즈가 생기고, 그것을 누적으로 지워야 하는 처음 문제로 돌아갑니다. 48탭 고정이면 비용은 조금 더 들지만 같은 입력에 같은 출력이라 끓지 않습니다. SSR 흐림 패스는 화면 공간 한 패스라 48탭도 감당할 수 있는 비용이었습니다.
    Q3. 에디터 그리드의 깊이 바이어스를 양수(카메라에서 먼 쪽)로 주면 어떻게 될까요? 그리드가 바닥보다 항상 뒤로 밀려 Z = 0 바닥에서는 항상 가려집니다. 깜빡임은 사라지지만 바닥 위 그리드가 보이지 않게 됩니다. 그리드는 "바닥과 같은 평면에서는 보여야" 하므로 카메라 쪽(음수)으로 당겨야 합니다.
