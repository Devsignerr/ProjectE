    성능과 확장성

    기능이 다 들어간 엔진은 이제 "빠르게, 많이" 돌아가야 합니다. 그리는 횟수를 줄이고, 메모리를 아끼고, 끊김을 없애고, 정확히 재고, 여러 코어에 일을 나누는 방법을 ProjectE가 실제로 측정하며 내린 결정과 함께 배웁니다.

    드로우콜과 삼각형 줄이기

    관련 Phase: 26 · 29 (+ 2026-10-04 스킨 LOD) · 살펴볼 곳: Renderer/InstanceBatching.h, Renderer/MeshInstancing.h, Engine/Shaders/MeshInstance.hlsli, Renderer/MeshSimplifier.h/.cpp, Renderer/LodMath.h, Renderer/OcclusionCuller.h, Renderer/HzbMath.h
    이 강의를 마치면
    • 드로우콜이 왜 CPU를 잡아먹는지, 인스턴싱이 그 비용을 어떻게 없애는지 설명할 수 있습니다.
    • "묶음 키"를 비트로 구성해 정렬 한 번으로 묶음을 만드는 방법과, 셰이더가 SV_InstanceID로 자기 데이터를 찾는 방법을 압니다.
    • QEM(이차 오차 척도) 메시 단순화의 원리와 LOD를 화면 크기로 고르는 식, 팝핑을 막는 히스테리시스를 이해합니다.
    • HZB 오클루전 컬링의 원리를 알고, ProjectE가 측정 결과 이것을 기본으로 끈 이유를 설명할 수 있습니다.

    왜 필요한가그리는 데 드는 비용은 두 군데서 나온다

    한 프레임에 물체 2,400개를 그린다고 해 봅시다. 비용은 크게 두 곳에서 생깁니다.

    • CPU 쪽 — 드로우콜(draw call): GPU에 "이 메시를 이 머티리얼로 그려라"라고 명령을 기록하는 일입니다. 명령 하나하나는 작지만, 그 앞에 파이프라인 상태(PSO)·루트 시그니처를 바꾸고, 상수 버퍼와 텍스처 표를 묶고, 정점·인덱스 버퍼를 지정하는 일이 따라붙습니다. 이것을 물체 수만큼 반복하면 CPU가 GPU보다 먼저 지칩니다.
    • GPU 쪽 — 삼각형과 픽셀: 멀리 있어 화면에 몇 픽셀로밖에 보이지 않는 나무도 가까이 있을 때와 똑같이 수만 개의 삼각형을 처리하면 정점 셰이더와 래스터라이저가 낭비됩니다. 벽 뒤에 완전히 가려진 물체를 그리는 것도 낭비입니다.

    ProjectE는 Phase 26에서 이 둘을 정면으로 다뤘습니다. 측정용 씬(정적 메시 2,400개를 깐 StressStatic)에서 출발해 인스턴싱으로 드로우콜을, LOD로 삼각형을, HZB 오클루전으로 가려진 물체를 줄였고, 각각을 켜기 전후로 쟀습니다. 결과는 아래 표와 같습니다 — 그리고 마지막 줄이 이 강의의 교훈 하나입니다.

    핵심 개념드로우콜과 인스턴싱

    드로우콜 비용의 핵심은 "그리기 명령 자체"보다 명령 앞에 붙는 준비 작업의 반복입니다. 같은 나무 메시를 같은 머티리얼로 300번 그린다면 바뀌는 것은 월드 행렬(위치·회전·크기)뿐인데도, 개별 드로우에서는 매번 상태를 확인하고 상수를 올리고 명령을 기록합니다.

    GPU 인스턴싱(instancing)은 "같은 메시를 N번 그려라"를 명령 하나로 보내는 기능입니다. D3D12의 DrawIndexedInstanced(인덱스 수, 인스턴스 수, ...)가 그것이고, GPU는 정점 셰이더를 인스턴스마다 다시 돌리면서 SV_InstanceID(0, 1, 2, …)라는 번호를 넘겨줍니다. 셰이더는 이 번호로 버퍼에서 "몇 번째 인스턴스의 월드 행렬"을 읽어 오면 됩니다.

    인스턴싱에는 조건이 있습니다. 한 명령으로 묶이는 인스턴스는 메시와 파이프라인 상태, 머티리얼이 모두 같아야 합니다. 그러면 문제는 "프레임마다 수천 개 인스턴스를 어떻게 빠르게 같은 것끼리 모으느냐"가 됩니다. ProjectE의 답은 묶음 키(batch key)와 정렬입니다.

    묶음 키: 같은지 비교할 것들을 64비트 정수 하나에

    "PSO가 같고, 머티리얼이 같고, 메시가 같고, LOD가 같다"를 매번 네 번 비교하는 대신, 네 값을 비트로 이어 붙여 정수 하나로 만듭니다. 그러면 정수 정렬 한 번으로 같은 것끼리 이웃하게 되고, 이웃한 같은 키를 한 묶음으로 자르기만 하면 됩니다.

    // 일반 키: PSO 종류(3비트) | 머티리얼 슬롯(24비트) | 메시 슬롯(24비트) | LOD(4비트). 슬롯 번호는 핸들 Index (같은 프레임 안에서 유일)
constexpr uint64 MakeKey(uint32 Pipeline, uint32 Material, uint32 Mesh, uint32 Lod)
{
	return (static_cast<uint64>(Pipeline & 0x7u) << 52) | (static_cast<uint64>(Material & 0xFFFFFFu) << 28) |
	       (static_cast<uint64>(Mesh & 0xFFFFFFu) << 4) | static_cast<uint64>(Lod & 0xFu);
}

// 키 → 깊이 → 인스턴스 번호 순으로 정렬 (스레드 안전 — 임시 버퍼는 스레드별)
void SortFrontToBack(std::vector<FInstanceSortItem>& Items);

    정렬 기준이 "키 → 깊이 → 인스턴스 번호"라는 점도 눈여겨보세요. 같은 묶음 안에서도 카메라에 가까운 인스턴스를 먼저 그리면, 뒤에 그리는 먼 인스턴스의 픽셀이 깊이 테스트에서 일찍 버려집니다(초기 깊이 기각, early-Z). 마지막 기준인 인스턴스 번호는 깊이가 같을 때도 순서를 하나로 정해 주는 장치입니다 — 실행할 때마다 같은 순서로 그려야 화면이 비트 단위로 같아지고, 자동 검증 스크린샷 비교가 가능해집니다.

    셰이더는 자기 인스턴스를 어떻게 찾나

    왜 번호를 한 번 더 거칠까요(간접 참조)? 인스턴스 데이터를 패스마다 다시 올리지 않기 위해서입니다. 메인 패스, 그림자 캐스케이드 셋, 로컬 그림자, 에디터 아웃라인이 모두 같은 FMeshInstanceList를 공유하고, 각 패스는 "내가 그릴 번호들"(4바이트 정수 목록)만 따로 올립니다. 월드 행렬 하나가 64바이트, FInstanceGpuData 전체는 192바이트이므로 이 차이는 큽니다.

    설계 이유: 스킨 메시도 같은 틀로 (Phase 29) 처음(Phase 26)에는 스킨 메시가 인스턴스마다 본 팔레트가 달라 묶지 않았습니다. "인스턴스마다 다른 데이터"는 묶음을 깨는 이유가 아니라 오프셋 하나로 바꿀 수 있는 것이었습니다.

    핵심 개념QEM 메시 단순화 — LOD를 자동으로 만들기

    LOD(Level of Detail)는 같은 물체를 삼각형 수가 다른 여러 버전으로 준비해 두고, 멀리 있을 때는 거친 버전을 그리는 기법입니다. 문제는 거친 버전을 누가 만드느냐입니다. 아티스트가 손으로 만들 수도 있지만 ProjectE는 임포트할 때 자동으로 만듭니다(임포트 설정 GenerateLods/LodCount). 그 알고리즘이 QEM(Quadric Error Metric, 이차 오차 척도) 기반 모서리 붕괴입니다 — Garland와 Heckbert가 1997년에 발표한, 지금도 가장 널리 쓰이는 방법입니다.

    모서리 붕괴(edge collapse)

    단순화의 기본 동작은 하나입니다. 모서리 PQ를 골라 점 P를 Q로 옮겨 합칩니다. 그러면 PQ를 공유하던 삼각형 두 개가 넓이 0이 되어 사라지고, P에 붙어 있던 나머지 삼각형은 Q에 붙습니다. ProjectE는 P를 새 위치가 아니라 이미 있는 정점 Q로 옮기는 "반-모서리 붕괴(half-edge collapse)"를 씁니다. 새 정점이 생기지 않으므로 LOD는 원본(LOD0)의 정점 버퍼를 그대로 공유하고 인덱스 버퍼만 새로 만들면 됩니다.

    이차 오차의 직관

    원래 메시의 각 삼각형은 하나의 평면 n·x + d = 0에 놓여 있습니다(n은 단위 법선). 점 x에서 이 평면까지 거리는 |n·x + d|이고, 그 제곱은 x에 대한 이차식입니다. 정점마다 주변 삼각형 평면들의 거리 제곱을 모두 더한 식 K를 만들어 두면, "이 정점을 x로 옮기면 원래 주변 면들에서 얼마나 벗어나는가"를 K(x) 한 번 계산으로 알 수 있습니다. 이차식은 대칭 4×4 행렬로 표현되어 계수 10개만 저장하면 되고, 두 이차식을 합치는 것도 계수끼리 더하기일 뿐입니다.

    // 대칭 4x4 이차식 (평면 a x + b y + c z + d = 0의 제곱 거리 합)
struct FQuadric
{
	double A[10] = {}; // aa ab ac ad bb bc bd cc cd dd

	void AddPlane(double Na, double Nb, double Nc, double D, double Weight) { ... }
	double Evaluate(const FVector3& P) const; // x^T K x
};
...
// 삼각형마다: 법선 N, 가중치 = 삼각형 넓이 (0.5 * |외적|)
Plane.AddPlane(N.X, N.Y, N.Z, D, 0.5 * Length);
...

FQuadric Combined = Quadrics[From];

    가중치를 삼각형 넓이로 주는 이유는, 큰 면에서 벗어나는 것이 작은 조각에서 벗어나는 것보다 눈에 더 띄기 때문입니다. 오차가 똑같이 0인 평평한 면에서는 짧은 모서리부터 붕괴하도록 아주 작은 항을 더해, 가늘고 긴 삼각형이 덜 생기게 합니다.

    단순화가 망가뜨리면 안 되는 것들

    이론은 간단하지만 실제 메시에서는 지켜야 할 조건이 많습니다. MeshSimplifier.h 머리 주석에 적힌 규칙을 정리하면 이렇습니다.

    • 위치가 같은 정점은 하나의 "위치"로: UV나 법선이 갈라지는 이음매(seam)에서는 같은 자리에 정점이 여러 개 있습니다. 붕괴는 위치 단위로 하고, 각 속성 정점은 Q 쪽의 짝 정점으로 바뀝니다. 짝이 없으면 붕괴하지 않으므로 이음매를 가로질러 UV가 섞이지 않습니다.
    • 열린 경계는 경계를 따라서만, 삼각형 3개 이상이 공유하는 비다양체 모서리의 위치는 고정합니다.
    • 뒤집힘 금지: 붕괴 뒤 어떤 삼각형의 법선이 원래와 78도 이상 꺾이면(내적 ≤ 0.2) 그 붕괴는 하지 않습니다.
    • 와인딩(CW) 유지, 원본이 64삼각형 미만이거나 직전 LOD보다 85% 넘게 남으면(덜 줄면) 거기서 LOD 생성을 멈춥니다.

    기본 LOD는 원본 대비 삼각형 비율 100% / 50% / 25% / 10%로 4단계이고, 앞 LOD에서 이어서 단순화합니다.

    핵심 개념LOD 선택: 화면 크기와 히스테리시스

    LOD를 거리로 고르면 문제가 있습니다. 같은 10m 거리라도 망원 렌즈(좁은 시야각)로 보면 크게 보이고, 화면 해상도가 다르면 픽셀 수가 다릅니다. 그래서 ProjectE는 언리얼처럼 화면 크기(screen size) — 경계 구의 지름이 화면 높이에서 차지하는 비율 — 로 고릅니다.

    화면 크기 식 원근 투영에서 거리 D에 있는 반지름 R의 구가 화면 세로에서 차지하는 비율은 R / (D · tan(세로 시야각 / 2))입니다. 화면 높이의 절반이 거리 D에서 D·tan(θ/2)만큼의 월드 크기를 덮기 때문입니다. 1이면 화면 높이만큼, 0.1이면 화면 높이의 10%. 직교 카메라는 2R / 직교 높이입니다. 카메라가 구 안에 있으면 아주 큰 값(→ LOD0)을 돌려줍니다.

    임계값은 LOD마다 { 1.0, 0.5, 0.25, 0.12 }입니다. 화면 크기가 0.5보다 작아지면 LOD1, 0.25보다 작으면 LOD2 … 하는 식입니다.

    팝핑과 히스테리시스

    LOD가 바뀌는 순간 모양이 툭 바뀌는 것을 팝핑(popping)이라고 합니다. 한 번은 참을 만하지만, 카메라가 임계값 근처에서 조금씩 흔들리면(캐릭터가 걸으면 카메라가 들썩입니다) LOD가 프레임마다 왔다 갔다 하며 깜빡입니다. 해결책은 히스테리시스(hysteresis) — 내려갈 때와 올라갈 때 문턱을 다르게 두는 것입니다. 온도 조절기가 22도에서 켜고 24도에서 끄는 것과 같은 원리입니다.

    constexpr float DefaultHysteresis = 0.1f; // 전환 여유: 임계값의 ±10% 띠 안에서는 이전 LOD 유지

// 낮은 품질로 내려가려면 화면 크기 < T × (1 - H), 높은 품질로 올라가려면 >= T × (1 + H).
//   = clamp(이전, SelectLod(크기 / (1 - H)), SelectLod(크기 / (1 + H)))
inline uint32 SelectLodWithHysteresis(float ScreenSize, const float* Thresholds, uint32 LodCount, float Scale, uint32 PreviousLod,
                                      float Hysteresis = DefaultHysteresis)
{
	const float H = FMath::Clamp(Hysteresis, 0.0f, 0.9f);
	if (PreviousLod >= LodCount || H <= 0.0f)
	{
		return SelectLod(ScreenSize, Thresholds, LodCount, Scale);
	}
	const uint32 Finest   = SelectLod(ScreenSize / (1.0f - H), Thresholds, LodCount, Scale); // 이보다 높은 품질은 유지 불가
	const uint32 Coarsest = SelectLod(ScreenSize / (1.0f + H), Thresholds, LodCount, Scale); // 이보다 낮은 품질은 유지 불가
	return FMath::Clamp(PreviousLod, Finest, Coarsest);
}

    이 구현은 짧지만 영리합니다. 화면 크기를 (1−H)로 나눠 "조금 더 크게 본다면 고를 LOD"와 (1+H)로 나눠 "조금 더 작게 본다면 고를 LOD"를 구하고, 이전 LOD를 그 사이로 자릅니다. 띠 안이면 이전 값이 그대로 살아남고, 띠를 벗어나면 경계로 끌려갑니다. 이 함수는 "이전 LOD"를 기억해야 하므로 렌더러가 엔티티별로 지난 프레임 LOD를 보관합니다.

    규칙: 그림자도 같은 LOD를 쓴다 LOD는 FSceneRenderer::SelectLods가 메인 카메라 화면 크기로 한 번 고르고, 사전 패스·메인·그림자 패스가 같은 값을 씁니다. 한 프레임 안에서 패스마다 LOD를 따로 고르면 같은 물체가 패스마다 다른 모양이 되어 물체와 그림자가 어긋날 수 있습니다. 그래서 그림자 LOD를 따로 고르는 코드도 이 선택 경로를 공유해야 합니다(CLAUDE.md "성능(Phase 26)").

    스킨 메시 LOD: 정점을 바꾸지 않는다는 것의 가치

    QEM 반-모서리 붕괴가 "기존 정점만 쓴다"는 성질은 스킨 메시(뼈로 움직이는 캐릭터)에서 빛을 발했습니다. 스킨 메시는 정점마다 뼈 번호·가중치를 담은 두 번째 정점 스트림(FSkinVertex, 슬롯 1)을 가집니다. 정점이 그대로이므로 LOD는 이 스킨 스트림까지 그대로 공유하고 인덱스만 바꾸면 됩니다. 2026-10-04 이 작업으로 Tests/Stress의 삼각형은 2.38M → 0.86M(그림자 4.87M → 1.82M), GPU는 7.6 → 5.2ms가 되었습니다.

    캐릭터는 가까이서 모양 변화가 잘 보이므로 정적 메시보다 보수적으로 고릅니다. 화면 크기에 r.LOD.SkinnedScale(기본 2)을 곱해 LOD0을 더 멀리까지 유지하고, r.LOD.Skinned 0(--no-skinned-lod)이면 이전과 비트 동일한 화면으로 돌아갑니다. 반대로 정점을 새로 만들거나 버리는 경로(잎 솎아내기, 삼각형 상한 MaxTriangles)는 스킨 스트림과 어긋나므로 정적 메시 전용으로 남겨 두었습니다.

    핵심 개념HZB 오클루전 컬링

    프러스텀 컬링(시야 밖 제거)은 이미 하고 있습니다. 남은 낭비는 시야 안에 있지만 앞의 벽에 가려진 물체입니다. 이를 걸러내는 것이 오클루전 컬링이고, GPU에서 하는 대표적인 방법이 HZB(Hierarchical Z-Buffer, 계층 깊이 버퍼)입니다.

    아이디어는 이렇습니다. 깊이 버퍼를 2×2씩 묶어 가장 먼 값(최댓값)으로 줄인 밉 체인을 만듭니다. 그러면 높은 밉의 텍셀 하나는 "이 넓은 영역에 그려진 것들 중 가장 먼 깊이"를 뜻합니다. 물체의 경계 상자를 화면에 투영했을 때, 그 사각형을 덮는 텍셀들의 최댓값보다 물체의 가장 가까운 점이 더 멀다면 — 그 영역의 모든 픽셀이 물체보다 앞에 있는 무언가로 이미 덮여 있다는 뜻이므로 물체는 완전히 가려졌습니다.

    2단계 컬링: 닭과 달걀 문제

    HZB를 만들려면 깊이 버퍼가 필요하고, 깊이 버퍼를 만들려면 먼저 그려야 합니다. 그래서 FOcclusionCuller는 두 단계로 나눕니다.

    1. 1단계: 지난 프레임의 HZB(와 그 프레임의 뷰-투영)로 판정해 보이는 것만 그립니다.
    2. 지금까지 그린 깊이로 이번 프레임 HZB를 만듭니다.
    3. 2단계: 1단계에서 가려졌다고 판정된 것만 이번 HZB로 다시 검사해, 실제로는 보이는 것(카메라가 움직여 새로 드러난 물체)을 같은 프레임에 그립니다.

    지난 프레임 정보만 쓰면 새로 드러난 물체가 한 프레임 늦게 "뿅" 나타나는데, 2단계가 이것을 막습니다. 판정과 드로우 인자는 모두 GPU 계산 셰이더가 쓰고, 드로우는 ExecuteIndirect로 CPU가 결과를 기다리지 않습니다. 판정 식은 CPU 참조 구현(HzbMath.h)과 셰이더(OcclusionCulling.hlsl)가 같은 식이며 OcclusionTests가 검증합니다.

    함정과 교훈잰 결과가 직관을 이긴다

    왜 필요한가VRAM은 한정되어 있고, 로딩은 프레임을 멈춘다

    게임이 맵을 옮겨 다닐 때마다 메시와 텍스처를 새로 불러온다고 해 봅시다. 이전 맵의 리소스를 아무도 해제하지 않으면 맵을 다섯 번 오가는 사이 VRAM이 바닥납니다. 반대로 아직 쓰는 텍스처를 실수로 해제하면 화면이 깨지거나 GPU가 해제된 메모리를 읽다가 장치가 제거(device removed)됩니다.

    또 하나의 문제는 시간입니다. 2048×2048 텍스처 하나를 디스크에서 읽고, 압축을 풀고, GPU로 복사하는 데는 수 밀리초에서 수십 밀리초가 걸립니다. 이것을 메인 스레드에서 하면 그동안 프레임이 멈춥니다(끊김, hitch). 마지막으로, 멀리 있어 화면에 50픽셀로 보이는 물체에 2048 해상도 텍스처 전체를 VRAM에 올려 두는 것도 낭비입니다.

    ProjectE는 이 세 가지를 순서대로 풀었습니다. Phase 37에서 리소스 수거와 비동기 업로드, Phase 53에서 텍스처 밉 스트리밍입니다.

    핵심 개념도달성 표시로 수거하기

    "아무도 안 쓰는 리소스"를 찾는 고전적 방법은 두 가지입니다.

    • 참조 카운트(reference counting): 리소스를 쥘 때마다 +1, 놓을 때마다 −1, 0이 되면 해제. 정확하지만 핸들을 복사하고 지우는 모든 곳에서 카운트를 맞춰야 합니다. ProjectE의 리소스 핸들(FMeshHandle 등)은 컴포넌트에 값으로 저장되고 JSON에서 읽히고 복사되는 평범한 구조체라, 카운트를 강제하기 어렵습니다.
    • 도달성 표시(mark & sweep): 가비지 컬렉터의 방식입니다. "지금 확실히 쓰는 것들"(루트)에서 출발해 참조를 따라가며 닿는 것에 표시를 하고, 표시되지 않은 것을 해제합니다. 핸들 자체는 아무것도 몰라도 됩니다.

    ProjectE는 두 번째를 골랐습니다. 대신 매 프레임이 아니라 필요할 때만(맵 전환, 서브 씬 내림, 에디터 씬 열기/플레이 정지, 썸네일 대기열 비움, 콘솔 r.CollectResources) 돌립니다.

	void AddScene(FScene& Scene); // 씬 컴포넌트의 핸들: 정적 메시(메시/머티리얼 — 모델 노드 포함), 데칼 머티리얼
};
using FResourceRootProvider = std::function<void(FResourceRoots&)>;
    규칙: 경로 핸들을 오래 드는 새 코드는 루트를 등록한다 렌더러 캐시, 편집기, 앱처럼 씬 밖에서 경로 핸들을 프레임을 넘겨 쥐는 코드는 FResourceManager::AddRootProvider로 제공자를 등록하고 Shutdown에서 RemoveRootProvider합니다. 미리보기처럼 새 씬 컨테이너를 만들면 제공자 안에서 FResourceRoots::AddScene을 부릅니다. 등록을 잊으면 수거 뒤 그 핸들은 해제된 리소스를 가리키고, 화면에는 기본 리소스가 대신 보이게 됩니다.

    수거 요청은 바로 처리하지 않고 2틱 뒤(FResourceManager::Tick)에 처리합니다. 맵을 막 바꾼 순간에는 새 씬의 에셋 해석·렌더러 캐시가 아직 루트를 채우지 않았기 때문입니다. 새 씬이 한 번 그려져 루트가 모두 채워진 뒤에 수거합니다. Phase 37 측정에서 런타임 맵 A↔B 왕복 6회 동안 메모리가 평탄했고(이전 맵의 머티리얼·텍스처만 오감), 에디터는 썸네일 해제로 VRAM 354.6 → 203.7MB가 되었습니다.

    핵심 개념복사 큐와 업로드 링

    GPU 메모리에 데이터를 넣으려면 먼저 CPU가 쓸 수 있는 업로드 힙(스테이징 메모리)에 쓰고, GPU에게 "여기서 저기로 복사하라"는 명령을 내려야 합니다. 가장 쉬운 구현은 이렇습니다: 업로드 버퍼를 만들고, 복사 명령을 기록하고, 실행하고, 끝날 때까지 CPU가 기다린다. 마지막 줄이 끊김의 원인입니다.

    D3D12 GPU에는 그리기용 직접 큐(direct queue) 말고 복사 전용 복사 큐(copy queue)가 따로 있어, 그리기와 동시에 복사를 진행할 수 있습니다. ProjectE의 FD3D12UploadQueue는 이 복사 큐와 64MB 영구 매핑 링 버퍼로 업로드를 기다림 없이 흘려보냅니다.

    리소스 상태와 큐의 규칙

    D3D12에서 리소스는 항상 어떤 "상태"(복사 대상, 셰이더 읽기, 렌더 타깃 …)에 있고, 상태를 바꾸려면 배리어(전이)를 기록해야 합니다. 그런데 복사 큐는 셰이더 읽기 상태로 전이할 수 없습니다(그 상태는 그리기 큐의 개념이므로). 이 제약에서 ProjectE의 규칙이 나옵니다.

    //   리소스 상태 규칙 (D3D12 복사 큐):
//     - 대상은 COMMON으로 만든다. 복사 큐에서 COPY_DEST로 암시적 승격, ExecuteCommandLists가 끝나면 COMMON으로 감쇠
//     - 텍스처는 완료 후 직접 큐에서 COMMON → PIXEL_SHADER_RESOURCE로 명시 전이한다 (기존 텍스처와 같은 상태 불변식)
//     - 버퍼는 전이하지 않는다 (직접 큐에서 VB/IB 등으로 암시적 승격 — 기존 정적 버퍼와 같음)
//   준비 판정: 대상의 펜스 <= GetFinalizedFence()면 사용 가능 (전이가 그 프레임 명령 리스트 맨 앞에 기록됨)

    "암시적 승격(promotion)과 감쇠(decay)"는 D3D12가 COMMON 상태 리소스에 허용하는 지름길입니다. 복사 큐가 COMMON 리소스에 복사하면 자동으로 COPY_DEST처럼 취급되고, 명령 리스트 실행이 끝나면 다시 COMMON으로 돌아갑니다. 덕분에 복사 큐 명령 리스트에는 배리어를 하나도 넣지 않아도 됩니다. 그래서 "복사 큐 명령 리스트에 다른 상태 전이를 넣지 않는다"가 규칙이 됩니다.

    링 버퍼: 스테이징 메모리를 재활용하기

    스테이징 메모리는 복사가 GPU에서 끝날 때까지 살아 있어야 합니다. 업로드마다 버퍼를 만들고 지우면 할당 비용이 크므로, 큰 버퍼 하나를 원형으로 돌려 씁니다.

    작업 스레드에 무엇을 맡기나

    파일 읽기, PNG/JPG 디코드, BC 압축, 모델 파싱은 CPU를 오래 쓰지만 엔진 상태를 건드리지 않습니다. 이런 일은 FJobQueue의 작업자 스레드로 보냅니다. 반면 GPU 리소스 만들기, ECS(씬) 수정, 리소스 관리자 갱신은 메인 스레드의 완료 콜백에서만 합니다.

    // 작은 작업자 스레드 풀 + 메인 스레드 완료 대기열.
//   - Submit(작업, 완료): 작업은 작업자 스레드에서, 완료 콜백은 메인 스레드가 PumpCompletions를 부를 때 실행된다
//   - 작업에서는 파일 읽기/디코딩/압축/파싱만 한다. ECS·GPU·리소스 관리자 접근은 완료 콜백(메인 스레드)에서
void Submit(FWork Work, FCompletion Completion = {});
uint32 PumpCompletions();

    이 선 긋기 덕분에 엔진의 거의 모든 코드는 "메인 스레드에서만 불린다"는 가정을 그대로 유지하고, 잠금(lock)을 새로 넣지 않아도 됩니다. 병렬화를 위해 엔진 전체를 스레드 안전하게 바꾸는 대신, 스레드에 넘기는 일의 종류를 좁힌 것입니다. Phase 37 측정에서 PixelArt 맵 로드의 메인 스레드 시간이 821 → 약 300ms, 쿠킹 캐시가 없는 Materials 씬은 131 → 12ms가 되었습니다.

    로딩 방식 CVar r.AsyncLoading -1(자동) = 사람이 쓰는 실행은 비동기, 자동 검증은 비동기이지만 프레임마다 비우기(모두 끝날 때까지 기다림) / 0 = 동기 / 1 = 비동기 / 2 = 비우기. 자동 검증이 "비우기"인 이유는 결정성입니다. 비동기로 두면 어떤 텍스처가 몇 번째 프레임에 준비되는지가 실행마다 달라져 스크린샷이 흔들립니다. 단위 테스트·도구는 비동기를 켜지 않습니다(동기). 끊김은 --log-hitches [ms]로 잽니다.

    핵심 개념텍스처 밉 스트리밍

    텍스처는 원본과 함께 가로세로를 반씩 줄인 밉맵(mipmap) 체인을 가집니다(2048, 1024, 512 …). GPU는 화면 픽셀 하나에 텍셀이 몇 개 들어가는지를 보고 알맞은 밉을 골라 읽습니다. 먼 물체는 작은 밉만 읽는데도, 보통은 전체 밉 체인을 VRAM에 올려 둡니다 — 밉 0(원본)이 전체 용량의 약 3/4을 차지하는데 말입니다.

    밉 스트리밍은 "이번 화면에 실제로 필요한 가장 세밀한 밉"까지만 VRAM에 두는 기법입니다. 질문은 셋입니다. 필요한 밉을 어떻게 계산하나, VRAM에서 어떻게 일부 밉만 두나, 예산이 모자라면 무엇을 줄이나.

    필요 밉 계산

    하드웨어가 고르는 밉(LOD)은 대략 log2(픽셀 하나가 덮는 텍셀 수)입니다. 이것을 CPU에서 미리 추정합니다.

    식 (TextureStreamingMath.h 머리 주석) ① 픽셀 하나가 덮는 월드 크기 CmPerPixel = 2 · 시야 깊이 · tan(세로 시야각/2) / 화면 높이 (직교: 직교 높이 / 화면 높이)
    ② 텍셀/픽셀 = 텍스처 큰 변 × UV 밀도(UV/cm) × CmPerPixel
    ③ LOD ≈ log2(텍셀/픽셀) + 밉 바이어스(TAAU, 네이티브는 0)
    ④ 필요한 최상위 밉 = floor(LOD) − 여유(기본 1밉), 0 아래면 0 
    uint32 TextureStreamingMath::ComputeRequiredTopMip(uint32 TextureMaxSize, float Log2UvPerPixel, float MipBias, int32 Margin, uint32 MipCount)
{
	...
	const float Lod = std::log2(static_cast<float>(TextureMaxSize)) + Log2UvPerPixel + MipBias;
	const float Top = std::floor(Lod) - static_cast<float>(Margin);
	if (!(Top > 0.0f))
	{
		return 0;
	}
	return std::min(static_cast<uint32>(std::min(Top, 64.0f)), MipCount - 1);
}

    이 식에는 의도적으로 보수적인(필요보다 더 세밀한 쪽으로 틀리는) 선택이 여럿 들어 있습니다.

    • 시야 깊이는 경계 상자의 가장 가까운 깊이입니다. 원근 투영에서 픽셀 크기는 거리보다 깊이에 비례하고, 깊이 ≤ 거리이므로 더 세밀한 쪽으로 틀립니다.
    • UV 밀도는 메시마다 쿠킹할 때 한 번 계산합니다. 삼각형마다 √(UV 면적 / 월드 면적)을 구하고 월드 면적으로 가중한 하위 1%를 씁니다. 밀도가 낮을수록(UV가 늘어난 곳) 더 세밀한 밉이 필요하므로 낮은 쪽이 기준입니다. 인스턴스 밀도는 메시 밀도 ÷ 가장 큰 축 스케일입니다.
    • 여유 1밉이 이방성 필터, 축마다 다른 UV 늘어남, 삼각형별 밀도 차이를 흡수합니다(r.Streaming.MipMargin).

    VRAM에 일부 밉만 두는 방법 — 새 텍스처와 SwapContents

    D3D12에는 "밉 일부만 메모리에 두는" 타일드 리소스(reserved resource) 기능도 있지만, ProjectE는 더 단순한 방식 (a)를 택했습니다. 상주 범위가 바뀌면 그 범위만 가진 새 텍스처를 통째로 만듭니다. 쿠킹 파일에서 필요한 밉만 범위 읽기(FFileSystem::ReadFileRange, pak 포함)로 읽어 복사 큐로 올리고, 업로드가 끝나면 리소스 풀 슬롯의 내용을 바꿉니다(FD3D12Texture::SwapContents). 핸들은 그대로이므로 텍스처를 가리키는 쪽은 아무것도 몰라도 됩니다. 단, 머티리얼의 텍스처 표(디스크립터)는 새 리소스를 가리키도록 RefreshMaterialTextures로 다시 만듭니다.

    규칙: 텍스처 SRV/디스크립터를 프레임을 넘겨 캐시하지 않는다 SwapContents 뒤에는 옛 리소스와 SRV가 지연 해제됩니다. 디스크립터를 따로 저장해 두고 다음 프레임에 쓰는 코드는 해제된 리소스를 가리키게 됩니다. 머티리얼 밖에서 텍스처를 쓰는 새 코드(UI·파티클 등)는 공개 LoadTexture로 불러 "고정"(항상 전체 밉)으로 둡니다.

    왜 "크기가 2k로 나누어떨어져야" 할까요? 하드웨어가 고르는 LOD는 "화면 미분 × 텍스처 크기"의 log2입니다. 1000×1000 텍스처의 밉 3은 125(= 1000/8, 정확히 나누어떨어짐)이므로, 밉 3을 새 밉 0으로 하는 텍스처는 원래보다 LOD가 정확히 3 작게 계산되어 원래와 같은 밉을 같은 비율로 섞어 읽습니다. 그러나 밉 4는 62.5를 내림한 62입니다. 밉 4를 새 밉 0으로 하면 62 ≠ 1000/16이라 LOD가 미세하게 어긋나고, 두 밉 사이 보간 비율이 달라져 픽셀 값이 바뀝니다. BC 압축은 4×4 블록 단위이므로 새 밉 0이 4의 배수여야 한다는 조건이 더해집니다. 이 조건들을 지키면 필요한 밉이 모두 상주하는 한 전체 밉 텍스처와 비트 단위로 같은 값을 읽습니다.

    내릴 때는 늦게 — 히스테리시스

    29강의 LOD와 같은 문제가 여기에도 있습니다. 카메라가 조금 멀어졌다고 바로 밉을 내리고, 다시 다가왔다고 바로 올리면 디스크 읽기와 업로드가 끝없이 반복됩니다. 그래서 올리기(더 세밀하게)는 즉시, 내리기는 r.Streaming.DropDelay(기본 2초) 동안 계속 덜 필요할 때만 합니다.

    uint32 TextureStreamingMath::UpdateHysteresis(FHysteresisState& State, uint32 WantedTop, float DeltaSeconds, float DropDelaySeconds)
{
	if (State.HeldTop == InvalidMip || WantedTop <= State.HeldTop) // 처음이거나 더 세밀한 밉이 필요 → 바로
	{
		State.HeldTop      = WantedTop;
		State.LowerSeconds = 0.0f;
		return State.HeldTop;
	}
	State.LowerSeconds += std::max(DeltaSeconds, 0.0f);
	if (State.LowerSeconds >= DropDelaySeconds)                    // 덜 세밀해도 되는 상태가 충분히 계속됨
	{
		State.HeldTop      = WantedTop;
		State.LowerSeconds = 0.0f;
	}
	return State.HeldTop;
}

    예산이 모자라면 — 우선순위와 고른 축소

    스트리밍 텍스처의 상주 합에는 예산(r.Streaming.PoolSizeMB, 0 = 자동: VRAM 예산의 40%, 256MB~4GB)이 있습니다. 모두 원하는 밉으로 두면 넘칠 때, FitToBudget은 "우선순위 × (이미 줄인 단계 + 1)"이 가장 작은 텍스처부터 한 밉씩 줄입니다. 우선순위는 화면 크기와 메인 뷰 여부로 정합니다(메인 프러스텀 밖 그림자 캐스터는 낮게). 곱하는 항 덕분에 한 텍스처만 계속 깎이지 않고 여러 텍스처가 고르게 줄어듭니다. 값이 같으면 번호가 작은 쪽을 골라 결과가 결정적입니다. 한 밉을 줄이면 그 텍스처 용량이 약 1/4로 줄어드므로 몇 단계면 대개 예산 안에 들어옵니다.

    Phase 53 측정에서 (당시) Showcase 씬의 텍스처 VRAM이 29.1 → 10.2MB가 되었습니다.

    함정과 교훈"켜도 화면이 같다"를 증명하기

    스트리밍은 화질을 바꿀 수 있는 최적화입니다. 그래서 ProjectE는 처음부터 목표를 "스트리밍을 켠 화면이 끈 화면(--no-texture-streaming)과 비트 동일"로 잡았습니다. 이것을 가능하게 한 장치들을 보면 결정성 설계가 무엇인지 알 수 있습니다.

    • 필요 밉 식은 보수적(깊이·하위 1% 밀도·여유 1밉)이어서 실제 하드웨어가 읽는 밉은 항상 상주 범위 안입니다.
    • 새 텍스처의 크기 조건(2k 나누어떨어짐)으로 같은 밉을 같은 값으로 읽습니다.
    • 자동 검증은 시간에 기대지 않는다: 자동 검증·동기 로딩에서는 처음에 전체 밉으로 올린 뒤 첫 보고에서 바로(지연 없이) 필요 밉으로 내리고, 더 세밀한 밉이 필요해지면 그 뷰의 보고 안에서 바로 읽어 바꾼 뒤(CPU 대기) 같은 프레임에 그립니다. 비동기로 "몇 프레임 뒤 도착"하게 두면 실행마다 화면이 달라지기 때문입니다.
    • 시간은 앱 프레임 시간으로: 내리기 지연처럼 시간에 따라 바뀌는 상태는 실제 시계가 아니라 FFrameTime(고정 델타 가능)을 씁니다(2026-10-04 규칙).

    필요 밉 식을 바꾸면 Tests/Materials 씬으로 켬/끔 MD5를 비교합니다. 남은 한계도 Plans.md에 적혀 있습니다: 아틀라스 모델(늘어난 UV 면이 1~5%)은 근거리에서 거의 줄어들지 않고, 대화형 비동기 실행의 첫 프레임은 흐린 밉으로 시작해 TAA 이력이 잠깐 흐립니다.

    수거와 스트리밍의 경계 두 시스템은 같은 텍스처를 다루므로 경계를 명확히 정했습니다. 수거는 텍스처 전체를 해제하고(그 텍스처의 스트리밍 항목과 진행 중 요청도 지움), 스트리밍은 살아 있는 텍스처의 밉만 조절합니다. 수거 중인 텍스처에 스트리밍 업로드가 도착하는 식의 경쟁을 처음부터 막는 규칙입니다.
    정리
    • 리소스 수거 = 루트에서 표시 → 표시 안 된 경로 리소스를 지연 해제. 계산(ResourceGc::Compute)은 순수 함수라 GPU 없이 테스트한다.
    • 씬 밖에서 경로 핸들을 오래 쥐는 코드는 AddRootProvider로 루트를 등록한다. 수거는 요청 때만, 2틱 뒤.
    • 업로드: 작업 스레드(읽기·디코드·압축) → 메인 완료 콜백(링 할당·복사 기록) → 복사 큐 → 직접 큐가 펜스 확인 후 전이. 메인 스레드는 기다리지 않는다.
    • 복사 큐 대상은 COMMON으로 만들고 승격/감쇠를 이용, 텍스처만 직접 큐에서 PIXEL_SHADER_RESOURCE로 전이.
    • 밉 스트리밍: 필요 밉 = floor(log2(큰 변 × UV 밀도 × CmPerPixel) + 바이어스) − 여유. 올리기 즉시, 내리기 지연, 예산 초과 시 우선순위 × 단계로 고르게 축소.
    • 상주 범위 변경 = 새 텍스처 + SwapContents. 크기 조건과 보수적 식으로 켬/끔 화면을 비트 동일하게 유지.

    생각해 볼 문제

    Q1. 수거를 맵 전환 직후 바로(같은 프레임에) 돌리면 어떤 일이 생길 수 있을까요? 새 맵의 에셋 해석과 렌더러 캐시(지형 레이어 등)가 아직 핸들을 채우지 않아 루트에서 빠진 리소스가 있을 수 있습니다. 특히 두 맵이 공유하는 텍스처는 "이전 맵은 놓았고 새 맵은 아직 안 쥔" 순간에 해제되었다가 바로 다시 로드되는 낭비가 생깁니다. 그래서 새 씬이 한 번 그려진 뒤(2틱 지연)에 수거합니다.
    Q2. 업로드 링이 가득 찼을 때 ProjectE는 무엇을 하나요? 왜 그게 드문가요? 열린 묶음을 제출하고 가장 오래된 묶음의 펜스를 CPU로 기다립니다(GetStallCount로 셉니다). 64MB 링은 보통 몇 프레임 안에 GPU 복사가 끝나 꼬리가 따라오므로 가득 차는 일이 드뭅니다. 또 링 절반(32MB)보다 큰 업로드는 링을 쓰지 않고 전용 버퍼를 만들어, 큰 텍스처 하나가 링을 막는 일을 피합니다.
    Q3. UV 밀도를 평균이 아니라 "하위 1%"로 잡는 이유는? 한 메시 안에서도 UV가 넓게 늘어난 곳(밀도가 낮은 곳)은 같은 화면 크기에서 픽셀당 텍셀이 적어 더 세밀한 밉이 필요합니다. 평균을 쓰면 그런 부분이 흐려집니다. 그렇다고 최솟값을 쓰면 아주 작은 조각 하나 때문에 항상 밉 0이 필요해지므로, 면적 기준 하위 1%만 제외해 작은 예외를 무시합니다.

    PSO 캐시와 셰이더 끊김

    관련 Phase: 48 (+ 2026-10-04 PSO 캐시 비결정성 버그) · 살펴볼 곳: RHI/D3D12/D3D12PipelineRecipe.h/.cpp, RHI/D3D12/D3D12PipelineCache.h/.cpp, RHI/D3D12/D3D12PipelineState.h
    이 강의를 마치면
    • PSO(파이프라인 상태 객체)가 무엇이고, 만드는 순간 왜 수~수십 밀리초가 걸리는지 설명할 수 있습니다.
    • PSO 설명을 포인터 없는 "레시피"로 바꿔 키를 만드는 방법과, 그 키에 무엇이 들어가야 하는지 압니다.
    • 드라이버 캐시(파이프라인 라이브러리)와 레시피 워밍이 각각 무엇을 아끼는지 구분합니다.
    • "캐시를 켜면 화면이 실행마다 달라진" 실제 사건을 통해, 원인을 끝까지 모를 때 안전하게 해결하는 방법을 배웁니다.

    왜 필요한가처음 보는 머티리얼에서 게임이 멈칫한다

    게임을 하다 처음 보는 이펙트가 터지는 순간 화면이 0.1초쯤 멈칫하는 경험이 있을 겁니다. PC 게임에서 흔히 "셰이더 컴파일 끊김(shader compilation stutter)"이라고 부르는 현상입니다. 원인은 대부분 PSO 생성입니다.

    D3D12에서 GPU에게 그리기를 시키려면 먼저 PSO(Pipeline State Object)를 바인딩해야 합니다. PSO는 한 번의 그리기에 필요한 거의 모든 고정 설정을 하나로 묶은 객체입니다.

    • 정점·픽셀 셰이더 바이트코드(DXIL)와 루트 시그니처
    • 블렌드 상태, 래스터라이저 상태(컬링·채우기), 깊이·스텐실 상태
    • 정점 입력 배치, 렌더 타깃·깊이 버퍼 형식, 샘플 수, 토폴로지

    DXIL은 GPU가 직접 실행하는 기계어가 아니라 중간 언어입니다. PSO를 만드는 순간 드라이버가 DXIL을 그 GPU의 기계어로 컴파일하고, 렌더 타깃 형식·블렌드 같은 고정 상태까지 반영해 최적화합니다. 이 작업이 PSO 하나에 수~수십 밀리초 걸립니다. 60fps 프레임 예산이 16.7ms이니 PSO 하나만 새로 만들어도 프레임을 넘길 수 있습니다.

    ProjectE는 Phase 48에서 이 문제를 PSO 캐시로 풀었습니다. 목표는 세 가지였습니다: 같은 PSO는 한 번만 만들기, 이전 실행에서 컴파일한 결과를 디스크에서 꺼내 쓰기(드라이버 캐시), 이전 실행에서 쓴 PSO를 시작할 때 다른 스레드에서 미리 만들기(워밍). 결과는 시작 때 메인 스레드가 PSO에 쓰는 시간이 약 80 → 0.4ms(두 번째 실행)였습니다.

    핵심 개념레시피와 키 — 무엇이 같으면 같은 PSO인가

    캐시의 출발점은 "이 PSO 요청이 저번 것과 같은가"를 판단하는 키입니다. D3D12의 PSO 설명 구조체(D3D12_GRAPHICS_PIPELINE_STATE_DESC)를 그대로 해시하면 안 됩니다. 이유는 셋입니다.

    1. 포인터가 들어 있습니다(셰이더 바이트코드 포인터, 루트 시그니처 포인터, 입력 배치 배열 포인터). 주소는 실행마다 다릅니다.
    2. 구조체 패딩 바이트는 초기화되지 않은 쓰레기 값일 수 있습니다.
    3. 디스크에 저장해 다음 실행에서 PSO를 다시 만들려면 포인터가 아닌 실제 내용이 필요합니다.

    그래서 설명을 포인터 없는 레시피(recipe)로 바꿉니다. 셰이더와 루트 시그니처는 내용 해시로, 고정 기능 상태는 필드를 하나씩 기록합니다.

    // PSO 캐시 (Phase 48) 순수 부분: PSO 설명을 포인터 없는 "레시피"로 직렬화해 키(64비트 해시)를 만들고, 다시 D3D12 설명으로 되살린다.
//   - 레시피 = 루트 시그니처 블롭 해시 + 셰이더 바이트코드 해시/크기 + 고정 기능 상태(필드별 기록 — 구조체 패딩을 해시하지 않는다)
//   - 키 = FNV-1a 64(레시피 바이트). 같은 설명 + 같은 바이트코드 → 같은 키, 바이트코드가 바뀌면(셰이더 핫 리로드·머티리얼 변형) 새 키
struct FRecipe
{
	EPipelineType Type              = EPipelineType::Graphics;
	uint64        RootSignatureHash = 0;
	FShaderRef    Shaders[2];        // 그래픽스: VS, PS / 계산: CS, -
	D3D12_BLEND_DESC           Blend{};
	D3D12_RASTERIZER_DESC      Rasterizer{};
	D3D12_DEPTH_STENCIL_DESC   DepthStencil{};
	std::vector<FInputElement> InputLayout;
	...
};
std::vector<uint8> Serialize(const FRecipe& Recipe);  // 필드별, 리틀 엔디언 그대로
uint64             ComputeKey(const FRecipe& Recipe); // HashBytes(Serialize)

    키에 바이트코드 해시가 들어 있다는 점이 중요합니다. 셰이더 파일을 고쳐 핫 리로드하거나, 머티리얼 그래프가 새 HLSL을 만들면 바이트코드가 바뀌므로 자동으로 새 키가 됩니다. "캐시가 낡은 PSO를 돌려준다"는 종류의 버그가 구조적으로 생길 수 없습니다. 루트 시그니처도 포인터가 아니라 직렬화 블롭의 해시로 넣습니다.

    규칙: PSO와 루트 시그니처는 래퍼로만 만든다 PSO는 FD3D12PipelineState::InitGraphics/InitCompute, 루트 시그니처는 FD3D12RootSignature로만 만듭니다. Device->CreateGraphicsPipelineState를 직접 부르면 캐시와 워밍에서 빠집니다. 루트 시그니처 래퍼는 만들 때 블롭을 캐시에 등록하는데(RegisterRootSignature), 등록되지 않은 루트 시그니처의 PSO는 키를 만들 수 없어 캐시를 건너뜁니다(Bypassed 통계). 레시피나 라이브러리 파일 형식을 바꾸면 FRecipeFile::Version/FLibraryHeader::Version을 올립니다.

    핵심 개념드라이버 캐시와 워밍

    드라이버 캐시: 컴파일 결과를 디스크에

    D3D12는 ID3D12PipelineLibrary라는 기능을 제공합니다. 만든 PSO를 이름을 붙여 라이브러리에 저장하고, 라이브러리 전체를 바이트 덩어리로 직렬화해 디스크에 쓸 수 있습니다. 다음 실행에서 그 바이트로 라이브러리를 다시 만들고 LoadGraphicsPipeline(이름, 설명)을 부르면 드라이버 컴파일 없이 PSO를 얻습니다.

    이 바이트는 그 GPU와 그 드라이버 버전에서만 유효합니다. 그래서 파일 머리(FLibraryHeader)에 어댑터의 Vendor/Device/SubSys/Revision, 드라이버(UMD) 버전, 엔진 형식 버전을 적고, 하나라도 다르거나 CreatePipelineLibrary가 거부하면 버립니다. 드라이버를 업데이트한 첫 실행은 캐시 없이 시작하는 셈입니다.

    // 드라이버 캐시 → 새로 만들기
const std::wstring Name = PipelineCache::MakeLibraryName(Key);
if (Library && LibraryKeys.contains(Key))   // 저장된 키 목록에 있을 때만 Load
{
	std::lock_guard Lock(LibraryMutex);
	Result = Recipe.Type == PipelineCache::EPipelineType::Graphics
		         ? Library->LoadGraphicsPipeline(Name.c_str(), ..., IID_PPV_ARGS(&Out))
		         : Library->LoadComputePipeline(Name.c_str(), ..., IID_PPV_ARGS(&Out));
	bFromLibrary = SUCCEEDED(Result);
}
if (!bFromLibrary)
{
	Result = CreateDirect(InDevice, Recipe, Desc, Out); // 드라이버 컴파일 (느림)
	...
}
    실제로 겪은 일: 없는 이름을 Load하면 경고가 난다 처음에는 키가 라이브러리에 있는지 모른 채 Load*Pipeline을 불러 보고 실패하면 새로 만들었습니다. 기능은 맞았지만 D3D12 디버그 레이어가 "없는 이름을 Load했다"는 경고(971)를 냈습니다. ProjectE는 디버그 레이어 경고 0건을 커밋 조건으로 두므로, 라이브러리 파일 뒤에 저장된 키 목록을 덧붙이고(형식 v2) 목록에 있는 키만 Load하도록 고쳤습니다. 또 종료할 때는 "이번 실행에서 요청된 PSO만"으로 라이브러리를 새로 써서 낡은 항목이 끝없이 쌓이지 않게 합니다.

    워밍: 다음 실행에서 쓸 것을 미리 만들기

    드라이버 캐시가 있어도 Load에는 시간이 들고, 첫 실행이나 드라이버 업데이트 직후에는 캐시가 없습니다. 그래서 두 번째 장치가 레시피 워밍입니다. 레시피 파일(.epso)에는 레시피와 함께 루트 시그니처·셰이더 블롭이 들어 있어, 그것만으로 PSO를 완전히 다시 만들 수 있습니다. 시작할 때 작업 스레드 2개가 이 레시피들로 루트 시그니처와 PSO를 미리 만들어 둡니다. ID3D12Device는 자유 스레드(free-threaded) 객체라 여러 스레드에서 동시에 PSO를 만들어도 됩니다.

    워밍한 PSO는 "같은 루트 시그니처 객체"로 만들었을 때만 메인 요청에 돌려줍니다. 워밍 스레드는 블롭에서 루트 시그니처를 새로 만들었는데, D3D12 런타임이 같은 블롭이면 같은 객체를 돌려주는 경우가 많지만 보장하지는 않기 때문입니다. 다른 객체로 만든 PSO를 섞어 바인딩하면 규칙 위반이므로 이때는 새로 요청합니다.

    레시피는 두 곳에서 옵니다. 사용자 캐시(<Saved>/ShaderCache/PipelineRecipes.epso)는 실행마다 번호를 매겨 8번 실행 동안 쓰이지 않은 레시피를 지웁니다. 프로젝트 레시피(Config/PipelineRecipes.epso)는 --record-pso로 기록해 패키지에 포함하므로, 플레이어의 첫 실행도 워밍을 받습니다(패키징 직전 자동 기록은 후속 과제로 남아 있습니다).

    함정과 교훈캐시를 켜면 화면이 실행마다 달라졌다

    실제로 겪은 일 (2026-10-04) PSO 캐시를 켠 상태에서 자동 검증을 연속으로 돌리자 Tests/Materials·Decals·Terrain의 스크린샷 MD5가 실행마다 바뀌었습니다. 차이는 픽셀의 0.1~0.8%, 파티클·반투명·조명의 미세한 값이었습니다. PSO는 같은 레시피로 만들었으니 같은 결과여야 하는데 말입니다.

    원인을 좁히는 과정이 교훈입니다. 요소를 하나씩 켜고 끄며 조합을 시험했습니다.

    각각은 결정적인데 "작업 스레드가 블롭으로 만든 루트 시그니처로 라이브러리를 Load"하는 조합에서만 깨졌습니다. 드라이버 내부에서 무슨 일이 일어나는지는 끝내 확인하지 못했습니다(드라이버 소스는 볼 수 없습니다). 그래서 원인을 고치는 대신 문제가 되는 조합을 구조적으로 없앴습니다: 워밍은 라이브러리를 읽지 않고 항상 Create하고, 라이브러리 Load는 요청한 스레드만 합니다.

    // 워밍은 드라이버 캐시(파이프라인 라이브러리)를 읽지 않고 항상 Create*PipelineState로 만든다 (드라이버 자체 셰이더 캐시는 쓴다).
// 2026-10-04 측정: 작업 스레드가 블롭으로 만든 루트 시그니처로 라이브러리 Load한 PSO를 쓰면(또는 같은 이름을 나중에 메인 스레드가
// 다시 Load해도) Tests/Materials/Decals/Terrain 화면이 실행마다 0.1~0.8% 픽셀 달라졌다 (파티클·반투명·조명 미세 차이, MD5가 실행마다 바뀜).
// 라이브러리만(--no-pso-warm) 또는 워밍만(라이브러리 없음)은 각각 비트 동일 — 드라이버 내부 원인은 미확인, 조합을 피한다
    • 결정성이 버그를 드러냈다: 화면이 0.1% 다른 것은 사람 눈으로는 절대 모릅니다. 자동 검증이 "같은 입력 → 같은 MD5"를 기대했기 때문에 발견할 수 있었습니다.
    • 검증 절차를 규칙으로 남긴다: 이후 PSO 캐시를 바꾸면 Tests/Materials·Decals·Terrain을 캐시를 켠 채 4회 연속 실행해 MD5가 모두 같고, --no-pso-cache 결과와도 같은지 확인합니다(CLAUDE.md "PSO 캐시"). 한 번 돌려 같은 것으로는 실행마다 달라지는 버그를 잡을 수 없습니다.
    • 원인을 모를 때의 정직한 기록: 주석과 Plans.md에 "원인 미상, 조합을 피함"이라고 적었습니다. 나중에 누군가 "워밍도 라이브러리를 쓰면 더 빠르지 않나?"라고 생각했을 때, 왜 그러면 안 되는지가 코드 옆에 있습니다.
    정리
    • PSO 생성 = 드라이버가 DXIL을 GPU 기계어로 컴파일하는 순간. 수~수십 ms라 처음 보는 PSO가 프레임을 튀게 한다.
    • 키 = 포인터·패딩 없는 레시피(루트 시그니처 블롭 해시 + 바이트코드 해시 + 필드별 상태)의 FNV-1a 64. 셰이더가 바뀌면 자동으로 새 키.
    • 요청 순서: ① 메모리(워밍·앞선 요청) → ② 드라이버 라이브러리(저장 키 목록에 있을 때만) → ③ 새로 만들기.
    • 드라이버 캐시는 GPU·드라이버마다 다르므로 머리로 무효화, 레시피 파일은 드라이버 무관이라 패키지에 넣을 수 있다.
    • 워밍 스레드는 항상 Create, 라이브러리 Load는 요청 스레드만 — 실행마다 화면이 달라진 조합을 구조적으로 배제했다.

    생각해 볼 문제

    Q1. 키에서 셰이더 바이트코드 해시를 빼고 "셰이더 파일 이름 + 엔트리 이름"을 넣으면 어떤 버그가 생길까요? 셰이더 파일을 고쳐도 키가 같으므로 드라이버 캐시나 워밍이 고치기 전의 PSO를 돌려줍니다. 핫 리로드가 반영되지 않거나, 엔진 업데이트 후 옛 셰이더로 그려지는 버그가 됩니다. 디파인이 다른 변형(머티리얼 그래프 등)도 같은 이름이면 구분하지 못합니다. 내용 해시를 쓰면 이런 무효화를 따로 신경 쓸 필요가 없습니다.
    Q2. 드라이버 캐시가 있는데 왜 레시피 워밍도 필요할까요? 드라이버 캐시는 그 PC·그 드라이버에서 한 번 실행한 뒤에야 생기고, 드라이버를 업데이트하면 버려집니다. 레시피는 드라이버와 무관해 패키지에 넣어 배포할 수 있으므로 첫 실행에도 효과가 있습니다. 또 워밍은 메인 스레드가 아닌 작업 스레드에서 미리 만들므로, Load조차 메인 스레드 시간에서 빠집니다.
    Q3. "결정성 테스트를 한 번만 돌려 기준과 같으면 통과"로 하면 왜 이 버그를 놓칠 수 있나요? 이 버그는 실행마다 결과가 달라지는 종류라, 어떤 실행은 우연히 기준과 같을 수 있습니다. 또 기준 자체가 캐시 상태(첫 실행은 라이브러리가 비어 있음)에 따라 달라집니다. 그래서 캐시를 켠 채 여러 번 연속 실행해 서로 같은지, 그리고 캐시를 끈 결과와도 같은지를 함께 확인합니다.

    핵심 개념콘솔 변수 — 다시 빌드하지 않고 켜고 끄기

    A/B 비교를 하려면 "같은 빌드, 같은 씬, 같은 카메라에서 한 가지만 바꾼 두 실행"이 필요합니다. 기능마다 #if로 끄고 다시 빌드하면 비교가 느리고, 빌드가 달라지는 순간 다른 요소도 함께 바뀝니다. 그래서 엔진은 콘솔 변수(console variable, CVar)를 둡니다 — 이름이 붙은 전역 설정값으로, 실행 중 콘솔이나 명령줄에서 바꿀 수 있습니다. 언리얼의 r.ScreenPercentage 같은 것이 대표적입니다.

    TAutoConsoleVariable<bool> Lod("r.LOD", true, "메시 LOD (화면 크기 전환). 끄면 항상 LOD0", EConsoleFlags::None,
                               { .CommandLine = { { L"--no-lod", "0" } } });
TAutoConsoleVariable<float> LodHysteresis("r.LODHysteresis", 0.1f, "LOD 전환 여유 (임계값 ±비율 띠 안에서는 이전 LOD 유지, 0 = 끔)",
                                          EConsoleFlags::None, { .Range = std::pair(0.0f, 1.0f), .CommandLine = { { L"--lod-hysteresis", "" } } });

    한 줄에 많은 정보가 들어 있습니다. 이름(r.LOD), 타입(bool), 기본값, 도움말(필수 — 콘솔 help와 자동 완성에 나옵니다), 범위, 그리고 명령줄 별칭입니다. TAutoConsoleVariable은 .cpp 전역 객체로, 프로그램이 시작될 때 생성자가 전역 레지스트리(FConsoleManager::Get())에 자신을 등록합니다.

    명령줄 별칭: 예전 플래그를 깨지 않기

    CVar가 생기기 전(Phase 38 이전)에는 --no-ssr, --no-lod, --occlusion 같은 명령줄 플래그가 이미 수십 개 있었고, 검증 스크립트와 문서가 그것을 쓰고 있었습니다. 이것들을 모두 --cvar r.SSR=0으로 바꾸면 기존 기록과 스크립트가 깨집니다. 그래서 각 CVar에 별칭을 붙였습니다. { L"--no-lod", "0" }은 "이 플래그가 있으면 값을 0으로", { L"--force-lod", "" }처럼 값이 비면 "플래그 다음 인자를 값으로"입니다. Phase 38 DoD는 "예전 플래그 결과와 픽셀 차이 0"이었습니다.

    핵심 개념Tracy — 프레임 안을 들여다보기

    평균 숫자는 "얼마나"를 알려 주지만 "어디서"는 알려 주지 않습니다. 계측 프로파일러(instrumentation profiler)는 코드의 구간 시작과 끝에 표시를 넣어, 프레임마다 어느 스레드에서 어느 구간이 언제부터 언제까지 실행되었는지를 타임라인으로 보여 줍니다. ProjectE는 오픈소스 프로파일러 Tracy(v0.11.1)를 씁니다. 표시한 구간을 존(zone)이라 부릅니다.

    // Tracy 프로파일러 래퍼 (CMake 옵션 E_TRACY). 꺼져 있으면 모든 매크로가 빈 문장 → 비용 0.
//   Tracy 헤더는 노출하지 않는다: 존은 Tracy C API와 같은 배치의 정적 위치 구조체 + 엔진 DLL 함수 호출.
//   켜져 있어도 뷰어가 연결되기 전에는 기록하지 않는다 (TRACY_ON_DEMAND), 로컬호스트만 받는다 (TRACY_ONLY_LOCALHOST).
#define E_PROFILE_SCOPE(Name)                                                                     \
	static constexpr FProfileSourceLocation E_PROFILE_CONCAT(ProfileLocation_, __LINE__){ Name, __FUNCTION__, __FILE__, \
	                                                                                      static_cast<uint32>(__LINE__), 0 }; \
	const FProfileScope E_PROFILE_CONCAT(ProfileScope_, __LINE__)(&E_PROFILE_CONCAT(ProfileLocation_, __LINE__))

    설계 포인트를 짚어 봅시다.

    • 정적 위치 구조체: 존마다 이름·함수·파일·줄을 담은 static constexpr 구조체를 만들고 그 주소만 넘깁니다. 실행 중에는 문자열을 복사하지 않고 포인터 하나만 기록하므로 존 하나의 비용이 매우 작습니다. 그래서 이름은 반드시 문자열 리터럴(정적 수명)이어야 합니다.
    • RAII: FProfileScope의 생성자가 존을 열고 소멸자가 닫으므로 return이 여러 개여도 짝이 맞습니다.
    • 헤더 숨기기: Tracy 헤더를 직접 포함하지 않고 Core/Profiling.h의 매크로만 씁니다(예외는 GPU 존을 다는 Renderer/RenderProfiling.cpp). Tracy를 바꾸거나 빼도 엔진 코드는 그대로입니다. E_TRACY를 끄면 매크로가 do { } while (0)로 사라져 비용이 0입니다.
    • ON_DEMAND: 켜져 있어도 뷰어가 연결되기 전에는 아무것도 기록하지 않습니다. 개발 실행은 항상 Tracy를 시작해 두고(필요할 때 뷰어를 붙이면 됨), 패키지 게임은 --tracy일 때만, --no-tracy면 끕니다. 테스트는 시작하지 않습니다. 로컬호스트에서만 받아 외부에서 붙을 수 없습니다.
    • 렌더 구간은 자동: 새 렌더 구간은 ERenderTimer에 칸을 추가하기만 하면 CPU 존, GPU 존, --perf-capture 통계가 함께 생깁니다.

    핵심 개념GPU 시간은 왜 늦게 나오나

    CPU 시간은 구간 앞뒤에서 시계를 읽으면 됩니다. GPU는 다릅니다. CPU가 명령 리스트에 "그려라"를 기록하는 시점과 GPU가 그것을 실행하는 시점은 다르고, 보통 GPU는 CPU보다 한두 프레임 뒤에서 따라옵니다. 그래서 GPU 시간은 GPU 자신이 재야 합니다. 방법은 타임스탬프 쿼리입니다 — 명령 리스트에 "이 지점을 실행할 때 GPU 시계 값을 여기에 적어라"(EndQuery(TIMESTAMP))를 구간 앞뒤로 넣고, 프레임 끝에 결과를 CPU가 읽을 수 있는 리드백 버퍼로 옮깁니다(ResolveQueryData).

    void FD3D12GpuTimer::BeginScope(ID3D12GraphicsCommandList* CommandList, uint32 Scope)
{
	...
	CommandList->EndQuery(QueryHeap.Get(), D3D12_QUERY_TYPE_TIMESTAMP, (CurrentSlot * MaxScopes + Scope) * 2);
}
void FD3D12GpuTimer::EndFrame(ID3D12GraphicsCommandList* CommandList)
{
	// 끝낸 구간만 옮긴다 (쓰지 않은 쿼리를 옮기면 디버그 레이어 경고)
	...
	CommandList->ResolveQueryData(QueryHeap.Get(), D3D12_QUERY_TYPE_TIMESTAMP, Index, 2, Readback.Get(), sizeof(uint64) * Index);
}

    "결과를 바로 읽고 싶으니 GPU가 끝날 때까지 기다리자"고 하면, 측정 자체가 CPU와 GPU의 병렬 실행을 깨서 측정값이 왜곡됩니다. 측정 도구가 측정 대상을 바꾸지 않게 하는 것이 측정의 기본입니다. 칸 수(MaxScopes)는 32이고, 렌더 구간이 늘어 Phase 50에서 24 → 32로 늘렸습니다.

    --perf-capture: 평균을 남기는 법

    매 프레임 숫자는 흔들리므로 평균을 냅니다. --perf-capture [--perf-warmup N]을 주면 처음 N프레임(셰이더·PSO·스트리밍이 자리 잡는 동안)을 버리고 나머지 프레임의 평균을 종료 때 [성능] 로그로 남깁니다 — 프레임 시간, 드로우 수, 삼각형 수, ERenderTimer 구간별 CPU/GPU ms, 그리고 게임 쪽 틱 구간(스크립트·물리·트랜스폼·애니메이션 …)의 CPU ms. 런타임은 --no-vsync를 함께 줍니다(VSync가 켜져 있으면 프레임 시간이 모니터 주사율에 묶여 비교가 안 됩니다). 자동 검증 실행은 창을 띄우지 않으므로 측정 중에도 작업 화면을 방해하지 않습니다.

    핵심 개념데이터 경합을 잠금 없이 피하기

    데이터 경합(data race)은 두 스레드가 같은 메모리에 동시에 접근하고 그중 적어도 하나가 쓰기일 때 생깁니다. C++에서는 정의되지 않은 동작이라 결과가 틀리거나, 가끔만 틀리거나, 크래시가 납니다. 흔한 해결책은 뮤텍스(잠금)지만, 매 프레임 수천 번 잠그면 병렬로 얻은 시간을 잠금 대기로 다 잃습니다.

    ProjectE의 해결책은 잠금이 아니라 규칙입니다.

    //   - Body(Begin, End)는 서로 겹치지 않는 구간을 받는다. 구간끼리 같은 데이터를 쓰지 않아야 하며(결과는 실행 순서와 무관 = 결정적),
//     ECS 구조 변경(엔티티/컴포넌트 추가·제거)·GPU·리소스 관리자·로그 외 전역 상태 변경은 하지 않는다
    1. 자기 칸만 쓴다: 결과 배열을 병렬 전에 항목 수만큼 미리 만들어 두고(resize), 항목 i를 처리하는 본문은 칸 i에만 씁니다. 병렬 중에 push_back하지 않습니다(배열이 재할당되면 다른 스레드가 쓰던 메모리가 사라집니다).
    2. 남의 것은 읽기만: 다른 엔티티의 데이터는 읽을 수 있지만, 그 값이 이번 병렬 구간 안에서 바뀌지 않는 것이어야 합니다.
    3. 구조 변경·로그·콜백은 밖에서: 엔티티 추가/삭제는 ECS 저장소를 재배치할 수 있고, 로그는 전역 상태이고, 콜백은 무엇을 할지 모릅니다. 이런 일은 병렬 앞(준비)이나 뒤(마무리)의 순차 단계로 옮깁니다.
    4. 순서가 필요한 합치기는 순서대로: 병렬로 모은 조각 목록을 합칠 때는 조각 번호 순서로 이어 붙입니다. 그러면 결과가 순차 실행과 같은 순서가 됩니다.

    4번이 중요합니다. 실행마다 결과 순서가 달라지면 그리는 순서가 달라지고, 반투명이나 같은 깊이의 물체는 화면이 미세하게 달라집니다. 이 프로젝트는 "병렬로 바꿔도 화면 MD5가 같다"를 검증 기준으로 씁니다. 렌더러 수집 병렬화 규칙(CLAUDE.md)도 "순서는 뷰 순서 그대로, 병렬 본문은 자기 칸만 쓰고 엔티티 칸 크기는 병렬 전에 맞춘다"입니다.

    ProjectE에서는애니메이션: 준비 → 평가 → 마무리

    애니메이션 갱신은 병렬화하기 좋아 보이지만 그대로는 안 됩니다. 한 캐릭터의 갱신 안에 이런 일들이 섞여 있기 때문입니다: 그래프·리타기팅 세트 해석(라이브러리 캐시 접근, 경고 로그), 래그돌 확인, 클립 변경 해석, IK 뼈 찾기, 포즈 계산, 노티파이 수집, 루트 모션 적용(캐릭터 이동 컴포넌트를 호출하는 콜백). 이 중 병렬로 해도 안전한 것은 포즈 계산뿐입니다. 그래서 갱신을 세 단계로 쪼갰습니다.

    // 준비(메인, 엔티티 순서) → 포즈 평가(FParallel, 엔티티별 독립) → 마무리(메인, 엔티티 순서).
// 노티파이·몽타주 끝 이벤트는 런타임별 Pending 목록에 쌓이므로 평가 순서와 무관하고, 루트 모션 콜백은 마무리에서 엔티티 순서대로 부른다
// (평가 중에는 노드 로컬 트랜스폼만 바뀌고 월드 행렬은 다음 UpdateTransforms까지 그대로 — 순차 실행과 결과가 같다)
void FAnimationSystem::Update(FScene& Scene, float DeltaSeconds)
{
	...
	{
		E_PROFILE_SCOPE("애니메이션 준비");
		Scene.GetRegistry().View<FAnimationComponent>().Each([&](FEntity Entity, FAnimationComponent& Animation) {
			FAnimUpdateItem Item;
			if (PrepareAnimation(Scene, Entity, Animation, DeltaSeconds, View, Item))
			{
				Items.push_back(Item);
			}
		});
	}
	{
		E_PROFILE_SCOPE("애니메이션 평가");
		const auto Evaluate = [&](uint32 Begin, uint32 End) {
			for (uint32 Index = Begin; Index < End; ++Index)
			{
				EvaluateAnimation(Scene, Items[Index]);
			}
		};
		FParallel::ParallelFor(static_cast<uint32>(Items.size()), 4, Evaluate);  // a.ParallelEvaluate 0이면 순차
	}
	for (const FAnimUpdateItem& Item : Items)
	{
		FinishAnimation(Scene, Item);
	}
}

    "노티파이를 런타임별 Pending 목록에 쌓는다"는 부분이 앞의 규칙 1(자기 칸만 쓴다)의 실제 모습입니다. 공용 이벤트 큐 하나에 여러 스레드가 넣으면 잠금이 필요하고 순서도 실행마다 달라집니다. 캐릭터마다 자기 목록에 넣고, 나중에 엔티티 순서대로 읽으면 잠금도 필요 없고 순서도 결정적입니다.

    ProjectE에서는URO — 멀리 있으면 덜 자주

    병렬화는 같은 일을 빨리 하는 것이고, URO(Update Rate Optimization, 갱신 빈도 LOD)는 일 자체를 줄이는 것입니다. 화면에서 손톱만 하게 보이는 캐릭터의 포즈를 매 프레임 계산할 필요는 없습니다. 29강의 메시 LOD가 삼각형 수를 줄였다면, URO는 시간 해상도를 줄입니다.

    //   - 화면 크기 = 반경 / (거리 × tan(세로 FOV / 2)) — 화면 세로 절반 대비 경계 구 반경
//   - 간격: 화면 크기 >= FullRateScreenSize → 매 프레임, >= HalfRateScreenSize → 2프레임마다, 그 밖 → MaxInterval프레임마다
//   - 평가 프레임 = (런타임 틱 + 엔티티 번호) % 간격 == 0 (결정적 엇갈림). 처음 갱신은 항상 평가
inline bool ShouldEvaluate(uint32 Tick, uint32 Phase, uint32 Interval, bool bFirst)
{
	return bFirst || Interval <= 1 || (Tick + Phase) % Interval == 0;
}

    기본값은 화면 크기 0.2 이상이면 매 프레임, 0.08 이상이면 2프레임마다, 그보다 작으면 4프레임마다입니다(a.URO.FullRateScreenSize/HalfRateScreenSize/MaxInterval, 반경은 a.URO.Radius 100cm × 루트 스케일).

    건너뛴 시간은 버리지 않는다

    URO에서 가장 쉽게 틀리는 부분은 이것입니다. 4프레임마다 평가하면서 매번 "이번 프레임 dt"만큼만 진행하면 먼 캐릭터의 애니메이션이 4배 느려집니다. ProjectE는 건너뛴 프레임에 UpdateRatePending에 시간을 모으고, 다음 평가가 모은 시간 + 이번 dt를 한 번에 진행합니다.

    // 갱신 빈도 LOD: 건너뛰는 프레임은 시간만 모은다
const uint32 Interval = SelectUpdateInterval(Scene, Entity, Animation, View);
const uint32 Tick     = Runtime.UpdateRateTick++;
if (!AnimUpdateRateMath::ShouldEvaluate(Tick, Entity.Index, Interval, !Runtime.bUpdateRateEvaluated))
{
	Runtime.UpdateRatePending += DeltaSeconds;
	return false;
}
Runtime.bUpdateRateEvaluated = true;
OutItem.DeltaSeconds         = DeltaSeconds + Runtime.UpdateRatePending;
Runtime.UpdateRatePending    = 0.0f;

    노티파이(발소리, 타격 시점) 판정은 "이전 시각에서 현재 시각까지 구간에 노티파이가 있는가"를 보는 구간 판정이므로, 4프레임 분량을 한 번에 진행해도 그 사이의 노티파이를 잃지 않고 평가 프레임에 나옵니다. 몽타주 끝 이벤트도 마찬가지입니다.

    URO에서 빼는 대상 (항상 매 프레임) 카메라가 없을 때, 일시정지 중(에디터 스크럽은 즉시 반영해야 함), 루트 모션을 추출하는 캐릭터(이동이 끊겨 보이므로), 래그돌. 특히 루트 모션은 애니메이션이 캐릭터의 실제 이동량을 정하므로, 4프레임마다 몰아서 움직이면 물리·네트워크 예측까지 영향을 받습니다.

    ProjectE에서는트랜스폼 갱신: 루트별 병렬

    애니메이션이 뼈의 로컬 트랜스폼을 바꾸면 FScene::UpdateTransforms가 계층을 따라 월드 행렬을 계산합니다(자식 월드 = 로컬 × 부모 월드). 계층은 트리이므로 서로 다른 루트의 하위 트리는 독립입니다. 캐릭터 하나가 하나의 루트 하위 트리이니, 루트마다 다른 스레드에 맡기면 됩니다.

    FParallel::ParallelFor(RootCount, 16, [this](uint32 Begin, uint32 End) {
	for (uint32 Index = Begin; Index < End; ++Index)
	{
		RootDeferred[Index].clear();                     // 루트마다 자기 칸
		UpdateTransformRecursive(TransformRoots[Index], FMatrix4x4::Identity, true, RootDeferred[Index]);
	}
});
for (uint32 Index = 0; Index < RootCount; ++Index)   // 루트 순서대로 합치기
{
	DeferredAttachments.insert(DeferredAttachments.end(), RootDeferred[Index].begin(), RootDeferred[Index].end());
}

    소켓 부착(무기를 손 뼈에 붙이기)은 계층 부모가 아니라 다른 모델의 뼈를 따라가므로, 그 뼈의 월드 행렬이 계산된 뒤에야 처리할 수 있습니다. 병렬 구간에서는 목록에만 모으고(RootDeferred는 루트마다 자기 칸), 병렬이 끝난 뒤 순서대로 처리합니다. 앞의 규칙 1과 4가 그대로 쓰였습니다.

    함정과 교훈병렬화의 증명은 "순차와 같다"

    결정성 테스트를 강하게 만든 이유 병렬 코드의 버그는 "가끔" 나타납니다. 그래서 애니메이션 병렬화 직후 결정성 테스트를 따로 강화했습니다(31ac60b): 모델 300개, 간격 1/2/4 혼합, 프레임마다 다른 dt, 크로스페이드를 넣고, 병렬 결과와 순차 결과의 포즈를 비트 해시로 반복 비교합니다. 고정 dt 하나로만 시험하면 "모은 시간 + 이번 dt" 계산의 실수가 드러나지 않습니다. 트랜스폼 캐시(931fa98)도 무작위 편집 60프레임 뒤 모든 월드 행렬을 전체 재계산과 비트 비교하는 테스트를 넣었고, 부모 월드 비교를 일부러 빼 보니 181건이 실패하는 것으로 테스트가 실제로 버그를 잡는다는 것까지 확인했습니다.
    • 병렬화보다 먼저 일을 줄인다: 스킨 팔레트는 프리미티브마다 계산하던 것을 "같은 스켈레톤을 쓰는 프리미티브들은 하나를 공유"하도록 바꾸자 3609개가 500개가 되었습니다. 병렬로 나누기 전에 중복을 없애는 쪽이 이득이 더 큽니다. URO도 같은 생각입니다.
    • 남은 비용은 메모리 대역폭: 렌더러 수집 병렬화 뒤에 남은 비용은 유닛당 팔레트 2.6KB×2 업로드, 인스턴스 7개×약 200B 같은 데이터 이동이었습니다(CLAUDE.md). 코어를 더 써도 메모리 버스는 하나이므로, 다음 단계는 병렬이 아니라 데이터 축소입니다.
    • "화면 밖이면 갱신 생략"은 이득 0이었다: Phase 29에서 재 본 결과 Stress 씬에서 이득이 없어 넣지 않았습니다. URO는 화면 밖이 아니라 화면 크기로 판정해, 화면 안에 많이 보이는 작은 캐릭터들에서 이득을 냅니다.
    • 스레드 하나로도 결과가 같아야 한다: core.ParallelFor 0, a.ParallelEvaluate 0으로 언제든 순차와 비교할 수 있게 한 것은 디버깅을 위한 것이기도 하지만, "병렬이 결과를 바꾸지 않는다"를 상시 확인할 수 있게 하는 장치입니다.
    정리
    • 작업 큐(FJobQueue)는 비동기 작업 + 메인 완료 콜백, ParallelFor는 프레임 안 데이터 병렬 루프(호출자도 참여, 끝나야 반환). 풀을 분리한다.
    • ParallelFor는 원자적 카운터로 묶음을 동적 분배, 스레드당 약 4묶음, 작으면 순차, 중첩은 순차.
    • 경합은 잠금이 아니라 규칙으로: 자기 칸만 쓰기(크기는 병렬 전에), 남의 것은 읽기만, 구조 변경·로그·콜백은 밖에서, 합치기는 순서대로.
    • 애니메이션 = 준비(메인) → 평가(병렬) → 마무리(메인). 노티파이는 런타임별 목록.
    • URO = 화면 크기로 간격 1/2/4, (틱 + 엔티티 번호) % 간격으로 엇갈림, 건너뛴 시간은 다음 평가가 진행. 루트 모션·래그돌·일시정지는 제외.
    • 트랜스폼은 루트 하위 트리별 병렬, 소켓 부착은 지연 목록을 루트 순서로 합쳐 처리. 병렬의 증명은 순차와의 비트 비교.

    생각해 볼 문제

    Q1. URO의 평가 프레임을 Tick % Interval == 0으로만 정하면(엔티티 번호를 더하지 않으면) 어떤 일이 생길까요? 간격이 4인 캐릭터 모두가 같은 프레임(틱 0, 4, 8 …)에 평가되고 나머지 세 프레임에는 아무도 평가되지 않습니다. 평균 비용은 같지만 4프레임마다 한 번씩 튀는 프레임이 생겨 끊김으로 느껴집니다. 엔티티 번호를 더하면 부하가 프레임마다 고르게 퍼집니다. 엔티티 번호를 쓰므로 같은 씬·같은 프레임 수면 결과가 항상 같습니다(결정적).
    Q2. 평가 단계에서 "클립을 못 찾았다"는 경고 로그를 찍고 싶다면 어디로 옮겨야 하나요? 왜죠? 준비 단계(PrepareAnimation, 메인 스레드)로 옮깁니다. 실제로 클립 변경 해석(ResolveClipChange)은 로그를 낼 수 있어 준비 단계에서 합니다. 로그는 전역 상태(파일·콘솔·에디터 패널)를 건드리므로 여러 스레드가 동시에 부르면 경합이 생기고, 줄 순서도 실행마다 달라집니다.
    Q3. 병렬 수집 결과를 std::vector 하나에 각 스레드가 push_back하게 하고 뮤텍스로 보호하면 정확성 외에 무엇이 문제일까요? 잠금 대기로 병렬 이득이 줄어드는 것도 문제지만, 더 큰 문제는 순서입니다. 어느 스레드가 먼저 넣느냐에 따라 결과 순서가 실행마다 달라지고, 그 순서로 그리기·정렬·ID 부여를 하면 화면과 동작이 비결정적이 됩니다. 칸을 미리 만들어 자기 칸에 쓰거나, 스레드별 조각을 만든 뒤 조각 번호 순서로 합쳐야 순차와 같은 결과가 됩니다.
