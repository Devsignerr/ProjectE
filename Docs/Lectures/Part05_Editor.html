    에디터 만들기

    엔진을 "쓸 수 있는 도구"로 만드는 단계입니다. 즉시 모드 GUI로 창과 패널을 짜고, 실행 취소와 플레이 인 에디터, 콘텐츠 브라우저, 프리팹, 설정 시스템처럼 "사용자가 실수해도 되돌릴 수 있게" 만드는 구조를 하나씩 봅니다.

    즉시 모드 GUI와 에디터 구조

    관련 Phase: 4, 에디터 UI 디자인, 버그 "뷰포트 클릭이 항상 Ground 선택" · 살펴볼 곳: Editor/ImGuiLayer.*, Editor/EditorApplication.cpp, Editor/Panels/ViewportPanel.cpp, Editor/Panels/HierarchyPanel.cpp, Editor/EditorContext.h, Editor/EditorTheme.h, Editor/EditorGrid.cpp

    • 에디터 한 프레임에서 UI 기술 → 씬 렌더 → UI 그리기가 어떤 순서로 일어나는지, 왜 UI는 UNORM 백버퍼 뷰에 그리는지 설명할 수 있습니다.
    • 오프스크린 뷰포트, 기즈모(부모 기준 로컬 분해), 클릭 선택(광선 → 경계 상자 → 삼각형)의 원리를 이해합니다.
    • "패널 = FEditorContext + Draw()" 구조와 테마 규칙이 왜 필요한지 압니다.

    왜 필요한가JSON을 손으로 고쳐서는 게임을 만들 수 없다

    2부까지 오면 엔진은 씬을 JSON(.escene)으로 저장하고 불러올 수 있습니다. 그렇다면 상자 하나를 옮길 때마다 텍스트 편집기를 열어 "Position": [2200, -1450, 0]을 고치면 될까요? 이론상 가능하지만 아무도 그렇게 게임을 만들지 않습니다. 화면을 보면서 물체를 끌어 옮기고, 클릭해서 고르고, 값을 슬라이더로 바꾸고, 실수하면 되돌릴 수 있어야 합니다. 이것이 에디터입니다.

    ProjectE에서 에디터는 특별한 존재가 아닙니다. 0강에서 본 것처럼 FApplication을 상속한 또 하나의 실행 파일(ProjectEEditor.exe)이고, 게임과 같은 엔진 DLL로 씬을 그립니다. 에디터가 하는 일은 그 위에 "사람이 만지는 층"을 얹는 것입니다. Phase 4의 완료 기준(DoD)이 그 층의 최소 모습을 잘 보여 줍니다.

    **DoD**: ProjectEEditor.exe에서 도킹된 뷰포트/계층/인스펙터/콘텐츠/통계 패널이 보이고,
계층에서 엔티티를 선택하거나 뷰포트를 클릭해 선택하면 기즈모로 이동/회전/스케일이 되며
인스펙터 값이 함께 바뀐다. ... 창 리사이즈/뷰포트 리사이즈에서 크래시·디버그 레이어 에러 없음.

    이 문장 안에 이번 강의의 주제가 모두 들어 있습니다: 도킹, 뷰포트(씬을 그린 그림을 창 안에 넣기), 선택(클릭 → 엔티티), 기즈모(화면에서 끌어 트랜스폼 바꾸기), 그리고 여러 패널이 같은 상태를 함께 보는 구조입니다.

    핵심 개념보존 모드와 즉시 모드

    GUI 라이브러리는 크게 두 갈래입니다.

    • 보존 모드(retained mode): 버튼·텍스트 상자 같은 위젯 객체를 만들어 트리로 보관하고, 라이브러리가 그것을 기억했다가 그립니다. 클릭은 콜백(이벤트 핸들러)으로 알려 줍니다. WinForms, Qt, 웹 DOM, 그리고 9부에서 만들 게임 UI(FUIWidget 트리)가 이 방식입니다.
    • 즉시 모드(immediate mode): 위젯 객체가 없습니다. 매 프레임 코드가 "지금 여기 버튼이 있다"고 함수를 부르고, 그 함수가 "이번 프레임에 눌렸는가"를 반환합니다. 화면은 그 프레임에 부른 함수들의 결과일 뿐입니다. Dear ImGui가 대표적입니다.

    에디터에 즉시 모드가 잘 맞는 이유는 "진실은 한 곳에만 있다"는 점입니다. 인스펙터의 위치 칸은 FTransformComponent::Position을 포인터로 직접 고칩니다. 스크립트가 플레이 중에 위치를 바꾸든, 실행 취소가 씬을 통째로 바꾸든, 다음 프레임에 인스펙터는 새 값을 그대로 보여 줍니다. 보존 모드라면 "씬이 바뀌었으니 위젯 트리를 다시 만들어라"는 동기화 코드가 곳곳에 필요합니다. 반대로 즉시 모드의 대가도 있습니다.

    • 매 프레임 CPU 비용: 화면 전체를 매번 다시 서술합니다. 도구에서는 감당할 만하지만, 수천 개 항목 목록은 보이는 것만 그리는 기법(클리퍼)이 필요합니다.
    • ID 충돌: 위젯을 식별하는 것은 객체가 아니라 라벨 문자열의 해시입니다. 같은 창에 "삭제" 버튼이 둘이면 둘이 같은 위젯으로 취급됩니다. ImGui는 "보이는 글자##숨은ID", "보이는 글자###고정ID" 문법과 PushID로 이를 풉니다.
    • 예쁜 게임 UI에는 부적합: 애니메이션, 정교한 레이아웃, 디자이너가 만드는 화면은 보존 모드가 낫습니다. 그래서 ProjectE는 에디터 UI = ImGui, 게임 UI = 자체 보존 모드 위젯(9부)으로 나눴습니다.
    비유 보존 모드는 무대 소품을 세워 두고 배우가 옮길 때마다 소품 담당이 위치를 고쳐 주는 연극이고, 즉시 모드는 매 장면마다 무대를 처음부터 그리는 애니메이션입니다. 그리는 수고는 크지만 "소품 위치가 대본과 다르다" 같은 사고는 원천적으로 없습니다.

    핵심 개념에디터 한 프레임: UI 서술 → 씬 렌더 → UI 그리기

    ImGui의 프레임은 세 단계입니다. NewFrame()으로 입력을 받아 새 프레임을 열고, 위젯 함수들이 그리기 목록(draw list)에 사각형과 글자를 쌓고, Render() + 백엔드의 RenderDrawData가 그 목록을 GPU 명령으로 바꿉니다. FImGuiLayer는 이것을 BeginFrame/EndFrame으로 감쌉니다.

    void FImGuiLayer::BeginFrame()
{
	ImGui_ImplDX12_NewFrame();
	ImGui_ImplWin32_NewFrame();
	ImGui::NewFrame();
	ImGuizmo::BeginFrame(); // 매 프레임 필수 — 없으면 기즈모 상호작용이 동작하지 않는다

	// 메인 창 전체를 도크스페이스로 (중앙은 뷰포트가 차지하도록 패스스루)
	DockSpaceId = ImGui::DockSpaceOverViewport(0, ImGui::GetMainViewport(), ImGuiDockNodeFlags_PassthruCentralNode);
	bFrameBegun = true;
}

void FImGuiLayer::EndFrame(ID3D12GraphicsCommandList* CommandList)
{
	ImGui::Render();
	ImGui_ImplDX12_RenderDrawData(ImGui::GetDrawData(), CommandList);
	bFrameBegun = false;
}

    에디터의 OnRender는 이 두 함수 사이에 모든 패널을 서술하고, 그 다음에야 GPU 프레임을 엽니다. 순서가 조금 낯설 수 있습니다. 뷰포트 패널은 UI를 서술할 때 "여기에 씬 그림(텍스처)을 붙여라"라는 명령만 그리기 목록에 넣고, 실제 씬은 그 뒤에 오프스크린 타깃에 그립니다. ImGui 그리기 목록이 GPU에서 실행되는 것은 맨 마지막이므로, 같은 프레임에 그린 씬이 그대로 보입니다.

    왜 UI는 UNORM 뷰에 그리나 — 색공간 한 번 더

    3부에서 "셰이더는 선형 공간에서 계산하고, 화면에 낼 때 sRGB(감마)로 인코딩한다"는 규칙을 세웠습니다. 백버퍼를 _SRGB 형식의 RTV로 열면 GPU가 쓰기 순간에 자동으로 인코딩해 줍니다. 그런데 ImGui의 색(테마 색, 글자 색)은 이미 인코딩된 값입니다. 디자이너가 "회색 0.5"라고 고른 그 값을 그대로 화면에 내야 합니다. 이것을 sRGB RTV에 쓰면 GPU가 한 번 더 인코딩해서 UI 전체가 희뿌옇게 밝아집니다.

    그래서 같은 백버퍼 메모리에 뷰를 두 개 둡니다. 씬은 sRGB 뷰로, UI는 UNORM 뷰(변환 없음)로 씁니다. FD3D12RHI::SetRenderTargetToBackBuffer(true)의 인자가 바로 "선형(변환 없는) 뷰를 쓸 것인가"입니다. 오프스크린 뷰포트 타깃도 같은 원리입니다.

    struct FRenderTargetDesc
{
	DXGI_FORMAT ResourceFormat = DXGI_FORMAT_R8G8B8A8_TYPELESS;
	DXGI_FORMAT RtvFormat      = DXGI_FORMAT_R8G8B8A8_UNORM_SRGB; // 선형 → 감마 인코딩
	DXGI_FORMAT SrvFormat      = DXGI_FORMAT_R8G8B8A8_UNORM;      // UI가 인코딩된 값을 그대로 표시
	...
};

    리소스를 TYPELESS로 만들면 "메모리는 같고 해석만 다른" 뷰를 여러 개 붙일 수 있습니다. 씬 렌더러는 sRGB RTV로 써서 인코딩된 값을 저장하고, ImGui는 UNORM SRV로 읽어서 인코딩된 값을 있는 그대로 UI 사각형에 붙입니다. 어느 단계에서도 두 번 변환되지 않습니다.

    핵심 개념도킹과 오프스크린 뷰포트

    도킹(docking)은 창을 끌어 다른 창의 옆이나 탭으로 붙이는 기능입니다. ProjectE는 Dear ImGui의 도킹 브랜치(1.93)를 쓰고, DockSpaceOverViewport로 메인 창 전체를 도크스페이스로 만듭니다. 사용자가 배치한 모양은 ImGui가 Saved/ 아래 ini 파일에 저장합니다.

    문제는 "처음 실행"입니다. 저장된 배치가 없으면 패널이 모두 겹쳐 뜹니다. 그래서 ApplyDefaultLayoutIfNeeded가 ini에 뷰포트 창 기록이 없으면 DockBuilder API로 언리얼 풍 기본 배치(가운데 뷰포트, 오른쪽 계층/인스펙터, 아래 콘텐츠·로그·통계 탭)를 직접 만듭니다. 여기서 창을 찾는 열쇠가 "###Viewport" 같은 고정 ID입니다.

    // "아이콘  이름###Id" (보이는 제목과 무관하게 ID 고정)
std::string FEditorTheme::PanelTitle(const char* Icon, std::string_view Label, std::string_view Id)
{
	return std::format("{}  {}###{}", Icon, Label, Id);
}

// ApplyDefaultLayoutIfNeeded: 언리얼 5 배치
const ImGuiID Right       = ImGui::DockBuilderSplitNode(DockSpace, ImGuiDir_Right, 0.26f, nullptr, &Main);
const ImGuiID Bottom      = ImGui::DockBuilderSplitNode(Main, ImGuiDir_Down, 0.38f, nullptr, &Center);
...
ImGui::DockBuilderDockWindow("###Viewport", Center);
ImGui::DockBuilderDockWindow("###ContentBrowser", Bottom);

    ### 뒤의 문자열만 ID가 되므로, 제목에 아이콘을 붙이거나 한국어 표시 이름을 바꿔도 사용자가 저장해 둔 배치가 깨지지 않습니다. 새 패널을 만들면 PanelTitle로 제목을 만들고 기본 배치에도 넣는 것이 규칙입니다.

    오프스크린 뷰포트

    게임 런타임은 씬을 백버퍼에 바로 그립니다. 에디터는 그럴 수 없습니다. 씬은 도킹된 "뷰포트" 패널 안, 임의 크기의 사각형에 들어가야 하기 때문입니다. 그래서 씬을 오프스크린 렌더 타깃(화면이 아닌 텍스처)에 그리고, 그 텍스처를 ImGui::Image로 패널에 붙입니다.

    const bool bNeedsResize = !bNeedsCreate && (RenderTarget->GetWidth() != DesiredWidth || RenderTarget->GetHeight() != DesiredHeight);
...
// 이전 타깃은 진행 중인 프레임이 참조할 수 있으므로 지연 해제
if (RenderTarget)
{
	RenderTarget->ShutdownDeferred(*Context.Rhi);
}
RenderTarget = std::make_unique<FD3D12RenderTarget>();
RenderTarget->Init(Context.Rhi->GetDevice(), Context.Rhi->GetSrvAllocator(), DesiredWidth, DesiredHeight, L"EditorViewport");
Context.Camera->SetAspectRatio(static_cast<float>(DesiredWidth) / static_cast<float>(DesiredHeight));

    두 가지가 중요합니다. 첫째, 패널 크기를 바꾸면 타깃을 다시 만드는데, 이 일은 UI 서술 전(PrepareFrame)에 합니다. UI 서술 도중에 타깃을 바꾸면 이미 그리기 목록에 들어간 옛 텍스처 핸들이 엉뚱한 것을 가리킵니다. 둘째, 옛 타깃은 바로 지우지 않고 지연 해제합니다. 2부에서 본 것처럼 GPU는 CPU보다 프레임 몇 개 늦게 따라오므로, 아직 그 텍스처를 읽는 명령이 GPU 대기열에 남아 있을 수 있습니다. 카메라의 종횡비도 여기서 맞춥니다 — 안 맞추면 패널을 넓힐 때 화면이 옆으로 늘어납니다.

    핵심 개념기즈모: 월드에서 끌고 로컬로 되돌리기

    기즈모(gizmo)는 선택한 물체 위에 그려지는 화살표·고리·상자 손잡이입니다. 손잡이를 끌면 물체가 움직입니다. ProjectE는 ImGuizmo 라이브러리를 씁니다. ImGuizmo는 뷰 행렬, 투영 행렬, 그리고 물체의 월드 행렬을 받아, 사용자가 끌면 그 월드 행렬을 고쳐서 돌려줍니다.

    그런데 씬에 저장되는 값은 월드 행렬이 아니라 부모 기준 로컬 위치·회전·스케일(2부)입니다. 자식 엔티티를 월드에서 오른쪽으로 100cm 옮겼다면, 부모가 90도 돌아 있을 때 로컬 값은 "앞으로 100cm"가 되어야 합니다. 그래서 기즈모 결과를 다음 식으로 되돌립니다.

    로컬 분해 식 (행벡터 규약 v · M) World = Local × ParentWorld 이므로   Local = World × ParentWorld−1
    그 다음 Local을 이동(T)·회전(R, 쿼터니언)·스케일(S)로 분해(Decompose)해 컴포넌트에 씁니다. 
    // ImGuizmo는 float[16]을 행벡터 규약(이동이 [12..14])으로 다루므로 FMatrix4x4 메모리를 그대로 전달
const bool bManipulated = ImGuizmo::Manipulate(&View.M[0][0], &Projection.M[0][0], Operation, Mode, &World.M[0][0], nullptr, SnapPointer);
...
if (bManipulated)
{
	const FMatrix4x4 Delta = OldWorld.GetInverse() * World;
	for (FEntity Target : FSceneEditOps::GetTopLevel(Scene, Context.Selection.GetEntities()))
	{
		...
		const FMatrix4x4 NewWorld = Target == Entity ? World : TargetTransform->WorldMatrix * Delta;
		// 월드 → 로컬: Local = World * Inverse(ParentWorld)
		const FMatrix4x4 Local = NewWorld * Scene.GetParentWorldMatrix(Target).GetInverse(); // 소켓 부착이면 소켓 기준
		Local.Decompose(TargetTransform->Position, TargetTransform->Rotation, TargetTransform->Scale);
	}
	Scene.UpdateTransforms();
	Context.MarkEdited(Labels[static_cast<int32>(GizmoOperation)]);
}

    ProjectE의 행렬이 처음부터 "행우선 저장 + 행벡터 규약"(4강)이었기 때문에 ImGuizmo에 전치 없이 메모리를 그대로 넘길 수 있습니다. 첫날 정한 수학 규약이 여기서 이득을 봅니다. 그 밖에 스냅(Ctrl로 반전), 스케일은 항상 로컬 축, Alt를 누른 채 끌기 시작하면 그 순간 선택을 복제하고 복제본을 움직이는(언리얼과 같은) 동작이 같은 함수 안에 있습니다. 복제와 이동이 같은 드래그 안에서 일어나므로 실행 취소 한 단계로 합쳐집니다.

    핵심 개념클릭 선택: 화면 점 → 광선 → 상자 → 삼각형

    "어딜 클릭해도 무조건 Ground가 선택돼" (2026-10-02) 직교 카메라(픽셀 아트 씬)에서 뷰포트를 어디 클릭해도 바닥(Ground)이나 아무것도 선택되지 않았습니다. 피킹 코드는 멀쩡했고, 원인은 수학 라이브러리에 있었습니다. FMatrix4x4::TryGetInverse가 "행렬식의 절대값 ≤ 1e-8이면 특이 행렬"이라는 절대 문턱을 썼는데, 직교 투영의 뷰-투영 행렬은 행렬식이 4 / (폭 × 높이 × 깊이 범위)라 10−11 수준으로 아주 작습니다. 멀쩡한 행렬을 특이로 보고 항등 행렬을 돌려주니, 광선이 화면 위치와 무관하게 늘 같은 방향(위)으로 나갔습니다. 수정은 상대 문턱입니다. 
    // 특이 판정은 행렬 크기에 상대적으로 한다: |det| / (행 길이의 곱)은 행마다 배율을 바꿔도 같고 직교 행렬이면 1.
float RowLengthProduct = 1.0f;
for (int32 Row = 0; Row < 4; ++Row)
{
	RowLengthProduct *= FMath::Sqrt(M[Row][0] * M[Row][0] + M[Row][1] * M[Row][1] + M[Row][2] * M[Row][2] + M[Row][3] * M[Row][3]);
}
if (!(RowLengthProduct > 0.0f) || !(FMath::Abs(Det) > RowLengthProduct * 1.0e-6f))

	return false;
}
    이 수정은 피킹만 고친 것이 아닙니다. 직교 카메라에서 역행렬을 쓰던 안개, 데칼, 재투영, 지형·폴리지 브러시도 함께 바로잡혔습니다. 같은 작업에서 피킹을 "광선-AABB"에서 "AABB로 거른 뒤 삼각형"으로 바꿨고, 재현용 자동 검증 인자 --verify-pick <이름,...> [--verify-pick-ortho|--verify-pick-no-focus]와 테스트 5개(Matrix_InverseOfOrthographicViewProjection 등)를 남겼습니다. 교훈: 부동소수점 문턱은 값의 크기에 상대적으로. 그리고 "증상이 보이는 곳"과 "원인이 있는 곳"은 다를 수 있습니다. 남은 한계도 기록돼 있습니다 — 스킨 캐릭터는 바인드 포즈 AABB로만 판정하므로 옆 물체를 가릴 수 있습니다.

    생각해 볼 문제

    Q1. 인스펙터에서 엔티티 목록을 그리며 각 행에 ImGui::Button("삭제")를 그렸더니, 어느 행의 버튼을 눌러도 첫 행이 지워지거나 버튼이 이상하게 반응합니다. 왜일까요? 즉시 모드 GUI는 위젯을 라벨 문자열의 해시로 식별하므로, 같은 창 안의 "삭제" 버튼들이 모두 같은 ID가 됩니다. 행마다 ImGui::PushID(엔티티 번호) … PopID()로 ID 범위를 나누거나, "삭제##3"처럼 숨은 ID를 붙여야 합니다. 그리고 버튼이 눌렸을 때 그 자리에서 지우지 말고 "지울 대상"만 기록했다가 순회가 끝난 뒤 지우는 것이 안전합니다(계층 패널의 PendingDelete).
    Q2. 부모가 Z축으로 90도 돌아 있고 스케일 2인 자식을 기즈모로 월드 +X 방향 100cm 끌었습니다. 컴포넌트의 로컬 Position은 대략 어떻게 바뀔까요? Local = World × ParentWorld−1이므로, 월드 이동을 부모의 회전·스케일 역변환으로 되돌립니다. 부모가 90도 돌아 있으니 월드 +X는 부모의 로컬 축으로는 ±Y 방향(회전 방향에 따라 부호)이고, 부모 스케일 2로 나누어 크기는 50이 됩니다. 즉 로컬 Position의 Y 성분이 약 ±50 변합니다. 월드 행렬을 그대로 로컬에 쓰면 부모 변환이 두 번 적용되어 엉뚱한 곳으로 튑니다.
    Q3. 피킹에 GPU를 쓰는 방법도 있습니다(엔티티 번호를 색으로 그린 "ID 버퍼"를 읽기). ProjectE의 CPU 광선 방식과 비교한 장단점은? ID 버퍼는 "실제로 그려진 픽셀"을 읽으므로 스킨 메시의 현재 포즈, 알파 테스트, 셰이더 변형까지 정확합니다. 대신 엔티티 번호를 쓰는 별도 패스가 필요하고, GPU 결과를 CPU로 읽어 오는 리드백이 몇 프레임 늦습니다. CPU 광선 방식은 즉시 답을 얻고 렌더러에 손대지 않지만, CPU 정점 사본이 필요하고 스킨 메시처럼 GPU에서 변형되는 것은 근사(바인드 포즈 AABB)로 판정합니다. ProjectE가 기록한 "스킨 캐릭터가 옆 물체를 가림" 한계가 바로 이 근사의 결과입니다.

    왜 필요한가되돌릴 수 없는 도구는 무섭다

    Ctrl+Z가 없는 편집기를 상상해 보세요. 실수로 엔티티 50개를 지우면 끝입니다. 사용자는 겁이 나서 실험을 하지 못하고, 자주 저장 파일을 복사해 두는 원시적인 방법에 기댑니다. 실행 취소는 편의 기능이 아니라 사용자가 마음 놓고 시도하게 해 주는 안전망입니다.

    문제는 "모든 편집"을 되돌려야 한다는 점입니다. 2026-10-01 야간 작업에서 정한 범위는 이렇습니다.

    - **Undo**: 모든 씬 편집(트랜스폼, 컴포넌트 속성/추가/삭제, 엔티티 생성/삭제/부모 변경, 복제),
  드래그 1회 = 1단계, 엔티티 스냅샷 기반

    트랜스폼, 리플렉션으로 노출된 모든 컴포넌트의 모든 프로퍼티, 계층 구조, 복제 … 그리고 앞으로 추가될 모든 컴포넌트까지. 이 목록이 설계를 결정합니다.

    핵심 개념명령 패턴 vs 스냅샷

    실행 취소를 만드는 고전적인 방법은 두 가지입니다.

    명령 패턴(Command pattern)은 편집 하나하나를 객체로 만듭니다. "엔티티 E의 위치를 A에서 B로"라는 FMoveCommand는 Do()(B로)와 Undo()(A로)를 함께 가집니다. 실행 취소 스택은 이 명령 객체들의 목록입니다. 메모리는 아주 적게 듭니다 — 바뀐 값 두 개만 있으면 됩니다.

    스냅샷(Memento) 방식은 편집이 끝날 때마다 상태 전체를 통째로 저장합니다. 되돌리기는 "이전 상태를 다시 불러오기"일 뿐입니다. 어떤 편집이었는지 알 필요가 없습니다.

    ProjectE는 스냅샷을 골랐습니다. 이유는 2부(Phase 5)의 결과물에 있습니다. 씬은 이미 리플렉션 기반으로 통째로 JSON 직렬화할 수 있었습니다(FSceneSerializer). 인스펙터가 고칠 수 있는 모든 값은 정의상 리플렉션에 등록된 값이고, 등록된 값은 정의상 직렬화됩니다. 그러니 스냅샷 방식에서는 "인스펙터로 고칠 수 있다 = 실행 취소할 수 있다"가 자동으로 성립합니다. 명령 패턴이라면 컴포넌트 추가/제거, 부모 변경, 복제, 프리팹 되돌리기, 내비메시 굽기 … 편집 종류마다 역연산을 짜야 하고, 그 코드는 테스트하기도 어렵습니다.

    설계 이유: 이미 가진 것을 재사용한다 좋은 설계는 종종 "이미 검증된 경로를 한 번 더 쓰는 것"입니다. 저장/불러오기는 매일 쓰이므로 버그가 빨리 드러납니다. 실행 취소가 같은 경로를 쓰면 실행 취소 전용 버그가 생길 자리가 줄어듭니다. 대가로 기록된 한계도 분명합니다: "머티리얼 편집은 Undo 제외, 대형 씬 스냅샷 비용"(Plans.md 1c). 머티리얼 쪽 한계는 37강의 에셋 편집 창이 자기 실행 취소 기록을 가지면서 풀렸습니다.

    핵심 개념FUndoHistory: 상태 목록과 커서

    스냅샷 스택은 의외로 단순한 자료 구조입니다. 각 항목은 "편집 후의 씬 상태 문자열"과 그 편집의 이름이고, 커서(Cursor)가 현재 상태를 가리킵니다.

    // 스냅샷 기반 실행 취소 기록. 각 항목은 "편집 후 씬 상태"(직렬화 문자열)와 그 편집의 이름이다.
//   항목 0 = 기준 상태(열기/새 씬), Cursor = 현재 상태 항목.

    "저장 안 한 변경 표시(*)"가 덤으로 따라온다는 점에 주목하세요. 저장할 때 커서 위치를 SavedIndex로 기억해 두면, 커서가 거기 있는지만으로 "더러운가(dirty)"를 알 수 있습니다. 편집한 뒤 Ctrl+Z로 저장 시점까지 되돌리면 *가 사라지는 것도 공짜입니다. 상태를 문자열로 비교하는 Commit의 첫 줄 덕분에, 값을 바꿨다가 원래대로 돌려놓은 "의미 없는 편집"도 단계를 만들지 않습니다.

    핵심 개념트랜잭션: 드래그 한 번 = 한 단계

    기즈모로 물체를 끌면 마우스가 움직이는 매 프레임 위치가 바뀝니다. 2초 끌면 120번 바뀝니다. 매번 스냅샷을 찍으면 실행 취소를 120번 눌러야 원위치로 갑니다. 사용자가 원하는 것은 "끌기 한 번 = 되돌리기 한 번"입니다. 데이터베이스 용어로 말하면 여러 변경을 하나의 트랜잭션으로 묶어야 합니다.

    ProjectE는 이것을 두 부분으로 나눴습니다.

    1. 편집 코드는 값을 바꾼 직후 Context.MarkEdited("라벨")만 부릅니다. 스냅샷을 찍지 않습니다. 여러 번 불러도 첫 라벨 하나만 남습니다.
    2. 애플리케이션은 매 프레임 끝(CommitPendingEdit)에 "아직 조작 중인가?"를 봅니다. ImGui의 어떤 위젯이 활성(드래그 중, 텍스트 입력 중)이거나 기즈모를 쓰는 중이면 기다리고, 조작이 끝난 첫 프레임에 스냅샷 하나를 커밋합니다.

    최상위 필터

    여러 엔티티를 고른 채로 삭제·복제·이동할 때 미묘한 문제가 있습니다. 부모 P와 그 자식 C를 함께 골랐다고 합시다.

    std::vector<FEntity> FSceneEditOps::GetTopLevel(const FScene& Scene, const std::vector<FEntity>& Entities)
{
	std::vector<FEntity> Result;
	Result.reserve(Entities.size());
	for (FEntity Entity : Entities)
	{
		if (!Scene.GetRegistry().IsValid(Entity)) { continue; }
		bool bHasSelectedAncestor = false;
		for (FEntity Other : Entities)
		{
			if (Other != Entity && Scene.IsAncestorOf(Other, Entity)) { bHasSelectedAncestor = true; break; }
		}
		if (!bHasSelectedAncestor) { Result.push_back(Entity); }
	}
	return Result;
}

const size_t MeshesBefore   = Resources.GetMeshCount();
FEditorActions::DuplicateSelection(Context);
CommitPendingEdit();
const uint32 EntitiesDuplicated = Scene.GetRegistry().GetAliveCount();

const bool bRedoOk = Scene.GetRegistry().GetAliveCount() == EntitiesDuplicated;

    마지막 조건 bNoNewMeshes가 핵심입니다. 엔티티 수가 맞아도, 복원할 때마다 메시를 새로 로드하고 있다면 실행 취소를 누를수록 GPU 메모리가 샙니다. 화면만 봐서는 절대 알 수 없는 종류의 버그를 숫자로 잡습니다. --select A,B와 함께 쓰면 원하는 엔티티를 선택한 상태로 시작할 수 있습니다.

    함정과 교훈스냅샷 방식이 요구하는 규율

    • 플레이 중에는 실행 취소를 막는다: 플레이 중 씬은 편집 씬의 복제본이고, 정지하면 버려집니다(36강). 플레이 중 Ctrl+Z가 편집 기록을 되돌리면 "보이는 씬"과 "되돌린 씬"이 다릅니다. 그래서 UndoEdit는 "플레이 중에는 실행 취소할 수 없습니다" 알림만 띄우고, CommitPendingEdit는 플레이 중 표시를 버립니다(Plans.md 1b 머지 통합 항목 "플레이 중 Undo 차단").
    • 스냅샷 안의 경로도 데이터다: 콘텐츠 브라우저에서 텍스처 파일을 옮기면 씬 파일의 경로는 갱신되지만, 기록 속 옛 스냅샷에는 옛 경로가 그대로 남습니다. 그 상태로 Ctrl+Z를 누르면 이미 없는 파일을 찾습니다. 그래서 에셋 이동 후 UndoHistory.TransformStates로 모든 기록 상태를 같이 고칩니다(37강). 스냅샷 방식에서는 "기록도 저장 파일처럼 관리해야 한다"는 뜻입니다.
    • 스냅샷이 맞지 않는 데이터: 지형 높이맵이나 폴리지 인스턴스처럼 거대한 데이터를 붓질 한 번마다 통째로 문자열로 찍을 수는 없습니다. 그래서 Phase 34는 지형에 별도 기록을 두었습니다: 컴포넌트의 EditRevision + 바뀐 영역의 전/후 기록 사슬(256MB 상한, 스트로크 끝에만 기록). 씬 스냅샷에는 컴포넌트의 리비전 번호가 담기고(높이맵 자체는 .eterrain 파일), 복원 후 TerrainToolPanel.Update가 버전을 맞춥니다. CLAUDE.md의 "끄는 도중 MarkEdited 금지" 규칙이 여기서 나왔습니다. 하나의 설계로 모든 것을 해결하려 하지 말고, 맞지 않는 곳에는 다른 도구를 붙이는 것이 현실적입니다.
    • "편집 코드는 반드시 MarkEdited": 스냅샷 방식은 무엇이든 되돌릴 수 있지만, 커밋되지 않으면 소용없습니다. 새 편집 기능을 만들고 MarkEdited를 잊으면, 그 변경은 다음 편집의 스냅샷에 묻어서 기록됩니다. Ctrl+Z 한 번에 두 편집이 함께 사라지는 이상한 동작이 되는데, 이는 기능 테스트로 잘 드러나지 않습니다.
    정리
    • 명령 패턴은 편집마다 역연산을 짜야 하고, 스냅샷은 상태 전체를 저장한다. ProjectE는 리플렉션 직렬화가 이미 있으므로 씬 JSON 스냅샷을 골랐다(대가: 대형 씬 비용).
    • FUndoHistory = 편집 후 상태 목록 + 커서. 새 커밋은 Redo 꼬리를 버리고, 같은 상태는 무시하며, 저장 지점 인덱스로 dirty를 판정한다(100단계).
    • 편집 코드는 MarkEdited만, 애플리케이션이 조작이 끝난 프레임(IsAnyItemActive/기즈모 사용 아님)에 한 번 커밋한다 → 드래그 한 번 = 한 단계.
    • 복원 후 엔티티 핸들이 바뀌므로 선택은 FEntityPath로 옮긴다. 모델 하위 노드는 템플릿 캐시로 다시 붙인다.
    • 선택은 Context.Select*로만 바꾸고, 여러 선택 대상 명령은 FEditorActions + FSceneEditOps::GetTopLevel로 한 번씩만 적용한다.

    생각해 볼 문제

    Q1. 인스펙터에서 이름 칸에 "Lamp"를 "LampPost"로 타이핑했습니다. 글자마다 값이 바뀌는데 실행 취소는 몇 단계가 생길까요? 한 단계입니다. 텍스트 입력 칸이 포커스를 가진 동안 ImGui::IsAnyItemActive()가 참이므로 TryTake가 계속 거절하고, 입력을 마치고 칸을 벗어나는 프레임에 첫 라벨로 한 번 커밋됩니다. 같은 규칙이 슬라이더 드래그와 기즈모에도 적용됩니다.
    Q2. 씬이 커져 스냅샷 한 번이 수 MB, 직렬화가 수십 ms가 되었습니다. 스냅샷 방식을 유지한 채 할 수 있는 개선은? ① 메모리: 직전 상태와의 차이(diff)만 저장하거나 압축합니다. ② 시간: 엔티티 단위 스냅샷 — 이번 편집에서 바뀐 엔티티만 직렬화하고 나머지는 이전 항목을 공유합니다. ③ 거대한 데이터(지형처럼)는 별도 기록으로 빼고 스냅샷에는 버전 번호만 둡니다. ProjectE는 ③을 이미 쓰고 있고, ①②는 기록된 한계("대형 씬 스냅샷 비용")에 대한 후보입니다.
    Q3. SelectedEntity를 패널이 직접 Context.SelectedEntity = E;로 바꾸면 어떤 일이 생길까요? Selection 집합은 그대로이므로 기즈모·인스펙터는 E를 보지만, 아웃라인·삭제·복제는 예전 선택을 대상으로 합니다. 사용자는 "보이는 선택"과 "명령이 적용되는 대상"이 다른 혼란을 겪습니다. 그래서 주 선택은 읽기 전용으로 쓰고 변경은 Select* 함수만 쓰는 것이 규칙입니다.

    왜 필요한가만든 것을 바로 해 보기

    게임 개발은 "고치고 → 해 보고 → 다시 고치기"의 반복입니다. 스크립트 숫자 하나 바꿀 때마다 에디터를 닫고 런타임을 실행하면 하루에 몇 번 못 해 봅니다. 그래서 유니티의 Play 버튼, 언리얼의 PIE(Play In Editor)처럼 에디터 안에서 바로 게임을 돌리는 기능이 필요합니다.

    그런데 게임은 씬을 마구 바꿉니다. 스크립트가 적을 생성·파괴하고, 물리가 상자를 굴리고, 애니메이션이 뼈를 움직입니다. 이 변화가 편집 중인 씬에 그대로 남으면 큰일입니다. 플레이를 한 번 할 때마다 레벨 디자이너가 공들여 놓은 상자가 바닥에 쓰러져 저장됩니다. 그래서 원칙은 하나입니다: 플레이는 사본에서 하고, 정지하면 사본을 버린다.

    핵심 개념복제하고, 돌리고, 버린다

    사본을 만드는 방법은 두 가지가 있습니다. 하나는 씬을 JSON으로 직렬화했다가 새 씬에 다시 불러오는 것이고(35강의 스냅샷과 같은 길), 다른 하나는 메모리에서 컴포넌트를 바로 복사하는 것입니다. ProjectE의 1인용 플레이는 후자, FSceneCloner를 씁니다.

    // 씬 → 씬 메모리 복제 (에디터 플레이 모드 스냅샷).
// JSON 왕복과 달리 런타임 리소스 핸들과 생성된(Transient) 엔티티까지 그대로 복사하므로 GPU 리소스를 다시 만들지 않는다.
//   - 리플렉션에 컴포넌트로 등록된 타입만 복사된다 (CopyComponent 훅). 미등록 컴포넌트는 복제본에 없다
//   - 엔티티 참조(계층 Parent/Children, Entity 타입 프로퍼티)는 복제본 엔티티로 다시 매핑한다
//   - 리플렉션 밖 런타임 데이터(스킨 바인딩, 애니메이션 노드 참조)는 CopyRuntimeData/RemapRuntimeReferences로 보정한다
struct FSceneCloner
{
	using FEntityMap = std::unordered_map<uint64, FEntity>; // 원본 FEntity::ToId() → 복제본 엔티티
	static void Clone(const FScene& Source, FScene& Dest, FEntityMap* OutEntityMap = nullptr);
	static void CopyRuntimeData(const FRegistry& Source, FEntity SourceEntity, FRegistry& Dest, FEntity DestEntity);
	static void RemapRuntimeReferences(FRegistry& Registry, FEntity Entity, const std::function<FEntity(FEntity)>& Remap);
};

    메모리 복제의 장점은 속도와 GPU 리소스입니다. JSON에서 다시 불러오면 메시·머티리얼 경로를 다시 해석하고, 모델(glTF) 하위 노드를 다시 만들어야 합니다. 메모리 복제는 리소스 핸들(1부의 THandle)을 그대로 복사하므로 GPU 쪽은 아무 일도 없습니다. 같은 메시를 두 씬이 공유할 뿐입니다.

    대신 두 가지를 직접 챙겨야 합니다.

    • 엔티티 참조 다시 잇기: 복제본의 부모 필드가 원본 씬의 엔티티를 가리키면 안 됩니다. 복제하면서 "원본 → 복제본" 표(FEntityMap)를 만들고, 계층의 Parent/Children과 리플렉션에서 EPropertyType::Entity로 등록된 모든 프로퍼티를 표로 바꿉니다.
    • 리플렉션 밖 데이터: 스킨 메시의 관절 목록(FSkinComponent), 애니메이션 런타임 상태처럼 인스펙터에 나오지 않는 데이터는 복사 훅이 없습니다. 이런 것은 CopyRuntimeData가 하나씩 손으로 복사하고 RemapRuntimeReferences가 안쪽 엔티티 참조를 바꿉니다. 파티클은 공유 설정만 넘기고 입자는 새로 시작합니다.
    // 같은 레지스트리면 Emplace가 풀을 재할당할 수 있으므로 값을 먼저 복사해 둔다
if (const FSkinComponent* Skin = Source.TryGet<FSkinComponent>(SourceEntity))
{
	FSkinComponent Copy = *Skin;
	Dest.GetOrEmplace<FSkinComponent>(DestEntity) = std::move(Copy);
}
...
// 파티클: 공유 설정만 넘기고 입자는 처음부터 (플레이 시작/복제 시 새로 방출)
if (const FParticleSystemComponent* Emitter = Source.TryGet<FParticleSystemComponent>(SourceEntity))
{
	...
	DestEmitter->Runtime               = FParticleRuntime{};
	DestEmitter->Runtime.System        = Emitter->Runtime.System;
	DestEmitter->Runtime.ResolvedAsset = Emitter->Runtime.ResolvedAsset;
}

    첫 줄의 주석은 실제 함정입니다. 같은 씬 안에서 복제할 때(Ctrl+D는 이 함수를 같은 레지스트리로 부릅니다) GetOrEmplace가 컴포넌트 풀을 재할당하면, 방금 얻은 Skin 포인터가 가리키던 메모리가 사라집니다. 값을 지역 변수로 먼저 복사해 두면 안전합니다. 2부에서 본 "희소 집합 풀에 추가하면 기존 포인터가 무효화될 수 있다"의 실제 사례입니다.

    정지(Stop)는 반대 순서입니다: World->EndPlay()(스크립트 OnDestroy, 물리 파괴) → PlayScene.Clear() → Context.Scene = EditScene → 기억해 둔 편집 선택 복원. 일시정지 중의 "한 프레임 진행"은 정확히 1/60초(StepSeconds)만 TickGameplay를 돌립니다.

    규칙: 플레이 중 에디터 코드는 Context.Scene을 쓴다 에디터 애플리케이션에는 편집 씬 멤버(Scene)가 따로 있습니다. 플레이 중에 패널이 그 멤버를 직접 쓰면, 화면에는 플레이 씬이 보이는데 선택·편집은 보이지 않는 편집 씬에 일어납니다. 그래서 "지금 보이는 씬"은 언제나 Context.Scene입니다. 반대로 "편집 씬만" 다뤄야 하는 일(에셋 이동 후 열린 씬 경로 고치기, 실행 취소 스냅샷)은 일부러 편집 씬 멤버를 씁니다. 플레이 중 인스펙터로 바꾼 값은 플레이 씬에만 적용되고 정지하면 사라집니다 — 유니티·언리얼과 같은 동작입니다.

    핵심 개념빙의와 해제

    플레이 중의 뷰포트는 두 가지 역할을 오갑니다. 하나는 게임 화면입니다. 마우스와 키보드가 게임 캐릭터를 움직이고, 게임 카메라로 봅니다. 다른 하나는 편집 화면입니다. 게임이 돌아가는 상태에서 물체를 클릭해 고르고, 기즈모로 옮겨 보고, 자유 카메라로 둘러봅니다. 언리얼은 이것을 Possess/Eject(빙의/해제)라 부르고 F8로 전환합니다. Phase 44에서 사용자가 요청한 것이 바로 이 구분이었습니다.

    "뷰포트에서 편집 상호작용을 해도 되는가"는 단 한 줄의 함수로 정의됩니다.

    // 뷰포트에서 씬 편집 상호작용(클릭 선택, 기즈모, 선택 아웃라인, W/E/R/F, 편집 도구)을 허용하는가: 편집 중이거나 빙의 해제된 플레이
bool CanEditInViewport() const { return !bPlaying || !bPossessed; }

    클릭 선택, 기즈모, 선택 아웃라인, 그리드, 편집 단축키, 뷰포트 툴바, 지형 브러시 같은 도구가 모두 이 함수를 봅니다. 이것을 패널마다 bPlaying && bPossessed로 따로 쓰면 언젠가 하나가 빠지고, 게임 중에 총을 쏘려고 클릭했는데 벽이 선택되어 기즈모가 뜨는 일이 생깁니다. 규칙을 함수 하나에 담고, 모두가 그 함수만 부르게 하는 것이 요점입니다. 계층 창 선택은 빙의 중에도 유지되지만 아웃라인은 그리지 않습니다 — 게임 화면을 그대로 보여 주기 위해서입니다.

    핵심 개념입력 모드: 입력을 UI와 게임에 나누는 규칙

    게임 화면에는 게임 UI(9부)도 있습니다. 인벤토리 창을 열었는데 클릭이 게임에도 전달되어 캐릭터가 공격하면 곤란합니다. 반대로 FPS 게임 중에는 UI가 마우스를 가져가면 안 됩니다. 언리얼의 SetInputMode처럼, ProjectE는 세 가지 모드를 둡니다.

    현재 모드는 전역, 그리고 리비전

    // 현재 입력 모드 (프로세스 전역 하나 — 엔진 DLL 안에 상태가 있다. 메인 스레드 전용).
//   바꾸는 쪽: Lua Game.SetInputMode / 게임 모듈(C++) FInputModeState::Set
//   적용하는 쪽: 런타임/에디터 앱이 매 프레임 Get()으로 입력을 나누고, GetRevision()이 바뀌면 커서 기본값(잠금)을 다시 적용한다
//   초기화: FGameWorld::BeginPlay/EndPlay가 Reset() → 플레이 시작/정지·맵 전환마다 GameAndUI로 돌아간다
class FInputModeState
{
public:
	static EInputMode Get();
	static void       Set(EInputMode Mode); // 같은 모드여도 리비전이 오른다 (커서 잠금 다시 적용)
	static void       Reset();              // GameAndUI
	static uint32     GetRevision();        // Set/Reset마다 1씩 오른다
};

    왜 모드 값만 두지 않고 리비전(변경 횟수)을 따로 둘까요? 커서 잠금 때문입니다. GameOnly는 "들어갈 때" 커서를 숨기고 가둡니다. 그 뒤 스크립트가 Game.SetMouseLocked(false)로 커서를 풀 수도 있습니다. 앱이 매 프레임 "모드가 GameOnly니까 잠근다"를 하면 스크립트의 결정을 매 프레임 덮어씁니다. 그래서 앱은 리비전이 바뀐 프레임에만 모드의 기본값을 적용하고, 그 사이에는 스크립트의 잠금 상태를 존중합니다. 같은 모드를 다시 Set해도 리비전이 오르므로 "다시 잠가라"는 의도도 표현할 수 있습니다. 상태 값(무엇인가)과 사건(언제 바뀌었나)을 분리한 작은 설계입니다.

    BeginPlay/EndPlay가 모드를 GameAndUI로 되돌리는 것도 의도된 규칙입니다. 앞 맵이 메뉴 때문에 UIOnly로 끝났는데 다음 맵이 그대로 이어받으면 조작이 안 되는 버그가 됩니다. 그래서 각 맵의 스크립트가 OnStart에서 자기 모드를 정합니다. 입력 모드는 로컬 화면 상태이므로 멀티플레이에서는 클라이언트에서 도는 스크립트가 부릅니다.

    함정과 교훈플레이 인 에디터의 세부 규칙들

    • 리플렉션에 등록하지 않은 컴포넌트는 플레이에 따라오지 않는다: 복제가 리플렉션의 CopyComponent 훅을 쓰기 때문입니다. 새 컴포넌트를 만들고 등록을 잊으면, 편집 중에는 멀쩡히 보이다가 Play를 누르는 순간 사라집니다. 런타임 전용 데이터에 새 엔티티 참조를 추가했다면 CopyRuntimeData/RemapRuntimeReferences에도 함께 넣어야 합니다(서브트리 복제 FSceneEditOps::CloneSubtree도 같은 함수를 씁니다).
    • 게임 마우스 버튼은 뷰포트에서 누른 것만: 에디터 창에는 게임 말고도 패널이 많습니다. 콘텐츠 브라우저를 클릭했는데 게임 캐릭터가 공격하면 안 되므로, 뷰포트 밖에서 시작된 클릭은 게임 입력에서 뺍니다. 커서 잠금은 창 가운데가 아니라 뷰포트 이미지 가운데(FWindow::SetCursorLockPoint)에 가둡니다.
    • 탈출구를 여러 개: 빙의 + GameOnly면 커서가 사라지므로 사용자가 에디터로 돌아올 방법이 분명해야 합니다. F8(해제), Shift+F1(빙의는 유지하고 커서만 풀기, 뷰포트를 다시 클릭하면 GameOnly가 다시 잠금), ESC(플레이 정지), 포커스 이동이 모두 잠금을 풉니다. 자동 검증 실행은 커서를 아예 잠그지 않습니다.
    • 자동 검증: --play로 플레이를 시작하고 --play-eject를 더하면 10프레임 뒤 빙의를 해제해 편집 카메라 + 선택/기즈모/아웃라인 화면을 스크린샷으로 확인할 수 있습니다. 상태 전이는 테스트 PlayMode_PossessEjectAndInputMode가 지킵니다.
    플레이 모드가 처음 들어올 때의 통합 작업 (2026-10-01) Lua 스크립팅과 플레이 모드는 서브에이전트 트랙에서 만들어 master에 합쳤는데, 같은 밤 다른 트랙(스켈레탈 애니메이션)도 들어오면서 둘이 맞물리는 지점이 생겼습니다. 스킨 메시는 관절 엔티티 목록과 애니메이션 런타임을 리플렉션 밖에 들고 있으므로, 리플렉션 복사만으로는 플레이 복제·Ctrl+D·실행 취소 템플릿 어디에서 복제하든 그 참조가 복제본으로 옮겨지지 않습니다. 그래서 머지 시 통합 작업으로 CopyRuntimeData/RemapRuntimeReferences를 만들어 세 복제 경로가 공유하게 했고, "플레이 중 Undo 차단"도 이때 함께 들어갔습니다. 기능 두 개가 각자 완벽해도, 만나는 지점(복제)에서 새 규칙이 필요해지는 전형적인 사례입니다.
    정리
    • 플레이 = 편집 씬을 FSceneCloner로 메모리 복제 → Context.Scene 포인터 교체 → BeginPlay. 정지 = EndPlay → 사본 폐기 → 편집 씬과 선택 복원.
    • 메모리 복제는 리소스 핸들을 공유해 빠르지만, 엔티티 참조 재매핑과 리플렉션 밖 데이터(CopyRuntimeData)를 챙겨야 한다. 네트워크 플레이는 NetId 일치를 위해 JSON 경로를 쓴다.
    • 빙의 = 입력이 게임으로, 해제 = 게임은 빈 입력으로 계속 + 편집 카메라. 뷰포트 편집 상호작용은 모두 CanEditInViewport() 하나로 판정한다.
    • 입력 모드(GameOnly/GameAndUI/UIOnly)는 순수 함수 SelectGameInput으로 나누고, 전역 상태의 리비전이 바뀔 때만 커서 기본값을 적용한다. 플레이 시작·정지·맵 전환마다 GameAndUI로 초기화.

    생각해 볼 문제

    Q1. 플레이 중 인스펙터로 조명 색을 완벽하게 맞췄습니다. 정지하면 사라집니다. 이 값을 편집 씬에 남기는 기능을 만든다면 무엇이 필요할까요? 플레이 씬 엔티티를 편집 씬 엔티티로 거꾸로 찾는 표가 필요합니다. FPlayMode는 이미 "편집 → 플레이" EntityMap을 들고 있으므로 역방향을 만들 수 있습니다. 그 다음 선택한 컴포넌트 값을 리플렉션으로 편집 씬에 복사하고, 편집 씬 쪽에서 MarkEdited로 실행 취소 단계를 만들어야 합니다(플레이 중에는 커밋이 막혀 있으므로 정지 직후에 적용). 언리얼의 "Keep Simulation Changes"가 이런 기능입니다.
    Q2. 빙의를 해제했을 때 게임에 nullptr(입력 없음) 대신 "빈 입력"을 주는 이유는? nullptr이면 "이번 프레임엔 입력 처리를 건너뜀"이 되어, 직전에 누르던 키 상태가 그대로 남을 수 있습니다. 특히 네트워크 클라이언트는 매 틱 입력을 서버로 보내는데, 보내지 않으면 서버는 마지막으로 받은 "W 누름"을 계속 적용합니다. 모든 키가 떼어진 빈 입력을 명시적으로 보내야 캐릭터가 멈춥니다.
    Q3. 메뉴 화면 스크립트가 Game.SetInputMode("UIOnly")를 부른 뒤 다른 맵으로 이동했습니다. 새 맵 스크립트가 아무것도 하지 않으면 입력 모드는? GameAndUI입니다. 맵 전환도 FGameWorld::BeginPlay/EndPlay를 거치며 FInputModeState::Reset()이 불리기 때문입니다. 이전 맵의 상태가 새는 것을 막는 규칙이고, 새 맵이 GameOnly를 원하면 자기 OnStart에서 정해야 합니다.

    핵심 개념경로 참조와 "옮기면 고친다"

    파일 사이 참조를 유지하는 방법은 크게 둘입니다.

    • 고유 ID(GUID)로 참조: 유니티는 에셋마다 .meta 파일에 GUID를 두고 참조는 GUID로 합니다. 파일을 옮겨도 GUID는 그대로라 참조가 깨지지 않습니다. 대신 ID → 경로 데이터베이스를 항상 최신으로 유지해야 하고, 사람이 파일을 열어 봐도 무엇을 가리키는지 알 수 없습니다.
    • 경로로 참조하고, 옮길 때 고친다: 파일이 읽기 쉽고 git diff가 명확합니다. 대신 이동·이름 변경은 반드시 도구를 통해야 하고, 도구가 참조하는 모든 파일을 찾아 고쳐야 합니다. 언리얼도 기본은 경로 참조입니다.

    ProjectE는 0강에서 "소스 에셋은 사람이 읽고 diff할 수 있는 JSON"을 정했으므로 두 번째 길을 갑니다. 그 대가로 CLAUDE.md에 강한 규칙이 붙습니다: 파일 이동/이름 변경은 반드시 FContentBrowserPanel::MoveAssets/RenameAsset을 거친다.

    상대 경로의 두 가지 기준

    경로 문자열은 어디를 기준으로 할까요? 파일 종류마다 다릅니다.

    왜 머티리얼만 파일 폴더 기준일까요? 머티리얼과 텍스처는 보통 함께 다니기 때문입니다. "Rock" 폴더에 Rock.emat과 텍스처 다섯 장을 두고 폴더째 옮기면, 파일 폴더 기준 경로("Rock_BaseColor.png")는 고칠 것이 하나도 없습니다. 반면 씬은 Content 곳곳의 에셋을 가리키므로 Content 기준이 자연스럽습니다. 갱신기는 확장자로 기준을 정합니다.

    // 에셋 이동/이름 변경 후 다른 에셋 파일 안의 경로 참조를 새 경로로 고친다 (파일 시스템 + JSON 문자열, GPU 비의존).
//   - .escene / .eproject / .eprefab / .estruct / .etable / .edata / .ebuilding: 문자열 값은 Content 기준 상대 경로
//   - 문자열 값이 JSON 객체/배열이면(스크립트 PropertyOverrides) 안쪽 문자열도 같은 규칙으로 고친다
//   - .emat / .eparticle : 문자열 값은 그 파일이 있는 폴더 기준 상대 경로 → 파일 자신이 옮겨져도 다시 계산한다
//   확장자가 있는 문자열만 경로 후보로 보고(엔티티 이름 등 오인 방지), 이동한 파일이거나 이동한 폴더 안이면 바꾼다.
//   파일은 JSON을 다시 쓰지 않고 해당 문자열 토큰만 바꿔 원래 서식(줄바꿈/키 순서)을 유지한다.

    마지막 줄이 실용적인 결정입니다. JSON을 파싱해 고친 뒤 다시 직렬화하면 키 순서·들여쓰기·숫자 표기가 바뀌어, 경로 한 줄만 바뀌었는데 git diff가 파일 전체로 커집니다. 그래서 파싱은 "어떤 문자열이 경로인가"를 알아내는 데만 쓰고, 실제 수정은 원문 텍스트에서 "옛 값" 토큰을 "새 값"으로 바꾸는 방식입니다. 스크립트 오버라이드처럼 JSON 문자열 안에 든 JSON은 따옴표가 이스케이프되어(\"...\") 들어 있으므로 그 형태도 함께 찾습니다.

"모든 등록 컴포넌트의 모든 String 프로퍼티"를 순회하면 되므로, 새 컴포넌트가 에셋 경로를 가져도 이 코드는 바뀌지 않습니다. ①번은 성능과 정확성 둘 다입니다. 리소스 관리자는 경로를 키로 텍스처를 캐시하는데(3부), 캐시 키를 옮기지 않으면 씬이 새 경로를 요청할 때 같은 텍스처를 한 번 더 로드합니다. 자동 검증 --verify-asset-move는 임시 복사본으로 폴더 이동과 텍스처 이름 변경을 한 뒤 "씬 파일/열린 씬/머티리얼 자기 참조/캐시 중복 없음"을 확인하고 정리합니다.

    사이드카 숨기기와 함께 옮기기

    모델 파일(.glb/.gltf/.fbx) 옆에는 사이드카(sidecar) 파일이 붙습니다. 임포트 설정 <모델>.eimport(10부의 쿠킹 입력)와 노티파이·소켓 같은 편집 데이터 <모델>.emeta(6부)입니다. 이들은 모델의 일부이므로 콘텐츠 브라우저 목록에서는 숨기고, 모델을 옮기기·복제·삭제할 때 같은 이름으로 따라가게 합니다. 사용자가 사이드카를 잊고 모델만 옮겨서 설정이 사라지는 일을 원천적으로 막는 것입니다.

    드래그 페이로드

    콘텐츠 브라우저에서 끌어 놓을 수 있는 곳은 많습니다. 폴더(이동), 뷰포트(모델·파티클 배치 / 머티리얼을 커서 아래 메시에 지정), 계층(엔티티로 추가), 인스펙터의 에셋 칸(경로 지정), 그리고 반대 방향으로 윈도우 탐색기에서 들어오는 파일(WM_DROPFILES → 현재 폴더로 복사)까지 있습니다.

    // 콘텐츠 브라우저에서 끄는 에셋 목록. ImGui 페이로드에는 형식만 싣고 경로는 여기에 둔다 (여러 파일, 가변 길이).
// 받는 쪽: 뷰포트(배치/머티리얼 지정), 계층(추가), 인스펙터 에셋 칸, 콘텐츠 폴더(이동)

    ImGui의 드래그 앤 드롭 페이로드는 고정 크기 바이트 덩어리를 복사하는 방식이라, 길이가 제각각인 경로 여러 개를 싣기 불편합니다. 그래서 페이로드에는 형식 이름만 싣고, 실제 경로 목록은 정적 저장소에 둡니다. 받는 쪽은 형식이 맞으면 저장소를 읽습니다. 에셋 칸이 받을 확장자는 리플렉션 프로퍼티에 .AssetFilter(".emat")처럼 적어 두면 인스펙터가 알아서 맞지 않는 드롭을 거절합니다. 계층의 엔티티를 콘텐츠 폴더에 놓으면 프리팹 파일이 됩니다(38강).

    썸네일

    Phase 10에서 콘텐츠 브라우저는 언리얼처럼 썸네일 타일을 갖게 됐습니다. 결정은 이렇습니다: 전용 FSceneRenderer 하나(256×256 고정, 그림자 512×2장, 하늘 없이 어두운 배경)로 보이는 타일만 프레임당 2개씩 그려 메모리에 두고, 파일 수정 시각이 바뀌면 다시 그립니다. 모델은 첫 포즈, 머티리얼은 구, 파티클은 1.5초 진행한 모습입니다. 이미지 썸네일은 텍스처가 _SRGB 형식이라 ImGui로 바로 보이면 어둡게 나오므로(34강의 색공간 문제의 반대 방향), 이미지를 발광 슬롯에 넣은 판을 톤매핑 없이 그려 원래 색으로 보여 줍니다. 디스크 캐시는 "즉석 생성으로 충분히 빠름"을 이유로 보류됐습니다.

    핵심 개념에셋 편집기의 공통 틀

    Phase 9는 머티리얼/스태틱 메시/애니메이션/파티클 편집 창을 한 번에 만들면서 공통 틀을 먼저 세웠습니다. 모든 편집 창은 FAssetEditor를 상속하고, 파생 클래스는 네 가지 질문에만 답합니다.

    // 에셋 편집 창 공통 기반: 파일 하나 + 미리보기 + 창 안 실행 취소(에셋 상태 문자열 스냅샷) + 저장/되돌리기.
class FAssetEditor
{
protected:
	// 파일에서 에셋을 읽어 편집 상태/미리보기 구성. 되돌리기에서도 다시 불리므로 여러 번 호출해도 안전해야 한다
	virtual bool        LoadAsset(FAssetEditorEnvironment& Env) = 0;
	virtual bool        SaveAsset(FAssetEditorEnvironment& Env) = 0;
	virtual std::string CaptureState() const = 0;
	virtual void        RestoreState(FAssetEditorEnvironment& Env, const std::string& State) = 0;
	virtual void        DrawProperties(FAssetEditorEnvironment& Env) = 0;

	FAssetPreview         Preview;
	std::filesystem::path Path;
	FUndoHistory          History;      // 35강과 같은 클래스
	FPendingEdit          PendingEdit;  // 35강과 같은 클래스
};

    35강의 FUndoHistory와 FPendingEdit을 그대로 재사용한다는 점이 핵심입니다. 씬 대신 "에셋 상태 문자열"을 스냅샷으로 쓸 뿐입니다. 대부분의 편집기에서 CaptureState는 에셋 JSON 그 자체입니다.

    새 편집기를 추가하는 절차는 CLAUDE.md에 고정되어 있습니다: FAssetEditor를 상속해 다섯 함수를 구현하고, FAssetEditorManager의 CreateEditor/CanOpen에 확장자를 등록합니다. 매니저는 경로당 창 하나를 보장하고, 창 제목을 ### 고정 ID로 만들며(34강), 저장 안 한 창을 닫을 때 확인 대화상자를 띄웁니다. 창이 포커스를 가지면 Ctrl+Z/Y/S와 Delete는 그 창이 처리하고 메인 씬으로 전달하지 않습니다.

    전용 미리보기 씬과 공유 렌더러

    머티리얼 편집 창 안의 구, 애니메이션 편집 창의 캐릭터는 어디에 그려질까요? 열린 씬에 임시로 넣으면 저장·실행 취소·플레이에 섞입니다. 그래서 창마다 자기 씬을 가진 FAssetPreview를 둡니다. 미리보기 코드는 Context.Scene/Context.Camera를 쓰지 않습니다.

    // 에셋 편집 창의 미리보기: 전용 씬 + 궤도 카메라 + 고정 크기 오프스크린 타깃.
// 모든 미리보기는 같은 전용 씬 렌더러(FAssetEditorManager 소유)로 그리므로 타깃 크기를 고정해
// 렌더러의 HDR/블룸 버퍼가 창마다 다시 만들어지지 않게 한다. 창에는 종횡비를 유지해 맞춰 표시한다.
class FAssetPreview
{
public:
	static constexpr uint32 Width  = 960;
	static constexpr uint32 Height = 720;
	...
};

    렌더러는 창마다 두지 않고 하나를 공유합니다. FSceneRenderer는 HDR 버퍼, 블룸 체인, 그림자 맵, TAA 이력처럼 화면 크기에 묶인 리소스를 많이 가집니다. 창 다섯 개가 각자 렌더러를 가지면 메모리가 다섯 배가 되고, 크기가 서로 다른 창을 한 렌더러로 그리면 매번 버퍼를 다시 만듭니다. 그래서 타깃을 960×720으로 고정하고 창에는 종횡비를 유지해 맞춥니다. 메인 뷰포트의 통계·자동 노출과도 분리됩니다. 3D 미리보기가 필요 없는 편집기(노드 그래프, 데이터 테이블)는 UsesPreview() = false로 렌더 타깃 자체를 만들지 않습니다.

    공유 리소스를 실시간으로 고치기

    머티리얼 편집기에서 거칠기 슬라이더를 움직이면 미리보기 구만이 아니라 열린 씬의 같은 머티리얼을 쓰는 모든 물체가 즉시 바뀝니다. 편집기가 리소스 관리자 캐시의 공유 머티리얼을 직접 고치기 때문입니다(Phase 9 결정, 언리얼과 같은 방식). 편리하지만 대가가 있습니다. 저장하지 않고 창을 닫으면 씬에는 "파일에 없는 값"이 남습니다. 그래서 Close가 dirty면 RevertToSaved로 파일을 다시 읽어 공유 리소스를 파일 상태로 되돌립니다. CLAUDE.md 규칙: "공유 리소스를 실시간으로 고치는 편집기는 닫을 때 저장 안 한 변경을 파일 상태로 되돌린다".

    함정과 교훈닫기 크래시와 남은 구멍

    "머티리얼 저장 안 하고 닫으면 크래시" (2026-09-30) 사용자 보고로 드러난 버그입니다. 창을 닫으면 미리보기 렌더 타깃을 지연 해제하는데, 이 요청이 프레임 도중(UI 단계, RHI BeginFrame 전)에 들어오면 직전 프레임 칸의 해제 목록에 쌓였습니다. 지연 해제는 "그 프레임 칸의 GPU 작업이 끝나면 해제"이므로, 직전 프레임이 끝나자마자 해제되었습니다. 그런데 이번 프레임이 아직 그 미리보기 타깃을 그리는 중이었고, 결과는 GPU 장치 제거(device removed)였습니다. 수정은 RHI가 요청을 모아 두었다가 EndFrame에 실제 제출된 프레임 칸으로 옮기는 것입니다. 재현용 자동 검증 --verify-asset-close(값을 바꾼 뒤 저장 안 하고 닫기)를 9회 돌려 오류가 없음을 확인했습니다. 교훈: 지연 해제의 "언제"는 요청 시점이 아니라 "마지막으로 그 리소스를 쓰는 제출" 기준이어야 합니다.
    • Lua 안의 경로 문자열은 갱신되지 않는다: Launcher.lua 안의 "Materials/Orange.emat" 같은 문자열은 참조 갱신 대상이 아니라서, 옮기면 플레이 때 깨집니다(Phase 10 후속 과제). 스크립트가 쓰는 에셋은 경로를 하드코딩하기보다 Properties의 에셋 타입(인스펙터 칸 → 씬의 PropertyOverrides JSON에 저장)으로 받는 편이 안전합니다. 그 문자열은 "JSON 안의 JSON"으로 갱신 대상이기 때문입니다.
    • 파일 조작은 Ctrl+Z 대상이 아니다: 삭제는 휴지통(FOF_ALLOWUNDO)으로 보내고 참조하는 파일 수를 확인 창에 보여 주는 것으로 대신합니다. 씬 실행 취소는 씬 편집만 다룹니다.

    정리
    • ProjectE 에셋은 경로로 서로를 참조하므로, 이동·이름 변경은 반드시 MoveAssets/RenameAsset을 거친다.

    왜 필요한가가로등 200개를 한 번에 고치고 싶다

추가 결정 (2026-09-30): 인스턴스는 씬에 일반 엔티티로 저장하고 연결 컴포넌트(FPrefabInstanceComponent 루트 /
FPrefabLinkComponent 엔티티마다)를 단다. 오버라이드는 "바꾼 항목의 키 목록"을 씬에 저장(값은 컴포넌트에).

    핵심 개념인스턴스를 어떻게 저장할 것인가

    씬 파일에 인스턴스를 저장하는 방법은 크게 둘입니다.

    • 참조 + 차이만 저장: 씬에는 "LampPost.eprefab, 위치 (100,0,0), 전구 색 = 빨강"만 적습니다. 파일이 작지만, 씬을 읽을 때마다 원본 파일이 반드시 있어야 하고, 런타임·서버·네트워크 복제 등 씬을 읽는 모든 코드가 "프리팹 펼치기"를 알아야 합니다.
    • 펼친 엔티티 + 연결 정보 저장: 씬에는 인스턴스의 엔티티들이 평범한 엔티티로 전부 들어가고, 각 엔티티에 "나는 어느 원본의 몇 번 엔티티"라는 표식이 붙습니다. 파일은 커지지만 씬은 그 자체로 완결됩니다.

//   Asset:     Content 기준 .eprefab 경로
//   Overrides: 인스턴스에서 바꾼 항목 목록(FPrefabOverrides JSON). 값은 엔티티 컴포넌트에 그대로 있고 여기에는 "무엇을 바꿨는지"만 둔다
struct FPrefabInstanceComponent
{
	std::string Asset;
	std::string Overrides;
};

// 프리팹에서 온 엔티티의 연결.
//   Id:   프리팹 파일 안에서 고정된 엔티티 ID (이름이 바뀌어도 유지). 중첩 프리팹 안 엔티티는 "바깥 ID/안쪽 ID" ("3/2")

// 연결이 없는 자식은 인스턴스에서 추가한 엔티티로 본다.
struct FPrefabLinkComponent
{
	std::string Id;
	FEntity     Root;

    핵심 개념오버라이드 = 현재 원본과의 차이

    오버라이드를 기록하는 방법도 두 가지가 가능합니다. 하나는 "인스펙터에서 값을 바꾸는 순간 그 키를 표시"하는 방법입니다. 그러면 인스펙터, 기즈모, 스크립트 편집, 실행 취소, 붙여넣기 … 값을 바꾸는 모든 경로가 표시 코드를 알아야 합니다. ProjectE는 다른 방법을 택했습니다: 값을 비교해서 알아낸다.

    핵심 개념왜 ChangePrefab의 순서가 중요한가

    오버라이드의 정의에 "현재 원본과의 차이"라는 말이 들어 있습니다. 이 정의가 옳으려면 한 가지 전제가 필요합니다: 기록하는 순간 인스턴스는 현재 원본에 맞춰져 있어야 한다. 원본이 바뀌었는데 아직 인스턴스를 동기화하지 않은 채로 차이를 계산하면, 원본 쪽 변화가 "인스턴스가 바꾼 것"처럼 보입니다.

    bool FEditorApplication::ChangePrefabAsset(const std::function<bool()>& Change)
{
	// 순서가 중요하다: 오버라이드 차이는 "현재 원본"과 비교하므로 원본이 바뀌기 전에 기록하고, 바뀐 뒤에는 인스턴스를 새 원본에 맞춘다
	FPrefabLibrary& Library = FPrefabLibrary::Get();
	Library.RecordAllOverrides(Scene);
	const bool bOk = Change();
	Library.Invalidate();
	Library.SyncAllInstances(Scene);
	FEditorActions::PruneSelection(Context);
	FSceneAssetResolver::Resolve(Scene, Resources, Context.ContentDirectory);
	return bOk;
}

    마지막 두 줄도 이유가 있습니다. 원본에서 엔티티가 지워졌다면 동기화가 인스턴스의 그 엔티티를 파괴하므로 선택에서 정리하고(PruneSelection), 원본의 메시·머티리얼 경로가 바뀌었다면 새로 해석합니다. 이 함수는 에디터 애플리케이션에 있고 패널에는 Context.ChangePrefab이라는 함수 객체로만 노출됩니다(34강의 "위로 가는 요청" 패턴).

    설계 이유: 차이로 정의하면 기록 경로가 하나뿐이다 "바꿀 때 표시" 방식은 값을 바꾸는 수십 개 경로에 표시 코드를 심어야 하고, 하나만 빠져도 오버라이드가 조용히 사라집니다. "커밋 때 비교" 방식은 기록 경로가 RecordOverrides 하나라 빠질 곳이 없습니다. 대신 비교 기준의 정합성(위 순서)이라는 한 가지 규칙만 지키면 됩니다. 규칙 하나를 지키는 것이 수십 곳을 지키는 것보다 쉽습니다.

    핵심 개념중첩 프리팹과 고정 ID

    가로등 프리팹(LampPost) 안에 전등 프리팹(Lamp)을 넣을 수 있습니다. 그러면 씬의 엔티티 하나가 "바깥 원본의 어느 엔티티"이면서 동시에 "안쪽 원본의 어느 엔티티"입니다. ProjectE는 이것을 ID 경로로 표현합니다.

    왜 이름이 아니라 번호일까요? 이름은 사용자가 바꾸고, 같은 이름의 형제가 여럿일 수 있습니다. 원본에서 "Bulb"를 "LightBulb"로 바꿨는데 이름으로 대응하고 있었다면, 모든 인스턴스에서 Bulb가 지워지고 LightBulb가 새로 생겨 오버라이드가 사라집니다. 생성할 때 한 번 부여하고 절대 재사용하지 않는 번호(NextId로 관리)는 이런 일이 없습니다. 데이터베이스의 기본 키와 같은 발상입니다.

    ProjectE에서는만들기, 편집하기, 생성하기

    • 만들기: 계층 창의 엔티티를 콘텐츠 브라우저 폴더에 끌어 놓습니다(37강의 E_ENTITY 페이로드). FEditorActions::CreatePrefabs가 선택된 최상위 엔티티마다 .eprefab을 만들고, 원래 엔티티를 그 인스턴스로 바꿉니다. 인스턴스 일부나 루트를 다시 프리팹으로 만드는 것은 거부합니다.
    • 편집하기: 프리팹 편집 창(FPrefabEditor, 계층 + 인스펙터)은 37강의 FAssetEditor를 상속합니다. 저장은 Context.ChangePrefab으로 감싸 열린 씬의 인스턴스에 반영됩니다. 인스턴스에서 "원본에 적용"(ApplyToPrefab)을 누르는 것도 같은 경로입니다.
    • 실행 취소·복제·플레이: 스냅샷 복원 후에는 동기화하고(씬 로드가 자동으로 함), 플레이 모드 복제(36강)는 링크의 Root가 FEntity 타입 프로퍼티이므로 리플렉션 재매핑으로 자동으로 복제본을 가리킵니다.
    • Lua에서 생성: 스크립트 프로퍼티에 프리팹 타입을 두고 Scene.SpawnPrefab(prefab, position?, onSpawned?)로 만듭니다. 계획과 달리 반환값이 아니라 콜백입니다 — 그 프레임 스크립트 갱신이 끝난 뒤 만들고 콜백에 루트를 넘깁니다(지연 생성). 스크립트가 도는 도중에 씬 구조를 바꾸지 않는다는 점에서 2부의 "순회 중 구조 변경 금지"와 같은 맥락입니다.
    • 파일 이동: 원본을 옮기거나 이름을 바꾸면 씬·다른 프리팹·스크립트 오버라이드(JSON 안 JSON)의 참조가 37강의 갱신기로 고쳐지고, 프리팹 캐시는 경로가 키이므로 비웁니다.

    함정과 교훈알려진 제한

    Phase 15는 기능을 끝내면서 제한을 명시적으로 기록했습니다. 프리팹 시스템을 설계할 때 어디가 어려운지를 잘 보여 줍니다.

    • 인스턴스 안에서 원본 엔티티의 부모를 바꾸면 다음 동기화 때 원본 계층으로 돌아간다: 오버라이드 키는 "컴포넌트.프로퍼티" 단위인데, 계층(부모)은 키로 기록하지 않기 때문입니다. 동기화 3단계가 "원본에서의 부모"로 다시 붙입니다.
    • 변형(Variant) 프리팹은 지원하지 않는다: 루트가 다른 프리팹의 인스턴스인 프리팹(유니티의 Prefab Variant)은 "오버라이드의 오버라이드"가 필요해 범위 밖으로 뒀습니다.
    • 모델 경로가 원본에서 바뀌면 이미 만든 모델 하위 노드는 다시 만들지 않는다, 열린 다른 프리팹 편집 창은 안쪽 원본 저장을 즉시 반영하지 않는다(다시 열면 반영).
    규칙 요약 (CLAUDE.md "프리팹") 원본을 바꾸는 코드는 반드시 Context.ChangePrefab(기록 → 변경 → Invalidate → SyncAllInstances → 해석)을 거치고, 원본을 바꾼 뒤 동기화 전에 기록하지 않는다. 루트의 위치/회전/이름은 항상 인스턴스 값. 새 컴포넌트/프로퍼티는 리플렉션 등록만 하면 동기화·오버라이드 대상이 된다(리소스 핸들/PF_Transient 제외, 경로 문자열이 바뀐 컴포넌트는 핸들을 비워 다시 해석).
    정리
    • 인스턴스는 씬에 일반 엔티티로 펼쳐 저장하고, 루트에 FPrefabInstanceComponent(원본 경로 + 오버라이드 키), 엔티티마다 FPrefabLinkComponent(고정 ID + 인스턴스 루트)를 단다. 씬을 읽는 다른 시스템은 프리팹을 몰라도 된다.
    • 오버라이드 = 인스턴스와 현재 원본의 값 차이를 커밋·저장 직전에 RecordOverrides로 계산한 키 목록. 값을 바꾸는 경로가 많아도 기록 경로는 하나다.
    • 동기화는 원본 값을 입히되 오버라이드 키는 건너뛰고, 원본에 생긴/사라진 엔티티를 맞춘다. 씬 로드가 자동으로 한다.
    • 원본 변경은 기록 → 변경 → 캐시 비우기 → 동기화 순서(ChangePrefab)여야 원본 변화가 가짜 오버라이드로 굳지 않는다.
    • 중첩 엔티티 ID는 "바깥/안쪽", ID는 이름이 아니라 생성 시 부여한 번호. 순환은 저장·드롭 때 거부.

    생각해 볼 문제

    Q1. 인스턴스의 전구 색을 빨강으로 바꿨다가, 마음이 바뀌어 원본과 같은 노랑으로 손으로 되돌렸습니다. 이 프로퍼티는 오버라이드 목록에 남을까요? 남습니다. RecordCore는 값이 다르면 키를 넣기만 하고, 같다고 해서 빼지는 않습니다. 그래서 나중에 원본을 주황으로 바꿔도 이 인스턴스는 노랑을 유지합니다. 원본을 따르게 하려면 우클릭 "되돌리기"(RevertProperty)로 키를 명시적으로 지워야 합니다. 의도를 보존하는 쪽을 택한 설계입니다.
    Q2. 프리팹 원본에서 엔티티 이름 "Bulb"를 "LightBulb"로 바꿨습니다. 인스턴스 200개에서 이 엔티티의 오버라이드는 어떻게 될까요? 이름으로 대응했다면? ProjectE에서는 ID("3")로 대응하므로 같은 엔티티로 인식되고, 오버라이드(예: 빨간 색)는 그대로 유지되며 이름만 새 원본 이름을 따릅니다(인스턴스에서 이름을 바꾼 경우는 예외). 이름으로 대응했다면 "Bulb"는 원본에서 사라진 엔티티로, "LightBulb"는 새 엔티티로 보여서 200개 인스턴스 모두에서 Bulb가 삭제되고 새로 만들어져 오버라이드가 사라집니다.
    Q3. 원본에 들어 있는 엔티티를 인스턴스에서 삭제했습니다. 다음 동기화 때 다시 생기지 않는 이유는? 커밋 때 RecordCore가 "원본에는 있는데 인스턴스에 대응 엔티티가 없다"를 발견하고 그 ID를 RemovedEntities에 넣습니다(하위 트리는 가장 위 것만). 동기화는 이 목록의 엔티티를 건너뛰므로 다시 만들지 않습니다. 되돌리려면 "전부 되돌리기"(RevertAll)로 목록을 비우면 됩니다.

    왜 필요한가설정은 늘어나고, 주인은 다르다

    엔진이 자라면 "정해 둘 값"이 쏟아집니다. 게임 시작 맵, 플레이어 프리팹, 물리 중력과 고정 스텝, 네트워크 포트, 패키지 실행 파일 이름과 아이콘, Steam App ID, 화면 기본 해상도 … 그리고 에디터 쪽에는 카메라 속도, 마우스 감도, 기즈모 스냅, 자동 저장 간격, 마지막으로 연 씬이 있습니다.

    Phase 20 이전에는 이런 값이 .eproject 파일에 조금, 명령줄 인자에 조금, 코드 상수에 조금 흩어져 있었습니다. 문제는 흩어진 것만이 아닙니다. 값마다 주인이 다릅니다.

    • "게임 기본 맵"은 팀 전체가 같아야 합니다. 저장소에 커밋해야 합니다.
    • "마우스 감도"는 나만의 취향입니다. 커밋하면 동료의 감도를 덮어씁니다.
    • "이 프로젝트에서 마지막으로 연 씬"은 나의, 이 프로젝트에 대한 상태입니다. 다른 프로젝트를 열면 달라야 합니다.

    2026-10-01 사용자는 "언리얼의 Project Settings, Editor Preferences처럼"을 요청했습니다. 언리얼은 이것을 Config/Default*.ini(커밋)와 사용자별 ini로 나눕니다. ProjectE는 같은 생각을 JSON + 리플렉션으로 옮겼습니다.

    핵심 개념설정 범위(scope)

    // 설정 저장 범위
enum class ESettingsScope : uint8
{
	Project,     // <프로젝트>/Config/<Id>.json — 저장소에 커밋 (언리얼 Config/Default*.ini)
	EditorUser,  // %LOCALAPPDATA%/ProjectE/EditorPreferences/<Id>.json — 개인, 모든 프로젝트 공통
	ProjectUser, // <Saved>/Config/<Id>.json — 개인, 프로젝트별 (마지막으로 연 씬 등 상태)
};

    범위에서 파일 경로를 얻는 코드는 짧습니다. 섹션 Id가 곧 파일 이름입니다.

    std::filesystem::path FSettingsSection::GetFilePath() const
{
	const std::wstring FileName = FStringConv::ToWide(Id) + L".json";
	if (Scope == ESettingsScope::EditorUser)
	{
		return FSettingsRegistry::GetEditorUserDirectory() / FileName;
	}
	if (Scope == ESettingsScope::ProjectUser)
	{
		return FPaths::GetSavedDirectory() / L"Config" / FileName;
	}
	return FPaths::HasProject() ? FPaths::GetProjectConfigDirectory() / FileName : std::filesystem::path();
}
    왜 섹션마다 파일 하나인가 프로젝트 설정을 파일 하나(Settings.json)에 모으면, 한 사람이 물리 중력을, 다른 사람이 네트워크 포트를 바꿨을 때 같은 파일에서 병합 충돌이 납니다. 섹션마다 파일을 나누면(Physics.json, Network.json) 서로 다른 섹션의 변경은 충돌하지 않고, diff를 보면 무엇이 바뀌었는지 파일 이름만으로 압니다(Phase 20 결정: "섹션마다 파일 — diff가 작다").

    핵심 개념구조체 + 등록 = 창 + 저장

    설정 하나를 추가할 때 해야 하는 일이 많으면 사람들은 상수를 코드에 박아 넣습니다. 그래서 목표는 "구조체 필드 하나 + 등록 한 줄"이었습니다. 이를 가능하게 한 것이 2부의 리플렉션입니다. 인스펙터가 컴포넌트를 리플렉션으로 그리듯, 설정 창은 설정 구조체를 리플렉션으로 그립니다.

    // "Maps" — 맵 & 모드 (Content 기준 경로)
struct FMapsSettings
{
	std::string EditorStartupMap; // 에디터 시작 맵 (비면 GameDefaultMap)
	std::string GameDefaultMap;   // 런타임/패키지 게임 시작 맵
	std::string ServerDefaultMap; // 전용 서버 시작 맵 (비면 GameDefaultMap)
	std::string PlayerPrefab;     // 멀티플레이: 입장한 플레이어마다 서버가 만드는 프리팹
};

Registry.Register(Maps, { "Maps", "맵 & 모드", GProjectCategory, "시작 맵과 플레이어 프리팹 (Content 기준 경로)" })
	.Property(&FMapsSettings::EditorStartupMap, "EditorStartupMap", "에디터 시작 맵").AssetFilter(".escene")
	.Tooltip("에디터를 열 때 여는 씬. 비면 게임 기본 맵 (에디터 환경설정 '시작 시 마지막 씬 열기'가 우선)")
	.Property(&FMapsSettings::GameDefaultMap, "GameDefaultMap", "게임 기본 맵").AssetFilter(".escene")
	...
	.Property(&FMapsSettings::PlayerPrefab, "PlayerPrefab", "플레이어 프리팹").AssetFilter(".eprefab");

    이 등록 한 번으로 생기는 것들:

    • 파일: Config/Maps.json을 읽고 씁니다. JSON 키는 등록 이름("GameDefaultMap"), 화면 이름은 한국어("게임 기본 맵")로 분리됩니다.
    • 창: "편집 → 프로젝트 설정"의 왼쪽 "프로젝트" 카테고리 아래 "맵 & 모드" 섹션, 오른쪽에 이름/값 표, 툴팁. .AssetFilter(".escene") 덕분에 값 칸은 콘텐츠 브라우저에서 씬 파일을 끌어 놓을 수 있는 칸이 됩니다(37강).
    • 검색·기본값: 창 왼쪽 검색은 모든 섹션의 일치 항목을 보여 주고, "섹션 기본값으로"는 등록 때 만든 ResetToDefaults(Object = T{})를 부릅니다.

    4바이트 enum은 .Enum({{이름, 표시}})로 콤보 상자가 되고 JSON에는 숫자 대신 이름이 저장되며, 숫자 범위는 .Range(min, max)로 슬라이더와 자르기가 붙습니다. 이 리플렉션 확장(enum, 툴팁)은 Phase 20에서 만들어 인스펙터도 함께 얻었습니다.

    관용적인 읽기 규칙

    설정 파일은 사람이 손으로 고치기도 하고, 엔진 버전이 바뀌며 필드가 늘거나 줄기도 합니다. 그래서 JSON ↔ 리플렉션 변환(FReflectionJson)은 관용적으로 읽습니다(Phase 20-1): 파일에 없는 키는 기존 값 유지(기본값), 모르는 키는 무시, 타입이 틀리면 경고, 범위를 벗어나면 자름. 덕분에 새 설정 필드를 추가해도 예전 Maps.json은 그대로 읽히고, 필드를 지워도 예전 파일이 오류를 내지 않습니다.

    RegisterCustom: 리플렉션으로 그릴 수 없는 설정

    모든 설정이 "이름 = 값" 표로 표현되지는 않습니다. 입력 액션 목록(액션마다 바인딩 여러 개, 수정자, 문턱 — 7부)과 충돌 레이어(16칸 이름 + 레이어×레이어 대칭 행렬 — Phase 43)가 그렇습니다. 이런 섹션은 리플렉션 대신 읽기/쓰기 함수를 직접 넘기고, 설정 창은 Id별 전용 UI를 그립니다.

	[this]() { return Collision.ToJson(); }, [this]() { Collision = {}; });

    프로젝트 설정의 로드 순서와 .eproject 정리

    Phase 20은 기존 프로젝트를 깨지 않고 옮겨야 했습니다. 예전 .eproject에는 DefaultScene, PlayerPrefab, DisplayName 같은 필드가 들어 있었습니다. 결정은 이렇습니다: .eproject에는 프로젝트의 정체성(Name/EngineVersion/GameModule)만 남기고, 나머지는 로드할 때 설정으로 옮겨 읽되 Config 파일이 있으면 그쪽이 이깁니다.

    void FProjectSettings::LoadForProject(const FProjectDescriptor& Descriptor)
{
	ResetToDefaults();                                    // ① 기본값
	// 마이그레이션: 예전 .eproject에 있던 값 (Config 파일이 있으면 그쪽이 덮어쓴다)
	const FProjectLegacyFields& Legacy = Descriptor.Legacy;  // ② 예전 필드
	if (!Legacy.DefaultScene.empty()) { Maps.GameDefaultMap = Legacy.DefaultScene; }
	Maps.PlayerPrefab = Legacy.PlayerPrefab;
	...
	FSettingsRegistry::Get().LoadAll(ESettingsScope::Project);   // ③ Config/<Id>.json
}

    "기본값 → 옛 위치 → 새 위치" 순서로 겹쳐 읽는 것은 데이터 이전(migration)의 정석입니다. 사용자가 아무것도 하지 않아도 예전 프로젝트가 같은 값으로 열리고, 설정 창에서 한 번 저장하면 새 위치에 쓰입니다. 규칙도 하나 생겼습니다: .eproject에 새 값을 넣지 않는다. 패키징 스크립트(PowerShell)도 같은 파일을 같은 규칙으로 읽어야 하므로 Scripts/ProjectSettings.ps1(Read-ProjectSettings)이 C++과 같은 순서를 구현합니다.

    값이 바뀌면 바로 적용, 조작이 끝나면 저장

    언리얼처럼 설정 창에는 "저장" 버튼이 없습니다. 값이 바뀐 프레임에 섹션의 OnChanged를 불러 즉시 적용하고(예: 뷰포트 섹션 → 카메라 시야각·감도 즉시 반영), 파일 저장은 35강과 같은 원리로 조작이 끝난 뒤 합니다. 슬라이더를 끄는 동안 매 프레임 파일을 쓰지 않기 위해서입니다.

    	if (Selected->OnChanged) { Selected->OnChanged(); }
	PendingSave.insert(Selected->Id);
	...
// 드래그/입력이 끝난 뒤 저장 (매 프레임 쓰지 않게)
if (!ImGui::IsAnyItemActive())
{
	SavePendingSections();
}

    값 위젯은 FPropertyWidgets로 분리해 인스펙터와 공유합니다. 그래서 인스펙터에 enum 콤보·툴팁·에셋 칸이 생기면 설정 창에도 똑같이 생기고, 그 반대도 마찬가지입니다.

    모든 설정이 즉시 효과를 내지는 않습니다. 물리 값은 FPhysicsSystem::Begin이, 네트워크 값은 세션을 열 때 읽습니다. 그래서 섹션 설명에 "다음 플레이(물리 시작)부터 적용", "다음 세션부터 적용"을 적고, 다시 시작해야 하는 섹션은 bRequiresRestart로 창에 표시합니다. "바꿨는데 왜 안 바뀌지?"라는 혼란을 문구로 막는 것입니다.

    함정과 교훈자동 검증은 개인 설정을 쓰지 않는다

    ProjectE는 --exit-after/--screenshot으로 에디터를 자동 실행해 화면을 검증합니다(1강). 이 실행이 개인 설정을 읽고 쓰면 두 가지 문제가 생깁니다.

    • 재현성: 검증 실행이 "마지막으로 연 씬"을 읽으면, 어제 개발자가 무엇을 열었느냐에 따라 시작 씬이 달라집니다. 스크린샷 비교가 의미를 잃습니다. 마우스 감도나 스냅 값도 마찬가지입니다.
    • 오염: 검증 실행이 끝날 때 "마지막 씬 = 테스트 씬", "카메라 = 검증용 위치", "스냅 = 기본값"을 저장하면, 개발자가 다음에 에디터를 열 때 자기 환경이 바뀌어 있습니다.
    // 개인 환경설정: 이 프로젝트에서 마지막으로 연 씬 (자동 검증은 개인 상태를 쓰지 않는다)
const std::string& LastScene = FEditorPreferences::Get().ProjectState.LastOpenedScene;

    같은 원칙이 엔진 곳곳에 있습니다. 자동 검증은 마지막 씬 기억(RememberOpenedScene)과 자동 저장을 건너뛰고, 플레이어의 입력 재지정 파일(InputBindings.json)과 게임 사용자 화면 설정 파일도 읽거나 쓰지 않으며, 세이브 게임은 임시 폴더로 돌립니다. 테스트는 사용자의 상태에 의존하지도, 상태를 바꾸지도 않는다 — 자동화가 믿을 만하려면 반드시 지켜야 하는 규칙입니다.

    Phase 20 검증 (2026-10-01) 검증은 설정이 "저장된다"에서 끝나지 않고 "모든 소비자가 그 값을 쓴다"까지 확인했습니다: 런타임과 패키지가 Config/Maps.json의 게임 기본 맵으로 시작하는지, 전용 서버가 서버 기본 맵과 LAN 포트를 쓰는지, 패키지 exe 스탬프가 Config/Project.json을 읽는지. 설정 시스템의 버그는 대개 "창에서 바꿨는데 실제로는 다른 곳에서 옛 값을 읽는다"이므로, 소비자 쪽을 확인하는 것이 핵심입니다. 이후 후속 과제로 남은 것은 속성별 기본값 되돌리기 화살표, 배열/구조체 프로퍼티, 게임 모듈의 자체 설정 섹션 예시 등입니다. 입력 매핑(Phase 24)과 충돌 레이어(Phase 43)는 이 체계 위에 RegisterCustom 섹션으로 들어왔습니다.
    정리
    • 설정은 주인에 따라 범위가 셋: Project(<프로젝트>/Config/<Id>.json, 커밋), EditorUser(%LOCALAPPDATA%/ProjectE/EditorPreferences/), ProjectUser(<Saved>/Config/, 상태). 섹션마다 파일 하나.
    • 새 설정 = 구조체 필드 + 등록부의 .Property(...). 창(FSettingsWindow, 인스펙터와 같은 FPropertyWidgets)과 저장(FReflectionJson, 관용적 읽기)이 자동으로 생긴다.
    • 표로 표현할 수 없는 설정은 RegisterCustom(ReadJson/WriteJson + 전용 UI).
    • 프로젝트 설정은 기본값 → .eproject 예전 필드 → Config 파일 순으로 읽고, .eproject에는 정체성만 둔다. 값 변경은 OnChanged로 즉시, 저장은 조작이 끝난 뒤.
    • 자동 검증 실행은 개인 설정과 상태를 읽지도 쓰지도 않는다 — 재현성과 사용자 환경 보호.

    생각해 볼 문제

    Q1. "에디터 UI 글꼴 크기" 설정을 추가하려 합니다. 어느 범위에 두고, 무엇을 고치면 될까요? 개인 취향이고 프로젝트와 무관하므로 EditorUser 범위입니다. FEditorGeneralSettings(또는 새 섹션 구조체)에 float FontScale = 1.0f; 필드를 추가하고 EditorPreferences.cpp 등록에 .Property(&...::FontScale, "FontScale", "글꼴 크기").Range(0.5f, 2.0f, 0.05f)를 더하면 창과 파일 저장이 생깁니다. 즉시 반영하려면 섹션의 OnChanged에서 ImGui 글꼴 배율을 갱신하고, 그렇지 않다면 재시작 필요를 표시합니다.
    Q2. 팀원 A가 Physics.json의 중력을, B가 Network.json의 포트를 바꿔 커밋했습니다. 모든 설정이 파일 하나였다면 무엇이 달랐을까요? 같은 파일의 다른 줄이라 git이 자동 병합할 수도 있지만, 키 순서가 재정렬되거나 들여쓰기가 바뀌면 충돌이 나기 쉽고, diff만 보고 "어느 영역의 설정이 바뀌었는지" 알기도 어렵습니다. 섹션마다 파일을 나누면 서로 다른 섹션의 변경은 애초에 다른 파일이라 충돌하지 않습니다.
    Q3. 자동 검증으로 에디터를 실행할 때 환경설정 "시작 시 마지막 씬 열기"를 따르게 하면 어떤 문제가 생길까요? 개발자가 마지막으로 연 씬에 따라 검증 시작 씬이 달라져, 같은 명령이 PC마다·날마다 다른 화면을 냅니다. 스크린샷 비교와 디버그 레이어 오류 확인의 재현성이 사라집니다. 그래서 자동 검증은 --scene 인자나 프로젝트 설정(커밋된 값)만 따르고 개인 상태는 무시하며, 끝날 때 개인 상태를 저장하지도 않습니다.
