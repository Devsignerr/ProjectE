    세계의 규칙 — 게임플레이 시스템 (후반)

    물리·캐릭터·스크립트·입력·AI(45~49강)라는 부품을 모았으니, 이제 그것들을 "한 판의 게임"으로 묶는 틀을 봅니다. 갱신 순서와 게임 모드, 스킬과 버프를 데이터로 정의하는 능력 시스템, 숫자를 코드 밖으로 꺼내는 데이터 테이블, 시드 하나로 건물을 짓는 절차적 생성, 그리고 지형·식생·파티클로 세계의 바탕을 채우는 방법입니다.

    50강

    게임 프레임워크

    관련 Phase: 25 · 31 (+ 2026-10-04 프레임 시간) · 살펴볼 곳: World/GameWorld.h, World/GameWorld.cpp, World/GameWorldGameplay.cpp, World/GameWorldTravel.h, World/GameWorldStreaming.cpp, Scene/Gameplay.h, Core/SaveGame.h, Core/FrameTime.h
    이 강의를 마치면
    • 게임 월드 한 프레임의 갱신 순서를 그리고, 각 단계가 왜 그 자리에 있는지 "누가 누구의 결과를 읽는가"로 설명할 수 있습니다.
    • Standalone / 리슨 서버 / 전용 서버 / 클라이언트에서 어떤 시스템이 도는지 구분할 수 있습니다.
    • 체력·게임 모드·데미지 이벤트·리스폰이 서버 권위로 어떻게 흘러가는지 압니다.
    • 세이브 게임, 맵 전환, 서브 씬 스트리밍을 안전하게 만드는 규칙(원자적 쓰기, 프레임 끝 전환, 백그라운드는 파싱만)을 이해합니다.

    왜 필요한가부품은 많은데, 누가 순서를 정하나

    45~49강에서 물리, 캐릭터 이동, Lua 스크립트, 입력, AI를 만들었습니다. 각각은 "한 프레임 동안 할 일"을 가진 시스템입니다. 그런데 이것들을 어떤 순서로 부르느냐에 따라 게임이 다르게 동작합니다. 스크립트가 "앞으로 가라"는 입력을 넣었는데 물리가 그보다 먼저 돌면, 캐릭터는 한 프레임 늦게 움직입니다. 카메라가 물리보다 먼저 캐릭터 위치를 읽으면 카메라가 늘 한 박자 늦게 따라가며 떨립니다.

    더 나쁜 것은 이 순서가 여러 곳에 복제되는 상황입니다. ProjectE에는 게임을 돌리는 실행 파일이 여럿 있습니다 — 런타임, 에디터의 플레이 모드, 전용 서버, 그리고 단위 테스트. 각자가 "스크립트 → 물리 → …"를 따로 적으면, 어느 날 한쪽에만 새 시스템이 추가되고 "에디터에서는 되는데 패키지에서는 안 된다" 같은 버그가 생깁니다.

    그래서 언리얼의 UWorld와 GameMode가 그렇듯, 엔진에는 게임 한 판을 굴리는 틀(게임 프레임워크)이 필요합니다. 이 강의는 그 틀의 다섯 기둥 — 갱신 순서, 게임 규칙(체력·게임 모드), 세이브, 맵 전환, 시간 — 을 차례로 봅니다.

    핵심 개념갱신 순서는 "읽기-쓰기 의존"으로 정한다

    순서를 정하는 원칙은 하나입니다. 어떤 단계가 다른 단계의 결과를 읽는다면, 쓰는 쪽이 먼저 와야 한다. 예를 들어:

    • 스크립트가 캐릭터에 이동 입력을 쓴다 → 캐릭터 이동이 그것을 읽는다 → 스크립트가 먼저.
    • 캐릭터 이동과 물리가 위치를 쓴다 → 트랜스폼 갱신(UpdateTransforms, 8강)이 로컬 값을 월드 행렬로 바꾼다 → 카메라가 월드 위치를 읽는다.
    • 애니메이션이 뼈 로컬 값을 쓴다 → 렌더러가 스킨 팔레트를 읽는다.

    이렇게 화살표를 이으면 하나의 방향 그래프가 되고, 그 그래프를 한 줄로 편 것이 갱신 순서입니다. ProjectE는 이것을 FGameWorld 하나에 적어 두고, 모든 실행 파일이 같은 함수를 부르게 했습니다.

    ProjectE에서는FGameWorld — 갱신 순서가 사는 곳

    FGameWorld는 시스템을 소유하지 않습니다. 스크립트·물리·게임 모듈·리소스 관리자는 앱이 만들고, 게임 월드는 비소유 포인터 묶음만 받습니다. 그래서 GPU가 없는 전용 서버는 Resources를 비워 두기만 하면 같은 코드로 돌아갑니다.

    // FGameWorld가 돌리는 시스템. 모두 비소유 — 앱이 소유하고 FGameWorld보다 오래 산다
struct FGameWorldSystems
{
	FScriptSystem*        Scripts    = nullptr; // 필수
	FPhysicsSystem*       Physics    = nullptr; // 없으면 물리 없음
	FGameModuleHost*      GameModule = nullptr; // 없으면 게임 모듈 없음
	FResourceManager*     Resources  = nullptr; // 없으면 에셋 핸들 해석을 건너뛴다 (GPU 없는 서버)

    몇 군데를 짚어 봅시다.

    • 스크립트가 엔티티를 만들었으면 에셋 해석: Lua가 Scene.Create로 메시를 붙이면 컴포넌트에는 "primitive:sphere" 같은 경로 문자열만 있습니다. 렌더러가 쓰는 핸들로 바꾸는 일은 GPU 리소스를 다루므로, 구조가 바뀐 프레임에만 한 번 합니다.
    • 게임 규칙과 래그돌이 물리 앞: 리스폰은 캐릭터를 PlayerStart로 순간이동시키고, 래그돌은 물리 바디를 켭니다. 둘 다 이번 물리 스텝에 반영되어야 "죽은 다음 프레임에 쓰러지기 시작"합니다.
    • 충돌 알림은 물리 뒤, 메인 스레드에서: 물리 엔진(Jolt)의 접촉 콜백은 물리 스레드에서 불립니다. 그 안에서 Lua를 부르면 경쟁 조건이 생기므로 이벤트를 쌓아 두었다가 여기서 배달합니다(45강).

    표시 틱을 따로 둔 이유

    에디터에서 씬을 편집하는 동안에는 게임 규칙이 돌면 안 됩니다(스크립트가 적을 움직이면 배치가 망가집니다). 하지만 애니메이션이 재생되고 파티클이 흩날리는 모습은 보고 싶습니다. 그래서 갱신을 둘로 나눴습니다. TickGameplay는 플레이 중이 아니면 바로 돌아가고, TickPresentation(TargetScene, dt)는 플레이 여부와 무관하게 "대상 씬"을 갱신합니다. 에디터는 편집 씬을 넘기고, 게임은 플레이 씬을 넘깁니다.

    시작과 끝의 순서

    Systems.Physics->Begin();                          // ① 바디가 먼저 있어야 스크립트가 힘을 줄 수 있다
if (Systems.GameModule != nullptr && !bClient)    // ② 게임 모듈(C++ 게임 로직)은 서버에서만
	Systems.GameModule->BeginPlay(InScene);
// 스크립트 BeginPlay는 Lua 상태만 만든다 (OnStart는 첫 TickGameplay).
// AI는 그 뒤 — 트리 시작 시 Lua 노드가 스크립트 객체를 만든다
Systems.Scripts->BeginPlay(InScene);               // ③
Abilities->Begin(InScene, !bClient);               // ④ 능력 스크립트를 그 Lua 상태에서 돌린다
if (!bClient) AI->Begin(InScene);                 // ⑤ AI도 서버에서만

    EndPlay는 이것의 역순입니다. 특히 AI와 능력 시스템을 Lua 상태보다 먼저 끝내야 합니다. 비헤이비어 트리를 멈추면 Lua 노드의 OnAbort가 불리고, 발동 중인 능력을 취소하면 능력 스크립트의 OnEnd가 불리는데, 이미 Lua 상태가 사라졌다면 크래시입니다. "만든 순서의 역순으로 부순다"는 C++ 생성자/소멸자 규칙을 시스템 단위로 지키는 것입니다.

    설계 이유: 새 시스템은 FGameWorld에 CLAUDE.md 규칙은 "새 게임 시스템은 앱마다 따로 부르지 말고 FGameWorld에 넣는다"입니다. 능력 시스템(51강)을 넣은 커밋은 런타임·에디터·서버 실행 파일의 소스를 하나도 고치지 않았습니다. FGameWorld 안에 TickAbilities와 시작/끝 호출을 넣는 것만으로 세 곳에 동시에 들어갔습니다.

    핵심 개념역할: 누가 무엇을 돌리나

    멀티플레이(8부)에서는 같은 씬을 여러 프로세스가 동시에 돌립니다. 게임 규칙의 "진실"은 하나여야 하므로, 권한(authority)을 가진 쪽만 규칙을 바꾸고 나머지는 결과를 받아 봅니다. FGameWorld는 앱이 정한 넷 모드(ENetMode)를 두 가지 역할로 줄여 씁니다.

    enum class EWorldRole : uint8
{
	Authority, // 서버/Standalone (게임 로직 전부)
	Client,    // 게임 로직은 서버가 돌리고 복제로 받는다. ClientOnly/Both 스크립트와 물리만
};
EWorldRole GetRole() const { return Mode == ENetMode::Client ? EWorldRole::Client : EWorldRole::Authority; }
    넷 모드스크립트(ExecutionLocation)게임 모듈·AI·규칙물리렌더
    Standalone (1인용)전부예예예
    리슨 서버 (호스트가 플레이)전부예예예
    전용 서버ServerOnly / Both예예아니오 (Resources 없음)
    클라이언트ClientOnly / Both아니오 — 복제로 받음예 (복제 바디는 키네마틱)예

    예를 들어 클라이언트에서 BeginPlay는 물리에 "NetId가 있는 엔티티(서버가 시뮬레이션하는 복제 엔티티)는 키네마틱으로" 라는 규칙을 꽂습니다. 클라이언트의 공은 스스로 굴러가지 않고, 서버가 보내 주는 위치를 따라가며 로컬 물체와 부딪히기만 합니다(56·58강).

    핵심 개념OnLateUpdate — "이번 프레임 최종 위치"가 필요한 일

    캐릭터를 따라가는 카메라를 스크립트로 만든다고 해 봅시다. 가장 쉬운 방법은 OnUpdate에서 캐릭터 위치를 읽어 카메라를 그 뒤에 놓는 것입니다. 그런데 그림 50-1을 보면 OnUpdate는 물리보다 먼저 돕니다. 그 시점의 캐릭터 위치는 지난 프레임 값입니다.

    그래서 Phase 21 수정에서 물리·트랜스폼 갱신 뒤에 도는 OnLateUpdate 단계를 추가했습니다. 스크립트 시스템 헤더의 주석이 용도를 분명히 적고 있습니다.

    // 물리·트랜스폼 갱신이 끝난 뒤 (FGameWorld::TickGameplay 끝): 스크립트 OnLateUpdate(dt) — 캐릭터를 따라가는 카메라처럼
// "이번 프레임 최종 위치"가 필요한 일 (OnUpdate에서 읽는 월드 위치는 물리가 움직이기 전 값이다)
void LateUpdate(float DeltaSeconds, const FInput* Input);

    ProjectE에서는체력, 게임 모드, 이벤트 배달

    Phase 25는 거의 모든 액션 게임에 필요한 최소한의 규칙 틀을 만들었습니다. 언리얼의 GameMode(규칙)와 GameState(모두가 보는 상태)를 ProjectE는 컴포넌트 하나로 합쳤습니다.

    struct FHealthComponent
{
	float        MaxHealth     = 100.0f;
	float        Health        = 100.0f; // 현재 체력 (서버 권위, 복제)
	bool         bInvulnerable = false;
	EDeathAction DeathAction   = EDeathAction::Auto;
	int32        ScoreValue    = 0; // 처치하면 가해자 소유 플레이어가 받는 점수
	FHealthRuntime Runtime;          // 비직렬화: 데미지 이벤트 큐, 리스폰 타이머
};

struct FGameModeComponent
{
	// ---- 규칙 (서버가 읽는다, 씬에 저장)
	float StartDelay = 0.0f;  float TimeLimit = 0.0f;  int32 ScoreToWin = 0;  float RespawnDelay = 3.0f;
	// ---- 상태 (PF_Transient: 저장 안 함, 복제됨)
	EMatchState MatchState       = EMatchState::WaitingToStart;
	int32       RemainingSeconds = 0;
	int32       WinnerPlayerId   = -1;
	std::string Scores;          // "플레이어=점수;..."
	FGameModeRuntime Runtime;
};

    몇 가지 설계 결정이 보입니다.

    • 사망 = Health <= 0. 따로 "죽음" 플래그를 두지 않습니다. 복제되는 값이 Health 하나뿐이므로 클라이언트도 같은 식으로 죽음을 판단할 수 있고, 두 값이 어긋날 일이 없습니다.
    • 규칙 = 저장, 상태 = 복제만. StartDelay는 레벨 디자이너가 씬에 적는 값이고, MatchState는 플레이할 때마다 처음부터 다시 시작하는 값입니다. 리플렉션 프로퍼티 플래그 PF_Transient(9강)로 "저장은 빼고 복제는 한다"를 표현합니다.
    • 점수를 문자열로: "1=3;2=5"처럼 담으면 새 복제 메시지 형식을 만들지 않고도 기존 리플렉션 복제가 그대로 실어 나릅니다. Plans.md 25-2의 "메시지 변경 없음"이 그 결과입니다.

    데미지는 즉시, 이벤트는 정해진 단계에서

    Gameplay::ApplyDamage는 값을 바로 깎고, "누가 누구에게 얼마"라는 이벤트를 컴포넌트 런타임 큐에 쌓기만 합니다. 이벤트를 받는 Lua OnDamaged/OnDeath는 게임플레이 규칙 단계에서 한꺼번에 불립니다. 왜 바로 부르지 않을까요? 데미지는 스크립트 안에서도, 능력 시스템 안에서도, 게임 모듈 안에서도 생깁니다. 그 자리에서 다른 스크립트를 부르면 "스크립트 A가 도는 도중에 스크립트 B의 OnDeath가 엔티티를 지우는" 재진입이 생깁니다. 한 단계로 모으면 호출 순서가 예측 가능해집니다.

    //   1) 데미지 이벤트: FHealthComponent 런타임 큐를 엔티티 인덱스 순으로 꺼내
//      대상 스크립트 OnDamaged(amount, instigator) → 게임 모듈 OnDamaged → 죽었으면 사망 처리.
//      이벤트 처리 중 생긴 데미지(반격 등)도 같은 틱에 몇 차례까지 이어서 처리한다
//   2) 사망 처리: 점수 → 대상 스크립트 OnDeath(instigator) → 게임 모듈 OnDeath
//      → 모든 스크립트 OnEntityDied(victim, instigator)
//      → DeathAction: Destroy = 스크립트 지연 파괴, 리스폰 = 게임 모드 RespawnDelay 뒤
//   3) 리스폰: 체력 = MaxHealth, PlayerStart를 돌아가며, 캐릭터 이동/강체 속도는 0
//      → 스크립트 OnRespawned() → 게임 모듈 OnRespawned. 폰을 다시 만들지 않으므로 NetId·소유권·프리팹이 그대로다
//   4) 매치: Gameplay::TickMatch (대기 → 진행 → 끝)

    "몇 차례까지"는 MaxDamagePasses = 4입니다. 가시 갑옷처럼 데미지를 받으면 되돌려 주는 효과가 서로 맞물리면 무한히 이어질 수 있으므로, 같은 틱에서는 네 바퀴까지만 돌고 남은 이벤트는 다음 틱으로 넘깁니다. 엔티티 인덱스 순으로 정렬하는 것도 같은 이유입니다 — 해시 맵 순회 순서에 기대면 실행마다 이벤트 순서가 달라질 수 있습니다(53강의 결정성 이야기와 같은 뿌리입니다).

    사망 처리에서 점수를 먼저 올리는 것도 의도입니다. OnDeath를 받은 HUD 스크립트가 점수판을 갱신할 때, 이미 반영된 점수를 보게 하려는 것입니다.

    설계 이유: 리스폰은 "다시 만들기"가 아니라 "되살리기" 언리얼은 보통 죽은 폰을 파괴하고 새 폰을 만듭니다. ProjectE는 체력을 채우고 PlayerStart로 옮기기만 합니다. 멀티플레이에서 폰을 새로 만들면 새 NetId를 발급하고, 소유권을 다시 연결하고, 클라이언트에 생성 메시지를 보내고, 프리팹 오버라이드를 다시 적용해야 합니다. 되살리기는 그 모든 것을 "아무것도 바뀌지 않음"으로 만듭니다.
    규칙: enum은 끝에만 추가 EDeathAction, EMatchState는 리플렉션 enum이고 씬 JSON에 번호로 저장되며 복제에도 번호로 실립니다. 가운데에 새 값을 끼우면 이미 저장된 씬의 의미가 조용히 바뀝니다. 그래서 헤더 주석에 "끝에만 추가"가 박혀 있습니다.

    ProjectE에서는세이브 게임 — 슬롯, 검증, 원자적 쓰기

    세이브 게임은 단순해 보이지만 사고가 나기 쉬운 곳입니다. 파일을 쓰는 도중 게임이 꺼지면 세이브가 반쯤 쓰인 채 남아 다음 실행에서 불러올 수 없게 되고, 슬롯 이름을 사용자 입력으로 받으면 "../../Windows/x" 같은 이름으로 엉뚱한 곳에 파일을 쓸 수 있습니다. FSaveGame은 이 두 가지를 막는 데 집중합니다.

    // 슬롯 이름 → <Saved>/SaveGames/<슬롯>.json (UTF-8 JSON 텍스트).
// 슬롯 이름: 1~64바이트, 영문/숫자/'_'/'-'/한글 등 UTF-8 문자만 (경로 구분자·'.'·공백·Windows 예약 이름 금지 — 경로 탈출 방지)
// 쓰기는 임시 파일에 쓴 뒤 바꿔치기 (도중에 꺼져도 이전 세이브가 남는다).
// 세이브는 콘텐츠가 아니므로 pak이 아니라 디스크에서 읽는다.
class FSaveGame
{
public:
	static bool                       Save(std::string_view Slot, std::string_view JsonText, std::string* OutError = nullptr);
	static std::optional<std::string> Load(std::string_view Slot); // 없거나 JSON이 깨졌으면 nullopt
	static bool                       Exists(std::string_view Slot);
	static bool                       Delete(std::string_view Slot);
	static std::vector<std::string>   List();
	static void SetDirectoryOverride(const std::filesystem::path& Directory); // 테스트/자동 검증
};
    const nlohmann::json Root = nlohmann::json::parse(JsonText, nullptr, false);
if (Root.is_discarded()) { return Fail(...); }      // JSON이 아니면 쓰지 않는다
std::filesystem::path TempPath = Path;
TempPath += L".tmp";
{
	std::ofstream File(TempPath, std::ios::binary | std::ios::trunc);
	File << Root.dump(2);                              // ① 임시 파일에 전부 쓴다
}
std::filesystem::rename(TempPath, Path, ErrorCode);  // ② 한 번에 바꿔치기

    파일 시스템의 이름 바꾸기는 "다 되거나 아예 안 되거나"에 가깝습니다. 그래서 ①에서 꺼지면 이전 세이브가 그대로이고, ② 뒤에는 새 세이브가 완전한 상태입니다. 중간 상태가 디스크에 남지 않습니다. 이것을 원자적 쓰기(atomic write)라고 부릅니다.

    Lua에서는 SaveGame.Save(slot, table)로 테이블을 그대로 넘깁니다. 그리고 자동 검증 실행(--exit-after)은 FApplication이 세이브 폴더를 프로세스 전용 임시 폴더로 돌려 놓습니다. 테스트가 개발자의 실제 세이브를 덮어쓰는 일을 막는 장치입니다.

    ProjectE에서는맵 전환 — 프레임 끝에, 한 함수로

    "포털에 들어가면 다른 맵으로" — 스크립트가 Game.OpenScene("Scenes/Demo/Forest.escene")을 부르는 순간 씬을 지워 버리면 어떻게 될까요? 지금 돌고 있는 그 스크립트, 그 스크립트를 순회하던 반복자, 물리 바디 핸들이 모두 사라진 메모리를 가리키게 됩니다. 그래서 맵 전환은 요청과 실행을 나눕니다.

    1. 요청: FGameWorld::RequestOpenScene이 파일이 있는지 확인하고 경로만 기억합니다. 서버/Standalone만 요청할 수 있고, 클라이언트는 서버가 보낸 Travel 메시지를 따라갑니다.
    2. 실행: 앱이 프레임 끝(게임플레이·복제 틱이 모두 끝난 뒤)에 FGameWorldTravel::ConsumePending으로 요청을 꺼내 Travel을 부릅니다.
    //   Travel 순서: (서버) 클라이언트에 이동 지시(BeginServerTravel)
//         → World.EndPlay(스크립트 OnDestroy, 게임 모듈 OnEndPlay, 물리/AI 정리) → OnEndPlay → 복제/플레이어 정리
//         → Scene.Clear → 씬 파일 로드 → 에셋 해석 → (서버) 정적 NetId → BeginPlay → (리슨) 호스트 폰
//         / (클라이언트) 정적 NetId → BeginPlay → TravelAck.
//   GPU 리소스: 같은 에셋은 다음 맵에서 재사용하고, 이전 맵만 쓰던 것은 몇 프레임 뒤 수거된다

    눈여겨볼 점은 Scene.Clear입니다. 씬 객체는 그대로 두고 내용만 비운 뒤 새 파일을 읽습니다. 앱과 에디터는 여기저기서 FScene*를 들고 있는데(렌더러, 패널, 플레이 모드), 객체를 새로 만들면 그 포인터를 전부 찾아 바꿔야 합니다. 내용만 교체하면 아무도 신경 쓸 필요가 없습니다. 맵 사이에 값을 넘기고 싶을 때는 Game.SetPersistent/GetPersistent(프로세스 메모리에만 유지)를 씁니다.

    이 순서를 런타임, 전용 서버, 에디터 플레이(FPlayMode::Travel), 테스트가 모두 같은 함수로 씁니다. Plans.md 31-1에 "앱마다 순서를 복제하지 않는다"가 명시된 이유입니다.

    핵심 개념서브 씬 스트리밍 — 백그라운드는 "읽고 파싱만"

    맵 전환은 화면이 한 번 끊기는 대신 단순합니다. 큰 맵을 끊김 없이 돌아다니게 하려면 필요한 부분만 그때그때 붙였다 떼는 스트리밍이 필요합니다. ProjectE의 서브 씬은 다른 .escene 파일을 현재 씬의 루트 엔티티 아래에 통째로 붙이는 방식입니다.

    문제는 씬 파일 읽기가 느리다는 것입니다(엔티티 1000개짜리 파일이 Release에서 파싱 4.0ms). 이것을 메인 스레드에서 하면 그만큼 프레임이 멈칫합니다. 그렇다고 전부 다른 스레드로 보내면 ECS(7강)와 GPU 리소스를 두 스레드가 동시에 만지게 됩니다. ProjectE의 답은 일을 성격대로 쪼개는 것입니다.

    몇 가지 규칙이 더 붙습니다.

    • 루트 하나 아래: 서브 씬 엔티티는 모두 "SubScene: <경로>" 루트 엔티티의 자손이고, 루트에 FTransientComponent를 붙여 메인 씬을 저장할 때 섞이지 않게 합니다. 내릴 때는 루트째 지연 파괴합니다.
    • 스트리밍 볼륨: 기준(주 카메라, 캐릭터, FStreamingSourceComponent) 중 하나라도 상자 안이면 불러오고, 모두 상자 + UnloadMargin 밖이면 내립니다. 경계에서 들락날락할 때 불러오기·내리기가 반복되지 않도록 여유를 둔 것입니다(히스테리시스).
    • 멀티플레이: 클라이언트는 판단하지 않고 서버의 SubSceneLoad 메시지를 받으면 그 자리에서 동기로 붙입니다. 뒤따르는 복제 메시지가 그 엔티티를 가리키기 때문입니다. 서브 씬 안 엔티티의 NetId는 1<<26 + (번호-1)*16384 + 하위 트리 순서로 양쪽이 같은 값을 계산합니다(Plans.md 31-2).

    ProjectE에서는FFrameTime — 화면을 움직이는 시계는 하나

    마지막 기둥은 시간입니다. 물결, 구름의 흐름, 자동 노출 적응, 머티리얼 그래프의 Time 노드처럼 시간에 따라 바뀌는 화면 효과는 어떤 시계를 읽어야 할까요? 처음에는 각자 std::chrono::steady_clock으로 "지난번 이후 경과 시간"을 쟀습니다. 실제로 흐른 시간이니 맞아 보입니다.

    // 앱 프레임 시간 (엔진 DLL 전역 하나).
//   화면·시뮬레이션 상태는 실제 시각(steady_clock)이 아니라 이 시간으로 진행한다
//   — `--fixed-delta`면 실행마다(부하와 무관하게) 같은 화면이 된다.
//   FApplication이 프레임(헤드리스는 틱)마다 FTimer 델타로 Advance한다. 앱 루프 밖(테스트·도구)은 0에서 멈춰 있다.
//   측정(프레임 간격, CPU/GPU 구간, 로딩 시간, 업로드 속도)은 계속 실제 시각을 쓴다
class FFrameTime
{
public:
	static void   Advance(float DeltaSeconds); // FApplication 전용
	static float  GetDeltaSeconds();
	static double GetTotalSeconds();        // 디버거 정지 등으로 버린 시간은 들어가지 않는다
	static uint64 GetFrameCount();
};

    원칙은 이렇습니다. 화면과 시뮬레이션은 "게임 시간"으로, 측정은 "실제 시간"으로. 게임 시간은 앱이 프레임마다 한 번 진행시키는 하나의 시계이고, --fixed-delta를 주면 한 프레임이 정확히 1/60초가 됩니다. 실제 시간은 PC가 바쁘면 늘어나므로, 같은 프레임 번호에서도 실행마다 다른 값이 됩니다.

    함정과 교훈시계와 순서에서 생긴 버그

    실제로 겪은 일: 화면 비교가 실행마다 달랐다 (2026-10-04) Demo/Hub를 --fixed-delta로 두 개 동시에 실행해 스크린샷 MD5를 비교하면 서로 달랐습니다. 프레임 시간은 고정했는데 자동 노출·물·구름·머티리얼 Time이 각자 steady_clock을 읽고 있었기 때문입니다. 두 프로세스가 CPU를 나눠 쓰면 실제 경과 시간이 달라지고, 그만큼 물결이 다른 위치에 그려집니다. 이 시간들을 모두 FFrameTime으로 바꾼 뒤 6회 실행이 모두 일치했습니다(커밋 dd5a624). 자동 검증의 신뢰도는 "같은 입력 → 같은 화면"에 달려 있습니다.
    실제로 겪은 일: 내 캐릭터만 떨린다 (Phase 21) 에디터 리슨 서버에서 자기 캐릭터가 떨렸습니다. 카메라 배치가 물리 전 위치를 쓰고 있었던 것입니다. 이 수정에서 OnLateUpdate 단계를 추가했고, 단위 테스트 GameWorld_LateUpdateSeesPhysicsResult로 "LateUpdate는 이번 물리 결과를 본다"를 고정했습니다. 같은 커밋에서 에디터 게임 월드에 네트워크 드라이버를 연결하지 않아(SetNetDriver) 원격 입력과 RPC가 버려지던 문제도 함께 고쳤습니다 — 순서를 한곳에 모았어도 "그 한곳에 무엇을 꽂았나"는 앱마다 확인해야 합니다.
    • 맵마다 쌓이는 메모리: Phase 31 당시 후속 과제로 "리소스 캐시 해제 없음(맵마다 에셋이 다르면 메모리 누적)"이 남았습니다. 이것이 Phase 37 리소스 수거로 이어졌고(30강), 지금 Travel 끝의 RequestGarbageCollection("맵 전환")이 그 연결점입니다.
    • 백그라운드 작업의 경계: "파싱 중에 내리면 대기"가 후속 과제로 남아 있습니다. 백그라운드 결과를 버리려 해도 작업 자체는 끝날 때까지 기다려야 하는 것이 std::future의 성질입니다. 스레드로 일을 넘길 때는 "취소"를 어떻게 할지도 함께 설계해야 합니다.
    정리
    • 갱신 순서는 "쓰는 쪽이 읽는 쪽보다 먼저"로 정하고, FGameWorld 한곳에 적어 모든 실행 파일이 공유한다.
    • 게임플레이 틱(플레이 중)과 표시 틱(항상)을 나눠, 편집 중에도 애니메이션·파티클을 보여 준다. 시작은 물리 → 게임 모듈 → 스크립트 → 능력 → AI, 끝은 역순.
    • 권한(서버/Standalone)만 규칙을 바꾸고, 클라이언트는 복제를 받는다. 데미지는 즉시 반영, 이벤트는 규칙 단계에서 정해진 순서로 배달.
    • 세이브는 슬롯 이름 검증 + 임시 파일 바꿔치기, 맵 전환은 프레임 끝에 한 함수로, 서브 씬은 백그라운드에서 파싱만.
    • 시간에 따라 바뀌는 화면은 FFrameTime으로 — 그래야 자동 검증이 재현된다.

    왜 필요한가스킬마다 if 문이 늘어나는 문제

    RPG에 화염구를 넣는다고 해 봅시다. 처음에는 간단합니다. "마나가 15 이상이면 마나를 15 깎고, 투사체를 쏘고, 맞으면 20 데미지." 그런데 기획이 붙기 시작합니다.

    • 쿨다운 1초. 기절하면 시전 불가. 시전 중에는 다른 스킬 불가.
    • 맞으면 화상: 1초마다 데미지, 최대 3번 겹침, 다시 맞으면 지속 시간 갱신.
    • 방어막을 켜면 받는 피해 절반. 방어막 두 개면? 화상에도 적용되나?
    • 레벨이 오르면 화상 데미지가 커진다.

    이것을 스킬마다 코드로 짜면 스킬 수 × 상태 수만큼 조건문이 생기고, "방어막이 화상에 적용되는가" 같은 상호작용을 매번 손으로 맞춰야 합니다. 언리얼의 Gameplay Ability System(GAS)은 이 문제를 "모든 스킬과 버프를 몇 개의 일반 개념의 조합으로 표현하고, 상호작용은 그 개념들의 계산 규칙이 자동으로 처리하게" 하는 방식으로 풀었습니다. ProjectE의 능력 시스템(Phase 53 사이드)은 이 구조를 따릅니다.

    핵심 개념속성: 기본값과 현재값

    속성에는 값이 두 개 있습니다. 왜 하나로 부족할까요? 이동 속도 450인 캐릭터가 대시(0.25초 동안 ×3)를 쓴다고 합시다. 값을 하나만 두고 450 × 3 = 1350으로 덮어쓰면, 0.25초 뒤 되돌릴 때 "원래 값이 뭐였지?"를 따로 기억해야 합니다. 그 사이 다른 버프가 값을 또 바꿨다면 되돌리기가 꼬입니다.

    • 기본값(Base): 영구적인 값. 즉시 효과(마나 소모, 회복)와 주기 효과(1초마다 화상)가 바꿉니다.
    • 현재값(Current): 기본값에 지금 활성 중인 지속 효과의 수정자를 얹어 매번 다시 계산한 값. 버프가 끝나면 그 수정자가 목록에서 빠지고, 다시 계산하면 자연히 원래 값이 나옵니다.

    즉 지속 효과는 값을 "바꾸는" 것이 아니라 "계산식에 항을 하나 추가하는" 것입니다. 되돌리기가 항 제거 하나로 끝납니다. 최대값도 다른 속성에 묶을 수 있습니다 — Health의 MaxAttribute = MaxHealth면 Health는 MaxHealth의 현재값을 넘지 못합니다.

    핵심 개념수정자 계산 순서와 스택

    여러 효과가 같은 속성을 건드릴 때 결과가 효과를 건 순서에 따라 달라지면 곤란합니다. "×2 다음 +10"과 "+10 다음 ×2"는 다르니까요. 그래서 계산 순서를 고정합니다.

    // 수정자 계산 순서 (AbilityMath::Aggregate):
//   1) Override가 하나라도 있으면 가장 나중에 적용된 효과(큰 핸들)의 값으로 끝 (Add/Multiply 무시)
//   2) 아니면 (Base + ΣAdd) × ΠMultiply  — 곱하기끼리는 곱한다 (방어막 ×0.5 두 개 = ×0.25)
//   3) 최소/최대로 자른다 (최대 = min(Max, MaxAttribute의 현재값))
//   쌓인 효과(스택 n): Add × n, Multiply^n, Override는 그대로
    float AbilityMath::Aggregate(float Base, const std::vector<FAppliedModifier>& Modifiers)
{
	const FAppliedModifier* Override = nullptr;
	float                   Add      = 0.0f;
	float                   Multiply = 1.0f;
	for (const FAppliedModifier& Modifier : Modifiers)
	{
		const int32 Stacks = std::max(1, Modifier.Stacks);
		switch (Modifier.Op)
		{
		case EModifierOp::Add:      Add += Modifier.Value * static_cast<float>(Stacks); break;
		case EModifierOp::Multiply: Multiply *= std::pow(Modifier.Value, static_cast<float>(Stacks)); break;
		case EModifierOp::Override:
			if (Override == nullptr || Modifier.Order >= Override->Order) { Override = &Modifier; }
			break;
		}
	}
	return Override != nullptr ? Override->Value : (Base + Add) * Multiply;
}

    크기(Magnitude): 숫자는 어디서 오나

    수정자의 값은 상수만 있는 것이 아닙니다. 효과를 적용하는 순간 한 번 계산해 저장(캡처)합니다.

    종류계산샘플에서
    Constant고정 값DashCost: Stamina Add −30
    Curve레벨 → 값, 점 사이 구간 선형 (범위 밖은 끝 값)BurnTick: 곡선 [[1,3],[5,8]] — 레벨 1이면 3, 레벨 5면 8
    AttributeBased계수 × (원천 또는 대상의 속성 현재값) + PostAddHealTick: 0.08 × 대상 MaxHealth + 2
    SetByCaller적용할 때 이름으로 넘긴 값 (없으면 0 + 경고)FireballHit: 스크립트가 { SetByCaller = { Damage = 20 } }

    캡처하는 이유는 "효과가 걸린 순간의 세기"를 유지하기 위해서입니다. 시전자 공격력에 비례하는 화상이라면, 화상이 도는 도중 시전자가 버프를 받아도 이미 걸린 화상은 그대로여야 자연스럽습니다.

    핵심 개념효과의 수명: 즉시, 지속, 무한, 주기

    같은 효과가 또 걸리면 어떻게 할지는 쌓기(Stacking) 정책이 정합니다.

    • None: 걸 때마다 별도 인스턴스. 방어막 두 개 = 두 인스턴스 = ×0.5 두 번.
    • ByTarget: 대상에 하나만, 다시 걸리면 스택 +1(상한 StackLimit). 화상은 대상에 최대 3스택이고 RefreshDurationOnStack으로 다시 맞으면 4초가 새로 시작합니다.
    • BySource: 원천(시전자)마다 하나. 두 마법사가 각자 화상을 걸면 따로 셉니다.
    • 만료 정책: ClearAll은 시간이 다 되면 통째로 제거, RemoveOneAndRefresh는 스택을 하나 빼고 시간을 다시 채웁니다.

    효과는 태그로 서로를 조건 짓습니다. ApplicationRequiredTags(대상이 모두 가져야 적용), ApplicationBlockedTags(하나라도 가지면 안 됨), RemoveEffectsWithTags(적용할 때 맞는 효과를 지움 — 해독제), GrantedImmunityTags(활성 동안 맞는 효과를 막음 — 화염 면역).

    핵심 개념태그: 계층 이름과 개수 세기

    태그는 State.Stunned.Hard처럼 점으로 구분한 계층 이름입니다. 일치 규칙은 "부모 질의는 자식을 포함한다"입니다. State.Stunned.Hard를 가진 캐릭터는 State.Stunned 질의에도, State 질의에도 맞습니다. 반대는 아닙니다. 그래서 "어떤 기절이든 막는다"는 State.Stunned 하나로 쓸 수 있습니다.

    // 태그 수 컨테이너: 같은 태그를 여러 원천(효과, 발동 중 능력, 느슨한 태그)이 더하고 뺀다.
// 명시 수(Explicit) = 그 태그 자체로 더한 수, 암시 수 = 자신 + 모든 자식 태그의 명시 수 합 (부모 질의를 O(1)로).
class FGameplayTagCountContainer
{
public:
	bool  AddTag(std::string_view Tag, int32 Delta = 1);

	bool  HasAny(const std::vector<std::string>& Queries) const; // 빈 목록 = false

    태그를 bool이 아니라 개수로 세는 이유가 중요합니다. 기절 효과 두 개가 겹쳐 있다가 하나가 끝났을 때, bool이면 "기절 끝"이 되어 버립니다. 개수로 세면 1이 남아 여전히 기절입니다. 언리얼 GAS와 같은 설계입니다.

    태그는 문자열이라 오타에 약합니다. 그래서 프로젝트 설정 "GameplayTags"(Config/GameplayTags.json)에 쓸 태그를 등록해 두면, 정의 데이터를 읽을 때 등록되지 않은 태그마다 경고를 한 번 냅니다. 목록이 비어 있으면 검사를 끕니다.

AbilityTypes.cpp 머리 주석은 이 선택의 이유를 이렇게 적었습니다: "RowRef 배열로 효과 → 수정자 목록을 표현할 수 있고, 편집기·CSV·핫 리로드·참조 검증을 그대로 쓴다. 전용 .eeffect 형식은 만들지 않았다." 새 파일 형식을 만들면 편집기, 검증, 핫 리로드를 처음부터 다시 만들어야 합니다.

    갱신 위치와 이동 속도

    실행 상태는 FGameWorld가 소유하는 FAbilitySystem에 있고, 게임플레이 틱에서 스크립트 갱신 뒤·캐릭터 이동 전에 돕니다(그림 50-1).

    //   1) 입력 발동: AcceptInput 컴포넌트 중 이 프로세스가 조종하는 엔티티에서 능력 표 InputAction이 눌렸으면 TryActivateAbility
//   2) FAbilitySystem::Tick (효과 시간·주기 → 능력 스크립트/C++ 능력 재개 → 복제 문자열 → 이벤트 감지)
//   3) MoveSpeed 속성 → FCharacterMovementComponent::MaxWalkSpeed (있을 때, 모든 역할)
//   4) 이벤트: OnAttributeChanged / OnTagChanged / OnAbilityActivated / OnAbilityEnded / OnAbilityFailed
//   데미지(IncomingDamage)는 Gameplay::ApplyDamage로 쌓이므로 같은 틱 게임플레이 규칙 단계에서 OnDamaged/OnDeath가 불린다.

    3번이 캐릭터 이동 전이어야 하는 이유가 보입니다. 대시 효과가 MoveSpeed를 ×3 하면, 그 값이 이번 프레임 무브의 최대 속도로 들어가야 대시가 즉시 시작됩니다.

    예약 속성: 체력은 하나만 진실

    체력은 이미 50강의 FHealthComponent가 가지고 있습니다. 능력 시스템에도 Health 속성이 있으면 진실이 둘이 됩니다. ProjectE는 체력 컴포넌트를 진실로 정하고, 몇몇 속성 이름을 예약해 다리를 놓았습니다.

    • Health/MaxHealth: 매 틱 Health 기본값 ← 컴포넌트, MaxHealth 현재값 → 컴포넌트. Health를 바꾸는 즉시 효과는 Gameplay::ApplyDamage/Heal을 거칩니다.
    • IncomingDamage(메타): 즉시 Add 값 × DamageTaken 현재값만큼 데미지를 줍니다. 기본값은 항상 0으로 돌아갑니다 — "값"이 아니라 "전달 통로"이기 때문에 메타 속성이라 부릅니다.
    • IncomingHeal(메타): 회복 통로. DamageTaken: 받는 피해 배율(기본 1, 방어막 = Multiply 0.5).

    덕분에 화염구 데미지도 무적·사망·리스폰·점수 규칙(50강)을 그대로 탑니다. CLAUDE.md 규칙은 짧습니다: "데미지는 IncomingDamage 효과나 Gameplay::ApplyDamage, Health 직접 변경 금지."

    Lua 능력 스크립트

    능력 표의 Script 칸에 Lua 파일을 적으면, 발동할 때마다 새 인스턴스의 OnActivate(ctx)가 코루틴(47강)으로 실행됩니다. 함수가 반환하면 능력이 끝나고, ctx:Wait로 시간을 기다릴 수 있습니다.

    function Fireball:OnActivate(ctx)
	if not ctx:HasAuthority() then
		return -- 예측 실행은 여기까지 (투사체는 서버가 만들고 복제한다)
	end
	...
	while Travelled < P.Range do
		ctx:Wait(0)                                    -- 다음 프레임까지
		...
		local Hits = Abilities.FindInRadius(Position, P.HitRadius, Owner)
		if #Hits > 0 then
			local Target = Hits[1]
			ctx:ApplyEffectToTarget(Target, "FireballHit", { SetByCaller = { Damage = P.Damage } })
			ctx:ApplyEffectToTarget(Target, "Burn")
			return
		end
	end
end

    스크립트 어디에도 마나, 쿨다운, 화상 데미지 숫자가 없다는 점을 보세요. 스크립트는 "언제 누구에게 어떤 효과를"만 결정하고, 숫자는 표에 있습니다. ctx에는 Wait/WaitFrames/WaitUntil/WaitAnimNotify, ApplyEffectToSelf/ToTarget, CommitAbility, EndAbility, HasAuthority, IsLocallyControlled 등이 있습니다(ScriptAbilityBindings.cpp 머리 주석). 엔티티 쪽에는 entity:TryActivateAbility(이름), GetAttribute, HasTag, 서버 전용 ApplyEffect 등이 붙습니다.

    if not ctx:HasAuthority()는 왜 있나 — 예측은 59강에서 멀티플레이에서 버튼을 누른 클라이언트가 서버 응답을 기다리면 스킬이 지연되어 보입니다. 그래서 소유 클라이언트는 같은 스크립트를 로컬로 먼저 돌려 비용·쿨다운·발동 태그를 예측합니다. 하지만 다른 대상에게 주는 데미지나 투사체 생성은 서버만 해야 하므로 HasAuthority() 안에 둡니다. 예측 키, 확정과 거절 시 되돌리기는 59강에서 자세히 다룹니다.

    정리
    • 능력 → 효과 → 수정자 → 속성, 그리고 효과 → 태그 → (능력·효과의 조건). 스킬의 상호작용은 이 부품들의 계산 규칙이 처리한다.
    • 기본값은 즉시·주기 효과가 영구히, 현재값은 지속 효과 수정자를 얹어 매번 다시 계산. 순서: Override → (Base + ΣAdd) × ΠMultiply → 자르기, 스택은 Add×n·Multiply^n.

    • 정의는 데이터 테이블 4종, 체력의 진실은 FHealthComponent(IncomingDamage/IncomingHeal은 통로). 스크립트는 "언제 누구에게"만.

    생각해 볼 문제

    Q1. MoveSpeed 기본값 400에 "+50" 버프와 "×1.5" 버프가 동시에 걸려 있습니다. 현재값은? 버프 거는 순서를 바꾸면 달라지나요? (400 + 50) × 1.5 = 675입니다. 계산 순서가 "더하기 다 모으고 → 곱하기 다 모으고"로 고정되어 있으므로 버프를 건 순서와 무관하게 항상 675입니다. 순서를 적용 순서대로 두었다면 400×1.5+50 = 650이 될 수도 있어 같은 상태인데 값이 달라졌을 것입니다.
    Q2. "기절" 효과 두 개(서로 다른 적이 건 것)가 겹쳐 있다가 하나가 끝났습니다. 태그를 bool로 관리하면 무엇이 잘못되나요? 첫 효과가 State.Stunned를 켜고 두 번째도 켠 뒤(이미 켜짐), 하나가 끝나며 끄면 아직 남은 기절 효과가 있는데도 기절이 풀립니다. 개수로 세면 2 → 1이 되어 여전히 기절이고, 마지막 효과가 끝나 0이 될 때 풀립니다. FGameplayTagCountContainer가 명시 수를 세는 이유입니다.
    Q3. 화염구 데미지를 Health에 Add −20 하는 즉시 효과로 만들지 않고 IncomingDamage 메타 속성을 거치게 한 이유는? IncomingDamage는 DamageTaken 배율(방어막)을 곱한 뒤 Gameplay::ApplyDamage로 들어갑니다. 그래서 방어막, 무적, 사망 이벤트(OnDamaged/OnDeath), 점수, 리스폰 규칙이 모두 한 경로로 적용됩니다. Health를 직접 깎으면 이 규칙들을 우회하게 되고, 체력의 진실(FHealthComponent)과 속성 값이 어긋날 수 있습니다.

    왜 필요한가숫자가 코드에 박혀 있으면

    Phase 45의 RPG 데모는 처음에 수치가 Lua 스크립트 안에 있었습니다. 아이템 목록은 GameManager.lua의 테이블, 적 체력과 공격력은 적 스크립트의 Properties, 치명타·스킬·콤보 배율 같은 수치도 스크립트 안의 상수였습니다. 처음에는 편합니다. 하지만 게임이 커지면 문제가 드러납니다.

    • 찾기 어렵다: "스켈레톤 마법사 체력"을 고치려면 어느 파일 몇째 줄인지 알아야 합니다. 기획자가 코드를 열어야 합니다.
    • 비교가 어렵다: 적 네 종류의 체력·공격력·속도를 한눈에 나란히 볼 방법이 없습니다. 밸런스 작업은 "표"로 하는 일입니다.
    • 검증이 없다: 전리품 표에 오타 난 아이템 id가 있어도 그 적이 죽어 그 아이템이 떨어질 때까지 모릅니다.
    • 도구와 연결이 어렵다: 스프레드시트에서 수치를 계산해 붙여 넣고 싶어도 Lua 문법으로 옮겨야 합니다.

    • 저장은 모든 필드 값을 구조체 필드 순서로 쓴다(행 하나 = 한 줄) — git diff에서 "어느 행이 바뀌었나"가 한 줄로 보인다.
    • 어떤 입력에도 크래시하지 않는다: 파싱 실패는 false + 오류, 의미 오류는 경고 목록.

    "구조체에 없는 필드 값을 보존한다"는 규칙이 특히 중요합니다. 누군가 구조체에서 필드를 지우거나 이름을 바꾼 상태로 테이블을 열었다고 합시다. 모르는 값을 버리고 저장하면 데이터가 영영 사라집니다. 원문을 들고 있다가 그대로 다시 쓰면, 구조체를 되돌리거나 마이그레이션(아래)할 때 값을 되살릴 수 있습니다.

    핵심 개념공유 캐시: 불변 객체와 세대 번호

    같은 표를 여러 시스템이 읽습니다. 능력 시스템(51강)은 속성·효과·능력 표를, RPG 스크립트는 아이템·적 표를 읽습니다. 매번 파일을 다시 읽고 파싱하면 낭비이고, 각자 사본을 들면 핫 리로드 때 누가 옛 사본을 쥐고 있는지 추적하기 어렵습니다. FDataLibrary는 두 가지 아이디어로 이를 풉니다.

    1. 불변 공유: Load*는 std::shared_ptr<const FDataTable>를 돌려줍니다. 받은 객체는 절대 바뀌지 않으므로 여러 곳이 안심하고 같은 객체를 들 수 있습니다.
    2. 세대 번호: 파일이 바뀌면 캐시 항목을 지우고(Invalidate) 전역 세대 번호를 올립니다. 옛 객체는 그것을 든 쪽이 놓을 때까지 살아 있고, 각자 "내가 받았을 때의 세대"와 지금 세대를 비교해 달라졌으면 다시 Load합니다.

    Lua 쪽 RPG 데이터 모듈이 이 패턴을 그대로 씁니다. Lua Data.*는 부를 때마다 새 테이블을 만들어 돌려주므로(스크립트가 고쳐도 다른 곳에 영향이 없게), 큰 표를 매 프레임 받으면 비쌉니다. 그래서 세대별로 한 번만 만들어 둡니다.

    -- 세대별 캐시 (데이터 사본만 — 게임 상태 아님)
local Cache = { Generation = nil }

local function Memo(Key, Build)
	local Generation = Data.GetGeneration()
	if Cache.Generation ~= Generation then
		Cache = { Generation = Generation }   -- 핫 리로드: 통째로 버리고 다시
	end
	local Value = Cache[Key]
	if Value == nil then
		Value      = Build()
		Cache[Key] = Value == nil and false or Value
	end
	return Value or nil
end
    "돌려준 테이블은 고치지 않는다" 이 모듈이 만든 테이블은 모든 스크립트가 공유합니다. 한 스크립트가 item.Price = 0으로 고치면 다른 스크립트의 가격도 0이 됩니다. 그래서 모듈 주석에 "돌려준 테이블은 모든 스크립트가 공유하므로 고치지 않는다(게임 상태는 GameManager/인스턴스에 둔다)"고 적었습니다. 정의 데이터(아이템의 기본 가격)와 게임 상태(이 아이템을 몇 개 가졌나)를 섞지 않는 것이 데이터 주도 설계의 기본 규율입니다.

    핵심 개념스키마가 바뀔 때: 마이그레이션

    데이터는 오래 삽니다. 개발 중에 필드 이름 Dmg를 Damage로 바꾸고 싶다면? 구조체 파일만 고치면, 이 구조체를 쓰는 모든 표의 Dmg 값이 "구조체에 없는 값"이 되고 Damage는 기본값이 됩니다. 사실상 데이터 손실입니다. 데이터베이스의 스키마 마이그레이션처럼, 구조체 변경과 데이터 변환을 한 번에 해야 합니다.

    // 필드 이름 변경 (마이그레이션). 목록 순서대로 적용하므로 A→B, B→C 연쇄도 된다
struct FDataFieldRename { std::string From; std::string To; };

// 구조체 교체 + 값 마이그레이션: 이름이 같은(Renames 적용 후) 필드 값은 옮기고(타입이 바뀌면 변환, 실패하면 기본값),
// 사라진 필드 값은 버리며, 새 필드는 기본값. Unknown 원문도 새 구조체 필드와 이름이 맞으면 되살린다
void FDataTable::Rebind(std::shared_ptr<const FDataStruct> NewStruct, const std::vector<FDataFieldRename>& Renames = {});

// 구조체 저장 + 마이그레이션: ContentDirectory 아래 이 구조체를 쓰는 .etable/.edata를 (저장 전) 디스크의 옛 구조체로 읽어
// 새 구조체로 Rebind(Renames 적용)한 뒤 다시 저장한다. 마지막에 전체 Invalidate.
bool FDataLibrary::SaveStructAndMigrate(const std::string& StructPath, const FDataStruct& NewStruct,
                                        const std::vector<FDataFieldRename>& Renames, ...);

    핵심 개념CSV 왕복과 행 참조 정규화

    밸런스 작업은 스프레드시트에서 하고 싶은 경우가 많습니다. DataCsv는 표를 CSV로 내보내고 다시 가져옵니다. 규칙은 실용적인 것들입니다.

    • 첫 줄 = 머리글(첫 칸은 행 이름 열 Name), 나머지 = 필드 이름. 정확히 같은 이름이 없으면 대소문자를 무시하고 찾습니다.
    • RFC 4180 따옴표("a,b", "say ""hi""", 칸 안 줄바꿈)를 지원하고, 머리글에 쉼표 없이 탭만 있으면 TSV로 읽습니다.
    • UTF-8 BOM은 읽을 때 무시하고 내보낼 때 기본으로 붙입니다. BOM이 없으면 엑셀이 한글을 시스템 코드 페이지로 읽어 깨뜨리기 때문입니다(1강의 인코딩 이야기와 같은 종류).
    • 배열은 요소를 |로 잇고, 벡터는 x;y;z. 모르는 열은 무시, 잘못된 칸은 기본값, 중복 행 이름은 이름_2 — 경고 후 계속합니다.

    중첩 대신 행 참조

    "전리품 표 하나에 항목 여러 개"는 자연스럽게는 중첩 구조(표 행 안에 항목 배열, 항목마다 아이템·확률·개수)입니다. v1 데이터 테이블은 중첩 구조체를 지원하지 않습니다. 대신 관계형 데이터베이스의 정규화처럼 표를 둘로 나눕니다.

    { "Name":"Skeleton_Warrior.bone",
  "Values":{ "LootTable":"Skeleton_Warrior", "Item":"bone", "Chance":0.6, "MinCount":1, "MaxCount":2 } },
{ "Name":"Skeleton_Warrior.potion_hp_small",
  "Values":{ "LootTable":"Skeleton_Warrior", "Item":"potion_hp_small", "Chance":0.25, ... } },

    항목 표의 LootTable 칸이 부모 표의 행을, Item 칸이 아이템 표의 행을 가리킵니다(그림 52-1). 이 방식은 CSV로 펼치기 쉽고(중첩은 CSV에 담기 어렵습니다), 참조 검증이 그대로 적용되며, 편집기에 새 위젯이 필요 없습니다. 51강의 능력 시스템이 "효과 → 수정자 목록"을 RowRef 배열로 표현한 것도 같은 선택입니다.

    함정과 교훈바이너리 한도와 반영 시점

    실제로 겪은 일: 엔진 DLL 내보내기 한도 엔진은 하나의 DLL로 빌드되고 함수를 자동으로 내보냅니다(12강). Windows DLL의 내보내기 수 한도는 65535개인데, 46-A 머지 시점에 61282개였습니다(Plans.md). std::variant와 템플릿을 많이 쓰는 데이터 코드는 템플릿 인스턴스마다 심볼이 생겨 이 숫자를 빠르게 올립니다. 그래서 CLAUDE.md에 "엔진 DLL 내보내기 여유가 약 4천 개이므로 큰 템플릿 인스턴스를 늘리는 변경은 .def 개수를 확인한다"가 남았고, 이후 std 범위 함수를 거르는 내보내기 필터 도구가 만들어졌습니다(64193 → 약 1만). 범용 코드를 쓸 때는 바이너리 차원의 비용도 있다는 교훈입니다.
    • 적용 시점: 적·플레이어 스탯은 OnStart에 한 번 적용합니다. 그래서 에디터에서 표를 고쳐도 이미 나와 있는 적은 그대로이고 새로 생긴 적부터 반영됩니다(46-C 후속 과제). 핫 리로드가 "어디까지" 반영되는지는 읽는 쪽의 설계에 달려 있습니다.
    • 남은 한계: 중첩 구조체, Enum 값 이름 변경 마이그레이션, 숫자 Min/Max 제약, 다른 파일이 가리키는 행 이름 자동 변경은 후속 과제로 남아 있습니다. 시작 아이템을 "배열 두 개 짝"으로 표현한 것은 중첩 구조체가 없어서 생긴 우회입니다.
    • 버전 번호: 값 형식이나 JSON/CSV 표기를 바꾸면 FDataStruct/FDataTable/FDataAsset::Version을 올리고 DataTableTests를 함께 고칩니다. 데이터 형식은 코드보다 오래 사는 계약입니다.
    정리
    • 코드는 "무엇을", 데이터는 "얼마나". 타입 있는 표로 꺼내면 비교·검증·도구 연결·핫 리로드가 가능해진다.
    • .estruct(스키마, 공유) + .etable(행 목록) / .edata(값 하나). 모르는 값은 원문 보존, 저장은 행 하나 = 한 줄.
    • FDataLibrary: 경로 캐시 + shared_ptr<const> 불변 공유 + 세대 번호. 읽는 쪽은 세대가 바뀌면 다시 받는다.
    • 이름 변경은 SaveStructAndMigrate(옛 구조체로 읽고 새 구조체로 Rebind), 중첩은 RowRef로 정규화, CSV는 BOM과 따옴표 규칙.

    생각해 볼 문제

    Q1. FDataLibrary가 shared_ptr<FDataTable>(const 없이)를 돌려주고, 핫 리로드 때 그 객체의 내용을 제자리에서 바꾸게 하면 무엇이 문제일까요? 읽는 쪽이 표를 순회하는 도중(또는 행 포인터를 들고 있는 동안) 내용이 바뀌어 무효 참조가 생길 수 있고, 한 시스템이 "정의"를 실수로 고치면 다른 모든 시스템에 퍼집니다. 불변 객체 + 새 객체로 교체 + 세대 번호면, 옛 객체를 든 쪽은 안전하게 옛 데이터로 이번 일을 마치고 다음 기회에 새 객체로 갈아탑니다.
    Q2. 구조체 편집기에서 필드 이름을 바꾼 뒤 그냥 SaveStruct만 하고, 나중에 테이블을 열어 저장하면 데이터는 어떻게 될까요? 테이블을 열 때 옛 필드 이름의 값은 "구조체에 없는 값"이 되어 경고 후 원문으로 보존되고, 새 이름 필드는 기본값으로 읽힙니다. 저장하면 원문은 다시 쓰이므로 당장 사라지지는 않지만, 게임은 새 필드의 기본값을 쓰게 됩니다. 값을 새 이름으로 옮기려면 이름 변경 목록과 함께 SaveStructAndMigrate를 거쳐야 합니다(Rebind는 Unknown 원문도 새 필드 이름과 맞으면 되살립니다).
    Q3. 전리품 항목 표의 행 이름을 "Skeleton_Warrior.bone"처럼 짓는 이유는 무엇일까요? 행 이름이 의미가 없는데도요. 행 이름은 표 안에서 고유해야 하고, 편집기·CSV·경고 메시지에서 그 행을 가리키는 이름입니다. 부모 표와 아이템 id를 이어 붙이면 고유성이 자연스럽게 보장되고 사람이 읽기에도 어느 표의 어떤 항목인지 바로 보입니다. 구조체 설명도 "행 이름은 구분용(아무 이름)"이라고 적고 있습니다 — 의미는 RowRef 칸에 있습니다.

    • 건물 뼈대 → 호실 → 방 → 문 → 창 → 모듈 → 소품으로 이어지는 생성 단계와 각 단계의 제약을 압니다.
    • 모듈 키트 프리팹 규약이 왜 필요한지, 생성기와 아티스트 사이의 "계약"으로서 이해합니다.
    • 생성 결과를 씬에 굳히고 손으로 고친 부분을 보존하는 방법, 멀티플레이에서 같은 시드로 각자 생성하는 이유를 압니다.

    왜 필요한가5층 아파트를 손으로 꾸민다면

    2026-10-03 로드맵 조정에서 사용자는 "오픈월드 규모 게임은 만들 것 같지 않음, 절차적 배치는 좋음 — 아파트 각 층을 절차적으로 꾸미기"라고 정했습니다. 5층 건물에 층마다 호실이 여럿, 호실마다 방이 대여섯 개, 방마다 벽·문·창·가구가 있다면 손으로 놓을 조각은 수천 개입니다(샘플 Apartment는 인스턴스 2239개). 게다가 층마다 조금씩 달라야 지루하지 않습니다.

    절차적 생성(procedural generation)은 규칙과 난수로 콘텐츠를 만드는 것입니다. 하지만 게임 엔진에서 쓰려면 한 가지가 더 필요합니다. 같은 입력이면 언제나 같은 결과여야 합니다. 이유는 셋입니다.

    • 편집: 마음에 드는 건물이 나오면 시드(seed) 번호만 적어 두면 됩니다. 다음 날 열어도 같은 건물이어야 합니다.
    • 테스트: "시드 7에서 욕실에 문이 없다"는 버그를 재현할 수 있어야 고칠 수 있습니다.
    • 멀티플레이: 서버와 클라이언트가 수천 개 조각을 네트워크로 주고받지 않고 시드 하나만 맞추면 각자 같은 건물을 지을 수 있습니다.

    핵심 개념결정성의 세 가지 적

    컴퓨터 프로그램은 원래 결정적인 것 같지만, "같은 결과"가 깨지는 길은 생각보다 많습니다. 생성기 헤더 첫 줄이 이것을 요약합니다.

    // 실내 절차적 생성 코어 — 순수 로직 (씬/GPU/파일 비의존), 시드 결정적: 같은 설정 + 같은 소품 규칙 + 같은 옵션 → 같은 결과.
// 난수는 자체 SplitMix64(표준 분포 함수 미사용 — 구현마다 결과가 다르다), 순회 순서는 모두 인덱스 순.
    1. 표준 라이브러리 분포: C++의 std::mt19937 같은 엔진은 수열이 표준으로 정해져 있지만, std::uniform_int_distribution 같은 분포는 그 수열을 범위로 바꾸는 방법이 구현(MSVC, libstdc++, libc++)마다 다를 수 있습니다. 같은 시드라도 컴파일러가 바뀌면 다른 건물이 나올 수 있습니다. 그래서 난수 생성부터 범위 변환까지 전부 직접 씁니다.
    2. 순서 없는 컨테이너 순회: std::unordered_map을 순회하는 순서는 해시 함수와 버킷 수에 달려 있고, 원소를 넣은 순서와도 무관합니다. "방마다 난수를 하나씩 뽑는다"를 unordered 순회로 하면, 어떤 방이 몇 번째 난수를 받는지가 달라집니다. 모든 순회는 인덱스 순으로 합니다.
    3. 외부 상태: 시간, 스레드 스케줄, 파일 시스템 나열 순서 같은 것에 기대지 않습니다. 생성기는 "씬/GPU/파일 비의존" 순수 함수이고, 입력은 설정 구조체와 소품 규칙 목록뿐입니다.
    // 난수 (SplitMix64 — 플랫폼/표준 라이브러리와 무관하게 같은 수열)
uint64 Mix64(uint64 Value)
{
	Value = (Value ^ (Value >> 30)) * 0xBF58476D1CE4E5B9ull;
	Value = (Value ^ (Value >> 27)) * 0x94D049BB133111EBull;
	return Value ^ (Value >> 31);
}
struct FRng
{
	uint64 State = 0;
	explicit FRng(uint64 Seed) : State(Mix64(Seed + 0x9E3779B97F4A7C15ull)) {}
	uint64 Next()  { State += 0x9E3779B97F4A7C15ull; return Mix64(State); }
	float  Float() { return static_cast<float>(Next() >> 40) * (1.0f / 16777216.0f); } // [0, 1)
	int32  Range(int32 Min, int32 Max) { ... return Min + static_cast<int32>(Next() % (Max - Min + 1)); } // [Min, Max]
	template <typename T> void Shuffle(std::vector<T>& Values); // 피셔-예이츠, 뒤에서부터
};

    SplitMix64는 64비트 상태에 황금비 상수(0x9E37…)를 더해 가며, 그 값을 섞는 함수(Mix64)를 통과시키는 아주 짧은 난수 생성기입니다. 품질이 게임 생성에 충분하고, 정수 곱셈·시프트·XOR만 쓰므로 어느 컴파일러에서도 비트 단위로 같습니다. Float()가 상위 24비트만 쓰는 것도 의도입니다 — float 가수가 24비트라 정확히 표현되는 값만 만듭니다.

    핵심 개념생성 단계: 큰 것에서 작은 것으로

    좋은 생성기는 한 번에 모든 것을 정하지 않고, 큰 구조부터 정해 가며 앞 단계의 결과를 다음 단계의 제약으로 씁니다. 건물 생성기는 층마다 다음 일곱 단계를 거칩니다.

    1. 뼈대: 외곽 칸 → 계단실(Core, 모든 층 같은 칸) → 복도(Center = 가운데 줄, Single = 한쪽 줄, None = 없음).
    2. 호실: 복도 양쪽 띠를 계단실이 끊는 구간으로 나눈 뒤, 구간을 너비 [UnitMinWidth, UnitMaxWidth]로 무작위 분할. 복도·계단실에 닿지 않는 호실은 이웃에 합칩니다(들어갈 방법이 없는 집은 안 됩니다).
    3. 방: 방 종류 고르기(필수 + 확률) → 사각형 무작위 분할(BSP — 가장 큰 칸을 긴 축으로 자르기를 반복, 변 ≥ MinRoomSide) → 종류 배정. 배정은 모든 순열의 점수(면적 비율, 현관이 복도에 닿음, 창이 필요한 방이 외벽에 닿음, 인접 선호)를 매겨 가장 좋은 것을 고르고, 동점은 시드 순서로 정합니다.
    4. 문: 호실 입구 = 현관 ↔ 복도 문 하나, 호실 안은 입구에서 최소 신장 트리(허브 방과 잇는 간선이 싸다). OpenTo 종류끼리(거실-주방)는 경계 전체를 트고, 1층 복도 끝 외벽에 건물 출입문.
    5. 창: 외벽 경계마다 방 종류의 WindowChance.
    6. 모듈 배치: 방마다 사각형 분해 → 바닥/천장 조각을 늘려 깔고, 경계마다 벽/외벽/문/창, 두 축 벽이 만나는 꼭짓점에 모서리 기둥, 계단·난간·지붕.
    7. 소품: 방 종류별 규칙 순서대로 후보 자리(벽 줄, 안쪽 모서리, 가운데)를 시드로 섞어 놓습니다. 겹침 금지, 문 앞 비움, 그리고 놓은 뒤에도 방의 모든 문 앞이 서로 이어지는지(25cm 격자) 확인합니다 — 소파가 문을 막으면 안 되니까요.

    4단계의 "최소 신장 트리"가 흥미로운 선택입니다. 방들을 정점, 맞닿은 경계를 간선으로 보면, 모든 방을 연결하는 가장 적은 문의 조합이 신장 트리입니다. 허브(거실)와 잇는 간선을 싸게 매기면 "모든 방이 거실을 거쳐 이어지는" 현실적인 구조가 나옵니다. 그리고 단계 끝마다 AreAllRoomsReachable로 "갇힌 방이 없음"을 검사합니다. 무작위 생성기는 이상한 경우를 반드시 만들어 내므로, 불변 조건을 코드로 확인하는 것이 필수입니다.

    핵심 개념모듈 키트 규약 — 생성기와 아티스트의 계약

    생성기는 "이 경계에 벽을 놓는다"까지만 압니다. 실제 벽은 아티스트가 만든 프리팹입니다. 생성기가 벽 프리팹을 칸 경계 가운데에 놓았는데, 프리팹의 원점이 벽 모서리에 있거나 벽이 X축으로 누워 있으면 모든 벽이 어긋납니다. 그래서 프리팹이 지켜야 할 규약을 문서로 고정했습니다.

    // 모듈 키트 프리팹 규약 (프리팹 루트 = 생성기가 놓는 위치, 칸 크기·층고에 맞게 자식 오프셋/스케일로 맞춘다):
//   Floor/CorridorFloor/Roof: 칸 한 개 가운데, 윗면 Z = 0, 아래로 두께. 생성기가 방 사각형마다 하나를 (칸 수 X, 칸 수 Y, 1)로 늘린다
//   Ceiling: 칸 한 개 가운데, 층 꼭대기(Z = FloorHeight)에 놓이고 아래로 두께
//   Wall/ExteriorWall/Door/EntranceDoor/Window/Railing: 칸 경계 가운데 바닥(Z = 0), 로컬 Y로 -칸/2..+칸/2, 앞(+X)이 방 안쪽
//   Corner: 격자 꼭짓점 바닥 / Stairs: 칸 한 개 크기 계단(로컬 +X로 오름, 높이 = 층고)
//   소품: 바닥 자리 가운데, 앞 = 로컬 +X (벽 소품은 등이 벽)

    ProjectE에서는설정 파일, 씬 적용, 유지 그룹

    입력: .ebuilding과 소품 규칙 표

    건물 설정은 JSON 에셋 .ebuilding(FBuildingConfig)이고, 소품 규칙은 52강의 데이터 테이블(Data/Building/BuildingProp.estruct 구조)입니다. 샘플의 일부를 보면 생성 단계의 매개변수가 그대로 보입니다.

  "Core": {"X": 11, "Y": 8, "Width": 3, "Depth": 6},

    출력: 순수한 결과 → 씬에 굳히기

    GenerateBuilding은 층 평면(FBuildingFloorPlan: 칸 → 방, 경계 → 벽/문/창/트임)과 배치 목록(FBuildingPlacement: 프리팹 경로, 위치, Yaw, 스케일, 층·호실·방)을 돌려줄 뿐 씬을 건드리지 않습니다. 씬에 적용하는 일은 FBuildingSceneBuilder 하나가 맡고, 에디터 인스펙터의 "생성" 버튼과 Lua entity:GenerateBuilding이 같은 함수를 씁니다.

    // 생성물 표식 하나로 두 역할 (컴포넌트 수 = 엔진 DLL 내보내기 수라 합쳤다):
//   - 생성 그룹: 생성기가 층 그룹(Unit = -1)·호실 그룹(Unit ≥ 0)에 Floor/Unit을 채우고 bKeep = false로 붙인다
//   - 유지 표식: 손으로 고친/추가한 엔티티에 "컴포넌트 추가"로 붙이면 기본 bKeep = true → 다시 생성해도 하위 트리째 남는다
//     층/호실 그룹 자체에 유지를 켜면 그 층/호실은 고정된다
struct FBuildingPartComponent
{
	int32 Floor = -1; // 그룹만 (0부터)
	int32 Unit  = -1; // 호실 그룹만 (층 그룹 -1)
	bool  bKeep = true;
};

    생성 결과는 건물 엔티티 아래 "층 그룹 → 호실 그룹 → 프리팹 인스턴스(일반 엔티티)"로 굳습니다. 일반 엔티티이므로 디자이너가 의자를 옮기거나 포스터를 붙이는 등 마음대로 고칠 수 있습니다. 문제는 그 뒤에 "새 시드"를 누르면 고친 것이 모두 사라진다는 점입니다. 그래서 다시 생성의 보존 정책을 정했습니다.

    • 생성 그룹(bKeep = false)과 그 하위는 지우고 새로 만듭니다.
    • 그룹 안에서 유지 표식이 붙은 엔티티는 하위 트리째 남겨 같은 (층, 호실) 새 그룹으로 옮깁니다. 그룹은 항상 건물 기준 단위 트랜스폼이라 옮겨도 월드 위치가 그대로입니다.
    • 유지를 켠 층/호실 그룹은 그대로 두고, 그 자리의 새 배치는 만들지 않습니다(손으로 꾸민 호실 고정).
    규칙: 생성물에 스크립트를 두지 않는다 다시 생성하면 생성물은 즉시 파괴됩니다. 그 엔티티에 스크립트가 붙어 상태를 들고 있었다면 함께 사라집니다. 그리고 씬 구조만 바꾸는 FBuildingSceneBuilder는 메시 핸들 해석과 Undo 기록을 하지 않습니다 — 그것은 호출한 쪽의 책임입니다(에디터 = 해석 + MarkEdited("건물 생성"), Lua = 구조 변경 표시). 순수 생성 / 씬 적용 / 에디터 통합을 세 층으로 나눈 결과입니다.

    멀티플레이: 복제하지 않고 각자 만든다

    생성물 2천여 개를 복제 엔티티로 만들면 접속할 때마다 생성 메시지 수천 개가 오갑니다. 생성기가 결정적이므로 그럴 필요가 없습니다. CLAUDE.md의 규칙은 "생성물은 복제하지 않으므로 멀티플레이는 같은 시드로 각자 생성"입니다. 결정성이 곧 네트워크 대역폭 절약입니다.

    결정성은 테스트로 고정한다

    E_TEST(Building_SameSeedSameResult)
{
	const FBuildingResult A = Generate(Config, 42, Props);
	const FBuildingResult B = Generate(Config, 42, Props);
	E_EXPECT_TRUE(SamePlacements(A, B));
	...
	// 다른 시드면 배치가 달라진다 (여러 시드 중 하나라도 같으면 실패)
	int32 Different = 0;
	for (uint32 Seed = 43; Seed < 48; ++Seed)
		Different += SamePlacements(A, Generate(Config, Seed, Props)) ? 0 : 1;
	E_EXPECT_EQ(Different, 5);
	// 층마다 시드가 다르면 층 평면도 달라진다 (VaryFloors)
	E_EXPECT_TRUE(A.Floors[0].Seed != A.Floors[2].Seed);
}

    "같으면 같다"만 확인하면, 시드를 무시하는 버그(항상 같은 건물)도 통과합니다. 그래서 "다르면 다르다"도 함께 검사합니다. 그 밖에 모든 방 도달(시드 1~40), 벽으로 막힌 방을 검출하는지, 모듈이 격자와 맞는지, 소품이 겹치지 않는지, 계단실이 전 층 같은지, L자 외곽 등 16+1개 테스트가 있습니다.

    왜 필요한가세계의 바탕과 공기

    지금까지의 씬은 메시를 하나하나 놓아 만들었습니다. 하지만 언덕과 골짜기가 이어진 1km 크기 땅을 메시 조각으로 만들 수는 없습니다. 풀 수만 포기를 엔티티로 놓을 수도 없습니다(엔티티 하나에 컴포넌트·트랜스폼·계층이 붙습니다). 불꽃과 연기처럼 수천 개 점이 생겼다 사라지는 효과도 엔티티로 표현하면 ECS가 감당하지 못합니다.

    이 세 가지는 공통점이 있습니다. 개별 객체가 아니라 "대량의 균질한 데이터"라는 점입니다. 그래서 셋 다 엔티티 하나(컴포넌트) 안에 큰 배열을 담고, 전용 시스템이 그 배열을 한꺼번에 처리합니다. 지형은 높이 격자, 식생은 인스턴스 배열, 파티클은 입자 배열입니다.

    핵심 개념하이트맵: 높이만 저장하는 격자

    땅의 모양을 일반 메시로 저장하면 정점마다 x, y, z가 필요합니다. 하지만 땅은 위에서 보면 규칙적인 격자입니다. x, y는 격자 위치로 정해지므로 z(높이)만 저장하면 됩니다. 이것이 하이트맵(heightmap)입니다. 흑백 이미지와 같은 구조라서, 외부 도구에서 만든 PNG/RAW 높이 이미지를 그대로 가져올 수도 있습니다.

    //   - 지형은 엔티티 월드 위치만 따른다 (회전/스케일 무시). 위치 = 지형 가운데, 높이 0(16비트 32768) = 위치 Z
//   - 높이맵 정점 격자 Resolution x Resolution (셀 = Resolution - 1), X = 열(+X 앞), Y = 행(+Y 오른쪽)
//   - 높이 Z = 위치 Z + (h / 65535 - 0.5) * HeightRange, 레이어 가중치는 정점마다 RGBA8 (합 255, 레이어 0~3)
//   - 데이터는 .eterrain(JSON + base64) 하나에 담고 FTerrainLibrary가 경로별로 공유한다 (렌더러/물리/에디터 공용)
    • 16비트 정수 높이: 0~65535를 HeightRange(기본 5000cm)에 펼칩니다. 한 단계는 5000/65535 ≈ 0.08cm로 눈에 보이지 않을 만큼 촘촘하고, float의 절반 크기입니다. 가운데 값 32768이 엔티티 위치 Z라서, 엔티티를 위아래로 옮기면 지형 전체가 따라 움직입니다.
    • 레이어 가중치: 정점마다 RGBA8 네 바이트 = 풀/흙/바위/모래 같은 레이어 4개의 섞는 비율(합 255). 셰이더가 이 비율로 머티리얼 4개를 섞습니다.
    • 회전·스케일 무시: 지형을 기울이면 "높이 = 위 방향"이라는 가정이 깨지고 충돌·스크립트의 "이 위치의 땅 높이" 질의가 복잡해집니다. 그래서 위치만 따르고, 크기는 컴포넌트의 Size(cm)로 정합니다.

    셀은 삼각형 두 개 — 대각선을 하나로 정한다

    격자의 한 칸(셀)은 꼭짓점 네 개의 높이가 서로 다르면 평면이 아닙니다. GPU는 삼각형만 그리므로 셀을 대각선으로 잘라 삼각형 두 개로 만들어야 하는데, 대각선은 두 방향이 가능하고, 어느 쪽으로 자르느냐에 따라 셀 안의 땅 모양이 달라집니다.

    const float H00 = Data.GetHeight(X0, Y0);
const float H10 = Data.GetHeight(X0 + 1, Y0);
const float H01 = Data.GetHeight(X0, Y0 + 1);
const float H11 = Data.GetHeight(X0 + 1, Y0 + 1);
// 대각선 (0,0)-(1,1)로 나눈 두 삼각형
if (FX >= FY)
{
	return H00 + FX * (H10 - H00) + FY * (H11 - H10);
}
return H00 + FY * (H01 - H00) + FX * (H11 - H01);

    흔한 대안은 네 꼭짓점을 쌍선형 보간하는 것입니다. 수학적으로는 부드럽지만, GPU가 그리는 면은 삼각형 두 개라 쌍선형 높이와 다릅니다. 그러면 캐릭터 발(물리)은 삼각형 면 위에 있는데 폴리지를 심을 때 계산한 높이는 쌍선형이라 풀이 땅에 떠 있거나 파묻힙니다. 높이가 크게 다른 셀에서는 그 차이가 수십 cm가 됩니다. CLAUDE.md 규칙 "셀 대각선은 (0,0)-(1,1)이며 수학·렌더·충돌이 같은 면을 쓴다"는 이 어긋남을 원천 차단합니다.

    핵심 개념청크 LOD와 스커트

    513×513 정점 지형은 셀이 26만 개, 삼각형이 52만 개입니다. 멀리 있는 땅을 같은 밀도로 그릴 필요는 없습니다. 지형 렌더러는 지형을 청크(기본 64셀 정사각형)로 나누고, 카메라에서 먼 청크일수록 정점을 건너뛰어 그립니다.

    // 청크 = ChunkCells 셀 정사각형(기본 64), LOD k = 정점 간격 2^k (카메라 거리 / 청크 크기)
uint32 FTerrainRenderer::SelectChunkLod(float Distance, float ChunkWorldSize, float DistanceScale, uint32 MaxLod)
{
	const float Ratio = Distance / std::max(ChunkWorldSize * std::max(DistanceScale, 0.01f), 1.0f);
	if (Ratio < 1.0f)
	{
		return 0;
	}
	const uint32 Lod = static_cast<uint32>(std::floor(std::log2(Ratio))) + 1;
	return std::min(Lod, MaxLod);
}

    거리가 청크 크기의 1배 미만이면 LOD 0, 1~2배면 1, 2~4배면 2 … 처럼 거리가 두 배가 될 때마다 정점 간격도 두 배가 됩니다. 원근 투영에서 물체의 화면 크기는 거리에 반비례하므로, 이렇게 하면 화면에서 본 삼각형 크기가 대략 일정하게 유지됩니다.

    지형 렌더러에는 정점 버퍼가 없습니다. 정점 셰이더가 정점 번호(SV_VertexID)로 "청크 안 몇 번째 격자점인지"를 계산하고, R16 높이 텍스처에서 높이를 읽습니다. 그래서 LOD마다 필요한 것은 인덱스 버퍼 하나(패치 크기별)와 "어느 청크를 이 LOD로 그릴지" 목록뿐이고, 같은 LOD 청크는 인스턴싱 한 번에 그립니다. Demo_Terrain(513², 폴리지 3.6만) 측정은 Release CPU 0.41ms / GPU 0.35ms, 드로우 14(그림자 36)였습니다(Plans.md 34-3).

    높이장 충돌: 축을 돌리고 표본을 전치한다

    물리 엔진 Jolt에는 높이장(height field) 모양이 있습니다. 문제는 좌표계입니다. Jolt 높이장은 Y가 높이이고 X–Z 평면에 격자가 깔리지만, ProjectE는 Z-up입니다(4강). 그래서 바디에 축 순환 회전을 주고, 표본 배열을 전치해 넣습니다.

    // 엔진 축 순환 회전: Jolt X → 엔진 Y, Jolt Y(높이) → 엔진 Z, Jolt Z → 엔진 X (축 (1,1,1) 120°)
const JPH::Quat TerrainRotation(0.5f, 0.5f, 0.5f, 0.5f);

// Jolt 표본 (x, y)는 y * N + x. 엔진 격자 (GridX = y, GridY = x) = Heights[x * N + y] (전치)
for (uint32 JoltY = 0; JoltY < Resolution; ++JoltY)
	for (uint32 JoltX = 0; JoltX < Resolution; ++JoltX)
		OutSamples[JoltY * Resolution + JoltX] = Data.Heights[JoltX * Resolution + JoltY] * HeightScaleMeters;

    축을 (1,1,1) 둘레로 120° 돌리면 X→Y→Z→X로 축이 순환합니다. 반사(거울상)가 아닌 회전이라 왼손/오른손 문제가 생기지 않고, 대각선 분할도 그대로 유지됩니다. 단위는 경계에서 cm → m(FUnits::UnitsToMeters)로 바꿉니다. 데이터의 ChangeCounter가 바뀌면(편집) 바디를 다시 만듭니다.

    Undo(35강)는 지형에서 특별합니다. 씬 JSON 스냅샷 방식으로는 수십만 개 높이를 매번 통째로 저장할 수 없기 때문입니다. 그래서 바뀐 영역의 전/후만 기록하는 사슬(상한 256MB)을 두고, 컴포넌트의 EditRevision(씬에 저장)과 데이터의 Revision을 맞추는 방식으로 씬 Undo와 연결합니다. 규칙은 "스트로크 끝에만 기록 + EditRevision 갱신 + MarkEdited, 끄는 도중 MarkEdited 금지"입니다. 마우스를 끄는 동안 매 프레임 기록하면 Undo 한 번에 한 프레임 분량만 되돌아가 수백 번을 눌러야 합니다.

    식생: 엔티티가 아닌 인스턴스 배열

    폴리지(FFoliageComponent)는 .efoliage 하나에 타입 목록(메시, 밀도, 크기 범위, 경사·높이 제한, 컬링·그림자 거리, 충돌)과 타입별 인스턴스 배열(32바이트: 위치, Yaw, 크기, 지면 법선)을 담습니다. 인스턴스는 월드 좌표로 저장해 지형 위에 칠한 그대로 둡니다. 렌더러는 20m 셀로 묶어 셀 단위로 거리·프러스텀 컬링을 한 뒤, 살아남은 인스턴스를 엔진의 공용 인스턴싱 목록에 밀어 넣습니다.

    const float Fade = FoliageMath::ComputeFade(Distance, CullDistance); // 끝 15%에서 크기를 줄여 사라짐
...
FMeshInstance Instance;
Instance.World         = Fade < 1.0f ? FoliageMath::MakeWorldMatrix(Instances[Index], Type, Fade) : Entry.Worlds[Index];
Instance.Entity        = Set.Entity;   // 폴리지 컴포넌트 엔티티 (NullEntity 금지)
Instance.bCastShadow   = bShadow;      // 그림자 거리 안만
Instance.bFixedLod     = true;         // LOD를 직접 골랐다
Instance.bShadowStatic = true;         // 배치 고정 → 그림자 캐시 대상
Instance.PrevWorld     = Instance.World; // 정적: 움직임 벡터는 카메라만
...
OutInstances.AddExternal(Instance);

    AddExternal로 넣은 인스턴스는 일반 정적 메시와 똑같이 묶음(29강)·그림자·사전 패스를 탑니다. 지형 전용 그리기 경로를 따로 만들지 않고 "인스턴스 목록"이라는 공용 입구로 들어가는 것이 핵심입니다. 대신 넣는 쪽이 지켜야 할 약속(Entity를 비우지 않기, 그림자 정적 여부, 직접 고른 LOD 표시)을 CLAUDE.md에 적어 두었습니다.

    핵심 개념나이아가라식 파티클: 이미터 × 단계 × 모듈

    파티클 시스템을 처음 만들면 보통 "불꽃 이미터 클래스", "연기 이미터 클래스"처럼 효과마다 코드를 짭니다. 효과가 늘면 끝이 없습니다. 언리얼 나이아가라(Niagara)는 효과를 작은 모듈의 조합으로 봅니다. "초당 50개 생성" + "원뿔 안 속도" + "중력" + "수명에 따라 색 바꾸기"를 쌓으면 불꽃이 되고, 숫자만 바꾸면 분수가 됩니다. Phase 12는 이 구조를 따랐고, 모듈 이름과 입력도 나이아가라 기본 모듈 이름에 맞췄습니다(나중에 변환할 때 1:1로 대응되도록).

    모듈 입력을 FParticleValue 하나로 통일한 것이 표현력의 핵심입니다. 같은 "크기" 입력이 상수 20이 될 수도, 10~30 사이 무작위가 될 수도, 수명에 따라 커졌다 작아지는 곡선이 될 수도 있습니다. 모듈 코드는 입력이 어떤 모드인지 모르고 Evaluate(난수, 곡선 위치)만 부릅니다.

    핵심 개념CPU와 GPU가 같은 식으로 시뮬레이션하기

    이미터마다 계산 방식을 고를 수 있습니다. CPU는 수천 개 이하, 반투명 정렬, 리본(입자를 이은 띠)이 필요할 때. GPU는 수만 개 이상일 때 계산 셰이더(ParticleSimulate.hlsl)로 돌립니다. 같은 에셋을 CPU에서 GPU로 바꿨을 때 다르게 움직이면 아티스트가 혼란스러우므로, 두 경로는 같은 식을 써야 합니다.

    가장 까다로운 것이 난수입니다. "무작위 10~30"이 CPU와 GPU에서 다른 값을 뽑으면 같은 효과가 다르게 보입니다. 그래서 상태를 가진 난수 생성기 대신, (생성 순번, 시드, 흐름 번호)를 넣으면 항상 같은 값이 나오는 해시 함수를 양쪽에 똑같이 구현했습니다.

    // PCG 해시 (셰이더와 같은 식)
uint32 FParticleSimulation::Hash(uint32 Value)
{
	const uint32 State = Value * 747796405u + 2891336453u;
	const uint32 Word  = ((State >> ((State >> 28u) + 4u)) ^ State) * 277803737u;
	return (Word >> 22u) ^ Word;
}
float FParticleSimulation::Random01(uint32 SpawnIndex, uint32 Seed, uint32 Stream)
{
	return HashToFloat(Hash(SpawnIndex ^ Hash(Seed + Stream * 0x9E3779B9u)));
}
// 입력 평가: 모듈 순번/입력 순번으로 난수 흐름을 나눠 CPU·GPU가 같은 값을 뽑게 한다
Random4(SpawnIndex, Seed, static_cast<uint32>(ModuleIndex * 16 + InputIndex))
    uint ParticleHash(uint Value)
{
	const uint State = Value * 747796405u + 2891336453u;
	const uint Word  = ((State >> ((State >> 28u) + 4u)) ^ State) * 277803737u;
	return (Word >> 22u) ^ Word;
}
float ParticleRandom01(uint SpawnIndex, uint Seed, uint Stream)
{
	return HashToFloat(ParticleHash(SpawnIndex ^ ParticleHash(Seed + Stream * 0x9E3779B9u)));
}

    입자 갱신 식도 한 줄 한 줄 대응됩니다. 예를 들어 속도 적분은 CPU P.Velocity = (P.Velocity + Acceleration * Dt) * (DragAmount > 0 ? std::exp(-DragAmount * Dt) : 1), GPU P.Velocity = (P.Velocity + Acceleration * DeltaSeconds) * (DragAmount > 0.0f ? exp(-DragAmount * DeltaSeconds) : 1.0f)로 같습니다. GPU에는 이미터 설정을 float4 배열 "프로그램"으로 구워 올리고(BuildGpuProgram), 셰이더는 모듈 헤더(종류, 입력 수, 모듈 순번)를 읽어 가며 같은 분기를 탑니다.

    규칙: 번호와 순서는 계약이다
    • EParticleModuleType 번호는 셰이더와 공유하므로 끝에만 추가합니다.
    • 입력 순서 = 난수 흐름 번호(모듈 순번 × 16 + 입력 순번)이므로 기존 입력 사이에 새 입력을 끼워 넣지 않습니다. 끼워 넣으면 뒤 입력들의 흐름 번호가 밀려, 이미 만든 모든 효과의 무작위 값이 바뀝니다.
    • 모듈을 추가·변경하면 Particles.cpp의 정보 표와 CPU 식, ParticleSimulate.hlsl(+ ParticleCommon.hlsli)를 같은 식으로 함께 고칩니다. 입자 구조를 바꾸면 FParticle / FParticleGpuData / HLSL FParticleData를 함께 맞춥니다.

    프레임 안의 순서도 정해져 있습니다: 애니메이션 → UpdateTransforms → 파티클 에셋 경로 해석 → FParticleSystem::Update(CPU 입자 적분, GPU는 계산 요청만 쌓음) → 렌더 그래프에서 GPU 계산 패스 → HDR 패스의 불투명 메시 뒤에 파티클 그리기. 이미터 엔티티의 월드 행렬(애니메이션·부모를 따라 움직임)을 읽으므로 트랜스폼 갱신 뒤에 돌고, GPU 계산은 렌더 그래프의 계산 패스(22강)로 등록되어 비동기 계산 큐 후보가 됩니다.

    ProjectE에서는경계와 컬링 — 보이지 않는 GPU 이미터는 계산도 미룬다

    화면 밖 이미터는 그리지 않아야 합니다. CPU 이미터는 실제 입자 위치의 AABB를 알기 때문에 쉽습니다. GPU 이미터는 입자가 GPU 메모리에 있어 위치를 모릅니다(읽어 오면 CPU가 GPU를 기다려야 합니다). 그래서 모듈 설정에서 보수적으로 추정합니다.

    //   GPU 이미터: 에셋의 "고정 경계"(bFixedBounds)가 있으면 그것, 없으면 모듈 설정으로 보수적 추정
//     반경 = 생성 모양 반경 + 최대 속력 × 최대 수명 + ½ × 최대 가속 × 최대 수명² + 렌더 크기 여유
//     감속/충돌은 줄이기만 하므로 무시(보수적). 입력은 상수/무작위/곡선의 성분별 최대 절댓값.
//   새 모듈이 입자를 더 멀리 보내면(속도/힘) EstimateLocalRadius에 함께 추가한다.

    물리 공식 s = v·t + ½·a·t²를 "가장 멀리 갈 수 있는 경우"로 계산한 것입니다. 실제보다 크게 잡으면 가끔 쓸데없이 그리는 손해뿐이지만, 작게 잡으면 보여야 할 효과가 사라지는 버그가 됩니다. 그래서 보수적으로 잡고, 정확한 상자가 필요하면 아티스트가 고정 경계를 지정합니다.

    GPU 이미터는 한 걸음 더 나아가 화면 밖에 있는 동안 계산 디스패치도 미룹니다. 그런데 그냥 멈추면, 다시 화면에 들어왔을 때 숨어 있던 시간만큼의 입자가 없어 "뚝 끊긴" 모습이 됩니다. ProjectE는 계산 요청을 버리지 않고 대기열에 쌓되, 영리하게 줄입니다.

    이것은 "효과가 같다는 것을 증명할 수 있는 최적화"의 좋은 예입니다. 근사는 대기열을 합칠 때 한 군데뿐이고, 그 경우도 주석에 명시되어 있습니다. 규칙은 순수 함수 TrimDeferredSteps에 있고 ParticleBoundsTests가 검증합니다.

    함정과 교훈계획과 달라진 것, 지켜야 할 짝

    계획과 달라진 것: GPU 빈칸 목록과 간접 그리기 (Phase 12) 원래 계획은 GPU 입자 풀에 "빈칸 목록"을 두어 죽은 입자 자리를 재사용하고, 살아 있는 입자 수만큼만 간접 그리기(ExecuteIndirect)하는 것이었습니다. 실제로는 입자 풀을 최대 개수 크기의 고리 버퍼로 두고(가득 차면 가장 오래된 입자를 덮어씀), 풀 전체를 계산·그리면서 죽은 입자는 정점 셰이더에서 버리는 단순한 방식으로 갔습니다. Plans.md는 이것을 "계획과 다름"으로 명시하고 "수만 개 수준에선 충분, 수십만 개 이상이면 후속 과제"라고 적었습니다. 복잡한 구조는 필요가 증명될 때 넣는다는 판단입니다. 대가로 GPU 반투명 정렬은 없고, 에디터의 입자 수는 추정치입니다.
    • 해상도 제약: 지형 셀 수는 64 이하 2의 거듭제곱 청크로 나뉘어야 해서 해상도는 129/257/513/1025 같은 값이어야 합니다(Phase 34 후속 기록). 청크 LOD가 정점 간격을 2배씩 늘리므로 청크 셀 수가 2의 거듭제곱이어야 끝이 맞습니다.
    • 지형 사전 패스: 지형도 깊이 사전 패스(19강)에 반드시 그려야 합니다. 빠지면 그 픽셀이 하늘로 취급되어 TAA·안개·SSR·SSAO가 틀어집니다. 그래서 세 PSO가 같은 정점 셰이더 바이트코드를 씁니다(사전 패스 깊이와 메인 패스 깊이가 비트 단위로 같아야 EQUAL 테스트가 통과).
    • CPU 파티클 경계도 새 모듈과 함께: 입자를 더 멀리 보내는 모듈(새 힘 등)을 추가하고 EstimateLocalRadius를 고치지 않으면, GPU 이미터가 화면 가장자리에서 일찍 사라집니다. 식과 테스트(ParticleBoundsTests)를 함께 고치는 규칙이 있는 이유입니다.
    정리
    • 지형·식생·파티클은 "엔티티 하나 안의 큰 배열 + 전용 시스템"이다.
    • 하이트맵: 16비트 높이(32768 = 위치 Z) + 정점별 레이어 가중치. 셀 대각선 (0,0)–(1,1)을 수학·렌더·충돌이 공유.
    • 청크 LOD(거리 2배 → 정점 간격 2배) + 스커트로 틈 가리기, 정점 버퍼 없이 같은 LOD를 인스턴싱. 충돌은 Jolt 높이장(축 순환 회전 + 전치), 편집은 바뀐 영역만, Undo는 스트로크 끝에만.
    • 폴리지는 월드 좌표 인스턴스를 셀 컬링 후 AddExternal로 공용 인스턴싱에 합류.
    • 파티클: 이미터 × (이미터 갱신 / 입자 생성 / 입자 갱신) 모듈 + 렌더러, 입력은 FParticleValue. CPU/GPU는 같은 식·같은 해시 난수, 번호·입력 순서는 끝에만 추가. 화면 밖 GPU 이미터는 수명만큼의 요청만 남겨 미룬다.

    생각해 볼 문제

    Q1. 지형 렌더러는 대각선 (0,0)–(1,1)로 그리는데 물리 충돌만 (1,0)–(0,1)로 만들면 플레이어는 무엇을 경험할까요? 경사가 꺾이는 셀에서 보이는 땅과 밟는 땅이 다른 면이 됩니다. 어떤 곳에서는 캐릭터 발이 보이는 땅 위로 떠 있고, 어떤 곳에서는 땅에 파묻힙니다. 높이 차가 큰 셀일수록 어긋남이 커집니다. 레이캐스트로 총알 자국을 찍어도 화면의 땅과 다른 높이에 찍힙니다.
    Q2. 파티클 모듈 "InitializeParticle"의 입력 목록에서 두 번째 입력 앞에 새 입력을 추가하면 기존 효과에 어떤 일이 생길까요? 입력 순번이 하나씩 밀리므로 난수 흐름 번호(모듈 순번 × 16 + 입력 순번)도 밀립니다. 무작위 모드인 입력들이 이전과 다른 난수를 받게 되어, 이미 만든 모든 효과의 크기·색·회전 분포가 미묘하게 바뀝니다. 직렬화 키로 값은 제자리를 찾더라도 "같은 시드 → 같은 효과"가 깨집니다. 그래서 새 입력은 끝에만 추가합니다.
    Q3. 브러시로 지형을 칠할 때 렌더러가 GetChangesSince로 "합친 영역"을 받는 대신 매 프레임 전체 높이 텍스처를 다시 올리면 무엇이 문제일까요? 513² 16비트 높이 텍스처는 약 0.5MB, 가중치까지 합치면 1.5MB 정도를 매 프레임 복사하게 됩니다. 업로드 대역과 동적 업로드 버퍼 용량을 쓸데없이 소모하고, 큰 지형(1025²)에서는 더 커집니다. 브러시는 보통 수 m 반경만 바꾸므로 바뀐 사각형만 CopyTextureRegion으로 올리는 것이 훨씬 쌉니다. 물리 높이장도 같은 변경 번호를 보고 다시 만듭니다.
