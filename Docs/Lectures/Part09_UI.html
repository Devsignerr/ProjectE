    플레이어가 보고 듣는 것을 다룹니다. 디자이너가 꾸미는 게임 UI 위젯 트리와 확대해도 깨지지 않는 SDF 글꼴, 언어를 바꿔도 다시 짤 필요 없는 문자열 표와 한글 IME 입력, 그리고 소리를 디지털로 다루는 기초부터 3D 공간화까지 차례로 봅니다.

    게임 UI 프레임워크

    관련 Phase: 16 (인게임 UI) · 살펴볼 곳: Engine/Source/UI/ (Widget.h, UILayout.cpp, UIInput.cpp, UIPainter.cpp, UIFont.cpp, UISdf.cpp, UIAnimation.h, UISystem.h), Engine/Source/Renderer/UIRenderer, Engine/Shaders/UI.hlsl
    이 강의를 마치면
    • 즉시 모드 UI(ImGui)와 보존 모드 UI(UMG식 위젯 트리)의 차이와, 게임 UI가 보존 모드를 택하는 이유를 설명할 수 있습니다.
    • "원하는 크기 → 배치" 2단계 레이아웃과 캔버스 앵커가 해상도 변화에 어떻게 대응하는지 손으로 계산할 수 있습니다.
    • 포인터가 UI와 게임 중 어디로 가는지 정하는 맞히기(hit test) 규칙을 압니다.
    • 부호 거리장(SDF) 글꼴의 원리와, ProjectE가 stb_truetype의 SDF 함수 대신 거리 변환을 직접 쓴 이유를 압니다.
    • 레이아웃에 영향을 주지 않는 렌더 변환으로 UI 애니메이션을 만드는 방법을 이해합니다.

    왜 필요한가에디터 UI와 게임 UI는 요구가 다르다

    ProjectE의 에디터는 Dear ImGui로 만들었습니다(34강). ImGui는 즉시 모드(immediate mode) UI입니다. 매 프레임 코드가 "여기 버튼, 그 아래 슬라이더"를 다시 호출하고, 호출 자체가 곧 UI입니다. 위젯 객체가 따로 남아 있지 않으니 상태를 동기화할 필요가 없어 도구를 빠르게 만들기에 아주 좋습니다.

    그런데 게임 UI는 사정이 다릅니다.

    • 코드가 아니라 디자이너가 만든다: 체력바 위치, 버튼 모양, 글꼴 크기를 프로그래머에게 부탁하지 않고 편집기에서 끌어다 놓고 싶습니다. 그러려면 UI가 데이터(파일)여야 합니다.
    • 해상도가 제각각: 1280×720 창과 2560×1440 전체 화면에서 같은 배치가 비율에 맞게 보여야 합니다.
    • 움직인다: 메뉴가 미끄러져 들어오고 점수가 통통 튀는 애니메이션이 필요합니다. 애니메이션은 "어떤 위젯의 어떤 값"을 시간에 따라 바꾸는 것이므로, 위젯이 이름을 가진 객체로 계속 존재해야 합니다.
    • 게임과 입력을 나눠 써야 한다: 버튼을 클릭했는데 캐릭터가 총을 쏘면 안 됩니다.

    그래서 Phase 16은 "UMG처럼"이라는 요청으로 시작했고, 첫 결정은 이렇습니다: 외부 라이브러리 없이 엔진이 직접 구현하고, ImGui는 에디터 전용으로 남긴다. 게임 UI는 보존 모드(retained mode) — 위젯 객체의 트리가 메모리에 남아 있고, 엔진이 그것을 배치하고 그리는 방식 — 로 만듭니다.

    비유 즉시 모드는 칠판에 매번 새로 그리는 것이고, 보존 모드는 자석 카드를 칠판에 붙여 두는 것입니다. 카드는 계속 그 자리에 있으므로 "3번 카드를 오른쪽으로 10cm"처럼 나중에 옮기거나 애니메이션할 수 있습니다.

    핵심 개념위젯 트리, 데이터, 슬롯

    보존 모드 UI의 뼈대는 위젯 트리입니다. 캔버스·박스 같은 패널이 자식을 담고, 텍스트·이미지·진행 막대 같은 잎이 실제 그림을 냅니다. 여기서 중요한 설계 질문이 하나 있습니다. "자식의 위치 정보는 누구의 것인가?"

    캔버스 안에서는 "왼쪽 위에서 (20, 30) 떨어진 곳"이 의미 있지만, 세로 박스 안에서는 위치가 자동으로 정해지고 대신 "남는 공간을 채울지"가 의미 있습니다. 즉 위치 정보의 종류는 부모가 정합니다. UMG는 이것을 슬롯(slot)이라 부르고, ProjectE의 FUISlot도 같은 생각입니다.

    // 부모 안에서의 배치 정보. 어떤 항목을 쓰는지는 부모 종류가 정한다 (UMG 슬롯).
//   캔버스: Anchor/Offsets/Alignment/bAutoSize/ZOrder
//   가로/세로 박스, 스크롤: Padding/HAlign/VAlign/SizeRule/FillWeight
struct FUISlot
{
	FVector2  AnchorMin = FVector2(0.0f, 0.0f);
	FVector2  AnchorMax = FVector2(0.0f, 0.0f);
	FUIMargin Offsets   = FUIMargin(0.0f, 0.0f, 100.0f, 40.0f);
	FVector2  Alignment = FVector2(0.0f, 0.0f);   // 피벗
	...
	EUISizeRule SizeRule   = EUISizeRule::Auto;
	float       FillWeight = 1.0f;
};

// 위젯의 저장되는 값 (복사 가능). 종류와 관계없이 모든 항목을 갖고, 종류별로 쓰는 항목만 의미가 있다.
struct FUIWidgetData { EUIWidgetType Type; std::string Name; EUIVisibility Visibility; FUISlot Slot; FUIBrush Brush; std::string Text; ... };

// 실행 중에만 쓰는 값 (저장/복제 안 함). 레이아웃/입력이 채운다.
struct FUIWidgetState { FVector2 DesiredSize; FUIRect Geometry; FUIRect Clip; FUIRect VisualGeometry; bool bHovered; ... };

struct FUIWidget : FUIWidgetData
{
	std::vector<std::unique_ptr<FUIWidget>> Children; // 자식 소유
	FUIWidget*                              Parent = nullptr; // 비소유
	FUIWidgetState                          State;
};

    세 겹으로 나눈 것이 눈여겨볼 점입니다.

    • FUIWidgetData = 저장되는 값. 종류(Type)와 상관없이 모든 종류의 항목을 한 구조체에 담습니다. 텍스트 위젯에도 Percent 필드가 있습니다. 메모리를 조금 낭비하는 대신 상속 계층이 없어 복사·JSON 저장·Undo·애니메이션이 모두 "구조체 하나"로 끝납니다. 언리얼처럼 위젯 종류마다 클래스를 두면 새 종류를 추가할 때마다 직렬화·복제·편집 코드를 각각 써야 합니다.
    • FUIWidgetState = 실행 중 값. 레이아웃 결과(Geometry)와 입력 상태(bHovered)는 파일에 저장하지 않고 복제할 때도 초기화합니다. 저장 값과 계산 값을 섞으면 "저장했더니 호버 상태까지 파일에 들어갔다" 같은 사고가 납니다.
    • 트리 소유권: 자식은 unique_ptr로 소유하고 부모는 비소유 raw 포인터로 가리킵니다. ProjectE 메모리 규칙(소유는 unique_ptr, 비소유는 raw + 수명 주석) 그대로입니다.

    위젯 종류는 캔버스, 가로/세로 박스, 오버레이, 균일 그리드, 스크롤 박스(패널), 보더·버튼(자식 1개), 이미지·텍스트·진행 막대·텍스트 상자(잎)입니다. 자식 수 제한은 FUIWidget::GetMaxChildren이 종류별로 돌려줍니다.

    핵심 개념레이아웃 2단계: 원하는 크기 → 배치

    세로 박스 안에 텍스트와 버튼이 있다고 합시다. 박스는 자식들의 크기를 알아야 자기 크기를 정할 수 있고, 자식은 박스가 준 공간을 알아야 실제 위치를 정할 수 있습니다. 닭과 달걀처럼 보이지만 두 번 순회하면 풀립니다. 언리얼 Slate와 같은 방식입니다.

    1. 원하는 크기(desired size), 아래 → 위: 잎부터 "나는 이만큼이면 좋겠다"를 계산합니다. 텍스트는 글꼴로 글자 폭을 재고, 이미지는 지정 크기를 냅니다. 세로 박스는 자식 높이의 합과 너비의 최댓값을 냅니다.
    2. 배치(arrange), 위 → 아래: 루트가 화면 전체를 받아, 자식에게 영역을 나눠 줍니다. 세로 박스는 Auto 자식에게 원하는 높이만큼 주고, Fill 자식끼리 남은 높이를 FillWeight 비율로 나눕니다.
    void FUILayout::Compute(FUIWidget& Root, const FVector2& RootSize, IUITextMeasurer& Measurer)
{
	ComputeDesired(Root, Measurer);                                                   // ① 아래 → 위
	Arrange(Root, FUIRect(FVector2::ZeroVector, RootSize), FUIRect::Infinite(), Measurer); // ② 위 → 아래
	ApplyRenderTransforms(Root, FVector2(1.0f, 1.0f), FVector2::ZeroVector, FUIRect::Infinite()); // ③ 렌더 변환
}

// ComputeDesired 안 — 세로/가로 박스
const FVector2 Size = SlotDesired(*Child);   // 자식 원하는 크기 + 슬롯 여백
if (bHorizontal) { Desired.X += Size.X; Desired.Y = FMath::Max(Desired.Y, Size.Y); }
else             { Desired.X = FMath::Max(Desired.X, Size.X); Desired.Y += Size.Y; }

    텍스트 크기를 재는 일은 IUITextMeasurer 인터페이스로 뺐습니다. 실제 게임에서는 글꼴 라이브러리(FUIFontLibrary)가 구현하고, 단위 테스트는 "글자당 10 단위" 같은 가짜 측정기를 넣습니다. 덕분에 UI 레이아웃 테스트(앵커, 박스 자동/채우기, 접힘/숨김, 줄바꿈, 스크롤 제한 등)는 글꼴 파일도 GPU도 없이 돌아갑니다.

    해상도 배율

    UI는 "설계 해상도"(예: 1920×1080) 기준 단위로 만들고, 실제 화면에 맞는 배율 하나를 곱합니다. 규칙은 넷입니다.

    const float ScaleX = ViewportSize.X / DesignSize.X;
const float ScaleY = ViewportSize.Y / DesignSize.Y;
switch (Mode)
{
case EUIScaleMode::MatchHeight: return ScaleY;                    // 높이 맞춤 (가로가 넓으면 양옆 여유)
case EUIScaleMode::MatchWidth:  return ScaleX;
case EUIScaleMode::Fit:         return FMath::Min(ScaleX, ScaleY); // 전체가 보이게
case EUIScaleMode::Fill:        return FMath::Max(ScaleX, ScaleY); // 화면을 채우게 (잘릴 수 있음)
}

    배율로 크기를 맞춘 다음, 어디에 붙어 있을지는 앵커가 정합니다.

    핵심 개념캔버스 앵커: 점 앵커와 늘이기 앵커

    앵커(anchor)는 "부모 영역의 어느 비율 지점에 붙을지"를 0~1로 적은 값입니다. (0,0)은 부모 왼쪽 위, (1,1)은 오른쪽 아래, (0.5,0.5)는 가운데입니다. AnchorMin과 AnchorMax가 축마다 같으면 점 앵커, 다르면 늘이기(stretch) 앵커입니다.

    • 점 앵커: Offsets = (앵커점에서의 위치 X, Y, 너비, 높이). Alignment(피벗)는 "내 몸의 어느 점을 그 위치에 놓을지"입니다. 피벗 (1,0)이면 오른쪽 위 모서리가 그 점에 붙습니다.
    • 늘이기 앵커: Offsets = (왼쪽 여백, 위 여백, 오른쪽 여백, 아래 여백). 부모가 넓어지면 위젯도 같이 넓어집니다.
    if (Slot.IsAnchorPointX())   // AnchorMin.X == AnchorMax.X
{
	const float Anchor = Parent.Min.X + Slot.AnchorMin.X * ParentSize.X;
	const float Width  = Slot.bAutoSize ? DesiredSize.X : Slot.Offsets.Right; // 점 앵커에서 Right = 너비
	Result.Min.X       = Anchor + Slot.Offsets.Left - Slot.Alignment.X * Width; // 피벗만큼 당김
	Result.Max.X       = Result.Min.X + Width;
}
else                         // 늘이기: Left/Right = 양쪽 여백
{
	Result.Min.X = Parent.Min.X + Slot.AnchorMin.X * ParentSize.X + Slot.Offsets.Left;
	Result.Max.X = Parent.Min.X + Slot.AnchorMax.X * ParentSize.X - Slot.Offsets.Right;
}

    Offsets 네 칸의 의미가 앵커 종류에 따라 바뀌는 것이 처음에는 헷갈리지만 UMG와 같은 규약입니다. 디자이너에서 앵커 프리셋(4×4)을 바꿀 때는 FUILayout::SetAnchorsKeepRect가 화면상 영역은 그대로 두고 오프셋을 다시 계산합니다. 위젯이 갑자기 튀지 않게 하려는 UMG와 같은 동작입니다.

    핵심 개념맞히기와 "포인터 가져가기"

    마우스를 클릭했을 때 그것이 버튼 클릭인지 게임 속 사격인지 정해야 합니다. 원리는 간단합니다. 포인터 아래에 입력을 받는 UI 위젯이 있으면 UI가 가져가고, 게임에는 마우스 버튼이 눌리지 않은 것처럼 보여 준다. 문제는 "입력을 받는 위젯"의 정의입니다. 화면 전체를 덮는 투명한 캔버스가 클릭을 다 먹어 버리면 게임을 할 수 없으니까요. ProjectE는 UMG의 Visibility 규칙을 그대로 씁니다.

    switch (Widget.Visibility)
{
case EUIVisibility::Collapsed:
case EUIVisibility::Hidden:
case EUIVisibility::HitTestInvisible: return nullptr;  // 자식까지 제외
default:                              break;
}
if (!Widget.State.VisualClip.Contains(Point)) { return nullptr; } // 스크롤 박스 밖으로 잘린 부분
std::vector<FUIWidget*> Children;

for (FUIWidget* Child : Children)
{
	if (FUIWidget* Hit = HitTestRecursive(*Child, Point)) { return Hit; }
}
if (Widget.Visibility == EUIVisibility::Visible && Widget.State.VisualGeometry.Contains(Point))

	return &Widget;                                // 자식이 아무도 안 맞으면 나
}
return nullptr;

    "위에 그려진 것부터 검사"가 그리기 순서의 정확한 역순이라는 점이 중요합니다. 그리기는 부모 → 자식, ZOrder 오름차순이고, 맞히기는 그 반대입니다. 그래야 눈에 보이는 가장 위의 위젯이 클릭됩니다.

    원시 입력을 직접 고치지 않고 FInput::WithoutMouseButtons() 같은 사본을 만들어 게임에 넘기는 것이 깔끔한 부분입니다. UI는 원본을 보고, 게임은 걸러진 사본을 보므로 두 시스템이 서로의 코드를 알 필요가 없습니다. 이 사본 패턴은 36강·48강의 입력 모드(UIOnly에서 FInput::WithoutAnyInput)로 이어집니다.

    ProjectE에서는그리기 목록, 사각형 하나 셰이더, sRGB

    레이아웃이 끝난 트리를 FUIPainter가 훑어 그리기 목록(FUIDrawList)으로 바꿉니다. 목록은 "화면 픽셀 사각형" 배열과, 같은 텍스처·같은 잘림 영역으로 이어지는 사각형 묶음(batch) 배열입니다. UI 모듈은 Core에만 의존하는 순수 로직이라 GPU를 모르고, 실제 그리기는 Renderer 모듈의 FUIRenderer가 목록을 받아 합니다.

    // 사각형 하나 (화면 픽셀). 색은 선형 + 직선 알파. UI.hlsl FUIQuad와 1:1
struct FUIDrawQuad
{
	FVector4 Rect;           // (MinX, MinY, MaxX, MaxY)
	FVector4 UV;             // SdfText는 아틀라스 텍셀 좌표
	FVector4 Color;          // 채우기 / 글자 색
	FVector4 SecondaryColor; // 테두리 / 외곽선 색
	FVector4 Params;         // Box: (모서리 반지름, 테두리 폭, 모드, 0)  SdfText: (거리 범위, 외곽선 폭, 모드, 0)
};

    핵심 개념SDF 글꼴: 거리를 저장하면 확대해도 날카롭다

    글자를 그리는 가장 단순한 방법은 글자 모양을 비트맵(검정/흰색 또는 회색 커버리지)으로 구워 텍스처에 넣는 것입니다. 하지만 48픽셀로 구운 글자를 96픽셀로 키우면 경계가 뿌옇게 번지고, 크기마다 따로 구우면 메모리가 늘어납니다. UI는 해상도 배율 때문에 같은 글자가 여러 크기로 그려지므로 문제가 큽니다.

    부호 거리장(Signed Distance Field, SDF)은 텍셀마다 "커버리지" 대신 가장 가까운 경계까지의 거리를 저장합니다. 안쪽이면 양수, 바깥이면 음수입니다. 핵심 관찰은 이것입니다: 텍스처 샘플러의 쌍선형 보간은 값을 선형으로 섞습니다. 커버리지를 섞으면 경계가 흐려지지만, 거리는 경계 근처에서 거의 선형 함수라서 섞어도 여전히 정확한 거리입니다. 그래서 확대해도 "거리 = 0"인 선, 즉 경계가 정확한 위치에 남고, 셰이더가 그 선 주변 1픽셀만 부드럽게 칠하면 어느 크기에서도 날카로운 글자가 됩니다.

    셰이더는 아틀라스 값 v(0~1)를 픽셀 거리로 되돌리고 경계 ±0.5픽셀을 부드럽게 칠합니다. 외곽선도 같은 거리를 조금 더 바깥까지 칠하는 것뿐이라 공짜에 가깝습니다.

    동적 아틀라스

    한글은 완성형만 11,172자입니다. 전부 미리 구우면 아틀라스가 거대해집니다. 그래서 FUIFont는 필요한 글자만 처음 쓸 때 구워 아틀라스에 추가합니다. 배치는 "선반(shelf) 채우기"입니다. 한 줄에 왼쪽부터 붙이다가 넘치면 지금 줄의 가장 높은 글자만큼 내려가 새 줄을 시작합니다. 아틀라스가 차면 크기를 두 배로 키우는데(1024에서 시작해 최대 4096), 기존 텍셀 좌표를 그대로 두고 오른쪽·아래로만 넓히므로 이미 구운 글자의 좌표를 고칠 필요가 없습니다. 바뀔 때마다 GetAtlasVersion()이 오르고 렌더러가 R8 텍스처를 다시 올립니다.

    ProjectE에서는렌더 변환과 UI 애니메이션, 디자이너

    버튼을 1.2배로 키우는 애니메이션을 생각해 봅시다. 버튼 크기 자체를 키우면 레이아웃이 다시 계산되어 옆 버튼들이 밀려납니다. 원하는 것은 "보이는 모습만 커지고 자리는 그대로"입니다. 이것이 UMG의 렌더 변환(Render Transform)이고, ProjectE에서는 RenderTranslation/RenderScale/RenderPivot입니다.

    렌더 변환은 레이아웃이 끝난 뒤 적용되어 State.VisualGeometry를 만듭니다. 변환은 자식에게 누적되고(부모가 1.2배면 자식도 1.2배), 그리기와 맞히기는 Visual 값을, 디자이너의 슬롯 편집(드래그로 위치 바꾸기)은 레이아웃 값 Geometry를 씁니다. 각 위젯은 "레이아웃 좌표 p → 화면 UI 좌표 p × VisualScale + VisualOffset"이라는 한 줄짜리 변환을 들고 있습니다. 텍스트 상자의 클릭 위치를 글자 위치로 바꿀 때도 이 변환의 역을 씁니다.

    // 로컬: p → (p - 피벗) × 배율 + 피벗 + 이동 (레이아웃 좌표), 부모 변환을 그 뒤에 적용
const FVector2 Pivot  = Rect.Min + Rect.GetSize() * Widget.RenderPivot;
const FVector2 LocalO = Pivot - Pivot * Widget.RenderScale + Widget.RenderTranslation;

    형식 인자: 위치와 이름

    FLocalization::Format은 {0}, {1} 같은 위치 인자와 {Name} 같은 이름 인자를 모두 받고, 중괄호 자체는 {{/}}로 씁니다. 없는 인자 자리는 지우지 않고 그대로 둡니다 — 번역 실수가 화면에 드러나도록. 이름 인자는 인자가 여럿일 때 번역가에게 의미를 알려 주고, 언어마다 순서를 바꿔도 안전합니다. Lua에서는 Loc.Get("HUD.Health", Hp)처럼 쓰고, 표를 넘기면 문자열 키는 이름 인자, 1부터의 정수 키는 {0}부터의 위치 인자가 됩니다(Lua 배열이 1부터 시작하는 것을 맞춘 변환).

    ProjectE에서는그릴 때마다 찾는다: GetDisplayText

    언어를 바꿨을 때 이미 화면에 있는 글자는 어떻게 바뀔까요? 흔한 방법은 "언어 변경 이벤트"를 받아 모든 위젯의 글자를 다시 써 넣는 것입니다. 하지만 그러면 이벤트를 놓친 위젯, 나중에 만든 위젯, 복제한 위젯을 모두 챙겨야 합니다. ProjectE는 더 단순한 길을 택했습니다. 텍스트 위젯은 TextKey를 들고 있고, 측정·그리기·미리 굽기 모두 그 순간에 키로 찾습니다.

    const std::string& GetDisplayText(const FUIWidgetData& Widget)
{
	return Widget.Type == EUIWidgetType::Text && !Widget.TextKey.empty() ? FLocalization::Get().Lookup(Widget.TextKey) : Widget.Text;
}

    해시 조회 몇 번이 매 프레임 드는 대신, 언어를 바꾸면 다음 프레임에 모든 글자가 저절로 바뀝니다. 그래서 규칙이 하나 생깁니다: 화면 글자를 읽는 코드는 Text를 직접 읽지 말고 GetDisplayText/GetDisplayHintText를 거친다. 레이아웃 측정만 Text를 읽고 그리기가 번역을 읽으면 글자 폭이 어긋나기 때문입니다.

    핵심 개념IME: 조합 중 글자와 확정 글자

    영어는 키 하나가 글자 하나입니다. 한글은 자모를 조합해 음절을 만들고, 중국어·일본어는 읽기를 친 뒤 후보 창에서 한자를 고릅니다. 이 일을 하는 운영체제 구성 요소가 IME(Input Method Editor)입니다. IME가 앱에 보내는 정보는 두 종류입니다.

    • 조합 문자열(composition string): 아직 확정되지 않은 글자. "한글"을 치는 중이면 ㅎ, 하, 한, (한 확정 후) ㄱ, 그, 글처럼 계속 바뀝니다. 커서 위치도 함께 옵니다.
    • 결과 문자열(result string): 확정된 글자. 이것만 실제 텍스트에 들어갑니다.

    Windows는 이 정보를 WM_IME_STARTCOMPOSITION → WM_IME_COMPOSITION(여러 번) → WM_IME_ENDCOMPOSITION 메시지로 보냅니다. 앱이 이 메시지를 DefWindowProc에 넘기면 시스템이 자기 조합 창(작은 회색 상자)을 띄우고 확정 글자를 WM_CHAR로 다시 보내 줍니다. 대부분의 앱은 그걸로 충분하지만, 게임 UI는 자기 글꼴로 텍스트 상자 안 캐럿 자리에 조합 글자를 그려야 하므로 메시지를 직접 처리합니다.

    if (bTextInput)  // 게임 UI 텍스트 상자가 포커스를 가진 동안만
{
	switch (Message)
	{
	case WM_IME_STARTCOMPOSITION: return 0; // DefWindowProc에 넘기지 않으면 시스템 조합 창이 뜨지 않는다
	case WM_IME_COMPOSITION:      HandleImeComposition(LParam); return 0;
	case WM_IME_ENDCOMPOSITION:   /* 조합 비우기 이벤트 */ return 0;
	}
}
...
// 확정 글자 먼저 (WM_CHAR와 같은 Char 이벤트 — DefWindowProc에 넘기지 않으므로 WM_CHAR는 오지 않는다)

    두 가지 세부가 있습니다. 하나는 순서입니다. 한 메시지에 결과와 새 조합이 함께 올 수 있으므로(그림의 ㄱ 칸) 확정을 먼저 보내고 조합을 나중에 보냅니다. 다른 하나는 인코딩입니다. Windows는 UTF-16이라 이모지나 일부 한자는 두 단위(서로게이트 쌍)이고, 엔진은 텍스트를 코드 포인트로 다루므로 커서 위치까지 변환표(UnitsToPoints)로 옮깁니다.

    ProjectE에서는텍스트 편집 모델: 순수 로직으로 떼어 내기

    텍스트 상자 동작(선택, 단어 단위 이동, 복사·붙여넣기, 최대 길이)은 생각보다 규칙이 많고, 사람이 손으로 확인하기 어렵습니다. 그래서 FUITextEdit는 글꼴도 창도 모르는 순수 구조체입니다. 텍스트는 코드 포인트 배열이고, 위치는 코드 포인트 번호(0 = 맨 앞)입니다.

    // 한 줄 텍스트 편집 (텍스트 상자의 순수 로직 — 글꼴/창과 무관). 위치는 코드 포인트 번호 (0 = 맨 앞).
//   선택 = [min(Anchor, Caret), max(Anchor, Caret)), Anchor < 0이면 선택 없음
//   한 프레임 순서: 전체 선택 → 복사/잘라내기 → 지우기(Backspace/Delete, 선택이 있으면 선택 영역) → 입력 문자 → 붙여넣기 → 이동
//   단어 이동(Ctrl+←/→): 공백/구두점 경계. 붙여넣기는 줄바꿈/탭을 공백으로 바꾸고 MaxLength에 맞춰 자른다
struct FUITextEdit
{
	std::vector<uint32> Text;
	int32               Caret  = 0;
	int32               Anchor = -1;

	bool Insert(std::u32string_view Chars, int32 MaxLength);          // 선택을 바꿔 넣는다
	bool Apply(const FUIKeyInput& Keys, int32 MaxLength, std::string* OutClipboard, bool* OutMoved = nullptr);
	static int32 FindWordLeft(const std::vector<uint32>& Text, int32 From);
	static std::u32string SanitizePaste(std::string_view Utf8);  // \r 제거, \n/\t → 공백
};

    왜 코드 포인트 단위일까요? UTF-8 바이트 단위로 캐럿을 두면 "한" 한 글자(3바이트) 중간에 캐럿이 들어가 문자열이 깨질 수 있습니다. 코드 포인트 배열이면 Backspace 한 번에 한 글자가 정확히 지워집니다(결합 문자·이모지 조합 같은 더 복잡한 경계는 다루지 않습니다).

    "한 프레임 적용 순서"를 정해 둔 것도 중요합니다. 같은 프레임에 Ctrl+A와 글자 입력이 함께 오면? 순서가 정해져 있으므로 "전체 선택 후 입력 = 전체를 입력 글자로 바꾸기"라는 결과가 항상 같습니다. 이런 규칙은 머리 주석에 적고 TextEditTests(UITests, 6개)로 고정했습니다. CLAUDE.md 규칙: FUITextEdit를 고치면 이 테스트를 함께 고친다.

    창에 의존하는 부분은 따로 떼어 냈습니다. 클립보드 같은 Win32 호출은 UI/UIPlatformWindows.cpp에만 두고, 편집 로직은 "클립보드에 쓸 글자"를 출력 인자로 돌려줄 뿐입니다. 복사한 글자를 실제 OS 클립보드에 쓰는 일은 호출자(FUIInputRouter::TakeClipboardText → 앱)가 합니다. 덕분에 테스트는 클립보드 없이 "Ctrl+X 하면 OutClipboard에 선택 글자가 나오고 Text에서 사라진다"를 확인합니다.

    조합 글자가 보이지 않던 첫 텍스트 상자 Phase 16의 텍스트 상자는 문자 입력을 WM_CHAR로만 받았습니다. 시스템이 조합 창을 따로 띄우고 확정된 글자만 보내 주므로, 게임 화면의 입력칸에는 음절이 완성될 때까지 아무것도 나타나지 않았습니다.     정리
    • 화면 글자는 키로 적고, .estrings(한 파일에 모든 언어)에서 현재 언어 → 기본 언어 → 키 순으로 찾는다. 없는 키는 경고 한 번 + 키 그대로.
    • 숫자가 섞인 문장은 문장 전체를 번역하고 {0}/{이름} 자리를 비운다. 어순이 다른 언어도 안전하다.
    • 텍스트 위젯은 그릴 때마다 키로 찾으므로 언어를 바꾸면 다음 프레임에 모두 바뀐다. 읽는 쪽은 반드시 GetDisplayText.
    • IME는 조합 문자열과 결과 문자열을 따로 보낸다. 게임 UI는 IME 메시지를 직접 받아 조합을 캐럿 자리에 그리고, 후보 창 위치는 SetTextInput으로 알린다.
    • 텍스트 편집은 코드 포인트 단위 순수 로직(FUITextEdit)으로 떼어 규칙을 테스트로 고정한다.

    생각해 볼 문제

    Q1. 번역가가 영어 문장 "Health {0} / 100"을 실수로 "Health / 100"으로 적었습니다. 화면에는 무엇이 보일까요? 반대로 "{1}"을 적었다면요? 첫 경우 인자 자리가 없으므로 숫자가 빠진 "Health / 100"이 보입니다(형식 함수는 남는 인자를 무시). 두 번째 경우 {1}에 해당하는 인자가 없으므로 지우지 않고 "{1}"이 그대로 화면에 남습니다. 번역 실수가 조용히 사라지지 않고 눈에 띄게 하려는 규칙입니다.
    Q2. 언어를 바꾸는 순간 "언어 변경 이벤트"를 받아 각 위젯의 Text를 다시 쓰는 방식과 비교해, 그릴 때마다 키로 찾는 방식의 단점은 무엇이고 왜 받아들였을까요? 매 프레임 텍스트 위젯마다 해시 조회가 몇 번 듭니다. 대신 언어 전환, 표 다시 읽기(편집기 저장), 나중에 만든 위젯, 복제한 위젯이 모두 별도 처리 없이 맞게 보입니다. UI 텍스트 위젯 수는 많아야 수백 개라 조회 비용은 작고, "놓친 위젯" 버그가 원천적으로 없어지는 이득이 큽니다.
    Q3. 텍스트 상자에 "한"까지 조합 중인 상태에서 플레이어가 다른 버튼을 클릭해 포커스가 옮겨 갔습니다. Text는 어떻게 되어야 할까요? ProjectE는 조합 중 글자를 버립니다. 텍스트 입력이 꺼지면 SetTextInput(false, ...)가 ImmNotifyIME(..., CPS_CANCEL)로 조합을 취소하고 조합 상태를 비웁니다. Text에는 확정된 글자만 있으므로 그대로입니다. (일부 앱은 포커스를 잃을 때 조합을 확정하기도 합니다 — 선택의 문제이며, ProjectE는 취소를 택했습니다.)

    왜 필요한가소리는 화면 밖 정보를 전한다

    등 뒤에서 다가오는 발소리, 벽 너머의 폭발, 멀어지는 자동차. 소리는 화면에 보이지 않는 것의 방향과 거리를 알려 줍니다. 엔진이 할 일은 세 가지입니다. 파일(WAV, MP3 …)을 읽어 숫자로 풀고(디코딩), 동시에 나는 여러 소리를 하나로 섞고(믹싱), 소리 위치와 듣는 사람(청자)의 위치·방향에 따라 좌우 크기와 음량을 바꾸는 것(공간화)입니다.

    ProjectE는 이 일을 miniaudio에 맡깁니다. 헤더 하나로 된 C 라이브러리로, 장치 출력·디코딩·리소스 캐시·3D 공간화를 모두 갖고 있습니다. 0강의 기준대로 "표준 해법이 있고 엔진 설계와 무관한 것"이므로 가져다 쓰고, 엔진과 맞닿는 경계(좌표 변환, 컴포넌트 동기화, 파일 읽기, 테스트)만 직접 설계합니다. 이 강의의 대부분은 그 경계 이야기입니다.

    핵심 개념디지털 오디오: 샘플, 샘플레이트, 프레임

    소리는 공기 압력의 떨림입니다. 마이크는 그 압력을 전압으로 바꾸고, 컴퓨터는 그 전압을 일정한 간격으로 재서 숫자로 저장합니다. 한 번 잰 값이 샘플(sample), 1초에 재는 횟수가 샘플레이트(sample rate)입니다. ProjectE의 테스트는 48,000Hz(1초에 48,000번)를 씁니다.

    • 나이퀴스트 한계: 샘플레이트의 절반보다 높은 주파수는 표현할 수 없습니다. 사람 귀의 상한이 약 20kHz이므로 44.1kHz·48kHz가 표준이 됐습니다.
    • 채널: 스테레오는 왼쪽·오른쪽 두 채널입니다. 같은 순간의 채널 값 묶음을 프레임(frame)이라 하고, 메모리에는 보통 L, R, L, R … 처럼 인터리브로 놓습니다.
    • 값의 범위: 믹싱 내부에서는 −1.0 ~ +1.0 부동소수를 쓰고, 파일은 16비트 정수(−32768 ~ 32767) 등으로 저장합니다.

    핵심 개념믹싱은 덧셈, 장치는 "가져가는" 쪽

    두 소리가 동시에 나면 공기 압력은 더해집니다. 디지털에서도 같습니다. 각 소리의 샘플에 음량(게인)을 곱한 뒤 더하면 믹스가 됩니다. 더한 값이 ±1을 넘으면 잘리며(클리핑) 찢어지는 소리가 나므로 마스터 음량으로 조절합니다.

    오디오에서 중요한 점은 시간이 기다려 주지 않는다는 것입니다. 화면은 한 프레임이 늦으면 같은 그림이 한 번 더 보일 뿐이지만, 소리 버퍼가 비면 "틱" 하는 끊김이 바로 들립니다. 그래서 오디오 장치는 보통 별도의 오디오 스레드에서 "다음 버퍼 몇 ms 분량을 채워 달라"고 콜백을 부르고, 라이브러리가 그 안에서 디코딩된 데이터를 믹싱해 넘깁니다. 게임 스레드는 "이 소리를 재생/정지, 위치는 여기"라는 상태만 바꾸고, 실제 샘플 계산은 오디오 스레드가 합니다.

    핵심 개념3D 공간화: 방향과 거리

    스테레오 스피커로 "오른쪽 앞에서 난다"를 표현하는 가장 기본적인 방법은 둘입니다.

    1. 패닝(panning): 청자 기준으로 소리가 오른쪽에 있으면 오른쪽 채널을 크게, 왼쪽을 작게 합니다. 이를 위해 소리 위치를 청자 기준 좌표(청자의 오른쪽·위·앞 축)로 바꿔야 합니다.
    2. 거리 감쇠(attenuation): 멀어지면 작아집니다. 자연에서는 음압이 거리에 반비례하므로, 게임도 "가까운 최소 거리까지는 그대로, 그 뒤로는 거리에 반비례"하는 곡선을 많이 씁니다.

    miniaudio가 제공하는 감쇠 모델 중 역수(inverse) 모델이 바로 그 곡선이고, ProjectE는 사운드를 만들 때 이 모델을 고릅니다(ma_attenuation_model_inverse). 식은 다음과 같습니다(miniaudio 소스 그대로, r = 롤오프, 기본 1).

    역수 감쇠 게인 = Min / (Min + r × (clamp(d, Min, Max) − Min))
    r = 1이면 d ∈ [Min, Max]에서 게인 = Min / d 입니다. Max를 넘으면 더 줄지 않습니다.

    단위에 주의할 점이 하나 있습니다. 감쇠 식은 거리의 비율만 보므로 단위가 무엇이든 Min/Max와 위치가 같은 단위이기만 하면 됩니다. 그래서 물리(45강)와 달리 오디오는 미터로 바꾸지 않고 엔진 단위 cm 그대로 넘깁니다. 컴포넌트 기본값 MinDistance = 100(1m), MaxDistance = 5000(50m)도 cm입니다.

    ProjectE에서는오른손 좌표계 문제와 청자 공간 변환

    ProjectE는 언리얼과 같은 왼손 Z-up(+X 앞, +Y 오른쪽, +Z 위)이고, miniaudio는 OpenGL 관례인 오른손(+X 오른쪽, +Y 위, −Z 앞)입니다. 손 방향이 다른 좌표계 사이에는 회전만으로 맞출 수 없는 반사가 끼어 있습니다. 월드 좌표를 그대로 넘기고 청자 방향만 맞춰 주면 회전 부분은 맞아도 반사 때문에 좌우가 뒤집힙니다 — 오른쪽 폭발이 왼쪽에서 들립니다.

    해결책은 문제를 우회하는 것입니다. miniaudio의 청자를 원점에서 −Z를 보는 자세로 영원히 고정하고, 소리 위치를 엔진 쪽에서 청자 기준 좌표(오른쪽, 위, 앞)로 바꿔서 miniaudio 축에 직접 꽂습니다. 그러면 miniaudio는 월드 좌표계가 무엇인지 알 필요가 없습니다.

    // 엔진 월드 위치 → miniaudio 청자 공간 (오른손: +X 오른쪽, +Y 위, -Z 앞, 청자는 원점).
// 엔진과 miniaudio의 손 방향이 달라 월드 좌표를 그대로 넘기면 좌우가 뒤집히므로,
// 청자 기준 상대 좌표로 바꿔 넘기고 miniaudio 리스너는 원점에서 -Z를 보게 고정한다.
inline FVector3 ToListenerSpace(const FAudioListener& Listener, const FVector3& WorldPosition)
{
	const FVector3 Forward = Listener.Forward.GetNormalized();
	// 왼손 좌표계: Cross(Forward, Right) == Up → Right = Cross(Up, Forward)
	const FVector3 Right = FVector3::Cross(Listener.Up, Forward).GetNormalized();
	const FVector3 Up    = FVector3::Cross(Forward, Right);

	const FVector3 Offset = WorldPosition - Listener.Position;
	return FVector3(FVector3::Dot(Offset, Right), FVector3::Dot(Offset, Up), -FVector3::Dot(Offset, Forward));
}
    // 청자는 원점에서 -Z를 본다. 사운드 위치는 AudioMath::ToListenerSpace로 청자 기준 좌표로 넘긴다
ma_engine_listener_set_position(&Impl->Engine, 0, 0.0f, 0.0f, 0.0f);
ma_engine_listener_set_direction(&Impl->Engine, 0, 0.0f, 0.0f, -1.0f);
ma_engine_listener_set_world_up(&Impl->Engine, 0, 0.0f, 1.0f, 0.0f);

    Right를 Cross(Up, Forward)로 구하는 것도 좌표계 규약(4강: Cross(Forward, Right) == Up)에서 나옵니다. 오른손 습관대로 Cross(Forward, Up)을 쓰면 여기서 또 좌우가 뒤집힙니다. 이 규칙을 테스트가 고정합니다.

	E_EXPECT_EQUALS(AudioMath::ToListenerSpace(Listener, FVector3(100, 0, 0)), FVector3(0, 0, -100), Tol);
	E_EXPECT_EQUALS(AudioMath::ToListenerSpace(Listener, FVector3(0, 100, 0)), FVector3(100, 0, 0), Tol);

    "마지막으로 본 프레임 번호"로 사라진 엔티티를 찾는 것이 깔끔합니다. 엔티티 파괴 이벤트를 구독하지 않아도, 이번 순회에서 만나지 못한 항목을 지우면 됩니다. 청자는 런타임에서는 게임 카메라(Audio.SetListener({카메라 위치, 앞, 위})), 에디터 플레이에서는 보고 있는 카메라입니다. Lua는 entity:PlaySound/StopSound, Audio.PlayOneShot을 쓰며, Scripting 모듈은 FScriptAudioHooks로만 Audio에 닿습니다(0강의 훅 패턴).

    장치가 없어도 게임은 계속된다

    오디오 장치가 없는 PC(원격 데스크톱, 서버, 헤드폰 분리 상태)도 있습니다. 소리가 안 난다고 게임이 시작되지 않으면 안 됩니다. FAudioEngine::Init이 실패하면 경고 한 줄을 남기고 IsInitialized() == false가 되며, 이후 모든 호출은 조용히 무시됩니다. 호출하는 쪽은 "오디오가 있나?"를 매번 확인할 필요가 없습니다.

    장치 없이 테스트하기: bNoDevice와 ReadFrames

    "오른쪽 소리가 오른쪽에서 들린다"를 사람 귀 없이 어떻게 확인할까요? miniaudio는 장치 없이 엔진을 만들고 믹스 결과를 직접 읽는 모드를 지원합니다. ProjectE는 이를 FAudioEngineDesc::bNoDevice + ReadFrames로 감쌌습니다. 테스트는 사인파 WAV를 직접 써서 만들고, 소리를 엔진 +Y(청자의 오른쪽)에 놓은 뒤 몇 천 프레임을 읽어 L/R 에너지를 비교합니다.

Engine.Play(Sound);
MixEnergy(Engine, 2048);                     // 공간화 스무딩 안정화
const FChannelEnergy Right = MixEnergy(Engine, 4096);
E_EXPECT_TRUE(Right.Right > Right.Left * 2.0f);

Engine.SetWorldPosition(Sound, FVector3(0.0f, -300.0f, 0.0f)); // 왼쪽
...
E_EXPECT_TRUE(Left.Left > Left.Right * 2.0f);

    "공간화 스무딩 안정화"로 처음 2048프레임을 버리는 부분이 실전 감각입니다. 공간화 라이브러리는 위치가 갑자기 바뀌어 딸깍 소리가 나지 않도록 게인을 몇 ms에 걸쳐 부드럽게 옮기므로, 바로 읽으면 이전 위치의 값이 섞입니다. 이 방식으로 Phase 7에서 AudioTests 10개(청자 공간 축, 무장치 믹스, 없는 파일, 미초기화 무시, 패닝, 감쇠, 컴포넌트 동기화 등)를 만들었습니다.

    패키지에서 사운드 읽기: VFS

    63강에서 볼 것처럼 패키지 게임의 콘텐츠는 pak 파일 하나에 묶입니다. 그런데 miniaudio는 파일 경로를 받아 스스로 디스크를 엽니다. pak 안 파일은 디스크에 없으니 열 수 없습니다. 다행히 miniaudio는 파일 열기·읽기·탐색 함수 표를 바꿔 끼울 수 있는 VFS(가상 파일 시스템) 인터페이스를 제공합니다. ProjectE는 열 때 FFileSystem::ReadFile(pak → 디스크)로 파일 전체를 메모리에 읽고, 읽기·탐색은 그 메모리 위에서 하는 VFS를 꽂았습니다.

    // miniaudio 파일 읽기를 FFileSystem(pak → 디스크)으로: 열 때 파일 전체를 메모리로 읽는다 (DECODE 로드라 어차피 전부 읽음)
ma_result VfsOpenW(ma_vfs*, const wchar_t* FilePath, ma_uint32 OpenMode, ma_vfs_file* OutFile)
{
	if ((OpenMode & MA_OPEN_MODE_WRITE) != 0) { return MA_ACCESS_DENIED; }
	auto File = std::make_unique<FMemoryFile>();
	if (!FFileSystem::ReadFile(FilePath, File->Bytes)) { return MA_DOES_NOT_EXIST; }
	*OutFile = File.release();
	return MA_SUCCESS;
}

    "파일 전체를 메모리로"가 단순한 이유는 주석에 있습니다. 사운드를 MA_SOUND_FLAG_DECODE로 만들어 어차피 전부 디코딩해 메모리에 두기 때문입니다. 긴 배경 음악을 스트리밍으로 읽는 것은 후속 과제로 남아 있습니다.

    함정과 교훈

    좌우가 뒤집히는 버그를 설계로 막다 손 방향이 다른 라이브러리를 엔진에 붙일 때 가장 흔한 버그가 "한 축만 뒤집힘"입니다. 그래픽스(glTF 임포트, 11강)와 내비메시(Recast, 49강)에서도 같은 문제가 있었고, 매번 해결책은 같았습니다. 변환을 경계 한 곳(여기서는 ToListenerSpace)에만 두고, 그 변환을 테스트로 고정한다. 오디오는 한 걸음 더 나아가 miniaudio 청자를 원점에 고정해, 회전 행렬을 라이브러리 쪽 좌표계로 옮기는 계산 자체를 없앴습니다.
    주의: Ogg Vorbis는 안 된다 ProjectE의 miniaudio 빌드에는 Vorbis 디코더가 들어 있지 않아 .ogg를 읽지 못합니다. 효과음은 WAV/FLAC/MP3로 준비합니다(CLAUDE.md RPG 데모 항목). 버스·리버브·차폐·Ogg를 포함한 오디오 믹서는 로드맵 54번으로 남아 있습니다.
    • miniaudio 헤더는 #pragma warning(push, 0)으로 감싸 포함합니다. 서드파티 헤더가 /W4 /WX에 걸려 빌드가 깨지지 않게 하는, 모든 서드파티 포함부의 규칙입니다.
    • ma_sound는 초기화 후 주소가 바뀌면 안 되므로 unique_ptr로 감싸 맵에 둡니다(FImpl::Sounds). C 라이브러리 구조체를 std::vector에 값으로 넣으면 재할당 때 옮겨져 내부 포인터가 깨집니다.
    정리
    • 디지털 오디오 = 일정 간격(샘플레이트)으로 잰 숫자. 스테레오는 L/R 샘플을 한 프레임으로 인터리브한다.
    • 믹싱은 게인을 곱해 더하는 것. 장치는 오디오 스레드에서 버퍼를 가져가고, 게임 스레드는 상태만 바꾼다.
    • 3D 사운드 = 청자 기준 방향으로 좌우 배분 + 거리 감쇠(역수 모델: Min까지 1, 이후 Min/d).
    • 엔진(왼손)과 miniaudio(오른손)의 차이는 청자를 원점에 고정하고 위치를 청자 기준 좌표로 넘겨 없앤다.
    • 장치가 없으면 무음으로 계속, 테스트는 bNoDevice + ReadFrames로 믹스를 숫자로 검증, 패키지는 VFS로 pak에서 읽는다.

    생각해 볼 문제

    Q1. Min 100, Max 5000인 소리가 청자에게서 10m(1000cm) 떨어져 있습니다. 게인은 얼마이고, 데시벨로는 몇 dB 줄어든 것일까요? 게인 = 100 / 1000 = 0.1입니다. 진폭 비율의 데시벨은 20·log10(0.1) = −20dB입니다. 거리 2배마다 20·log10(0.5) ≈ −6dB씩 줄어드는 것이 역수 모델의 성질입니다.
    Q2. ToListenerSpace에서 Right를 Cross(Forward, Up)으로 잘못 계산하면 어떤 테스트가 깨질까요? Cross(Forward, Up) = −Cross(Up, Forward)이므로 Right가 반대 방향이 됩니다. 엔진 +Y(오른쪽)의 소리가 miniaudio −X(왼쪽)로 가서 AudioMath_ListenerSpaceAxes의 두 번째 기대값 (100, 0, 0)이 (−100, 0, 0)이 되어 실패하고, AudioEngine_SpatialPanning도 왼쪽 에너지가 커져 실패합니다. Up도 Cross(Forward, Right)로 다시 구하므로 함께 뒤집혀 위·아래까지 틀어집니다.
    Q3. 소리가 매 프레임 움직이지 않는데도 SetWorldPosition을 매 프레임 부르는 이유는 무엇일까요? miniaudio에 넘기는 값은 월드 위치가 아니라 청자 기준 위치이기 때문입니다. 플레이어(카메라)가 돌거나 움직이면 가만히 있는 소리의 청자 기준 좌표가 바뀝니다. 청자를 원점에 고정한 설계의 대가가 "모든 공간 사운드의 위치를 매 프레임 다시 계산"이며, 내적 세 번이라 비용은 작습니다.
