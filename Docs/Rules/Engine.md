# 엔진 코어 (트랜스폼·엔진 DLL·게임 모듈·프리팹)

> CLAUDE.md에서 옮긴 상세 규칙이다. 이 영역의 코드·에셋을 고치기 전에 읽는다. 규칙을 바꾸거나 더할 때는 이 문서(또는 관련 머리 주석)를 고치고 CLAUDE.md 요약 줄도 맞춘다.

- 트랜스폼 갱신 캐시(2026-10-04): `FScene::UpdateTransforms`는 엔티티마다 마지막 계산 입력(`FTransformComponent::WorldCache` = 로컬 TRS 사본 + **부모의 `WorldStamp`**)과 **비트 단위로 같으면** 월드 행렬 계산을 건너뛴다 — `WorldStamp`는 월드 행렬을 계산할 때마다 받는 프로세스 전역 고유 번호(구조체 복사는 행렬과 함께 옮겨지므로 같은 번호 = 같은 값, 루트의 부모 = 1, 0 = 무효)라 부모 월드 64바이트 대신 번호를 비교한다. 결과는 전체 재계산과 비트 동일, 로컬 값을 쓰는 쪽(스크립트·물리·애니메이션·복제·편집기·게임 모듈)은 표시할 필요가 없다. **`WorldMatrix`를 직접 쓰고 되돌리지 않는 코드는 `InvalidateWorldCache()`**를 부른다(그래야 새 번호로 다시 계산해 자식도 따라온다 — 예: `AISystem` SetWorldPose, 렌더 동안만 바꾸고 정확히 되돌리는 `FPixelArtObjectSnap`은 불필요). 캐시는 리플렉션에 등록하지 않으며 구조체 통째 복사(`CopyComponent`)는 월드 행렬·번호와 함께 옮겨져 일관된다. 소켓 부착 엔티티는 항상 다시 계산. **갱신 계획**: 루트 순서(풀 순서) + 루트별 깊이 우선 전위 평탄화 배열(트랜스폼 풀 밀집 인덱스 + 부모 칸 + 하위 트리 끝)을 계층(`SetParent`/생성/파괴 — `HierarchyRevision`)·트랜스폼/계층 풀 구조(`TSparseSet::GetRevision`)가 바뀔 때만 다시 만들고, 평소에는 재귀·자식 목록·희소 조회 없이 배열을 루트별 병렬로 돈다. **계층 컴포넌트를 `SetParent` 밖에서 직접 고치는 코드는 `FScene::NotifyHierarchyChanged()`**(현재 `FSceneCloner`뿐). `FMatrix4x4::operator*`는 헤더 인라인 SSE(칸마다 ((p0+p1)+p2)+p3 — 스칼라와 비트 동일, `Math_MatrixMultiplyMatchesScalarBitExactly`, FMA 금지). 비교 `--cvar scene.TransformCache=0`, 바꾸면 `Scene_TransformCacheMatchesFullRecompute`·`Scene_PartialTransformUpdateMatchesFull`

- 뼈(모델 노드) 트랜스폼 소유와 프레임당 갱신(2026-10-04, 1000유닛 게임 틱 3.6 → 1.7ms): 뼈는 계속 엔티티이고 **진실은 엔티티 로컬 TRS**(애니메이션 `WritePose`·IK·래그돌(물리)이 쓰고, 편집기·스크립트·시퀀서도 쓸 수 있음)이며 월드 행렬은 `FScene` 갱신만 쓴다 — 렌더러 팔레트·소켓·IK·래그돌·편집기는 엔티티 `WorldMatrix`를 그대로 읽는다(애니메이션 런타임 배열로 옮기지 않았다: 게임플레이 갱신 직후 뼈 월드를 읽는 코드(OnLateUpdate·충돌 알림·LookAt 대상·뼈에 붙은 카메라)가 있어 늦게 계산하면 의미가 바뀐다). 프레임 흐름: 게임플레이 1차 갱신 = 전체(루트가 움직이면 뼈 전부 다시 계산 — 메모리 대역폭이 바닥, 500유닛은 L3 안이라 1000에서 비선형으로 보임), **2차 갱신은 충돌 알림·OnLateUpdate(+지연 파괴)가 아무것도 안 했으면 생략**(`FLuaRuntime::LateUpdate`/`DispatchCollisionEvents`가 알림 — 그 사이 다른 코드는 트랜스폼을 읽기만), **표시 틱은 `FScene::UpdateTransformsPartial`** — 직전 게임플레이 갱신 뒤 로컬을 쓴 것(`FTimeOfDaySystem::Update`가 돌려준 태양, `FAnimationSystem::Update(…, OutWritten)`의 평가한 모델 루트 하위 트리 + 노드)만 알리고 나머지(URO로 건너뛴 모델·래그돌·정적 물체)는 하위 트리째 건너뛴다. 이 계약은 앱 순서 `TickGameplay → TickPresentation`(사이에 트랜스폼 쓰기 없음)에 기댄다 — `FGameWorld::GameplayValidatedScene`(게임플레이 틱이 설정, 표시 틱·BeginPlay/EndPlay가 비움)이 없으면 전체 갱신. **표시 틱에서 트랜스폼을 쓰는 새 코드(애니메이션 단계·시간대 등)는 쓴 엔티티를 `PresentationWritten`에 넣는다**(빠지면 그 프레임 화면이 틀린다). 새 앱이 두 틱 사이에 트랜스폼을 쓰면 안 된다. 구조가 바뀐 프레임(계획 재생성)·캐시 끔이면 부분 갱신은 전체로 대체

- 엔진 DLL: 런타임 모듈(Core/RHI/Scene/Renderer/Audio/Physics/AI/Scripting/World/Network/UI)은 `ProjectEEngine.dll` 하나로 빌드된다(`E_ENGINE_SHARED`, 기본 ON — OBJECT 라이브러리를 DLL에 링크, 함수는 자동 내보내기 — `WINDOWS_EXPORT_ALL_SYMBOLS`와 같은 `__create_def` 목록에서 sol2 내부(`@sol@@`)와 **std:: 범위 함수**(템플릿 인스턴스 — `UnDecorateSymbolName` 이름만으로 판정, 데이터 심볼은 유지)를 뺀 `.def`, 호스트 도구 `Tools/ExportFilter`(`EExportFilter`, 빌드 중 실행). DLL 내보내기 한도 65535(2026-10-04 Release 64193개 → std 함수 제외로 약 10400개). 한도를 넘으면 도구가 실패 — DLL 밖이 실제로 가져다 쓰지 않는 심볼군(`dumpbin /imports`로 확인)만 더 거른다). 실행 파일/테스트/게임 모듈은 **`ProjectE::Engine`만 링크**한다(모듈 타깃 직접 링크 금지 — 객체 중복). DLL 밖에서 접근하는 **전역 데이터**는 `E_ENGINE_API`(Core/EngineApi.h), 엔진 공개 헤더의 로그 카테고리는 `E_DECLARE_ENGINE_LOG_CATEGORY`. 헤더 인라인 템플릿의 함수 지역 static처럼 바이너리마다 따로 생기는 상태에 전역 의미를 두지 않는다(예: ECS 타입 ID는 `FRegistry::AssignComponentTypeId`가 엔진 DLL에서 부여)

- 게임 모듈: `Projects/<이름>/Source/CMakeLists.txt` → `<이름>.dll`(SHARED, `ProjectE::Engine` 링크, `E_GAME_MODULE_TARGETS`에 추가). `.eproject`의 `"GameModule"`로 지정하면 에디터/런타임이 실행 파일 폴더에서 로드(`FGameModuleHost`). `IGameModule`(Scene/GameModule.h) + `E_IMPLEMENT_GAME_MODULE`: `OnLoad`에서 컴포넌트 리플렉션 등록(인스펙터/직렬화/Lua 자동 노출), `OnBeginPlay/OnUpdate/OnEndPlay`(에디터는 플레이 중에만, 스크립트 뒤·물리 앞). 언로드 시 모듈 소유 타입 제거(+ `AddUnloadCleanup`으로 등록된 다른 모듈의 소유자별 정리 — 예: 비헤이비어 트리 노드. 게임 모듈의 BT 노드는 OnLoad에서 Owner를 비운 채 `FBehaviorTreeNodeRegistry::Get().Register`), DLL은 프로세스 종료까지 유지. 멀티플레이(`GameModuleApiVersion` 3): 게임 모듈은 서버에서만 돌며 `OnPlayerJoined/Left`, `OnRpc`(Server RPC·자신의 Multicast, 같은 이름의 스크립트 메서드와 함께), `GetNet()->CallRpc`(`Scene/GameRpc.h` — Lua와 같은 경로)를 쓴다. 인터페이스를 바꾸면 버전을 올린다

- C++ 게임 모듈 핫 리로드(Phase 48 사이드): 에디터는 게임 모듈을 그림자 복사본 `<Saved>/HotReload/<이름>_<번호>.dll`(+ PDB, 복사본 CodeView PDB 경로를 복사본 파일 이름으로 바꿔 원본 DLL/PDB 잠금 없음, `FGameModuleHotReload` — `Editor/GameModuleHotReload.h`)로 로드한다(런타임·서버·패키지는 원본 직접). 다시 로드 절차는 `Editor/EditorHotReload.cpp` 머리 주석이 기준(플레이 정지 → 씬/에셋 창 JSON → `FGameModuleHost::Reload` → `FPrefabLibrary::Invalidate` → 실행 취소 복원 경로로 복원, 실행 취소 기록 유지, 옛 DLL 해제 안 함). 다시 로드 때 모듈 소유 컴포넌트의 ECS 타입 ID는 폐기(`FRegistry::RetireComponentTypeId`)되고 새 DLL은 새 풀을 쓰므로 **모듈 타입 ID를 캐시해 다시 로드 너머로 쓰지 말고 모듈 타입은 리플렉션으로만 다룬다**. 씬 밖에서 리플렉션 정보/모듈 컴포넌트를 드는 새 캐시(`FTypeInfo*`, 캐시된 씬)는 `ReloadGameModule`에서 비우거나 다시 만든다. 메뉴 도구 → C++ 다시 로드(Ctrl+Alt+F11) / 게임 모듈 빌드 후 다시 로드(`FGameModuleBuild`, 에디터 빌드 폴더의 `cmake --build --target`), 자동 감지 = 환경설정 일반 `AutoReloadGameModule`(자동 검증은 끔). 검증 `--verify-hot-reload`(`--scene Scenes/Tests/GameModule.escene`), `--verify-hot-reload-build`. 엔진 DLL 자체 변경은 에디터 재시작 필요. CMake 구성 시점 생성 파일은 내용이 바뀔 때만 쓴다(`file(CONFIGURE)` — `file(WRITE)`는 시각을 바꿔 엔진 DLL을 다시 링크시켜 에디터가 열린 동안 게임 모듈 빌드가 LNK1168로 깨짐)

- 프리팹(`.eprefab`, `Scene/Prefab.h` `FPrefabLibrary::Get()`): 인스턴스는 씬에 일반 엔티티로 저장되고 루트에 `FPrefabInstanceComponent`(원본 경로 + 오버라이드 키 목록), 엔티티마다 `FPrefabLinkComponent`(고정 ID, 인스턴스 루트)를 단다. 파일과 씬은 `Scene/EntityJson`(엔티티 목록 직렬화)을 공유한다. **오버라이드는 인스턴스와 "현재 원본"의 차이를 `RecordAllOverrides`로 기록한 것**이므로 원본을 바꾸는 코드는 반드시 `Context.ChangePrefab`(기록 → 변경 → `Invalidate` → `SyncAllInstances` → 해석)을 거치고, 원본을 바꾼 뒤 동기화 전에 기록하지 않는다. 씬 로드(`FSceneSerializer::FromJsonString`)는 자동으로 동기화한다. 루트의 위치/회전/이름은 항상 인스턴스 값. 중첩 인스턴스 안 엔티티 ID는 "바깥/안쪽". 새 컴포넌트/프로퍼티는 리플렉션 등록만 하면 동기화·오버라이드 대상이 된다(ResourceHandle/PF_Transient 제외, 경로 문자열이 바뀐 컴포넌트는 핸들을 비워 다시 해석). Lua 생성은 `Scene.SpawnPrefab`(지연 생성 + 콜백)
