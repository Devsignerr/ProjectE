    왜 필요한가"내 PC에서는 되는데요"

    개발 중의 게임은 아주 친절한 환경에서 돕니다. 엔진 소스 폴더가 바로 옆에 있고, 셰이더 컴파일러(DXC)가 있어 셰이더를 즉석에서 컴파일하고, glTF 원본이 있어 없는 쿠킹본을 그 자리에서 만들고, Visual Studio가 설치한 VC++ 런타임이 System32에 있습니다. 쓰기도 자유롭습니다. 로그와 세이브를 프로젝트 폴더에 써도 아무도 막지 않습니다.

    플레이어의 PC에는 이 중 아무것도 없습니다.

    개발 환경플레이어 PC대응 (이 강의)
    셰이더 소스 + DXC로 즉석 컴파일DXC 없음쿠킹된 DXIL만 동봉
    glTF/PNG 원본 → 필요할 때 쿠킹원본 없음(용량·유출)쿠킹본만 동봉, 원본 제외
    파일 수천 개가 폴더에 흩어짐설치·패치·무결성 확인이 어려움pak 하나로 묶기 + 항목별 해시
    프로젝트 폴더에 로그·세이브 쓰기Program Files는 쓰기 금지일 수 있음%LOCALAPPDATA%로 Saved 이동
    VC++ 런타임이 System32에 있음없을 수 있음app-local 런타임 동봉 + 검사
    크래시 나면 디버거로 봄"꺼졌어요"라는 말뿐미니덤프 + 보고서 + 로그 + 따로 보관한 PDB
    ProjectERuntime.exe --project ..."게임이름.exe" 더블클릭exe 복사 + 아이콘/버전 스탬프, 프로젝트 자동 탐색

    Phase 19는 사용자 요청 "게임을 바이너리화해서 스팀 같은 데 올릴 수 있게"로 시작했고, DoD는 "Package.ps1 한 번으로 <게임 이름>.exe를 더블클릭하면 바로 실행되는 폴더가 나오고, VC++ 런타임이 설치되지 않은 PC에서도 실행된다"였습니다.

    핵심 개념쿠킹과 패키지 배치

    쿠킹(cooking)은 사람이 편집하기 좋은 원본 에셋을 엔진이 바로 읽기 좋은 형식으로 미리 바꾸는 일입니다(10강). 셰이더 HLSL → DXIL 바이트코드, glTF → .emodel, PNG/JPG → 용도별 BC 압축 .etex, 그래프 머티리얼 → 생성된 셰이더 변형의 DXIL. 쿠킹 도구 ProjectECook은 GPU 없이 돕니다. 패키지 게임은 쿠킹본만 읽으므로 DXC가 필요 없습니다(dxcompiler.dll은 지연 로드라 없어도 실행됨).

    배치는 언리얼 패키지와 같은 모양입니다: 실행 파일 + Engine/ + 실행 파일 이름의 프로젝트 폴더. 몇 가지 파일은 일부러 pak 밖에 둡니다. Shaders.json은 엔진 디렉터리를 찾는 마커이고(FPaths가 실행 파일 위쪽에서 이 파일을 찾아 엔진 폴더를 정함), .eproject와 Config/는 pak을 마운트하기 전에 읽어야 하기 때문입니다. 닭이 먼저 있어야 달걀을 찾을 수 있습니다.

    ProjectE에서는Package.ps1의 다섯 단계

    4단계 검사가 이 스크립트에서 가장 값진 부분입니다. "실행되는지"는 개발 PC에서 확인할 수 없는 것이 있기 때문입니다. 대표가 VC++ 런타임입니다. 개발 PC에는 System32에 런타임이 있으므로 패키지에 빠뜨려도 잘 실행됩니다. 그래서 검사는 일부러 엄격합니다.

# 개발 PC에는 VC++ 런타임이 System32에 있으므로 vcruntime/msvcp 계열은 패키지 안에 있어야만 통과
$Lines = & $DumpBin /nologo /dependents $Binary.FullName

    함정: std::ifstream은 pak을 모른다

    pak을 도입하는 순간 엔진 전체에 규칙이 하나 생깁니다. 콘텐츠를 읽는 모든 코드는 FFileSystem을 거친다. std::ifstream("…/Scenes/Hub.escene")이나 std::filesystem::exists는 디스크만 보므로, 개발 중에는 멀쩡히 동작하다가 패키지에서만 "파일 없음"이 됩니다. 테스트도 개발 폴더에서 돌므로 이 버그는 패키지를 실제로 실행해 보기 전까지 숨어 있습니다.

    그래서 Phase 19 2단계는 pak 형식을 만드는 것보다 읽기 경로를 통합하는 데 더 많은 일을 했습니다: 쿠킹 모델/텍스처/.enav, 씬·머티리얼·파티클·프리팹·UI·BT JSON, Lua, 글꼴, 이미지, 쿠킹 셰이더, 에셋 캐시 신선도 판정, 오디오(62강의 miniaudio VFS). 반대로 쓰기, 에디터 전용 폴더 탐색, glTF/FBX 원본 임포트는 디스크를 직접 씁니다(패키지에는 원본이 없으므로). pak은 폴더 나열이 안 된다는 점도 영향을 줬습니다 — 61강의 문자열 표가 패키지에서 설정에 경로를 적어야 하는 이유입니다.

    확인 방법: 디스크 Content 없이 돌려 보기 2단계 검증은 "패키지에서 원본 콘텐츠 폴더를 지운 상태로" 했습니다. pak 93개 파일 32.1MB, 패키지 52.3MB — 기본 씬, Demo_UI(글꼴·9-slice·Lua), Demo_AI(.enav·.ebt), Demo_Audio(사운드)가 모두 디스크 Content 없이 정상이고 경고·오류 0. 어떤 로더가 아직 ifstream을 쓰면 이 실행에서 바로 드러납니다. CLAUDE.md에는 "새 로더에서 std::ifstream/std::filesystem::exists로 콘텐츠를 읽으면 패키지(pak)에서 깨진다"로 남겨 두었습니다.

    ProjectE에서는exe 스탬프와 사용자 폴더

    프로젝트마다 exe를 다시 빌드하지 않는다

    게임마다 이름·아이콘·버전 정보가 다른 exe가 필요하지만, 그것 때문에 런타임을 프로젝트마다 다시 컴파일하고 싶지는 않습니다. Windows 실행 파일의 아이콘과 버전 정보는 리소스라는 별도 영역에 있고, UpdateResource API로 빌드 후에 바꿔 쓸 수 있습니다. 패키징은 ProjectERuntime.exe를 <ExecutableName>.exe로 복사한 뒤 ProjectECook --stamp-exe로 프로젝트 설정(DisplayName/Version/Company/Icon)을 써 넣습니다. FExecutableResources가 .ico 파싱(또는 PNG → 256/64/48/32/16 크기 아이콘), VS_VERSIONINFO 생성, 기록을 맡고, 아이콘 그룹 ID 1을 창 클래스 아이콘으로 쓰므로 작업 표시줄 아이콘도 함께 바뀝니다. 테스트(ExecutableResourcesTests 4개)는 복사한 exe에 스탬프한 뒤 GetFileVersionInfo/LoadImage로 되읽어 확인합니다.

    Saved는 사용자 폴더로

    패키지 게임은 C:\Program Files에 설치될 수 있고, 그곳은 일반 권한으로 쓸 수 없습니다. 그래서 패키지일 때는 로그·세이브·설정·크래시 덤프를 %LOCALAPPDATA%/[회사/]<프로젝트>/Saved로 옮깁니다. "지금 패키지인가?"는 Package.ps1이 기록하는 Engine/Packaged.json의 존재로 판정합니다(FPaths::IsPackaged()).

return EnsureDirectory(GetProjectDirectory() / L"Saved");   // 개발: 프로젝트 폴더

    핵심 개념크래시를 "증거"로 남기기: 미니덤프, 보고서, PDB

    플레이어 PC에서 게임이 꺼지면 개발자가 받는 정보는 "꺼졌어요"뿐입니다. 재현이 안 되면 고칠 수 없습니다. 그래서 크래시 순간의 상태를 파일로 남깁니다.

    • 미니덤프(minidump): 크래시 순간의 스레드 스택, 레지스터, 로드된 모듈 목록, (옵션에 따라) 스택이 가리키는 메모리 등을 담은 작은 파일. Visual Studio로 열면 디버거가 그 순간에 멈춘 것처럼 콜스택과 지역 변수를 볼 수 있습니다.
    • PDB(프로그램 데이터베이스): 기계어 주소 ↔ 함수 이름·소스 줄 대응표. 덤프만 있으면 "0x7FF6…에서 크래시"이지만, 빌드 당시의 PDB와 같은 바이너리가 있으면 "Scene.cpp 120줄"이 됩니다.
    LONG WINAPI HandleUnhandledException(EXCEPTION_POINTERS* Info)
{
	if (IsDebuggerPresent()) { return EXCEPTION_CONTINUE_SEARCH; }            // 디버거가 먼저 처리
	if (InterlockedExchange(&GbHandlingCrash, 1) != 0) { return EXCEPTION_EXECUTE_HANDLER; } // 처리 중 또 크래시

	ShowCrashDialog(CrashDirectory);
	return EXCEPTION_EXECUTE_HANDLER;
}

	__except (WriteFatalDump(GetExceptionInformation(), Message)) {}
}

    Fatal 경로가 일부러 예외를 던지는 이유는 미니덤프가 예외 정보(EXCEPTION_POINTERS)와 함께 쓸 때 가장 정확한 콜스택을 담기 때문입니다. 스택 오버플로일 때는 남은 스택이 적어 보고서의 심볼화를 생략하는 것처럼, 크래시 처리기 자체가 또 크래시 나지 않도록 하는 작은 방어가 여러 군데 있습니다.

    Release에도 PDB를: /Z7

    최적화된 Release 빌드에서 일어나는 크래시가 진짜 크래시입니다. 그래서 Release도 디버그 정보를 만듭니다(/Z7 + 링커 /DEBUG /OPT:REF /OPT:ICF). /Z7은 디버그 정보를 오브젝트 파일에 넣는 방식이라 병렬 컴파일 때 공유 PDB 파일 잠금 경합이 없습니다. /DEBUG를 켜면 링커가 기본으로 최적화(사용 안 하는 함수 제거, 같은 함수 합치기)를 끄므로 /OPT:REF /OPT:ICF를 명시해 되살립니다(루트 CMakeLists.txt 주석). PDB는 패키지에 넣지 않고 -Symbols 폴더에 같은 바이너리와 함께 보관합니다. 디버거는 덤프의 모듈과 PDB의 서명이 일치해야 심볼을 붙이므로, 다시 빌드한 PDB로는 열리지 않습니다.

    핵심 개념VC++ 런타임: app-local과 "정적 CRT 금지"

    MSVC로 빌드한 프로그램은 C/C++ 표준 라이브러리 구현(CRT: vcruntime140.dll, msvcp140.dll …)을 필요로 합니다. 배포 방법은 셋입니다.

    방법장점단점ProjectE
    재배포 패키지 설치 요구패키지가 작음설치 단계 필요, 없으면 실행 실패—
    app-local: CRT DLL을 exe 옆에 복사설치 불필요DLL 몇 개가 늘어남채택 (Microsoft.VC143.CRT)
    정적 CRT (/MT)DLL 없음모듈마다 CRT 사본(힙)이 따로 생김금지

    정적 CRT가 왜 안 될까요? ProjectE는 ProjectEEngine.dll, 게임 모듈 DLL, exe가 std::string, std::vector, std::unique_ptr 같은 STL 객체를 함수 경계 너머로 주고받습니다(12강). 정적 CRT로 빌드하면 각 모듈이 자기만의 힙을 가집니다. 엔진 DLL이 만든 std::string을 게임 모듈이 소멸시키면, 게임 모듈의 힙에 "내가 할당하지 않은 메모리"를 해제하라고 하는 셈이 되어 힙이 깨집니다. 모든 모듈이 같은 CRT DLL을 공유해야 힙도 하나입니다.

    설계 이유가 다른 결정과 이어진다 "엔진을 DLL 하나로 만들고 게임 모듈과 STL로 대화한다"(12강)는 결정이 "정적 CRT를 쓸 수 없다"를 낳고, 그것이 "app-local 런타임 + dumpbin 검사"를 낳았습니다. 배포 방식은 아키텍처의 결과입니다. Debug 구성은 디버그 CRT가 재배포 불가라 검증용으로만 패키징합니다.

    핵심 개념Steamworks의 동작 방식

    Steamworks API는 게임 프로세스 안에서 혼자 동작하지 않습니다. 게임이 SteamAPI_Init()을 부르면 steam_api64.dll이 같은 PC에서 실행 중인 Steam 클라이언트에 연결합니다. 그래서 Steam이 꺼져 있거나 로그인되지 않았거나 그 계정이 게임을 소유하지 않으면 초기화가 실패합니다. 이때 SDK는 "이 게임이 어떤 App ID인지"를 알아야 하는데, 정상 경로(Steam 라이브러리에서 실행)에서는 Steam이 환경 변수로 넘겨 주고, 개발 중에는 보통 exe 옆에 steam_appid.txt를 둡니다.

    Steam에서 오는 응답은 대부분 비동기입니다. "통계를 받아 와"라고 요청하면 결과는 나중에 콜백으로 옵니다. 콜백은 게임이 SteamAPI_RunCallbacks()를 불러 줄 때 그 스레드에서 실행되므로, 게임 루프가 매 프레임 한 번 불러 펌프해야 합니다(1강의 Win32 메시지 펌프와 같은 구조).

    또 하나의 기본 개념은 SteamAPI_RestartAppIfNecessary(AppId)입니다. 플레이어가 Steam을 거치지 않고 설치 폴더의 exe를 직접 실행했다면, 이 함수가 true를 돌려주고 Steam을 통해 게임을 다시 실행시킵니다. 그러면 게임은 즉시 종료해야 하고, Steam이 정식 경로로 새 프로세스를 띄웁니다.

    자동 검증이 "라이브 D3D 객체"를 보고하다 Phase 21 작업 중 런타임 자동 검증이 종료 시 해제되지 않은 D3D 객체를 보고했습니다. 원인은 Steam 오버레이였습니다. 오버레이가 스왑체인과 큐를 잡고 있는데 Steam 종료가 렌더러 종료보다 늦었던 것입니다. 수정은 둘: 런타임 Steam 종료를 렌더러 앞으로 옮기고, 자동 검증 실행은 기본으로 Steam을 켜지 않게 했습니다(오버레이가 프로세스 끝까지 D3D 객체를 잡으므로 — 확인할 때만 --steam).     Steam 없이도 검증할 수 있는 부분과 없는 부분 SDK 없이 빌드한 엔진은 Steam_DisabledWithoutInit 테스트와 Lua Steam 기본값 테스트로, Steam 클라이언트가 꺼진 PC는 "경고 후 정상 실행"으로 자동 확인합니다. 업로드는 -GenerateOnly로 vdf 생성(Release 패키지 52.6MB, 18개 파일, steam_api64.dll 포함)까지 확인했습니다. 실제 Steam 연결은 Phase 20 검증 때 "사용자 이름 로그"까지 확인됐고, 그때 Steamworks에 통계가 등록되어 있지 않아 통계 수신 실패 경고가 한 번 나왔습니다. 실제 업로드와 오버레이·업적 동작은 Plans.md에 사용자 확인 항목으로 남아 있습니다.
    • 비밀은 저장소 밖에: SDK 경로는 gitignore된 CMakeLocal.cmake나 환경 변수로, 업로드 계정 비밀번호는 steamcmd가 직접 묻게 합니다. 스크립트 인자나 로그에 비밀번호가 남지 않게 하는 것이 기본입니다.

    정리
    • Steamworks는 실행 중인 Steam 클라이언트와 통신하며, 응답은 콜백으로 오므로 매 프레임 RunCallbacks로 펌프한다.
    • SDK는 파트너 전용이라 선택적 의존: CMake가 찾으면 E_WITH_STEAM=1, 아니면 같은 API의 빈 구현. Steam 헤더는 .cpp 하나에만.
    • 오버레이 때문에 Init은 렌더러보다 먼저, Shutdown도 렌더러보다 먼저. 런타임만 초기화하고 자동 검증은 끈다.
    • Steam 밖 실행은 RestartAppIfNecessary로 재실행, steam_appid.txt는 쓰지 않고 패키지에 있으면 업로드 거부.
    • 업적은 통계 수신 전이면 대기열 → 수신 콜백에서 적용. 업로드는 vdf 두 개 + steamcmd, 기본 브랜치 공개는 사람이 웹에서.

    창을 띄우지 않는 자동 검증

    자동 검증 실행은 창을 숨깁니다(FWindowDesc::bHidden). 그리기와 스크린샷은 그대로이고 결과는 보이는 창과 비트 동일합니다. 처음부터 그랬던 것은 아닙니다.

    "게임 화면이 계속 뜬다" 검증을 자주 돌리자 작업 중인 사용자의 화면에 게임 창이 계속 떠서 포커스를 빼앗았습니다(2026-10-04 사용자 보고). 그래서 --exit-after/--screenshot 실행은 숨긴 창이 기본이 됐고, --show-window는 사용자가 직접 요청할 때만 씁니다. 높은 fps 측정도 숨긴 창 + --no-vsync로 하고 로그의 프레임 시간을 함께 기록합니다. 창을 보이게 만드는 새 코드(ShowWindow, WS_VISIBLE …)는 이 플래그를 존중해야 한다는 규칙이 CLAUDE.md에 남았습니다. 검증 도구도 사용자 경험이 있는 제품이라는 교훈입니다. 비슷한 이유로, 자동 검증은 소리를 끄고(62강) Steam을 켜지 않으며(64강), 개인 설정 파일을 읽거나 쓰지 않습니다.

    // C++
inline float DistanceWindow(float Distance, float Radius)
{
	if (Radius <= 0.0f) { return 0.0f; }
	const float Ratio  = Distance / Radius;
	const float Ratio2 = Ratio * Ratio;
	const float Window = FMath::Clamp(1.0f - Ratio2 * Ratio2, 0.0f, 1.0f);
	return Window * Window;
}
// HLSL
float LightDistanceWindow(float Distance, float Radius)
{
	if (Radius <= 0.0f) { return 0.0f; }
	const float Ratio  = Distance / Radius;
	const float Ratio2 = Ratio * Ratio;
	const float Window = saturate(1.0f - Ratio2 * Ratio2);
	return Window * Window;
}

    이 패턴은 엔진 전체에 퍼져 있습니다. 조명(LightMath), 면광원(AreaLightMath), DDGI(DdgiMath), 레이 트레이싱(RayTracingMath), 대기(AtmosphereMath), 반사(ReflectionMath), 파티클 경계(ParticleBounds), 오클루전(HzbMath), 픽셀 아트(PixelArtMath) … CLAUDE.md의 규칙은 거의 항상 같은 문장 꼴입니다: "식은 X.h ↔ X.hlsl, 바꾸면 X_* 테스트도". 이 테스트들은 엔진 테스트 프레임워크의 E_TEST로 등록되며, 이 글을 쓰는 시점 Tests/ 아래 E_TEST가 800개를 넘습니다.

//   E_TEST(VectorDot) { E_EXPECT_NEAR(FVector3::Dot(A, B), 1.0f, 1e-5f); }
#define E_TEST(TestName)                                                                  \

	static void TestFunction_##TestName()

    프레임워크는 일부러 작습니다. 정적 객체 생성자로 자기 등록, 실패하면 파일·줄과 "기대: A ≈ B (실제 x, 기대 y, 허용 z)"를 한글로 남기는 매크로 몇 개가 전부입니다. 외부 테스트 라이브러리가 하는 일 대부분이 필요 없었고, 엔진 DLL·로그와 바로 붙는 것이 더 중요했습니다. 순수 로직을 분리해 두는 습관(61강 FUITextEdit, 62강 ToListenerSpace, 60강 가짜 텍스트 측정기)이 테스트를 가능하게 합니다.

    테스트를 위한 설계 장치들 FTestRegistry::GetTempDirectory()(프로세스별 임시 폴더 — 동시에 도는 다른 테스트 실행과 충돌 방지), AllowRealSockets()(실제 소켓 테스트는 환경 변수가 있을 때만 — 아래 방화벽 이야기), 오디오 bNoDevice(62강), 네트워크 FLoopbackTransport(55강), 세이브 SetDirectoryOverride. 실제 장치·OS 자원을 바꿔 끼울 수 있는 자리를 처음부터 두는 것입니다.

    핵심 개념결정성: 같은 입력이면 비트까지 같은 화면

    스크린샷을 자동으로 비교하려면 같은 코드를 두 번 돌렸을 때 같은 이미지가 나와야 합니다. 그런데 실제 게임은 매 실행이 조금씩 다릅니다. 프레임 시간이 부하에 따라 흔들리고, 비동기 로딩이 다른 순서로 끝나고, 스레드가 다른 순서로 일을 마칩니다. ProjectE는 자동 검증 실행에서 이 흔들림의 원천을 하나씩 제거했습니다.

    • 시간: --fixed-delta면 FTimer가 실제 경과 대신 고정 값을 줍니다(1강). 그리고 화면·시뮬레이션 상태가 시간을 읽는 곳은 모두 FFrameTime(앱 프레임 시간)을 씁니다. 자동 노출 적응, 물·구름·머티리얼 Time, 쿠키 패닝, 스트리밍 내림 지연이 steady_clock을 직접 읽으면 부하에 따라 화면이 달라집니다. 실제 시각은 측정(프레임 간격, CPU/GPU 구간, 로딩 시간)에만 씁니다.
    • 로딩: 자동 검증은 비동기 로딩을 쓰되 프레임마다 비우고(r.AsyncLoading 기본값 −1 = 자동 검증이면 "비동기 + 프레임마다 비우기"), RT 가속 구조는 같은 프레임에 모두 빌드하며(상한 없음), 텍스처 스트리밍은 "스트리밍 켬 화면 = 끔 화면, 비트 동일"을 요구합니다.
    • 순서: 병렬 코드는 결과를 엔티티 순서로 합칩니다(33강). 난수는 시드 결정적(53강 절차적 생성은 자체 SplitMix64, 표준 분포 함수·unordered 순회 금지).

//   실제 시각(steady_clock)이 아니라 이 시간으로 진행한다 — `--fixed-delta`면 실행마다(부하와 무관하게) 같은 화면이 된다.
//   측정(프레임 간격, CPU/GPU 구간, 로딩 시간, 업로드 속도)은 계속 실제 시각을 쓴다
class FFrameTime

    회귀 비교: "끈 화면은 예전과 비트 동일"

    결정성의 가장 큰 쓸모는 새 기능의 안전 확인입니다. 새 렌더링 기능을 넣을 때 ProjectE는 거의 항상 끄는 스위치(CVar, 명령줄 별칭)를 같이 만들고, "끈 화면 = 도입 전 화면"을 MD5로 확인합니다. CLAUDE.md에 그런 문장이 여럿 있습니다: 레이 트레이싱 효과가 꺼진 화면은 래스터와 비트 동일(--no-raytracing), 면광원·IES·쿠키가 없는 씬은 비트 동일, TAAU의 네이티브 100%는 Phase 47 화면과 비트 동일, 스킨 메시 LOD를 끄면 이전과 비트 동일. 그림자 캐시 최적화는 "화면 비트 차이 없음(Terrain/Materials/GI MD5 동일)"으로 들어갔습니다.

    최적화의 기본값도 이 측정에 기댑니다. 눈에 띄는 화질 차이가 없으면 최적화는 기본으로 켜고, 끄는 CVar는 남겨 둡니다. 차이가 생기는 설정(예: 그림자 LOD 바이어스 0.5에서 Hub 나무 그림자 모양 변화)은 기본으로 끕니다.

    결정성이 잡아낸 드라이버 문제: PSO 캐시 PSO 캐시(31강)를 켜자 화면이 실행마다 달라졌습니다. 결정적이어야 할 자동 검증의 MD5가 흔들린 것이 신호였습니다. 원인은 워밍 작업 스레드가 드라이버 파이프라인 라이브러리에서 Load한 것이었습니다(드라이버 내부 원인은 미상). 수정은 "워밍 스레드는 항상 Create, 라이브러리 Load는 요청 스레드만"이었고, 확인 기준은 "Tests/Materials·Decals·Terrain을 캐시를 켠 채 4회 연속 실행해 MD5가 모두 같고 --no-pso-cache와 같음"으로 CLAUDE.md에 남았습니다. 결정성이 없었다면 "가끔 화면이 조금 다르다"는 영원히 재현되지 않는 버그였을 것입니다.

    핵심 개념평균에 안 잡히는 것을 재기: 화면 안정성과 규모 추세

    화면 안정성

    "화면이 지글거린다"(20강), "구석이 깜빡인다"(26강) 같은 보고는 한 장의 스크린샷으로는 보이지 않습니다. 시간에 따른 변화이기 때문입니다. 처음에는 화면 전체 평균 밝기의 프레임 간 변화를 쟀는데, 이것으로는 국소 깜빡임과 얼룩을 놓쳤습니다(2026-10-04 기록). 지금의 측정 방법은 이렇습니다.

    1. 충분히 수렴한 뒤(--exit-after 600 이상) 연속 32프레임을 저장합니다(--screenshot-frames 32).
    2. 화소마다 밝기의 시간 표준편차 지도를 만들고(×64 증폭해 눈으로도 봄), 99%·99.9% 분위와 1.0 초과 비율을 봅니다.
    3. 16×16 블록 평균의 시간 표준편차로 넓은 저주파 깜빡임을 따로 봅니다(8비트 양자화 경계 제거).
    4. 영역 평균의 시계열로 2프레임 주기 왕복을 확인하고, TAA를 끈 실행과 비교합니다(TAA·효과를 모두 끄면 정지 장면의 표준편차는 0).
    5. 공간 얼룩은 4배 최근접 확대 크롭을 직접 보고, 고표본(예: 256탭) 기준 이미지와의 RMSE·최대 오차로 잽니다.

    이 방법으로 찾은 것이 26강의 DDGI 깜빡임입니다. 텍셀 급변 감지 문턱이 광선 잡음에 걸려 프로브 단위로 깜빡였고, 기본값을 끄는 것(r.DDGI.ChangeThreshold 1.0)으로 고쳤습니다. 자동 검증이 결정적이라 vsync와 --no-vsync 결과가 같다는 점도 측정을 쉽게 만듭니다.

    규모 추세

    성능 최적화도 평균의 함정이 있습니다. 유닛 1000개에서 빨라진 최적화가 2000개에서는 오히려 느려질 수 있습니다. 시간이 개수에 비례하지 않고 더 빨리 늘어나는 구간(비선형)이 숨어 있으면 지금 규모에서는 안 보입니다. Scripts/ScaleBench.ps1은 같은 스트레스 씬을 유닛 수별(기본 500, 1000, 2000)로 생성해 구간별 시간을 재고, 이웃한 두 규모 사이에서 시간 배율이 개수 배율 × 1.25를 넘는 구간을 "비선형"으로 표시합니다(종료 코드 1).

    목표도 숫자로 적어 둡니다: 스킨 유닛 1000개에서 60fps 이상(1280×720 Release, RT 끔 기준 16ms 이하 — 2026-10-04 현재 12.4ms), 정적 인스턴스 1만. 그리고 알려진 한계(뼈 = 엔티티라 유닛당 엔티티 약 50개, 게임·렌더가 같은 스레드에서 순서대로)도 같은 자리에 적어, 다음 최적화의 방향이 기록에서 바로 보이게 합니다.

    ProjectE에서는Plans.md와 CLAUDE.md: 기록이 곧 설계

    0강에서 본 것처럼 모든 작업은 Plans.md의 Phase와 DoD(완료 기준)로 시작합니다. 상태 표시는 [ ] 대기 · [~] 진행 · [x] 완료 · [!] 블로커입니다. 좋은 DoD는 확인 가능한 문장입니다 — 63강의 "VC++ 런타임이 설치되지 않은 PC에서도 실행된다"처럼. 완료 항목에는 결과뿐 아니라 측정값과 한계를 함께 적습니다("패키지 52.2MB", "한계: 압축 없음"). 그리고 사람만 확인할 수 있는 것은 - [ ] 실행 검증 (사용자)로 따로 남겨, 자동 검증이 덮지 못한 범위를 숨기지 않습니다.

    CLAUDE.md는 다른 역할을 합니다. 설계 규칙과 버그에서 나온 규칙을 모읍니다. 이 문서의 많은 문장은 "~하지 않는다 — 했더니 이런 일이 있었다" 꼴입니다: "stb_truetype SDF 함수는 CFF 3차 곡선을 버리므로 쓰지 않는다"(60강), "새 로더에서 std::ifstream으로 콘텐츠를 읽으면 pak에서 깨진다"(63강), "조도 아틀라스는 RGBA32F — 16비트는 히스테리시스 걸음이 반올림에 먹혀 어둡게 치우친다"(26강). 버그 하나를 고칠 때 같은 종류의 버그가 다시 생기지 않게 하는 문장을 남기는 것, 그것이 이 프로젝트의 가장 강력한 품질 도구였습니다. 다음 작업자(사람이든 에이전트든)는 이 문서를 먼저 읽습니다.

    ProjectE에서는병렬 트랙과 워크트리 운영

    독립적인 작업은 병렬로 진행했습니다. 예를 들어 Phase 23~26은 조명/입력/게임플레이 세 트랙, 데모 서브맵들(Lighting, Alley, Gallery, Forest, Workshop, Training, Campfire)도 각자의 브랜치에서 만들어 병합했습니다(git log의 "Merge demo-…"). 각 트랙은 git worktree(같은 저장소의 다른 작업 폴더)에서 자기 브랜치에 커밋하고, 메인이 병합하며, 트랙마다 "수정해도 되는 범위"를 명시합니다. Plans.md/CLAUDE.md처럼 모두가 건드리는 파일은 "끝에 추가"하는 변경만 하게 해 충돌을 줄였습니다.

    "왜 이렇게 오래 걸리냐" 처음에는 작업마다 새 워크트리를 만들었습니다. 그런데 새 워크트리는 빌드 폴더가 비어 있어 엔진 전체 빌드(약 8분)와 셰이더·모델 재쿠킹이 매번 들었습니다. 사용자 피드백(2026-10-04) 뒤 규칙이 둘 생겼습니다. ① 동시에 도는 작업이 없으면 워크트리 없이 메인 체크아웃에서 한다. ② 병렬이 필요하면 고정 레인 lane-a/b/c를 재사용해 빌드 폴더·쿠킹 캐시를 남긴다. 덧붙여 큰 작업은 진단 결과를 먼저 짧게 보고한 뒤 고치고, 성능 3회 측정은 마지막 확인 때만 합니다. 도구의 속도도 방법론의 일부입니다.
    워크트리마다 뜨는 방화벽 확인 창 Windows 방화벽은 0.0.0.0에 바인드하는 프로그램을 실행 파일 경로마다 처음 한 번 묻습니다. 워크트리마다 exe 경로가 다르니, 네트워크 테스트나 멀티플레이 검증을 돌릴 때마다 확인 창이 떴습니다(2026-10-04 사용자 보고). 해결: 자동 검증 실행과 그 자식 프로세스는 루프백(127.0.0.1) 전용으로 대기하고 LAN 알림을 하지 않으며(NetBindPolicy), 실제 소켓을 여는 단위 테스트는 E_TEST_SOCKETS=1일 때만 돕니다. 사람이 직접 띄운 서버만 모든 주소에서 대기합니다.
    규칙: 링크로 공유하지 말고 설정으로 공유한다 워크트리마다 서드파티 소스(수백 MB)를 다시 받지 않으려고 Build/_deps를 정션(디렉터리 링크)으로 잇고 싶어집니다. 하지만 워크트리를 지울 때 링크 너머의 메인 소스까지 지워질 수 있습니다. 그래서 공유는 gitignore된 CMakeLocal.cmake의 set(E_THIRDPARTY_SOURCE_CACHE ...)로만 하고, 워크트리를 지우기 전에 정션이 없는지 확인합니다.

    함정과 교훈전 과정에서 반복된 것들

    • 재지 않은 직관은 자주 틀린다: 글꼴이 느린 이유는 SDF가 아니라 파일 읽기였고(60강), 실내 그림자가 형편없다는 보고의 원인은 직접광 그림자가 아니라 간접광 가림 부재였습니다(26강 RTAO). 고치기 전에 원인을 숫자로 확인합니다.
    • "끈 상태 = 예전"을 지키면 실험이 싸진다: 모든 새 효과에 끄는 스위치와 비트 동일 보장이 있으면, 문제가 생겨도 기본값만 바꿔 되돌릴 수 있습니다.
    • 경고를 끄지 말고 원인을 고친다: /W4 /WX, 디버그 레이어 0건, 라이브 객체 0. 기준을 낮추면 진짜 문제가 소음에 묻힙니다(1강).
    • 순수 로직을 떼어 테스트한다: 창·GPU·장치·소켓에 붙은 코드에서 규칙만 분리하면 테스트가 가능해지고, 규칙은 머리 주석 + 테스트로 고정됩니다.
    • 사람이 확인할 것은 남겨 둔다: 자동화가 덮지 못하는 범위를 정직하게 적는 것이 "다 됐다"는 착각을 막습니다.

    • 자동 화면 검증 = 숨긴 창으로 N프레임 실행 → 스크린샷 + 로그 → 디버그 레이어 오류 0건 확인. 스크린샷은 직접 본다.
    • 셰이더 핵심 식은 C++ XxxMath.h에 같은 모양으로 두고 단위 테스트한다. 바꾸면 둘을 함께, 테스트도 함께.
    • 결정성(--fixed-delta, FFrameTime, 결정적 로딩·순서·난수)이 있으면 회귀를 MD5로 비교할 수 있고, 결정성이 깨지는 것 자체가 버그 신호다.
    • 국소 깜빡임은 시간 표준편차 지도와 블록 지표로, 성능은 규모별 추세(×1.25 규칙)로 잰다.
    • Plans.md는 DoD·측정·한계·사용자 확인 항목을, CLAUDE.md는 버그에서 나온 규칙을 기록한다. 병렬 작업은 범위를 정한 브랜치와 재사용 워크트리로 한다.

    생각해 볼 문제

    Q1. 새 화면 효과를 추가했더니 효과를 끈 상태의 스크린샷 MD5가 도입 전과 달라졌습니다. 무엇을 의심해야 할까요? 효과가 "꺼져 있어도" 다른 경로에 영향을 준다는 뜻입니다. 흔한 원인: 공용 셰이더 헤더나 상수 버퍼 배치를 바꿔 기존 패스의 계산 순서가 달라짐, 렌더 그래프에 패스가 끼어 리소스 상태·순서가 바뀜, 프레임 시간을 실제 시각으로 읽는 새 코드가 결정성을 깨뜨림. 먼저 같은 빌드를 두 번 돌려 MD5가 같은지(결정성)부터 확인하고, 같다면 끈 상태의 경로 차이를 찾습니다.
    Q2. 셰이더에 새 감쇠 식을 넣고 화면도 그럴듯해 보입니다. C++ 쪽에 같은 식과 테스트를 두지 않으면 어떤 위험이 남을까요? 경계값(거리 0, 반경 바깥), 단조성, 극한(반경 무한대) 같은 성질이 틀려도 특정 장면에서는 눈에 띄지 않을 수 있습니다. 또 CPU가 같은 식을 써야 하는 곳(컬링 경계, 클러스터 배정 등)이 셰이더와 어긋나면 "가끔 빛이 잘리는" 버그가 됩니다. 같은 모양의 C++ 식 + 테스트는 이 두 가지를 모두 막습니다.
    Q3. 성능 최적화를 측정하는 동안 다른 터미널에서 빌드를 돌렸더니 ScaleBench가 "비선형"을 보고했습니다. 결과를 믿어도 될까요? 믿으면 안 됩니다. 빌드가 CPU를 나눠 쓰면 특정 규모 측정만 느려져 배율이 튀고, 비선형 판정(개수 배율 × 1.25 초과)이 거짓으로 나올 수 있습니다. 스크립트와 CLAUDE.md 모두 "측정 중 다른 빌드/Verify를 돌리지 않는다"를 규칙으로 둔 이유입니다. 조용한 상태에서 다시 잽니다.
