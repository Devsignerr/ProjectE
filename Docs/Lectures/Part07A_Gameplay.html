    세계의 규칙 — 게임플레이 시스템 (전반)

    화면을 그리는 엔진이 "게임"이 되려면 세계에 규칙이 있어야 합니다. 물체가 떨어지고 부딪히는 물리, 사람처럼 걷는 캐릭터, 디자이너가 쓰는 스크립트, 키를 의도로 바꾸는 입력, 스스로 판단하고 길을 찾는 AI — 다섯 시스템을 외부 라이브러리와의 경계 설계부터 차례로 봅니다.

    물리 엔진 통합

    이 강의를 마치면

    • 외부 물리 엔진(Jolt)을 붙일 때 단위·축·회전 변환을 "경계 한 곳"에 가두는 설계를 이해합니다.
    • 충돌 이벤트를 물리 콜백 안에서 게임 코드로 바로 부르면 안 되는 이유를 압니다.
    • 충돌 레이어 행렬이 Jolt의 오브젝트 레이어 비트로 어떻게 표현되는지, 관절과 래그돌이 어떻게 만들어지는지 압니다.

    왜 필요한가"떨어지고, 부딪히고, 구르는" 세계

    지금까지의 씬은 물체가 스스로 움직이지 않았습니다. 트랜스폼은 누군가(에디터, 애니메이션, 스크립트)가 값을 써 줄 때만 바뀌었습니다. 하지만 게임 세계에서는 상자를 밀면 넘어지고, 공을 던지면 포물선을 그리며 떨어져 바닥을 구르다 멈춰야 합니다. 이것을 스크립트로 일일이 계산하면 두 물체까지는 어떻게든 되지만, 상자 50개가 서로 기대어 쌓인 더미가 무너지는 장면은 불가능합니다.

    물리 엔진은 이 계산을 대신해 주는 라이브러리입니다. 물체마다 질량·모양·속도를 주면, 매 스텝마다 힘을 적용해 속도를 바꾸고, 겹친 물체들을 찾아 밀어내고, 그 결과로 위치를 갱신합니다. ProjectE는 0강에서 본 기준("표준 해법이 있고 그 자체로 거대한 분야")에 따라 Jolt Physics를 쓰기로 했습니다. 대신 엔진과 맞닿는 경계 — 단위, 컴포넌트, 시간 진행, 이벤트 전달 — 는 직접 설계합니다. 이 강의는 그 경계 이야기입니다.

    핵심 개념강체 시뮬레이션 한 스텝

    강체(rigid body)는 "모양이 절대 변하지 않는 물체"라는 가정입니다. 이 가정 덕분에 물체의 상태를 위치·회전(자세)·선속도·각속도 네 가지로만 표현할 수 있습니다. 물리 엔진의 한 스텝은 대략 다음 순서로 진행됩니다.

    1. 힘 적분: 중력과 외부 힘으로 속도를 바꿉니다. v += (F / m) · Δt
    2. 충돌 검출: 먼저 경계 상자로 "겹칠 가능성이 있는 쌍"을 빠르게 추리고(브로드페이즈), 그 쌍만 정확한 모양으로 접촉점·법선·침투 깊이를 구합니다(내로페이즈).
    3. 구속 풀기(solver): 접촉(서로 파고들지 않기), 마찰, 관절 같은 조건을 만족하도록 속도를 반복적으로 보정합니다.
    4. 위치 적분: 보정된 속도로 위치와 회전을 옮깁니다. x += v · Δt

    여기서 Δt(스텝 시간)가 중요합니다. 적분은 "짧은 시간 동안 속도가 일정하다"는 근사이므로, Δt가 크면 오차가 커지고 빠른 물체가 얇은 벽을 건너뛰기도 합니다. 그리고 Δt가 매번 다르면 같은 장면이 실행할 때마다 다르게 굴러갑니다. 그래서 물리는 항상 같은 간격으로 진행하는 것이 원칙입니다.

    핵심 개념경계에서만 변환한다: cm ↔ m, 쿼터니언은 그대로

    ProjectE는 1단위 = 1cm(4강)이지만 Jolt는 미터 단위로 튜닝되어 있습니다. 허용 오차, 잠들기 문턱, 기본 중력이 모두 미터 기준이라, cm 값을 그대로 넘기면 Jolt 입장에서는 "100배 큰 세계"가 되어 물체가 둔하게 움직이거나 잘 잠들지 못합니다. 그래서 변환이 필요한데, 핵심 규칙은 하나입니다. 변환은 FPhysicsWorld 경계에서만 한다.

    namespace PhysicsMath
{
	// 엔진은 cm, Jolt는 m. 축은 그대로 쓴다 (둘 다 좌표 축에 손 방향을 강제하지 않으며, 엔진 FQuat도
	// 해밀턴 곱 + v' = q v q* 규약이라 Jolt Quat와 성분이 1:1로 같다 — PhysicsTests에서 회전 결과로 검증).
	// 중력만 엔진 위(+Z) 기준으로 -Z로 준다.
	inline FVector3 ToMeters(const FVector3& Centimeters) { return Centimeters * FUnits::UnitsToMeters; }
	inline FVector3 ToCentimeters(const FVector3& Meters) { return Meters * FUnits::MetersToUnits; }
}

    흥미로운 점은 축과 회전은 변환하지 않는다는 것입니다. 왼손 좌표계 엔진과 오른손 좌표계 라이브러리를 이을 때는 보통 축 하나를 뒤집어야 합니다(49강의 Recast가 그런 예입니다). 그런데 물리 엔진의 계산 — 벡터 덧셈, 외적, 쿼터니언 곱 — 은 "어느 손으로 축을 그렸는가"를 따지지 않습니다. 손 방향이 의미를 갖는 것은 화면에 투영하거나 삼각형 앞면을 정할 때뿐입니다. 그래서 Jolt에게 "+Z가 위인 세계"라고만 알려 주면(중력을 -Z로) 성분을 그대로 넘겨도 됩니다. 단, 이것은 가정이므로 PhysicsTests가 엔진 FQuat와 Jolt의 회전 결과를 직접 비교해 고정해 둡니다.

    "가정"은 테스트로 고정한다 "성분이 1:1로 같다"는 주장은 엔진 쿼터니언의 곱셈 순서 규약(4강의 A * B는 B 먼저)이 바뀌는 순간 조용히 깨집니다. 주석으로만 적어 두면 아무도 모르게 틀어지므로, 실제 회전 결과를 비교하는 테스트로 묶어 둡니다. 경계 설계에서 가장 값싼 보험입니다.

    핵심 개념고정 스텝과 렌더 보간

    게임 프레임은 들쭉날쭉합니다. 12ms, 18ms, 15ms… 반면 물리는 항상 1/60초씩 가고 싶습니다. 둘을 잇는 방법이 누적기(accumulator)입니다. 프레임 시간을 통에 붓고, 통에 1/60초 이상 차 있는 동안 스텝을 하나씩 꺼내 진행합니다. 남은 찌꺼기는 다음 프레임으로 넘어갑니다.

    struct FFixedStepper
{
	float  StepSeconds = 1.0f / 60.0f;
	uint32 MaxSteps    = 4;
	float  Accumulator = 0.0f;

	uint32 Advance(float DeltaSeconds)
	{
		Accumulator += std::max(DeltaSeconds, 0.0f);
		uint32 Steps = 0;
		while (Accumulator >= StepSeconds && Steps < MaxSteps)
		{
			Accumulator -= StepSeconds;
			++Steps;
		}
		if (Steps == MaxSteps && Accumulator >= StepSeconds)
		{
			Accumulator = 0.0f; // 따라잡지 못한 시간은 버린다 (시뮬레이션이 느려질 뿐 폭주하지 않음)
		}
		return Steps;
	}
	float GetAlpha() const { return std::clamp(Accumulator / StepSeconds, 0.0f, 1.0f); }
};

    MaxSteps가 왜 필요할까요? 한 프레임이 매우 느렸다고 해 봅시다(로딩 끊김 200ms). 그러면 12스텝을 몰아서 돌려야 하는데, 그 12스텝 자체가 또 프레임을 느리게 만들고, 다음 프레임엔 더 많은 스텝이 쌓입니다. 이 악순환을 죽음의 나선(spiral of death)이라 부릅니다. 상한을 넘은 시간은 과감히 버립니다. 그 순간 게임이 살짝 슬로모션이 될 뿐 멈추지는 않습니다. 스텝 주파수와 상한은 프로젝트 설정 Physics의 FixedStepHz(기본 60)와 MaxSubSteps(기본 4)이고, FPhysicsSystem::Begin이 플레이 시작 때 읽습니다.

    보간은 WriteDynamicTransforms가 합니다. 동적 바디마다 직전 스텝과 현재 스텝의 위치·회전을 보관해 두었다가 Lerp/Slerp로 섞어 트랜스폼에 씁니다. 전용 서버는 SetInterpolation(false)로 보간을 끕니다 — 복제해서 보낼 값에 "화면용으로 섞인 값"이 들어가면 안 되기 때문입니다.

    질량은 밀도로, 구르기 저항은 직접

    질량을 지정하지 않으면(Mass = 0, 기본) 콜라이더 부피 × Density(기본 500kg/m³ — 대략 나무)로 계산합니다. 그래서 같은 재질이면 큰 상자가 자동으로 더 무겁습니다. 값을 넣으면 그 질량을 직접 씁니다.

    구르기 저항(rolling resistance)은 Jolt에 없는 기능이라 엔진이 만들었습니다. 현실의 공은 바닥과 공이 조금씩 찌그러지면서 에너지를 잃어 결국 멈추는데, 강체는 찌그러지지 않으므로 마찰만으로는 영원히 굴러갑니다. FPhysicsWorld::Step은 스텝이 끝난 뒤, 이번 스텝에 무언가와 접촉한 동적 바디의 각속도만 일정량 줄입니다(공중에서 도는 물체는 건드리지 않음).

    // 구르기 저항 계수 → 각감속 배율. 회전만 줄이면 마찰이 선속도를 끌어내리는데, 속이 찬 구(I = 2/5 m r²)의
// 선감속이 계수 × g가 되려면 각감속을 (I + m r²) / I = 3.5배로 줘야 한다
constexpr float RollingCouplingFactor = 3.5f;
...
const float Deceleration = Rolling.Coefficient * Gravity * RollingCouplingFactor / Rolling.Radius; // rad/s²
const float NewSpeed     = std::max(Speed - Deceleration * DeltaSeconds, 0.0f);
Bodies.SetAngularVelocity(Id, Angular * (NewSpeed / Speed));

    "이번 스텝에 접촉했는가"는 Jolt 접촉 리스너가 기록합니다. 그런데 이 콜백은 Jolt의 작업 스레드 여러 개에서 동시에 불립니다. 그래서 바디 인덱스마다 원자 변수(std::atomic<uint32>)에 "마지막으로 접촉한 스텝 번호"를 쓰는 방식으로 잠금 없이 기록합니다. 이 "콜백은 다른 스레드에서 온다"는 사실이 다음 절의 핵심입니다.

    핵심 개념충돌 이벤트: 콜백에서 게임 코드를 부르지 않는다

    게임은 "총알이 벽에 닿았다", "플레이어가 문 앞 영역에 들어왔다"를 알고 싶어 합니다. Jolt는 접촉이 생기거나(OnContactAdded) 사라질 때(OnContactRemoved) 콜백을 불러 줍니다. 가장 쉬운 구현은 그 콜백 안에서 바로 Lua의 OnCollisionBegin을 부르는 것이지만, ProjectE는 이것을 규칙으로 금지합니다.

    • 스레드: 콜백은 Jolt 작업 스레드에서 동시에 옵니다. Lua 상태와 ECS는 메인 스레드 전용입니다.
    • 재진입: 콜백 시점은 Jolt가 스텝을 계산하는 도중입니다. 게임 코드가 거기서 엔티티를 지우거나 바디를 새로 만들면 Jolt 내부 자료구조를 계산 중에 건드리게 됩니다.
    • 순서: 콜백 순서는 스레드 스케줄에 따라 매번 다릅니다. 게임 로직이 실행마다 다른 순서로 불리면 재현할 수 없는 버그가 생깁니다.

    모든 바디의 접촉을 기록하면 비용이 큽니다. 그래서 보고 대상을 정합니다: 트리거, 강체의 bReportContacts, 스크립트가 붙은 엔티티, 게임 모듈이 WantsCollisionEvents로 원한 엔티티. 쌍의 한쪽이라도 보고 대상이 아니면 콜백 첫 줄에서 바로 버립니다.

    트리거(콜라이더 bIsTrigger)는 부딪히지 않고 "들어왔다/나갔다"만 알리는 영역입니다. Jolt의 센서로 만드는데, 한 가지 함정이 있습니다. 정적 센서는 상대 물체가 잠들면(sleep) 접촉을 잃습니다. 그래서 운동 형식과 상관없이 잠들지 않는 키네마틱 센서로 만들고, 전용 Trigger 레이어에 두어 레이캐스트에서 빼고(문 앞 영역이 총알을 막으면 안 되니까) 정적 바닥과는 겹침 계산조차 하지 않게 합니다.

    핵심 개념충돌 레이어 행렬과 ObjectLayers::Make

    "플레이어끼리는 통과하지만 벽에는 막힌다", "탄피는 바닥과만 부딪힌다" 같은 규칙이 필요합니다. ProjectE는 유니티 방식을 골랐습니다(Phase 43, 사용자 결정): 콜라이더마다 레이어 이름 하나, 프로젝트 설정에 레이어 × 레이어 충돌 표 하나. 최대 16칸이고 0번은 Default로 고정입니다.

    Jolt에는 이미 "오브젝트 레이어"라는 정수가 있고, 두 레이어가 부딪힐지를 묻는 필터를 엔진이 구현해 넘깁니다. 문제는 Jolt 레이어가 이미 다른 용도 — "정적인가, 움직이는가, 트리거인가" — 로 쓰이고 있었다는 것입니다. 둘을 한 정수에 담기 위해 비트를 나눕니다.

    namespace ObjectLayers
{
	constexpr JPH::ObjectLayer NonMoving = 0;
	constexpr JPH::ObjectLayer Moving    = 1;
	constexpr JPH::ObjectLayer Trigger   = 2;
	constexpr uint32           KindBits  = 2;

	constexpr JPH::ObjectLayer Make(JPH::ObjectLayer Kind, uint32 CollisionLayer)
	{
		return static_cast<JPH::ObjectLayer>(Kind | ((CollisionLayer % FCollisionLayerSettings::MaxLayers) << KindBits));
	}
}
...
bool ShouldCollide(JPH::ObjectLayer A, JPH::ObjectLayer B) const override
{
	// 트리거 ↔ 움직이는 것만, 그 밖은 한쪽 이상이 움직이는 것
	if (KindOf(A) != ObjectLayers::Moving && KindOf(B) != ObjectLayers::Moving) { return false; }
	return ((Matrix[CollisionLayerOf(A)] >> CollisionLayerOf(B)) & 1u) != 0;
}

    행렬은 줄마다 16비트(uint16) 하나입니다. 줄 i의 비트 j가 "i와 j가 부딪힌다"이고, 대칭이므로 설정 창은 유니티처럼 삼각형으로 보여 줍니다. 이 필터 하나가 바디끼리, 캐릭터 이동 질의(46강), 캐릭터 내부 바디, 트리거 알림 모두에 쓰이므로 "레이어를 끄면 모든 곳에서 꺼진다"가 보장됩니다.

    컴포넌트에는 레이어 번호가 아니라 이름을 저장합니다. 설정에서 칸 순서를 바꿔도 씬이 깨지지 않게 하기 위해서입니다. 비었거나 없는 이름은 Default로 처리하고(없는 이름은 경고 한 번), 레이캐스트는 이름 목록 → 마스크(MakeMask)로 거릅니다: Lua Physics.Raycast(o, d, dist, {"Ground"}).

    ProjectE에서는관절과 래그돌

    관절(joint, constraint)은 두 바디 사이의 상대 운동을 제한하는 조건입니다. 솔버는 접촉과 똑같이 이 조건을 만족하도록 속도를 보정합니다. ProjectE는 네 종류를 컴포넌트로 제공합니다.

    컴포넌트남기는 자유도예
    FixedJointComponent없음 (용접)부서질 수 있는 판(BreakForce)
    HingeJointComponent축 하나 회전 (+제한·모터·마찰)문, 풍차
    DistanceJointComponent거리 범위 안 (+스프링)사슬, 스프링
    BallJointComponent원뿔 안 흔들림 + 비틀림매달린 추

    모두 Target(비면 월드)과 Anchor를 가지며, FPhysicsSystem::SyncJoints가 바디 동기화 뒤에 만듭니다. 관절은 두 바디를 가리키므로, 바디를 지우기 전에 관절을 먼저 지워야 합니다(FPhysicsWorld만 관절을 소유). BreakForce가 있으면 스텝마다 구속 힘(N)을 재서 넘으면 관절을 지우고 OnJointBreak(other, force)를 보냅니다. 관절로 이은 두 바디는 보통 서로 충돌하면 안 되므로(겹쳐 있으니 계속 튕겨 나감) 충돌 그룹으로 쌍을 끕니다.

    래그돌(ragdoll)은 캐릭터가 죽었을 때 애니메이션 대신 물리로 쓰러지게 하는 연출입니다. 스켈레탈 모델 루트에 FRagdollComponent를 달면, 켤 때 순수 함수 RagdollMath::BuildLayout이 뼈마다 "뼈 시작 → 자식 뼈들 평균 위치" 캡슐을 만들고(짧은 뼈는 부모 캡슐에 합침), 부모 캡슐과 SwingTwist 관절로 잇습니다. SwingTwist는 "원뿔 안에서 흔들리고(swing), 뼈 축으로는 제한된 각도만 비틀리는(twist)" 관절로, 사람 어깨·목처럼 동작합니다. 기본값은 흔들림 45°, 비틀림 ±30°입니다.

    래그돌은 애니메이션 시스템(Scene 모듈)과 물리(Physics 모듈)가 같은 뼈를 두고 싸우지 않게 하는 것이 핵심입니다. 플래그 하나 FAnimationRuntime::bPhysicsPose로 소유권을 넘깁니다. 켜져 있으면 애니메이션은 그 모델을 건너뛰고, 물리 갱신이 캡슐 자세를 뼈 엔티티 로컬 트랜스폼으로 씁니다. 사망 연동(World/GameWorldRagdoll.cpp)은 복제된 체력을 보고 서버·클라이언트가 각자 켭니다 — 래그돌 자세 자체는 복제하지 않는 로컬 연출입니다.

    함정과 교훈"물리가 이상하다"의 진짜 원인

    실제로 겪은 일 1 — 굴러가던 공이 0.5초 만에 멈춘다 (Phase 8) 사용자 보고는 "물체끼리 부딪혀도 자연스럽게 상호작용하지 않고 어색하게 밀려난다"였습니다. 실험해 보니 500cm/s로 굴린 공이 0.5초 만에 멈췄고, 3초 동안 바디가 79번 다시 생성되고 있었습니다. 원인은 "모양이 바뀌었으면 바디를 다시 만든다"는 검사였습니다. 회전하는 물체의 월드 행렬을 분해하면 스케일이 수 ULP(부동소수점 최소 단위)씩 흔들리는데, 이 값을 비트 해시로 비교했으니 매 프레임 "모양이 바뀌었다"고 판단해 바디를 새로 만들었고, 그때마다 속도가 0으로 초기화됐습니다. 수정: 생성 설정(CreatedDesc)을 보관하고, 컴포넌트 값은 정확히, 스케일에서 나온 치수만 상대 오차 1e-4로 비교(NeedsRecreate). 테스트 Physics_RollingSphereKeepsMomentum으로 고정했습니다.
    실제로 겪은 일 2 — 솔버는 정상, 숫자가 비정상 같은 조사에서 쌓기 안정성(3초 이동 0cm), 비탄성 충돌, 마찰 감속(이론 208cm / 실측 209cm)은 모두 정상이었습니다. 문제는 설정 값이었습니다. 질량이 크기와 무관하게 기본 1kg이라 60cm 상자 5kg은 밀도 23kg/m³ — 스티로폼 수준인데, 거기에 8kg 공을 22m/s로 던졌으니 상자 더미가 4.8m 날아갔습니다. 또 구르기 저항이 없어 공이 10초 뒤에도 130cm/s로 굴렀습니다. 그래서 밀도 기반 질량과 구르기 저항을 넣었고, 공 300cm/s가 4.2m 구르고 멈추게 됐습니다. 교훈: "물리가 이상하다"는 보고를 받으면 솔버를 의심하기 전에 단위와 질량부터 봅니다.

    정리
    • 강체 한 스텝 = 힘 적분 → 충돌 검출(브로드/내로페이즈) → 구속 풀기 → 위치 적분. Δt는 일정해야 한다.
    • 누적기로 고정 스텝(기본 60Hz, 최대 4스텝)을 돌리고, 화면에는 직전·현재 스텝을 α로 보간해 그린다.
    • 단위 변환은 FPhysicsWorld 한 곳. 바디 핸들은 컴포넌트가 아니라 FPhysicsSystem이 든다.
    • 충돌 콜백은 작업 스레드에서 기록만, 정리·전달은 메인 스레드가 정해진 단계에서.
    • Jolt 오브젝트 레이어 = 종류(하위 2비트) | 충돌 레이어 칸 << 2. 종류 규칙 → 행렬 순으로 판정.
    • 래그돌 = 뼈마다 캡슐 + SwingTwist 관절, bPhysicsPose로 애니메이션과 소유권을 나눈다.

    생각해 볼 문제

    Q1. 물리를 프레임 시간 그대로(가변 Δt) 한 번씩 돌리면 어떤 문제가 생길까요? 두 가지 이상 들어 보세요. ① 프레임이 느릴 때 Δt가 커져 빠른 물체가 얇은 벽을 건너뛰거나(터널링) 쌓인 상자가 튀는 등 적분 오차가 커집니다. ② 같은 입력이라도 PC 성능·부하에 따라 Δt 열이 달라 결과가 매번 다릅니다(재현 불가, 네트워크 예측 불가). ③ 스프링·관절처럼 Δt에 민감한 구속은 큰 Δt에서 발산할 수 있습니다. 고정 스텝은 이 셋을 한 번에 해결하고, 남는 "화면이 계단처럼 움직이는" 문제는 보간으로 해결합니다.
    Q2. 충돌 레이어를 Jolt 레이어 번호 하나에 담지 않고, "종류"는 따로 두고 레이어 행렬만 엔진에서 보면 안 될까요? 왜 비트를 합쳤을까요? Jolt의 필터 인터페이스(ObjectLayerPairFilter::ShouldCollide)가 받는 정보는 두 바디의 오브젝트 레이어 정수뿐입니다. 바디 ID나 엔티티를 보고 판정하면 쌍마다 조회가 필요해 느리고, 브로드페이즈 단계에서 걸러 내지도 못합니다. 종류와 칸을 한 정수에 담으면 필터가 비트 연산 두세 번으로 끝나고, 칸 0일 때 예전 번호와 같아 기존 씬·지형이 바뀌지 않는 덤도 얻습니다.
    Q3. 트리거 안에 들어온 물체가 잠들었더니 OnTriggerExit도 안 오고, 다시 움직여도 Enter가 오지 않았습니다. 무엇을 의심해야 할까요? 정적 센서는 상대가 잠들면 접촉을 잃는다는 Jolt의 동작입니다. ProjectE는 그래서 트리거를 운동 형식과 무관하게 "잠들지 않는 키네마틱 센서"로 만듭니다. 또 잠들면서 생기는 "접촉 제거"를 곧바로 끝으로 보지 않고, 깨어난 뒤 온전한 스텝 하나 동안 접촉이 없을 때만 끝으로 정리합니다(Phase 30-1). 직접 센서를 만드는 코드가 있다면 이 두 규칙을 지키는지 확인합니다.

    왜 필요한가사람은 상자처럼 움직이지 않는다

    45강의 강체로 플레이어를 만들어 봅시다. 캡슐 모양 동적 바디에 회전을 잠그고(넘어지지 않게), W를 누르면 앞으로 속도를 주고, 스페이스를 누르면 위로 속도를 줍니다. ProjectE도 처음(Phase 21)에는 정확히 이렇게 만들었습니다 — "동적 강체 캡슐(회전 고정) + 수평 속도 지정 + 바닥 레이캐스트 후 점프". 동작은 합니다. 하지만 곧 문제가 드러납니다.

    • 계단: 캡슐 아래쪽 둥근 면이 계단 모서리에 걸려 멈추거나 튕깁니다. 물리적으로는 맞는 결과지만 게임에서 원하는 것은 "그냥 올라가기"입니다.
    • 경사: 마찰 때문에 내리막에서 미끄러지거나, 급경사를 속도로 밀고 올라가 버립니다. "몇 도까지는 걸을 수 있다"는 규칙을 표현할 방법이 없습니다.
    • 밀림: 굴러오는 상자에 맞으면 캐릭터가 밀려납니다. 질량을 키우면 이번엔 캐릭터가 상자를 대포처럼 날립니다.
    • 내리막 점프: 내리막을 달리면 속도가 수평이라 발이 땅에서 떨어져 "통통" 튑니다.
    • 되감기 불가: 네트워크 예측(57강)은 "과거 상태로 되돌려 입력을 다시 적용"해야 하는데, 물리 월드 전체를 되감을 수는 없습니다.

    그래서 게임 엔진은 플레이어를 강체가 아니라 캐릭터 컨트롤러(character controller)로 움직입니다. 언리얼의 CharacterMovementComponent, 유니티의 CharacterController가 그것이고, ProjectE에서는 FCharacterMovementComponent입니다(Phase 22).

    핵심 개념시뮬레이션되지 않는 캡슐 — "쿼리로 움직이기"

    캐릭터 컨트롤러의 핵심 아이디어는 캐릭터는 물리 시뮬레이션에 참여하지 않는다는 것입니다. 캐릭터는 힘을 받지도, 솔버가 밀어내지도 않습니다. 대신 매번 "이 속도로 이만큼 가고 싶다"를 정한 다음, 캡슐 모양을 그 방향으로 쓸어 보면서(shape cast) 어디서 막히는지 물어보고(query), 막힌 면을 따라 남은 이동을 미끄러뜨립니다. 이것을 흔히 collide-and-slide라고 부릅니다.

    Jolt에는 이 방식의 구현인 CharacterVirtual이 있습니다. 이름의 "Virtual"은 물리 월드에 실제 바디로 존재하지 않는다는 뜻입니다. 이 성질이 결정적으로 중요합니다. 캐릭터의 상태가 "위치 + 속도 + 바닥 여부"뿐이고, 나머지 세계는 질의로 읽기만 하므로 상태를 저장했다가 되돌리고 다시 돌리는 것이 쉽습니다. 강체로는 불가능했던 네트워크 예측의 재조정(57강)이 여기서 가능해집니다.

    그런데 시뮬레이션에 없는 캡슐은 다른 물체 입장에서 보이지 않습니다. 굴러오는 공이 캐릭터를 통과해 버리겠죠. 그래서 캐릭터를 따라다니는 내부 키네마틱 바디(inner body)를 함께 둡니다. 다른 물체는 이 바디와 부딪히고, 트리거도 이 바디로 캐릭터를 감지합니다.

    // Jolt 캡슐은 +Y 축 → 엔진 +Z 축 (CreateShape와 같은 회전)
JPH::RefConst<JPH::Shape> Capsule = new JPH::CapsuleShape(Half, Radius);
...
Settings->mShape          = Shape;
Settings->mInnerBodyShape = Shape; // 다른 캐릭터/동적 물체가 이 캐릭터와 부딪히게
Settings->mInnerBodyLayer = Layer; // 다른 물체가 이 캐릭터와 부딪히는지도 행렬을 따른다
Settings->mUp             = JPH::Vec3::sAxisZ();
// 아래 반구의 중심보다 낮은 접촉만 "발밑"으로 본다 (위치 = 캡슐 중심)
Settings->mSupportingVolume = JPH::Plane(JPH::Vec3::sAxisZ(), Half);
Settings->mMaxSlopeAngle    = FMath::DegreesToRadians(std::clamp(Desc.MaxSlopeDegrees, 0.0f, 89.0f));
Settings->mMaxStrength      = std::max(Desc.MaxStrength, 0.0f); // 동적 물체를 미는 최대 힘 (N)

    Jolt의 new가 보이는데, 이는 Jolt의 참조 계수 객체(Ref)가 요구하는 생성 방식이고 소유는 Ref가 합니다. 엔진 코드 규칙의 "raw new 금지"는 엔진이 직접 소유하는 객체에 대한 것입니다.

    mSupportingVolume은 "어떤 접촉을 발밑으로 칠까"입니다. 캡슐 중심에서 원기둥 절반 높이 아래, 즉 아래쪽 반구의 중심보다 낮은 접촉만 바닥으로 봅니다. 그래야 벽에 옆구리가 닿은 것을 "바닥에 서 있다"로 착각하지 않습니다. 실제 이동은 ExtendedUpdate가 하는데, 계단 오르기 높이(mWalkStairsStepUp)와 바닥 붙이기 깊이(mStickToFloorStepDown)를 함께 넘깁니다. ProjectE는 두 값 모두 컴포넌트의 MaxStepHeight(기본 35cm)를 쓰되, 바닥 붙이기는 바닥에서 걷는 중이고 점프하지 않았을 때만 켭니다. 점프하는 순간 바닥으로 당기면 점프가 씹히니까요.

    핵심 개념속도 규칙은 순수 함수로

    "이번 무브에 어떤 속도로 가고 싶은가"는 Jolt와 무관한 순수한 규칙입니다. ProjectE는 이것을 CharacterMovementMath::ComputeVelocity라는 순수 함수로 떼어 냈습니다. 순수 함수는 입력이 같으면 출력이 같고 전역 상태를 건드리지 않으므로, 물리 월드 없이 단위 테스트할 수 있고 서버와 클라이언트가 똑같이 계산한다는 것이 보장됩니다.

    const FVector2 Input = ClampInput(Move.Input); // 길이 1로 자름 (대각선이 빠르지 않게)
const FVector2 Desired(Input.X * Movement.MaxWalkSpeed, Input.Y * Movement.MaxWalkSpeed);
if (bGrounded)
{
	Velocity.X = Desired.X;
	Velocity.Y = Desired.Y;
	Velocity.Z = 0.0f;
	if (Move.bJump)
	{
		Velocity.Z = Movement.JumpZVelocity;
		bOutJumped = true;
	}
}
else
{
	// 공중: 초당 (AirControl × 최대 속도 × 4)까지 입력 쪽으로 가속 — AirControl 1이면 0.25초에 최고 속도 방향 전환
	const float MaxDelta = std::clamp(Movement.AirControl, 0.0f, 1.0f) * Movement.MaxWalkSpeed * 4.0f * DeltaSeconds;
	FVector2    Delta(Desired.X - Velocity.X, Desired.Y - Velocity.Y);
	... // Delta 길이를 MaxDelta로 자른다
	Velocity.X += Delta.X;
	Velocity.Y += Delta.Y;
}
Velocity.Z += GravityZ * Movement.GravityScale * DeltaSeconds;

    몇 가지 짚어 볼 점이 있습니다.

    • 바닥에서는 가속·마찰 단계가 없습니다. 언리얼의 캐릭터 이동은 가속도와 제동 마찰로 속도가 서서히 붙고 줄어들지만, 현재 ProjectE의 규칙은 "바닥이면 입력 × 최대 속도"로 즉시 정합니다. 반응이 아주 빠른 대신 관성이 없습니다. 관성 있는 출발·정지가 필요하면 이 순수 함수에 가속/제동 항을 넣고 CharacterMovementTests를 함께 고치면 됩니다(CLAUDE.md 규칙).
    • 공중 제어(air control)는 실제 물리에는 없는 게임적 허용입니다. 0이면 점프한 순간 궤적이 고정되고, 1이면 0.25초 만에 방향을 완전히 바꿉니다. 기본 0.35는 그 사이의 타협입니다.
    • 점프 높이는 공식으로 예측됩니다. 위쪽 속도 v로 뛰면 최고점은 v² / 2g입니다. 기본 520cm/s, g = 980.665cm/s²이면 520² / (2 × 980.665) ≈ 138cm — Phase 22 테스트에 기록된 "점프 높이 ≈138cm"와 일치합니다.
    • dt 상한: 무브 dt는 0~0.1초로 자릅니다(MaxMoveDeltaSeconds). 느린 프레임 하나로 캐릭터가 벽을 뚫거나, 네트워크로 조작된 큰 dt를 서버가 받아들이지 않게 하기 위해서입니다.

    ProjectE에서는"무브" — 같은 무브는 같은 결과

    Phase 22의 가장 중요한 결정은 이동을 무브(move)라는 작은 값 묶음 단위로 진행한다는 것입니다. 한 프레임의 입력이 무브 하나가 됩니다.

    // 무브 하나 = 한 프레임 입력 (네트워크로 보내고 다시 적용하는 단위). 같은 무브 → 같은 결과
struct FCharacterMove
{
	uint32   Sequence     = 0;     // 소유 클라이언트가 붙이는 순번 (재조정 기준)
	float    DeltaSeconds = 0.0f;  // 0~MaxMoveDeltaSeconds로 잘라 적용
	FVector2 Input;                // 월드 XY 이동 방향 (길이 ≤ 1)
	float    Yaw   = 0.0f;         // 도 (bFaceControlYaw일 때 몸 방향)
	bool     bJump = false;        // 바닥에 있으면 점프
	bool     bRootMotion = false;  // 루트 모션 무브: Input 대신 RootMotionVelocity로 이동
	FVector2 RootMotionVelocity;   // 월드 XY cm/s
};

    "같은 무브 → 같은 결과"가 왜 그렇게 중요할까요? 원격 클라이언트는 키를 누른 순간 자기 캐릭터를 움직이고 싶습니다(서버 왕복을 기다리면 130ms쯤 늦음). 그러려면 클라이언트가 서버와 똑같은 계산을 미리 해 봐야 합니다. 계산 단위가 무브이고 계산 함수가 하나라면, 같은 시작 상태에 같은 무브를 넣었을 때 양쪽 결과가 일치하고, 어긋날 때만(서버만 아는 상자에 부딪힘 등) 보정하면 됩니다. Phase 22 측정에서 이 덕분에 키를 누른 다음 프레임(약 20ms)에 이동이 시작됐습니다. 예측 이전에는 약 130ms였습니다.

    그래서 규칙이 생깁니다: 스크립트는 이동을 직접 계산하지 않는다. 스크립트가 SetPosition으로 캐릭터를 옮기면 그 계산은 무브에 들어가지 않으므로 서버와 클라이언트가 어긋납니다. 조종하는 쪽이 매 프레임 이동 방향과 점프만 넘깁니다.

    -- ---- 조종하는 쪽: 이동 입력 (실제 이동은 엔진이 이번 프레임에 — 클라이언트는 예측)
function PlayerCharacter:UpdateMovementInput()
	local Radians = math.rad(self.Yaw)
	local Forward = Vector3(math.cos(Radians), math.sin(Radians), 0)
	local Right   = Vector3(-math.sin(Radians), math.cos(Radians), 0)
	local MoveX, MoveY = Input.GetAction("Move") -- X = 오른쪽, Y = 앞 (48강)
	local Move = Forward * MoveY + Right * MoveX
	if Move:LengthSquared() > 0 then
		self.entity:AddMovementInput(Move)
	end
	if Input.WasActionPressed("Jump") then
		self.entity:Jump() -- 바닥에 있을 때만 뛴다
	end
end

    갱신 순서도 이 설계에 맞춰져 있습니다: 스크립트(입력) → 캐릭터 이동 → 게임 모듈 → AI → 물리 → 트랜스폼 → LateUpdate. 캐릭터는 스크립트 직후 FGameWorld::TickCharacters에서 이번 프레임 dt로 무브 하나를 진행합니다(45강의 강체처럼 고정 스텝을 쓰지 않습니다 — 무브에 자기 dt가 들어 있으므로 다시 적용해도 같은 결과입니다).

    루트 모션과의 연결

    공격 모션에서 "한 걸음 내딛으며 베기"처럼 애니메이션 자체가 몸을 앞으로 옮기는 경우가 있습니다. 이것이 루트 모션입니다(43강). 애니메이션이 추출한 이동을 캐릭터 이동에 넘길 때도 무브를 거칩니다. 애니메이션 시스템은 루트 모션을 자기 또는 가장 가까운 조상의 FCharacterMovementComponent에 쌓아 두기만 하고(Scene 모듈은 Physics를 모르므로 SetRootMotionReceiver 훅으로 연결), 다음 무브가 ConsumeRootMotion으로 "쌓인 이동 ÷ 쌓인 시간"을 루트 모션 속도로 싣습니다. 그 무브는 입력 대신 그 속도로 움직이되, 충돌·계단·바닥 붙이기는 그대로 Jolt 이동이 맡습니다. 0.25초 넘게 아무도 가져가지 않은 루트 모션(편집 모드, 원격 캐릭터)은 버립니다. 루트 모션 무브도 결국 "무브"이므로 네트워크 예측 경로를 그대로 탑니다.

    함정과 교훈한 프레임 늦은 카메라

    실제로 겪은 일 — 내 캐릭터만 떨린다 (Phase 21) 3인칭 카메라가 캐릭터를 따라가는데, 자기 캐릭터가 미세하게 떨려 보였습니다. 카메라를 OnUpdate에서 캐릭터의 월드 위치로 놓고 있었는데, OnUpdate는 물리보다 앞에 돌므로 그 위치는 이번 프레임에 움직이기 전 값이었습니다. 카메라가 항상 한 프레임 늦게 따라가니, 프레임 시간이 12ms/18ms로 번갈아 바뀌면 화면상 이동 속도가 1.5배/0.67배로 번갈아 보였습니다. 해결: 물리·트랜스폼 갱신 뒤에 도는 OnLateUpdate 단계를 새로 만들고 카메라를 거기서 놓았습니다. 측정: 프레임당 이동량 ÷ 프레임 시간 비율이 평균 1.00, 표준편차 0.03. 테스트 GameWorld_LateUpdateSeesPhysicsResult로 고정했습니다.
    규칙 모음
    • 속도 규칙을 바꾸면 CharacterMovementMath::ComputeVelocity와 CharacterMovementTests를 함께 고친다(계단 30cm 오름/60cm 막힘, 경사 30° 오름/70° 못 오름, 점프 ≈138cm 등이 여기 고정돼 있다).
    • 트랜스폼 위치 = 캡슐 중심. 발 위치가 아니다. 캐릭터에는 콜라이더·강체가 필요 없고, 있어도 캐릭터가 우선한다.
    • 캐릭터를 따라가는 카메라는 OnLateUpdate에서.
    • 스크립트가 캐릭터를 직접 옮기면 FPhysicsSystem이 "순간이동"으로 감지해 캐릭터 상태를 거기로 맞춘다. 순간이동은 의도할 때만.

    Phase 22 기록의 "후속" 목록도 교재로 좋습니다: 서버 측 속도 조작 방지(무브 dt 합과 실제 경과 시간 비교), 움직이는 발판 위 캐릭터(발판 속도 상속), 웅크리기/수영 같은 이동 모드. dt를 0.1초로 자르는 것만으로는 "작은 dt를 아주 많이 보내는" 조작을 막지 못한다는 뜻입니다. 결정성은 공정함의 출발점일 뿐, 신뢰는 서버가 따로 검증해야 합니다.

    정리
    • 플레이어를 강체로 움직이면 계단·경사·밀림·되감기 문제가 생긴다 → 캐릭터 컨트롤러.
    • CharacterVirtual은 시뮬레이션에 참여하지 않고 쓸어 보기 질의로 움직인다(collide-and-slide). 다른 물체는 내부 키네마틱 바디와 부딪힌다.
    • 속도 규칙은 순수 함수 ComputeVelocity: 바닥은 즉시 목표 속도, 공중은 제한된 가속, 중력은 항상, dt는 0.1초 상한.
    • 이동 단위 = 무브. 같은 무브 → 같은 결과이므로 서버·예측 클라이언트·Standalone이 한 함수를 공유한다.
    • 스크립트는 AddMovementInput/Jump만. 루트 모션도 무브에 실려 같은 경로를 탄다.

    생각해 볼 문제

    Q1. 공중 제어를 "공중에서도 바닥처럼 입력 × 최대 속도로 즉시 설정"으로 바꾸면 무엇이 달라질까요? 점프 중에도 방향을 즉시 꺾을 수 있어 조작은 쉬워지지만, 점프가 "궤적"이 아니라 "공중 걷기"가 됩니다. 뛰어서 건너야 하는 구멍 같은 플랫폼 퍼즐이 의미를 잃고, 멀리뛰기에 도움닫기가 필요 없어집니다. AirControl은 이 손맛을 조절하는 손잡이이고, 가속 한계로 구현했기 때문에 0~1 사이 값이 자연스럽게 섞입니다.
    Q2. 캐릭터 이동을 45강의 60Hz 고정 스텝 안에서 돌리지 않고 프레임 dt로 무브를 만드는데도 결정적이라고 할 수 있는 이유는? 결정성의 조건은 "같은 입력 열 → 같은 결과"입니다. 무브에는 그 프레임의 dt가 값으로 들어 있으므로, 서버나 재조정 중인 클라이언트가 같은 무브를 다시 적용하면 같은 dt로 같은 계산을 합니다. 실행 시점의 실제 시계를 읽지 않는다는 것이 핵심입니다. (다만 다른 물체가 움직이는 세계를 질의하므로, 세계 상태가 다르면 결과도 달라집니다 — 그래서 보정이 존재합니다.)
    Q3. 무브의 Input을 "로컬 키 상태(W 눌림 여부)"로 보내지 않고 "월드 XY 방향"으로 보내는 이유는 무엇일까요? 키 → 방향 변환에는 카메라 yaw, 키 재지정, 게임패드 스틱 같은 클라이언트 쪽 정보가 들어갑니다. 서버가 이것을 다시 계산하려면 그 정보를 모두 알아야 하고, 바인딩이 다르면 결과도 달라집니다. 이미 해석된 "월드 방향(길이 ≤ 1)"을 보내면 서버는 입력 장치를 몰라도 되고, 길이를 1로 잘라 "대각선 속도 부풀리기" 같은 조작도 막을 수 있습니다.

    왜 필요한가"문이 3초 뒤에 열린다"를 위해 엔진을 다시 빌드할 것인가

    게임에는 작고 많고 자주 바뀌는 로직이 있습니다. "레버를 당기면 3초 뒤 문이 열린다", "보스 체력이 절반이 되면 음악을 바꾼다". 이것을 C++로 쓰면 고칠 때마다 컴파일·링크를 기다리고 에디터를 다시 띄워야 합니다. 실수로 널 포인터를 건드리면 에디터 전체가 죽습니다. 그리고 이런 코드를 쓰는 사람은 엔진 프로그래머가 아니라 게임 디자이너인 경우가 많습니다.

    스크립트 언어를 엔진에 넣으면(embedding) 세 가지를 얻습니다.

    • 반복 속도: 파일을 저장하면 플레이 중에도 바로 반영됩니다(핫 리로드).
    • 격리: 스크립트 오류는 그 스크립트만 멈추고, 엔진은 계속 돕니다.
    • 제한된 권한: 콘텐츠 코드에 파일 시스템이나 프로세스 접근을 주지 않을 수 있습니다.

    대가는 속도입니다. 인터프리터는 네이티브 코드보다 수십 배 느릴 수 있고, C++ ↔ 스크립트 경계를 넘을 때마다 비용이 듭니다. 그래서 ProjectE는 첫날 하이브리드로 정했습니다(0강).

    핵심 개념Lua와 스택, 그리고 sol2

    Lua는 게임 업계에서 오래 쓰인 임베디드 언어입니다. 인터프리터 전체가 수백 KB 크기의 C 코드라 어디든 넣기 쉽고, 자료구조는 사실상 테이블(table) 하나뿐입니다 — 배열도, 사전도, 객체도 모두 테이블입니다. 테이블에 메타테이블을 붙이면 "없는 키를 읽을 때"(__index), "더하기를 할 때"(__add) 같은 동작을 바꿀 수 있어서, 이것으로 클래스와 C++ 객체 감싸기를 만듭니다.

    C++과 Lua는 가상 스택으로 대화합니다. C++이 Lua 함수를 부르려면 함수와 인자를 스택에 쌓고 lua_pcall을 부르며, 결과는 다시 스택에 올라옵니다. 반대로 Lua가 C++ 함수를 부르면 인자가 스택에 쌓여서 넘어옵니다.

    sol2는 C++ 타입을 Lua에 노출하는 코드를 거의 선언처럼 쓰게 해 줍니다. 엔진 벡터를 Lua에 내보내는 부분을 보면 생성자, 필드, 연산자 메타함수가 한눈에 보입니다.

    ProjectE에서는스크립트 = 클래스 테이블, Properties = 인스펙터 값

    ProjectE의 스크립트는 유니티의 MonoBehaviour와 비슷한 모양입니다. 파일 하나가 클래스 테이블을 돌려주고, 엔티티에 FScriptComponent(스크립트 경로 + 프로퍼티 덮어쓰기 JSON)를 달면 엔티티마다 인스턴스(self)가 생깁니다.

    local CircleWalker = {
	Properties = {
		Radius     = 120.0, -- cm
		Speed      = 30.0,  -- 도/초 (음수면 시계 방향)
		StartAngle = 0.0,   -- 도
	},
}

function CircleWalker:OnStart()
	self.Center = self.entity:GetPosition()
	self.Angle  = self.Properties.StartAngle
end

function CircleWalker:OnUpdate(dt)
	local P    = self.Properties
	self.Angle = self.Angle + P.Speed * dt
	local A    = math.rad(self.Angle)
	self.entity:SetPosition(self.Center + Vector3(math.cos(A) * P.Radius, math.sin(A) * P.Radius, 0))
end

return CircleWalker

    Properties는 기본값 선언입니다. 에디터 인스펙터가 이것을 읽어 입력 칸을 그리고, 씬에서 바꾼 값만 컴포넌트의 덮어쓰기 JSON에 저장합니다. 인스턴스를 만들 때 MakeProperties가 기본값을 복사한 뒤 덮어쓰기를 얹는데, 타입이 다르면(숫자 자리에 문자열) 무시합니다. 수명 함수는 OnStart(첫 OnUpdate 직전 한 번), OnUpdate(dt), OnLateUpdate(dt)(물리·트랜스폼 뒤 — 46강의 카메라), OnDestroy입니다. 그리고 플레이 세션마다 새 Lua 상태를 만듭니다. 지난 플레이에서 전역 변수에 남긴 값이 다음 플레이로 새어 나오지 않게 하기 위해서입니다.

    오류 격리

    스크립트 오류가 엔진을 죽이면 스크립트를 쓰는 의미가 반감됩니다. ProjectE는 세 겹으로 막습니다.

    1. 모든 스크립트 메서드는 sol::protected_function으로 부르고, 메시지 처리기로 debug.traceback(디버거가 있으면 디버거의 처리기)을 붙여 오류 위치와 호출 스택을 받습니다.
    2. C++ 바인딩 안에서 잘못된 사용을 발견하면 std::runtime_error를 던집니다. ProjectE는 Lua를 C++로 컴파일하므로 이 예외가 Lua 오류로 바뀌어 같은 pcall에서 잡힙니다.
    3. 오류가 난 인스턴스는 FaultInstance가 "멈춤" 표시를 하고 타이머·코루틴을 모두 지웁니다. 다른 인스턴스는 계속 돕니다. 스크립트 파일을 고쳐 저장하면(핫 리로드 성공) 멈춘 인스턴스가 다시 돕니다.

sol::protected_function_result Result = bPassDelta ? Function(Self, DeltaSeconds) : Function(Self);

    어디서 도는가 — ExecutionLocation

    멀티플레이(8부)에서는 같은 씬이 서버와 여러 클라이언트에 동시에 있습니다. 문을 여는 판정은 서버에서만, 카메라 조작은 클라이언트에서만 돌아야 합니다. 그래서 스크립트 컴포넌트마다 ExecutionLocation을 둡니다: ServerOnly(기본), ClientOnly, Both. 인스턴스는 이 머신에서 돌아야 할 때만 만들어지므로, 그 인스턴스가 만드는 타이머·코루틴도 자동으로 같은 규칙을 따릅니다. 46강의 PlayerCharacter.lua는 Both이고, 안에서 "내가 조종하는 쪽인가"를 확인해 입력을 처리합니다.

    핵심 개념타이머와 코루틴 — 시간에 걸친 로직

    "불꽃을 쏘고, 2초 뒤 공중에서 터뜨리고, 빛이 3초 동안 서서히 꺼진다"를 OnUpdate만으로 쓰면 상태 변수와 경과 시간 변수가 잔뜩 생깁니다. 코루틴(coroutine)은 실행을 중간에 멈췄다가(yield) 나중에 그 자리에서 이어 갈(resume) 수 있는 함수입니다. 덕분에 시간에 걸친 순서를 위에서 아래로 읽히게 쓸 수 있습니다.

    self.Running = Coroutine.Start(function()
	local P = self.Properties
	self.Particles.Asset = ""
	Wait()                                  -- 다음 프레임까지
	self.Particles.Asset = P.LaunchAsset.Path
	Wait(P.RiseTime)                        -- 올라가는 시간만큼
	...
	while T < P.BurnTime do
		T = T + Time.DeltaTime
		...                                 -- 위치·빛 세기 갱신
		Wait()
	end
	self.HeadLight.Intensity = 0.0
end)

    구현에서 중요한 결정은 두 가지입니다.

    ① 소유자. 타이머와 코루틴은 그것을 만든 스크립트 인스턴스의 소유입니다. 문 엔티티가 파괴됐는데 그 문이 걸어 둔 "3초 뒤 문 열기" 타이머가 남아 있으면, 3초 뒤 사라진 엔티티를 건드립니다. 그래서 인스턴스가 사라질 때(OnDestroy 뒤, 엔티티 파괴, 스크립트 변경, EndPlay) 그 인스턴스의 타이머·코루틴을 함께 지웁니다. 그런데 Timer.After라는 전역 함수는 "누가" 불렀는지 어떻게 알까요? 엔진이 인스턴스 코드를 부를 때마다 FInstanceScope라는 RAII 객체로 "지금 실행 중인 인스턴스"를 기록하고, 스코프가 끝나면 이전 값으로 되돌립니다. 인스턴스 코드 밖(예: 비헤이비어 트리 스크립트 객체)에서 Timer.After를 부르면 소유자가 없으므로 오류입니다. 그래서 CLAUDE.md 규칙이 "인스턴스 코드를 부르는 새 경로에는 FInstanceScope를 건다"입니다.

    ② Wait는 Lua로 구현한다. Lua 5.4에서 C 함수 안에서 yield하는 것은 제약이 많습니다. 그래서 Wait/WaitFrames/WaitUntil은 Lua 코드 조각으로 정의하고, 엔진만 아는 토큰을 함께 yield합니다. 사용자가 직접 쓴 coroutine.yield와 엔진 대기를 이 토큰으로 구분합니다.

    local Token, IsYieldable, Yield = ...
function Wait(Seconds)
	Check("Wait")   -- Coroutine.Start로 시작한 코루틴 안이 아니면 오류
	return Yield(Token, "Seconds", Seconds or 0)
end

    모듈: Script.Require

    아이템 표처럼 여러 스크립트가 공유할 데이터·함수는 Script.Require("Scripts/RPG/ItemDatabase.lua")로 읽습니다. 표준 require는 파일 시스템을 마음대로 뒤지므로 막아 두고, Content 기준 경로만 받아 FFileSystem(pak → 디스크, 63강)으로 읽습니다. Lua 상태마다 한 번만 실행해 결과를 캐시하고, 순환(A가 실행 중 다시 A를 Require)은 오류입니다. 모듈 파일이 바뀌면 새 코드가 성공했을 때만 값을 교체하고, 그 모듈을 Require한 파일들을 따라가며 다시 실행합니다. 주의할 점: 모듈 값은 모든 인스턴스가 공유하는 같은 테이블이므로, 한 인스턴스가 고치면 모두에게 보입니다. 모듈에는 정의와 함수만 두고 상태는 인스턴스에 둡니다.

    ProjectE에서는중단점 디버거 — 쓰지 않을 때는 비용 0

    스크립트가 커지면 로그 출력만으로는 부족해집니다. Phase 47 사이드 트랙에서 에디터에 Lua 디버거(중단점, 조건, 단계 실행 Into/Over/Out, 지역 변수·upvalue·self 보기, 조사식, 오류 정지)를 넣었습니다. 바탕은 Lua의 디버그 훅(lua_sethook)입니다. 훅을 걸면 Lua가 줄이 바뀔 때마다(line), 함수에 들어가고 나올 때마다(call/return) 콜백을 부릅니다.

    문제는 비용입니다. 줄 훅은 모든 줄마다 C 함수를 부르므로, 훅을 상시로 걸면 스크립트 전체가 크게 느려집니다. ProjectE의 디버거는 훅을 세 단계로 나눕니다.

    몇 가지 까다로운 부분이 더 있습니다.

    • 코루틴: Lua 훅은 스레드(코루틴)마다 따로 걸립니다. 그래서 디버거는 coroutine.create/wrap을 자기 것으로 교체해 새로 만든 코루틴을 약한 표에 기록하고 훅을 겁니다. 이 교체가 엔진 바인딩보다 먼저여야 Coroutine.Start가 잡아 두는 coroutine.create도 디버거 것이 됩니다. 그래서 Lua 상태를 만든 직후, RegisterBindings 전에 Attach합니다.
    • 멈춰 있는 동안의 에디터: 중단점에서 멈추면 Lua는 C++ 호출 스택 깊숙한 곳(스크립트 갱신 도중)에 정지해 있습니다. 그 상태에서도 에디터 UI는 그려져야 변수를 볼 수 있습니다. 그래서 정지 처리기가 FApplication::RunNestedFrame으로 중첩 프레임 루프를 돌며 UI만 그립니다. 게임·물리·스크립트 갱신, 씬을 바꾸는 메뉴는 이 동안 그리지 않습니다(계층/인스펙터는 비활성) — 갱신 도중에 씬을 바꾸면 바깥 프레임이 깨진 상태로 돌아오기 때문입니다.
    • 단계 실행의 깊이: Over는 "같은 스레드에서 깊이 ≤ 시작 깊이인 줄", Out은 "깊이 < 시작 깊이인 줄"에서 멈춥니다. 코루틴 안에서 Over를 하다가 그 코루틴이 Wait로 yield하면, 다른 코드의 줄은 건너뛰고 그 코루틴이 다시 재개될 때 이어 갑니다.

    함정과 교훈자동 바인딩이 해 주지 않는 것

    실제로 겪은 일 — 경로는 바뀌었는데 화면은 그대로 (Phase 21) 멀티플레이 캐릭터를 만들 때 서버 스크립트가 플레이어 번호별로 머티리얼 경로(MaterialAsset)를 바꿔 색을 정하게 했습니다. 리플렉션 바인딩 덕분에 문자열 프로퍼티는 바로 바뀌었지만, 렌더러가 쓰는 것은 로드 때 그 경로로 해석해 둔 리소스 핸들이었습니다. 문자열만 바뀌고 핸들은 옛 머티리얼 그대로 남는 문제가 검증 중 발견됐습니다. 수정: 정적 메시 컴포넌트가 "해석한 경로"를 기억해 두었다가 경로가 달라지면 다시 해석하고(ResolvedMeshAsset/ResolvedMaterialAsset), Lua가 에셋 필터가 붙은 문자열 프로퍼티를 쓰면 bStructureChanged를 세워 앱이 재해석하게 했습니다(위 __newindex 발췌의 마지막 부분). 자동 바인딩은 "값"을 바꿔 줄 뿐, 그 값에서 파생된 상태까지 알아서 갱신해 주지는 않습니다.
    규칙 — 소멸 순서 FLuaRuntime에는 sol::state Lua와 함께 sol 테이블·함수 멤버(타이머 목록, 모듈 캐시, 코루틴 함수 참조 …)가 있습니다. sol 참조는 소멸될 때 Lua 상태에서 자기 참조를 해제하는데, C++ 멤버의 소멸 순서는 선언 순서에 묶여 있어서 상태가 먼저 사라지면 이미 없는 상태에 접근해 크래시가 납니다. 그래서 소멸자가 sol 멤버를 직접 먼저 비우고, CLAUDE.md에 "FLuaRuntime에 sol 객체 멤버를 새로 두면 ~FLuaRuntime에서 직접 비운다"를 규칙으로 남겼습니다(능력 시스템이 sol 멤버를 추가할 때 함께 기록된 규칙). 선언 순서 같은 "보이지 않는 계약"은 이렇게 글로 남겨야 지켜집니다.
    플랫폼의 숨은 기본 동작 — F10 디버거의 단계 실행 키는 관례대로 F10(Over)입니다. 그런데 Windows는 F10 단독 입력을 "창 메뉴 활성화" 키(WM_SYSKEYDOWN)로 다룹니다. 그대로 두면 F10을 누를 때 단계 실행 대신 포커스가 창 메뉴로 넘어갑니다. 그래서 ProjectE의 창 프로시저는 F10 단독을 창 메뉴로 넘기지 않습니다(CLAUDE.md 디버거 항목). 키 하나를 고를 때도 운영체제가 이미 그 키에 붙여 둔 의미를 확인해야 합니다.

    왜 필요한가IsKeyDown(EKey::W)의 한계

    1강에서 만든 입력은 "키가 눌렸는가"를 묻는 구조였습니다. 첫 데모에는 충분했지만, 게임이 커지면 곧 벽에 부딪힙니다.

    • 장치가 여럿이다: 같은 "앞으로 이동"을 W 키로도, 게임패드 왼쪽 스틱으로도 해야 합니다. 스크립트마다 IsKeyDown(W) or 스틱Y > 0.2를 쓰면 코드가 장치에 묶입니다.
    • 값의 종류가 다르다: 키는 0 아니면 1, 스틱은 -1~1 연속값, 마우스는 "이번 프레임 이동량"입니다.
    • 플레이어가 키를 바꾼다: 왼손잡이, 다른 자판 배열, 접근성. 키 재지정은 출시 게임의 기본 기능입니다.
    • 시점 회전: 마우스로 화면을 돌리는 FPS식 조작은 커서 "위치"로는 만들 수 없습니다.

    핵심 개념원시 마우스 입력과 커서 잠금

    마우스로 시점을 돌릴 때 필요한 것은 "커서가 어디 있는가"가 아니라 "마우스를 얼마나 움직였는가"입니다. 커서 위치(WM_MOUSEMOVE)로 이동량을 구하면 두 가지 문제가 있습니다. 커서가 화면 끝에 닿으면 더 움직여도 값이 변하지 않고, 운영체제의 포인터 가속("포인터 정밀도 향상")이 섞여 같은 손 동작이 빠르기에 따라 다른 각도로 바뀝니다. FPS 게이머가 가장 싫어하는 일입니다.

    Windows의 Raw Input은 장치가 보고한 이동 카운트를 가속 없이 그대로 줍니다. 창을 만들 때 마우스를 원시 입력 장치로 등록하면 WM_INPUT 메시지로 받습니다.

Mouse.usUsagePage = 0x01; // HID_USAGE_PAGE_GENERIC
Mouse.usUsage     = 0x02; // HID_USAGE_GENERIC_MOUSE

    • 다른 창이 앞에 있으면 잠그지 않고, 포커스를 잃으면(WM_KILLFOCUS) 즉시 풉니다 — Alt+Tab 했는데 커서가 사라져 있으면 사용자는 당황합니다.
    • 창이 움직이면(WM_MOVE) 가둘 위치를 다시 계산합니다.
    • 런타임에서 ESC는 먼저 잠금을 풀고, 에디터 플레이는 뷰포트 가운데를 잠금 점으로 씁니다(SetCursorLockPoint). Lua는 Game.SetMouseLocked/IsMouseLocked.

    핵심 개념키 대신 액션: 바인딩 · 수정자 · 합산 · 문턱

    입력 액션은 "게임이 알고 싶은 의도"에 이름을 붙인 것입니다: Move, Look, Jump. 액션에는 값 종류가 있고(버튼 / 1D 축 / 2D 축), 여러 개의 바인딩을 가집니다. 바인딩 하나 = 입력 소스 하나 + 수정자(modifier) 목록입니다.

    struct FInputBinding
{
	FInputSource                Source;    // 키 / 마우스 버튼 / 마우스 축 / 게임패드 버튼 / 게임패드 축
	std::vector<FInputModifier> Modifiers; // 순서대로 적용
};

struct FInputAction
{
	std::string                Name;
	EInputActionType           Type = EInputActionType::Button; // Button / Axis1D / Axis2D
	float                      ActuationThreshold = 0.5f;
	std::vector<FInputBinding> Bindings;
};

    모든 소스는 일단 2D 값 하나로 읽힙니다: 키·버튼은 (1, 0) 또는 (0, 0), 1D 축은 (값, 0), 2D 축은 (X, Y). 여기에 수정자를 차례로 적용하고, 액션 값은 모든 바인딩 결과의 합입니다. 그러면 놀랍도록 단순한 규칙만으로 WASD를 2D 이동으로 바꿀 수 있습니다.

    for (const FInputBinding& Binding : Action.Bindings)

	{
		const float Magnitude = GetMagnitude(EInputActionType::Axis2D, Value);
		Result.bActive        = Result.bActive || (Magnitude > 0.0f && Magnitude >= Action.ActuationThreshold);
	}
	else
	{
		Result.Value += Value; // 축: 바인딩 결과의 합
	}
}

    버튼 액션은 합하지 않고 "바인딩 중 하나라도 문턱을 넘었는가"입니다. 그래야 스페이스와 패드 A를 동시에 눌러도 2가 아니라 그냥 "눌림"입니다. 작동 문턱(actuation threshold)은 축을 버튼처럼 쓸 때 의미가 있습니다. 트리거(0~1)를 "발사" 버튼에 묶으면 0.5 이상 당겼을 때만 켜집니다. "이번에 눌림/뗌"(WasActionPressed/Released)은 1강의 키와 똑같이 지난 프레임의 켜짐과 비교합니다.

    이 계산 전체가 Core/InputActions.h의 순수 로직입니다. 창도 전역 상태도 모르고, 소스를 읽는 방법은 템플릿 인자(Read)로 받습니다. 그래서 InputActionTests가 가짜 입력으로 수정자·합산·문턱을 모두 검증합니다.

    왜 사용자 파일에 매핑 전체가 아니라 "바뀐 액션"만 저장할까요? 게임 업데이트로 새 액션이 추가되거나 기본 바인딩이 바뀌어도, 플레이어가 손대지 않은 액션은 새 기본값을 그대로 따르게 하기 위해서입니다. 또 재지정은 소스만 바꾸고 수정자는 유지합니다. W에 걸린 Swizzle은 플레이어가 W를 I로 바꿔도 여전히 필요하니까요. 자동 검증 실행은 사용자 파일을 읽지도 쓰지도 않습니다 — 개발자 PC의 개인 키 설정이 스크린샷 결과를 바꾸면 안 되기 때문입니다.

    게임패드: XInput을 링크 없이

    Xbox 호환 패드는 XInput API로 읽습니다. 그런데 XInput DLL은 Windows 버전에 따라 이름이 다르고(xinput1_4.dll, xinput9_1_0.dll, xinput1_3.dll), 정적으로 링크하면 해당 DLL이 없는 PC에서 실행 자체가 실패합니다. 그래서 FGamepadInput은 실행 중에 LoadLibraryW로 차례로 시도하고 GetProcAddress로 XInputGetState만 꺼내 씁니다. 하나도 없으면 "패드 연결 안 됨"으로 계속 동작합니다.

    • 빈 슬롯은 드물게 확인: XInputGetState는 연결 안 된 슬롯에서 느립니다. 연결된 슬롯은 매 프레임, 빈 슬롯은 1초마다(ReconnectIntervalSeconds) 확인합니다.
    • 원시 값만: 스틱 -32768~32767을 -1~1로, 트리거 0~255를 0~1로 바꿀 뿐 데드존은 넣지 않습니다. 데드존은 액션 수정자의 일입니다 — 한 곳에서만 처리해야 이중 데드존이 생기지 않습니다.
    • 첫 번째 연결된 패드가 FInput에 들어갑니다(GetPrimary). 로컬 분할 화면 같은 다중 패드는 아직 범위 밖입니다.

    네트워크: 액션 "값"을 보낸다

    멀티플레이에서 서버 스크립트가 Input.GetAction("Move")를 부르면 그 엔티티를 소유한 플레이어의 입력이 돌아와야 합니다. 클라이언트는 매 틱 입력 커맨드를 보내는데, 여기에 원시 키 상태뿐 아니라 클라이언트가 자기 유효 매핑으로 계산한 액션 값을 함께 싣습니다.

    // 액션 이름 + 종류 순서의 해시 (네트워크 입력 커맨드가 액션 값을 순서로 보낼 때 양쪽 목록이 같은지 확인)
uint32 FInputMapping::GetLayoutHash() const
{
	uint32     Hash   = 2166136261u; // FNV-1a
	const auto Mix    = [&Hash](uint8 Byte) { Hash = (Hash ^ Byte) * 16777619u; };
	for (const FInputAction& Action : Actions)
	{
		for (const char Char : Action.Name) { Mix(static_cast<uint8>(Char)); }
		Mix(0);
		Mix(static_cast<uint8>(Action.Type));
	}
	return Hash;
}

    액션 이름 문자열을 매번 보내면 커맨드가 커집니다. 순서와 값만 보내고, "순서가 같다"는 사실은 4바이트 해시 하나로 확인합니다. 바인딩은 해시에 들어가지 않는다는 점에 주목하세요. 바인딩은 플레이어마다 달라도 되지만, 액션의 이름·종류·순서는 프로젝트 전체가 같아야 합니다.

    함정과 교훈입력이 지나가는 길과 주인

    실제로 겪은 일 — 클라이언트 입력이 서버에서 사라진다 (Phase 21 사용자 피드백) 에디터를 리슨 서버로 띄우고 클라이언트 창 두 개를 붙였더니, 클라이언트에서는 아무리 키를 눌러도 캐릭터가 움직이지 않았습니다. 입력 코드는 멀쩡했습니다. 원인은 에디터의 게임 월드에 네트워크 드라이버가 연결되어 있지 않아, 클라이언트가 보낸 입력 커맨드 메시지를 받을 곳이 없어 버려지고 있었던 것입니다(에디터 클라이언트 모드의 입력 전송·RPC도 같은 원인). 수정: FGameWorld::SetNetDriver를 두고 에디터 네트워크 플레이(FPlayInEditorNet)가 준비·정지 때 연결·해제합니다. 입력 버그처럼 보여도 실제로는 "입력이 지나가는 길"의 문제인 경우가 많습니다. 자동 검증용 --hold-keys, --play-client-hold-keys가 이때 함께 생겼습니다.
    입력의 주인을 정한다 에디터 플레이 중에는 같은 창 안에 게임 뷰포트와 에디터 패널이 함께 있습니다. 그래서 게임에 가는 마우스 버튼은 뷰포트 안에서 누른 것만 인정하고, 빙의(possess)·해제와 입력 모드(GameOnly / GameAndUI / UIOnly)로 "지금 이 입력은 누구 것인가"를 정합니다(Phase 44, 36강). 입력 시스템은 값을 계산하는 일만큼 입력을 올바른 주인에게 보내는 라우팅이 중요합니다.

    정리
    • 시점 회전은 커서 위치가 아니라 Raw Input(WM_INPUT)의 가속 없는 이동량으로. 커서 잠금 = 숨김 + 가운데 1px ClipCursor, 포커스를 잃으면 해제.

    • XInput은 동적 로드, 네트워크는 액션 값 + 배치 해시.

    Q1. 2D 이동 액션의 데드존을 "축별"로 하면 원형일 때와 무엇이 다를까요? 축별 데드존은 X와 Y를 따로 자르므로 스틱을 대각선 근처로 살짝 기울이면 한 축만 살아남아 이동이 축 방향으로 "달라붙습니다"(십자 모양 데드존). 원형(길이 기준)은 방향은 그대로 두고 크기만 다시 펼치므로 모든 방향이 고르게 반응합니다. 그래서 스틱에는 Radial이 기본이고, 축별은 1D 트리거처럼 독립 축에 씁니다.
    Q2. 플레이어가 Jump를 Space에서 F로 재지정했습니다. 서버가 원시 키 비트로 액션을 다시 계산한다면 무슨 일이 생길까요? 서버는 프로젝트 매핑만 알기 때문에 Space가 눌리지 않았으니 점프하지 않습니다. 플레이어가 F를 눌러도 서버에서 캐릭터가 뛰지 않고, 예측 클라이언트에서는 뛰었다가 보정으로 끌려 내려옵니다. 클라이언트가 자기 유효 매핑으로 계산한 액션 값을 보내는 이유입니다.
    Q3. 버튼 액션도 축처럼 "바인딩 결과의 합 ≥ 문턱"으로 판정하면 어떤 문제가 있을까요? 값이 (1,0)인 바인딩 두 개를 동시에 누르면 합이 2가 되는 것은 버튼에선 무해하지만, 반대 방향 수정자가 붙은 바인딩(예: Negate)이 섞이면 합이 0이 되어 둘 다 눌렀는데 꺼질 수 있습니다. 버튼은 "어느 하나라도 켜졌는가"라는 의미이므로 OR로 판정하는 것이 맞습니다.

    왜 필요한가"생각하고" "걸어가는" 적

    경비병 하나를 만든다고 합시다. 평소엔 순찰 지점을 돌고, 플레이어가 보이면 돌아서서 쫓아가고, 놓치면 다시 순찰합니다. 이 요구에는 성격이 다른 두 문제가 섞여 있습니다.

    • 의사결정: 지금 무엇을 할까? (순찰 / 추적 / 공격) — 상황이 바뀌면 하던 일을 그만두고 다른 일을 해야 합니다.
    • 길 찾기: 저기까지 어떻게 갈까? — 벽을 돌아가고, 계단을 오르고, 좁은 틈은 피해야 합니다.

    ProjectE는 사용자 요청("언리얼 비헤이비어 트리처럼")에 따라 Phase 18에서 의사결정은 비헤이비어 트리, 길 찾기는 Recast/Detour(오픈소스 표준 내비메시 라이브러리)로 만들었습니다. AI는 서버(와 Standalone)에서만 돌고, 클라이언트는 결과 트랜스폼을 복제로만 받습니다.

    핵심 개념FSM에서 비헤이비어 트리로

    가장 단순한 AI 구조는 유한 상태 기계(FSM)입니다. 상태(순찰, 추적, 공격…)와 상태 사이 전이 조건을 그립니다. 상태가 셋일 때는 명쾌하지만, 상태가 늘수록 전이 화살표가 거의 제곱으로 늘어납니다. "어느 상태에서든 체력이 낮으면 도망"을 넣으려면 모든 상태에서 도망으로 가는 화살표를 그려야 합니다.

    비헤이비어 트리(behavior tree)는 행동을 트리로 조립합니다. 노드는 실행되면 Running(아직 하는 중), Success, Failure 중 하나를 돌려줍니다. ProjectE의 노드 분류는 네 가지입니다(EBTNodeCategory).

    핵심 개념이벤트 기반 실행기와 관찰자 중단

    가장 단순한 BT 실행기는 매 틱 루트부터 트리를 다시 평가합니다. 이해하기 쉽지만 두 가지 문제가 있습니다. 매 프레임 모든 조건을 다시 계산하므로 비싸고, "하던 일"이라는 개념이 약해 3초짜리 Wait 같은 태스크가 매 틱 새로 시작될 수 있습니다. 언리얼과 ProjectE는 이벤트 기반 실행기를 씁니다.

    // 비헤이비어 트리 실행기 (UE식 이벤트 기반).
//  - 매 틱 루트부터 재평가하지 않는다. 실행 중(Running) 태스크만 틱하고, 서비스는 활성 가지에서만 간격마다 틱한다
//  - 블랙보드 관찰 키가 바뀌면 대기열에 넣고 다음 Tick 시작에서 중단 규칙을 평가한다 (BehaviorTreeTypes.h의 EBTAbortMode)
//  - 루트가 끝나면 다음 틱에 루트부터 다시 시작한다
//  - 이번 틱에 시작된 태스크/서비스/데코레이터는 그 틱에 틱하지 않는다
//  - 틱(또는 Start)당 노드 방문 예산을 넘으면 남은 진입은 다음 틱으로 미룬다 (즉시 끝나는 노드를 도는 무한 Loop 대비)
// 한 틱의 순서: 지연 진입(루트 재시작/병렬 배경 재시작) → 블랙보드 중단 평가 → 진입 처리 → 서비스/데코레이터/태스크 틱 → 진입 처리

    그렇다면 순찰 중에 적이 보이면 어떻게 즉시 추적으로 바꿀까요? 매 틱 다시 평가하지 않으니, 바뀌었을 때만 알림을 받아야 합니다. 블랙보드는 값이 실제로 바뀔 때만 관찰자를 부르고, 데코레이터는 자기가 보는 키(GetObservedKeys)와 중단 모드(abort mode)를 선언합니다.

    중단 모드언제 무엇을예
    None진입할 때만 검사한 번 정하면 끝까지
    Self붙은 노드가 실행 중인데 조건이 거짓이 되면 그 가지를 중단추적 중 Target을 잃으면 추적 중단
    LowerPriority부모에서 이 노드보다 뒤(낮은 우선순위) 자식이 실행 중인데 조건이 참이 되면, 그 자식을 중단하고 이 노드를 실행순찰 중 Target이 생기면 순찰 중단 → 추적
    Both둘 다경비병의 추적 가지

    중단 평가에는 두 가지 세부 규칙이 있습니다. 첫째, 관찰 키가 바뀌면 바로 평가하지 않고 대기열에 넣었다가 다음 Tick 시작에 평가합니다. 노드 콜백 도중(트리를 순회하는 중)에 다른 가지를 중단하면 순회 중인 자료구조가 바뀌기 때문입니다 — 45강에서 물리 콜백 안에서 게임 코드를 부르지 않은 것과 같은 이유입니다. 둘째, 조건 결과가 바뀐 경우에만 중단 규칙을 적용합니다. Target이 적 A에서 적 B로 바뀌어도 "IsSet"은 계속 참이므로 추적을 다시 시작하지 않습니다.

    // 조건 결과가 바뀐 경우에만 중단 규칙을 적용한다 (UE의 ResultChange 알림)
const bool bCondition = Decorator.Node->CalculateCondition(*this);
if (Decorator.LastCondition == (bCondition ? 1 : 0)) { continue; }
Decorator.LastCondition = bCondition ? 1 : 0;
...
if (bSelf && !bCondition && Node.bActive)
{
	AbortAndFail(Node); // Self: 실행 중인 가지 중단 → 부모에 Failure
	continue;
}
if (bLower && bCondition && !Node.bActive)
{
	// LowerPriority: 부모가 이 노드보다 뒤 자식을 실행 중이면 그 자식을 중단하고 이 노드부터 다시 실행
	FRuntimeNode* Parent = Node.Parent;
	if (Parent && Parent->bActive && !Parent->bParallel && Parent->CurrentChild > Node.ChildIndex)
	{
		AbortSubtree(*Parent->Children[Parent->CurrentChild]);
		SelectChild(*Parent, Node.ChildIndex);
	}
}

    "이번 틱에 시작된 노드는 그 틱에 틱하지 않는다"와 "틱당 방문 예산 1000"도 의미가 있습니다. 즉시 Success를 돌려주는 태스크를 Loop로 무한히 돌리면 한 틱 안에서 영원히 끝나지 않습니다. 예산을 넘으면 남은 진입은 다음 틱으로 미뤄서 게임이 멈추지 않게 합니다.

    ProjectE에서는노드 레지스트리, 소유자, Lua 노드

    노드는 이름으로 FBehaviorTreeNodeRegistry::Get()에 등록되고, .ebt(JSON)는 노드 이름과 파라미터만 저장합니다. 등록 정보에는 소유자 태그가 있습니다. 엔진 기본 노드는 "Engine", 게임 모듈 DLL이 OnLoad에서 등록한 C++ 노드는 Owner를 비우면 그 모듈 이름이 됩니다. 모듈을 내릴 때(핫 리로드, 12강) UnregisterOwner(모듈 이름)로 그 모듈의 노드를 한 번에 지웁니다. 단, 노드 객체의 코드가 그 DLL 안에 있으므로, 해제 전에 그 노드를 쓰는 트리 인스턴스를 먼저 파기해야 합니다.

    Lua로도 노드를 만들 수 있습니다. LuaTask/LuaDecorator/LuaService라는 C++ 노드가 파라미터로 스크립트 경로를 받아 스크립트 객체를 만들고 부릅니다. 형식은 스크립트 컴포넌트와 같은 클래스 테이블입니다.

    local GuardNextWaypoint = {
	Properties = {},
}

function GuardNextWaypoint:OnExecute()
	local Guard = self.entity:GetScript()
	if Guard == nil or Guard.NextWaypoint == nil then return "Failure" end
	local Point = Guard:NextWaypoint()
	if Point == nil then return "Failure" end
	self.entity:GetBlackboard():Set("PatrolPoint", Point)
	return "Success"
end

return GuardNextWaypoint

    태스크는 OnExecute/OnTick(dt)/OnAbort, 데코레이터는 CanExecute(+ ObservedKeys/AbortMode), 서비스는 OnBecomeRelevant/OnTick/OnCeaseRelevant를 정의합니다(AI/LuaNodes.h). 그런데 AI 모듈과 Scripting 모듈은 서로를 모릅니다(0강의 의존 규칙). Lua → AI는 FScriptAIHooks(블랙보드·이동), AI → Lua는 FAIScriptHooks(스크립트 객체 생성·호출)라는 함수 묶음으로만 통하고, 둘을 아는 FGameWorld::ConnectScriptsAndAI가 연결합니다. 갱신 순서는 스크립트 → 게임 모듈 → AI → 물리입니다.

    핵심 개념내비메시 굽기 — Recast의 단계

    길 찾기의 고전은 격자(grid) 위 A*입니다. 하지만 3D 지형·계단·경사가 있는 세계를 격자로 덮으면 칸이 수백만 개가 되고, 경로가 계단 모양으로 꺾입니다. 내비게이션 메시(navigation mesh)는 "걸을 수 있는 바닥"을 볼록 다각형 몇백 개로 요약한 것입니다. 다각형 하나 안에서는 어느 두 점이든 직선으로 갈 수 있으므로(볼록성), 길 찾기는 다각형 그래프 위에서 하면 됩니다.

    문제는 씬의 삼각형(렌더용 메시)에서 이것을 만드는 일입니다. 렌더 메시는 겹치고, 구멍이 있고, 걸을 수 없는 천장·벽이 섞여 있습니다. Recast는 이를 복셀화로 해결합니다.

    핵심은 ③의 침식(erode)입니다. 에이전트는 점이 아니라 반경 35cm인 원기둥이므로, 벽에서 35cm 안쪽은 "중심이 갈 수 없는 곳"입니다. 내비메시를 반경만큼 미리 깎아 두면 이후 길 찾기는 에이전트를 점으로 취급해도 벽에 부딪히지 않습니다. 설정 값(에이전트 반경/키/턱/경사, 복셀 크기 …)은 cm·도로 받아 FNavMesh::Build가 복셀 단위로 바꿉니다(예: walkableRadius = ceil(AgentRadius / CellSize)).

    에디터에서는 도구 메뉴의 내비메시 굽기(FNavMeshBaker)가 씬의 보이는 정적 메시를 모아 굽습니다. 동적 강체, AI 에이전트, 스크립트 엔티티와 그 자손은 제외합니다 — 움직이는 것을 장애물로 구우면 영원히 그 자리에 구멍이 남기 때문입니다. 결과는 씬 옆 .enav(매직 + 버전 + 설정 원본 + Detour 타일 + FNV-1a 해시)이고, FNavMeshComponent가 그 경로를 가집니다.

    핵심 개념Detour: 다각형 위 A*와 경로 직선화

    길 찾기는 두 단계입니다.

    1. 다각형 경로(A*): 다각형을 노드, 이웃 다각형을 간선으로 보고 A*로 시작 다각형에서 끝 다각형까지 다각형 열을 찾습니다. A*는 각 노드에 f = g + h(지금까지 비용 g + 목표까지 추정 h, 보통 직선 거리)를 매기고 f가 가장 작은 노드부터 넓혀 가는 탐색입니다. h가 실제 거리를 과대평가하지 않으면 최단 경로를 보장하면서, 목표 반대 방향은 거의 탐색하지 않습니다.
    2. 직선화(string pulling): 다각형 열의 가운데를 이으면 지그재그가 됩니다. 다각형 사이 경계선(포털)을 통과하는 끈을 팽팽히 당긴 모양 — 모서리에서만 꺾이는 최단 꺾은선 — 을 구합니다. Detour의 findStraightPath가 이 일을 합니다(퍼널 알고리즘).

    FNavMesh::FindPath는 시작·끝을 먼저 가장 가까운 다각형에 투영하고(findNearestPoly), A*로 다각형 열을 찾은 뒤(최대 512개), 목표 다각형에 닿지 못했으면 마지막 다각형 위에서 목표에 가장 가까운 점까지 가는 Partial 경로를 돌려줍니다. 결과는 Complete / Partial / Failed 셋 중 하나입니다. MoveTo 태스크는 이 경로점을 따라 이동하는데, 동적 강체면 물리에 수평 속도를 주고(Z 속도 유지), 아니면 트랜스폼을 경로 높이를 따라 직접 옮깁니다. 목표 엔티티가 RepathDistance보다 많이 움직이면 경로를 다시 찾습니다.

    ProjectE에서는좌표 변환과 뒤집힌 와인딩

    Recast는 Y가 위, 1단위 = 1m입니다. 엔진은 Z가 위, 1단위 = 1cm입니다. 변환은 NavCoordinates.h 한 파일이 맡고, FNavMesh 경계에서만 씁니다(45강과 같은 원칙). 축 매핑은 간단히 "Y와 Z를 바꾸고 0.01배"입니다. 그런데 함정이 하나 있습니다.

    // 와인딩: Y와 Z를 맞바꾸는 매핑은 반사(행렬식 -1)라서 같은 인덱스 순서의 외적 방향이 뒤집힌다.
//   - 엔진 규약: Cross(P1 - P0, P2 - P0)가 앞면 노멀 (CLAUDE.md의 glTF 와인딩 검증식과 같다)
//   - Recast:    Cross(v1 - v0, v2 - v0).y > cos(최대 경사)인 면만 걸을 수 있는 면으로 표시한다
//   → 엔진 삼각형 (I0, I1, I2)는 Recast에 (I0, I2, I1)로 넘긴다. 그래야 +Z를 향한 엔진 바닥이 +y를 향한다.
static void ToRecast(const FVector3& Engine, float* Out)
{
	Out[0] = Engine.X * FUnits::UnitsToMeters;
	Out[1] = Engine.Z * FUnits::UnitsToMeters;
	Out[2] = Engine.Y * FUnits::UnitsToMeters;
}

    45강의 Jolt는 축을 그대로 썼기 때문에 이 문제가 없었습니다. Recast는 Y-up을 강제하므로 축을 바꿔야 하고, 축을 바꾸는 순간 "어느 쪽이 앞면인가"가 뒤집힙니다. Recast는 바닥을 "법선이 위를 향하는 면"으로 판단하므로, 와인딩을 보정하지 않으면 모든 바닥이 천장으로 보여 내비메시가 텅 빕니다. 이 규칙은 NavMeshTests의 NavCoordinates_*, NavMesh_UpFacingFloorIsWalkable, NavMesh_DownFacingFloorIsNotWalkable가 고정합니다. 에디터 굽기 쪽에서도 같은 원리로, 음수 스케일(거울상) 변환이 걸린 메시는 와인딩을 한 번 더 뒤집어 넘깁니다.

    함정과 교훈초기화 순서와 굽기 대상

    실제로 겪은 일 1 — 트리가 시작하자마자 블랙보드를 못 찾는다 (Phase 18-5) Lua 노드를 붙이자 트리가 시작하는 순간 노드가 블랙보드를 찾지 못했습니다. Start가 첫 진입을 그 자리에서 처리하는데(첫 노드의 OnExecute가 바로 불림), 그 시점에 트리 인스턴스가 아직 FAISystem에 등록되기 전이라 엔티티로 트리를 찾는 경로(entity:GetBlackboard())가 비어 있었던 것입니다. 수정: 트리를 등록한 뒤 Start. 같은 맥락에서 게임 월드의 순서도 BeginPlay는 스크립트(Lua 상태 생성) → AI, EndPlay는 AI(Lua 노드의 OnAbort) → 스크립트로 정리했습니다. "누가 먼저 존재해야 하는가"는 초기화 순서 버그의 단골 원인입니다.
    실제로 겪은 일 2 — 플레이어가 장애물로 구워졌다 (Phase 18-9) 데모 씬 Demo_AI를 굽고 보니 플레이어가 서 있던 자리에 구멍이 나 있었습니다. 플레이어는 스크립트로 움직이는 엔티티였는데 굽기 제외 규칙(동적 강체, AI 에이전트)에 걸리지 않아 정적 장애물로 구워진 것입니다. 스크립트 엔티티와 그 자손을 제외 규칙에 추가했습니다. 굽기 대상 규칙은 FNavMeshBaker 헤더 주석에 기준으로 남겨 두었습니다.
    알려진 한계 (Phase 18 기록)
    • LowerPriority는 부모가 SimpleParallel이거나 실행이 부모 컴포지트 밖이면 적용되지 않는다. 태스크 중단은 즉시(언리얼의 "중단 중" 지연 상태 없음).
    • 내비메시는 단일 타일(Solo) — 4096×4096셀 또는 정점 65535개를 넘으면 실패. 무리 회피(DetourCrowd), 동적 장애물, 오프메시 링크, 영역 비용은 없다.
    • FNavMesh는 쿼리 객체를 공유하므로 스레드 안전하지 않다.
    • FNavMeshBuildSettings 필드를 바꾸면 NavFileVersion을 올린다(.enav에 설정 원본이 그대로 들어간다). 실행기 규칙을 바꾸면 BehaviorTreeTests를 함께 고친다.
    정리
    • BT는 우선순위를 트리 위치로 표현한다. 노드 = 컴포지트 / 태스크 / 데코레이터 / 서비스, 노드끼리는 블랙보드로 대화.
    • 실행기는 이벤트 기반: Running 태스크만 틱하고, 관찰 키 변경은 다음 틱 시작에, 조건 결과가 바뀔 때만 Self/LowerPriority 중단.
    • 노드는 레지스트리에 소유자 태그와 함께 등록(엔진/게임 모듈), Lua 노드는 훅으로 이어진 스크립트 객체.
    • Recast = 복셀화 → 걸러내기 → 침식 → 영역 → 윤곽 → 다각형 → 디테일. Detour = 다각형 A* → 직선화.
    • Z-up ↔ Y-up 변환은 반사이므로 삼각형 와인딩을 (I0, I2, I1)로 뒤집는다. 변환은 NavCoordinates.h 한 곳에서.

    생각해 볼 문제

    Q1. 경비병의 추적 가지 데코레이터를 Both 대신 Self로만 두면 어떤 행동이 될까요? Target을 잃었을 때 추적을 멈추는 것은 그대로지만, 순찰 가지가 실행 중일 때 Target이 생겨도 순찰을 중단하지 않습니다. 순찰 Sequence(다음 지점 → 이동 → 2초 대기)가 끝나 루트가 다시 시작될 때에야 추적 가지가 평가되므로, 플레이어를 보고도 몇 초 동안 하던 순찰을 계속하는 "둔한" 경비병이 됩니다.
    Q2. 내비메시를 침식하지 않고, 길 찾기 때 에이전트 반경을 고려하면 안 될까요? 가능은 하지만 경로 탐색과 직선화가 "두께 있는 원이 지나갈 수 있는가"를 매번 계산해야 해 복잡하고 느려집니다. 미리 반경만큼 깎아 두면 런타임은 점 하나의 길 찾기로 단순해집니다. 대가는 반경이 다른 에이전트마다 내비메시가 따로 필요하다는 점입니다(ProjectE는 설정 하나 — 큰 몬스터용 메시는 별도 굽기가 필요).
    Q3. Recast에 넘길 때 Y와 Z를 바꾸는 대신 Y만 부호를 뒤집는(반사가 아닌 회전) 매핑을 쓰면 와인딩을 뒤집지 않아도 될까요? 회전(행렬식 +1)이면 외적 방향이 보존되므로 와인딩은 그대로 둘 수 있습니다. 예를 들어 (x, y, z) = (X, Z, −Y)는 X축 둘레 90° 회전이라 와인딩 보정이 필요 없습니다. ProjectE는 (X, Z, Y)를 택하고 와인딩을 뒤집었는데, 어느 쪽이든 "반사인가 회전인가"를 확인하고 테스트로 고정하는 것이 핵심입니다. (단, 엔진 자체가 왼손 좌표계라는 점까지 섞이면 직관이 쉽게 틀리므로, 판단은 머릿속이 아니라 NavMesh_UpFacingFloorIsWalkable 같은 테스트로 합니다.)
