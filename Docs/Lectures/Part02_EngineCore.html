    엔진의 뼈대 — 데이터와 구조

    게임 세계를 메모리에 어떻게 담고(ECS·씬 계층), 그 데이터를 어떻게 스스로 설명하게 만들며(리플렉션), 파일로 어떻게 남기고 다시 읽는지(직렬화·쿠킹·임포트), 그리고 그 모든 코드를 어떤 바이너리로 묶는지(엔진 DLL·게임 모듈)를 다룹니다. 화면에는 보이지 않지만 에디터·스크립트·네트워크가 모두 이 층 위에 서 있습니다.

    7강

    ECS — 엔티티, 컴포넌트, 시스템

    관련 Phase: 3 · 살펴볼 곳: Engine/Source/Core/ECS/ (Entity.h, SparseSet.h, Registry.h, Registry.cpp), Tests/CoreTests/ECSTests.cpp
    이 강의를 마치면
    • 게임 물체를 클래스 상속 트리로 표현할 때 생기는 문제와, ECS가 그것을 어떻게 피하는지 설명할 수 있습니다.
    • 희소 집합(sparse set)이 "찾기 O(1), 삭제 O(1), 연속 순회"를 동시에 얻는 원리를 그림으로 그릴 수 있습니다.
    • 세대(generation)가 붙은 엔티티 핸들이 "지워진 물체를 가리키는 핸들" 문제를 어떻게 막는지 압니다.
    • View가 가장 작은 풀을 기준으로 도는 이유와, 순회 중 같은 타입 컴포넌트를 추가·제거하면 안 되는 이유를 압니다.

    왜 필요한가상속 트리는 게임 물체를 담기에 너무 뻣뻣하다

    게임 세계에는 플레이어, 상자, 횃불, 카메라, 적, 문, 파티클 이미터 같은 물체가 수백에서 수만 개 있습니다. C++을 배운 사람이 가장 먼저 떠올리는 설계는 클래스 상속입니다. GameObject를 맨 위에 두고, 움직이는 것은 Pawn, 그중 사람 모양은 Character, 고정된 물체는 StaticProp … 이렇게 내려가는 트리입니다.

    처음엔 잘 됩니다. 문제는 "조합"이 필요해질 때 생깁니다. "물리로 굴러가는데 체력도 있어서 부서지는 상자"는 StaticProp 밑일까요, Pawn 밑일까요? "빛을 내는 캐릭터"는? 기능 하나를 추가할 때마다 트리 어딘가를 잘라 붙여야 하고, 결국 다중 상속(다이아몬드)이나 모든 기능을 다 가진 거대한 기반 클래스로 무너집니다.

    성능 문제도 있습니다. 상속 트리의 물체들은 보통 new로 하나씩 힙에 흩어져 만들어지고, 엔진은 std::vector<GameObject*>를 돌며 가상 함수 Update()를 부릅니다. CPU 입장에서는 포인터를 따라 메모리 이곳저곳으로 뛰어다니는 셈입니다. 매 프레임 1000개 캐릭터의 위치만 갱신하고 싶어도 위치와 상관없는 멤버(이름, 메시 포인터, 체력 …)까지 캐시로 끌려 들어옵니다.

    핵심 개념엔티티 · 컴포넌트 · 시스템

    ECS(Entity-Component-System)는 이 두 문제를 "데이터와 로직을 떼어 놓는" 방식으로 풉니다.

    요소정체ProjectE에서
    엔티티 (Entity)그냥 번호. 아무 데이터도 로직도 없다FEntity = 슬롯 인덱스 + 세대, 8바이트
    컴포넌트 (Component)엔티티에 붙는 순수 데이터 묶음POD에 가까운 struct (FTransformComponent, FHealthComponent …)
    시스템 (System)"이 컴포넌트들을 가진 모든 엔티티"를 돌며 일하는 로직View<A, B>().Each(...)를 쓰는 함수나 클래스 (FPhysicsSystem, FAnimationSystem …)

    CLAUDE.md는 이 원칙을 규칙으로 적어 둡니다. "컴포넌트는 POD에 가까운 struct, 로직은 시스템(뷰 순회)에 둔다." 컴포넌트에 가상 함수나 복잡한 메서드를 넣기 시작하면 다시 객체 지향으로 돌아가는 셈입니다.

    비유: 회사 인사 기록 사원 번호(엔티티)는 그냥 번호입니다. 인사팀은 "번호 → 연락처" 표를, 급여팀은 "번호 → 급여" 표를, 보안팀은 "번호 → 출입 권한" 표를 따로 가집니다. 급여팀이 월급을 계산할 때는 급여 표만 처음부터 끝까지 훑으면 되고, 연락처 표는 건드리지 않습니다. 컴포넌트 타입마다 표(풀)가 따로 있고, 시스템은 필요한 표만 읽는 것 — 이것이 ECS입니다.

    데이터 지향: 왜 "같은 종류끼리 모아 두기"가 빠른가

    CPU는 메모리를 한 바이트씩 읽지 않고 캐시 라인(보통 64바이트) 단위로 가져옵니다. 다음에 읽을 데이터가 방금 가져온 줄 안에 있으면 거의 공짜이고, 멀리 떨어져 있으면 수백 사이클을 기다립니다. 같은 타입 컴포넌트를 빈틈없는 배열에 모아 두면, 시스템이 배열을 앞에서부터 읽을 때 다음 원소가 이미 캐시에 있거나 하드웨어 프리페처가 미리 가져다 놓습니다. 이것이 데이터 지향 설계(Data-Oriented Design)의 핵심입니다. "객체 하나를 잘 표현하는 것"보다 "같은 일을 수천 번 하는 순회를 빠르게 하는 것"을 먼저 생각합니다.

    핵심 개념희소 집합 — 세 가지를 동시에 얻는 자료 구조

    컴포넌트 풀이 해야 할 일은 셋입니다. ① 엔티티 번호로 컴포넌트를 바로 찾기, ② 컴포넌트를 빨리 지우기, ③ 모든 컴포넌트를 빈틈없이 순회하기. 배열 하나로는 ①과 ③이 충돌합니다(엔티티 번호를 인덱스로 쓰면 빈칸이 생기고, 빈칸 없이 모으면 번호로 찾을 수 없음). 희소 집합(sparse set)은 배열 두 개로 둘 다 얻습니다.

    • Sparse: 엔티티 인덱스 → 밀집 배열의 몇 번째인지. 빈칸이 많아도 된다(이름이 "희소").
    • Dense(+Components): 컴포넌트를 가진 엔티티와 그 컴포넌트가 빈틈없이 나란히. 순회는 이것만 본다.

    2부 소개의 그림 2-1이 이 구조입니다. 찾기는 Sparse[엔티티] 한 번이면 O(1)이고, 순회는 Components 배열을 처음부터 끝까지 읽으면 됩니다. 남은 문제는 삭제입니다. 중간 원소를 지우고 뒤를 한 칸씩 당기면 O(n)이고, 당겨진 모든 원소의 Sparse 값을 고쳐야 합니다. 그래서 마지막 원소와 맞바꾸고 꼬리를 자르는 swap-remove를 씁니다.

    실제 코드가 그림과 똑같습니다.

    // 희소 집합 기반 컴포넌트 풀.
// Sparse[엔티티 인덱스] → 밀집 인덱스, Dense/Components는 빈틈없이 연속 저장되어 순회가 빠르다.
// 제거는 마지막 원소와 교환(swap-remove)하므로 순회 중 제거는 허용하지 않는다.
template <typename T>
class TSparseSet final : public FSparseSetBase
{
	...
	void Remove(FEntity Entity) override
	{
		if (!Contains(Entity)) { return; }
		const uint32 DenseIndex = Sparse[Entity.Index];
		const uint32 LastIndex  = static_cast<uint32>(Dense.size() - 1);
		if (DenseIndex != LastIndex)
		{
			// 마지막 원소를 빈자리로 이동
			const FEntity LastEntity = Dense[LastIndex];
			Dense[DenseIndex]        = LastEntity;
			Components[DenseIndex]   = std::move(Components[LastIndex]);
			Sparse[LastEntity.Index] = DenseIndex;
		}
		Dense.pop_back();
		Components.pop_back();
		Sparse[Entity.Index] = InvalidDense;
	}
private:
	std::vector<uint32>  Sparse;
	std::vector<FEntity> Dense;
	std::vector<T>       Components;
};

    Contains도 눈여겨보세요. Sparse가 가리키는 칸의 엔티티가 세대까지 같은지 비교합니다(Dense[DenseIndex] == Entity). 이것이 바로 다음 절의 "세대 핸들"과 맞물리는 부분입니다.

    핵심 개념세대 핸들 — 지워진 물체를 가리키는 번호

    엔티티 번호를 다 쓰면 재사용해야 합니다. 그렇지 않으면 탄환을 쏠 때마다 번호가 하나씩 늘어 배열이 끝없이 커집니다. 그런데 재사용에는 함정이 있습니다. 적 AI가 "내 목표는 엔티티 5번"이라고 기억하고 있었는데, 5번이 죽어 지워지고 그 자리에 새로 생긴 나무가 5번을 받으면? AI는 나무를 쫓아갑니다. C++의 댕글링 포인터와 같은 문제가 번호 수준에서 일어나는 것입니다.

    해결책은 번호에 세대(generation)를 붙이는 것입니다. 슬롯마다 "몇 번째로 재사용되었는가"를 세고, 핸들은 (슬롯, 세대) 쌍으로 들고 다닙니다. 슬롯이 파괴되면 세대를 1 올리므로, 예전 핸들은 세대가 맞지 않아 자동으로 무효가 됩니다.

    // 엔티티 식별자: 슬롯 인덱스 + 세대(재사용된 슬롯의 오래된 핸들을 구별)
struct FEntity
{
	static constexpr uint32 InvalidIndex = ~0u;
	uint32 Index      = InvalidIndex;
	uint32 Generation = 0;
	// 64비트 하나로 (저장·해시·네트워크용)
	constexpr uint64 ToId() const { return (static_cast<uint64>(Generation) << 32) | Index; }
};
    FEntity Create()
{
	FEntity Entity;
	if (!FreeIndices.empty()) { Entity.Index = FreeIndices.back(); FreeIndices.pop_back(); } // 재사용
	else { Entity.Index = static_cast<uint32>(Generations.size()); Generations.push_back(0); }
	Entity.Generation = Generations[Entity.Index];
	++AliveCount;
	return Entity;
}

// 모든 컴포넌트를 제거하고 슬롯을 재사용 목록에 넣는다 (세대 증가로 기존 핸들 무효화)
void Destroy(FEntity Entity)
{
	if (!IsValid(Entity)) { return; }
	for (std::unique_ptr<FSparseSetBase>& Pool : Pools)
	{
		if (Pool) { Pool->Remove(Entity); }   // 타입을 몰라도 지울 수 있게 가상 함수
	}
	++Generations[Entity.Index];
	FreeIndices.push_back(Entity.Index);
	--AliveCount;
}

    이 동작은 테스트 ECS_StaleHandleDoesNotAliasReusedSlot이 그대로 확인합니다. 엔티티를 지우고 새로 만들면 같은 인덱스를 받지만, 옛 핸들로 Has/TryGet을 부르면 새 엔티티의 컴포넌트가 보이지 않아야 합니다.

    같은 아이디어는 엔진 곳곳에 다시 나옵니다. GPU 리소스(메시·텍스처·머티리얼)도 포인터 대신 THandle(인덱스 + 세대)로 참조하는데, 이것은 6강의 TResourcePool에서 이미 본 구조입니다.

    핵심 개념View — 여러 컴포넌트의 교집합 순회

    시스템은 대개 컴포넌트 여러 개를 함께 원합니다. "트랜스폼과 체력을 모두 가진 엔티티". 풀은 타입마다 따로이니, 두 집합의 교집합을 구해야 합니다. 방법은 단순합니다. 가장 작은 풀을 골라 그것을 순회하고, 나머지 풀에는 Contains로 물어봅니다. 교집합은 가장 작은 집합보다 클 수 없으므로 이것이 최소한의 일입니다.

    template <typename... TComponents>
template <typename TFunc>
void TView<TComponents...>::Each(TFunc&& Func)
{
	std::tuple<TSparseSet<TComponents>*...> PoolTuple{ Registry.TryGetPool<TComponents>()... };
	const std::vector<FEntity>* SmallestEntities = GetIterationEntities();
	if (SmallestEntities == nullptr) { return; }

	// 순회 중 풀 변경을 허용하지 않으므로 목록 복사 없이 순회
	for (size_t Index = 0; Index < SmallestEntities->size(); ++Index)
	{
		const FEntity Entity = (*SmallestEntities)[Index];
		bool bHasAll = true;
		std::apply([&](auto*... Pools) { ((bHasAll = bHasAll && Pools->Contains(Entity)), ...); }, PoolTuple);
		if (!bHasAll) { continue; }
		std::apply([&](auto*... Pools) { Func(Entity, Pools->Get(Entity)...); }, PoolTuple);
	}
}

    C++17의 접기 식(fold expression) (... , ...)과 std::apply로 "타입 개수만큼 반복"을 컴파일 타임에 풉니다. 사용하는 쪽은 이렇게 간단합니다. Sample 게임 모듈의 회전 시스템입니다.

    Registry.View<FTransformComponent, FSpinnerComponent>().Each(
	[DeltaSeconds](FEntity, FTransformComponent& Transform, FSpinnerComponent& Spinner) {
		const FVector3 Axis = Spinner.Axis.GetNormalized();
		...   // 회전 갱신 — 컴포넌트는 데이터, 로직은 여기(시스템)
	});
    규칙: View<...>().Each 순회 중 같은 타입 컴포넌트를 추가·제거하지 않는다 이유는 둘입니다. ① 제거는 swap-remove라 아직 안 본 마지막 원소가 이미 지나간 자리로 옮겨져 건너뛰어집니다(그림 7-2). ② 추가는 std::vector가 자라며 메모리를 다시 잡을 수 있어, 람다가 받은 T& 참조와 순회 중인 목록 포인터가 허공을 가리키게 됩니다. Each가 "목록 복사 없이" 도는 것은 이 규칙을 전제로 한 최적화입니다. 바꿔야 한다면 대상을 모아 두었다가 순회가 끝난 뒤 적용합니다. FScene::DestroyEntity가 자식 목록을 복사해서 도는 것도 같은 이유입니다.

    ProjectE에서는레지스트리와 타입 ID

    FRegistry는 엔티티 수명(세대 배열, 빈 슬롯 목록)과 컴포넌트 타입마다 하나씩인 풀을 가집니다. 풀은 std::vector<std::unique_ptr<FSparseSetBase>>이고, 인덱스는 컴포넌트 타입의 타입 ID입니다. FSparseSetBase는 Remove/Contains 같은 가상 함수만 가진 타입 소거(type erasure) 기반 클래스입니다. Destroy는 엔티티가 어떤 타입들을 가졌는지 모르므로 모든 풀에 "이 엔티티 지워"라고 가상 호출로 말합니다.

    그러면 타입 ID는 어떻게 정할까요? 처음 구현은 교과서적인 방법이었습니다. 템플릿 함수 안의 static 변수로 "처음 불린 순서대로 0, 1, 2 …"를 매기는 것입니다. 지금 코드는 한 단계가 더 있습니다.

    // 엔진 DLL과 게임 모듈 DLL이 같은 타입에 같은 ID를 쓰도록 ID 표는 Core(엔진 DLL) 한 곳에 둔다.
// 바이너리별 지역 static은 조회 결과 캐시일 뿐이다. 키는 std::type_index
template <typename T>
static uint32 GetTypeId()
{
	static const uint32 TypeId = AssignComponentTypeId(std::type_index(typeid(T)));
	return TypeId;
}

// Registry.cpp — 프로세스 전역 (엔진 DLL 안에 하나). 첫 사용 순서대로 0, 1, 2 ... (버린 ID는 다시 쓰지 않는다)
uint32 FRegistry::AssignComponentTypeId(std::type_index Type)
{
	FComponentTypeIdTable& Table = GetComponentTypeIdTable();
	std::scoped_lock       Lock(Table.Mutex);
	const auto [It, bInserted] = Table.Ids.try_emplace(Type, Table.NextId);
	if (bInserted) { ++Table.NextId; }
	return It->second;
}

    왜 이렇게까지 할까요? 템플릿 함수의 지역 static은 그 함수를 인스턴스화한 바이너리마다 따로 생깁니다. 엔진 DLL 안에서 GetTypeId<FTransformComponent>()가 3을 받았어도, 게임 모듈 DLL 안의 같은 함수는 자기만의 카운터로 0을 받을 수 있습니다. 그러면 게임 모듈이 3번 풀(트랜스폼)을 0번 풀(이름?)로 착각해 캐스팅합니다. 그래서 진짜 표는 엔진 DLL 안 한 곳(Registry.cpp)에 두고, 키는 std::type_index로 합니다(MSVC는 타입 장식 이름으로 비교하므로 DLL이 달라도 같은 타입은 같은 키). 지역 static은 "한 번 물어본 답을 기억하는 캐시"로만 남았습니다. 이 함정은 12강에서 엔진 DLL 전체 이야기와 함께 다시 봅니다.

    이 표에는 RetireComponentTypeId도 있습니다. 게임 모듈을 에디터에서 다시 로드할 때(12강), 구조체 멤버가 바뀐 새 컴포넌트 타입이 옛 풀을 자기 타입으로 잘못 캐스팅하지 않도록 옛 ID를 버리고 새 ID를 받게 합니다. 버린 번호는 다시 쓰지 않으므로 NextId를 표와 따로 셉니다.

    왜 직접 만들었나 (EnTT 같은 라이브러리 대신) 0강의 기준대로 ECS는 "엔진의 성격과 성능을 결정하는 것"이라 직접 구현했습니다. 덕분에 리플렉션(9강)·DLL 경계 타입 ID·핫 리로드용 ID 폐기처럼 엔진 사정에 맞춘 기능을 자유롭게 넣을 수 있었습니다. 구현 자체는 Core/ECS/ 네 파일, 합쳐서 약 490줄입니다. Phase 3에서 테스트 5개(ECS_EntityLifetime, ComponentAddGetRemove, StaleHandleDoesNotAliasReusedSlot, SwapRemoveKeepsPoolConsistent, ViewIteratesIntersection)와 함께 들어왔습니다.

    함정과 교훈

    실제로 겪은 일: DLL마다 다른 타입 ID 엔진을 ProjectEEngine.dll로 묶고 게임 모듈 DLL이 컴포넌트를 등록하게 만든 날(2026-09-30), 위의 "지역 static 카운터" 방식으로는 엔진과 게임 모듈이 같은 컴포넌트에 서로 다른 번호를 매길 수 있다는 점이 문제가 됐습니다. 그 커밋에서 타입 ID를 엔진 DLL의 전역 표(std::type_index 키)로 옮겼고, CLAUDE.md에 "헤더 인라인 템플릿의 함수 지역 static처럼 바이너리마다 따로 생기는 상태에 전역 의미를 두지 않는다"는 규칙이 생겼습니다.
    • View도 공짜는 아니다: 엔티티마다 Contains와 Get을 풀 수만큼 부릅니다. 8강에서 볼 트랜스폼 갱신의 루트 찾기는 View<트랜스폼, 계층>::Each(엔티티당 조회 4번)를 쓰다가, 풀 배열을 직접 묶음으로 나눠 도는 방식으로 바꿔 순차 0.22ms → 0.05ms가 됐습니다. 아주 뜨거운 경로에서는 풀을 직접 보는 것이 낫습니다.
    • 테스트 매크로와 템플릿 쉼표: E_EXPECT_EQ(Registry.View<A, B>().Count(), 2)처럼 쓰면 전처리기가 꺾쇠를 모르기 때문에 View<A와 B>()...를 서로 다른 매크로 인자로 자릅니다. CLAUDE.md 규칙대로 지역 변수로 먼저 받습니다.
    • 순서에 기대지 말 것: swap-remove 때문에 Dense 순서는 생성 순서가 아닙니다. 씬 저장처럼 순서가 의미 있는 곳은 계층(부모 → 자식)이나 별도 기준으로 정렬합니다.
    정리
    • ECS = 엔티티(번호) + 컴포넌트(순수 데이터) + 시스템(순회 로직). 상속 대신 조합으로 물체를 표현한다.
    • 같은 타입 컴포넌트를 연속 배열에 모으면 캐시 친화적으로 순회할 수 있다(데이터 지향).
    • 희소 집합: Sparse(번호 → 위치) + Dense(빈틈없는 배열). 찾기·삭제 O(1), 삭제는 swap-remove.
    • 엔티티 핸들 = (슬롯, 세대). 파괴 시 세대를 올려 옛 핸들을 자동 무효화한다.
    • View는 가장 작은 풀을 돌고 나머지는 Contains로 확인. 순회 중 같은 타입 추가/제거 금지.
    • 타입 ID 표는 엔진 DLL 한 곳에 — 지역 static은 바이너리마다 따로 생긴다.

    생각해 볼 문제

    Q1. 컴포넌트 A를 가진 엔티티가 10만 개, B를 가진 엔티티가 20개입니다. View<A, B>와 View<B, A>의 비용은 다를까요? 다르지 않습니다. 두 경우 모두 GetIterationEntities가 크기를 비교해 B 풀(20개)을 기준으로 고르고, A 풀에는 Contains만 20번 묻습니다. 타입 순서는 크기가 같을 때의 기준(앞 타입)과 람다 인자 순서만 정합니다.
    Q2. 스크립트가 다른 엔티티의 FEntity를 컴포넌트 프로퍼티에 저장해 두었는데 그 엔티티가 파괴됐습니다. 다음 프레임에 그 값으로 TryGet을 부르면? 파괴 시 그 슬롯의 세대가 올라갔으므로 IsValid가 거짓이 되고, 희소 집합의 Contains도 Dense에 들어 있는 (인덱스, 세대)와 비교하므로 nullptr를 돌려줍니다. 슬롯이 이미 다른 엔티티에게 재사용되었더라도 세대가 다르므로 엉뚱한 물체를 건드리지 않습니다. 단, 세대는 32비트이므로 같은 슬롯이 약 43억 번 재사용되면 한 바퀴 돌 수 있다는 이론적 한계는 있습니다.
    Q3. "체력이 0인 엔티티를 모두 지우는" 시스템을 View<FHealthComponent>().Each 안에서 바로 Registry.Destroy로 구현하면 어떤 버그가 날까요? 어떻게 고칠까요? Destroy는 체력 풀에서도 swap-remove를 하므로, 순회 중인 바로 그 배열의 마지막 원소가 현재 위치로 옮겨집니다. 루프는 다음 인덱스로 넘어가므로 옮겨진 엔티티를 검사하지 않고 지나치고, 경우에 따라 람다가 받은 참조도 다른 원소를 가리키게 됩니다. 순회 중에는 지울 대상을 목록에 모으고, 순회가 끝난 뒤 한꺼번에 지웁니다. (ProjectE의 스크립트 Destroy()가 "프레임 끝에 지연 적용"인 것도 같은 이유입니다.)

    씬 그래프와 트랜스폼

    관련 Phase: 3 (계층), 2026-10-04 트랜스폼 캐시 · 살펴볼 곳: Engine/Source/Scene/Scene.h, Scene.cpp, Scene/Components.h (FTransformComponent, FHierarchyComponent), Tests/RendererTests/SceneTests.cpp
    이 강의를 마치면
    • 로컬 트랜스폼과 월드 행렬의 관계, 그리고 계층을 따라 행렬을 곱하는 순서를 설명할 수 있습니다.
    • 부모 변경(SetParent)에서 순환을 막는 방법과 재귀 파괴의 순서를 압니다.
    • "입력이 비트 단위로 같으면 계산을 건너뛴다"는 캐시가 왜 전체 재계산과 비트 동일한 결과를 보장하는지 이해합니다.
    • 루트별 하위 트리를 병렬로 갱신해도 결과와 순서가 순차 갱신과 같게 만드는 방법을 압니다.

    왜 필요한가물체는 다른 물체에 붙어 움직인다

    자동차가 달리면 바퀴도 함께 갑니다. 캐릭터가 손을 들면 손에 쥔 칼도 따라 올라갑니다. 이때 바퀴의 위치를 매 프레임 "월드 어디"로 직접 계산해 넣는 것은 비현실적입니다. 대신 바퀴는 "차체 기준으로 앞쪽 오른편 아래"라는 상대 위치만 갖고, 차체가 움직이면 엔진이 그 관계를 따라 바퀴의 실제 위치를 계산하게 합니다.

    이 "누가 누구에게 붙어 있는가"의 트리를 씬 그래프(scene graph) 또는 계층(hierarchy)이라고 합니다. Phase 3의 완료 기준(DoD)에도 "회전하는 부모 아래 큐브 링이 따라 돈다(계층)"가 들어 있었습니다. 계층은 렌더링뿐 아니라 에디터 계층 패널, 프리팹, 모델 노드(뼈), 소켓 부착, 서브 씬이 모두 기대는 구조입니다.

    핵심 개념로컬 트랜스폼과 월드 행렬

    각 엔티티의 FTransformComponent는 사람이 편집하는 로컬 값(위치·회전·스케일, 줄여서 TRS)을 저장합니다. "부모 기준으로 어디에, 어느 방향으로, 얼마나 크게"입니다. 렌더러·물리·오디오가 필요로 하는 것은 월드 공간의 최종 변환이므로, 엔진이 이를 월드 행렬로 계산해 같은 컴포넌트에 캐시해 둡니다.

    ProjectE의 행렬은 행벡터 규약(v * M, 4강)을 쓰므로 "먼저 적용할 것을 왼쪽에" 둡니다. 로컬 행렬은 S * R * T(스케일 → 회전 → 이동), 그리고 월드 행렬은 다음 한 줄입니다.

    식 World자식 = Local자식 × World부모   (루트는 World = Local)
    풀어 쓰면 World손자 = Local손자 × Local자식 × Local루트. 점 하나를 손자의 공간에서 월드로 보내려면 손자 → 자식 → 루트 공간을 차례로 거친다는 뜻입니다. 
    // 로컬 트랜스폼 + 캐시된 월드 행렬 (FScene::UpdateTransforms가 계층 순서로 갱신)
struct FTransformComponent
{
	FVector3 Position;
	FQuat    Rotation;
	FVector3 Scale = FVector3::OneVector;

	FMatrix4x4 WorldMatrix;   // 파생 값 — 리플렉션에 등록하지 않는다(저장 안 함)
	...
	FMatrix4x4 GetLocalMatrix() const { return FMatrix4x4::MakeTransform(Position, Rotation, Scale); }
};

// 부모/자식 관계. FScene::SetParent로만 변경한다.
struct FHierarchyComponent
{
	FEntity              Parent;
	std::vector<FEntity> Children;
};

    계층은 양방향으로 저장합니다. 자식은 부모를 알고(위로 올라가며 조상 확인), 부모는 자식 목록을 압니다(아래로 내려가며 갱신·파괴). 대가는 두 정보가 항상 일치해야 한다는 것입니다. 그래서 CLAUDE.md는 "계층 변경은 반드시 FScene::SetParent"를 규칙으로 둡니다. 누군가 Parent 필드만 직접 바꾸면 옛 부모의 Children에 유령이 남습니다.

    핵심 개념SetParent — 순환을 거부하기

    트리는 순환이 없어야 트리입니다. 에디터 계층 패널에서 사용자가 "할아버지"를 "손자" 밑으로 끌어다 놓으면? 그대로 받아들이면 갱신 재귀가 끝나지 않고 스택이 터집니다. SetParent(Child, Parent)는 새 부모가 자기 자신이거나 자기 자손이면 거부합니다. "Parent가 Child의 자손인가?"는 Parent에서 위로 올라가며 Child를 만나는지 보면 됩니다.

    void FScene::SetParent(FEntity Child, FEntity Parent)
{
	...
	if (Parent.IsValid() && (Parent == Child || IsAncestorOf(Child, Parent)))
	{
		E_LOG(LogScene, Warning, "순환 계층은 허용되지 않습니다 (엔티티 {} → {})", Child.Index, Parent.Index);
		return;
	}
	// 기존 부모에서 제거
	if (FHierarchyComponent* OldParent = Registry.TryGet<FHierarchyComponent>(ChildHierarchy->Parent))
	{
		std::erase(OldParent->Children, Child);
	}
	// 새 부모에 추가
	...
	ChildHierarchy->Parent = Parent;
}

void FScene::DestroyEntity(FEntity Entity)
{
	if (!Registry.IsValid(Entity)) { return; }
	// 자식 먼저 (목록을 복사해 순회 중 변경 회피)
	if (FHierarchyComponent* Hierarchy = Registry.TryGet<FHierarchyComponent>(Entity))
	{
		const std::vector<FEntity> Children = Hierarchy->Children;
		for (FEntity Child : Children) { DestroyEntity(Child); }
	}
	SetParent(Entity, NullEntity);   // 부모의 자식 목록에서 빠진다
	Registry.Destroy(Entity);
}

    파괴는 자식부터 재귀로 합니다. 자식 목록을 복사해 두는 이유는, 자식이 파괴되며 SetParent(자식, Null)로 바로 이 목록에서 자기를 지우기 때문입니다(7강의 "순회 중 변경 금지"와 같은 문제). 이 동작은 테스트 Scene_ReparentAndCycleRejection, Scene_DestroyEntityRecursive가 지킵니다. 참고로 부모 변경은 로컬 값을 그대로 두므로, 월드 위치를 유지한 채 부모를 바꾸고 싶은 에디터 코드는 로컬 값을 새 부모 기준으로 다시 계산해 넣어야 합니다.

    핵심 개념UpdateTransforms — 한 프레임에 한 번, 위에서 아래로

    월드 행렬은 FScene::UpdateTransforms()가 한꺼번에 계산합니다. 매번 위치를 바꿀 때마다 자손 전체를 다시 계산하면(즉시 갱신) 한 프레임에 같은 엔티티를 여러 번 계산하게 되므로, ProjectE는 "로컬 값은 언제든 바꾸고, 월드는 정해진 시점에 한 번"을 택했습니다. 게임 월드 갱신 순서(7부)에서 이 함수는 물리 뒤, 애니메이션 뒤 등 정해진 자리에서 불립니다.

    현재 구현은 세 단계입니다.

    // 2) 루트 하위 트리는 서로 겹치지 않으므로 병렬로 갱신한다 (하위 트리의 월드 행렬은 그 루트를 맡은 스레드만 쓰고, 읽는 것은 계층·로컬 값뿐).
//    미룬 부착 목록은 루트별로 모아 루트 순서대로 이어 붙인다 → 순차 갱신과 같은 순서·같은 결과
FParallel::ParallelFor(RootCount, 16, [this](uint32 Begin, uint32 End) {
	for (uint32 Index = Begin; Index < End; ++Index)
	{
		RootDeferred[Index].clear();
		UpdateTransformRecursive(TransformRoots[Index], FMatrix4x4::Identity, true, RootDeferred[Index]);
	}
});
for (uint32 Index = 0; Index < RootCount; ++Index)
{
	DeferredAttachments.insert(DeferredAttachments.end(), RootDeferred[Index].begin(), RootDeferred[Index].end());
}

    병렬화가 안전한 근거는 루트 하위 트리끼리는 겹치지 않는다는 트리의 성질입니다. 엔티티 하나는 부모가 하나뿐이므로 정확히 한 루트에 속하고, 그 루트를 맡은 스레드만 그 엔티티의 WorldMatrix를 씁니다. 예외는 소켓 부착(42강)입니다. 칼이 손 뼈에 붙어 있으면 칼의 부모 행렬은 계층 부모가 아니라 다른 루트(캐릭터 모델) 아래 뼈의 월드 행렬입니다. 그래서 부착 엔티티는 ②에서 건너뛰어 목록에 모아 두었다가, 모든 뼈가 계산된 뒤 ③에서 처리합니다. 로컬 ↔ 월드를 변환하는 코드(기즈모, 물리, 스크립트)가 GetTransform(Parent).WorldMatrix 대신 FScene::GetParentWorldMatrix를 써야 하는 이유도 이것입니다.

    핵심 개념비트 동일 캐시 — "같은 입력이면 같은 결과"

    큰 씬에서 실제로 움직이는 물체는 일부입니다. 건물, 바닥, 나무는 매 프레임 같은 월드 행렬을 다시 계산할 뿐입니다. 흔한 해법은 더티 플래그(dirty flag)입니다. 로컬 값을 바꾸는 쪽이 "나 바뀜" 표시를 하고, 갱신은 표시된 것만 계산합니다. 하지만 ProjectE에서 로컬 값을 쓰는 쪽은 스크립트, 물리, 애니메이션, 네트워크 복제, 에디터 기즈모, 게임 모듈 … 너무 많고, 한 곳이라도 표시를 잊으면 물체가 화면에서 멈춰 버리는 버그가 생깁니다.

    ProjectE의 답은 표시를 아무에게도 요구하지 않는 캐시입니다. 엔티티마다 "월드 행렬을 마지막으로 계산할 때 쓴 입력" — 로컬 TRS와 부모 월드 행렬 — 을 저장해 두고, 이번 입력이 그것과 memcmp로 비트 단위로 같으면 계산을 건너뜁니다.

    // 월드 행렬 = 로컬 × 부모 월드. 입력(로컬 TRS, 부모 월드)이 마지막 계산과 비트 단위로 같으면 그대로 둔다 — 같은 입력이면 같은 결과이므로
// 전체 재계산과 비트 동일하다. 로컬을 쓰는 쪽(스크립트·물리·애니메이션·복제·편집기)이 표시할 필요가 없다
void UpdateWorldMatrix(FTransformComponent& Transform, const FMatrix4x4& ParentWorld, bool bUseCache)
{
	FTransformComponent::FWorldCache& Cache = Transform.WorldCache;
	if (bUseCache && Cache.bValid && BitEqual(Cache.Position, Transform.Position) && BitEqual(Cache.Rotation, Transform.Rotation) &&
	    BitEqual(Cache.Scale, Transform.Scale) && BitEqual(Cache.ParentWorld, ParentWorld))
	{
		return;
	}
	// 행벡터 규약: Local * Parent
	Transform.WorldMatrix = Transform.GetLocalMatrix() * ParentWorld;
	Cache.Position = Transform.Position;  Cache.Rotation = Transform.Rotation;
	Cache.Scale    = Transform.Scale;     Cache.ParentWorld = ParentWorld;
	Cache.bValid   = true;
}

    몇 가지 설계 포인트를 짚어 봅시다.

    • 왜 오차 비교(ε)가 아니라 비트 비교인가? "거의 같으면 건너뛴다"면 아주 천천히 움직이는 물체가 영영 갱신되지 않거나, 결과가 전체 계산과 미세하게 달라집니다. 비트 비교는 "같은 입력"을 수학적으로 보장하므로 결과도 정확히 같습니다. 자동 스크린샷 검증(MD5 비교)이 캐시를 켜도 끄도 같은 화면을 요구하는 이 엔진에서는 중요한 성질입니다.
    • 왜 부모 월드도 입력인가? 그림 8-1처럼 부모만 움직이면 자식의 로컬 값은 그대로입니다. 부모 월드를 비교하지 않으면 자식이 제자리에 남습니다.
    • 예외: WorldMatrix를 직접 쓰는 코드. 캐시는 "WorldMatrix = 저장된 입력의 결과"라는 불변식에 기댑니다. 누군가 WorldMatrix를 직접 덮어쓰면 입력은 그대로이므로 다음 갱신이 건너뛰어 덮어쓴 값이 남습니다. 그래서 그런 코드(예: AI 시스템의 SetWorldPose)는 InvalidateWorldCache()를 부릅니다. 반대로 렌더 동안만 값을 바꾸고 정확히 되돌리는 코드(픽셀 아트 도트 스냅)는 불변식이 다시 성립하므로 부를 필요가 없습니다.
    • 캐시는 리플렉션에 등록하지 않는다. 저장되지 않고, 컴포넌트를 통째로 복사(CopyComponent)하면 WorldMatrix와 함께 옮겨져 일관됩니다.
    • 끄는 스위치를 남긴다. 콘솔 변수 scene.TransformCache(기본 1)로 끄면 매번 전체 계산합니다 — 결과가 같아야 하므로 비교 수단이 됩니다.

    함정과 교훈

    실제로 겪은 일: 테스트가 잡아낸 "부모 월드" 비교 캐시를 넣을 때 테스트 Scene_TransformCacheMatchesFullRecompute를 함께 만들었습니다. 엔티티 200개에 무작위로 부모를 정하고, 60프레임 동안 로컬 값 변경·부모 변경·생성/파괴·컴포넌트 통째 복사·WorldMatrix 직접 쓰기·소켓 뼈 이동을 섞은 뒤, 모든 월드 행렬이 "로컬 × 부모 월드"와 비트까지 같은지 확인합니다. 부모 월드 비교를 일부러 빼 보면 181건이 실패했습니다. "캐시가 결과를 바꾸지 않는다"를 말로 주장하지 않고 테스트로 못 박은 것입니다.
    측정: 무엇이 얼마나 빨라졌나 스킨 캐릭터가 가득한 Tests/Stress 씬(Release)에서 게임 틱의 트랜스폼 구간이 약 1.5ms → 0.8ms가 됐습니다(커밋 기록: 게임플레이 2회 + 표시 1회 합계 0.97~1.13 + 0.43~0.51ms → 0.60~0.75 + 0.15~0.16ms). 같은 커밋에서 루트 찾기를 View<트랜스폼, 계층>::Each(엔티티당 풀 조회 4번, 0.22ms)에서 풀 배열을 1024개 묶음으로 나눈 병렬 순회(0.05ms)로 바꿨고, 화면 MD5(Stress, 소켓을 쓰는 PixelArt, Materials)는 변하지 않았습니다. 그보다 앞서 하위 트리 병렬화는 애니메이션 포즈 병렬 평가와 함께 들어왔습니다.
    • 병렬화의 조건은 "같은 결과": 하위 트리를 병렬로 돌린 뒤 결과 목록을 스레드가 끝난 순서대로 합치면 실행마다 순서가 달라집니다. 루트 인덱스별 칸에 모았다가 루트 순서로 합치는 것이 핵심입니다.
    • "되돌리는 코드"와 "바꾸고 끝내는 코드"를 구분할 것: 픽셀 아트 도트 스냅(FPixelArtObjectSnap)은 씬 렌더 동안만 월드 행렬의 이동값을 바꾸고 정확히 되돌리므로 캐시를 무효화하지 않아도 됩니다. 반면 AI의 SetWorldPose처럼 바꾸고 끝내는 코드는 반드시 무효화해야 합니다. CLAUDE.md는 두 예를 모두 적어 두었습니다.

    • 엔티티는 로컬 TRS만 저장하고, 월드 = 로컬 × 부모 월드를 루트에서 잎으로 계산한다.

    생각해 볼 문제

    Q1. 부모가 1프레임에 한 번씩 미세하게 흔들리고, 그 아래 자손이 1만 개 있습니다. 이 캐시는 도움이 될까요? 거의 되지 않습니다. 부모 월드가 바뀌면 모든 자손의 "부모 월드" 입력이 바뀌므로 1만 개 모두 다시 계산합니다. 캐시가 이득을 보는 것은 "움직이지 않는 하위 트리"입니다. 다만 비교 비용(부모 행렬 64바이트 + TRS의 memcmp)은 쿼터니언 → 행렬 변환과 4×4 곱보다 대체로 가벼우므로, 전부 다시 계산하는 최악의 경우에도 추가 비용은 크지 않습니다.
    Q2. 물리 시스템이 강체 위치를 로컬 Position에 쓰는 대신 WorldMatrix에 바로 썼다고 해 봅시다. 화면에서 어떤 일이 생길까요? 그 엔티티의 로컬 TRS와 부모 월드가 지난 프레임과 같다면 다음 UpdateTransforms는 계산을 건너뛰므로, 이번 프레임엔 물리 값이 남아 보입니다. 그런데 다른 이유(예: 로컬 값 편집)로 입력이 바뀌는 순간 로컬 기준으로 다시 계산되어 물체가 원래 자리로 "순간 이동"합니다. 또 캐시를 끄면(scene.TransformCache 0) 매 프레임 덮어써져 화면이 달라집니다. 직접 쓰는 코드는 InvalidateWorldCache()를 부르거나, 원칙대로 로컬 값을 써야 합니다(ProjectE 물리는 실제로 로컬 트랜스폼에 씁니다).
    Q3. 루트가 1개(예: 모든 것을 담은 "World" 엔티티)뿐인 씬에서는 루트별 병렬화가 어떻게 될까요? 병렬화 단위가 루트 하위 트리이므로 작업이 하나뿐이라 사실상 순차로 돕니다. 하위 트리를 더 잘게 나누려면 "자식별 하위 트리"까지 내려가 작업을 쪼개야 하지만, 그만큼 합치는 순서 관리가 복잡해집니다. 큰 씬을 하나의 루트 밑에 묶는 습관은 이 구조에서 성능상 불리하다는 점을 기억해 둘 만합니다.

    왜 필요한가컴포넌트 N개 × 시스템 M개의 손 코드

    방향광 컴포넌트를 하나 새로 만들었다고 합시다. 에디터 인스펙터에 색과 강도를 편집하는 UI가 있어야 하고, 씬을 저장할 때 JSON에 써야 하고, 불러올 때 읽어야 하고, Lua에서 light.Intensity = 3이 되어야 하고, 멀티플레이에서는 서버 값을 클라이언트로 보내야 하고, 플레이 버튼을 누르면 편집 씬을 복제해야 합니다. 이걸 컴포넌트마다 손으로 짜면 컴포넌트 수 × 시스템 수만큼의 코드가 생기고, 필드 하나를 추가할 때마다 여섯 곳을 고쳐야 합니다. 한 곳을 빼먹는 순간 "저장은 되는데 Lua에서 안 보이는" 버그가 납니다.

    해결책은 각 컴포넌트가 자기 모양을 스스로 설명하게 하는 것입니다. "나는 Color(Vector3, 색)와 Intensity(float, 0~50)를 가진다." 이 설명을 읽는 범용 코드를 시스템마다 한 번만 짜면, 이후 컴포넌트는 설명만 추가하면 됩니다. 프로그램이 실행 중에 자기 타입 구조를 들여다보는 능력을 리플렉션(reflection)이라고 합니다. 2부 소개의 그림 2-2가 이 강의의 요점입니다.

    핵심 개념C++의 RTTI로는 부족하다

    C++에도 실행 시간 타입 정보(RTTI)가 있습니다. typeid(T)는 std::type_info를 돌려주고, 거기서 타입 이름 문자열과 "같은 타입인가" 비교 정도를 얻습니다. 하지만 "이 구조체에 어떤 멤버가 몇 번째 바이트에 있는가"는 알려 주지 않습니다. C#이나 Java는 런타임이 이 정보를 갖고 있지만, C++(이 프로젝트의 C++20)에는 멤버를 열거하는 표준 기능이 없습니다. 그래서 언리얼은 UPROPERTY() 매크로를 읽는 별도 코드 생성기(UHT)를 두고, ProjectE는 등록 코드를 손으로 한 줄씩 쓰는 더 단순한 방식을 택했습니다.

    매크로로 구조체 정의 자체를 감싸기별도 도구 없음구조체 선언이 읽기 어려워짐
    등록 함수에서 멤버 포인터로 기술 (ProjectE)평범한 C++, 구조체는 그대로 POD, 컴파일러가 타입 검사필드를 추가하면 등록 줄도 직접 추가해야 함

    핵심 개념프로퍼티 = 이름 + 타입 + 오프셋

    리플렉션의 원리는 놀랄 만큼 단순합니다. 구조체의 멤버는 객체 시작 주소에서 고정된 바이트 거리(오프셋)에 있습니다. "Intensity는 오프셋 12에 있는 float"라는 정보만 있으면, 어떤 방향광 객체의 주소 p가 주어지든 *(float*)(p + 12)로 값을 읽고 쓸 수 있습니다. 범용 코드는 구체 타입(FDirectionalLightComponent)을 몰라도 void*와 오프셋, 그리고 "그 자리에 무슨 타입이 있는지"만 알면 됩니다.

	size_t        Size   = 0;
	float MinValue = 0.0f, MaxValue = 0.0f, Step = 0.0f;   // 편집 범위
	...
	template <typename T>
	T& GetRef(void* Object) const
	{
		E_CHECKF(TPropertyTypeOf<T>::Value == Type, "프로퍼티 '{}' 타입 불일치", Name);
		return *static_cast<T*>(GetPtr(Object));   // GetPtr = (uint8*)Object + Offset
	}
};

    GetRef<T>가 E_CHECKF로 타입을 다시 확인하는 점에 주목하세요. void*와 오프셋은 강력한 만큼 위험합니다. float 자리를 문자열로 읽으면 메모리를 망가뜨리므로, 열거형과 요청 타입이 다르면 그 자리에서 멈춥니다(1강의 "문제가 생긴 그 자리에서 멈추기").

    지원하는 값 타입이 EPropertyType의 11가지로 닫혀 있다는 점도 설계입니다. 인스펙터·JSON·Lua·복제는 모두 이 열거형에 대한 switch로 동작하므로, 타입을 하나 늘리면 그 모든 switch를 함께 고쳐야 합니다. CLAUDE.md의 "프로퍼티 타입은 EPropertyType에 있는 것만 지원"이 그 뜻입니다. std::vector나 중첩 구조체는 프로퍼티가 될 수 없고, 그런 데이터는 문자열(에셋 경로, JSON)이나 별도 컴포넌트로 표현합니다. 예외적으로 4바이트 enum은 Int32로 취급하고 .Enum({...})으로 선택지 이름을 붙일 수 있습니다.

    등록 코드는 이렇게 생겼습니다. 메서드를 사슬처럼 잇는 유창한 빌더(fluent builder) 패턴입니다.

    &FTransformComponent::Position는 멤버 포인터(pointer to member)입니다. "어떤 FTransformComponent 객체든 그 안의 Position"을 가리키는 값으로, 타입이 FVector3 FTransformComponent::*입니다. 빌더는 이 타입에서 두 가지를 컴파일 타임에 뽑아냅니다.

    template <typename TMember>
TTypeBuilder& Property(TMember T::*Member, std::string Name, std::string DisplayName, uint32 Flags = PF_None)
{
	FPropertyInfo& PropertyInfo = Info.Properties.emplace_back();
	PropertyInfo.Name        = std::move(Name);
	PropertyInfo.DisplayName = std::move(DisplayName);
	PropertyInfo.Type        = TPropertyTypeOf<TMember>::Value;   // ① C++ 타입 → 열거형 (지원 안 하면 컴파일 오류)
	PropertyInfo.Flags       = Flags;
	PropertyInfo.Offset      = GetMemberOffset(Member);           // ② 바이트 오프셋
	PropertyInfo.Size        = sizeof(TMember);
	return *this;
}

// 멤버 포인터 → 바이트 오프셋 (생성자 호출 없이 계산)
template <typename T, typename TMember>
size_t GetMemberOffset(TMember T::*Member)
{
	alignas(T) static unsigned char Storage[sizeof(T)];
	const T* Object = reinterpret_cast<const T*>(Storage);
	return static_cast<size_t>(reinterpret_cast<const unsigned char*>(&(Object->*Member)) - Storage);
}
    1. 타입: TPropertyTypeOf<TMember>는 특수화로만 정의된 템플릿입니다(bool → Bool, FVector3 → Vector3 …). std::vector<int> 같은 지원하지 않는 멤버를 등록하면 특수화가 없어 컴파일 오류가 납니다. 실수가 실행 전에 잡힙니다.
    2. 오프셋: 표준 offsetof는 "표준 레이아웃" 타입에서만 보장되는데, 컴포넌트에는 std::string 같은 멤버가 섞입니다. 그래서 정적 저장소 위에서 멤버 포인터로 멤버 주소를 구하고 시작 주소를 빼는 방식으로 계산합니다. 객체를 실제로 생성하지 않으므로 생성자 부작용도 없습니다.

    마지막 .AsComponent()는 이 타입이 ECS 컴포넌트임을 표시하고, 레지스트리 조작 훅을 람다로 만들어 둡니다. 템플릿 안에서 만들어지므로 람다는 구체 타입 T를 알고, 바깥에서는 void*만 주고받습니다.

    Info.HasComponent    = [](const FRegistry& Registry, FEntity Entity) { return Registry.Has<T>(Entity); };
Info.GetComponent    = [](FRegistry& Registry, FEntity Entity) -> void* { return Registry.TryGet<T>(Entity); };
Info.AddComponent    = [](FRegistry& Registry, FEntity Entity) -> void* { return &Registry.GetOrEmplace<T>(Entity); };
Info.RemoveComponent = [](FRegistry& Registry, FEntity Entity) { Registry.Remove<T>(Entity); };
Info.CopyComponent   = [](FRegistry& Dest, FEntity DestEntity, const FRegistry& Source, FEntity SourceEntity) {
	Dest.GetOrEmplace<T>(DestEntity) = Source.Get<T>(SourceEntity);
};

    이 다섯 함수 덕분에 에디터는 "컴포넌트 추가" 메뉴를 등록된 타입 목록으로 자동 생성하고, 플레이 모드는 편집 씬을 컴포넌트 타입을 모른 채 통째로 복제할 수 있습니다.

    플래그 — 같은 정보를 시스템마다 다르게 해석하기

    모든 필드가 모든 시스템에 보여야 하는 것은 아닙니다. 런타임 GPU 핸들은 저장하면 안 되고(다음 실행에선 의미 없는 번호), 서버 전용 값은 클라이언트로 보내면 안 됩니다. 이 차이를 플래그로 표현합니다.

    PF_Transient가 "저장은 안 하지만 복제는 된다"는 점이 흥미롭습니다. 체력이나 매치 상태 같은 실행 중에만 의미 있는 값은 씬 파일에 들어가면 안 되지만, 멀티플레이에서는 클라이언트가 봐야 합니다. 저장과 복제를 별개의 축으로 둔 덕분에 이런 값을 표현할 수 있습니다.

    소유자(Owner)와 등록 시점

    엔진 컴포넌트는 RegisterSceneTypes()가 등록하고, FScene 생성자가 이것을 부르므로 씬이 있으면 등록은 보장됩니다(static bool로 한 번만). 물리·오디오·AI·UI 컴포넌트는 각 모듈의 Register*Types()를 앱이 씬 로드 전에 부릅니다. 게임 모듈이 등록하는 동안에는 레지스트리의 "현재 소유자"가 모듈 이름으로 바뀌어 각 FTypeInfo::Owner에 기록됩니다. 모듈을 내릴 때 RemoveTypesByOwner로 그 타입만 지우는데, 훅 람다가 모듈 DLL의 코드를 가리키므로 DLL보다 오래 살게 두면 안 되기 때문입니다.

    함정과 교훈

    등록하지 않으면 존재하지 않는 것과 같다 플레이 모드는 FSceneCloner가 리플렉션 CopyComponent 훅으로 편집 씬을 복제합니다. 그래서 리플렉션에 등록되지 않은 컴포넌트는 플레이 씬에 복사되지 않습니다. 예외로 스킨·애니메이션 런타임처럼 일부러 등록하지 않은 런타임 전용 데이터는 FSceneCloner::CopyRuntimeData가 따로 복사·재매핑합니다. "새 런타임 전용 엔티티 참조를 추가하면 여기에도 추가"가 CLAUDE.md 규칙으로 남아 있습니다.
    • 파생 값은 등록하지 않는다: WorldMatrix처럼 다른 값에서 계산되는 것을 저장하면, 불러올 때 로컬 값과 어긋난 두 진실이 생깁니다. 등록은 "원천 데이터"만.
    • 씬 enum은 번호로 저장된다: 씬 컴포넌트의 enum 프로퍼티는 JSON에 번호로 들어갑니다. 그래서 EDeathAction, EMatchState 같은 열거형은 끝에만 값을 추가합니다(중간에 끼우면 기존 씬의 값이 한 칸씩 밀림). 반면 설정 파일은 .Enum({이름, 표시})로 이름 문자열을 저장해 이 문제를 피합니다.
    • 관용적 읽기: JSON 적용(FReflectionJson::Apply)은 파일에 없는 키는 현재 값 유지, 모르는 키는 무시, 형식이 틀린 값은 경고 후 건너뛰고, Range가 있으면 잘라 넣습니다. 필드를 추가·삭제해도 옛 파일이 계속 열리는 이유입니다(10강).
    • 핫 리로드 후의 타입: 게임 모듈을 다시 로드하면 모듈 타입의 FTypeInfo*와 ECS 타입 ID가 바뀝니다. 그래서 "모듈 타입은 리플렉션으로만 다루고 타입 ID를 캐시하지 않는다"가 규칙입니다(12강).
    정리
    • C++ RTTI는 멤버 목록을 주지 않는다 → 엔진이 타입마다 "이름 + 타입 열거형 + 오프셋 + 플래그"를 직접 기록한다.
    • 범용 코드는 void* + 오프셋 + EPropertyType switch로 어떤 컴포넌트든 읽고 쓴다.
    • TTypeBuilder는 멤버 포인터에서 타입과 오프셋을 컴파일 타임에 뽑아 실수를 컴파일 오류로 만든다. AsComponent는 ECS 훅을 단다.
    • 한 번의 등록으로 인스펙터·씬 JSON·Lua·복제·프리팹·플레이 모드 복제가 따라온다.
    • 플래그는 시스템별 해석: Transient = 저장 제외/복제 O, NoReplicate = 복제 제외, 핸들은 둘 다 제외.

    생각해 볼 문제

    Q1. FHealthComponent에 std::vector<float> DamageHistory를 추가하고 .Property(&FHealthComponent::DamageHistory, ...)로 등록하려 하면 어떻게 될까요? TPropertyTypeOf<std::vector<float>> 특수화가 없으므로 컴파일 오류가 납니다. 지원 타입이 닫혀 있기 때문입니다. 이 데이터가 꼭 필요하면 등록하지 않는 런타임 필드로 두거나(저장·복제 안 됨), 문자열로 직렬화하거나, 지원 타입을 늘리되 인스펙터·JSON·Lua·복제의 switch를 모두 함께 고쳐야 합니다.
    Q2. 오프셋을 등록 시 한 번 계산해 저장해 두는데, Debug와 Release에서 std::string 크기가 다르다면 문제가 될까요? 되지 않습니다. 오프셋은 실행 중인 바이너리가 GetMemberOffset으로 자기 구조체 배치를 보고 계산하므로 항상 그 빌드에 맞습니다. 문제가 되는 것은 오프셋을 파일에 저장하거나 다른 빌드와 교환할 때입니다. 그래서 JSON과 네트워크 복제는 오프셋이 아니라 프로퍼티 이름을 키로 씁니다.
    Q3. 컴포넌트 필드 이름 Speed를 MoveSpeed로 바꾸고 등록 이름도 바꿨습니다. 기존 씬 파일을 열면 어떻게 될까요? 씬 JSON의 키는 프로퍼티 Name이므로 파일의 "Speed"는 "알 수 없는 프로퍼티"로 경고 후 무시되고, MoveSpeed는 기본값이 됩니다. 크래시는 나지 않지만 값이 사라집니다. C++ 멤버 이름만 바꾸고 등록 이름("Speed")은 유지하면 파일 호환이 지켜집니다 — 등록 이름은 파일 형식의 일부라는 뜻입니다. (데이터 테이블은 이를 위해 이름 변경 목록으로 파일을 함께 옮기는 SaveStructAndMigrate를 둡니다.)

    왜 필요한가사람과 기계는 다른 파일을 원한다

    씬 하나에는 엔티티 수백 개와 그 컴포넌트 값이 들어 있습니다. 이걸 파일로 남겨야 에디터를 닫았다 다시 열 수 있고, 게임이 맵을 불러올 수 있습니다. 메모리의 객체를 바이트나 텍스트로 바꾸는 일을 직렬화(serialization), 반대를 역직렬화라고 합니다.

    그런데 누가 그 파일을 읽느냐에 따라 좋은 형식이 다릅니다.

    • 사람(그리고 git): 열어서 읽을 수 있어야 하고, 두 사람이 고친 것을 병합할 수 있어야 하며, 무엇이 바뀌었는지 diff로 보여야 합니다. → 텍스트, JSON.
    • 엔진(실행 중): 최대한 빨리 읽어 GPU에 올려야 합니다. PNG를 매번 압축 해제하고, glTF를 매번 파싱하고, 셰이더를 매번 컴파일하는 것은 낭비입니다. → 미리 변환해 둔 엔진 전용 바이너리.

    ProjectE는 첫 결정 중 하나로 이것을 정했습니다(Plans.md 핵심 결정, 2026-09-30). "에디터가 다루는 씬/머티리얼/설정은 JSON, 런타임용은 쿠킹 단계에서 엔진 바이너리로 변환." 미리 변환하는 단계를 쿠킹(cooking)이라고 부릅니다. 효과는 바로 보였습니다. Phase 5에서 쿠킹을 넣자 DamagedHelmet 모델 로드가 Debug 기준 562ms → 120ms가 됐습니다(Plans.md 트랙 E).

    씬 파일 .escene은 9강의 리플렉션 정보만으로 쓰고 읽습니다. 엔티티마다 이름, 부모(파일 안 인덱스, 루트는 -1), 그리고 등록된 컴포넌트의 프로퍼티를 이름 키로 적습니다.

    {
  "Version": 1,
  "Entities": [
    {
      "Name": "Ground",
      "Parent": -1,
      "Components": {
        "TransformComponent": {
          "Position": [0.0, 0.0, -10.0],
          "Rotation": [0.0, 0.0, 0.0, 1.0],

          "MaterialAsset": "Materials/Checker.emat",

        }

    눈여겨볼 점이 몇 가지 있습니다.

    • 메시·머티리얼은 핸들이 아니라 경로 문자열로 저장됩니다. 핸들(THandle)은 이번 실행의 리소스 풀 번호일 뿐이므로 PF_Transient로 빼고, 불러온 뒤 FSceneAssetResolver가 경로에서 핸들을 다시 만듭니다.
    • 엔티티 참조(FEntity 프로퍼티, 부모)는 파일 안 배열 인덱스로 바뀝니다. 엔티티 슬롯 번호와 세대는 실행마다 달라지기 때문입니다.
    • 파생 값(WorldMatrix)과 런타임 생성물(FTransientComponent가 붙은 엔티티 — 예: 모델을 불러올 때 만든 노드 엔티티)은 저장하지 않습니다.

    읽을 때 가장 중요한 성질은 관용(寬容)입니다. 엔진은 계속 바뀝니다. 컴포넌트가 생기고 사라지고 필드가 바뀝니다. 그때마다 기존 씬 파일이 열리지 않으면 작업물이 모두 날아갑니다.

    // 씬 ↔ JSON (.escene). 리플렉션에 등록된 컴포넌트/프로퍼티를 기준으로 동작한다.
//   - 이름/계층은 구조적으로 기록 (Parent = 파일 내 인덱스, 루트는 -1)
//   - PF_Transient 프로퍼티와 리소스 핸들은 제외, FTransientComponent가 있는 엔티티(와 그 하위)는 제외
//   - 로드 시 알 수 없는 컴포넌트/프로퍼티는 경고 후 무시 (버전 간 호환)
//   - 엔티티 목록 직렬화는 프리팹(.eprefab)과 공유한다 (Scene/EntityJson.h)
struct FSceneSerializer
{
	static constexpr int32_t      Version   = 1;
	static constexpr const wchar_t* Extension = L".escene";
	...
};
    상황처리
    파일에 모르는 컴포넌트 (삭제된 타입, 안 불러온 게임 모듈)경고 "알 수 없는 컴포넌트 무시" 후 계속
    파일에 모르는 프로퍼티경고 후 무시
    파일에 없는 프로퍼티 (새로 추가된 필드)구조체 기본값 유지
    값 형식이 틀림 (숫자 자리에 문자열 등)경고 후 그 값만 건너뜀
    범위 밖의 숫자Range로 잘라 넣음
    파일 버전 > 엔진 버전"일부 데이터가 무시될 수 있습니다" 경고 후 최선을 다해 읽음
    JSON 자체가 깨짐 / Entities 배열 없음오류, 로드 실패 (씬은 건드리지 않음)

    원칙은 "읽을 수 있는 것은 최대한 읽고, 못 읽는 것은 크게 알린다"입니다. 경고로 남기므로 무엇이 사라졌는지는 로그에서 확인할 수 있습니다. JSON 파서도 주석을 허용하도록(ignore_comments) 엽니다. 로드 끝에는 프리팹 인스턴스를 원본의 현재 내용으로 맞추고(SyncAllInstances, 프리팹 강의) 트랜스폼을 한 번 갱신합니다.

    서브 씬: 읽기를 두 단계로 나눈 이유 게임 중 큰 맵의 일부를 이어 붙일 때(서브 씬)는 ParseFile(파일 읽기 + JSON 파싱만, ECS 접근 없음 → 백그라운드 스레드 가능)과 AppendDocument(메인 스레드에서 엔티티 생성)로 나눕니다. 느린 부분(디스크·파싱)은 스레드로, ECS를 만지는 부분은 메인으로 — 이 분리는 7부의 맵 전환에서 다시 나옵니다.

    핵심 개념쿠킹 캐시는 언제 믿을 수 있나

    캐시의 어려움은 언제나 같습니다. "이 캐시가 아직 유효한가?" 틀리게 "유효하다"고 하면 고친 내용이 반영되지 않는 기묘한 버그가, 틀리게 "무효"라고 하면 매번 다시 변환하는 느린 실행이 됩니다. FAssetCache는 여러 조건을 겹쳐 확인합니다.

    ① 형식 버전 — 엔진 쪽이 바뀌었을 때

    원본이 그대로여도 엔진의 쿠킹 형식이 바뀌면 옛 쿠킹 파일은 무효입니다. 정점에 탄젠트를 추가했거나, 단위를 cm로 바꿨다면 옛 파일을 그대로 읽으면 안 됩니다. 그래서 쿠킹 파일 맨 앞에 매직 번호와 형식 버전을 쓰고, 형식을 바꾸는 사람이 버전을 올립니다. 이 버전 주석은 그 자체로 엔진 역사의 요약입니다.

    static constexpr uint32 ModelMagic   = 0x4C444D45; // "EMDL"
static constexpr uint32 ModelVersion = 11; // 11: 스킨 메시 LOD, 10: 임포트 MaxTriangles + 잎 메시 솎아내기 LOD,
	// 9: 메시 UV 밀도(텍스처 밉 스트리밍), 8: 머티리얼 블렌드 모드/알파 컷오프/양면, 7: 메시 LOD,
	// 6: FBX + 임포트 설정(.eimport), 5: 이미지 BC 압축 + 밉, 4: 스킨/애니메이션,
	// 3: 센티미터 단위(glTF ×100), 2: 정점 탄젠트 + PBR
static constexpr uint32 TextureVersion = 1; // 1: 전체 밉 체인 + BC7/BC5/BC4 (용도별)

    읽기는 엄격합니다. LoadCookedFile은 읽기 함수가 성공하고, 읽는 도중 오류가 없고(IsOk), 정확히 파일 끝에서 끝나야(IsAtEnd) 성공으로 칩니다. 중간에 잘린 파일이나 형식이 미묘하게 다른 파일은 "손상되었거나 형식이 달라 원본을 다시 읽습니다" 경고 후 원본으로 돌아갑니다. CLAUDE.md의 규칙 "쿠킹 형식을 바꾸면 FAssetCache::*Version을 올린다"가 이 장치를 지키는 약속입니다.

    ② 시각 비교 — 원본이 바뀌었을 때

    "쿠킹 파일이 원본보다 새로우면 유효"는 가장 흔한 규칙입니다. 빌드 도구 make가 쓰는 방식이기도 합니다. 단, 원본이 없으면(패키지 배포본) 쿠킹본을 그대로 믿습니다. Content 밖의 파일은 캐시하지 않습니다.

    ③ 설정 기록 — 시각만으로 못 잡는 변경

    Phase 11에서 모델마다 임포트 설정 파일(.eimport, 11강)이 생기자 시각 비교의 빈틈이 드러났습니다. 설정 파일을 지우거나 예전 내용으로 되돌리면, 쿠킹 파일은 여전히 "모든 입력보다 새롭기" 때문에 바뀐 설정이 반영되지 않습니다. 그래서 쿠킹할 때 사용한 설정을 <쿠킹 파일>.import로 함께 기록하고, 다음에는 현재 설정과 내용을 비교합니다. Plans.md에는 이것이 "자동 검증에서 발견해 추가"했다고 남아 있습니다.

    핵심 개념셰이더 쿠킹과 내용 해시

    셰이더(HLSL)도 원본을 그대로 쓰면 실행할 때마다 DXC로 컴파일해야 합니다. 그래서 Phase 5 트랙 D에서 셰이더 매니페스트(Engine/Shaders/Shaders.json)를 만들어 "어떤 파일의 어떤 엔트리를 어떤 단계·디파인으로" 컴파일할지 목록으로 적고, FShaderLibrary가 다음 순서로 바이트코드를 공급하게 했습니다.

    1. 메모리 캐시 (이번 실행에서 이미 얻은 것)
    2. 쿠킹된 DXIL (Engine/Shaders/Cooked/) — 아직 유효하면
    3. DXC 컴파일 → 결과를 쿠킹 디렉터리에 기록

    쿠킹 파일 이름은 <스템>_<Entry>_<Stage>[_sm<모델>][_<디파인 해시>][.debug].dxil입니다. 디파인 목록을 FNV-1a 64비트로 해시해 이름에 넣으므로 같은 소스의 변형이 서로 덮어쓰지 않고, Debug 구성의 DXIL(최적화 없음 + 디버그 정보)은 .debug로 구분합니다.

    처음에는 이 캐시도 시각으로 유효성을 판단했습니다(Plans.md Phase 5: "소스·포함 파일 mtime 검사"). 그런데 셰이더는 git으로 관리되는 소스입니다. 브랜치를 바꾸거나, 머지하거나, 워크트리로 복사하면 파일 시각이 실제 내용 변경과 무관하게 바뀌거나 어긋납니다. "내용은 같은데 시각이 새로워져 재컴파일"은 느릴 뿐이지만, "내용은 바뀌었는데 시각이 오래돼 옛 DXIL 사용"은 틀린 화면을 냅니다. 그래서 지금은 내용 해시를 씁니다.

    // 소스 + 포함 파일 내용 해시 (FNV-1a 64, 파일 순서 포함). 파일을 하나라도 읽지 못하면 0.
// 쿠킹 DXIL 옆 사이드카(<쿠킹 파일>.srchash)에 기록해 두고, 로드 시 다시 계산해 비교한다
// (파일 시각은 git 체크아웃/머지/복사로 쉽게 어긋나므로 캐시 유효성에 쓰지 않는다)
uint64 HashShaderSources(std::span<const std::filesystem::path> Dependencies);

// TryLoadCooked — 소스(+포함 파일) 내용이 쿠킹 당시와 같은지 (사이드카 해시). 소스가 없으면(패키지 배포) 쿠킹 파일을 그대로 신뢰한다
if (std::filesystem::exists(SourcePath, ErrorCode))
{
	const uint64 SourceHash = HashShaderSources(CollectShaderDependencies(SourcePath, ShaderDir));
	if (SourceHash == 0 || ReadSourceHash(CookedPath) != SourceHash)
	{
		E_LOG(LogD3D12, Log, "쿠킹된 셰이더가 현재 소스와 다름(내용 해시), 재컴파일: {}", DisplayName);
		return nullptr;
	}
}

    해시에는 셰이더 파일뿐 아니라 그것이 #include로 끌어오는 모든 파일(재귀)이 들어갑니다. Common.hlsli 한 줄을 고치면 그것을 포함하는 모든 셰이더의 해시가 바뀝니다. 내용을 읽어 해시하는 비용이 들지만, 셰이더 소스는 작고 정확성이 훨씬 중요합니다.

    시각 vs 내용 해시 — 언제 무엇을 모델·텍스처 쿠킹은 여전히 시각을 씁니다(원본이 수십 MB라 매번 해시하면 느리고, 대개 사람이 직접 바꾸는 파일). 셰이더는 작고 git 브랜치 전환이 잦으므로 내용 해시를 씁니다. 정답이 하나가 아니라 "입력의 크기와 바뀌는 방식"에 따라 고릅니다.

    핵심 개념핫 리로드 — 파일 감시와 디바운스

    에디터가 켜진 채로 셰이더를 고치고 저장하면 화면이 바로 바뀌는 것이 핫 리로드(hot reload)입니다. 매번 에디터를 껐다 켜면 반복 속도가 크게 떨어집니다. Phase 5 트랙 F에서 만든 흐름은 이렇습니다.

    1. 감시: FFileWatcher가 Win32 ReadDirectoryChangesW를 overlapped I/O로 걸어 둡니다. 별도 스레드 없이 메인 스레드가 매 프레임 Poll()로 결과만 확인합니다(블로킹 없음).
    2. 디바운스: 이벤트를 바로 처리하지 않고 경로별로 모아 두었다가, 마지막 이벤트 후 150ms 동안 조용하면 한 번만 보고합니다.
    3. 무효화: FShaderLibrary::Invalidate(바뀐 파일)가 그 파일을 직접 또는 #include로 쓰는 캐시 항목을 지우고, 영향받은 셰이더 목록을 돌려줍니다.
    4. 다시 만들기: 렌더러가 새 PSO를 만들어 성공하면 교체하고 이전 PSO는 지연 해제합니다. 컴파일에 실패하면 이전 셰이더를 그대로 씁니다 — 오타 하나로 에디터 화면이 깨지지 않습니다.
    // 파일 변경 이벤트 디바운서 (순수 로직, 테스트 가능).
// 같은 경로의 이벤트가 연속으로 오면 마지막 이벤트 후 Delay가 지났을 때 한 번만 보고한다.
class FChangeDebouncer
{
public:
	explicit FChangeDebouncer(std::chrono::milliseconds InDelay = std::chrono::milliseconds(150));
	void AddEvent(const std::filesystem::path& Path, FTimePoint Time);
	// Delay가 지난 경로를 반환하고 대기 목록에서 제거 (추가된 순서 유지)
	std::vector<std::filesystem::path> CollectReady(FTimePoint Now);
};

    디바운서를 "현재 시각을 인자로 받는 순수 로직"으로 분리한 점이 좋은 습관입니다. 실제 파일 시스템과 시계 없이도 "0ms, 70ms에 이벤트 → 200ms엔 아직, 221ms엔 보고" 같은 테스트를 쓸 수 있습니다. 에디터는 셰이더 폴더용과 프로젝트 콘텐츠 폴더용 FFileWatcher를 따로 두고, 콘텐츠 쪽에서는 Lua 스크립트·머티리얼(.emat)·애니메이션 그래프·비헤이비어 트리·프리팹 변경을 확장자별로 받아 각자 다시 읽게 합니다. "조용해질 때까지 기다린다"는 아이디어는 12강의 C++ 게임 모듈 핫 리로드에서 "시각·크기가 1초 동안 그대로"라는 더 긴 안정화로 다시 나옵니다.

    ProjectE에서는FPaths — 절대 경로를 코드에 쓰지 않는다

    마지막 조각은 "파일이 어디 있는가"입니다. 개발 중 실행 파일은 Build/ninja-debug/Bin/에 있고, 패키지 게임은 설치 폴더에, 게임 데이터는 Projects/Sample/에 있습니다. 소스에 "E:/Projects/ProjectE/..."를 넣으면 다른 PC에서 바로 깨집니다. Phase 5 트랙 A는 이런 컴파일 타임 절대 경로를 모두 지우고 FPaths로 바꿨습니다.

    // 엔진 디렉터리: 실행 파일 디렉터리에서 상위로 올라가며 "Engine/Shaders/Shaders.json" 마커가 있는 첫 디렉터리.

    함정과 교훈

    실제로 겪은 일: BOM이 첫 줄 #include를 숨겼다 셰이더 핫 리로드는 "어떤 파일이 어떤 파일을 include하는지"를 직접 스캔해 의존 관계를 만듭니다. 그런데 1강에서 본 대로 .hlsl은 DXC 1.6 때문에 UTF-8 BOM이 반드시 있어야 합니다. 파일 맨 앞 세 바이트(EF BB BF)가 첫 줄 앞에 붙어 있으니, "줄이 #include로 시작하는가?" 검사가 첫 줄에서만 실패했습니다. 첫 줄에 include가 있는 셰이더는 그 헤더를 고쳐도 다시 컴파일되지 않았습니다. 지금 ShaderManifest.cpp에는 "HLSL 파일은 UTF-8 BOM으로 시작하므로(DXC 요구) 첫 줄의 BOM을 제거해야 "#include"가 줄 시작에 온다"는 주석이 남아 있습니다.
    실제로 겪은 일: 파일 시각을 믿지 않게 되기까지 셰이더 쿠킹 캐시는 처음에 소스·포함 파일의 수정 시각으로 유효성을 판단했습니다. 병렬 작업용 git 워크트리와 브랜치 머지가 일상이 되자 시각이 내용과 어긋나는 일이 생겼고, 커밋 "쿠킹 셰이더 캐시를 내용 해시로 검증"에서 시각 비교를 없애고 .srchash 사이드카로 바꿨습니다. 함께 추가한 테스트는 "시각만 오래된 경우에는 캐시를 쓰고, 해시가 다르거나 사이드카가 없으면 재컴파일"을 확인합니다.
    • 콘텐츠 읽기는 한 함수로: 패키지 게임은 콘텐츠를 Content.epak 하나에 묶습니다. 새 로더가 std::ifstream으로 직접 읽으면 개발 중엔 되다가 패키지에서만 깨집니다. 그래서 규칙은 "콘텐츠 읽기는 FFileSystem(pak → 디스크)만"입니다(10부).
    • 버전 올리기를 잊지 말 것: 쿠킹 형식을 바꾸고 ModelVersion을 올리지 않으면, 이미 쿠킹된 PC에서만 옛 형식을 새 코드로 읽는 버그가 납니다. 내 PC에서는 지웠다 다시 쿠킹했으니 재현이 안 되는, 가장 찾기 어려운 종류입니다.
    정리
    • 소스(JSON, glTF, PNG, HLSL)는 사람과 git을 위해, 쿠킹 결과(.emodel, .etex, .dxil)는 엔진을 위해. 쿠킹 결과는 캐시라 커밋하지 않는다.

    왜 필요한가남이 만든 모델은 남의 좌표계로 온다

    캐릭터·소품·건물 모델은 Blender, Maya 같은 도구에서 만들어 파일로 내보냅니다. 엔진은 그 파일을 읽어 정점·인덱스·머티리얼·뼈·애니메이션을 자기 형식으로 옮겨야 합니다. 이것이 임포트(import)입니다. 어려운 점은 파일 형식 해독이 아닙니다(그건 라이브러리가 합니다). 어려운 것은 좌표계 규약입니다.

    ProjectE는 언리얼과 같은 왼손 Z-up, 1단위 = 1cm입니다(4강). 그런데 glTF 2.0 표준은 오른손, +Y 위, 1단위 = 1m이고, FBX는 파일마다 축과 단위가 다를 수 있습니다. 그대로 읽으면 모델이 옆으로 눕고, 100배 작아지고, 거울에 비친 것처럼 뒤집히고, 뒷면만 보이고, 노멀 맵 음영이 반대로 나옵니다. 이 강의는 그 각각이 왜 생기고 어떻게 고치는지를 다룹니다. Phase 3의 DoD가 정확히 이것이었습니다. "DamagedHelmet(glTF)이 텍스처와 함께 올바른 방향(Z-up)으로 표시된다."

    핵심 개념glTF의 구조

    glTF(GL Transmission Format)는 Khronos 그룹의 "3D 모델의 JPEG"을 목표로 한 개방 형식입니다. JSON(.gltf) 하나와 바이너리(.bin)·이미지 파일들로 되어 있거나, 전부를 한 파일에 담은 .glb로 옵니다. ProjectE는 파싱을 cgltf(헤더 하나짜리 C 라이브러리, 커밋 고정)에 맡기고, 결과를 엔진의 중간 형식 FModelData로 옮깁니다.

    엔진 쪽 중간 형식은 GPU와 무관한 순수 데이터입니다. FModelData = 이미지 목록 + 머티리얼 목록 + 메시 목록 + 노드 트리 + 스킨 + 애니메이션. 씬에 놓을 때(FModelLoader)는 노드 하나가 엔티티 하나가 되어 8강의 계층에 그대로 들어갑니다. 이 엔티티들은 모델 파일에서 언제든 다시 만들 수 있으므로 FTransientComponent를 달아 씬 파일에는 저장하지 않습니다(10강).

    핵심 개념좌표계 변환 — 축 바꾸기는 사실 "거울"이다

    먼저 축 대응을 정합니다. glTF는 +X 오른쪽, +Y 위이고, 카메라는 −Z 방향(화면 안쪽)을 바라봅니다. ProjectE 로더는 이 "보는 방향" −Z를 엔진의 앞(+X)에, 오른쪽과 위는 각각 엔진의 오른쪽(+Y)과 위(+Z)에 대응시킵니다(FGltfLoader 머리 주석).

    왼손 좌표계와 오른손 좌표계는 거울상 관계입니다. 오른손 장갑을 아무리 돌려도 왼손 장갑이 되지 않듯, 둘 사이의 변환에는 반드시 반사(행렬식 −1)가 들어갑니다. 위치와 방향 벡터는 이 행렬을 곱하기만 하면 되지만, "손잡이 방향(handedness)"에 의존하는 양 — 회전 방향, 외적, 삼각형의 감김 방향 — 은 반사에서 부호가 뒤집힙니다. 이 강의의 나머지는 사실 이 한 문장의 결과들입니다.

    쿼터니언 벡터부의 부호가 왜 뒤집히나

    축 a를 중심으로 θ만큼 도는 회전의 쿼터니언은 (sin(θ/2)·a, cos(θ/2))입니다. 같은 물리적 회전을 다른 좌표계로 표현하면 회전 행렬은 Re = C·R·C−1가 됩니다. C가 순수 회전이라면 "축이 C·a로 옮겨진 같은 각도의 회전"이 되지만, C가 반사이면 거울에 비친 회전은 방향이 반대로 돕니다. 즉 축 C·a, 각도 −θ. sin(−θ/2) = −sin(θ/2), cos(−θ/2) = cos(θ/2)이므로 결과 쿼터니언은 (−sin(θ/2)·Ca, cos(θ/2)) — 벡터부만 변환 후 부호를 뒤집으면 됩니다.

	const FVector3 Axis = ConvertPosition({ Gltf.X, Gltf.Y, Gltf.Z });

{
	// M_e = C^T * M * C
	return GAxisConversion.GetTransposed() * GltfRowMajor * GAxisConversion;
}

    행렬로 저장된 노드(matrix)는 켤레 변환 후 이동·스케일·회전으로 다시 분해합니다. 이동은 ×100, 스케일은 각 축 벡터의 길이, 회전은 스케일을 나눈 3×3에서 쿼터니언으로. 엔진의 노드는 항상 TRS로 저장되기 때문입니다(에디터 기즈모와 애니메이션이 TRS를 다룸).

    핵심 개념와인딩 — 앞면과 뒷면

    삼각형에는 앞면과 뒷면이 있습니다. GPU는 화면에 투영된 세 꼭짓점이 시계 방향(CW)인지 반시계 방향(CCW)인지로 앞뒤를 정하고, 보통 뒷면은 그리지 않습니다(뒷면 컬링 — 닫힌 물체의 안쪽 면을 그리지 않아 절반을 아낌). glTF는 CCW가 앞면이고, ProjectE는 "앞면은 시계 방향(CW)"입니다(CLAUDE.md 좌표계 규약).

    여기서 함정이 하나 있습니다. 축 변환은 반사이므로 월드 공간에서 삼각형의 감김을 뒤집습니다. 그런데 엔진의 카메라 규약(뷰 공간 +X 오른쪽, +Y 위, +Z 앞 — 월드 +Y가 오른쪽)도 그 자체로 반사를 하나 포함합니다. 두 반사가 상쇄되어 화면에 찍힌 감김은 glTF에서와 같은 CCW로 남습니다. 엔진은 CW를 앞으로 보므로, 그대로 두면 모든 앞면이 뒷면으로 취급되어 컬링됩니다.

    // 와인딩 반전: glTF는 CCW 앞면. 축 변환(반사)과 엔진 카메라 규약(오른쪽=+Y, 역시 반사)이 상쇄되어
// 화면상 방향이 그대로 유지되므로, 엔진의 CW 앞면 규약에 맞추려면 삼각형마다 뒤 두 인덱스를 교환한다.
for (size_t Index = 0; Index + 2 < OutMesh.Data.Indices.size(); Index += 3)
{
	std::swap(OutMesh.Data.Indices[Index + 1], OutMesh.Data.Indices[Index + 2]);
}

    와인딩 규약을 검증하는 식은 CLAUDE.md에 한 줄로 고정되어 있습니다. Cross(P1 − P0, P2 − P0) · Normal > 0. 엔진의 내장 큐브(FPrimitiveShapes)가 이 식을 만족하고, 임포트한 메시도 같아야 합니다. 테스트 Gltf_LoadTriangleFile과 실제 DamagedHelmet을 읽는 테스트가 기하 법선(외적)과 파일의 정점 법선 방향이 일치하는지 확인합니다.

    핵심 개념탄젠트 공간과 w 부호

    노멀 맵(5강)은 표면의 미세한 요철을 텍스처에 담습니다. 텍스처의 RGB는 월드 방향이 아니라 표면에 붙은 좌표계(탄젠트 공간)의 방향입니다. R = 표면을 따라 "텍스처 오른쪽(+U)", G = "텍스처 위쪽", B = 법선. 셰이더가 이것을 월드 방향으로 바꾸려면 정점마다 세 축 — 탄젠트 T, 바이탄젠트 B, 법선 N — 이 필요합니다.

    정점에 B까지 저장하면 낭비이므로, 보통 T(xyz)와 부호 하나(w = ±1)만 저장하고 셰이더에서 B = Cross(N, T) × w로 복원합니다. 부호가 필요한 이유는 UV가 거울처럼 뒤집혀 펼쳐진 부분(좌우 대칭 모델의 반쪽 등)에서는 Cross(N, T)가 텍스처 위쪽과 반대가 되기 때문입니다. ProjectE의 규약은 CLAUDE.md에 이렇게 적혀 있습니다. "FVertex::Tangent.xyz = UV +U 방향, B = Cross(N, T) * Tangent.w = 노멀 맵 +Y = UV 위쪽(−V)."

    FTangentBasis ComputeTriangleTangentBasis(const FVector3& P0, ..., const FVector2& UV2)
{
	const FVector3 E1 = P1 - P0;  const FVector3 E2 = P2 - P0;
	const FVector2 DUV1 = UV1 - UV0;  const FVector2 DUV2 = UV2 - UV0;
	const float Determinant = DUV1.X * DUV2.Y - DUV2.X * DUV1.Y;
	if (FMath::Abs(Determinant) < 1.0e-12f) { return Basis; }   // UV가 퇴화한 삼각형
	const float InvDeterminant = 1.0f / Determinant;
	// E = dP/du * dU + dP/dv * dV 를 풀면
	const FVector3 dPdu = (E1 * DUV2.Y - E2 * DUV1.Y) * InvDeterminant;
	const FVector3 dPdv = (E2 * DUV1.X - E1 * DUV2.X) * InvDeterminant;
	Basis.Tangent   = dPdu;
	Basis.Bitangent = -dPdv; // 노멀 맵 +Y = UV 위쪽 = -V
	...
}

FVector4 OrthonormalizeTangent(const FVector3& Normal, const FVector3& Tangent, const FVector3& Bitangent)
{
	// 그람-슈미트: 탄젠트에서 법선 성분 제거
	FVector3 T = (Tangent - Normal * FVector3::Dot(Normal, Tangent)).GetNormalized();
	...
	// Cross(N, T)가 원하는 바이탄젠트와 같은 방향이면 +1
	const float Sign = FVector3::Dot(FVector3::Cross(Normal, T), Bitangent) < 0.0f ? -1.0f : 1.0f;
	return FVector4(T, Sign);
}

    파일에 TANGENT 속성이 없으면 로더가 ComputeTangents()로 위 계산을 합니다(위치와 UV만 쓰므로 인덱스 교환과 무관). 파일에 TANGENT가 있으면 변환해야 하는데, 여기서 다시 반사가 등장합니다. 반사 C에 대해 외적은 Cross(C·N, C·T) = −C·Cross(N, T)입니다. 방향 벡터 N, T를 그대로 변환하면 Cross(N, T)가 원래 가리키던 쪽의 반대가 되므로, 같은 바이탄젠트를 얻으려면 w의 부호를 뒤집어야 합니다.

    FVector4 FGltfLoader::ConvertTangent(const FVector4& Gltf)
{
	// 반사 C에 대해 Cross(C·N, C·T) = -C·Cross(N, T). 같은 바이탄젠트를 얻으려면 w 부호를 뒤집어야 한다
	const FVector3 Tangent = ConvertPosition(FVector3(Gltf.X, Gltf.Y, Gltf.Z)).GetNormalized();
	return FVector4(Tangent, Gltf.W < 0.0f ? 1.0f : -1.0f);
}

    함정과 교훈

    실제로 겪은 일: 모두 뒷면이었던 헬멧 Phase 3의 첫 glTF 로더는 축 변환은 했지만 인덱스는 그대로 두었습니다. "변환이 반사이니 감김도 뒤집혔겠지"가 아니라 "카메라 규약의 반사와 상쇄되어 화면상 CCW가 유지된다"가 실제였고, 결과적으로 엔진(CW 앞면) 기준으로 모든 삼각형이 뒷면이 됐습니다. Phase 4 에디터 작업 중(2026-09-30) "glTF 와인딩 반전(뒷면 컬링 정상화)" 커밋으로 인덱스 교환을 넣고, 기하 법선과 정점 법선이 일치하는지 보는 테스트를 추가했습니다. Plans.md Phase 4의 사용자 확인 기록에도 "glTF 와인딩·기즈모 BeginFrame 수정 후"라고 남아 있습니다.
    실제로 겪은 일: 미터에서 센티미터로 처음 엔진 단위는 glTF와 같은 미터였습니다. 언리얼식 1단위 = 1cm로 바꾼 커밋(2026-09-30)에서 glTF 임포트에 위치·이동 ×100을 넣고 ModelVersion을 3으로 올렸습니다. 기본 큐브는 100cm, 카메라 클립 범위, 플라이 카메라 속도, 그림자 기본값, 기존 씬 위치도 모두 함께 바꿔야 했습니다. 0강에서 말한 "좌표계·단위는 나중에 바꾸기 매우 비싸다"의 실제 사례입니다. 이때 생긴 규칙이 "미터 기반 외부 데이터는 경계에서 FUnits::MetersToUnits로만 변환, 방향 벡터는 스케일하지 않는다"입니다.
    • 방향 벡터에 ×100을 곱하지 말 것: 법선에 100을 곱해도 정규화하면 같아 보이지만, 탄젠트·노드 회전 축 등에서 정규화가 빠진 곳이 있으면 조명이 100배로 튀는 식의 버그가 납니다. 테스트가 "법선 (0,0,1) → (−1,0,0), 길이 1"을 확인합니다.
    • 에셋의 "앞"은 제각각: 변환 규칙이 맞아도 모델마다 만든 사람이 정한 정면이 다릅니다(예: CLAUDE.md에 "Fox.glb는 모델 공간 −X를 바라봄"이 기록되어 있음). 로더를 고치지 말고 .eimport의 YawDegrees나 컴포넌트 설정(LookAt ForwardAxis)으로 맞춥니다.
    • 새 속성을 읽으면 테스트도: CLAUDE.md 규칙 "새 속성 추가 시 GltfLoaderTests에 케이스 추가". 알파 모드와 양면(doubleSided)을 Phase 36에서 추가할 때도 테스트 glTF에 MASK·alphaCutoff·doubleSided를 넣어 확인합니다.
    정리
    • glTF = 노드(계층·TRS) → 메시 → 프리미티브 → 접근자 → 버퍼, 머티리얼 → 텍스처 → 이미지. 엔진은 GPU와 무관한 FModelData로 먼저 옮긴다.
    • 엔진 = (−g.z, g.x, g.y), 행렬식 −1인 반사. 위치·이동만 ×100, 방향은 축만, 스케일은 순서만.
    • 반사는 손잡이 방향에 의존하는 것을 뒤집는다: 쿼터니언 벡터부 부호, 탄젠트 w, 삼각형 감김.
    • 축 반사와 카메라 규약 반사가 상쇄되므로 화면 감김은 그대로 → 엔진 CW 앞면에 맞추려면 인덱스 교환. 검증식 Cross(P1−P0, P2−P0)·N > 0.
    • 탄젠트 = dP/du, B = Cross(N, T)·w = 텍스처 위쪽(−V). 없으면 UV로 계산.
    • FBX는 ufbx로 glTF 축·미터로 맞춘 뒤 같은 변환을 재사용. 모델별 차이는 .eimport + ImportRoot 노드.

    생각해 볼 문제

    Q1. 축 대응을 (−g.z, g.x, g.y) 대신 (g.z, g.x, g.y)로 잡으면 반사가 사라지지 않을까요? (g.z, g.x, g.y)는 행렬식이 +1인 순수 회전(축 순환)이지만, 그러면 glTF의 "뒤(+Z)"가 엔진의 "앞(+X)"이 됩니다. glTF 모델의 앞(−Z)이 엔진 뒤(−X)를 보게 되죠. 더 근본적으로, 오른손 좌표계에서 왼손 좌표계로 가면서 위·앞·오른쪽의 의미를 모두 지키는 회전은 존재하지 않습니다. 의미를 지키려면 반사가 반드시 하나 들어가고, 그 결과(감김·외적·회전 방향)를 처리하는 것이 임포터의 일입니다.
    Q2. 노멀 맵이 적용된 벽돌 벽에서 빛이 위에서 오는데 홈의 그늘이 위쪽에 생깁니다(요철이 뒤집혀 보임). 무엇을 의심해야 할까요? 바이탄젠트 방향, 즉 탄젠트 w 부호나 "노멀 맵 +Y = UV 위쪽(−V)" 규약입니다. G 채널이 반대로 해석되면 세로 방향 요철만 뒤집혀 보입니다. 반사 변환에서 w를 뒤집지 않았거나(ConvertTangent), DirectX식(+Y 아래)으로 만든 노멀 맵을 OpenGL식(+Y 위) 규약 엔진에 넣은 경우에 이런 증상이 납니다. 위 그림의 규약대로 하나씩 확인합니다.
    Q3. 임포트 설정의 Scale을 정점에 곱하지 않고 ImportRoot 노드에 두면, 스킨 메시와 애니메이션 측면에서 무엇이 편해질까요? 스킨 메시의 정점은 바인드 포즈 기준이고, 역바인드 행렬과 애니메이션 키(뼈의 이동값)도 같은 단위·방향을 전제로 맞물려 있습니다. 정점만 스케일하면 이 셋이 어긋나 메시가 찌그러지므로 모두를 함께 고쳐야 합니다. 맨 위 노드에 스케일·회전을 두면 셋 다 손대지 않고, 계층의 월드 행렬 합성(8강)이 전체에 같은 변환을 곱해 줍니다. "다시 가져오기"로 값을 되돌리기도 쉽습니다.

    • 게임 모듈 인터페이스(IGameModule)와 버전 검사, 그리고 에디터에서 C++ 게임 코드를 다시 로드하는 절차를 그릴 수 있습니다.

    왜 필요한가게임 코드는 엔진과 따로 바뀐다

    0강에서 엔진과 게임 프로젝트를 나눴습니다. 게임에는 Lua 스크립트뿐 아니라 C++ 코드도 있습니다(47강의 하이브리드 결정 — 매 프레임 대량 순회는 C++). 이 C++ 게임 코드를 어디에 넣을까요? 엔진 소스 안에 섞으면 게임마다 엔진을 고쳐야 하고, 에디터 실행 파일에 넣으면 게임 코드를 바꿀 때마다 에디터 전체를 다시 빌드해야 합니다. 그래서 게임 코드는 별도의 DLL(Projects/Sample/Source → SampleGame.dll)로 빌드하고, 에디터·런타임이 실행 중에 불러옵니다. 이것이 게임 모듈입니다.

    그런데 게임 모듈은 엔진을 씁니다. 컴포넌트를 리플렉션에 등록하고(9강), View로 순회하고(7강), 로그를 찍습니다. 엔진이 어떤 형태로 존재해야 에디터와 게임 모듈이 같은 엔진을 쓸 수 있을까요? 이 질문이 엔진 전체를 DLL 하나(ProjectEEngine.dll)로 묶은 이유입니다.

    핵심 개념정적 링크와 동적 링크 — 전역 상태는 몇 개인가

    정적 링크는 라이브러리의 기계어를 실행 파일 안에 복사해 넣습니다. 동적 링크는 라이브러리를 DLL로 따로 두고, 실행 파일은 "이 DLL의 이 함수를 쓴다"는 목록(import table)만 가집니다. 실행 시 운영체제가 DLL을 메모리에 올려 주소를 이어 줍니다.

    평소엔 차이가 크지 않지만, 전역 상태가 있으면 결정적으로 달라집니다. 엔진에는 프로세스에 하나여야 하는 것들이 있습니다. 타입 레지스트리(FTypeRegistry::Get()), ECS 타입 ID 표, 로그 카테고리, 콘솔 변수, 디버그 선 그리기 … 엔진을 정적 라이브러리로 두고 에디터 exe와 게임 DLL이 각각 링크하면 두 바이너리에 엔진 사본이 하나씩 생기고, 이 전역들도 둘이 됩니다.

    그래서 2026-09-30 커밋 "엔진 런타임을 ProjectEEngine.dll로 빌드"에서 런타임 모듈(Core, RHI, Scene, Renderer, Audio, Physics, Scripting … 지금은 AI, World, Network, UI, Online까지)을 DLL 하나로 묶었습니다. 그리고 규칙을 하나 세웠습니다. "실행 파일/테스트/게임 모듈은 ProjectE::Engine만 링크한다(모듈 타깃 직접 링크 금지 — 객체 중복)." ProjectE::Core를 직접 링크하면 Core의 객체 파일이 DLL에도, 실행 파일에도 들어가 그림 12-1 왼쪽 상황이 다시 생기기 때문입니다.

    핵심 개념내보내기 — 무엇을 DLL 밖에 보여 줄까

    DLL 안의 함수는 기본적으로 밖에서 보이지 않습니다. 밖에서 부르려면 내보내기(export) 목록에 올려야 합니다. 방법은 소스에 __declspec(dllexport)를 붙이거나, 링커에 .def 파일(내보낼 이름 목록)을 주는 것입니다. 엔진 함수 수만 개에 일일이 표식을 다는 것은 비현실적이므로, ProjectE는 처음에 CMake의 WINDOWS_EXPORT_ALL_SYMBOLS로 "객체 파일의 모든 함수를 자동으로 내보내기"를 썼습니다.

    문제는 Windows PE 형식의 내보내기 표가 최대 65535개(16비트 서수)라는 것입니다. 엔진이 커지면서 이 한도에 부딪혔습니다.

    무엇을 걸러도 안전할까요? 판단 기준은 "DLL 밖에서 실제로 가져다 쓰는가"입니다.

    • sol2 내부(Lua 바인딩 라이브러리): sol 헤더는 Scripting 모듈 안에서만 포함하므로 DLL 밖은 sol 심볼을 쓰지 않습니다. dumpbin /imports로 확인해 0개였습니다.
    • std:: 범위 함수(std::vector<FFoo>::push_back 같은 템플릿 인스턴스): 헤더에 정의된 템플릿이라, 쓰는 쪽이 각자 인스턴스화할 수 있습니다. 굳이 DLL에서 가져올 필요가 없습니다.
    • 데이터 심볼은 남긴다: 함수 지역 static의 가드나 정적 멤버 같은 데이터는 바이너리마다 따로 생기면 의미가 달라지므로(바로 아래) 거르지 않습니다.

    함수는 자동, 전역 데이터는 표식

    함수는 .def 목록만으로 내보내고 가져올 수 있습니다(가져오는 쪽 링커가 import 라이브러리의 작은 점프 코드로 잇습니다). 하지만 전역 변수는 다릅니다. DLL 밖의 코드는 변수 주소를 직접 알 수 없고 "주소가 담긴 칸"(__imp_ 포인터)을 거쳐 접근해야 하는데, 컴파일러는 그 변수 선언에 __declspec(dllimport)가 붙어 있어야 이 간접 접근 코드를 만듭니다. 그래서 DLL 밖에서 접근하는 전역 데이터에만 표식을 붙입니다.

//   DLL 밖(에디터/런타임/게임 모듈/테스트)에서 접근하는 **전역 데이터**(로그 카테고리 등)만 E_ENGINE_API를 붙인다.
#if defined(E_ENGINE_SHARED)

	#else

	#endif

    함수 지역 static의 함정

    7강에서 본 타입 ID 문제의 정체가 여기 있습니다. 헤더에 정의된 인라인 함수나 템플릿 함수는 그것을 쓰는 바이너리마다 따로 컴파일되어 들어갑니다. 그 안의 static 변수도 바이너리마다 하나씩 생깁니다. 정적 링크에서는 링커가 중복을 하나로 합쳐 주지만, DLL은 서로 다른 바이너리라 합쳐지지 않습니다. 그래서 CLAUDE.md는 "헤더 인라인 템플릿의 함수 지역 static처럼 바이너리마다 따로 생기는 상태에 전역 의미를 두지 않는다(예: ECS 타입 ID는 FRegistry::AssignComponentTypeId가 엔진 DLL에서 부여)"를 규칙으로 둡니다. 진짜 상태는 .cpp(엔진 DLL 안)에 두고, 헤더 쪽 static은 캐시로만 씁니다.

    CRT도 하나여야 한다 엔진 함수가 std::string이나 std::vector를 인자·반환값으로 주고받으므로, 한 바이너리에서 할당한 메모리를 다른 바이너리가 해제하는 일이 생깁니다. 바이너리마다 C 런타임(CRT)을 정적으로 링크하면 힙도 바이너리마다 따로라 이 순간 크래시합니다. 그래서 규칙은 "VC++ 런타임은 app-local(정적 CRT 금지 — DLL 경계로 STL을 넘긴다)"이고, GameModule.h도 "게임 모듈은 엔진 DLL을 링크하고 같은 컴파일러/CRT로 빌드되어야 한다"고 적어 둡니다.

    2. 옛 코드를 가리키는 것들: 씬 레지스트리에는 게임 모듈이 만든 컴포넌트 풀(TSparseSet<FSpinnerComponent>)이 있고, 그 가상 함수 표는 옛 DLL의 코드를 가리킵니다. 리플렉션 훅 람다도 마찬가지입니다.
    3. 구조체가 바뀌었을 수 있다: 프로그래머가 컴포넌트에 필드를 추가했다면, 새 코드가 옛 풀의 메모리를 새 구조체로 해석하는 순간 메모리가 망가집니다.

    장애물별 해법을 정리하면 이렇습니다.

    • 파일 잠금 → 그림자 복사: 원본을 <Saved>/HotReload/<이름>_<번호>.dll로 복사해서 그것을 로드합니다. 원본은 잠기지 않으므로 빌드가 자유롭게 덮어씁니다. 다만 DLL 안에는 "내 디버그 정보는 이 경로의 PDB에 있다"는 기록(CodeView RSDS)이 있어, 디버거가 원본 PDB를 열어 잠그면 다음 링크가 실패합니다. 그래서 복사본 DLL 바이트 안의 PDB 경로 문자열을 복사본 PDB 이름으로 바꿉니다(원래 칸 안에서만 — 넘치면 실패 처리). 이 바이트 조작은 순수 함수(ReadPdbPath/PatchPdbPath)로 분리해 실제 DLL 이미지로 테스트합니다(HotReload_PatchPdbPathInRealImage).
    • 옛 코드를 가리키는 것들 → 옛 DLL을 해제하지 않기: FreeLibrary로 옛 DLL을 내리면, 남아 있던 풀의 가상 함수나 함수 포인터를 부르는 순간 해제된 메모리로 점프합니다. 옛 DLL을 메모리에 그냥 두면 메모리를 조금 쓰는 대신 이런 경우가 모두 안전해집니다. 복사본마다 파일 이름이 다르므로 몇 번이고 새로 로드할 수 있고, 지우지 못한 옛 복사본 파일은 다음 에디터 시작 때 정리합니다.
    • 구조체 변경 → 타입 ID 폐기 + JSON 왕복: 다시 로드할 때 모듈 소유 컴포넌트의 ECS 타입 ID를 RetireComponentTypeId로 버립니다(7강). 새 DLL은 같은 이름의 컴포넌트에 새 ID와 새 풀을 받으므로 옛 풀을 자기 타입으로 잘못 캐스팅할 일이 없습니다. 값은 씬 JSON(이름 키 — 9강·10강)으로 옮겨지므로, 필드를 추가해도 관용적 로드가 나머지 값을 살립니다. 옛 풀은 레지스트리에 남아 엔티티 파괴 때 옛 DLL 코드로 정리됩니다.

    에디터 메뉴에는 "C++ 다시 로드"(Ctrl+Alt+F11)와 "게임 모듈 빌드 후 다시 로드"(에디터 빌드 폴더에서 cmake --build --target <모듈>를 백그라운드로 실행)가 있고, 자동 감지는 환경설정에서 켭니다. 자동 검증 인자 --verify-hot-reload는 씬을 요약(엔티티 수, 모듈 컴포넌트 수, Float 값 합)했다가 다시 로드 후 같은지 비교합니다.

    함정과 교훈

    실제로 겪은 일: LNK1189 — 내보내기 67,315개 2026-10-02, Release 링크가 LNK1189(내보내기 한도 초과)로 실패했습니다. 자동 내보내기 목록이 67,315개였습니다. 같은 __create_def 목록에서 sol2 내부 심볼(@sol@@)을 걸러 Release 57,472 / Debug 55,672로 내렸습니다. 하루 뒤 엔진이 더 자라 64,193개가 되자, 필터를 호스트 도구로 옮기고 std:: 범위 함수까지 걸러 10,235개가 됐습니다. 같은 날 "절차적 건물 내부 컨테이너를 익명 네임스페이스 타입으로" 바꿔 약 470개를 줄인 커밋도 있습니다 — 익명 네임스페이스 안의 타입은 밖에서 보이지 않으므로 내보내기 목록에 오르지 않습니다. 교훈: "모두 자동으로 내보내기"는 편하지만 공짜가 아니며, 한도를 넘으면 도구가 빌드를 실패시키도록 해 두어야 조용한 문제가 되지 않습니다.
    실제로 겪은 일: 에디터를 연 채 게임 모듈을 빌드하면 LNK1168 핫 리로드의 전제는 "에디터가 켜진 동안 게임 모듈만 다시 빌드"입니다. 그런데 CMake 구성 단계가 생성 파일을 file(WRITE)로 매번 다시 쓰면, 내용이 같아도 파일 시각이 바뀌어 엔진 DLL까지 다시 링크하려 들었습니다. 에디터가 엔진 DLL을 쥐고 있으니 링커가 쓸 수 없어 LNK1168로 실패했습니다. 규칙이 생겼습니다. "CMake 구성 시점 생성 파일은 내용이 바뀔 때만 쓴다(file(CONFIGURE))." 그리고 "엔진 DLL 자체 변경은 에디터 재시작 필요" — 핫 리로드는 게임 모듈만의 기능입니다.
    • 모듈 타입 ID·FTypeInfo*를 캐시하지 말 것: 다시 로드하면 바뀝니다. 모듈 타입은 리플렉션(이름)으로만 다루고, 씬 밖에 리플렉션 정보를 쥐는 새 캐시를 만들면 ReloadGameModule에서 비우거나 다시 만듭니다.
    • 인터페이스를 바꾸면 버전을 올린다: IGameModule에 가상 함수를 추가하고 GameModuleApiVersion을 그대로 두면, 옛 모듈이 검사를 통과해 엉뚱한 함수가 불립니다. 멀티플레이 메시지의 NetProtocolVersion, 쿠킹 형식의 ModelVersion과 같은 종류의 약속입니다 — "경계를 넘는 형식에는 버전 번호를 붙이고, 바꾸면 올린다."
    정리
    • 정적 링크는 바이너리마다 엔진 사본(과 전역)을 만든다 → 엔진을 DLL 하나로 묶고 모두 ProjectE::Engine만 링크.
    • 모듈은 OBJECT 라이브러리로 컴파일하고 객체를 DLL 하나에 넣는다(E_ENGINE_SHARED).
    • 함수는 자동 .def로 내보내되, 한도 65535 때문에 DLL 밖이 쓰지 않는 sol2 내부·std 범위 함수를 거른다. 전역 데이터는 E_ENGINE_API(dllexport/dllimport).
    • 헤더의 함수 지역 static은 바이너리마다 따로 — 전역 의미는 엔진 DLL의 .cpp에. CRT도 하나(동적).
    • 게임 모듈 = extern "C" 함수 두 개 + IGameModule + API 버전 검사. 등록 타입에 Owner를 붙여 언로드 때 제거.

    생각해 볼 문제

    Q1. 게임 모듈 CMake가 실수로 ProjectE::Engine 대신 ProjectE::Core와 ProjectE::Scene을 직접 링크했습니다. 빌드는 됩니다. 실행하면 어떤 증상이 나타날까요? Core·Scene의 객체가 게임 모듈 DLL 안에도 복사되어 FTypeRegistry::Get(), 타입 ID 표, 로그 카테고리 같은 전역이 게임 모듈 쪽에 따로 생깁니다. 게임 모듈이 OnLoad에서 등록한 컴포넌트가 에디터 인스펙터·씬 저장에 나타나지 않거나, 같은 컴포넌트에 다른 타입 ID가 매겨져 엉뚱한 풀을 캐스팅하는 등 "빌드는 되는데 이상한" 증상이 납니다(그림 12-1 왼쪽). 그래서 규칙으로 금지합니다.
    Q2. std:: 범위 함수는 내보내지 않는데, 엔진 DLL 밖의 코드가 std::vector<FEntity>::push_back을 부르면 링크 오류가 나지 않을까요? 나지 않습니다. 그 함수는 표준 헤더에 정의된 템플릿이라, 밖의 코드를 컴파일할 때 컴파일러가 그 바이너리 안에 직접 인스턴스화합니다. DLL에서 가져올 필요가 없습니다. 반대로 템플릿 안의 데이터(함수 지역 static 등)는 바이너리마다 따로 생기면 의미가 달라질 수 있어 필터가 일부러 남겨 둡니다.
    Q3. 다시 로드할 때마다 옛 DLL을 해제하지 않으면 메모리가 계속 늘어납니다. 그래도 이 선택이 합리적인 이유는? 게임 모듈 DLL은 보통 수 MB 수준이고, 핫 리로드는 개발 중 에디터에서만 일어나며, 에디터를 다시 켜면 모두 정리됩니다. 반면 해제하면 씬에 남은 옛 풀의 가상 함수, 리플렉션 훅, 다른 시스템이 들고 있을지 모르는 함수 포인터 중 하나라도 불리는 순간 크래시합니다. 그 모든 참조를 빠짐없이 찾아 끊는 것은 어렵고 틀리기 쉽습니다. "약간의 메모리로 큰 종류의 크래시를 통째로 없앤다"는 교환입니다.
