    화면에 무언가를 그리기 — 그래픽스 기초

    GPU와 대화하는 법(DirectX 12)부터 첫 삼각형, 3D 수학, 카메라·깊이·텍스처·조명, 그리고 GPU 리소스를 안전하게 지우는 법까지. 이후 모든 렌더링 강의의 바닥이 되는 내용을 ProjectE의 Phase 0~3 코드로 따라갑니다.

    2강

    GPU와 DirectX 12의 사고방식

    관련 Phase: 0 · 살펴볼 곳: Engine/Source/RHI/D3D12/ (D3D12Device.cpp, D3D12CommandQueue.cpp, D3D12RHI.cpp, D3D12DescriptorHeap.h, D3D12DescriptorAllocator.cpp, D3D12SwapChain.cpp)
    이 강의를 마치면
    • CPU와 GPU가 왜 "따로 달리는" 두 프로세서이고, 둘 사이에 무엇이 오가는지 설명할 수 있습니다.
    • 커맨드 리스트·할당자·큐·펜스가 각각 어떤 역할이며, 왜 프레임마다 "칸"을 여러 벌 두는지(frames in flight) 이해합니다.
    • 디스크립터와 디스크립터 힙이 무엇인지, 셰이더 가시 힙이 왜 따로 있는지 압니다.
    • 스왑체인이 화면에 이미지를 내보내는 방식과 디버그 레이어를 켜야 하는 이유를 압니다.

    왜 필요한가GPU는 부탁을 받아 두었다가 나중에 일한다

    0강에서 Phase 0의 완료 기준(DoD)을 보았습니다. "창이 열리고 DX12로 배경색이 클리어된다." 화면을 한 색으로 지우는 일은 너무 단순해 보이지만, DirectX 12(이하 DX12)로 이 한 줄을 하려면 디바이스, 커맨드 큐, 커맨드 할당자, 커맨드 리스트, 펜스, 디스크립터 힙, 스왑체인을 모두 만들어야 합니다. 왜 이렇게 많은 부품이 필요할까요?

    이유는 GPU가 CPU와 다른 프로세서이기 때문입니다. GPU에는 자기 메모리(VRAM)와 자기 실행 흐름이 있습니다. CPU가 "이 삼각형을 그려"라고 말하는 순간 GPU가 바로 그리는 것이 아닙니다. CPU는 해야 할 일을 명령 목록으로 적어서 GPU의 대기열에 넣고, 곧바로 다음 일을 하러 갑니다. GPU는 대기열에서 목록을 꺼내 자기 속도로 실행합니다. 둘은 비동기로, 보통 1~3프레임 정도 차이를 두고 달립니다.

    비유 CPU는 식당의 홀 직원, GPU는 주방입니다. 직원은 주문서를 써서 주방 창구에 꽂고 다음 손님에게 갑니다. 주방은 주문서를 순서대로 처리합니다. 직원이 요리가 끝날 때까지 창구 앞에서 기다리면 식당이 멈추고, 반대로 주방이 아직 쓰고 있는 접시를 직원이 치워 버리면 사고가 납니다. DX12의 부품들은 전부 이 "주문서를 쓰고, 넘기고, 끝났는지 확인하는" 일을 위한 것입니다.

    예전 API인 DirectX 11에서는 이런 일을 드라이버가 대부분 숨겨서 처리했습니다. 편했지만, 드라이버가 언제 무엇을 기다리고 언제 메모리를 복사하는지 알 수 없었고 여러 스레드에서 명령을 만들기도 어려웠습니다. DX12는 반대로 "드라이버가 추측하지 않게, 애플리케이션이 다 말해 준다"는 설계입니다. 그래서 장황합니다. 대신 동작이 예측 가능하고, 엔진이 메모리·동기화·병렬 기록을 직접 통제할 수 있습니다. 엔진을 만드는 입장에서는 이 장황함이 곧 통제권입니다.

    핵심 개념디바이스: GPU와 대화하는 창구

    어댑터(adapter)는 컴퓨터에 꽂힌 그래픽 카드 하나(또는 내장 GPU)를 가리키고, 디바이스(device)는 그 어댑터와 대화하는 객체입니다. 리소스(버퍼, 텍스처), 파이프라인 상태, 디스크립터 힙 같은 모든 GPU 객체는 디바이스를 통해 만듭니다. 노트북처럼 GPU가 둘인 경우를 위해 ProjectE는 "고성능 우선" 순서로 어댑터를 훑고, 소프트웨어 렌더러는 건너뜁니다.

    for (UINT Index = 0;
     Factory->EnumAdapterByGpuPreference(Index, DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE, IID_PPV_ARGS(&Candidate)) != DXGI_ERROR_NOT_FOUND;
     ++Index)

	{
		Adapter = Candidate;

    MinFeatureLevel은 D3D_FEATURE_LEVEL_11_0입니다. "DX12 API로 말하되, 하드웨어는 11_0 수준 이상이면 받아 준다"는 뜻입니다. 레이 트레이싱 같은 고급 기능은 디바이스를 만든 뒤 CheckFeatureSupport로 따로 확인하고, 없으면 그 기능만 끕니다(25강).

    디바이스 생성 같은 초기화 호출은 E_D3D_VERIFY로 감쌉니다. 1강의 구분 그대로입니다. 초기화 실패는 "일어날 수 있는 일"이므로 Error 로그를 남기고 return false, 반면 프레임 도중의 실패(E_D3D_CHECK)는 복구할 방법이 없으므로 Fatal입니다.

    핵심 개념커맨드 리스트, 할당자, 큐

    DX12에서 GPU에 일을 시키는 경로는 세 부품으로 나뉩니다.

    부품역할식당 비유
    커맨드 할당자 (ID3D12CommandAllocator)기록된 명령이 실제로 저장되는 메모리 덩어리주문서 용지 묶음
    커맨드 리스트 (ID3D12GraphicsCommandList)"파이프라인 설정, 리소스 바인딩, 그리기" 같은 명령을 기록하는 인터페이스. 할당자의 메모리에 쓴다주문서에 적는 펜
    커맨드 큐 (ID3D12CommandQueue)닫힌 리스트를 제출받아 GPU가 순서대로 실행하는 대기열주방 창구

    할당자와 리스트를 나눈 이유가 중요합니다. 리스트는 제출하고 나면 곧바로 Reset해서 다음 기록에 재사용할 수 있습니다. 하지만 할당자의 메모리는 GPU가 그 명령을 다 실행할 때까지 건드리면 안 됩니다. GPU가 읽고 있는 주문서를 지우는 셈이니까요. 그래서 할당자는 "GPU가 그 프레임을 끝냈다"는 것이 확인된 뒤에만 Reset합니다. 이 확인 수단이 펜스입니다.

    핵심 개념펜스와 frames in flight

    펜스(fence)는 GPU 메모리에 있는 64비트 정수 하나라고 생각하면 됩니다. CPU가 큐에 Signal(펜스, 7)을 넣으면, GPU는 그 앞의 명령을 모두 실행한 뒤 펜스 값을 7로 씁니다. CPU는 GetCompletedValue()로 이 값을 읽어 "7번 지점까지 끝났구나"를 압니다. 기다려야 하면 이벤트를 걸고 잠듭니다. ProjectE의 큐 래퍼는 이 일을 몇 줄로 묶어 둡니다.

    uint64 FD3D12CommandQueue::Signal()
{
	const uint64 FenceValue = NextFenceValue++;
	E_D3D_CHECK(Queue->Signal(Fence.Get(), FenceValue));
	return FenceValue;
}

void FD3D12CommandQueue::WaitForFenceValue(uint64 FenceValue)
{
	if (IsFenceComplete(FenceValue)) // Fence->GetCompletedValue() >= FenceValue
	{
		return;
	}
	E_D3D_CHECK(Fence->SetEventOnCompletion(FenceValue, FenceEvent));
	WaitForSingleObject(FenceEvent, INFINITE);
}

void FD3D12CommandQueue::Flush() { WaitForFenceValue(Signal()); } // 지금까지 제출한 모든 일이 끝날 때까지

    가장 단순한 방법은 매 프레임 끝에 Flush()하는 것입니다. 그러면 할당자를 언제 Reset해도 안전하지만, CPU가 GPU를 기다리는 동안 놀고 GPU도 CPU가 다음 프레임을 기록하는 동안 놉니다. 두 프로세서가 번갈아 쉬는 셈입니다.

    해법은 프레임 자원을 여러 벌 두는 것입니다. 할당자, 매 프레임 쓰는 업로드 메모리(5강), 해제 대기 목록(6강)을 프레임 "칸(slot)"마다 따로 두면, CPU는 GPU가 이전 프레임을 실행하는 동안 다른 칸에 다음 프레임을 기록할 수 있습니다. 칸을 다시 쓰기 직전에만 "그 칸을 마지막으로 쓴 프레임이 끝났는지"를 펜스로 확인하면 됩니다. 동시에 GPU 쪽에 걸려 있는 프레임이 여러 개라서 이것을 frames in flight라고 부릅니다.

    ProjectE에서 이 규칙은 FD3D12RHI의 BeginFrame/EndFrame 두 함수에 모여 있습니다.

    void FD3D12RHI::BeginFrame(const float ClearColor[4])
{
	CurrentBackBufferIndex = SwapChain.GetCurrentBackBufferIndex();
	// 이 백버퍼를 마지막으로 사용한 프레임이 GPU에서 끝날 때까지 대기
	GraphicsQueue.WaitForFenceValue(FrameFenceValues[CurrentBackBufferIndex]);

	// 이 인덱스의 이전 프레임에서 예약된 해제를 실행 (GPU 사용 완료 보장됨)
	ProcessPendingReleases(PendingReleases[CurrentBackBufferIndex]);
	DynamicBuffers[CurrentBackBufferIndex].Reset();
	// 지난번 이 슬롯이 쓴 할당자를 모두 비우고 첫 할당자로 시작
	...
	E_D3D_CHECK(CommandList->Reset(Allocator, nullptr));
	...
}

void FD3D12RHI::EndFrame()
{
	...
	E_D3D_CHECK(CommandList->Close());
	FrameFenceValues[CurrentBackBufferIndex] = GraphicsQueue.ExecuteCommandList(CommandList.Get()); // 제출 + Signal
	...
	SwapChain.Present(bVSync);
}

    읽는 순서대로 보면 이렇습니다. 프레임을 시작할 때 이번 칸 번호를 정하고, 그 칸의 마지막 펜스 값까지 기다립니다. 통과했다면 그 칸의 모든 자원(할당자, 업로드 메모리, 해제 대기 목록)은 GPU가 더 이상 쓰지 않으므로 마음 놓고 초기화합니다. 프레임을 끝낼 때는 리스트를 닫아 제출하고, 그때 받은 펜스 값을 그 칸에 적어 둡니다. 다음에 같은 칸이 돌아오면 바로 그 값을 기다리게 됩니다.

    왜 칸 번호를 백버퍼 번호와 같게 두나 스왑체인의 백버퍼(아래 절)도 3장이고, 백버퍼 하나를 다시 그리려면 그 백버퍼를 쓰던 프레임이 끝나야 합니다. 프레임 자원의 칸을 백버퍼 번호(GetCurrentBackBufferIndex)에 맞추면 "백버퍼를 기다리는 일"과 "칸을 기다리는 일"이 한 번의 대기로 합쳐집니다. FD3D12RHI::FrameCount가 FD3D12SwapChain::BackBufferCount(3)로 정의된 이유입니다.

    핵심 개념리소스 상태와 배리어

    GPU 메모리의 같은 텍스처라도 "렌더 타깃으로 쓰는 중", "셰이더가 읽는 중", "화면에 내보내는 중"에 따라 하드웨어가 내부 압축이나 캐시를 다르게 다룹니다. DX12는 이 상태(state)를 애플리케이션이 직접 관리하게 하고, 상태를 바꿀 때는 리소스 배리어(resource barrier) 명령을 기록하게 합니다. 배리어는 "이 시점 전의 쓰기를 끝내고, 이 리소스를 다음 용도에 맞게 준비해 달라"는 주문입니다.

    // BeginFrame: 화면 표시용 상태 → 그리기 대상
const D3D12_RESOURCE_BARRIER ToRenderTarget =
	MakeTransitionBarrier(BackBuffer, D3D12_RESOURCE_STATE_PRESENT, D3D12_RESOURCE_STATE_RENDER_TARGET);
CommandList->ResourceBarrier(1, &ToRenderTarget);
...
// EndFrame: 그리기 대상 → 화면 표시용 상태 (Present 전에 반드시)
const D3D12_RESOURCE_BARRIER ToPresent = MakeTransitionBarrier(BackBuffer, BackBufferState, D3D12_RESOURCE_STATE_PRESENT);
CommandList->ResourceBarrier(1, &ToPresent);

    MakeTransitionBarrier는 공식 도우미 헤더(d3dx12.h)를 쓰지 않고 D3D12Common.h에 직접 만든 작은 함수입니다. 배리어를 빠뜨리거나 상태를 잘못 적으면 디버그 레이어가 바로 오류를 냅니다(아래 절). 상태 추적은 엔진이 커질수록 복잡해지는데, ProjectE는 나중에 이 일을 렌더 그래프가 자동으로 하게 바꿉니다(22강). 지금은 "상태는 내가 관리한다"는 감각만 잡으면 충분합니다.

    핵심 개념디스크립터와 디스크립터 힙

    셰이더가 텍스처를 읽으려면 "이 메모리는 1024×1024 RGBA8 텍스처이고, 밉은 11개다" 같은 해석 정보가 필요합니다. 이 작은 설명서가 디스크립터(descriptor), 또는 뷰(view)입니다. 용도별로 이름이 있습니다: SRV(셰이더가 읽기), UAV(셰이더가 읽고 쓰기), CBV(상수 버퍼), RTV(렌더 타깃), DSV(깊이 버퍼).

    디스크립터는 디스크립터 힙(descriptor heap)이라는 고정 크기 배열 안의 한 칸에 삽니다. 칸 하나의 크기는 GPU마다 다르기 때문에, i번째 칸의 주소는 "힙 시작 + i × 증분 크기"로 계산합니다. 증분 크기는 디바이스에게 물어봐야 합니다(GetDescriptorHandleIncrementSize).

    힙에는 두 종류가 있습니다. 셰이더 가시(shader-visible) 힙은 GPU가 그리기 도중 직접 읽을 수 있는 힙이고, CBV/SRV/UAV와 샘플러만 이렇게 만들 수 있습니다. RTV/DSV 힙은 CPU 쪽에만 있는 힙으로, "어디에 그릴지"를 기록하는 순간에 읽히고 끝납니다. 셰이더 가시 힙은 한 번에 하나만 바인딩할 수 있고 바꾸는 비용이 크기 때문에, ProjectE는 큰 힙 하나를 만들어 프레임 내내 고정합니다.

    uint32 SrvDescriptorCount = 65536; // 셰이더 가시 CBV/SRV/UAV 힙 크기 (바인드리스 ...)
...
// BeginFrame: 셰이더 가시 힙 바인딩 (프레임 내내 동일)
ID3D12DescriptorHeap* DescriptorHeaps[] = { SrvAllocator.GetHeap() };
CommandList->SetDescriptorHeaps(1, DescriptorHeaps);

    힙 자체는 고정 크기 배열일 뿐이므로, 칸을 나눠 주고 돌려받는 관리자가 필요합니다. FD3D12DescriptorAllocator는 프리 리스트 방식입니다. 반환된 칸 번호를 목록에 모아 두었다가 다음 요청에 먼저 내주고, 없으면 아직 안 쓴 칸(NextUnused)을 내줍니다. 머티리얼 텍스처 표처럼 연속 칸이 필요한 요청은 AllocateRange로 따로 처리합니다.

    FD3D12DescriptorHandle FD3D12DescriptorAllocator::Allocate()
{
	uint32 Index;
	if (!FreeList.empty())
	{
		Index = FreeList.back();
		FreeList.pop_back();
	}
	else
	{
		E_CHECKF(NextUnused < Capacity, "디스크립터 힙 용량 초과 ({}개)", Capacity);
		Index = NextUnused++;
	}
	return MakeHandle(Index, 1); // Cpu/Gpu 핸들 = 힙 시작 + Index × 증분
}
    주의: Free는 "즉시 재사용 가능"을 뜻한다 할당자 머리 주석에 이렇게 적혀 있습니다: "Free는 즉시 재사용 가능 상태로 만들므로 GPU가 해당 디스크립터 사용을 끝낸 뒤 호출해야 한다." 반환한 칸에 곧바로 다른 텍스처의 디스크립터가 써지면, 아직 실행 중인 이전 프레임이 엉뚱한 텍스처를 읽습니다. 이 문제는 6강의 지연 해제가 해결합니다.

    핵심 개념스왑체인: 그린 그림을 화면에 내보내기

    모니터는 일정한 주기(예: 60Hz)로 화면 이미지를 읽어 갑니다. 엔진이 그 이미지를 그리는 도중에 모니터가 읽어 가면 위아래가 다른 프레임인 "찢어진" 화면(티어링)이 보입니다. 그래서 그리기용 버퍼와 표시용 버퍼를 따로 두고, 다 그리면 둘을 바꿉니다. 이 버퍼 묶음이 스왑체인(swap chain)이고, 바꾸는 동작이 Present입니다.

    여기에 세 가지 결정이 담겨 있습니다.

    • 플립 모델(FLIP_DISCARD): 버퍼 내용을 복사하지 않고 "어느 버퍼가 화면인지"만 바꿉니다. 현대 Windows에서 권장되는 방식이고, VSync를 끄고 티어링을 허용하는 기능(ALLOW_TEARING)도 이 모델에서만 됩니다. Phase 0 DoD의 "F1 VSync 토글"이 바로 SyncInterval 0/1 전환입니다.
    • 백버퍼 3장: 하나는 화면에 표시 중, 하나는 표시 대기, 하나에 그리는 중일 수 있어 CPU/GPU가 덜 기다립니다. 그리고 앞 절대로 프레임 칸 수와 같습니다.
    • UNORM 리소스 + sRGB 뷰: 플립 모델은 sRGB 포맷 버퍼를 직접 만들 수 없습니다. 그래서 리소스는 R8G8B8A8_UNORM으로 만들고, 같은 버퍼에 RTV를 두 개 만듭니다 — sRGB 뷰(씬을 그릴 때, 선형 색을 쓰면 하드웨어가 감마 인코딩)와 UNORM 뷰(UI처럼 이미 sRGB인 색을 그대로 쓸 때). 색공간 이야기는 5강과 15강에서 이어집니다.

    창 크기가 바뀌면 스왑체인 버퍼도 다시 만들어야 합니다. 이때 GPU가 옛 백버퍼를 아직 쓰고 있으면 안 되므로, FD3D12RHI::Resize는 큐를 Flush한 뒤에 ResizeBuffers를 부르고 깊이 버퍼도 함께 다시 만듭니다. 크기가 0(최소화)이면 아무것도 하지 않습니다. 1강의 "최소화 상태에서는 렌더링을 건너뛴다"와 짝을 이루는 부분입니다.

    함정과 교훈

    실제로 겪은 일: 디버그 레이어 오류 1,900여 건 Phase 6에서 자동 화면 검증 도구를 처음 만들고 디버그 레이어 메시지를 로그로 모으자, 화면은 멀쩡한데 IBL과 포스트 프로세스 쪽에서 상태 검증 오류가 1,900여 건 쌓여 있었습니다. 컴퓨트와 그래픽스가 함께 쓰는 디스크립터 범위의 플래그가 실제 사용과 맞지 않았던 것입니다(범위를 DATA_VOLATILE로 바꿔 해결 — 루트 시그니처는 3강). 화면이 맞다고 해서 API 사용이 맞는 것은 아닙니다. 드라이버나 GPU가 바뀌면 같은 코드가 깨진 화면을 낼 수 있습니다. 이후 "디버그 레이어 오류·경고 0건"은 모든 렌더링 작업의 기본 검사가 되었습니다.
    실제로 겪은 일: 셰이더 가시 힙 4096 → 65536 처음 셰이더 가시 힙은 4096칸이었습니다. 2026-10-04 레이 트레이싱 스트레스 장면(Tests/Stress)을 다시 만들면서, RT 스킨 인스턴스가 프리미티브마다 정점 SRV를 잡자 "유닛 500 × 9 > 4096"으로 힙이 모자랐습니다. 할당자는 용량을 넘으면 E_CHECKF로 즉시 멈추게 되어 있어서(조용히 덮어쓰지 않음) 원인을 바로 알 수 있었고, 힙을 65536칸으로 늘렸습니다. 고정 크기 자원은 "넘치면 어떻게 되는가"를 처음부터 정해 두어야 합니다.
    • 리사이즈 전에는 반드시 GPU를 비운다: 백버퍼를 참조하는 프레임이 GPU에 남아 있는데 ResizeBuffers를 부르면 실패합니다. 리사이즈는 드물게 일어나므로 Flush의 비용은 문제되지 않습니다.
    • "생성 직후 리스트는 기록 상태": CreateCommandList로 만든 리스트는 열린 상태라, 초기화 끝에 바로 Close해 두어야 첫 BeginFrame의 Reset이 성공합니다. FD3D12RHI::Init에 이 주석이 그대로 남아 있습니다.
    • 대기는 꼭 필요한 곳에서만: 프레임마다 Flush하면 코드는 단순해지지만 CPU와 GPU가 번갈아 놉니다. 기다림은 "칸을 다시 쓰기 직전" 한 곳에 모아 둡니다.
    정리
    • CPU는 명령을 기록해 큐에 넣고, GPU는 나중에 실행한다. 둘은 비동기다.
    • 할당자 = 명령 메모리, 리스트 = 기록 도구, 큐 = 실행 대기열, 펜스 = "어디까지 끝났나" 신호.
    • 프레임 자원을 칸마다 따로 두고(ProjectE 3칸), 칸을 다시 쓰기 직전에만 그 칸의 펜스를 기다린다.
    • 디스크립터는 리소스 해석 정보, 힙은 그 배열. 셰이더 가시 힙은 큰 것 하나를 프레임 내내 고정한다.
    • 스왑체인은 플립 모델 + 백버퍼 3장 + UNORM 리소스/sRGB 뷰. 디버그 레이어 메시지는 엔진 로그로 모아 0건을 확인한다.

    생각해 볼 문제

    Q1. 칸이 1개뿐이라면(FrameCount = 1) 그림 2-2의 타임라인은 어떻게 바뀔까요? 프레임 N을 시작하려면 그 칸을 쓴 프레임 N-1이 GPU에서 끝나야 합니다. 즉 CPU가 기록하는 동안 GPU는 놀고, GPU가 실행하는 동안 CPU는 기다리는 "핑퐁"이 됩니다. 프레임 시간은 대략 CPU 시간 + GPU 시간이 되고, 칸이 여러 개일 때는 둘 중 큰 쪽에 가까워집니다.
    Q2. 커맨드 리스트는 제출 직후 Reset해도 되는데, 할당자는 왜 안 될까요? 리스트는 "기록하는 도구"일 뿐이고 명령의 실제 바이트는 할당자 메모리에 있습니다. 제출 직후 할당자를 Reset하면 GPU가 아직 읽지 않은 명령이 지워지거나 덮어써집니다. 그래서 ProjectE는 할당자를 칸마다 두고, BeginFrame에서 그 칸의 펜스를 통과한 뒤에만 Reset합니다.
    Q3. 백버퍼 리소스는 UNORM인데 왜 씬은 sRGB 뷰로 그릴까요? 셰이더의 조명 계산은 선형 공간에서 해야 맞습니다(5강). 모니터는 감마 인코딩된 값을 기대하므로, 선형 결과를 sRGB 뷰에 쓰면 하드웨어가 쓰는 순간 자동으로 인코딩해 줍니다. 플립 모델이 sRGB 리소스를 허용하지 않으므로 "리소스는 UNORM, 뷰는 sRGB"로 같은 메모리를 두 방식으로 봅니다. 이미 sRGB인 UI 색은 UNORM 뷰로 그려 이중 인코딩을 피합니다.

    왜 필요한가GPU는 "삼각형을 칠하는 기계"다

    Phase 1의 완료 기준은 이렇습니다: "Sandbox 화면 중앙에 빨강/초록/파랑 정점 색이 보간된 삼각형이 그려진다." 3D 게임의 모든 물체 — 캐릭터, 건물, 지형 — 는 결국 수많은 삼각형입니다. 삼각형 하나를 그릴 수 있으면 백만 개도 그릴 수 있고, 그래서 그래픽스 공부는 늘 "첫 삼각형"에서 시작합니다.

    그런데 2강에서 보았듯이 GPU는 CPU의 말을 그 자리에서 듣지 않습니다. 명령 목록을 받아 나중에 실행하고, 실행할 때 필요한 정보는 전부 미리 준비되어 있어야 합니다. 정점 데이터는 어디 있고 어떤 모양인지, 정점마다·픽셀마다 무슨 계산을 할지(셰이더), 셰이더가 읽을 상수와 텍스처는 어디 있는지(루트 시그니처), 깊이 비교와 블렌딩은 어떻게 할지(PSO). 이 강의는 이 준비물을 하나씩 만듭니다.

    핵심 개념래스터화 파이프라인

    GPU가 삼각형을 그리는 과정은 공장의 조립 라인처럼 단계가 정해져 있습니다. 일부 단계는 우리가 직접 프로그램(셰이더)을 짜 넣고, 나머지는 하드웨어에 고정된 기능을 설정값으로만 조절합니다.

    • 입력 조립(Input Assembler): 정점 버퍼의 바이트를 입력 레이아웃에 따라 잘라 정점으로 만들고, 인덱스(또는 순서)대로 세 개씩 묶어 삼각형을 만듭니다.
    • 정점 셰이더(Vertex Shader): 정점마다 한 번 실행됩니다. 가장 중요한 출력은 클립 공간 위치(SV_Position)입니다. 3D 변환은 거의 전부 여기서 일어납니다(4강, 5강).
    • 래스터화(Rasterizer): 화면에서 삼각형이 덮는 픽셀을 찾고, 정점 셰이더가 내보낸 나머지 값(색, UV, 법선 …)을 픽셀 위치에 맞게 섞어 줍니다. 뒷면 제거(컬링), 뷰포트 변환도 여기서 합니다.
    • 픽셀 셰이더(Pixel Shader): 덮인 픽셀마다 한 번 실행되어 최종 색을 계산합니다. 텍스처 읽기와 조명 계산이 여기 있습니다.
    • 출력 병합(Output Merger): 깊이 테스트(5강)를 통과한 색을 렌더 타깃에 쓰거나, 이미 있는 색과 섞습니다(블렌딩).

    핵심 개념정점 버퍼와 입력 레이아웃

    GPU 입장에서 정점 버퍼는 그냥 바이트의 나열입니다. "몇 바이트마다 정점 하나이고, 그 안의 몇 번째 바이트부터가 위치인지"를 알려 주는 것이 입력 레이아웃(input layout)입니다. 각 항목은 시맨틱(semantic)이라는 이름표(POSITION, COLOR …)를 달고 있고, 셰이더 입력 구조체의 같은 이름표와 짝지어집니다.

    Phase 1의 삼각형 정점은 위치(float3)와 색(float4)뿐이었습니다. Phase 2~3에서 텍스처와 조명을 위해 법선과 UV가 붙은 FVertex가 됩니다. 아래는 Phase 3 시점의 정점 구조와 입력 레이아웃입니다.

    // 정적 메시 정점 (셰이더 입력 레이아웃은 FStaticMesh::GetInputLayout 참조)
struct FVertex
{
	FVector3 Position;
	FVector3 Normal;
	FVector2 UV;
	FVector4 Color = FVector4::OneVector;
};

static const std::vector<D3D12_INPUT_ELEMENT_DESC> Layout = {
	{ "POSITION", 0, DXGI_FORMAT_R32G32B32_FLOAT,    0, offsetof(FVertex, Position), D3D12_INPUT_CLASSIFICATION_PER_VERTEX_DATA, 0 },
	{ "NORMAL",   0, DXGI_FORMAT_R32G32B32_FLOAT,    0, offsetof(FVertex, Normal),   D3D12_INPUT_CLASSIFICATION_PER_VERTEX_DATA, 0 },
	{ "TEXCOORD", 0, DXGI_FORMAT_R32G32_FLOAT,       0, offsetof(FVertex, UV),       D3D12_INPUT_CLASSIFICATION_PER_VERTEX_DATA, 0 },
	{ "COLOR",    0, DXGI_FORMAT_R32G32B32A32_FLOAT, 0, offsetof(FVertex, Color),    D3D12_INPUT_CLASSIFICATION_PER_VERTEX_DATA, 0 },
};

    버퍼를 GPU 메모리에 올리기

    GPU가 가장 빨리 읽는 메모리는 VRAM의 DEFAULT 힙인데, CPU는 여기에 직접 쓸 수 없습니다. CPU가 쓸 수 있는 UPLOAD 힙에 먼저 복사한 뒤, GPU에게 "업로드 힙에서 기본 힙으로 복사하라"는 명령을 시킵니다. Phase 1의 FD3D12Buffer::InitStatic이 정확히 이 두 단계입니다.

    // GPU 전용 버퍼. 버퍼는 COMMON 상태에서 생성하며 복사/사용 시 암시적 상태 승격·감쇠 규칙을 따른다.
const D3D12_HEAP_PROPERTIES DefaultHeap = MakeHeapProperties(D3D12_HEAP_TYPE_DEFAULT);
E_D3D_VERIFY(D3DDevice->CreateCommittedResource(&DefaultHeap, D3D12_HEAP_FLAG_NONE, &BufferDesc,
                                                D3D12_RESOURCE_STATE_COMMON, nullptr, IID_PPV_ARGS(&Resource)));
// 스테이징용 업로드 버퍼
const D3D12_HEAP_PROPERTIES UploadHeap = MakeHeapProperties(D3D12_HEAP_TYPE_UPLOAD);
...
E_D3D_VERIFY(UploadBuffer->Map(0, &NoRead, &Mapped));
std::memcpy(Mapped, Data, static_cast<size_t>(SizeInBytes));
UploadBuffer->Unmap(0, nullptr);
// 복사 후 완료 대기
Queue.ExecuteImmediate(D3DDevice, [&](ID3D12GraphicsCommandList* CommandList) {
	CommandList->CopyBufferRegion(Resource.Get(), 0, UploadBuffer.Get(), 0, SizeInBytes);
});

    ExecuteImmediate는 2강의 큐 래퍼에 있는 함수로, 임시 할당자·리스트를 만들어 기록하고 제출한 뒤 끝날 때까지 기다립니다. 업로드 버퍼는 함수가 끝나면 사라지는 지역 변수인데, GPU가 복사를 마친 뒤이므로 안전합니다. 로딩 시점에는 이렇게 동기적으로 해도 괜찮지만, 게임 도중 큰 에셋을 불러오면 화면이 멈칫합니다. 그래서 Phase 37에서 복사 큐로 비동기 업로드하는 InitStaticAsync가 추가되었습니다(30강).

    그릴 때는 버퍼의 GPU 주소·크기·간격(stride)을 담은 정점 버퍼 뷰를 입력 조립 단계에 꽂습니다. 이건 디스크립터 힙을 거치지 않고 명령에 바로 들어가는 작은 구조체입니다.

    const D3D12_VERTEX_BUFFER_VIEW VertexView = VertexBuffer.GetVertexBufferView(sizeof(FVertex));
const D3D12_INDEX_BUFFER_VIEW  IndexView  = IndexBuffer.GetIndexBufferView(DXGI_FORMAT_R32_UINT);

CommandList->IASetPrimitiveTopology(D3D_PRIMITIVE_TOPOLOGY_TRIANGLELIST);
CommandList->IASetVertexBuffers(0, 1, &VertexView);
CommandList->IASetIndexBuffer(&IndexView);
CommandList->DrawIndexedInstanced(IndexCount, 1, 0, 0, 0);
    인덱스 버퍼는 왜 쓰나 정육면체는 꼭짓점이 8개지만 삼각형은 12개(면 6개 × 2)입니다. 정점을 삼각형마다 따로 적으면 36개가 되지만, 정점은 한 번씩만 두고 "몇 번 정점 세 개로 삼각형을 만든다"는 번호 목록(인덱스)을 따로 두면 메모리도 줄고, GPU가 같은 정점의 셰이더 결과를 재사용할 수도 있습니다. (ProjectE의 큐브는 면마다 법선이 달라 면별로 정점 4개, 총 24개를 둡니다.)

    핵심 개념HLSL 셰이더와 DXC

    셰이더(shader)는 GPU에서 실행되는 작은 프로그램이고, DirectX에서는 HLSL이라는 C와 비슷한 언어로 씁니다. Phase 1의 셰이더는 지금도 Engine/Shaders/Triangle.hlsl에 그대로 남아 있습니다.

    #include "Common.hlsli"

// Phase 1: NDC 좌표를 그대로 출력하는 첫 삼각형

struct FVertexInput
{
	float3 Position : POSITION;
	float4 Color    : COLOR;
};

struct FPixelInput
{
	float4 Position : SV_Position;
	float4 Color    : COLOR;
};

FPixelInput VSMain(FVertexInput Input)
{
	FPixelInput Output;
	Output.Position = float4(Input.Position, 1.0f);
	Output.Color    = Input.Color;
	return Output;
}

float4 PSMain(FPixelInput Input) : SV_Target
{
	return Input.Color;
}

    정점 셰이더 VSMain은 위치에 w = 1을 붙여 그대로 내보냅니다. 아직 카메라가 없으므로 정점 좌표를 처음부터 NDC(정규화 장치 좌표)로 줍니다. NDC는 화면 왼쪽 끝이 x = −1, 오른쪽 끝이 +1, 아래가 y = −1, 위가 +1인 좌표계입니다. 삼각형을 화면 중앙에 두려면 정점을 이 범위 안에 두면 됩니다. SV_로 시작하는 시맨틱은 "시스템 값"으로, SV_Position은 래스터라이저가 읽는 위치, SV_Target은 렌더 타깃에 쓸 색입니다. 그 밖의 출력(COLOR)은 래스터라이저가 보간해서 픽셀 셰이더 입력으로 넘겨줍니다.

    컴파일: HLSL → DXIL

    GPU는 HLSL 텍스트를 바로 실행하지 못합니다. 마이크로소프트의 컴파일러 DXC가 HLSL을 DXIL이라는 중간 바이트코드로 바꾸고, 드라이버가 PSO를 만들 때 그것을 GPU 기계어로 다시 번역합니다. ProjectE는 DXC를 라이브러리로 불러 엔진 안에서 컴파일합니다(FD3D12ShaderCompiler).

    ArgStorage.push_back(L"-E");  ArgStorage.push_back(Desc.EntryPoint);                       // 진입 함수 (VSMain)
ArgStorage.push_back(L"-T");  ArgStorage.push_back(GetShaderTargetProfile(Desc.Stage, ...)); // vs_6_0, ps_6_0 ...
ArgStorage.push_back(L"-I");  ArgStorage.push_back(ShaderDir.wstring());                     // #include 기준 폴더
ArgStorage.push_back(L"-HV"); ArgStorage.push_back(L"2021");                                 // HLSL 2021 문법
ArgStorage.push_back(L"-Zpr"); // 행우선 행렬 (CPU FMatrix4x4 레이아웃과 동일)
ArgStorage.push_back(L"-WX");  // 경고를 에러로
#if E_DEBUG
ArgStorage.push_back(L"-Zi"); ArgStorage.push_back(L"-Od"); ArgStorage.push_back(L"-Qembed_debug");
#else
ArgStorage.push_back(L"-O3"); ArgStorage.push_back(L"-Qstrip_debug");
#endif

    C++ 쪽 규칙이 셰이더에도 똑같이 적용된다는 점을 보세요. 경고는 에러(-WX), 디버그 빌드는 최적화를 끄고 디버그 정보를 넣습니다. -Zpr은 4강의 행렬 규약과 직결되는 옵션입니다.

    셰이더를 매번 컴파일하면 시작이 느리고, 출시한 게임에는 DXC를 넣고 싶지도 않습니다. 그래서 셰이더는 항상 FShaderLibrary를 통해 얻습니다. 조회 순서는 "메모리 캐시 → 쿠킹된 DXIL 파일 → DXC 컴파일(+쿠킹 파일 기록)"이고, 미리 쿠킹할 셰이더 목록은 Engine/Shaders/Shaders.json에 적습니다. 첫 삼각형의 두 진입점도 이 목록에 그대로 있습니다.

    { "File": "Triangle.hlsl", "Entry": "VSMain", "Stage": "Vertex" },
{ "File": "Triangle.hlsl", "Entry": "PSMain", "Stage": "Pixel" },

    쿠킹 파일이 아직 유효한지는 파일 시각이 아니라 소스와 #include 파일 내용의 해시로 판정합니다. 쿠킹과 핫 리로드(에디터에서 셰이더를 저장하면 바로 반영)는 10강에서 자세히 다룹니다.

    핵심 개념루트 시그니처: 셰이더가 받을 인수 목록

    셰이더는 상수 버퍼(register(b0)), 텍스처(register(t0)), 샘플러(register(s0)) 같은 리소스를 레지스터 번호로 선언합니다. 그런데 CPU는 "b0에 이 버퍼를 꽂는다"를 어떻게 지시할까요? 그 연결표가 루트 시그니처(root signature)입니다. C++ 함수의 시그니처가 "이 함수는 int 하나와 포인터 하나를 받는다"를 정하듯, 루트 시그니처는 "이 셰이더 묶음은 루트 인수 0번에 CBV b0, 1번에 CBV b1, 3번에 t0 테이블을 받는다"를 정합니다.

    루트 인수로 넘길 수 있는 것은 세 종류이고 크기 비용이 다릅니다. 루트 시그니처 전체는 32비트 값(DWORD) 64개를 넘을 수 없습니다.

    종류담는 것비용쓰임
    루트 상수 (AddConstants)값 자체값 하나당 1 DWORD아주 작은 값 (밉 생성 크기, 인스턴스 시작 번호 등)
    루트 디스크립터 (AddConstantBufferView 등)버퍼의 GPU 주소2 DWORD매 드로우 바뀌는 상수 버퍼
    디스크립터 테이블 (AddDescriptorTable)힙 안의 시작 칸 (2강 그림 2-3)1 DWORD텍스처처럼 디스크립터가 꼭 필요한 리소스
    정적 샘플러 (AddStaticSampler)시그니처에 박힌 샘플러 설정0바뀌지 않는 필터/주소 모드

    ProjectE의 FD3D12RootSignature는 이 네 가지를 Add*로 차례로 쌓고 Finalize로 직렬화·생성하는 빌더입니다. 각 Add*는 자기 루트 파라미터 번호를 돌려줍니다. Phase 2~3의 메시 렌더러는 이렇게 만들었습니다.

    const uint32 PerObjectIndex = RootSignature.AddConstantBufferView(0);
const uint32 PerFrameIndex  = RootSignature.AddConstantBufferView(1);
const uint32 MaterialIndex  = RootSignature.AddConstantBufferView(2, 0, D3D12_SHADER_VISIBILITY_PIXEL);
const uint32 TextureIndex   = RootSignature.AddDescriptorTable(
	{ FD3D12RootSignature::MakeRange(D3D12_DESCRIPTOR_RANGE_TYPE_SRV, 1, 0) }, D3D12_SHADER_VISIBILITY_PIXEL);
E_CHECK(PerObjectIndex == RootParam_PerObject && PerFrameIndex == RootParam_PerFrame &&
        MaterialIndex == RootParam_Material && TextureIndex == RootParam_MaterialTexture);
RootSignature.AddStaticSampler(FD3D12RootSignature::MakeStaticSampler(0));
RootSignature.Finalize(Device, D3D12_ROOT_SIGNATURE_FLAG_ALLOW_INPUT_ASSEMBLER_INPUT_LAYOUT, L"MeshRootSignature");

    그릴 때는 루트 시그니처를 바인딩하고 번호별로 인수를 넣습니다: SetGraphicsRootConstantBufferView(RootParam_PerFrame, 주소), SetGraphicsRootDescriptorTable(RootParam_MaterialTexture, 텍스처 SRV의 GPU 핸들). 파라미터 번호를 enum으로 고정하고, 빌더가 돌려준 번호와 같은지 E_CHECK로 확인하는 습관을 보세요. 파라미터 순서를 바꾸고 enum을 깜빡하면 셰이더가 엉뚱한 버퍼를 읽는데, 이 검사가 그 실수를 시작하자마자 잡아 줍니다.

    버전 1.1과 범위 플래그 ProjectE의 루트 시그니처는 버전 1.1로만 만듭니다(Finalize가 지원 여부를 확인). 1.1에서는 디스크립터 범위에 "이 데이터는 그리기 도중 바뀌지 않는다/바뀔 수 있다" 같은 플래그를 달아 드라이버 최적화를 돕습니다. 기본값은 "그리기 중에는 고정(STATIC_WHILE_SET_AT_EXECUTE)"인데, 실제로는 바뀌는 범위에 기본값을 두면 디버그 레이어가 오류를 냅니다 — 2강의 "1,900여 건" 이야기가 바로 이것이었습니다.

    핵심 개념파이프라인 상태 객체(PSO)

    그림 3-1의 고정 기능 단계에는 설정이 많습니다. 뒷면을 버릴지, 깊이 테스트를 할지, 블렌딩은 어떻게 할지, 렌더 타깃 형식은 무엇인지. DirectX 11까지는 이것들을 상태마다 따로 바꿀 수 있었는데, 그러면 드라이버가 그리기 직전에 "이 조합에 맞는 GPU 기계어"를 그때그때 만들어야 해서 예측할 수 없는 끊김이 생겼습니다.

    DX12는 셰이더 바이트코드, 입력 레이아웃, 래스터라이저·깊이·블렌드 설정, 렌더 타깃 형식, 루트 시그니처를 통째로 하나의 객체로 미리 굽게 합니다. 이것이 PSO(Pipeline State Object)입니다. 그리기 직전에는 SetPipelineState(PSO) 한 번이면 됩니다. 비용은 PSO 생성 시점으로 옮겨졌고, 그래서 "PSO를 언제 미리 만들어 둘 것인가"가 나중에 중요한 문제가 됩니다(31강).

    ProjectE의 FGraphicsPipelineDesc는 이 수십 개 필드 중 자주 쓰는 값을 기본값으로 두고 필요한 것만 바꾸게 한 구조체입니다.

    // 그래픽스 파이프라인 설정. 자주 쓰는 값이 기본값이며 필요한 항목만 바꾼다.
struct FGraphicsPipelineDesc
{
	ID3D12RootSignature*  RootSignature = nullptr;
	D3D12_SHADER_BYTECODE VertexShader{};
	D3D12_SHADER_BYTECODE PixelShader{};
	std::vector<D3D12_INPUT_ELEMENT_DESC> InputLayout;
	uint32      NumRenderTargets       = 1;
	DXGI_FORMAT RenderTargetFormats[8] = { DXGI_FORMAT_R8G8B8A8_UNORM };
	DXGI_FORMAT DepthStencilFormat     = DXGI_FORMAT_UNKNOWN;
	// 래스터라이저. 왼손 좌표계 기본: 시계 방향(CW)이 앞면
	D3D12_CULL_MODE CullMode               = D3D12_CULL_MODE_BACK;
	bool            bFrontCounterClockwise = false;
	// 깊이
	bool                  bDepthEnable = false;
	D3D12_COMPARISON_FUNC DepthFunc    = D3D12_COMPARISON_FUNC_LESS;
	// 블렌딩
	EBlendMode BlendMode = EBlendMode::Opaque;
	...
};
    FGraphicsPipelineDesc PsoDesc;
PsoDesc.RootSignature          = RootSignature.Get();
PsoDesc.VertexShader           = FD3D12ShaderCompiler::ToBytecode(VertexShader.Get());
PsoDesc.PixelShader            = FD3D12ShaderCompiler::ToBytecode(PixelShader.Get());
PsoDesc.InputLayout            = FStaticMesh::GetInputLayout();
PsoDesc.RenderTargetFormats[0] = FD3D12RHI::RenderTargetFormat; // 백버퍼 sRGB 뷰 (2강)
PsoDesc.DepthStencilFormat     = FD3D12RHI::DepthBufferFormat;  // D32_FLOAT (5강)
PsoDesc.bDepthEnable           = true;
PipelineState.InitGraphics(Device, PsoDesc, L"MeshPipeline");

    PSO의 렌더 타깃 형식은 실제로 그릴 렌더 타깃 뷰의 형식과 정확히 같아야 합니다. 그래서 RHI가 RenderTargetFormat(sRGB)과 DepthBufferFormat을 상수로 공개하고, PSO를 만드는 쪽은 그 상수를 씁니다. 숫자를 각자 적으면 한쪽만 바뀌는 사고가 납니다.

    앞면은 시계 방향(CW) 래스터라이저는 화면에서 정점이 시계 방향으로 도는 삼각형을 앞면으로 보고, 기본 설정(CULL_MODE_BACK)은 뒷면을 버립니다. 메시를 만드는 모든 코드는 이 규약을 지켜야 하며, ProjectE는 이것을 테스트로 고정합니다(Tests/RendererTests의 Cube_WindingIsClockwiseFromOutside: 바깥에서 본 삼각형의 Cross(P1−P0, P2−P0)가 바깥 법선과 같은 방향). 왜 외적의 방향이 시계 방향과 연결되는지는 4강의 왼손 좌표계에서 설명합니다.

    핵심 개념래스터화와 보간

    정점은 세 개뿐인데 삼각형 안의 픽셀은 수천 개입니다. 픽셀마다 색은 어떻게 정해질까요? 래스터라이저는 픽셀 중심 P가 삼각형 안에 있는지 판정하면서, 동시에 P가 세 꼭짓점에 얼마나 "가까운지"를 나타내는 세 가중치 w0, w1, w2를 구합니다. 이것이 무게중심 좌표(barycentric coordinates)입니다.

    보간된 값은 정점 셰이더가 내보낸 모든 출력에 똑같이 적용됩니다. 첫 삼각형에서는 색이 보간되어 무지개 같은 그라데이션이 생기고, 5강에서는 같은 원리로 UV(텍스처 좌표)와 법선이 보간되어 픽셀마다 다른 텍스처 위치와 조명이 계산됩니다. 3D에서는 가까운 부분이 화면에서 더 크게 보이므로 화면 넓이 비율로만 섞으면 텍스처가 휘어 보이는데, GPU는 이를 피하려고 원근 보정 보간을 자동으로 합니다(값/w와 1/w를 보간해 나눔 — w는 4강의 동차 좌표).

    핵심 개념뷰포트와 시저

    NDC는 [−1, 1] 범위의 추상적인 좌표입니다. 이것을 실제 픽셀 좌표로 바꾸는 규칙이 뷰포트(viewport)이고, 뷰포트 안에서도 일부 사각형 밖은 그리지 않게 자르는 것이 시저(scissor) 사각형입니다. 둘 다 PSO에 들어가지 않고 매번 명령으로 설정하는 몇 안 되는 상태입니다(창 크기는 수시로 바뀌므로).

    CommandList->OMSetRenderTargets(1, &Rtv, FALSE, &Dsv);

const D3D12_VIEWPORT Viewport{ 0.0f, 0.0f,
                               static_cast<float>(SwapChain.GetWidth()), static_cast<float>(SwapChain.GetHeight()),
                               D3D12_MIN_DEPTH, D3D12_MAX_DEPTH };
const D3D12_RECT Scissor{ 0, 0, static_cast<LONG>(SwapChain.GetWidth()), static_cast<LONG>(SwapChain.GetHeight()) };
CommandList->RSSetViewports(1, &Viewport);
CommandList->RSSetScissorRects(1, &Scissor);

    뷰포트 변환은 x픽셀 = (xNDC + 1) / 2 × 너비, y픽셀 = (1 − yNDC) / 2 × 높이입니다. 화면 픽셀은 위에서 아래로 번호가 늘지만 NDC의 +y는 위쪽이라 y가 뒤집힙니다. 깊이는 NDC z(0~1)를 MinDepth~MaxDepth로 옮기며, 여기서는 기본값 0과 1입니다. 시저는 기본적으로 전체 화면이지만, 에디터 UI처럼 "이 패널 안에서만 그려라"가 필요할 때 좁혀 씁니다.

    여기까지가 첫 삼각형의 준비물 전부입니다. 프레임마다 하는 일은 BeginFrame(2강) → 루트 시그니처·PSO 설정 → 정점 버퍼 바인딩 → DrawInstanced → EndFrame입니다. 이 몇 줄을 위해 위의 부품들이 미리 만들어져 있어야 합니다.

    생각해 볼 문제

    Q1. 정점 색을 보간하지 않고 삼각형 전체를 V0의 색으로 칠하고 싶다면 어떻게 할까요? 가장 간단한 방법은 픽셀 셰이더가 정점 색 대신 상수를 출력하는 것입니다. 보간 자체를 끄려면 HLSL 출력에 nointerpolation 수식어를 붙입니다. 그러면 래스터라이저가 보간하지 않고 삼각형의 "기준 정점"(첫 번째 정점) 값을 모든 픽셀에 그대로 넘깁니다. 정수 ID처럼 섞이면 의미가 없는 값을 넘길 때 실제로 쓰입니다.
    Q2. 매 드로우 바뀌는 4×4 행렬 두 개(128바이트)를 루트 상수로 넘기면 어떤 문제가 있을까요? 행렬 두 개는 32비트 값 32개, 즉 32 DWORD입니다. 루트 시그니처 한도 64 DWORD의 절반을 이것 하나가 차지합니다. 게다가 루트 인수가 클수록 드로우마다 GPU에 넘기는 양이 늘어납니다. 그래서 큰 데이터는 업로드 메모리에 쓰고 2 DWORD짜리 루트 CBV로 주소만 넘깁니다(그림 3-3).
    Q3. 같은 셰이더로 "불투명" 물체와 "반투명" 물체를 그리려면 PSO가 몇 개 필요할까요? 블렌드 설정은 PSO에 구워지므로 최소 두 개입니다(블렌딩 끔/켬, 반투명은 보통 깊이 쓰기도 끔). 실제로 ProjectE의 메시 PSO는 Masked/Additive·양면·스킨 여부의 조합으로 변형 8개를 가집니다(CLAUDE.md "메시 PSO 변형 = 묶음 키 Pipeline 3비트"). 상태 조합마다 PSO가 생기기 때문에 PSO 수 관리가 엔진의 중요한 일이 됩니다.

    왜 필요한가3D 그래픽스는 "좌표를 옮기는 일"이다

    3강의 삼각형은 처음부터 화면 좌표(NDC)로 주어졌습니다. 하지만 실제 게임에서 물체의 정점은 모델을 만든 사람이 정한 자기 좌표계로 저장되어 있습니다. 이것을 월드에 놓고(이동·회전·크기), 카메라 기준으로 바꾸고, 원근을 입혀 화면으로 옮겨야 합니다. 물리, 애니메이션, AI, 네트워크도 결국 위치와 방향을 계산합니다. 수학 라이브러리는 엔진 전체가 쓰는 공용어이고, 그 규약(축의 방향, 곱하는 순서, 단위)이 한 군데라도 어긋나면 화면이 뒤집히거나 물체가 엉뚱한 쪽을 봅니다.

    그래서 ProjectE는 수학 라이브러리를 직접 만들고(0강의 "직접 구현" 목록), 규약을 CLAUDE.md 맨 앞에 적고, 단위 테스트로 고정했습니다. Phase 1의 완료 기준에 "수학 단위 테스트 전부 통과"가 들어간 이유입니다.

    핵심 개념벡터, 내적, 외적

    벡터는 방향과 크기를 가진 양입니다. 위치(원점에서 그 점까지의 화살표), 속도, 법선(표면이 바라보는 방향)이 모두 벡터입니다. ProjectE의 FVector3는 float 세 개짜리 구조체이고, 축의 의미가 주석과 상수로 박혀 있습니다.

    // 엔진 좌표계: 왼손 Z-up — +X 앞(Forward), +Y 오른쪽(Right), +Z 위(Up). Cross(Forward, Right) == Up.
struct FVector3
{
	float X, Y, Z;
	static const FVector3 ForwardVector; // (1, 0, 0)
	static const FVector3 RightVector;   // (0, 1, 0)
	static const FVector3 UpVector;      // (0, 0, 1)

	static constexpr float Dot(const FVector3& A, const FVector3& B) { return A.X * B.X + A.Y * B.Y + A.Z * B.Z; }
	static constexpr FVector3 Cross(const FVector3& A, const FVector3& B)
	{
		return { A.Y * B.Z - A.Z * B.Y,
		         A.Z * B.X - A.X * B.Z,
		         A.X * B.Y - A.Y * B.X };
	}
	...
};

    내적(dot product): "얼마나 같은 방향인가"

    a·b = axbx + ayby + azbz = |a||b| cos θ 입니다. 두 벡터가 같은 방향이면 양수, 수직이면 0, 반대면 음수입니다. 한쪽이 길이 1(정규화)이면 내적은 "다른 쪽을 그 방향으로 투영한 길이"가 됩니다. 쓰임새는 끝이 없습니다: 조명의 밝기(법선과 빛 방향의 내적, 5강), 물체가 카메라 앞에 있는지, 평면에서 점까지의 거리(프러스텀 컬링, 13강).

    외적(cross product): "두 벡터에 모두 수직인 방향"

    a×b는 a와 b 모두에 수직이고 길이가 |a||b| sin θ(두 벡터가 만드는 평행사변형 넓이)인 벡터입니다. 삼각형의 면 법선, 카메라의 오른쪽 축 계산에 씁니다. 그런데 "수직인 방향"은 두 가지(위/아래)라서, 어느 쪽이 나오는지는 좌표계의 손잡이(handedness)가 정합니다. ProjectE는 왼손 좌표계라 Cross(Forward, Right) == Up이 되며, 테스트가 이것을 지킵니다.

    E_TEST(Vector3_DotAndCross)
{
	E_EXPECT_NEAR(FVector3::Dot(FVector3(1.0f, 2.0f, 3.0f), FVector3(4.0f, 5.0f, 6.0f)), 32.0f, Tol);
	// 좌표계 규약: Forward × Right == Up
	E_EXPECT_EQUALS(FVector3::Cross(FVector3::ForwardVector, FVector3::RightVector), FVector3::UpVector, Tol);
	E_EXPECT_EQUALS(FVector3::Cross(FVector3::RightVector, FVector3::UpVector), FVector3::ForwardVector, Tol);
	E_EXPECT_EQUALS(FVector3::Cross(FVector3::UpVector, FVector3::ForwardVector), FVector3::RightVector, Tol);
}
    왼손과 오른손 세 축 중 둘(앞, 위)을 정하면 나머지 하나(오른쪽)는 두 방향 중 하나를 고를 수 있습니다. 왼손 엄지를 +X, 검지를 +Y로 펴고 중지를 꺾으면 +Z가 나오는 쪽이 왼손 좌표계입니다. 어느 쪽도 "옳은" 것은 아니고 약속일 뿐이지만, 섞이면 모든 것이 거울에 비친 것처럼 뒤집힙니다. 외적 공식 자체는 같고, 결과 벡터를 "어느 쪽"으로 해석하느냐가 달라집니다. 3강의 "시계 방향이 앞면" 규약도 여기서 나옵니다: 왼손 좌표계에서 바깥에서 볼 때 시계 방향으로 도는 삼각형은 Cross(P1−P0, P2−P0)가 바깥을 향합니다.

    핵심 개념행렬과 변환의 합성

    점을 옮기는 기본 변환은 셋입니다. 크기(Scale), 회전(Rotation), 이동(Translation). 크기와 회전은 3×3 행렬 곱으로 표현되지만, 이동은 "더하기"라서 곱으로 표현되지 않습니다. 이 문제를 푸는 요령이 동차 좌표(homogeneous coordinates)입니다. 3D 점에 네 번째 성분 w = 1을 붙여 (x, y, z, 1)로 쓰면, 4×4 행렬의 마지막 행에 이동량을 넣어 곱 한 번으로 이동까지 할 수 있습니다. 방향 벡터는 w = 0으로 두면 이동의 영향을 받지 않습니다 — 방향은 옮겨도 방향이니까요. FMatrix4x4의 TransformPosition(W = 1)과 TransformVector(W = 0)가 이 구분입니다.

    // 4x4 행렬. 행우선(row-major) 저장, 행벡터 규약: v' = v * M.
// 변환 합성은 적용 순서대로 곱한다: World = Scale * Rotation * Translation, MVP = World * View * Projection.
// 이동 성분은 마지막 행(M[3][0..2])에 위치한다.
struct FMatrix4x4
{
	float M[4][4];
	FVector3 TransformPosition(const FVector3& P) const; // 위치 변환 (W = 1). 원근 나눗셈은 하지 않는다.
	FVector3 TransformVector(const FVector3& V) const;   // 방향 변환 (W = 0, 이동 무시)
	constexpr FVector3 GetOrigin() const { return { M[3][0], M[3][1], M[3][2] }; }
	...
	// Scale * Rotation * Translation
	static FMatrix4x4 MakeTransform(const FVector3& Translation, const FQuat& Rotation, const FVector3& Scale);
};

    행벡터 규약: 곱하는 순서 = 적용하는 순서

    벡터를 행렬의 왼쪽에 두는 행벡터 규약(v * M)에서는, 여러 변환을 곱할 때 먼저 적용할 것을 왼쪽에 씁니다. v · S · R · T는 "크기 → 회전 → 이동" 순서로 읽힙니다. 읽는 방향과 적용 순서가 같아서 직관적이라는 것이 이 규약(DirectX 전통, 언리얼과 같음)을 고른 이유입니다. 반대로 열벡터 규약(OpenGL 교재에 흔함)은 M * v로 쓰고, 같은 변환을 T · R · S · v로 오른쪽부터 읽습니다. 두 규약의 행렬은 서로 전치(transpose) 관계입니다.

    E_TEST(Matrix_MakeTransformOrder)
{
	const FVector3 Translation(5.0f, -2.0f, 1.0f);
	const FQuat    Rotation = FQuat::FromAxisAngle(FVector3::UpVector, FMath::HalfPi);
	const FVector3 Scale(2.0f, 2.0f, 2.0f);
	const FMatrix4x4 W = FMatrix4x4::MakeTransform(Translation, Rotation, Scale);
	// Scale → Rotation → Translation 순서: (1,0,0) → (2,0,0) → (0,2,0) → (5,0,1)
	E_EXPECT_EQUALS(W.TransformPosition(FVector3::ForwardVector), FVector3(5.0f, 0.0f, 1.0f), Tol);
	E_EXPECT_EQUALS(W.GetOrigin(), Translation, Tol);
}

    같은 규칙이 화면까지 이어집니다. 정점을 화면으로 보내는 행렬은 MVP = World · View · Projection(모델 → 월드 → 카메라 → 클립)이고, 부모-자식 계층에서는 자식의 월드 행렬 = 자식 로컬 · 부모 월드입니다(8강).

    HLSL로 넘길 때: -Zpr과 mul(v, M)

    행렬을 메모리에 저장하는 방식도 규약입니다. FMatrix4x4는 M[행][열]로 행 단위 연속 저장(행우선)이고, 이동은 M[3][0..2]에 있습니다. HLSL은 기본적으로 cbuffer의 행렬을 열우선으로 해석합니다. 그대로 올리면 GPU는 전치된 행렬을 보게 되므로, 많은 엔진이 업로드 전에 전치합니다. ProjectE는 대신 셰이더를 -Zpr(행우선)로 컴파일해 CPU와 GPU의 메모리 배치를 똑같이 만들고, 셰이더에서도 행벡터 규약대로 mul(v, M)을 씁니다. 3강의 컴파일 인자와 Common.hlsli 머리 주석이 이 약속을 적어 둡니다.

    // 엔진 공통 셰이더 헤더
// - 행렬은 CPU(FMatrix4x4)와 동일한 행우선(row-major) 레이아웃 (컴파일 옵션 -Zpr)
// - 벡터는 행벡터: 변환은 mul(v, M)
// - 좌표계: 왼손 Z-up (+X 앞, +Y 오른쪽, +Z 위)

    핵심 개념쿼터니언: 회전을 담는 네 개의 수

    회전을 표현하는 가장 직관적인 방법은 오일러 각(Pitch/Yaw/Roll — 고개 들기, 좌우 돌기, 기울이기)입니다. 사람이 입력하기엔 좋지만 엔진 내부 표현으로는 문제가 있습니다. 두 회전 사이를 부드럽게 보간하기 어렵고, 특정 자세에서 두 축이 겹쳐 한 자유도를 잃는 짐벌 락(gimbal lock)이 생깁니다. 회전 행렬은 이런 문제가 없지만 숫자가 9개라 무겁고, 오차가 쌓이면 회전이 아닌 행렬(찌그러짐)이 됩니다.

    쿼터니언(quaternion)은 회전을 네 개의 수로 담습니다. 단위 축 n 둘레로 θ만큼 회전은

    축-각 → 쿼터니언 q = (x, y, z, w) = (nx·sin(θ/2), ny·sin(θ/2), nz·sin(θ/2), cos(θ/2)), |q| = 1
    벡터 회전: v′ = q v q* (q*는 켤레 = (−x, −y, −z, w)) — 코드로는 v′ = v + 2w(qv×v) + 2 qv×(qv×v)

    입니다. 절반 각(θ/2)이 쓰이는 탓에 q와 −q가 같은 회전을 나타낸다는 특이한 성질이 있습니다(FQuat::Equals가 둘을 같게 취급하는 이유). 장점은 분명합니다: 숫자 4개, 정규화만 하면 언제나 올바른 회전, 두 회전 사이를 구면 선형 보간(Slerp)으로 매끄럽게 섞을 수 있습니다. 애니메이션 블렌딩(40강)이 바로 이것에 기댑니다.

    FQuat FQuat::FromAxisAngle(const FVector3& NormalizedAxis, float AngleRadians)
{
	float S, C;
	FMath::SinCos(&S, &C, AngleRadians * 0.5f);
	return { NormalizedAxis.X * S, NormalizedAxis.Y * S, NormalizedAxis.Z * S, C };
}

FQuat FQuat::operator*(const FQuat& Q) const
{
	// 해밀턴 곱: (this * Q) — Q 먼저, this 나중
	return {
		W * Q.X + X * Q.W + Y * Q.Z - Z * Q.Y,
		W * Q.Y - X * Q.Z + Y * Q.W + Z * Q.X,
		W * Q.Z + X * Q.Y - Y * Q.X + Z * Q.W,
		W * Q.W - X * Q.X - Y * Q.Y - Z * Q.Z,
	};
}

FVector3 FQuat::RotateVector(const FVector3& V) const
{
	// v' = v + 2w(q × v) + 2 q × (q × v)
	const FVector3 QVec(X, Y, Z);
	const FVector3 T = FVector3::Cross(QVec, V) * 2.0f;
	return V + T * W + FVector3::Cross(QVec, T);
}

    A * B는 "B 먼저"

    쿼터니언 곱은 해밀턴 곱이고 회전은 v′ = q v q*이므로, (A·B) v (A·B)* = A (B v B*) A* — 즉 B를 먼저 적용하고 A를 나중에 적용합니다. 행렬의 행벡터 규약(왼쪽 먼저)과 반대 방향이라는 점이 함정입니다. ProjectE는 이 규약을 헤더 주석과 테스트 양쪽에 고정했습니다.

    E_TEST(Quat_Composition)
{
	const FQuat A = FQuat::FromAxisAngle(FVector3::UpVector, FMath::HalfPi);
	const FQuat B = FQuat::FromAxisAngle(FVector3::RightVector, FMath::HalfPi);
	const FVector3 V(1.0f, 2.0f, 3.0f);
	// (A * B): B 먼저, A 나중
	E_EXPECT_EQUALS((A * B).RotateVector(V), A.RotateVector(B.RotateVector(V)), Tol);
}
    FQuat FQuat::FromEuler(float PitchDegrees, float YawDegrees, float RollDegrees)
{
	// 왼손 Z-up 축계에서 UE 부호 규약을 맞추기 위해 Pitch/Roll은 음의 축 회전
	const FQuat Yaw   = FromAxisAngle(FVector3::UpVector, FMath::DegreesToRadians(YawDegrees));
	const FQuat Pitch = FromAxisAngle(FVector3::RightVector, -FMath::DegreesToRadians(PitchDegrees));
	const FQuat Roll  = FromAxisAngle(FVector3::ForwardVector, -FMath::DegreesToRadians(RollDegrees));
	// Roll → Pitch → Yaw 순으로 적용
	return Yaw * Pitch * Roll;
}

    Pitch와 Roll에 마이너스가 붙은 것을 보세요. 왼손 좌표계에서 오른쪽(+Y)축 둘레로 양의 각을 돌리면 기수가 아래로 내려갑니다. 언리얼의 "+Pitch = 기수 위로"와 맞추려고 축 회전의 부호를 뒤집은 것입니다. 이런 부호 하나하나가 테스트(Quat_EulerConvention: FromEuler(90, 0, 0)의 Forward는 Up)로 고정되어 있습니다.

    핵심 개념투영 행렬과 깊이 [0, 1]

    마지막 단계는 3D를 2D로 납작하게 만드는 투영(projection)입니다. 원근 투영에서는 멀리 있는 것이 작게 보여야 하므로 x, y를 거리 z로 나눠야 합니다. 그런데 행렬 곱은 나눗셈을 못 합니다. 여기서도 동차 좌표가 해결책입니다. 투영 행렬은 출력의 w에 z를 복사해 두고, GPU가 래스터화 직전에 (x/w, y/w, z/w)로 나눕니다(원근 나눗셈). 그 결과가 3강의 NDC입니다.

    FMatrix4x4 FMatrix4x4::MakePerspectiveFov(float FovYRadians, float AspectRatio, float NearZ, float FarZ)
{
	const float YScale = 1.0f / FMath::Tan(FovYRadians * 0.5f);
	const float XScale = YScale / AspectRatio;
	const float Range  = FarZ / (FarZ - NearZ);

	return FMatrix4x4(
		FVector4(XScale, 0.0f,   0.0f,           0.0f),
		FVector4(0.0f,   YScale, 0.0f,           0.0f),
		FVector4(0.0f,   0.0f,   Range,          1.0f),  // 세 번째 열의 1: w′ = z
		FVector4(0.0f,   0.0f,   -NearZ * Range, 0.0f));
}

    뷰 공간 점 (x, y, z, 1)을 곱하면 z′ = z·F/(F−N) − N·F/(F−N), w′ = z입니다. 나누면 깊이 d = F/(F−N) · (1 − N/z). z = N이면 0, z = F이면 1입니다 — DirectX 관례의 깊이 범위 [0, 1]입니다(OpenGL은 [−1, 1]). tan(FOV/2)로 나누는 XScale/YScale은 "시야각 가장자리에 있는 점이 NDC ±1에 오도록" 맞추는 값이고, 종횡비로 x만 다시 나눠 화면이 늘어나 보이지 않게 합니다.

    주목할 점은 d가 z에 대해 선형이 아니라는 것입니다. 1 − N/z 꼴이라 가까운 곳에서 급하게 오르고 멀리서는 1에 붙어 버립니다.

    직교 투영(MakeOrthographic)은 나눗셈이 없어(w′ = 1) 깊이가 거리에 선형입니다. 에디터 직교 뷰와 픽셀 아트 카메라(28강)가 이것을 씁니다.

    CLAUDE.md의 "좌표계 / 수학 규약" 절은 엔진의 헌법 같은 부분입니다. 정리하면 다음과 같습니다.

    항목규약지켜지는 곳
    축왼손 Z-up: +X 앞, +Y 오른쪽, +Z 위, Cross(Forward, Right) == UpFVector3 상수, Vector3_DotAndCross
    단위1 = 1cm, 질량 kg, 시간 초Core/Math/Units.h (FUnits)

    왜 이 조합일까요? 기록에 남은 이유는 "UE 방식"입니다. 언리얼 엔진과 같은 축·단위·회전 부호를 쓰면, 언리얼에 익숙한 사람의 직관(“Z가 위, 캐릭터 키 180”)과 언리얼식 자료·관례가 그대로 통합니다. Z-up은 지형 높이, 중력(−Z), 건물 층처럼 "위"가 특별한 게임 세계에 자연스럽고, cm 단위는 사람 크기 물체를 소수점 없이 다루기 편합니다. 하지만 더 중요한 점은 무엇을 고르든 하나로 정하고 첫날 정했다는 것입니다(0강). 좌표계를 중간에 바꾸면 수학, 셰이더, 임포터, 물리, 저장된 씬 전부가 바뀝니다.

    // 엔진 단위 규약: 1 단위 = 1 센티미터 (언리얼과 동일). 질량은 kg, 시간은 초.
// 외부 형식(glTF = 미터)이나 미터 기반 라이브러리(Jolt 물리)와의 경계에서만 변환한다.
struct FUnits
{
	static constexpr float MetersToUnits = 100.0f;
	static constexpr float UnitsToMeters = 1.0f / MetersToUnits;
	// 표준 중력 가속도 (cm/s², -Z 방향)
	static constexpr float StandardGravity = 980.665f;
};
    설계 원칙: 변환은 경계에서만, 한 번만 바깥 세계는 엔진과 규약이 다릅니다. glTF 모델은 오른손 Y-up에 미터 단위이고, Jolt 물리는 미터를 씁니다. ProjectE는 이런 데이터를 들어오는 경계 한 곳에서만 변환합니다. glTF는 FGltfLoader::Convert*만 쓰고 위치·이동만 ×100(ImportScale) — 방향 벡터는 스케일하지 않습니다(11강). 물리는 FPhysicsWorld 경계에서만 cm↔m(45강). 엔진 내부 코드는 "모든 것이 cm, 왼손 Z-up"이라고 믿고 짜면 됩니다. 변환이 여기저기 흩어지면 반드시 어딘가에서 두 번 하거나 빠뜨립니다.

    함정과 교훈

    실제로 겪은 일: 직교 카메라에서 클릭 선택이 늘 바닥을 잡다 2026-10-02, 에디터를 직교 카메라로 바꾸면 무엇을 클릭해도 항상 바닥(Ground)이 선택되었습니다. 클릭 선택은 화면 좌표를 뷰-투영 행렬의 역행렬로 되돌려 광선을 만드는데, 그 역행렬이 항등 행렬로 나오고 있었습니다. 원인은 TryGetInverse의 특이 판정이 절대값(|det| ≤ 1e-8)이었던 것입니다. 직교 뷰-투영의 행렬식은 4 / (폭 × 높이 × 깊이 범위) ≈ 1e-11로 아주 작지만, 멀쩡히 역행렬이 있는 행렬입니다. 판정을 "행렬 크기에 상대적"으로 바꿔 해결했고, 그 사례가 테스트(Matrix_InverseOfOrthographicViewProjection)와 CLAUDE.md 규칙("절대 문턱을 다시 넣지 말 것")으로 남았습니다. 
    // 특이 판정은 행렬 크기에 상대적으로 한다: |det| / (행 길이의 곱)은 행마다 배율을 바꿔도 같고 직교 행렬이면 1.
//   절대값(|det| <= 1e-8)으로 판정하면 직교 투영 뷰-투영(det ≈ 4 / (폭 × 높이 × 깊이 범위) ≈ 1e-11)처럼
//   멀쩡한 행렬을 특이로 보고 항등 행렬을 돌려준다 (에디터 직교 카메라 클릭 선택이 늘 원점 위로 쏘던 원인)
float RowLengthProduct = 1.0f;
for (int32 Row = 0; Row < 4; ++Row)
{
	RowLengthProduct *= FMath::Sqrt(M[Row][0] * M[Row][0] + M[Row][1] * M[Row][1] + M[Row][2] * M[Row][2] + M[Row][3] * M[Row][3]);
}
if (!(RowLengthProduct > 0.0f) || !(FMath::Abs(Det) > RowLengthProduct * 1.0e-6f))
{
	return false;
}

    교훈은 부동소수점의 "0에 가까움"은 크기에 상대적이라는 것입니다. cm 단위 엔진에서 1km 범위의 행렬은 숫자가 크거나 작게 나오기 쉽고, 절대 문턱은 단위나 장면 크기가 바뀌는 순간 틀립니다.

    • 곱셈 순서를 두 규약에서 헷갈리지 않기: 행렬은 왼쪽 먼저(S * R * T), 쿼터니언은 오른쪽 먼저(A * B = B 먼저). FMatrix4x4::MakeRotation(A * B)는 MakeRotation(B) * MakeRotation(A)와 같습니다. 그래서 둘 다 테스트로 고정했습니다(Matrix_RotationMatchesQuat).
    • 외부 라이브러리의 규약을 믿지 않고 검증: Jolt 물리와 쿼터니언을 주고받을 때 "엔진 FQuat도 해밀턴 곱 / q v q*"임을 PhysicsTests가 Jolt와 직접 비교해 확인합니다(CLAUDE.md). 수학 규약은 말로 맞추지 말고 테스트로 맞춥니다.
    정리
    • 내적 = 같은 방향의 정도(투영, 조명), 외적 = 두 벡터에 수직인 방향(법선). 외적의 방향은 좌표계 손잡이에 달렸다.
    • 동차 좌표로 이동까지 4×4 곱 하나로. 위치는 w = 1, 방향은 w = 0.
    • 행벡터 규약: 곱하는 순서 = 적용 순서. World = S·R·T, MVP = World·View·Proj. HLSL은 -Zpr + mul(v, M).
    • 쿼터니언 = 축-각을 담은 4개의 수. A * B는 B 먼저. FromEuler = Yaw·Pitch·Roll(적용은 Roll → Pitch → Yaw).
    • 원근 투영은 w에 z를 넣어 GPU가 나누게 한다. 깊이 d = F/(F−N)(1 − N/z) ∈ [0, 1]은 근평면에 몰린다.
    • 왼손 Z-up · 1단위 = 1cm(UE 방식)를 첫날 정하고, 외부 데이터는 경계에서 한 번만 변환한다.

    생각해 볼 문제

    Q1. 부모가 (100, 0, 0)에 있고 Yaw 90°로 돌아 있습니다. 자식의 로컬 위치가 (10, 0, 0)이면 월드 위치는? 자식 월드 = 자식 로컬 · 부모 월드이고, 부모 월드 = R(Yaw 90°) · T(100, 0, 0)입니다. (10, 0, 0)을 Yaw 90°로 돌리면 앞(+X)이 오른쪽(+Y)이 되어 (0, 10, 0), 여기에 이동을 더하면 (100, 10, 0)입니다. 부모가 바라보는 방향(+Y)으로 10cm 앞에 놓인 것이죠.
    Q2. NearZ를 10cm에서 1cm로 줄이면 100m 떨어진 물체의 깊이 정밀도는 어떻게 될까요? d = F/(F−N)(1 − N/z)에서 z에 대한 기울기는 대략 N/z²입니다. N이 10배 작아지면 같은 거리에서 깊이 값의 변화도 약 10배 작아져, 100m 근처의 서로 가까운 두 면이 같은 깊이 값으로 반올림될 가능성이 커집니다(Z-파이팅). 그래서 근평면은 가능한 한 크게 잡습니다.
    Q3. 셰이더를 -Zpr 없이 컴파일하고 CPU 행렬을 그대로 올리면 어떻게 될까요? 그래도 맞게 하려면? GPU는 각 행렬을 전치된 것으로 읽습니다. 이동 성분이 마지막 행이 아니라 마지막 열(w 계산)에 들어가 정점이 엉뚱하게 원근 나눗셈되고 화면이 깨집니다. 맞추려면 업로드 전에 모든 행렬을 전치하거나, 셰이더에서 mul(M, v)로 곱 순서를 바꿔야 합니다. ProjectE는 둘 다 하지 않아도 되도록 -Zpr로 메모리 배치를 일치시켰습니다.

    핵심 개념공간의 사슬과 카메라

    4강의 행렬들이 한 줄로 이어지면 정점이 화면까지 가는 길이 됩니다.

    뷰 행렬(view matrix)은 "카메라를 원점으로 옮기고 카메라가 바라보는 쪽을 +Z로 돌리는" 변환, 즉 카메라 월드 변환의 역행렬입니다. MakeLookAt은 시선 방향에서 직접 세 축을 만들어 이 행렬을 조립합니다.

    // 뷰 공간 축: Z = 앞, X = 오른쪽, Y = 위
const FVector3 ZAxis = (Target - Eye).GetNormalized();
FVector3 XAxis = FVector3::Cross(WorldUp, ZAxis).GetNormalized();
const FVector3 YAxis = FVector3::Cross(ZAxis, XAxis);

return FMatrix4x4(
	FVector4(XAxis.X, YAxis.X, ZAxis.X, 0.0f),
	FVector4(XAxis.Y, YAxis.Y, ZAxis.Y, 0.0f),
	FVector4(XAxis.Z, YAxis.Z, ZAxis.Z, 0.0f),
	FVector4(-FVector3::Dot(XAxis, Eye), -FVector3::Dot(YAxis, Eye), -FVector3::Dot(ZAxis, Eye), 1.0f));

    회전 부분은 세 축을 열로 세운 것입니다. 회전 행렬의 역행렬은 전치이므로, "축을 행으로 놓은 카메라 회전"의 역이 곧 이 모양입니다. 마지막 행은 카메라 위치를 각 축에 투영한 값의 음수 — 카메라를 원점으로 끌어오는 이동입니다. 외적 두 번으로 세 축을 서로 수직으로 만드는 요령, 시선이 위쪽과 평행하면 대체 축을 쓰는 예외 처리도 눈여겨보세요.

    FCamera는 위치 + 쿼터니언 회전 + 투영 설정(FOV, 종횡비, 근/원평면)을 들고 두 행렬을 만들어 줍니다. 렌더러는 GetViewProjectionMatrix()(= View · Proj)를 받아 상수 버퍼에 넣습니다.

    float FovYDegrees = 60.0f;

    핵심 개념깊이 버퍼

    큐브를 그리면 앞면과 뒷면이 화면의 같은 픽셀에 겹칩니다. 삼각형을 먼 것부터 그리는 방법(화가 알고리즘)은 삼각형끼리 서로 꿰뚫거나 순환으로 겹치면 실패합니다. 대신 GPU는 깊이 버퍼(depth buffer, Z-버퍼)를 씁니다. 화면과 같은 크기의 버퍼에 "지금까지 그린 것 중 가장 가까운 깊이"를 픽셀마다 저장해 두고, 새 픽셀은 그보다 가까울 때만 색을 쓰고 깊이를 갱신합니다. 그리는 순서와 상관없이 가장 가까운 면이 남습니다.

    // 스왑체인 크기에 맞춘 깊이 버퍼 (D32_FLOAT, 리소스는 R32_TYPELESS라 R32_FLOAT SRV 생성 가능)
static constexpr DXGI_FORMAT Format         = DXGI_FORMAT_D32_FLOAT;
static constexpr DXGI_FORMAT ResourceFormat = DXGI_FORMAT_R32_TYPELESS; // SRV로도 읽을 수 있도록
static constexpr DXGI_FORMAT SrvFormat      = DXGI_FORMAT_R32_FLOAT;
static constexpr float       ClearDepth     = 1.0f;

    매 프레임 BeginFrame이 깊이를 1.0(원평면)으로 지우고, PSO에서 bDepthEnable = true, 비교 함수 LESS(더 작으면 통과)를 씁니다. 4강의 그림 4-4처럼 깊이 값은 근평면에 몰려 있으므로, 32비트 부동소수점(D32_FLOAT)을 써서 정밀도를 확보합니다. 리소스를 TYPELESS로 만드는 것은 같은 메모리를 깊이 쓰기용(DSV)과 셰이더 읽기용(SRV)으로 함께 보기 위해서입니다 — 지금은 쓰지 않지만 나중에 화면 공간 기법(19강)과 픽셀 아트 외곽선(28강)이 깊이를 읽습니다. 창 크기가 바뀌면 깊이 버퍼도 스왑체인과 함께 다시 만듭니다(2강).

    핵심 개념텍스처 업로드와 풋프린트

    텍스처는 GPU가 읽기 좋게 배치된 이미지입니다. 셰이더는 0~1 범위의 UV 좌표로 위치를 지정해 색을 읽습니다(샘플링). 정점마다 UV를 주면 3강의 보간으로 픽셀마다 UV가 생기고, 픽셀 셰이더가 그 위치의 색을 읽습니다.

    이미지 파일(PNG 등)은 stb_image로 디코딩해 RGBA 바이트 배열로 만듭니다. 이걸 GPU 텍스처로 올리는 과정은 3강의 버퍼 업로드와 같은 두 단계지만, 함정이 하나 있습니다. GPU 텍스처의 내부 배치는 하드웨어마다 다르고(타일링), 복사 원본인 업로드 버퍼의 행 간격(row pitch)은 256바이트의 배수여야 합니다. 그래서 먼저 디바이스에게 "이 텍스처를 복사하려면 업로드 버퍼를 어떻게 배치해야 하나"를 물어봅니다. 그 답이 풋프린트(footprint)입니다.

    // 밉 0 업로드 레이아웃 (행 피치는 256바이트 정렬)

UINT   NumRows = 0;
UINT64 RowSizeInBytes = 0, TotalBytes = 0;

E_CHECKF(RowSizeInBytes == SourceRowPitch, "포맷과 BytesPerPixel이 일치하지 않습니다 ({} != {})", RowSizeInBytes, SourceRowPitch);
...

{

	            Source + static_cast<uint64>(Row) * SourceRowPitch, static_cast<size_t>(SourceRowPitch));

    복사가 끝나면 텍스처를 COPY_DEST 상태에서 PIXEL_SHADER_RESOURCE로 전이하고(2강의 배리어), 셰이더 가시 힙에 SRV를 하나 만들어 둡니다. 그릴 때는 그 SRV의 GPU 핸들을 루트 테이블로 넘깁니다(3강 그림 3-3).

    규칙: 색 텍스처는 sRGB, 데이터 텍스처는 UNORM PNG의 색 값은 사람 눈에 맞춘 감마 인코딩(sRGB) 값입니다. 조명 계산은 선형 공간에서 해야 맞으므로, 색 텍스처는 *_SRGB 포맷으로 만들어 샘플링하는 순간 하드웨어가 선형으로 풀게 합니다. 반대로 노멀 맵처럼 "숫자"를 담은 텍스처를 sRGB로 만들면 값이 휘어 버립니다.     핵심 개념밉맵과 샘플러

    멀리 있는 바닥을 생각해 봅시다. 화면의 픽셀 하나에 텍스처의 텍셀(텍스처 픽셀) 수십 개가 들어갑니다. 픽셀 셰이더는 그중 한 지점만 읽으므로, 카메라가 조금만 움직여도 읽는 텍셀이 바뀌어 화면이 자글자글 깜빡입니다(앨리어싱). 해법은 미리 줄인 그림들 — 밉맵(mipmap) — 을 만들어 두는 것입니다. 원본(밉 0)의 가로세로를 절반씩 줄인 사본을 1×1까지 만들고, GPU가 화면에서 텍셀이 촘촘한 정도(UV의 화면 미분)를 보고 알맞은 밉을 골라 읽습니다.

    constexpr uint32 CalculateMipCount(uint32 Width, uint32 Height)
{
	uint32 Size  = Width > Height ? Width : Height;
	uint32 Count = 1;
	while (Size > 1)
	{
		Size >>= 1;
		++Count;
	}
	return Count;
}

    GPU에서 밉 만들기

    밉은 CPU에서 만들 수도 있지만, ProjectE는 컴퓨트 셰이더로 GPU에서 만듭니다(FD3D12MipGenerator, Phase 3 후속 "렌더링 트랙 B"). 밉 N−1을 SRV로 읽어 밉 N을 UAV로 씁니다. 목적지 텍셀 중심에서 선형 샘플러로 한 번 읽으면 짝수 크기에서는 정확히 2×2 평균이 되는 요령을 씁니다.

    // 색공간: sRGB 포맷은 UAV를 만들 수 없으므로 리소스를 TYPELESS로 두고 SRV는 *_SRGB(읽을 때 하드웨어가 선형 변환),
//       UAV는 *_UNORM으로 만든다. 평균은 선형 공간에서 계산되고, 쓰기 직전에 다시 sRGB로 인코딩한다(bSRGB).
[numthreads(8, 8, 1)]
void CSMain(uint3 ThreadId : SV_DispatchThreadID)
{
	if (ThreadId.x >= DstSize.x || ThreadId.y >= DstSize.y) { return; }
	const float2 UV    = (float2(ThreadId.xy) + 0.5f) * DstTexelSize;
	float4       Color = SrcMip.SampleLevel(LinearClampSampler, UV, 0.0f);
	if (bSRGB != 0) { Color.rgb = LinearToSrgb(Color.rgb); }
	DstMip[ThreadId.xy] = Color;
}

    주석에 담긴 색공간 처리가 중요합니다. sRGB 값을 그대로 평균하면 어두운 쪽으로 치우친 밉이 나옵니다(감마 곡선이 휘어 있으므로). 그래서 sRGB 뷰로 읽어 선형으로 평균한 뒤 다시 인코딩합니다. 그런데 sRGB 포맷으로는 UAV(쓰기 뷰)를 만들 수 없으므로, 리소스를 TYPELESS로 만들고 읽기용 sRGB SRV와 쓰기용 UNORM UAV를 따로 만드는 우회로를 씁니다 — 2강 스왑체인의 "UNORM 리소스 + sRGB 뷰"와 같은 발상입니다.

    샘플러와 이방성 필터링

    샘플러(sampler)는 "UV 위치의 색을 어떻게 읽을지"를 정합니다: 필터(가까운 텍셀 하나/주변 보간/밉 간 보간), UV가 0~1 밖일 때 반복할지 자를지(주소 모드). 바닥처럼 화면에 비스듬히 누운 면은 한 픽셀이 텍스처에서 길쭉한 영역을 덮는데, 정사각형 기준으로 밉을 고르면 지나치게 흐려집니다. 이방성(anisotropic) 필터는 그 길쭉한 방향으로 여러 번 읽어 선명함을 유지합니다. 트랙 B에서 씬 렌더러의 샘플러를 16배 이방성으로 바꿨고, 3강의 정적 샘플러로 루트 시그니처에 박아 둡니다.

    핵심 개념프레임 링 동적 업로드 버퍼

    큐브가 자전하면 월드 행렬이 매 프레임 바뀌고, 카메라가 움직이면 뷰-투영 행렬도 바뀝니다. 이런 상수를 GPU에 넘길 때마다 버퍼를 새로 만들면 너무 느립니다. 그렇다고 버퍼 하나를 매 프레임 덮어쓰면, 2강에서 본 것처럼 GPU가 아직 이전 프레임을 그리면서 그 버퍼를 읽고 있을 수 있습니다.

    해법은 2강의 칸 구조를 그대로 쓰는 것입니다. 칸마다 CPU에서 쓸 수 있는 큰 업로드 버퍼(기본 4MB)를 하나씩 만들어 항상 매핑해 둡니다. 프레임 동안에는 앞에서부터 차례로 잘라 쓰고(선형 할당 — 포인터 하나를 밀기만 하므로 매우 빠름), 다음에 같은 칸이 돌아오면 — 즉 그 칸의 펜스를 통과한 뒤 — 포인터를 0으로 되돌립니다. 개별 해제가 없고 칸 전체를 한 번에 버리는 방식입니다.

    핵심 개념Blinn-Phong 조명

    표면이 빛을 받아 보이는 밝기는 두 부분으로 나눠 근사할 수 있습니다. 확산(diffuse)은 빛이 표면 속에서 흩어져 사방으로 고르게 나오는 몫으로, 보는 방향과 무관하고 빛이 표면에 얼마나 정면으로 닿는지(N·L)에만 비례합니다(램버트 법칙). 정반사(specular)는 매끄러운 표면이 거울처럼 반사하는 하이라이트로, 보는 방향에 따라 달라집니다.

    원래의 Phong 모델은 빛의 반사 방향 R과 V의 내적을 썼는데, Blinn이 제안한 변형은 L과 V의 중간 방향 H를 구해 N·H를 씁니다. 계산이 싸고, 시선이 표면에 비스듬할 때도 하이라이트가 자연스럽습니다. Phase 2의 메시 셰이더는 이 식을 그대로 옮겼습니다.

    // Blinn-Phong: 확산(Lambert) + 하프 벡터 스페큘러
float3 ShadeBlinnPhong(float3 N, float3 V, float3 L, float3 LightRadiance, float3 Albedo)
{
	const float NdotL = saturate(dot(N, L));
	if (NdotL <= 0.0f) { return 0.0f; }

	const float3 H     = normalize(L + V);
	const float  NdotH = saturate(dot(N, H));

	const float3 Diffuse  = Albedo * NdotL;
	const float3 Specular = SpecularColor * SpecularStrength * pow(NdotH, Shininess) * NdotL;
	return (Diffuse + Specular) * LightRadiance;
}

float4 PSMain(FPixelInput Input) : SV_Target
{
	const float4 BaseColor = BaseColorTexture.Sample(LinearSampler, Input.UV) * Input.Color * BaseColorTint;
	const float3 N = normalize(Input.WorldNormal);              // 보간되면 길이가 1이 아니므로 다시 정규화
	const float3 V = normalize(CameraPosition - Input.WorldPosition);
	const float3 L = -DirectionalLight.Direction;              // 표면 → 광원
	const float3 Radiance = DirectionalLight.Color * DirectionalLight.Intensity;
	const float3 Lit      = ShadeBlinnPhong(N, V, L, Radiance, BaseColor.rgb) + AmbientColor * BaseColor.rgb;
	return float4(Lit, BaseColor.a);
}

    방향광(태양)은 위치가 없고 방향만 있으므로 L이 모든 점에서 같습니다. AmbientColor는 그림자 진 면이 완전히 까맣지 않게 더하는 아주 거친 근사입니다. 이 근사들은 3부에서 하나씩 제대로 된 것으로 바뀝니다: 물리 기반 BRDF(14강), 환경에서 오는 빛(17강), 전역 조명(26강). 하지만 "확산 + 정반사, N·L, 하프 벡터"라는 뼈대는 그대로 남습니다.

    핵심 개념법선은 역전치 행렬로 변환한다

    조명에는 월드 공간의 법선이 필요합니다. 위치처럼 월드 행렬로 곱하면 될 것 같지만, 크기 변환이 축마다 다르면(비균등 스케일) 틀립니다. 구를 옆으로 두 배 늘린 타원을 생각해 보세요. 표면은 납작해졌는데, 법선을 같은 행렬로 늘리면 법선도 옆으로 누워 더 이상 표면에 수직이 아닙니다.

    왜 역전치인가 (짧은 증명) 표면의 접선 t와 법선 n은 수직이므로 n·t = 0입니다. 행벡터 규약에서 접선은 t′ = t·M으로 바뀝니다. 변환된 법선을 n′ = n·G라고 하면 n′·t′ = (n·G)·(t·M) = n·G·Mᵀ·tᵀ … 가 0이 되려면 G·Mᵀ = I, 즉 G = (Mᵀ)⁻¹ = (M⁻¹)ᵀ입니다. 회전만 있는 행렬은 역행렬 = 전치이므로 G = M이 되어 그냥 곱해도 되고, 균등 스케일은 길이만 바뀌어 정규화로 해결됩니다. 문제는 비균등 스케일뿐입니다.

    Phase 2 셰이더는 이 행렬을 CPU에서 오브젝트마다 계산해 상수로 넘겼습니다(위 Render 코드의 Command.World.GetInverse().GetTransposed()). 셰이더는 이동이 필요 없으므로 상단 3×3만 잘라 씁니다.

    실제로 겪은 일: 4MB 업로드 버퍼가 모자라기 시작하다 프레임 칸마다 4MB면 상수 몇 개에는 차고 넘쳤습니다. 하지만 스킨 캐릭터 수백 개를 띄우는 스트레스 장면(Tests/Stress)에서는 뼈 행렬 팔레트만으로 약 3.7MB를 쓰게 되었습니다(CLAUDE.md, Phase 26 측정). 버퍼가 고정 크기였다면 넘치는 순간 멈췄을 것입니다. Phase 29에서 "차면 같은 프레임에 페이지를 덧붙이고(경고 로그), 그 칸이 다음에 돌아올 때 사용량 × 1.25 크기 한 페이지로 합친다(상한 256MB)"로 바꿨습니다. 이미 나간 GPU 주소는 그대로 유효해야 하므로 기존 페이지를 키우지 않고 새 페이지를 붙이는 방식이고, 합치는 일은 그 칸의 GPU 작업이 끝났다고 보장되는 Reset에서만 합니다. CLAUDE.md에는 "프레임당 업로드를 늘리는 기능은 용량을 확인한다"는 규칙이 함께 적혀 있습니다.
    실제로 겪은 일: Phase 2에는 밉맵이 없었다 Phase 2를 마칠 때 Plans.md의 "후속 과제"에는 "텍스처 밉맵 생성, sRGB 처리(백버퍼/텍스처 포맷), 디스크립터/리소스 지연 해제, 비동기 업로드 컨텍스트"가 적혀 있었습니다. 눈앞에서 도는 체커 큐브 하나는 밉 없이도 그럴듯해 보이지만, 멀리 깔린 바닥처럼 텍셀이 픽셀보다 촘촘한 면에서는 앨리어싱을 피할 수 없습니다. 밉맵은 Phase 3 직후 "렌더링 트랙 B"로 들어왔습니다. 완료 기준을 작게 잡고 빠진 것을 "후속 과제"로 명시해 두는 방식 덕분에, 다음 단계에서 무엇을 먼저 할지 분명했습니다. 이 목록 중 지연 해제는 다음 6강의 주제입니다.
    • 보간된 법선은 다시 정규화: 단위 벡터 셋을 보간하면 길이가 1보다 짧아집니다. 픽셀 셰이더 첫 줄의 normalize(Input.WorldNormal)을 빼면 삼각형 가운데가 어둡게 보입니다.
    • 상수 버퍼 구조체는 C++과 HLSL을 함께 고친다: 필드 하나를 추가하며 패딩을 빠뜨리면 그 뒤의 모든 값이 4바이트씩 밀려 엉뚱한 값을 읽습니다. 컴파일 오류도 경고도 없이 화면만 이상해지므로, static_assert로 크기를 고정하는 것이 유일한 방어선입니다(CLAUDE.md 코드 규칙).
    정리
    • 로컬 → 월드 → 뷰 → 클립(정점 셰이더) → NDC(÷w) → 화면(뷰포트). 뷰 행렬은 카메라 월드 변환의 역.
    • 플라이 카메라는 Yaw/Pitch를 따로 들고 매번 쿼터니언을 만든다. 이동 = 정규화한 방향 × 속도 × dt.
    • 깊이 버퍼: 픽셀마다 가장 가까운 깊이를 저장, 1.0으로 지우고 LESS로 비교, D32_FLOAT(TYPELESS 리소스).
    • 텍스처 업로드는 풋프린트(행 간격 256B 정렬)를 받아 행 단위로 복사. 색은 sRGB, 데이터는 UNORM.
    • 밉맵은 앨리어싱을 막는다. 컴퓨트로 선형 공간 평균. 이방성 16× 정적 샘플러.
    • 프레임 칸마다 상시 매핑 업로드 버퍼에 선형 할당, 상수는 256B 정렬. Blinn-Phong = 램버트 확산 + (N·H)광택 정반사. 법선은 (M⁻¹)ᵀ로 변환.

    생각해 볼 문제

    Q1. 깊이 테스트를 켜 두었는데 반투명 유리 뒤의 물체가 사라집니다. 왜일까요? 유리를 먼저 그리면 유리의 깊이가 깊이 버퍼에 기록되고, 그 뒤에 그리는 물체는 "더 멀다"는 이유로 깊이 테스트에서 떨어집니다. 반투명은 섞여야 하므로 깊이 테스트로 해결할 수 없습니다. 보통 불투명을 먼저 다 그린 뒤, 반투명은 깊이 쓰기를 끄고 먼 것부터 그립니다. ProjectE도 반투명은 사전 패스·그림자에 넣지 않고 먼 것부터 깊이 쓰기 없이 그립니다(21강).
    Q2. 오브젝트 1000개를 그리면 PerObject 상수(행렬 2개 = 128바이트)에 업로드 버퍼를 얼마나 쓸까요? 상수 하나가 256바이트 경계로 정렬되므로 128바이트짜리도 256바이트를 차지합니다. 1000 × 256 = 256,000바이트, 약 250KB입니다. 실제 데이터의 두 배이므로, 물체가 아주 많아지면 상수를 오브젝트마다 따로 두지 않고 큰 구조화 버퍼 하나에 모아 인스턴스 번호로 읽는 방식(인스턴싱, 29강)으로 바뀝니다.
    Q3. 균등 스케일(모든 축 2배)만 있는 물체라면 역전치 대신 월드 행렬로 법선을 곱해도 될까요? 됩니다. 균등 스케일 s는 법선 방향을 바꾸지 않고 길이만 s배 하므로, 곱한 뒤 정규화하면 같은 결과입니다. 회전은 역행렬이 전치라 (M⁻¹)ᵀ = M입니다. 문제는 비균등 스케일뿐이지만, 어떤 물체가 비균등 스케일을 가질지 셰이더는 모르므로 일반적으로 역전치를 씁니다.

    • GPU가 아직 쓰고 있는 리소스를 CPU가 지우면 무슨 일이 생기는지, 왜 C++의 일반적인 수명 관리로는 막을 수 없는지 설명할 수 있습니다.
    • 지연 해제(deferred release)가 2강의 프레임 칸·펜스 위에서 어떻게 동작하는지 압니다.
    • 세대(generation) 핸들이 댕글링 포인터 문제를 어떻게 막는지 압니다.
    • FResourceManager가 리소스를 소유하고, 나머지 코드는 핸들만 들게 한 설계와 기본 텍스처의 역할을 이해합니다.

    왜 필요한가"지웠는데 아직 쓰고 있다"

    C++에서 객체의 수명은 보통 분명합니다. std::unique_ptr가 범위를 벗어나면 지워지고, 그 뒤로는 아무도 그 객체를 쓰지 않는다고 가정합니다. 그런데 GPU 리소스에는 이 가정이 성립하지 않습니다. 2강에서 보았듯이 CPU가 프레임 N을 기록하고 있을 때 GPU는 아직 프레임 N−1, N−2를 실행 중일 수 있습니다. CPU 쪽 코드에서는 텍스처를 "다 썼다"고 판단해 지웠더라도, 이미 제출된 명령 목록 안에는 그 텍스처를 읽으라는 명령이 남아 있습니다.

    이렇게 되면 GPU는 해제된 메모리를 읽습니다. 운이 좋으면 이상한 색이 잠깐 보이고, 운이 나쁘면 드라이버가 디바이스를 제거(device removed)해 게임이 꺼집니다. 디스크립터도 마찬가지입니다. 2강의 할당자는 반환된 칸을 곧바로 다음 요청에 내주므로, GPU가 아직 읽을 칸에 다른 텍스처의 디스크립터가 덮어써질 수 있습니다. 게다가 이런 버그는 타이밍에 따라 가끔만 나타나 재현이 어렵습니다.

    에디터가 생기면 이 문제는 일상이 됩니다. 머티리얼을 고치면 텍스처가 바뀌고, 모델을 다시 가져오면 메시가 교체되고, 씬을 닫으면 리소스가 지워집니다. 모두 "렌더링 도중"에 일어납니다. Phase 3는 이것을 위해 두 가지 장치를 만들었습니다: 지연 해제와 세대 핸들.

    핵심 개념지연 해제: GPU가 끝낸 뒤에 지운다

    해법의 아이디어는 단순합니다. 리소스를 지우라는 요청이 오면 바로 지우지 않고 목록에 넣어 두었다가, 그 리소스를 쓸 수 있었던 마지막 프레임이 GPU에서 끝난 것이 확인된 뒤에 실제로 놓습니다. "끝난 것의 확인"은 이미 2강에서 만들었습니다 — 프레임 칸마다 기록해 둔 펜스 값입니다.

    ProjectE의 RHI에서 이 일을 하는 코드는 세 군데에 나뉘어 있습니다: 요청을 받는 곳, 요청을 프레임 칸에 묶는 곳, 실제로 놓는 곳.

    // ① 요청: 지금 기록 중인 프레임의 목록에 담아 둔다

	if (Object)

    ComPtr를 목록에 옮겨 담는 것만으로 수명이 연장된다는 점이 깔끔합니다. 목록이 참조를 하나 들고 있는 동안 COM 객체는 살아 있고, Objects.clear()가 마지막 참조를 놓는 순간 실제로 해제됩니다. 디스크립터도 같은 시점에 할당자에 반환되므로, 2강의 "Free는 즉시 재사용 가능"이라는 주의 사항이 여기서 해결됩니다.

    리소스 클래스들은 이 장치를 쓰는 ShutdownDeferred를 하나씩 가지고 있습니다. 텍스처는 리소스와 SRV 디스크립터를 함께 넘깁니다.

    void FD3D12Texture::ShutdownDeferred(FD3D12RHI& Rhi)
{
	Rhi.DeferRelease(Resource);
	Rhi.DeferFreeDescriptor(Srv);
	Srv          = FD3D12DescriptorHandle{};
	SrvAllocator = nullptr;
	Resource.Reset();
	...

    즉시 해제와 지연 해제의 구분 모든 해제를 지연시킬 필요는 없습니다. 프로그램 종료처럼 GPU를 Flush로 완전히 비운 뒤라면 즉시 해제(Shutdown())가 안전하고 단순합니다. CLAUDE.md의 규칙이 바로 이 구분입니다: "렌더링 중 삭제는 Destroy*(지연 해제)로, 즉시 Shutdown()은 GPU Flush 이후에만." FResourceManager::Shutdown도 업로드 큐와 그래픽스 큐를 먼저 비우고(WaitIdle, Flush) 그다음에 모든 리소스를 즉시 놓습니다.

    핵심 개념세대 핸들: 오래된 참조를 알아보는 법

    지연 해제로 GPU 쪽은 안전해졌습니다. 그런데 CPU 쪽에도 같은 문제가 있습니다. 씬의 메시 컴포넌트, 머티리얼, 에디터 패널이 텍스처를 가리키고 있는데 그 텍스처가 지워지면, 그 포인터들은 모두 댕글링 포인터가 됩니다. 수많은 곳에 흩어진 포인터를 일일이 찾아 지울 수는 없습니다.

    ProjectE는 리소스를 포인터 대신 핸들(handle)로 가리킵니다. 핸들은 두 정수 — 풀 안의 칸 번호(Index)와 세대(Generation) — 입니다. 풀은 칸마다 현재 세대를 기억하고, 리소스를 지울 때 그 칸의 세대를 하나 올립니다. 나중에 옛 핸들로 접근하면 핸들의 세대와 칸의 세대가 달라 "이미 지워진 리소스"임을 알 수 있습니다. 칸이 새 리소스로 재사용되어도 세대가 다르므로 엉뚱한 리소스를 잡지 않습니다.

    // 세대 검증이 있는 리소스 핸들. Tag로 타입을 구분해 서로 다른 리소스 핸들이 섞이지 않게 한다.
//   struct FMeshHandleTag {}; using FMeshHandle = THandle<FMeshHandleTag>;
template <typename TTag>
struct THandle
{
	static constexpr uint32 InvalidIndex = ~0u;
	uint32 Index      = InvalidIndex;
	uint32 Generation = 0;

	constexpr bool   IsValid() const { return Index != InvalidIndex; }
	constexpr uint64 ToId() const { return (static_cast<uint64>(Generation) << 32) | Index; }
};
    // 세대 검증 핸들로 접근하는 리소스 풀. 슬롯을 재사용하되 오래된 핸들은 무효 처리된다.
template <typename TResource, typename THandleType>
class TResourcePool
{
public:
	bool IsValid(THandleType Handle) const
	{
		return Handle.IsValid() && Handle.Index < Slots.size() && Slots[Handle.Index].Generation == Handle.Generation &&
		       Slots[Handle.Index].Resource != nullptr;
	}
	TResource* Get(THandleType Handle) const { return IsValid(Handle) ? Slots[Handle.Index].Resource.get() : nullptr; }

	// 슬롯을 비우고 세대를 올린다. 소유권을 호출자에게 넘긴다 (지연 해제 등).
	std::unique_ptr<TResource> Remove(THandleType Handle)
	{
		if (!IsValid(Handle)) { return nullptr; }
		std::unique_ptr<TResource> Resource = std::move(Slots[Handle.Index].Resource);
		++Slots[Handle.Index].Generation;
		FreeIndices.push_back(Handle.Index);
		return Resource;
	}
	...
private:
	struct FSlot
	{
		std::unique_ptr<TResource> Resource;
		uint32                     Generation = 0;
	};
	std::vector<FSlot>  Slots;
	std::vector<uint32> FreeIndices;
};

    세 가지 설계 포인트가 있습니다.

    • 태그 타입: THandle<FMeshHandleTag>와 THandle<FTextureHandleTag>는 내용은 같아도 서로 다른 타입이라, 메시 핸들을 텍스처 함수에 넘기면 컴파일 오류가 납니다. 정수 두 개짜리 구조체에 타입 안전성을 공짜로 얹는 요령입니다.
    • Remove는 소유권을 돌려준다: 풀에서 꺼낸 unique_ptr을 받은 쪽이 ShutdownDeferred를 부르고 버립니다. 풀은 "칸 관리"만, GPU 수명은 지연 해제가 맡는 역할 분담입니다.
    • 핸들은 값이다: 복사·비교·해시가 공짜이고(ToId로 64비트 키), 파일에 쓸 수 없는 포인터와 달리 정렬 키나 캐시 키로 쓰기 좋습니다. 3강의 렌더러가 머티리얼 상수 캐시와 그리기 정렬에 MaterialHandle.ToId()와 Index를 쓴 것이 그 예입니다.
    같은 생각이 ECS에도 씬의 엔티티 FEntity도 "번호 + 세대"로 된 세대 핸들입니다. 지워진 엔티티를 가리키는 옛 핸들이 같은 번호의 새 엔티티를 잡지 않게 하는 원리가 똑같습니다(7강). 세대 핸들은 게임 엔진에서 가장 자주 보는 패턴 중 하나입니다.

    ProjectE에서는FResourceManager — 렌더 리소스의 유일한 소유자

    Phase 3에서 메시·텍스처·머티리얼은 모두 FResourceManager가 소유하게 되었습니다. 씬 컴포넌트, 머티리얼, 에디터는 핸들만 들고, 실제 객체가 필요할 때 관리자에게 묻습니다. 핸들 타입은 Scene 모듈의 작은 헤더에 정의되어 있어서, 씬은 렌더러(Renderer 모듈)를 몰라도 "이 엔티티는 저 메시를 쓴다"를 표현할 수 있습니다 — 0강의 단방향 의존 원칙이 여기서도 지켜집니다.

    DestroyTexture는 세 가지를 한 번에 정리합니다: 풀에서 꺼내 세대를 올리고(CPU 참조 무효화), GPU 메모리는 지연 해제로 넘기고, 이 텍스처를 디스크립터 표에 넣어 두었던 머티리얼은 표를 다시 만듭니다. 마지막 것이 중요합니다. 머티리얼 표는 텍스처 SRV를 복사해 둔 디스크립터 칸들이라, 원래 텍스처가 사라지면 그 칸도 고쳐야 합니다. 이 복사 관계는 나중에 더 중요해지는데, 아래 함정 절에서 다시 봅니다.

    또 같은 파일 경로를 두 번 불러도 텍스처를 두 번 만들지 않도록 경로 캐시(경로 → 핸들)를 둡니다. 모델 열 개가 같은 텍스처를 쓰면 GPU 메모리에는 하나만 있습니다.

    ProjectE에서는기본 텍스처 — "없음"을 위한 진짜 리소스

    ResolveTexture의 마지막 줄을 보세요. 핸들이 무효이거나 아직 준비되지 않았으면 1×1 흰색 텍스처를 돌려줍니다. 관리자는 초기화하자마자 이런 기본 리소스를 만듭니다.

    // 기본 리소스: 1x1 흰색/평면 노멀 텍스처, 기본 머티리얼
WhiteTexture      = CreateTexture(FImage::MakeSolidColor(1, 1, 255, 255, 255), true, L"DefaultWhite");
FlatNormalTexture = CreateTexture(FImage::MakeSolidColor(1, 1, 128, 128, 255), false, L"DefaultFlatNormal");

    왜 "없으면 nullptr"이 아니라 진짜 텍스처를 줄까요?

    • 셰이더에 분기가 필요 없다: 베이스 컬러 텍스처가 없는 머티리얼도 "흰색 텍스처 × 색상 값"으로 똑같이 계산하면 색상 값만 남습니다. 노멀 맵이 없으면 (0.5, 0.5, 1) — 디코딩하면 정확히 표면 법선 그대로 — 인 평면 노멀 텍스처를 쓰면 됩니다. 셰이더와 루트 시그니처는 언제나 같은 모양입니다. 그래서 평면 노멀은 sRGB가 아니라 선형(false)으로 만듭니다(5강의 색/데이터 구분).
    • 호출하는 쪽에 null 검사가 필요 없다: ResolveTexture는 언제나 유효한 참조를 돌려주므로 렌더 코드 곳곳에 "없으면?"을 쓸 필요가 없습니다. 실수로 지워진 핸들을 써도 크래시 대신 "하얗게 보이는" 눈에 띄는 증상이 됩니다.
    • 비동기 로딩의 자리표시: Phase 37에서 텍스처를 백그라운드에서 읽게 되자, 준비되기 전에도 그릴 수 있어야 했습니다. 이미 "준비 안 됨 → 기본 텍스처"(IsReady() 검사) 경로가 있었기 때문에 자연스럽게 확장되었습니다.

    기본 텍스처는 지울 수 없게 막혀 있습니다(DestroyTexture 첫 줄). 모두가 기대는 바닥이 사라지면 안 되니까요.

    함정과 교훈

    실제로 겪은 일: "현재 칸"이 현재가 아닐 때 처음의 DeferRelease는 요청을 PendingReleases[CurrentBackBufferIndex], 즉 "현재 칸" 목록에 바로 넣었습니다. 그런데 에디터가 생기자 해제 요청이 BeginFrame 전, ImGui UI를 만드는 단계에서도 오기 시작했습니다. 그 시점의 CurrentBackBufferIndex는 아직 지난 프레임의 칸입니다. 그러면 요청이 지난 프레임 칸에 들어가 그 칸이 다시 돌아올 때 — 이번에 기록할 프레임이 GPU에서 끝났는지는 확인하지 않은 채 — 해제됩니다. 에셋 편집 창·다시 가져오기를 들여온 Phase 9~12 작업에서 이를 고쳐, 요청은 칸과 무관한 RecordingReleases에 모았다가 EndFrame에서 "방금 제출한 프레임"의 칸으로 옮기도록 했습니다(위 코드 ②). 헤더 주석도 "요청한 뒤 처음 제출되는 프레임(EndFrame)을 GPU가 끝낸 뒤 실제로 해제한다. BeginFrame 전(UI 단계)에 요청해도 그 프레임이 아직 쓰는 리소스를 먼저 지우지 않는다"로 바뀌었습니다. 교훈: "지금 몇 번째 칸인가" 같은 암묵적 상태에 기대지 말고, 해제 시점을 제출이라는 확실한 사건에 묶어라.
    규칙: 디스크립터는 프레임을 넘겨 캐시하지 않는다 핸들은 세대로 보호되지만, 핸들에서 꺼낸 SRV 디스크립터 주소는 보호되지 않습니다. 텍스처 밉 스트리밍(Phase 53)은 같은 핸들 뒤의 텍스처 내용을 새 밉 범위로 교체(SwapContents)하고 이전 내용은 지연 해제합니다. 어떤 코드가 지난 프레임에 얻은 SRV 주소를 들고 있으면 그것은 곧 해제될 칸을 가리킵니다. 그래서 CLAUDE.md는 "텍스처 SRV/디스크립터를 프레임을 넘겨 캐시하지 않는다"를 규칙으로 두고, 매 프레임 핸들에서 다시 얻게 합니다(30강).
    • 종료 시 누수 확인: 디스크립터 할당자는 종료할 때 반환되지 않은 칸이 있으면 "디스크립터 N개가 반환되지 않은 채 할당자가 종료됩니다" 경고를 남기고, 디바이스는 2강의 ReportLiveObjects로 살아남은 D3D 객체를 보고합니다. 수명 관리가 맞는지는 "종료가 깨끗한가"로 확인합니다.
    • "언제 지울지"는 다음 문제: 이 강의는 "지우라고 했을 때 안전하게 지우는 법"까지입니다. 맵을 바꾸면 이전 맵에서만 쓰던 텍스처를 누가 언제 지우라고 할지는 Phase 37의 리소스 수거(도달성 표시 → Destroy*)가 다룹니다(30강). 그 수거기도 결국 이 강의의 Destroy*와 지연 해제 위에 서 있습니다.
    정리
    • GPU는 CPU보다 몇 프레임 늦게 실행하므로, CPU가 "다 썼다"고 지운 리소스를 GPU가 아직 읽을 수 있다.
    • 지연 해제: 요청은 기록 중 목록에 → EndFrame에서 제출한 프레임의 칸 목록으로 → 같은 칸의 BeginFrame에서 펜스 통과 후 해제. 리소스와 디스크립터 모두.
    • 세대 핸들 = 칸 번호 + 세대. 지울 때 칸 세대를 올려 옛 핸들을 무효화한다. 태그 타입으로 종류가 섞이지 않는다.
    • FResourceManager가 메시·텍스처·머티리얼을 소유하고, 나머지는 핸들만 든다. Destroy*는 지연, Shutdown은 Flush 뒤에만.
    • 무효·미준비 핸들은 흰색/평면 노멀 기본 텍스처로 해석된다 — 셰이더 분기 없음, null 검사 없음, 비동기 로딩 자리표시.

    생각해 볼 문제

    Q1. 세대 값은 uint32입니다. 한 칸에서 생성·삭제가 232번 반복되면 어떻게 될까요? 현실적인 문제일까요? 세대가 한 바퀴 돌아 0으로 돌아오면, 아주 오래된 핸들이 우연히 같은 세대가 되어 새 리소스를 잘못 잡을 수 있습니다. 하지만 한 칸을 초당 1000번씩 지웠다 만들어도 약 50일이 걸리고, 그동안 그 옛 핸들을 계속 들고 있어야 문제가 됩니다. 게임 리소스에서는 사실상 일어나지 않으므로 32비트로 충분합니다. 엔티티처럼 생성·삭제가 훨씬 잦은 곳에서는 비트 배분을 다시 따져 봐야 합니다.
    Q2. 지연 해제 목록에 들어간 텍스처가 해제되기 전(최대 3프레임) 같은 경로로 다시 불러오면 메모리가 잠깐 두 배가 됩니다. 문제가 될까요? 잠깐 동안은 옛 리소스와 새 리소스가 함께 존재합니다. 텍스처 하나라면 무시할 수 있지만, 맵 전환처럼 수백 MB를 한꺼번에 바꾸면 VRAM 정점이 커질 수 있습니다. 그래서 대규모 교체는 "지우기 → 몇 프레임 뒤 해제가 끝난 것을 확인 → 새로 읽기" 순서를 쓰거나, 예산을 보고 나눠서 합니다. ProjectE의 리소스 수거가 요청 후 2틱 지연을 두고 VRAM 통계를 따로 보는 것도 이런 이유입니다(30강).
    Q3. 셰이더가 쓰는 텍스처가 없을 때 "흰색 텍스처"가 아니라 "검은색 텍스처"를 기본으로 쓰면 무엇이 달라질까요? 베이스 컬러는 "텍스처 × 색상 값"이라 흰색(1)이어야 색상 값이 그대로 남습니다. 검은색이면 텍스처 없는 모든 물체가 검게 보입니다. 반대로 발광(emissive)처럼 "없으면 0이어야 하는" 슬롯은 흰색이면 모든 물체가 빛나 버립니다. 그래서 기본 텍스처는 슬롯의 의미에 맞춰 고르며, ProjectE는 노멀 슬롯만 평면 노멀, 나머지는 흰색을 쓰고, 발광은 "텍스처 × EmissiveFactor"에서 계수의 기본값을 0으로 두어 끕니다(MaterialDefault.hlsli, ShaderTypes.h).
