    움직임 — 애니메이션

    뼈 몇십 개의 회전만으로 수만 개 정점의 메시를 살아 움직이게 하는 스키닝에서 출발해, 상태 머신과 블렌드 스페이스로 동작을 섞고, 노티파이·소켓·IK로 세계와 맞물리게 하고, 다른 체형의 동작을 옮기는 리타기팅과 루트 모션, 마지막으로 컷신을 만드는 시퀀서까지 다룹니다.

    이 강의를 마치면
    • 뼈 계층에서 각 뼈의 월드 행렬이 "로컬 × 부모 월드"로 이어진다는 것을 설명할 수 있습니다.
    • 바인드 포즈와 역바인드 행렬이 왜 필요한지, 본 팔레트 InverseBind × JointWorld가 정점에 무슨 일을 하는지 압니다.
    • 키프레임 보간에서 이동·스케일은 lerp, 회전은 slerp/nlerp를 쓰는 이유를 압니다.
    • 선형 블렌드 스키닝 식과 그것이 GPU 정점 셰이더에서 어떻게 계산되는지 따라갈 수 있습니다.
    • ProjectE가 팔레트를 한 프레임에 한 번, 스킨 단위로, 병렬로 만드는 이유와 "뼈 = 엔티티" 설계의 장단점을 설명할 수 있습니다.

    왜 필요한가정점을 하나하나 움직일 수는 없다

    캐릭터 메시는 정점이 수천~수만 개입니다. 걷는 동작을 "매 프레임 모든 정점의 위치"로 저장한다면 1초 30프레임짜리 걷기 한 번에도 수십만 개의 위치가 필요하고, 걷기와 뛰기를 섞는 일은 아예 불가능에 가깝습니다. 사람의 몸을 생각해 보면 답이 보입니다. 팔의 피부는 스스로 움직이지 않고 뼈를 따라 움직입니다. 그러니 뼈 몇십 개의 움직임만 저장하고, 정점은 "어느 뼈를 얼마나 따라갈지"만 기억하게 하면 됩니다.

    이것이 스켈레탈 애니메이션(skeletal animation)입니다. 데이터는 세 가지로 나뉩니다.

    • 스켈레톤(skeleton): 뼈의 부모-자식 계층과 기본 자세.
    • 클립(clip): 시간에 따른 각 뼈의 이동·회전·스케일 키프레임.
    • 스킨(skin): 정점마다 영향을 주는 뼈 번호(최대 4개)와 가중치, 그리고 뼈마다 역바인드 행렬.

    매 프레임 하는 일은 "클립을 시각 t에 샘플링 → 뼈 월드 행렬 계산 → 정점을 뼈 행렬의 가중 합으로 변환"입니다. 이 마지막 단계를 스키닝(skinning)이라 부르고, 정점이 많으므로 GPU 정점 셰이더에서 합니다.

    핵심 개념뼈 계층 — 월드 행렬은 사슬로 곱해진다

    뼈 하나의 움직임은 부모 기준(로컬)으로 저장합니다. 어깨를 돌리면 위팔·아래팔·손이 모두 따라가야 하는데, 손의 키프레임에 어깨 회전까지 미리 섞어 두면 동작을 섞거나 고칠 수 없기 때문입니다. 로컬로 저장해 두면 손의 모델 공간 행렬은 손에서 루트까지 로컬 행렬을 곱해 얻습니다.

    ProjectE에서 뼈 하나의 로컬 포즈는 FNodePose(이동 + 쿼터니언 회전 + 스케일)이고, 행렬로 바꿀 때는 S·R·T 순서로 합성합니다. 계층을 따라 모델 공간 행렬을 만드는 함수는 부모가 배열에서 자식보다 뒤에 와도 동작하도록, 조상 사슬을 거슬러 올라갔다가 내려오며 계산합니다.

	FVector3 Translation;
	FQuat    Rotation;

};

    "노드"와 "뼈" glTF에서는 뼈도 일반 노드입니다. 그래서 ProjectE 코드도 "노드"라고 부르고, 스킨이 참조하는 노드를 조인트(joint)라고 부릅니다. 이 강의에서 뼈·노드·조인트는 같은 것을 가리킵니다.

    핵심 개념바인드 포즈와 역바인드 행렬

    아티스트는 메시를 특정 자세(보통 팔을 벌린 T 포즈나 A 포즈)에서 뼈에 붙입니다. 이 자세를 바인드 포즈(bind pose)라고 합니다. 메시의 정점 좌표는 바인드 포즈의 모델 공간에 저장되어 있습니다.

    문제는 "지금 팔꿈치가 90도 굽었다"는 정보를 정점에 어떻게 적용하느냐입니다. 정점을 팔꿈치 뼈를 따라 돌리려면, 먼저 정점을 팔꿈치 뼈 기준 좌표로 바꿔야 합니다(바인드 포즈 때 팔꿈치 뼈에서 얼마나 떨어져 있었나). 그 다음 지금 팔꿈치 뼈의 월드 행렬을 곱하면 정점이 뼈를 따라 옮겨집니다. "바인드 포즈의 모델 공간 → 뼈 공간" 변환은 바인드 포즈에서의 뼈 행렬의 역행렬이고, 이것을 역바인드 행렬(inverse bind matrix)이라 부릅니다. glTF 파일이 뼈마다 미리 계산해 담아 둡니다.

    ProjectE는 이 곱을 "팔레트"라 부르고, CPU에서 뼈마다 한 번 계산해 GPU로 올립니다. 스킨 메시를 그리는 엔티티는 런타임 전용 컴포넌트 FSkinComponent를 가집니다.

    // 스킨 메시 바인딩 (모델 인스턴스화 시 생성되는 런타임 전용, 직렬화/리플렉션 제외).
// 본 행렬 = InverseBindMatrices[i] * Joints[i]의 월드 행렬 (스킨 메시 노드 자신의 트랜스폼은 무시 — glTF 규약)
struct FSkinComponent
{
	std::vector<FEntity>    Joints;
	std::vector<FMatrix4x4> InverseBindMatrices;
};

    주석의 마지막 줄이 중요합니다. 팔레트가 정점을 바로 월드 공간으로 보내므로, 스킨 메시를 그릴 때는 메시 노드 자신의 월드 행렬을 곱하지 않습니다(셰이더 쪽 World는 항등). 조인트 월드 행렬에 이미 모델 루트의 배치가 들어 있기 때문입니다.

    핵심 개념키프레임 보간 — lerp, slerp, nlerp

    클립은 뼈마다, 속성(이동/회전/스케일)마다 하나의 채널입니다. 채널은 오름차순 시각 배열과 같은 개수의 값 배열을 가집니다. 키와 키 사이 시각이 주어지면 양쪽 키를 찾아 그 사이 비율 α로 보간합니다.

    // 노드 하나의 속성 하나에 대한 키프레임 트랙
struct FAnimationChannel
{
	int32                   Node          = -1; // 모델 노드 인덱스
	EAnimationPath          Path          = EAnimationPath::Translation;
	EAnimationInterpolation Interpolation = EAnimationInterpolation::Linear;
	std::vector<float>      Times;  // 오름차순 (초)
	std::vector<FVector4>   Values; // Times와 같은 개수. 이동/스케일은 xyz
};

    쿼터니언은 길이 1인 4차원 벡터라 "단위 구 위의 점"으로 볼 수 있습니다. 성분마다 직선 보간하면 두 점을 잇는 현 위의 점이 되어 길이가 줄어듭니다. 두 가지 해법이 있습니다.

    • slerp(구면 선형 보간): 두 회전 사이 각도 θ를 구해 sin((1−α)θ)/sin θ · A + sin(αθ)/sin θ · B. 호를 따라 일정한 각속도로 움직입니다. 키 두 개 사이를 정확히 따라가야 하는 클립 샘플링에 씁니다.
    • nlerp(정규화 선형 보간): 그냥 성분별 가중 합 후 길이로 나눕니다. 각속도가 약간 일정하지 않지만 싸고, 무엇보다 여러 개를 한꺼번에 가중 합할 수 있습니다. 41강의 블렌드 스페이스처럼 클립 서너 개를 섞을 때 씁니다.

    어느 쪽이든 q와 −q는 같은 회전이므로, 내적이 음수면 한쪽 부호를 뒤집어 "가까운 쪽 반구"로 맞춥니다. 그러지 않으면 350도를 거꾸로 돌아가는 회전이 나옵니다.

}

    키 찾기는 이진 탐색(upper_bound)이고, 범위 밖 시각은 끝 키로 고정됩니다. FQuat::Slerp는 두 회전이 거의 같으면(cos θ ≥ 0.9999) sin θ로 나누는 것이 불안정하므로 선형 보간으로 대신합니다. 재생 시각 진행(AdvanceTime)은 루프면 [0, 길이)로 감고 "감았다"는 표시를 돌려주는데, 이 표시는 42강의 노티파이와 43강의 루트 모션이 루프 경계를 정확히 다루는 데 쓰입니다.

    핵심 개념선형 블렌드 스키닝

    팔꿈치 근처 정점은 위팔과 아래팔 둘 다를 조금씩 따라가야 자연스럽게 접힙니다. 그래서 정점마다 최대 4개의 뼈와 가중치(합 1)를 두고, 각 뼈의 팔레트로 옮긴 결과를 가중 평균합니다. 이것이 선형 블렌드 스키닝(Linear Blend Skinning, LBS)입니다.

    식 v′ = Σk=1..4 wk · ( v × 팔레트[jk] )  =  v × ( Σ wk · 팔레트[jk] )   (Σ wk = 1)
    행렬 곱이 선형이므로 "점을 4번 옮겨 섞기"와 "행렬 4개를 먼저 섞고 한 번 옮기기"가 같습니다. 셰이더는 뒤쪽을 씁니다 — 법선·탄젠트도 같은 섞인 행렬로 변환할 수 있기 때문입니다.

    행렬을 성분별로 섞으면 회전 부분이 더 이상 순수한 회전이 아니게 되어, 비틀림이 큰 관절(손목을 180도 돌리기 등)에서 부피가 줄어드는 현상이 알려져 있습니다(흔히 "사탕 포장지" 현상이라 부릅니다). 그래도 LBS는 빠르고 단순해서 대부분의 게임이 기본으로 씁니다.

    ProjectE의 스킨 정점 데이터는 일반 정점과 다른 정점 버퍼 슬롯에 둡니다.

    // 스킨 정점 스트림 (정점 버퍼 슬롯 1). FVertex(슬롯 0)와 같은 개수·순서.
// 정적 메시는 이 스트림이 없으므로 정적 경로의 정점 크기/대역폭은 그대로다.
struct FSkinVertex
{
	uint16   Joints[4]  = { 0, 0, 0, 0 };                 // FSkinComponent::Joints 인덱스
	FVector4 Weights    = FVector4(1.0f, 0.0f, 0.0f, 0.0f); // 합 = 1
};
static_assert(sizeof(FSkinVertex) == 24);

    GPU 쪽 계산은 몇 줄뿐입니다. 프레임의 모든 팔레트가 한 구조화 버퍼 SkinBones(t15)에 이어 붙어 있고, 인스턴스마다 자기 팔레트가 시작하는 자리 BoneOffset을 압니다.

    // 팔레트[BoneOffset + i] = InverseBind[i] * JointWorld[i] (행벡터 규약) — 스킨 정점은 바로 월드 공간으로 변환된다
StructuredBuffer<float4x4> SkinBones : register(t15);

float4x4 ComputeSkinMatrix(uint BoneOffset, uint4 Joints, float4 Weights)
{
	return SkinBones[BoneOffset + Joints.x] * Weights.x + SkinBones[BoneOffset + Joints.y] * Weights.y +
	       SkinBones[BoneOffset + Joints.z] * Weights.z + SkinBones[BoneOffset + Joints.w] * Weights.w;
}

const float4   WorldPosition = mul(float4(Input.Position, 1.0f), Skin);
const float3x3 Skin3         = (float3x3)Skin;
Output.Position      = mul(WorldPosition, ViewProjection);
const float4x4 PrevSkin = ComputeSkinMatrix(Instance.PrevBoneOffset, Input.Joints, Input.Weights);
Output.PreviousClip  = mul(mul(float4(Input.Position, 1.0f), PrevSkin), PrevViewProjection);
Output.WorldNormal   = normalize(mul(Input.Normal, Skin3));

    PrevBoneOffset는 지난 프레임의 팔레트를 가리킵니다. TAA·모션 블러 같은 시간 효과는 픽셀마다 "지난 프레임에 이 점이 화면 어디에 있었나"(움직임 벡터)를 알아야 하는데, 스킨 메시는 물체가 제자리에 있어도 팔다리가 움직이므로 정점을 지난 팔레트로도 한 번 더 변환해야 합니다.

    팔레트는 프레임에 한 번, 스킨 단위로

    팔레트를 만드는 곳은 렌더러의 FSkinnedMeshPalette::Build 하나입니다. 메인 패스, 방향광 그림자, 로컬 라이트 그림자, 선택 아웃라인이 모두 같은 버퍼를 BoneOffset으로 인덱싱합니다. 패스마다 팔레트를 다시 계산하거나 올리지 않는다는 뜻입니다.

    // 팔레트 공유: 한 모델의 여러 프리미티브 엔티티는 각자 FSkinComponent를 갖지만 조인트 엔티티 목록과 역바인드 행렬이 같으면

// 계산 (모두 결정적 — 결과는 실행 순서와 무관, IsVisible은 여러 스레드에서 불린다 — 읽기 전용이어야 한다):
//   1) 후보 조회(병렬) → 2) 그룹 묶기(호출 스레드) → 그룹 평가(병렬) →
//   3) 업로드 자리·드로우 번호(호출 스레드) → 4) 그룹마다 병렬: 팔레트/경계/업로드 버퍼에 직접 쓰기/이력/드로우 정보
// 호출: FScene::UpdateTransforms 이후, 그림자 캐스터 볼륨(캐스케이드/로컬 그림자 장)을 정한 뒤, 메시 인스턴스 Gather 전에 Build

    여기에 세 가지 설계가 겹쳐 있습니다.

    1. 가시성 먼저: 팔레트를 계산하기 전에 "조인트 위치 + 조인트별 반경"으로 보수적인 경계 상자를 만들어 판정합니다. 보이지 않는 캐릭터는 팔레트도, 업로드도, 그리기도 하지 않습니다. 판정 기준은 "메인 카메라 프러스텀 ∪ 그림자 캐스터 볼륨"입니다 — 화면 밖에 서 있지만 그림자가 화면 안으로 드리우는 캐릭터도 있기 때문입니다.
    2. 스킨 단위 공유: glTF 모델은 머티리얼마다 프리미티브(엔티티)가 나뉘는데, 모두 같은 뼈를 씁니다. 조인트 목록과 역바인드가 같으면 그룹으로 묶어 팔레트를 한 번만 계산합니다.
    3. 결정적 병렬: 그룹마다 FParallel::ParallelFor로 나눠 계산하되, 업로드 버퍼 안 자리는 미리 호출 스레드에서 정해 두므로 실행 순서와 결과가 무관합니다(같은 입력이면 같은 화면).

    뼈 = 엔티티

    ProjectE는 모델을 인스턴스화할 때 glTF 노드마다 엔티티를 하나씩 만듭니다(FAnimationRuntime::NodeEntities). 애니메이션 시스템은 뼈 엔티티의 로컬 트랜스폼에 포즈를 쓰고, 월드 행렬은 씬의 일반 트랜스폼 갱신(FScene::UpdateTransforms)이 계산합니다.

    장점단점
    계층 패널에서 뼈가 보이고 선택된다. 소켓(42강)·래그돌·스크립트가 뼈를 그냥 "엔티티"로 다룬다. 월드 행렬 계산을 따로 만들 필요가 없다(트랜스폼 캐시·병렬 갱신을 그대로 씀). 뼈마다 엔티티·트랜스폼 컴포넌트가 생긴다. CLAUDE.md는 이것을 알려진 한계로 적어 둡니다: "뼈 = 엔티티(유닛당 엔티티 약 50개 — 수천 마리 군중 부적합)".

    애니메이션 갱신 자체도 규모에 맞게 나뉘어 있습니다. FAnimationSystem::Update는 준비(메인 스레드, 엔티티 순서) → 포즈 평가(엔티티별 병렬) → 마무리(메인)의 세 단계이고, 평가 단계 코드는 로그·ECS 구조 변경·콜백·다른 엔티티 쓰기를 하지 않는다는 규칙을 따릅니다. 화면에 작게 보이는 모델은 몇 프레임마다 한 번만 평가하는 갱신 빈도 LOD(URO)도 있습니다 — 건너뛴 시간은 다음 평가가 한 번에 진행하므로 노티파이(42강)를 잃지 않습니다.

    함정과 교훈"보이는 것만, 한 번만"

    스킨 메시 인스턴싱 (Phase 29) 처음에는 스킨 메시마다 팔레트를 상수 버퍼(b4)로 묶어 하나씩 그렸습니다. Phase 29에서 팔레트를 프레임 구조화 버퍼(t15)로 모으고 인스턴스 데이터의 BoneOffset으로 인덱싱하게 바꾸자, 스킨 228개 스트레스 씬의 드로우가 145/822 → 2/8로, Release 프레임이 3.53 → 2.23ms로 줄었습니다(Plans.md 29-2). 같은 Phase에서 팔레트 가시성 컬링을 넣어 먼 군중을 볼 때 업로드가 372 → 4KB로 줄었습니다.
    팔레트를 프리미티브마다 계산하고 있었다 스킨 유닛 500개 스트레스 씬에서 팔레트 계산이 3609번이었습니다 — 모델 하나가 프리미티브 여러 개로 나뉘어 있었기 때문입니다. 조인트 목록 + 역바인드가 같은 프리미티브끼리 공유하게 바꾸자 팔레트 500개, 업로드 19.5MB → 3.5MB/프레임, 수집 9.2 → 2.3ms가 되었고, 정지 포즈 화면 MD5는 이전과 같았습니다(커밋 4b78587).
    규칙: 새 그림자 패스는 팔레트 가시성 판정에도 넣는다 팔레트 가시성은 "메인 프러스텀 ∪ 그림자 캐스터 볼륨"으로 정해지고, 판정에서 빠진 엔티티(IsCulled)는 그 프레임 어떤 패스에도 나오지 않습니다. 새 그림자 패스를 추가하면서 이 판정에 넣지 않으면, 화면 밖 캐릭터의 그림자가 사라집니다(CLAUDE.md "스킨 인스턴싱/컬링 보강"). 같은 이유로 그림자 캐스터 볼륨은 팔레트보다 먼저 정해야 합니다.

    포즈 평가를 병렬로 바꾸고 URO를 넣은 작업에서는 스트레스 씬(1280x720)의 게임 틱 CPU가 14.2 → 2.7ms, 프레임이 26.9 → 16.5ms가 되었습니다(커밋 e0f4398). 이때 결과가 순차 실행과 같은지 확인하는 테스트(모델 300개, 간격 혼합, 크로스페이드, 비트 해시 비교)를 함께 넣었습니다 — 병렬화는 빨라지는 것보다 같은 결과가 먼저입니다.

    정리
    • 뼈는 부모 기준 로컬 포즈로 저장하고, 월드 = 로컬 × 부모 월드로 사슬을 곱한다.
    • 역바인드 행렬은 바인드 포즈 정점을 뼈 공간으로 옮기고, 팔레트 = InverseBind × JointWorld는 정점을 바로 월드로 보낸다.
    • 이동·스케일은 lerp, 회전은 slerp(키 사이)·nlerp(여러 개 가중 합). q와 −q는 같은 회전이므로 반구를 맞춘다.
    • LBS: 정점마다 뼈 4개·가중치 합 1, 행렬을 먼저 섞어 한 번 변환. 스킨 데이터는 슬롯 1 스트림(24바이트).
    • 팔레트는 프레임에 한 번, 보이는 것만(그림자 포함), 스킨 단위로 공유해 병렬 계산하고 t15 하나로 모든 패스가 쓴다.

    생각해 볼 문제

    Q1. 스킨 메시 노드 자신에게 이동이 걸려 있는데 셰이더에서 그 World 행렬을 곱하지 않습니다. 왜 맞을까요? 팔레트의 JointWorld에 모델 루트부터 그 뼈까지의 월드 배치가 이미 들어 있으므로, 팔레트를 곱한 정점은 이미 월드 공간입니다. 여기에 메시 노드의 World를 또 곱하면 배치가 두 번 적용됩니다. glTF 규약도 "스킨 메시 노드의 트랜스폼은 무시"이고, FSkinComponent 주석에 그대로 적혀 있습니다.
    Q2. 블렌드 스페이스로 클립 세 개를 섞을 때 slerp가 아니라 nlerp를 쓰는 이유는? slerp는 두 회전 사이에서만 정의됩니다. 세 개 이상을 섞으려면 slerp를 두 번 중첩해야 하는데 순서에 따라 결과가 달라집니다. nlerp는 가중 합(반구 맞춤) 후 정규화라 몇 개든 순서와 무관하게 한 번에 섞을 수 있고 쌉니다. 프레임 사이 포즈 차이가 작아 각속도 오차는 눈에 띄지 않습니다.
    Q3. 화면 밖에 있는 캐릭터의 팔레트를 계산하지 않는 최적화가 버그가 되는 경우는? 그 캐릭터가 화면 안으로 그림자를 드리울 때입니다. 팔레트가 없으면 그림자 패스에서도 그릴 수 없어 그림자가 사라집니다. 그래서 ProjectE는 가시성을 "메인 프러스텀 ∪ CSM 캐스케이드 ∪ 로컬 그림자 장"으로 판정하고, 그림자 캐스터 볼륨을 팔레트보다 먼저 정합니다. 한편 애니메이션 갱신 자체를 화면 밖이라고 건너뛰는 일은 Phase 29에서 측정해 보니 이득이 없어 하지 않았고, 후속 목록에 "소켓 대상 제외"가 함께 적혀 있습니다 — 소켓에 붙은 무기처럼 그리기 외의 이유로 뼈 위치가 필요한 경우가 있기 때문입니다.

    핵심 개념상태 머신과 전이

    상태(state)는 "지금 재생할 것" 하나입니다 — 클립 하나이거나, 뒤에서 볼 블렌드 스페이스입니다. 전이(transition)는 "어느 상태에서 어느 상태로, 어떤 조건이면, 몇 초에 걸쳐 섞으며 넘어간다"입니다. Phase 27에서 만든 여우 플레이어 그래프가 좋은 예입니다.

    전이를 고르는 규칙은 단순하지만 정확히 알아야 합니다.

    • 목록 순서대로 처음 맞는 것 하나만, 프레임당 최대 한 번. 그래서 목록 순서가 곧 우선순위입니다.
    • From이 "*"면 "어느 상태에서든"(단, 목적지 자신은 제외). 사망처럼 어디서든 끼어들어야 하는 전이에 씁니다.
    • ExitTime ≥ 0이면 현재 상태의 정규화 시간(Phase, 0~1)이 그 이상일 때만 넘어갑니다. "공격 동작이 80% 끝나야 다음으로"를 표현합니다.
    for (size_t Index = 0; Index < Machine.Transitions.size(); ++Index)

    크로스페이드 — 끼어들어도 튀지 않게

    전이가 일어나면 이전 상태를 바로 끊지 않고 Duration 동안 가중치를 넘겨줍니다. 가중치 곡선은 직선 대신 smoothstep s(t) = 3t² − 2t³을 씁니다. 시작과 끝에서 기울기가 0이라, 섞임이 갑자기 시작하거나 갑자기 멈추는 느낌이 없습니다.

    까다로운 것은 페이드 도중에 또 전이가 오는 경우입니다. 점프하자마자 낙하로 넘어가는 식입니다. ProjectE는 그 순간의 가중치를 모든 상태의 "출발점"으로 기억하고 다시 섞습니다. 이미 섞이고 있던 상태로 돌아가면 그 상태의 재생 위치와 가중치를 이어 갑니다. 페이드아웃 중인 상태도 재생은 계속 진행합니다(멈춘 포즈로 사라지면 어색하므로).

    핵심 개념블렌드 스페이스와 정규화 시간 동기화

    속도 0, 120, 450cm/s에 대기·걷기·뛰기 클립이 있다고 합시다. 지금 속도가 300이면? 상태 하나 안에서 이웃한 두 샘플을 섞으면 됩니다. 이것이 1D 블렌드 스페이스입니다. 샘플을 위치 오름차순으로 두고, 값이 들어간 구간의 두 샘플만 0이 아닌 가중치를 받습니다(합 1, 범위 밖은 끝 샘플 1).

    // Positions[Next - 1] <= Value < Positions[Next]
const size_t Next  = std::upper_bound(Positions.begin(), Positions.end(), Value) - Positions.begin();
const size_t Prev  = Next - 1;
const float  Span  = Positions[Next] - Positions[Prev];
const float  Alpha = Span > FMath::SmallNumber ? (Value - Positions[Prev]) / Span : 1.0f;
OutWeights[Prev]   = 1.0f - Alpha;
OutWeights[Next]   = Alpha;

    2D 블렌드 스페이스 — 그래디언트 밴드

    앞뒤 속도와 좌우 속도처럼 축이 둘이면 샘플이 평면에 흩어집니다. 흔한 방법은 샘플을 삼각형으로 나누고 무게중심 좌표를 쓰는 것인데, 삼각분할이 바뀌는 경계에서 가중치가 튈 수 있습니다. ProjectE는 Phase 42에서 그래디언트 밴드(gradient band, Freeform Cartesian) 방식을 택했습니다 — 유니티 Animator의 Freeform 2D가 쓰는 방식으로, 삼각분할이 없습니다.

    직관은 이렇습니다. 샘플 i에서 다른 샘플 j로 가는 선분 위에 입력을 투영해, j 쪽으로 얼마나 갔는지(0~1)를 봅니다. j에 가까울수록 i의 몫은 줄어듭니다. 모든 j에 대해 이 값을 구해 가장 작은 것을 i의 가중치로 삼으면, 입력이 어느 방향으로든 다른 샘플 쪽으로 가는 만큼 i의 영향이 줄어듭니다. 축 단위가 달라도(속도 cm/s와 방향 각도) 한쪽 축이 지배하지 않도록, 계산 전에 축마다 샘플 범위로 정규화합니다.

    파라미터는 복제하지 않는다

    파라미터는 float와 bool(0/1로 저장) 두 종류이고, Lua entity:SetAnimParam/GetAnimParam/GetAnimState나 C++ FAnimationSystem::SetAnimParam으로 씁니다. 캐릭터 루트처럼 조상 엔티티에서 불러도 자손의 그래프를 찾아갑니다.

    멀티플레이에서 파라미터는 네트워크로 보내지 않습니다. 애니메이션은 화면 연출이므로, 각 프로세스가 자기가 가진 정보로 계산하면 됩니다. 이 정보를 자동으로 넣어 주는 것이 bUseCharacterMovement(기본 켬)입니다.

    //   bUseCharacterMovement: 자신 또는 가장 가까운 조상의 FCharacterMovementComponent 상태를 매 게임플레이 틱 파라미터로 넣는다 (FGameWorld)
//     Speed = 수평 속도 (cm/s), VerticalSpeed = 수직 속도 (cm/s), Grounded = 바닥 (bool). 같은 이름을 스크립트가 써도 덮인다.
//     속도: 이 프로세스가 시뮬레이션하는 캐릭터(서버/Standalone, 예측하는 소유 클라이언트)는 캐릭터 이동 상태, 그 밖(복제 보간을 따르는
//     다른 플레이어)은 보간된 월드 위치의 변화(짧게 평활). 바닥은 어디서나 캡슐 접촉(복제 위치에 맞춘 캡슐 포함)

    섞일 때는 누구의 노티파이인가

    걷기와 뛰기가 섞이는 블렌드 스페이스를 생각해 봅시다. 두 클립 모두 발소리 노티파이가 있습니다. 둘 다 판정하면 한 걸음에 발소리가 두 번 납니다. 그래서 ProjectE는 출처(기본 레이어, 추가 레이어마다, 몽타주마다) 안에서 이번 프레임 가중치가 가장 큰 기여 하나의 클립에서만 판정합니다.

    이벤트는 애니메이션 갱신 중에 FAnimationRuntime::PendingNotifies에 모였다가 다음 프레임에 전달됩니다(게임 모듈: OnUpdate 직전, Lua: OnUpdate 뒤). 40강에서 본 것처럼 포즈 평가는 여러 스레드에서 돌기 때문에, 평가 중에 스크립트를 부를 수는 없습니다 — 모아 두었다가 메인 스레드에서 나눠 주는 것이 유일하게 안전한 방법입니다. Lua 수신자는 노티파이가 난 모델 루트의 스크립트이고, 없으면 가장 가까운 조상의 스크립트입니다.

    function SparringFighter:OnAnimNotify_SwordHit()

    핵심 개념소켓 — 뼈에 붙은 부착 지점

    소켓(socket)은 "뼈 기준 상대 트랜스폼"에 이름을 붙인 것입니다(FModelSocket: 이름, 뼈, 위치·회전·스케일). 칼을 손에 붙일 때 손뼈 원점에 바로 붙이면 칼자루가 손바닥 안으로 파묻히거나 방향이 틀어지므로, 손뼈에서 조금 옮기고 돌린 지점을 소켓으로 정해 둡니다. 다른 엔티티를 붙이는 것은 FSocketAttachmentComponent(대상 모델 루트 + 소켓 이름)입니다.

    bool FScene::GetSocketWorldMatrix(FEntity ModelRoot, std::string_view Socket, FMatrix4x4& OutWorld) const

	OutWorld = Found->GetLocalMatrix() * GetTransform(Bone).WorldMatrix; // 소켓 로컬 × 뼈 월드

    핵심 개념2본 IK — 코사인 법칙

    지금까지는 뼈 회전에서 끝 위치를 계산했습니다(FK, Forward Kinematics). IK(Inverse Kinematics)는 반대로 "발이 여기 있어야 한다"는 끝 위치에서 뼈 회전을 구합니다. 일반적인 IK는 반복 계산이 필요하지만, 허벅지-정강이-발이나 위팔-아래팔-손처럼 뼈 두 개짜리 사슬은 삼각형 하나의 문제라 닫힌 식으로 바로 풀립니다.

    const float MaxReach  = (UpperLength + LowerLength) * 0.9999f;
const float MinReach  = FMath::Abs(UpperLength - LowerLength) * 1.0001f + FMath::SmallNumber;
const float Reach     = FMath::Clamp(Distance, MinReach, MaxReach);
...
// 코사인 법칙: 허벅지와 목표 방향 사이 각
const float CosAngle = FMath::Clamp((UpperLength * UpperLength + Reach * Reach - LowerLength * LowerLength) / (2.0f * UpperLength * Reach), -1.0f, 1.0f);
const float SinAngle = std::sqrt(FMath::Max(0.0f, 1.0f - CosAngle * CosAngle));
const FVector3 DesiredMid = Root + Direction * (UpperLength * CosAngle) + Bend * (UpperLength * SinAngle);
const FVector3 DesiredEnd = Root + Direction * Reach;

Result.RootDelta          = FromToRotation(Mid - Root, DesiredMid - Root);
const FVector3 RotatedEnd = DesiredMid + Result.RootDelta.RotateVector(End - Mid);
Result.MidDelta           = FromToRotation(RotatedEnd - DesiredMid, DesiredEnd - DesiredMid);

    0.9999를 곱해 다리를 "완전히 펴지 않는" 데는 이유가 있습니다. 완전히 편 다리는 무릎 각이 0이라 어느 쪽으로 굽어야 할지(Bend) 방향 정보가 사라지고, 목표가 조금만 움직여도 무릎이 갑자기 뒤집힐 수 있습니다. Pole이 없거나 목표 방향과 평행하면 지금 무릎 방향을, 그것도 없으면 위·앞 축 중 하나를 씁니다.

    발 IK — 바닥 탐색은 World가 한다

    발 IK(FFootIkComponent, 모델 루트에)는 발마다 위 2본 IK를 한 번씩 풉니다. 문제는 목표, 즉 바닥 높이를 어디서 아느냐입니다. 바닥을 알려면 물리 레이캐스트가 필요한데, 애니메이션 시스템은 Scene 모듈에 있고 Scene은 Physics에 의존하면 안 됩니다(0강의 의존 방향). 그래서 둘을 모두 아는 World(FGameWorld)가 탐색을 대신하고 결과를 컴포넌트 런타임에 넣습니다.

    const FMatrix4x4& RootWorld = Scene->GetTransform(Entity).WorldMatrix;
const float       Distance  = FMath::Max(FootIk.TraceUp + FootIk.TraceDown, 1.0f);
for (FFootIkFoot& Foot : FootIk.Runtime.Feet)
{
	FVector3 Origin = RootWorld.TransformPosition(Foot.ProbeModelPosition) + FVector3::UpVector * FootIk.TraceUp;
	float    Left   = Distance;
	for (int32 Try = 0; Try < 3 && Left > 0.0f; ++Try)
	{
		FPhysicsHit Hit;
		if (!Physics->Raycast(Origin, -FVector3::UpVector, Left, Hit)) { break; }
		if (!IsSelf(Entity, Hit.Entity))  // 자기 몸(조상/자손)에 맞으면 1cm 아래에서 다시
		{
			Foot.bHit = true; Foot.HitPoint = Hit.Position; ...
			break;
		}
		Left -= Hit.Distance + 1.0f;
		Origin = Hit.Position - FVector3::UpVector * 1.0f;
	}
}
FootIk.Runtime.ProbeAge = 0.0f;

    애니메이션 쪽 규칙은 이렇습니다.

    • 발 보정 = clamp(바닥 높이 − 모델 루트 월드 Z, ±MaxAdjust)를 InterpSpeed로 부드럽게.
    • 골반 보정 = min(0, 발 보정들) — 내리기만 합니다. 계단에서 한 발이 낮은 칸에 있으면 골반을 내려야 그 발이 닿습니다. 올리기까지 하면 캐릭터가 떠 보입니다.
    • 골반을 내린 뒤 각 발을 (애니메이션 발 위치 + 위 × 보정)으로 2본 IK. bAlignToGround면 발을 바닥 법선에 맞춰 MaxAlignAngle까지 기울입니다.
    • 탐색 결과가 ProbeMaxAge(0.25초)보다 오래되면 맞지 않은 것으로 보고 보정을 0으로 돌립니다(에디터 편집 중, 물리 없음).
    • 계산은 모델 공간(모델 루트 기준)이고, 월드 값은 모델 루트 월드 행렬의 역행렬로 바꿔 씁니다. 회전 사슬은 균등 스케일을 가정합니다.

    시선(LookAt)

    FLookAtComponent는 목·머리처럼 뼈 목록(위 → 아래)의 마지막 뼈가 목표를 보게 합니다. 회전 = "애니메이션의 앞 방향 → 목표 방향"을 MaxAngle에서 자르고 가중치를 곱한 뒤, 뼈 개수로 나눠 위 뼈부터 차례로 나눠 줍니다. 한 뼈가 다 돌리면 목이 꺾여 보이지만, 목과 머리가 나눠 돌리면 자연스럽습니다. 목표는 Lua SetLookAtTarget(점/엔티티)이 있으면 그것, 없으면 컴포넌트의 Target이고, 목표가 사라지면 가중치가 BlendSpeed로 0이 됩니다.

    함정과 교훈

    여우는 -X를 본다 시선 IK의 "앞 방향"은 기본 포즈에서 모델 공간의 어느 축이 캐릭터의 앞인지(ForwardAxis)로 정합니다. 엔진 규약은 +X가 앞이지만, 여우 모델(Fox.glb)은 모델 공간 −X를 바라봅니다. 그래서 여우의 LookAt은 ForwardAxis = [-1, 0, 0]입니다(CLAUDE.md "애니메이션 고급"). 외부 에셋의 "정면"은 엔진 규약과 다를 수 있으니, 방향을 가정하는 기능은 축을 설정으로 받아야 합니다. 43강 리타기팅의 "정면 보정"도 같은 문제를 다룹니다.
    소켓 무기를 모델 엔티티의 자식으로 두면 훈련장 데모를 만들 때, 소켓에 붙일 무기 엔티티를 모델 엔티티의 자식으로 두면 모델 노드 계층이 만들어지지 않는 문제가 기록되었습니다. 그래서 규칙은 "소켓 부착 무기는 형제나 루트 아래에"입니다. 소켓 부착은 계층 부모를 무시하므로 굳이 자식일 필요도 없습니다(그림 42-3).
    래그돌 중에는 IK도 꺼진다 래그돌(FAnimationRuntime::bPhysicsPose) 동안은 애니메이션 갱신 자체를 건너뛰므로 IK도 꺼지고 보정값과 가중치는 0으로 돌아갑니다. 물리가 뼈를 움직이는 중에 IK가 다리를 끌어당기면 둘이 싸우게 됩니다. IK 식을 바꾸면 AnimIK_* 테스트를, 노티파이 판정을 바꾸면 AnimNotifyTests를 함께 고칩니다.
    정리
    • 노티파이 판정 = 이번 진행 구간에 시각이 들었는가. 루프는 두 구간, 역재생은 시간축 뒤집기, 멈춤·스크럽은 점 노티파이 없음.
    • 섞일 때는 출처마다 가중치가 가장 큰 기여 하나에서만 판정해 중복을 막고, 이벤트는 모았다가 다음 프레임 메인 스레드에서 전달한다.
    • 노티파이·소켓은 쿠킹 입력이 아닌 .emeta 사이드카에 둔다.
    • 소켓 부착 엔티티 월드 = 로컬 × 소켓 로컬 × 뼈 월드. 로컬↔월드 변환은 GetParentWorldMatrix로.
    • 2본 IK는 코사인 법칙의 닫힌 식, 무릎 방향은 Pole. 발 IK 바닥 탐색은 의존 방향 때문에 World가 하고 한 프레임 늦다.

    생각해 볼 문제

    Q1. 루프 경계를 나누지 않고 [이전 시각, 새 시각) 하나로 판정하면 어떤 일이 생길까요? 루프로 감긴 프레임은 새 시각이 이전 시각보다 작아(예: 0.66 → 0.04) 구간이 비거나 뒤집힙니다. 그러면 끝 근처(0.66~D)와 처음 근처(0~0.04)의 노티파이가 모두 누락됩니다. "끝까지"와 "처음부터" 두 구간으로 나눠야 한 바퀴의 모든 노티파이가 정확히 한 번씩 나옵니다.
    Q2. 노티파이를 애니메이션 갱신 도중 바로 Lua로 부르지 않고 다음 프레임에 전달하는 이유는? 포즈 평가는 엔티티별로 여러 스레드에서 병렬로 돌고, 평가 단계에서는 콜백·로그·ECS 구조 변경을 금지합니다. Lua 상태는 스레드 안전하지 않고, 스크립트가 엔티티를 만들거나 지울 수도 있습니다. 그래서 런타임별 목록에 모았다가 메인 스레드에서 정해진 시점에 나눠 줍니다. 대가는 한 프레임 지연입니다.

    리타기팅과 루트 모션

    관련 Phase: 52 사이드(리타기팅 + 루트 모션) · 살펴볼 곳: Scene/AnimRetarget.h(머리 주석)·.cpp, Scene/AnimRootMotion.h(머리 주석), Physics/CharacterMovement.h, Scene/ModelMetadata.h("Retarget")
    이 강의를 마치면
    • 스켈레톤마다 다른 것(이름, 뼈 수, 비율, 바인드 포즈, 정면)이 무엇이고, 왜 로컬 회전을 그대로 복사하면 안 되는지 설명할 수 있습니다.
    • 휴머노이드 23뼈 리그로 자동/수동 매핑하는 방법과, 모델 공간 바인드 보정 식의 각 항이 하는 일을 압니다.
    • 루트 모션을 추출하고 포즈를 제자리화하는 원리, 그리고 그것을 캐릭터 이동·멀티플레이와 연결하는 방식을 설명할 수 있습니다.

    왜 필요한가동작은 많은데 스켈레톤이 다르다

    41강 끝에서 본 것처럼 그래프의 품질은 결국 클립에서 나옵니다. 그런데 애니메이션 에셋은 스켈레톤에 묶여 있습니다. ProjectE 샘플에는 마네킹(Quaternius UAL2, CC0)과 치비 비율의 KayKit 캐릭터들이 있는데, KayKit 기사에게 마네킹의 동작을 그대로 틀 수는 없습니다. 뼈 이름도, 개수도, 팔다리 길이도, 기본 자세도 다르기 때문입니다.

    리타기팅(retargeting)은 한 스켈레톤의 클립을 다른 스켈레톤에서 재생할 수 있게 바꾸는 것입니다. ProjectE의 방식은 언리얼 IK Retargeter의 FK 체인 부분을 단순화한 것입니다(Phase 52 사이드).

    같은 작업에서 루트 모션(root motion)도 들어왔습니다. 애니메이터가 만든 "앞으로 세 걸음 걸으며 베기" 같은 동작은 이동량이 클립 안에 들어 있는데, 이것을 캐릭터의 실제 이동으로 꺼내 쓰는 기능입니다. 둘 다 "다른 곳에서 만든 동작을 우리 캐릭터에 정확히 옮기기"라는 같은 문제의 두 얼굴입니다.

    핵심 개념모델 공간 바인드 보정

    가장 단순한 리타기팅은 "같은 리그 뼈의 로컬 회전을 그대로 복사"입니다. 이것이 틀리는 이유는 두 가지입니다. 첫째, 로컬 축이 리그마다 다릅니다 — 소스의 "X축으로 30도"가 대상에서는 엉뚱한 방향으로 도는 회전일 수 있습니다. 둘째, 바인드 포즈가 다릅니다. 같은 "팔 들기" 동작이라도 T 포즈에서 시작한 30도와 A 포즈에서 시작한 30도는 결과가 다릅니다.

    ProjectE는 회전을 모델 공간에서 다루고, "소스가 자기 바인드 포즈에서 얼마나 돌았는가(델타)"를 대상의 기준 포즈에 얹습니다.

    식 (AnimRetarget.h 머리 주석) Gd(t) = F · Gs(t) · Gs(bind)−1 · F−1 · Align · Gd(bind)
    Gs, Gd = 소스/대상 뼈의 모델 공간 회전, bind = 기본(임포트) 포즈.
    · Gs(t) · Gs(bind)−1 — 소스가 바인드에서 돈 양(델타, 모델 공간)
    · F … F−1 — 그 델타를 대상 모델의 정면 기준으로 옮김 (Z축 회전 — 왼다리→오른다리 수평 방향을 맞춘다)
    · Align · Gd(bind) — 대상 바인드 포즈를 소스 바인드 포즈 모양으로 돌려 놓은 "기준 포즈"
    로컬 회전 = (대상 부모의 그 시각 모델 회전)−1 · Gd(t), 부모부터 차례로.

    Align은 뼈마다 "대상 기본 포즈의 뼈 방향(그 뼈 → 리그 자식 뼈)을 소스 기본 포즈 방향(F 적용)으로 돌리는 최소 회전"입니다. 손·머리·발끝처럼 방향을 정할 자식 뼈가 양쪽에 없으면 리그 부모의 Align을 이어받고, Root/Hips는 항등입니다.

    이동은 Root/Hips만, 키 비율로

    회전과 달리 이동은 대부분의 뼈에서 옮기지 않습니다(대상 기본 포즈 유지). 팔뼈의 이동을 옮기면 대상의 팔 길이가 소스 길이로 바뀌어 버리기 때문입니다. 몸 전체가 움직이는 Root/Hips만 옮기되 키 비율(대상 Hips 높이 ÷ 소스 Hips 높이, 기본 포즈 모델 공간 Z)을 곱합니다.

    이동 식 대상 모델 위치 = Pd(bind) + F · (Ps(t) − Ps(bind)) × 키 비율
    다리가 절반 길이인 캐릭터가 같은 걸음을 걸으면 한 걸음에 절반만 나아가야 발이 미끄러지지 않습니다. 루트 모션도 이 이동 채널에 실려 오므로 같이 스케일됩니다.

    변환된 클립은 30Hz로 다시 샘플링됩니다(RetargetClip). 소스 클립의 키 시각이 뼈마다 제각각이라도, 대상 부모의 그 시각 모델 회전을 알아야 로컬 회전을 구할 수 있으므로 모든 뼈를 같은 시각 격자에서 계산합니다.

    핵심 개념루트 모션 — 추출과 제자리화

    보통의 이동은 "코드가 캐릭터를 속도 v로 옮기고, 애니메이션은 제자리에서 다리만 움직이는" 방식입니다. 이러면 발이 땅에 붙어 있지 않고 미끄러지기 쉽습니다. 특히 "세 걸음 밀고 들어가며 베기"처럼 이동 속도가 동작 중에 변하는 클립은 코드로 흉내 내기 어렵습니다. 루트 모션은 반대로 애니메이션이 이동을 결정하게 합니다.

    규칙은 AnimRootMotion.h 머리 주석이 기준입니다.

    • 루트 노드: 컴포넌트 RootMotionBone이 있으면 그 노드, 없으면 클립마다 "조상에 이동 채널이 없는 최상위 이동 채널 노드"(ClipRootMotionNodes) — 전용 root 뼈가 있으면 root, 없으면 보통 Hips입니다. 클립마다 따로 정하는 이유는 같은 모델이라도 클립마다 이동이 실린 뼈가 다를 수 있기 때문입니다.
    • 추출: 루트 노드의 모델 공간 위치 P(t)와, 회전 추출이 켜져 있으면 시작 대비 Z축(위) 회전 Y(t)(twist 분해). 구간 a → b의 이동 = RotZ(−Y(a)) × (P(b) − P(a))의 XY, 회전 = Y(b) − Y(a)를 [−π, π]로. RotZ(−Y(a))는 이동량을 "그 시점 캐릭터가 바라보는 방향 기준"으로 바꿉니다 — 그래야 캐릭터가 돌아선 뒤에도 "앞으로 한 걸음"이 앞으로 갑니다.
    • 루프 경계: (a → 끝)과 (시작 → b)를 합성합니다(Compose). 노티파이와 같은 발상입니다. 역재생은 (a → 시작) 다음 (끝 → b).
    • 제자리화: 샘플한 포즈의 루트 노드 모델 공간 XY를 P(0)의 XY로 고정하고, 회전 추출이면 Z축 회전 −Y(t)를 곱해 시작 방향으로 되돌립니다. 루프 끝과 시작에서 포즈 XY가 같은 자리라 튀지 않습니다.
    • 섞기: 크로스페이드는 Lerp, 그래프 기여는 Σ 가중치 × 이동량, 레이어·몽타주는 시작 순서대로 Lerp(아래, 위, 가중치 × 루트 노드의 마스크 가중치).

    멀티플레이

    루트 모션은 애니메이션을 평가하고 그 캐릭터를 시뮬레이션하는 프로세스에서만 무브에 실립니다. 상황별로 정리하면 이렇습니다(CharacterMovement.h 주석).

    누구의 캐릭터루트 모션 처리
    원격 플레이어 (예측하는 소유 클라이언트)소유 클라이언트가 몽타주를 재생해 루트 모션 무브를 예측 적용하고, 무브와 함께 속도를 보낸다. 서버는 받은 속도를 MaxRootMotionSpeed(3000cm/s)로 잘라 같은 무브를 적용 → 보정이 거의 없다.
    다른 클라이언트에서 보이는 캐릭터복제 보간 위치를 따른다. 루트 모션은 포즈에서만 빠지므로, 발이 맞으려면 같은 몽타주를 재생해야 한다(Both 스크립트).
    서버/AI 캐릭터서버 권한.
    전용 서버모델·애니메이션을 인스턴스화하지 않으므로 서버 소유 캐릭터의 루트 모션은 없다(후속).

    클라이언트가 보낸 속도를 그대로 믿으면 "루트 모션"을 핑계로 순간 이동하는 치트가 가능하므로 서버가 상한으로 자릅니다. 무브 메시지 형식이 바뀌었으므로 NetProtocolVersion이 11이 되었습니다(CLAUDE.md "루트 모션").

    함정과 교훈변환은 맞는데 이상해 보일 때

    "팔이 T 포즈로 뜬다"는 보고 리타기팅 뒤 KayKit 걷기를 마네킹에 틀었더니 팔이 수평으로 들려 보인다는 보고가 있었습니다. 실제 에셋으로 양방향(KayKit → UAL2, UAL2 → KayKit) 클립의 길이 0/25/50/80% 프레임에서 위팔·아래팔·허벅지·정강이 월드 방향이 소스와 같은지(내적 > 0.98) 비교하는 테스트를 만들어 조사했습니다. 결론은 "변환은 맞다" — KayKit의 걷기·대기 동작은 원래 위팔을 거의 수평으로 앞뒤로 흔들고 아래팔을 바깥으로 벌리는데, 치비 비율이라 짧은 팔이 몸에 가려 내려간 것처럼 보였던 것입니다(커밋 1a01ed8). 각도를 그대로 옮기는 방식이라 비율이 다른 체형에서 과장된 동작은 그대로 보이며, 이것은 버그가 아니라 한계입니다. 체인별 보정은 후속 과제로 남았습니다.
    알려진 한계 모델 공간 정면이 같다고 보고 F는 Z축 회전만 보정하므로 누운 모델은 안 됩니다. 비균등 스케일 뼈, 발이 다리 사슬 밖에 있는 IK 리그도 맞지 않습니다. 변환 식을 바꾸면 AnimRetarget_*(실제 에셋 양방향 방향 비교 포함), 루트 모션 식을 바꾸면 RootMotion_* 테스트를 함께 고칩니다.

    40강의 URO(갱신 빈도 LOD)도 루트 모션과 얽힙니다. 몇 프레임씩 평가를 건너뛰면 이동이 끊겨 캐릭터가 뚝뚝 움직이므로, 루트 모션을 추출하는 모델은 URO 대상에서 빠져 항상 매 프레임 평가합니다(AnimUpdateRate.h).

    정리
    • 리타기팅은 휴머노이드 23뼈로 매핑(이름 규칙 + 계층, .emeta 수동 지정)한 뒤, 로컬이 아니라 모델 공간에서 "바인드 대비 델타"를 옮긴다.
    • F는 정면 차이, Align은 A/T 포즈 차이를 보정한다. 이동은 Root/Hips만, 키 비율을 곱한다.
    • 다른 모델의 클립은 RetargetSources 또는 "모델:클립" 이름으로 쓰고, 결과는 세트 뒤에 덧붙어 그래프·몽타주가 그대로 쓴다.
    • 루트 모션 = 루트 노드 수평 이동 추출 + 포즈 제자리화. 루프 경계는 두 구간 합성.
    • 이동은 수신자를 거쳐 캐릭터 무브의 "루트 모션 속도"로 적용되고, 멀티플레이는 시뮬레이션하는 쪽만 싣고 서버가 속도를 자른다.

    생각해 볼 문제

    Q1. 리타기팅에서 팔뼈의 "이동" 채널까지 옮기면 어떻게 될까요? 뼈의 로컬 이동은 사실상 "부모 뼈로부터의 거리 = 뼈 길이"입니다. 소스의 이동을 옮기면 대상의 팔 길이가 소스 팔 길이로 바뀌어 메시가 늘어나거나 줄어듭니다. 그래서 몸 전체 위치를 나타내는 Root/Hips만 옮기고(키 비율 적용), 나머지는 대상 기본 포즈의 이동을 유지합니다.
    Q2. 루트 모션의 이동량을 모델 공간 차이 P(b) − P(a)로 바로 쓰지 않고 RotZ(−Y(a))를 곱하는 이유는? 회전 추출을 켜면 캐릭터가 클립 중에 돌아섭니다. 돌아선 뒤의 이동을 모델 공간 그대로 쓰면, 엔티티는 이미 회전했는데 이동은 "원래 방향 기준"이라 엉뚱한 쪽으로 갑니다. 그 시점까지 돈 만큼(Y(a)) 되돌려 "지금 바라보는 방향 기준"으로 바꾸면, 적용할 때 엔티티의 현재 회전을 곱해 올바른 방향이 됩니다.
    Q3. 원격 클라이언트가 루트 모션 몽타주를 재생할 때, 서버가 자기 애니메이션으로 루트 모션을 계산하지 않고 클라이언트가 보낸 속도를 쓰는 이유는? 클라이언트는 입력 즉시 몽타주를 재생해 예측 이동을 하고 있습니다. 서버가 따로 애니메이션을 돌려 계산하면 시각·블렌드가 미묘하게 달라 매번 보정(되감기)이 일어납니다. 같은 무브(속도 포함)를 서버가 그대로 적용하면 결과가 같아 보정이 거의 없습니다. 대신 치트를 막기 위해 서버가 MaxRootMotionSpeed로 자릅니다. 서버의 애니메이션이 쌓은 루트 모션은 원격 캐릭터에는 쓰이지 않고 버려집니다.

    핵심 개념보간 — 계단, 직선, 곡선

    키의 Interp는 "그 키에서 다음 키까지"를 어떻게 이을지 정합니다.

    case ESequenceInterp::Constant: return Alpha >= 1.0f ? V1 : V0;
case ESequenceInterp::Linear:   return V0 + (V1 - V0) * Alpha;
...
// 3차 에르미트: 기울기 = 이웃 키를 잇는 기울기 (Catmull-Rom, 시각 간격이 달라도 맞게 초당 값으로), 양 끝 키는 0
const float Span   = T1 - T0;
const float Slope0 = bHasPrev && T1 - TPrev > FMath::SmallNumber ? (V1 - VPrev) / (T1 - TPrev) : 0.0f;
const float Slope1 = bHasNext && TNext - T0 > FMath::SmallNumber ? (VNext - V0) / (TNext - T0) : 0.0f;
const float H00    = 2.0f * A3 - 3.0f * A2 + 1.0f;
const float H10    = A3 - 2.0f * A2 + Alpha;
const float H01    = -2.0f * A3 + 3.0f * A2;
const float H11    = A3 - A2;
return H00 * V0 + H10 * Span * Slope0 + H01 * V1 + H11 * Span * Slope1;

    에르미트 곡선은 "두 끝점의 값과 기울기"로 정해지는 3차 곡선입니다. H00·H01은 값을, H10·H11은 기울기를 섞는 기저 함수입니다. 기울기를 "초당 값"으로 계산한 뒤 구간 길이(Span)를 곱하는 이유는, 키 간격이 고르지 않아도 이웃 구간과 속도가 이어지게 하기 위해서입니다.

    회전은 오일러 각으로 보간한다 Transform 키의 회전은 Pitch/Yaw/Roll 도로 저장하고 성분마다 보간합니다(언리얼과 같음). 사람이 숫자로 읽고 고치기 쉽고 "두 바퀴 돌기(720°)" 같은 표현도 가능하기 때문입니다. 대신 −170°에서 170°로 가는 키는 짧은 20°가 아니라 340°를 돌아가므로, 편집기가 키를 넣을 때 이전 키와 가까운 동치 각(±360°)으로 펼쳐 저장합니다(SequenceMath::QuatToEulerNear). 피치 ±90° 근처는 오일러 보간이 어색한 알려진 후속 과제입니다.

    재생과 적용

    씬에서 시퀀스를 재생하는 것은 FSequencePlayerComponent(시퀀스 경로, 자동 재생, 반복, 배속, bRestoreState)입니다. 재생은 FGameWorld 게임플레이 틱의 스크립트 뒤 · 물리 앞에서 일어납니다. 스크립트가 PlaySequence를 부르면 같은 틱에 반영되고, 시퀀스가 쓴 트랜스폼은 이번 프레임 물리·트랜스폼 갱신에 들어가기 때문입니다.

    • Animation 트랙: 구간 동안 모델의 애니메이션을 일시정지 + SetTime으로 구동합니다. 42강의 "스크럽" 경로와 같으므로 결정적이고, 시퀀스를 아무 시점으로 점프해도 포즈가 정확히 그 시각입니다. 마지막 구간이 끝나면 끝 포즈를 유지합니다.
    • Event 트랙: 지나간 구간의 이벤트를 모아 다음 틱에 Lua OnSequenceEvent_<이름>()로, 끝나면 OnSequenceFinished로 보냅니다(노티파이와 같은 "모았다가 전달").
    • 원래 값 기억: 처음 쓰는 프로퍼티마다 원래 값을 FSequenceEvalState::Saved에 기억합니다. bRestoreState면 끝나거나 멈출 때 되돌리고, 끄면 마지막 값을 유지합니다(열린 채로 남는 문).

    카메라 컷 — 두 값만 빌렸다 돌려준다

    카메라 컷은 새 카메라 시스템을 만들지 않고, 기존 규칙("주 카메라 중 Priority가 큰 것이 이긴다")을 그대로 이용합니다. 컷 대상 카메라를 bPrimary = true, Priority = 1 << 20으로 만들면 플레이어 카메라(로컬 카메라에 높은 Priority를 주는 방식, 48강)보다 확실히 위에 섭니다.

{

	RestoreProperty(State, Scene, State.ActiveCamera, CameraType->FindProperty("Primary"));

    "컷이 바뀌거나 끝나면 그 두 값만 되돌린다"가 핵심입니다. 컷 카메라의 시야각은 Property 트랙이 따로 움직이는 값이라 그 트랙의 규칙(bRestoreState)을 따르고, 컷 해제가 건드리지 않습니다. 이렇게 책임을 나눠 두면 "컷은 끝났는데 시야각이 갑자기 튀는" 일이 없습니다. 카메라 컷 트랙은 첫 번째 것 하나만 씁니다.

    ProjectE에서는편집 씬 미리보기와 맞바꾸기

    시퀀서 편집기(FSequenceEditor)에서 재생 헤드를 끌면, 그 시점을 편집 중인 씬에 직접 적용해 뷰포트에서 보여 줍니다(FSequenceSystem::Evaluate). 별도 미리보기 씬이 아니라 진짜 편집 씬이어야 주변 배치와 함께 구도를 볼 수 있기 때문입니다. 그런데 이것은 위험합니다. 미리보기로 문이 −100° 열린 상태에서 사용자가 Ctrl+S를 누르면, 씬 파일에 "열린 문"이 저장되어 버립니다. 실행 취소 스냅샷도 마찬가지입니다.

    해법은 FSequenceEvalState::SwapWithScene 하나입니다. 기억해 둔 원래 값과 씬의 현재 값을 맞바꾸므로 두 번 부르면 원상태입니다. 편집기는 씬을 직렬화하는 모든 지점을 이 함수 쌍으로 감쌉니다.

    void FSequenceEvalState::SwapWithScene(FScene& Scene)
{
	FRegistry& Registry = Scene.GetRegistry();
	for (FSaved& Item : Saved)
	{
		void* Component = Registry.IsValid(Item.Entity) ? Item.Type->GetComponent(Registry, Item.Entity) : nullptr;
		if (Component != nullptr)
		{
			FValue Current = ReadProperty(*Item.Property, Component);
			WriteProperty(*Item.Property, Component, Item.Value);
			Item.Value = std::move(Current);
		}
	}
}
    AssetEditors.SwapScenePreviews(Context);         // 시퀀서 미리보기 값이 아니라 원래 값을 저장
const bool bSaved = FSceneSerializer::SaveToFile(Scene, CurrentScenePath);
AssetEditors.SwapScenePreviews(Context);

    같은 감싸기가 "다른 이름으로 저장", 실행 취소 커밋(씬 JSON 스냅샷), 자동 저장에도 있습니다. 반대로 플레이 시작·씬 교체·핫 리로드 전에는 EndScenePreviews로 미리보기를 끝내 원래 값으로 되돌립니다. 플레이 씬은 편집 씬의 복제이므로, 미리보기 값이 남아 있으면 게임이 열린 문 상태로 시작하기 때문입니다.

    규칙 (CLAUDE.md) 편집 씬에 미리보기 값을 쓰는 편집기는 FAssetEditor::SwapScenePreview/EndScenePreview를 구현하고, 씬을 직렬화하는 새 코드(저장/스냅샷/Undo 커밋)는 FAssetEditorManager::SwapScenePreviews로 감싸 원래 값이 저장되게 합니다. 시퀀스 파일을 바꾸는 코드는 FSequenceLibrary::Invalidate(경로)를 불러, 재생 중인 컴포넌트가 다음 갱신에서 다시 읽게 합니다(그래프·리타기팅 라이브러리와 같은 "세대 번호" 방식).

    함정과 교훈연출은 로컬이다

    • 멀티플레이: 시퀀스는 복제하지 않는 로컬 연출입니다. 각 프로세스가 자기 시계로 재생하므로, 모두 같은 순간에 보게 하려면 서버 스크립트가 Multicast RPC로 PlaySequence를 부릅니다. 복제 엔티티를 시퀀스로 움직이면 클라이언트 보간과 충돌한다는 것이 후속 목록에 있습니다.
    • 미리보기 중 직접 고친 값: 미리보기가 켜진 동안 시퀀스가 움직이는 값을 손으로 고치면 다음 평가에 덮입니다. 편집기 주석의 안내대로 "키로 넣어야" 합니다.
    • 애니메이션 그래프가 붙은 모델: Animation 트랙은 클립 재생 경로를 쓰므로, 그래프로 재생하는 모델에는 적용되지 않고 경고를 냅니다(Phase 35 후속).
    쇼케이스 투어 쇼케이스 씬은 시작하면 63초짜리 시퀀스(ShowcaseTour.esequence)가 구역마다 카메라를 컷하며 투어하고, 구역에 들어갈 때 Zone_<이름> 이벤트를 디렉터 스크립트(ShowcaseDirector.lua)로 보냈습니다(Plans.md S-3). 후속 목록에 "투어는 실제 시간 기준(자동 검증 프레임과 어긋남)"이 남았습니다 — 자동 검증은 프레임 수로 끝나는데 연출은 초로 흐르니, 스크린샷 시점이 의도한 구도와 어긋날 수 있다는 것입니다. 이후 엔진은 화면·시뮬레이션 시간을 앱 프레임 시간(FFrameTime, --fixed-delta)으로 통일하는 규칙을 세웠습니다(65강).
    정리
    • 시퀀스 = 길이 + 트랙(Transform/Property/CameraCut/Animation/Event). 아무 시각 t에서 모든 값을 바로 계산할 수 있어 스크럽·편집이 된다.
    • 보간은 Constant/Linear/Smooth(Catmull-Rom 기울기 3차 에르미트, 양 끝 기울기 0). 회전은 오일러 각, 키를 넣을 때 가까운 각으로 펼친다.
    • 대상은 이름 경로(재생 엔티티 하위 → 씬 전체). 핸들은 저장·복제마다 바뀌지만 이름은 남는다.
    • 카메라 컷 = 기존 주 카메라 규칙 이용(bPrimary + Priority 1<<20), 끝나면 그 두 값만 되돌린다.
    • 편집 씬 미리보기는 SwapWithScene(두 번 = 원상태)으로 저장·스냅샷을 감싸고, 플레이·씬 교체 전에는 EndScenePreviews.

    생각해 볼 문제

    Q1. 시퀀스의 Animation 트랙이 클립을 "재생"하지 않고 매 프레임 일시정지 + SetTime으로 구동하는 이유는? 재생 속도에 맡기면 시퀀스 시각과 클립 시각이 프레임 시간 오차로 조금씩 어긋나고, 스크럽으로 아무 시점에 점프했을 때 그 시점의 포즈를 바로 낼 수 없습니다. 시퀀스 시각에서 클립 시각을 계산해 SetTime으로 지정하면, 언제 어디로 점프해도 같은 시각엔 같은 포즈가 나옵니다(결정적). 노티파이 규칙에서 스크럽이 점 노티파이를 내지 않는 것도 이 경로와 맞물립니다.
    Q2. 카메라 컷이 끝날 때 카메라 컴포넌트 전체를 원래대로 되돌리면 어떤 문제가 생길까요? 같은 카메라의 시야각이나 위치를 Property/Transform 트랙이 움직이고 있었다면, 컷 해제가 그 값까지 되돌려 화면이 튀거나 bRestoreState를 끈 의도(마지막 값 유지)를 깨뜨립니다. 컷이 직접 바꾼 것은 bPrimary와 Priority뿐이므로 그 둘만 되돌리는 것이 맞습니다.
    Q3. 미리보기 값을 저장에서 빼기 위해, 맞바꾸기 대신 "씬 전체를 복사해 두었다가 저장 때 복사본을 직렬화"하면 어떨까요? 동작은 하지만, 미리보기 중에 사용자가 다른 엔티티를 편집하면 복사본에는 그 편집이 없으므로 저장에서 사라집니다. 매번 씬 전체를 복사하는 비용도 큽니다. 맞바꾸기는 시퀀스가 실제로 건드린 프로퍼티만 대상으로 하고, 나머지 편집은 그대로 둔 채 그 값들만 잠시 원래대로 돌려놓습니다. 다만 기억한 엔티티가 실행 취소 등으로 새로 만들어졌으면 기록이 무효이므로 HasStaleEntities로 확인합니다.
