    사실적인 화면 — 렌더링 심화 (후반)

    머티리얼을 코드로 컴파일하고, 늘어나는 패스를 렌더 그래프로 다스리고, 하늘·물·레이 트레이싱·전역 조명·면광원까지 "현대 엔진의 화면"을 이루는 기술을 하나씩 뜯어봅니다. 마지막으로 정반대 방향 — 진짜 도트 게임처럼 보이게 하는 스타일 렌더링으로 마무리합니다.

    21강

    머티리얼 시스템

    관련 Phase: 36(블렌드·양면·인스턴스) · 49 사이드(그래프 → HLSL) · 51 사이드(노드 편집기) · 살펴볼 곳: Renderer/Material.h, Renderer/MaterialAsset.h, Renderer/MaterialGraph.h, Renderer/MaterialGraphCompiler.cpp, Engine/Shaders/MaterialCommon.hlsli, Editor/AssetEditors/MaterialEditor
    이 강의를 마치면
    • Opaque/Masked/Translucent/Additive가 렌더링 파이프라인의 어느 패스에 어떻게 들어가는지 설명할 수 있습니다.
    • 머티리얼 인스턴스(부모 체인)가 "덮어쓴 키만 바꾼다"는 규칙으로 어떻게 해석되는지 압니다.
    • 노드 그래프를 HLSL 함수로 바꾸는 컴파일러의 타입 규칙·공통식 재사용·결정적 해시가 왜 필요한지 이해합니다.
    • 모든 머티리얼이 하나의 함수 EvaluateMaterial로 표면을 내는 구조가 래스터·그림자·레이 트레이싱을 어떻게 하나로 묶는지 압니다.

    왜 필요한가"표면이 어떻게 보이는가"를 데이터로

    3부 전반에서 우리는 PBR(물리 기반 렌더링)의 금속/거칠기 모델로 표면을 셰이딩했습니다. 표면 하나를 설명하는 값 묶음 — 베이스 색, 금속도, 거칠기, 노멀 맵, AO, 발광 — 을 머티리얼(material)이라고 부릅니다. ProjectE에서는 .emat라는 JSON 파일이 머티리얼 하나이고, 셰이더는 고정된 식(텍스처 슬롯 t0~t4)으로 이 값을 읽었습니다.

    그런데 실제 게임 화면을 만들다 보면 이 고정 모델로는 곧 부족해집니다.

    • 철망·나뭇잎: 사각형 판 하나에 구멍 뚫린 텍스처를 붙입니다. 구멍 부분은 "없는 것"처럼 그려야 합니다.
    • 유리·불꽃: 뒤가 비쳐 보이거나(반투명), 빛이 더해지기만 합니다(가산).
    • 같은 재질의 변형: "녹슨 철"을 거칠기만 바꿔 열 가지 만들 때마다 파일 전체를 복사하면, 원본을 고칠 때 열 개를 다 고쳐야 합니다.
    • 절차적 효과: 흐르는 용암, 높이에 따라 섞이는 이끼, 월드 좌표로 반복되는 바닥 타일. 이런 것은 "값"이 아니라 "식"이 필요합니다.

    이 강의는 이 네 가지 요구를 순서대로 해결한 ProjectE의 머티리얼 시스템을 봅니다. 블렌드 모드와 양면(Phase 36), 인스턴스 상속(Phase 36), 그리고 노드 그래프를 HLSL로 컴파일하는 머티리얼 그래프(Phase 49 사이드)와 그 편집기(Phase 51 사이드)입니다.

    핵심 개념블렌드 모드 — 픽셀이 화면에 섞이는 방식

    GPU가 픽셀 셰이더 결과를 렌더 타깃에 쓸 때, 그냥 덮어쓸 수도 있고 이미 있는 색과 섞을 수도 있습니다. 이것이 블렌딩입니다. 그리고 깊이 버퍼에 자기 깊이를 쓸지 말지도 정해야 합니다. 네 가지 모드는 이 두 질문에 대한 서로 다른 답입니다.

    모드색깊이 쓰기대표 예
    Opaque (불투명)덮어쓰기예벽, 바닥, 대부분의 물체
    Masked (알파 테스트)알파 < 컷오프면 픽셀을 버림(clip), 나머지는 덮어쓰기예철망, 잎, 투조 장식
    Translucent (반투명)결과 = 알파 × 새 색 + (1 − 알파) × 뒤의 색아니오유리, 연기
    Additive (가산)결과 = 뒤의 색 + 새 색아니오불꽃, 빛줄기, 홀로그램

    Masked는 "반투명"처럼 보이지만 실은 불투명입니다. 픽셀이 있거나 없거나 둘 중 하나이므로 깊이를 쓸 수 있고, 그래서 그림자도 드리우고 그리는 순서도 상관없습니다. 반면 Translucent는 뒤에 무엇이 있는지 알아야 섞을 수 있으므로 반드시 불투명한 것을 다 그린 뒤에, 먼 것부터 가까운 것 순서로 그려야 합니다. 깊이를 쓰지 않는 이유도 여기 있습니다 — 유리가 깊이를 쓰면 그 뒤에 그릴 다른 유리가 깊이 테스트에서 탈락합니다.

    Masked는 "세 곳에서 똑같이" 잘려야 한다

    19강의 깊이 사전 패스를 떠올려 봅시다. 사전 패스가 깊이를 먼저 채우고, 메인 패스는 깊이 테스트를 EQUAL로 두어 "사전 패스가 남긴 그 표면"만 셰이딩합니다. 만약 사전 패스는 잎의 구멍을 자르지 않고 메인 패스만 자른다면? 구멍 부분에 잎 판의 깊이가 남아 뒤의 하늘이나 땅이 가려진 채 비어 보입니다. 그림자 패스가 자르지 않으면 구멍 뚫린 잎이 꽉 찬 사각형 그림자를 드리웁니다. 그래서 CLAUDE.md는 이렇게 못 박아 둡니다: Masked = 베이스 알파(텍스처 × 정점 색 × 팩터) < 컷오프면 버림 — PSMainMasked/PSPrepassMasked/ShadowMaskedPS가 같은 식이라 함께 고친다.

    양면(Two-Sided)

    보통 GPU는 카메라를 등진 삼각형(뒷면)을 버립니다(백페이스 컬링). 잎이나 천처럼 두께 없는 판은 뒤에서도 보여야 하므로 TwoSided면 컬링을 끕니다. 그런데 뒷면을 그대로 셰이딩하면 법선이 카메라 반대를 향해 조명이 깜깜해집니다. 그래서 픽셀 셰이더가 SV_IsFrontFace로 뒷면인지 확인하고, 셰이딩 법선·기하 법선·화면 법선 버퍼에 쓰는 값을 모두 뒤집습니다.

    PSO 변형 비트

    블렌드 상태와 컬링 모드는 DirectX 12에서 파이프라인 상태 객체(PSO)에 구워 넣는 값입니다. 즉 모드마다 다른 PSO가 필요합니다. ProjectE는 메시 패스마다 PSO를 8개 만들고, 3비트 번호로 고릅니다.

    // 메시 패스 PSO 변형 비트 (묶음 키의 Pipeline 필드 3비트 = PSO 배열 인덱스).
//   bit0 = Masked(불투명 패스) / Additive(반투명 패스), bit1 = 양면(컬링 없음), bit2 = 스킨.
//   스킨을 최상위에 두어 정적 묶음이 모두 스킨 묶음보다 앞에 정렬된다 (오클루전 1단계 번호 목록 전환이 이 순서에 기댄다)
constexpr uint32 VariantMaskedOrAdditive = 1u;
constexpr uint32 VariantTwoSided         = 2u;
constexpr uint32 VariantSkinned          = 4u;
constexpr uint32 VariantCount            = 8u;
constexpr uint32 MakeVariant(bool bSkinned, bool bMaskedOrAdditive, bool bTwoSided)
{
	return (bMaskedOrAdditive ? VariantMaskedOrAdditive : 0u) | (bTwoSided ? VariantTwoSided : 0u) | (bSkinned ? VariantSkinned : 0u);
}

    bit0이 패스에 따라 뜻이 바뀌는 점이 재미있습니다. 불투명 패스에는 Additive가 오지 않고, 반투명 패스에는 Masked가 오지 않으니 한 비트를 나눠 써도 겹치지 않습니다. 그리고 이 번호는 29강의 인스턴싱 묶음 키 맨 앞에 들어가 정렬 순서를 정합니다. 스킨 비트를 최상위에 둔 이유가 주석에 그대로 있습니다 — 정렬했을 때 정적 묶음이 전부 앞에 와야 오클루전 컬링 1단계가 번호 목록을 한 번만 바꾸면 되기 때문입니다. 그래서 규칙이 하나 생깁니다: 새 메시 패스는 변형 8개와 Masked clip을 함께 지원한다.

    핵심 개념머티리얼 인스턴스 — 덮어쓴 키만 바꾸는 상속

    "금(거칠기 0.1)", "금(거칠기 0.4)", "금(거칠기 0.8)"을 만든다고 합시다. 베이스 색·금속도·텍스처는 같고 거칠기만 다릅니다. 언리얼의 머티리얼 인스턴스처럼, ProjectE의 .emat는 "Parent" 키로 부모 파일을 가리킬 수 있고, 파일에 실제로 적힌 키만 부모 값을 덮어씁니다. 부모도 또 다른 인스턴스일 수 있으므로 이것은 체인이 됩니다.

    "파일에 적힌 키"를 기억하는 방법이 OverrideMask 비트 마스크입니다. 필드마다 비트가 하나씩 있고, JSON을 읽을 때 키가 있으면 그 비트를 켭니다.

    enum EField : uint32
{
	Field_BaseColorFactor   = 1u << 0,
	Field_EmissiveFactor    = 1u << 1,
	Field_Metallic          = 1u << 2,
	Field_Roughness         = 1u << 3,
	...
	Field_BlendMode         = 1u << 7,
	Field_TwoSided          = 1u << 8,
	Field_Texture0          = 1u << 9, // ~ 1u << 13
};
static constexpr uint32 MaxParentDepth = 16;
// 인스턴스 해석: Path(이 에셋 파일 경로) 기준으로 부모 체인을 읽어 평탄한 머티리얼(Parent 없음, 텍스처는 Path 폴더 기준)을 만든다.
// OutChain = 부모 경로 (가까운 부모부터). 순환·깊이 초과·부모 읽기 실패면 오류를 남기고 false
static bool Resolve(const FMaterialAsset& Asset, const std::filesystem::path& Path, const FLoader& Loader,
                    FMaterialAsset& OutResolved, std::vector<std::filesystem::path>* OutChain = nullptr, ...);

    두 가지 세부가 중요합니다. 첫째, 텍스처 경로 다시 쓰기. .emat의 텍스처 경로는 그 파일 폴더 기준 상대 경로입니다. 부모가 Materials/Metal/에 있고 자식이 Materials/Demo/에 있으면 부모의 "Brushed.png"를 자식 폴더 기준으로 해석하면 엉뚱한 파일이 됩니다. 그래서 Resolve는 부모에서 가져온 경로를 자식 폴더 기준으로 다시 계산합니다. 둘째, 부모가 바뀌면 자식도 다시 해석해야 합니다. 해석 결과에 체인(ParentChain)을 저장해 두고, 리소스 관리자가 부모 파일이 바뀌면 그 부모를 체인에 가진 자식들을 다시 해석합니다. 그래서 코드에서 머티리얼을 고칠 때는 FMaterial을 직접 고치지 말고 ApplyMaterialAsset을 거치라는 규칙이 있습니다.

    핵심 개념머티리얼 그래프 — 노드를 HLSL로 컴파일하기

    고정 PBR 머티리얼은 "값"만 바꿀 수 있습니다. 하지만 "UV를 시간에 따라 흘리고, 텍스처 두 장을 높이에 따라 섞고, 가장자리에 프레넬 빛을 더하라" 같은 것은 식입니다. 아티스트가 HLSL을 직접 짜지 않고도 식을 만들 수 있게 하는 것이 머티리얼 그래프입니다. 노드(텍스처 샘플, 곱하기, 보간 …)를 선으로 이어 데이터 흐름을 그리면, 엔진이 그것을 셰이더 코드로 바꿉니다.

    핵심은 "그래프를 해석하는 셰이더"를 만드는 것이 아니라, 그래프를 컴파일해서 보통의 HLSL 함수를 생성한다는 점입니다. GPU에서 그래프를 해석하면 노드마다 분기가 생겨 느리지만, 생성된 코드는 손으로 짠 것과 똑같이 최적화됩니다.

    에셋 형식

    그래프는 .emat 안에 "Parameters"(외부에서 바꿀 값)와 "Graph"(노드와 출력)로 들어갑니다.

    "Parameters": [ { "Name": "Speed", "Type": "Scalar", "Value": 0.2 },
                { "Name": "Tint", "Type": "Vector", "Value": [1, 0.5, 0.2, 1] },
                { "Name": "Albedo", "Type": "Texture", "Value": "../Rock.png", "Usage": "Color" },
                { "Name": "UseDetail", "Type": "StaticSwitch", "Value": true } ],
"Graph": { "Nodes": [ { "Id": "uv", "Type": "TexCoord", "Tiling": [2, 2] },
                      { "Id": "rock", "Type": "TextureSample", "Texture": "Albedo", "Inputs": { "UV": "uv" } },
                      { "Id": "tint", "Type": "Multiply", "Inputs": { "A": "rock:1", "B": [1, 0.8, 0.7] } } ],
           "Output": { "BaseColor": "tint", "Roughness": 0.7 } }

    입력은 다른 노드의 출력("노드Id" 또는 "노드Id:출력번호")이거나 상수(숫자 = float1, 배열 = float2~4)입니다. 파라미터는 두 종류로 나뉩니다. Scalar/Vector/Texture는 실행 시간 값이라 상수 버퍼와 텍스처 테이블로 넘어가고, 값을 바꿔도 셰이더는 그대로입니다. StaticSwitch는 컴파일 시간 분기라 값이 다르면 다른 셰이더가 생깁니다 — 꺼진 쪽 노드는 코드에서 완전히 사라지니 비용이 0입니다.

    타입 규칙: 암시적 변환을 거의 허용하지 않는다

    HLSL은 float4를 float3에 넣으면 경고만 내고 뒤 성분을 잘라 버립니다. 노드 그래프에서 이런 일이 조용히 일어나면 아티스트는 왜 색이 이상한지 알 수 없습니다. 그래서 컴파일러는 엄격합니다.

    • 노드 입력은 같은 너비이거나 float1(모든 성분으로 확장)만 허용합니다. 그 밖의 너비 차이는 오류입니다.
    • 예외로 자르기를 허용하는 곳은 두 군데뿐입니다: 머티리얼 출력 핀(float4 → BaseColor float3)과 UV 입력(앞 2성분).
    • 이항 산술의 결과 너비는 두 입력 중 큰 쪽, Dot/Length는 float1, Cross는 float3, Append는 너비 합(≤ 4)입니다.

    공통식 재사용과 결정적 해시

    컴파일러의 핵심은 Local 함수 하나입니다.

    // 지역 변수로 남긴다 (같은 키 = 같은 식이면 이전 변수 재사용)
FValue Local(const std::string& Key, uint32 Width, const std::string& Expression)
{
	const std::string FullKey = std::format("{}#{}={}", Key, Width, Expression);
	if (const auto Found = LocalByKey.find(FullKey); Found != LocalByKey.end())
	{
		return { Found->second, Width };
	}
	const std::string Name = std::format("Local{}", LocalCount++);
	Lines += std::format("\tconst {} {} = {};\n", FloatType(Width), Name, Expression);
	LocalByKey.emplace(FullKey, Name);
	return { Name, Width };
}

    노드 하나를 평가하면 그 결과 식(예: "Local1.xyz * float3(1, 0.8, 0.7)")이 나옵니다. 이 식을 키로 지역 변수를 만들되, 같은 식이 이미 있으면 그 변수를 다시 씁니다. 아티스트가 실수로 같은 텍스처 샘플 노드를 두 개 만들어도 생성 코드에는 샘플이 한 번만 나옵니다. 이것이 컴파일러 용어로 공통 부분식 제거(CSE)입니다.

    더 중요한 것은 변수 이름입니다. 이름이 노드 Id("rock")가 아니라 방문 순서 번호(Local0, Local1 …)입니다. 그래서 노드 Id를 바꾸거나 편집기에서 노드 위치를 옮겨도 생성 문자열이 한 글자도 바뀌지 않습니다. 그 문자열의 FNV-1a 64비트 해시가 곧 셰이더 변형의 키입니다.

    왜 해시가 결정적이어야 하나
    • 공유: 같은 그래프를 쓰는 머티리얼 100개(파라미터만 다른 인스턴스)는 바이트코드와 PSO를 하나만 씁니다.
    • 쿠킹: 해시가 쿠킹 파일명과 셰이더 캐시 키에 들어가므로 ProjectECook이 미리 컴파일해 두면 패키지 게임은 DXC 없이 돕니다. 해시가 실행마다 달라지면 쿠킹이 무의미합니다.
    • 편집기 반응성: 노드를 옮기거나 주석만 고치면 해시가 같으므로 다시 컴파일할 필요가 없습니다(아래 노드 편집기).
    같은 이유로 CLAUDE.md는 편집기 정보(EditorPosition/EditorOutputPosition/EditorComments)가 해시에 영향을 주면 안 된다고 적어 둡니다.

    파라미터 레이아웃

    파라미터 값은 상수 버퍼로 넘어갑니다. 레이아웃 규칙도 결정적이어야 같은 그래프의 인스턴스들이 같은 셰이더를 공유할 수 있습니다: 출력에서 닿는 파라미터만, 선언 순서로, 벡터는 레지스터(float4) 하나씩 먼저, 스칼라는 그 뒤 레지스터에 4개씩 x, y, z, w 순으로 묶고, 텍스처는 테이블 칸 0부터. 스칼라 넷을 한 float4에 몰아 넣는 것은 3부 전반에서 본 16바이트 패킹 규칙 때문입니다.

    ProjectE에서는하나의 함수 EvaluateMaterial

    그래프 머티리얼을 도입하면서 가장 큰 설계 결정은 "모든 머티리얼은 같은 함수 하나로 표면을 낸다"였습니다. 고정 PBR도 예외가 아닙니다 — 기존 식이 MaterialDefault.hlsli 안의 EvaluateMaterial 구현으로 옮겨졌고, 그래프 머티리얼은 디파인 E_MATERIAL_GRAPH와 함께 생성 파일이 같은 이름의 함수를 제공합니다.

    struct FMaterialPixelInputs
{
	float3 WorldPosition;
	float3 WorldNormal;   // 기하(정점) 법선, 정규화
	float4 WorldTangent;  // xyz = +U 방향, w = 바이탄젠트 부호
	float2 UV0;
	float4 VertexColor;
	float3 CameraVector;  // 표면 → 카메라 (정규화)
	float2 PixelPosition; // SV_Position.xy (래스터 전용)
	bool   bFrontFace;
};
struct FMaterialSurface
{
	float3 BaseColor;  float Metallic;  float Roughness;
	float3 Normal;           // 탄젠트 공간 (+Z = 기하 법선)
	float  AmbientOcclusion; float3 Emissive;
	float  Opacity;          // Translucent/Additive 알파
	float  OpacityMask;      // Masked: E_MATERIAL_ALPHA_CUTOFF보다 작으면 버림
};
//   void EvaluateMaterial(in FMaterialPixelInputs In, out FMaterialSurface Out);

    이 구조가 가능한 이유는 텍스처를 읽는 방법을 매크로로 미뤄 둔 것입니다. 래스터 픽셀 셰이더는 화면 미분(ddx/ddy)으로 밉을 자동으로 고르지만, 레이 트레이싱 히트나 계산 셰이더에는 "옆 픽셀"이 없어 미분이 없습니다. 그래서 규칙이 하나 생깁니다: 머티리얼 셰이더에서 ddx/ddy와 .Sample을 직접 쓰지 않고, 텍스처는 MATERIAL_SAMPLE만 쓴다. 메시 패스는 이 매크로를 SampleBias로, RT는 SampleLevel로 정의합니다. 리소스도 마찬가지로 기본은 b2 상수 버퍼와 공간 2 텍스처 테이블이지만, RT는 E_MATERIAL_CUSTOM_RESOURCES를 정의하고 바인드리스 배열 인덱싱으로 바꿉니다.

    Masked 판정도 이 인터페이스 위에서 한 줄입니다. 메인/사전 패스는 clip(Material.OpacityMask - E_MATERIAL_ALPHA_CUTOFF)를 부르고, RT는 any-hit 후보 단계에서 같은 비교로 IgnoreHit합니다.

    셰이더 변형은 어떻게 만들어지나

    MaterialRender::MakeGraphShaderDesc가 엔진 셰이더(Mesh.hlsl의 픽셀 엔트리)에 디파인 E_MATERIAL_GRAPH와 가상 파일 MaterialGraph.generated.hlsli(내용 = 생성 문자열)를 붙여 컴파일 설명을 만듭니다. 셰이더 컴파일러는 #include를 디스크 대신 이 가상 파일에서 찾고, 가상 파일 내용 해시가 캐시 키와 쿠킹 파일명에 들어갑니다. 정점 셰이더는 머티리얼과 무관하게 기본 바이트코드를 씁니다 — 사전 패스와 메인 패스가 같은 VS여야 깊이 EQUAL이 비트 단위로 맞기 때문입니다(19강).

    오류 처리도 보수적입니다. 그래프 컴파일 오류면 이전 셰이더를 유지하고, PSO 생성 실패면 기본 머티리얼로 떨어집니다. 편집 중 잠깐 잘못된 연결을 만들었다고 화면이 깨지면 안 되니까요.

    ProjectE에서는노드 편집기

    Phase 51 사이드에서 imgui-node-editor로 그래프 편집기를 만들었습니다. 구조는 셋으로 나뉩니다.

    • MaterialGraphEditing — 노드 추가·삭제·연결 같은 구조 변경 순수 로직(테스트 MaterialGraphEditorTests). UI는 이 함수만 부릅니다.
    • MaterialGraphPanel — 그리기와 입력. 변경은 그래프 순회가 끝난 뒤 적용하고 OnEdited(라벨, 의미 변경)으로 알립니다. 위치·주석만 바뀌었으면 "의미 변경 = false".
    • MaterialEditor — 에셋 창. 편집마다 Compile + Analyze를 돌려 오류 노드(ErrorNodes)를 빨갛게 표시하고, 미리보기에 반영합니다.

    Analyze는 Compile과 달리 출력에서 닿지 않는 노드까지 모두 평가해 핀마다 너비(핀 색)와 노드별 오류를 얻습니다. 아직 연결하지 않은 노드도 "이 출력은 float3"라고 보여 줄 수 있어야 하니까요. 새 노드 종류는 컴파일러의 노드 표(GetNodeTable)에 범주와 함께 넣기만 하면 팔레트·핀·출력 이름이 자동으로 생깁니다 — 편집기는 GetNodeInfos로 표를 읽을 뿐입니다.

    공유 머티리얼 실시간 반영: 즉시 vs 0.2초 편집기는 씬에서 같은 머티리얼을 쓰는 물체에 변경을 실시간으로 보여 줍니다. 파라미터 값만 바뀌면 셰이더 해시가 같으므로 상수만 다시 올리면 되어 즉시 반영합니다. 구조가 바뀌어 해시가 달라지면 셰이더 컴파일과 PSO 생성이 필요하므로 0.2초 디바운스(마지막 변경 후 0.2초 조용하면 반영)를 겁니다. 슬라이더를 끄는 동안 매 프레임 DXC를 돌리는 일을 막는 것입니다. 컴파일 실패면 반영하지 않습니다.

    함정과 교훈

    "새 메시 패스"가 생길 때마다 반복된 체크리스트 머티리얼 기능은 메시를 그리는 모든 패스에 퍼져 있습니다. Phase 36 이후 CLAUDE.md에는 "새 메시 패스는 변형 8개와 Masked clip을 함께 지원한다", Phase 49 이후에는 "새 메시 패스는 Mesh.hlsl처럼 MaterialCommon.hlsli → 생성 파일/MaterialDefault.hlsli를 include하고, Masked clip = OpacityMask - E_MATERIAL_ALPHA_CUTOFF"가 추가되었습니다. 지형·폴리지·반투명·그림자처럼 패스가 늘 때마다 이 목록을 확인하지 않으면 "어떤 패스에서만 잎이 꽉 찬 사각형" 같은 버그가 납니다. 규칙을 한 곳에 적어 두는 것이 이런 확산형 기능을 지키는 방법입니다.
    기존 화면을 한 픽셀도 바꾸지 않기 고정 PBR 식을 MaterialDefault.hlsli로 옮기는 리팩터링은 위험합니다. 식의 연산 순서가 조금만 달라도 부동소수점 결과가 바뀌어 모든 화면이 미세하게 달라집니다. 그래서 Phase 49 사이드의 완료 기준은 "Demo_Materials·Decals 기준 비트 동일"이었고, CLAUDE.md에도 "MaterialDefault.hlsli(기존 식 — 바꾸면 기존 화면이 바뀐다)"라고 경고가 남아 있습니다. 구조를 바꾸는 작업은 "결과가 비트 단위로 같다"를 검증 기준으로 삼으면 안심하고 진행할 수 있습니다.

    Plans.md에 남은 후속 과제도 머티리얼 시스템의 한계를 잘 보여 줍니다. Masked 텍스처의 밉이 내려가면 알파가 평균되어 먼 잎이 얇아지는 문제(커버리지 보존 밉 필요), 반투명 정렬이 인스턴스 중심 기준이라 서로 교차하는 유리는 틀릴 수 있다는 점, 그래프 UV 채널은 0만 지원한다는 점입니다.

    정리
    • Opaque/Masked는 깊이를 쓰는 불투명 경로(그림자·사전·메인), Translucent/Additive는 불투명 뒤 먼 것부터 정렬된 별도 패스.
    • Masked clip은 모든 불투명 경로에서 같은 식이어야 하고, 블렌드·컬링·스킨은 PSO 변형 3비트(8개)로 고른다.
    • 인스턴스는 파일에 적힌 키(OverrideMask)만 부모 값을 덮어쓰며, Resolve가 체인을 평탄화하고 텍스처 경로를 다시 쓴다.
    • 그래프는 출력에서 닿는 노드만, 엄격한 타입 규칙, 공통식 재사용, 방문 순서 이름으로 결정적 HLSL을 생성하고 그 해시가 변형 키다.
    • 모든 머티리얼은 EvaluateMaterial 하나 + MATERIAL_SAMPLE 매크로로 래스터·그림자·RT·GI가 공유한다.

    생각해 볼 문제

    Q1. Masked 잎을 Translucent로 바꾸면 무엇이 좋아지고 무엇이 나빠질까요? 가장자리가 부드럽게 섞이는 장점이 있지만, 깊이를 쓰지 않으므로 그림자를 드리우지 않고(이 엔진의 반투명은 그림자 패스에 들어가지 않음), 사전 패스에 없어 SSAO/SSR/데칼이 적용되지 않으며, 수천 장의 잎을 먼 것부터 정렬해야 합니다. 서로 교차하는 잎은 인스턴스 중심 정렬로 순서가 틀릴 수도 있습니다. 그래서 잎은 보통 Masked로 둡니다.
    Q2. 지역 변수 이름을 노드 Id로 지으면(const float4 rock = ...) 어떤 문제가 생길까요? 노드 Id만 바꿔도 생성 문자열이 바뀌어 해시가 달라집니다. 의미가 같은 두 머티리얼이 다른 셰이더 변형으로 취급되어 바이트코드·PSO를 공유하지 못하고, 쿠킹된 셰이더도 못 찾습니다. 또 Id에 HLSL에서 쓸 수 없는 글자가 들어가면 컴파일 오류가 납니다. 방문 순서 번호는 이 두 문제를 동시에 없앱니다.
    Q3. 레이 트레이싱 히트 셰이더에서 그래프 머티리얼이 ddx(UV)를 쓰면 어떻게 될까요? 히트 셰이더(또는 RayQuery를 쓰는 셰이더의 광선 처리)에는 이웃 픽셀 개념이 없어 화면 미분이 정의되지 않습니다. 그래서 규칙상 머티리얼 코드는 ddx/ddy와 .Sample을 직접 쓰지 않고 MATERIAL_SAMPLE만 쓰며, RT 쪽은 이 매크로를 광선 원뿔로 고른 LOD의 SampleLevel로 정의합니다.

    왜 필요한가배리어 지옥

    2강에서 보았듯 DirectX 12는 드라이버가 해 주던 일을 앱에 넘깁니다. 그중 가장 손이 많이 가는 것이 리소스 상태(resource state)입니다. GPU는 같은 텍스처라도 "렌더 타깃으로 쓰는 중"과 "셰이더가 읽는 중"에 내부 압축 방식이나 캐시 처리가 다를 수 있습니다. 그래서 용도를 바꿀 때마다 앱이 배리어(barrier)로 "이제 이 리소스를 RENDER_TARGET에서 PIXEL_SHADER_RESOURCE로 바꾼다"고 알려야 합니다. 빠뜨리면 디버그 레이어가 오류를 내거나, 더 나쁘게는 특정 GPU에서만 화면이 깨집니다.

    패스가 셋일 때는 손으로 할 만합니다. 하지만 Phase 46 무렵 ProjectE의 프레임에는 그림자, 사전 패스, SSAO(+블러 2개), 데칼, 볼류메트릭 안개, SSR(+해석), 메인, 안개 적용, 파티클, TAA, 블룸 다운/업, 자동 노출, 톤매핑이 있었고, 로드맵 47~53은 여기에 대기·구름·물·레이 트레이싱·GI·면광원 그림자를 더할 예정이었습니다. 이때 생기는 문제는 이렇습니다.

    • 암묵적 계약: SSAO 패스는 "앞 패스가 깊이 버퍼를 읽기 상태로 바꿔 두었을 것"이라 가정합니다. 누군가 SSAO를 끄거나 순서를 바꾸면 뒤 패스의 가정이 깨집니다.
    • 낭비: 각 패스가 안전하게 "쓰기 전에 전이, 끝나면 원래대로"를 하면 같은 리소스를 왔다 갔다 하는 배리어가 쌓입니다.
    • 죽은 패스: 디버그 뷰가 꺼져 있어 아무도 결과를 읽지 않는 패스도 그대로 돕니다.
    • 메모리: 프레임 안에서 잠깐 쓰는 중간 텍스처를 패스마다 따로 들고 있습니다.

    Plans.md 로드맵은 그래서 렌더 그래프를 맨 앞(Phase 47)에 두었습니다: "49~53이 모두 새 패스 — 나중에 넣으면 전부 다시 옮김".

    핵심 개념선언형 패스와 "프레임 전체를 먼저 보기"

    렌더 그래프(render graph, 프레임 그래프라고도 함)의 발상은 단순합니다. 바로 그리지 말고, 이번 프레임에 할 일을 먼저 전부 적어 둔 다음, 그 목록을 분석해서 실행한다. 각 패스는 두 가지를 제출합니다.

    1. 선언: 이 패스가 GPU에서 어떤 리소스(의 어떤 밉/배열 장)를 어떤 방식으로 읽고 쓰는지. 예: "깊이를 픽셀 셰이더 리소스로 읽고, AO 텍스처를 렌더 타깃으로 쓴다."
    2. 실행 함수(람다): 명령 목록에 그리기 명령을 기록하는 코드. 배리어는 넣지 않습니다.

    모든 패스가 등록되면 컴파일 단계가 선언만 보고 다음을 계산합니다. 어떤 패스가 필요 없는지(컬링), 각 패스 앞에 어떤 전이가 필요한지, 어떤 패스를 다른 큐에서 동시에 돌릴 수 있는지, 중간 리소스가 언제부터 언제까지 살아 있는지. 마지막으로 실행 단계가 계산된 배리어를 넣으며 람다를 차례로 부릅니다.

    이것은 컴파일러가 소스 전체를 본 뒤 최적화하는 것과 같은 구조입니다. 패스 하나하나는 자기 입력과 출력만 알면 되고, 앞뒤 패스가 무엇인지 몰라도 됩니다.

    접근 종류 = D3D12 상태 비트

    // 쓰기 접근(RenderTarget/DepthWrite/Uav/CopyDest)은 서로 배타적이고, 읽기 접근(DepthRead/SrvPixel/SrvNonPixel/CopySource/IndirectArgs)은
// OR로 합칠 수 있다 (한 상태로 여러 종류 읽기).
enum class ERGAccess : uint32
{
	None         = 0,
	RenderTarget = 1u << 0,  // RENDER_TARGET (쓰기)
	DepthWrite   = 1u << 1,  // DEPTH_WRITE (쓰기)
	DepthRead    = 1u << 2,  // DEPTH_READ (깊이 테스트만)
	SrvPixel     = 1u << 3,  // PIXEL_SHADER_RESOURCE
	SrvNonPixel  = 1u << 4,  // NON_PIXEL_SHADER_RESOURCE (계산/정점 셰이더)
	Uav          = 1u << 5,  // UNORDERED_ACCESS (읽기·쓰기)
	...
	AccelStructRead  = 1u << 11, // RayQuery가 TLAS를 읽음 (Phase 50)
	AccelStructWrite = 1u << 12, // 가속 구조 빌드/갱신 대상
};

    읽기 상태끼리는 비트 OR로 합칠 수 있다는 점이 중요합니다. D3D12에서 한 리소스를 동시에 "픽셀 셰이더가 읽고 + 계산 셰이더가 읽는" 상태(PIXEL | NON_PIXEL)로 둘 수 있기 때문입니다. 컴파일러는 이를 이용해 연속된 읽기를 한 번의 전이로 묶습니다.

    눈여겨볼 것이 넷 있습니다.

    1. 리소스의 두 종류. 렌더러가 프레임을 넘어 소유하는 것(AO 결과, 이력 버퍼, 그림자 맵)은 Import로 "빌려" 옵니다. 그래프가 시작 상태와 끝 상태를 알아야 하므로 "평소 상태"를 정해 두었습니다 — 색 타깃(ImportColor)은 평소 SrvPixel, 깊이(ImportDepth)는 평소 DepthWrite. 이 프레임 안에서만 쓰는 중간 버퍼(가로 블러 결과)는 CreateTexture로 그래프 풀에서 받습니다.
    2. bOverwrite. 마지막 인자 true는 "이 쓰기는 이전 내용을 전혀 읽지 않는다(화면 전체를 덮는다)"는 뜻입니다. 컬링 의존을 끊는 데 쓰입니다(아래).
    3. CPU 준비는 등록 시점에. 상수 업로드(ComputeConstants)와 디스크립터 핸들은 AddPass 전에 계산해 두고 람다에는 값으로 캡처합니다. 람다는 명령 기록만 합니다.
    4. 람다 안에서 ResourceBarrier 금지. 렌더 타깃도 전이 없는 Bind로 묶습니다. 전이는 그래프만 합니다.
    규칙: 셰이더가 읽지 않아도 루트에 묶는 리소스는 선언한다 메시 패스는 그림자 맵, SSAO, DBuffer 같은 표를 루트 시그니처에 항상 묶습니다. 어떤 셰이더 변형은 그중 일부를 읽지 않지만, D3D12 디버그 레이어는 그리기 호출 시점에 묶인 리소스의 상태를 검사합니다. 선언을 빠뜨리면 그래프가 전이를 넣지 않아 디버그 레이어 오류가 납니다. 그래서 CLAUDE.md는 "셰이더가 읽지 않아도 루트에 묶는 표·루트 SRV의 리소스도 선언한다"고 적어 둡니다.
    규칙: 람다는 다른 람다가 만든 CPU 데이터에 기대지 않는다 비동기 컴퓨트가 켜지면 그래프는 계산 큐 패스들을 묶어 따로 기록하므로, 람다가 등록 순서와 다른 CPU 순서로 불릴 수 있습니다. "앞 패스 람다가 채운 배열을 뒤 패스 람다가 읽는다" 같은 코드는 이때 깨집니다. CPU 데이터는 전부 등록 시점에 만들고, 지역 변수는 값으로 캡처합니다.

    핵심 개념컴파일: 컬링 · 전이 · 서브리소스 · 수명

    컴파일러(RenderGraphCompiler::Compile)는 GPU를 전혀 모르는 순수 함수입니다. 입력은 리소스 목록(서브리소스 수, 가져온 것인지, 시작/끝 상태)과 패스 목록(큐, 컬링 금지 여부, 접근 목록), 출력은 살아남은 패스, 패스 앞 배리어 묶음, 비동기 묶음, 끝 배리어, 리소스 수명입니다. GPU 없이 테스트할 수 있다는 것이 큰 장점입니다 — RenderGraphTests 12개가 이 함수만 검사합니다.

    ① 컬링

    뿌리(root)는 "외부에 흔적을 남기는 패스"입니다. 가져온 리소스(백버퍼, 이력 버퍼처럼 다음 프레임이나 화면이 볼 것)에 쓰는 패스, 그리고 통계·리드백처럼 부수 효과만 있어 명시적으로 NeverCull()을 붙인 패스입니다. 살아 있는 패스가 읽는 서브리소스마다 직전에 그것을 쓴 패스를 찾아 살리고, 이를 반복합니다.

    여기서 bOverwrite가 쓰입니다. 쓰기는 보통 "이전 내용을 읽는 것"으로 간주합니다 — 블렌딩, 부분 갱신, UAV 누적은 이전 값을 읽으니까요(보수적). 그런데 전체 화면을 덮어쓰는 패스까지 그렇게 보면, 그 이전 쓰기 패스가 쓸데없이 살아납니다. bOverwrite는 "여기서 의존이 끊긴다"를 알려 줍니다.

    ② 상태 전이와 읽기 합치기

    서브리소스마다 현재 상태를 추적하며 패스가 필요로 하는 상태와 다르면 그 패스 앞에 전이를 넣습니다. 이때 look-ahead를 합니다: 읽기 상태로 바꿀 때, 다음 쓰기 전까지 이어지는 모든 읽기를 미리 모아(예: SrvPixel | SrvNonPixel) 한 번에 그 합친 상태로 전이합니다. 같은 UAV를 연속 패스가 쓰면 상태 전이 대신 UAV 배리어를 넣습니다. 그리고 리소스의 모든 서브리소스가 같은 전/후 상태로 바뀌면 ALL_SUBRESOURCES 배리어 하나로 묶습니다. 마지막으로 한 패스 앞의 배리어들은 ResourceBarrier 호출 한 번에 담깁니다.

    ③ 서브리소스

    블룸 다운샘플은 같은 텍스처의 밉 0을 읽어 밉 1에 쓰고, 다시 밉 1을 읽어 밉 2에 씁니다. "텍스처 전체"를 단위로 상태를 추적하면 이것을 표현할 수 없습니다. 그래서 접근은 FRGSubresourceRange(밉 범위 × 배열 장 범위)로 선언하고, 컴파일러는 서브리소스(= 밉 + 장 × 밉 수)마다 따로 상태를 추적합니다. 점광원 그림자 큐브의 면 6장도 같은 방식입니다.

    ④ 가속 구조는 예외 (Phase 50)

    레이 트레이싱의 BLAS/TLAS 버퍼는 만들 때부터 RAYTRACING_ACCELERATION_STRUCTURE 상태 하나뿐이고 다른 상태로 전이할 수 없습니다. 그래서 규칙 2.5가 추가되었습니다: AS 접근끼리는 전이를 만들지 않고, 쓰기가 끼면(빌드 → 읽기) UAV 배리어를 넣습니다. 다른 접근과 섞어 선언하면 오류입니다.

    ⑤ 수명

    리소스마다 실행 타임라인상 첫 사용과 마지막 사용 패스를 기록합니다. 지금은 통계·덤프에만 쓰지만, 이것이 "메모리 별칭"의 재료입니다 — 수명이 겹치지 않는 두 중간 텍스처는 같은 메모리를 나눠 쓸 수 있습니다(placed resource). Phase 47 결정에서 이것은 2차 작업으로 미뤘습니다.

    ImportTracked는 "한 번에 이전"하는 과정에서 생긴 다리입니다. Phase 47 이전 코드 중에는 리소스 상태를 멤버 변수 하나로 추적하며 그래프 밖에서도 쓰는 것들이 있었습니다. 이들을 강제로 평소 상태 규칙에 맞추지 않고, 그래프가 시작 상태를 그 변수에서 읽고 끝에 다시 써 주게 해서 그래프 안팎이 같은 진실을 보게 했습니다.

    풀링: CreateTexture는 크기·형식·플래그가 모두 같은 항목을 FRGResourcePool에서 재사용합니다. 프레임마다 텍스처를 만들고 지우면 할당 비용과 디스크립터 낭비가 크기 때문입니다. 60프레임 동안 안 쓴 항목은 Trim이 지연 해제합니다. 그래서 규칙: 프레임 안 중간 버퍼는 직접 만들지 않는다.

    컴파일 캐시: 대부분의 프레임은 지난 프레임과 똑같은 그래프입니다. 풀은 입력(리소스 설명·시작 상태·패스 선언·옵션)을 키로 최근 8개 컴파일 결과를 기억해 두고, 같으면 컴파일을 건너뜁니다. 통계 창의 bCompileCached가 이것입니다.

    핵심 개념비동기 컴퓨트 — 포크와 조인

    GPU에는 그래픽스 큐 말고 계산 전용 큐가 따로 있습니다. 그림자 맵을 그리는 동안(정점 처리·래스터라이저가 바쁘고 셰이더 유닛은 놀 수 있음) 계산 셰이더 작업을 다른 큐에 넣으면 둘이 겹쳐서 실행될 수 있습니다. 이것이 비동기 컴퓨트(async compute)입니다.

    컴파일러 규칙 3이 이것을 정합니다. 등록 순서상 연속한 살아 있는 AsyncCompute 패스들이 묶음 하나가 되고, 포크는 "묶음보다 앞에 등록된 그래픽스 패스 중 묶음과 충돌하는 마지막 패스 뒤", 조인은 "뒤에 등록된 그래픽스 패스 중 충돌하는 첫 패스 앞"입니다. 까다로운 점은 계산 큐가 할 수 없는 전이입니다. 계산 큐 명령 목록은 픽셀 셰이더·렌더 타깃·깊이 상태로(에서) 전이할 수 없으므로, 묶음이 처음 쓰는 상태로의 전이는 포크 앞 그래픽스 큐에서 해 두고, 묶음 안에서는 계산 큐 합법 상태(SrvNonPixel/Uav/Copy*)만 다룹니다. 그래서 비동기 후보 패스는 이 상태만 선언해야 합니다. 그리고 뒤 묶음의 포크가 앞 묶음의 조인보다 앞이면 두 묶음을 하나로 합쳐 제출 수를 줄입니다.

    함정과 교훈

    비동기 컴퓨트는 동작했지만 기본으로 껐다 Phase 47의 완료 기준에는 "컴퓨트 큐로 옮긴 패스 1개 이상 겹쳐 실행"이 있었고, 구현은 동작했습니다. 그런데 측정해 보니 이 GPU(RTX 3060 Laptop)에서는 이득이 없었습니다: Showcase 5.77 → 5.92ms로 오히려 느려졌습니다. 계산 큐로 넘기려면 명령 목록을 중간에 제출하고 큐 사이 펜스를 걸어야 하는데, 그 제출 비용이 겹침 이득보다 컸던 것입니다. 그래서 r.RenderGraph.AsyncCompute 기본값은 0이고, CLAUDE.md에는 "새 계산 패스를 넣으면 --async-compute로 다시 잰다"는 규칙이 남았습니다. 기능을 만들었다고 켜지 않고, 숫자가 이득을 보일 때만 켭니다.
    "패스별 단계 이전" 계획을 버리고 한 번에 이전 원래 계획은 기존 리소스를 Import로 받아 들여 패스를 하나씩 옮기고 패스마다 화면을 확인하는 것이었습니다. 실제로 해 보니 하위 렌더러들이 "앞 패스가 이 상태로 남겨 두었을 것"이라는 가정으로 얽혀 있어서, 하나만 옮기면 그 가정이 깨졌습니다. 결국 한 번에 이전했고(Plans.md 후속 기록), 대신 검증 기준을 엄격하게 잡았습니다: 정적 데모 8개가 비트 단위로 동일, 프레임·GPU 시간 동일(렌더 CPU +0.02~0.09ms). 그래프는 "어떻게 그리는지"를 바꾸지 않고 "언제 전이하는지"만 바꾸므로 결과 화면이 한 비트도 달라지면 안 된다는 것이 명확한 기준이 되었습니다.
    엔티티마다 그래프 리소스를 가져오면 안 된다 Phase 50에서 스킨 메시 레이 트레이싱을 붙이며 남긴 기록입니다. 엔티티마다 정점 버퍼와 BLAS를 그래프에 가져오면, 같은 리소스를 이미 가져왔는지 찾는 FindImported가 선형 탐색이라 3600개에서 CPU가 20ms 이상 듭니다. 해결은 정점·BLAS를 큰 풀 버퍼 2개에 하위 할당해 "엔티티 수와 무관하게 그래프 리소스는 2개"로 만든 것입니다(25강). 그래프는 리소스 수십~수백 개 규모를 가정한 도구이고, 수천 개의 작은 리소스는 풀로 묶어 넣어야 합니다.

    디버깅 도구도 같이 만들었습니다. r.RenderGraph.Dump는 패스 순서·큐·제거된 패스·전이 수·포크/조인·리소스 수명을 로그로 남기고, 통계 창의 "렌더 그래프" 칸은 패스/전이/풀 메모리를 보여 줍니다. 컬링이 의심되면 --cvar r.RenderGraph.Cull=0으로 꺼서 비교합니다.

    정리
    • D3D12는 리소스 용도가 바뀔 때마다 배리어가 필요하고, 패스가 많아지면 손 관리가 깨지기 쉽고 낭비가 생긴다.
    • 렌더 그래프 = 패스가 읽기/쓰기를 선언 → 컴파일(컬링, look-ahead 전이, 서브리소스, 수명) → 실행(람다는 기록만).
    • 렌더러 소유 리소스는 Import(평소 상태), 중간 버퍼는 CreateTexture(풀링), 상태를 직접 추적하던 것은 ImportTracked.
    • 비동기 컴퓨트는 포크/조인과 계산 큐 합법 상태로 구현했지만, 측정 결과 이득이 없어 기본 끔.
    • 구조 변경의 검증 기준은 "화면 비트 동일 + 시간 동일".

    생각해 볼 문제

    Q1. 전체 화면 패스가 출력에 bOverwrite를 빠뜨리면 어떤 일이 생길까요? 결과 화면은 같습니다. 하지만 컴파일러가 그 쓰기를 "이전 내용을 읽는다"고 보수적으로 간주하므로, 같은 리소스에 앞서 쓴 패스(예: 지난 단계의 클리어나 다른 패스)가 불필요하게 살아남을 수 있습니다. 즉 성능만 손해이고 정확성은 지켜집니다. 그래서 기본값을 보수적인 쪽으로 둔 것입니다.
    Q2. 패스 A가 텍스처를 SrvPixel로, 바로 다음 패스 B가 같은 텍스처를 SrvNonPixel로 읽습니다. 손으로 하면 전이가 몇 번, 그래프는 몇 번일까요? 손으로 각 패스가 자기 상태로 바꾸면 A 앞에 1번, B 앞에 1번(PIXEL → NON_PIXEL)으로 2번입니다. 그래프는 look-ahead로 다음 쓰기 전까지 이어지는 읽기를 합쳐 A 앞에서 PIXEL | NON_PIXEL 상태로 1번만 전이합니다.
    Q3. 계산 큐로 보내려는 패스가 깊이 버퍼를 DepthRead로 선언했습니다. 왜 문제일까요? 계산 큐 명령 목록은 깊이·렌더 타깃·픽셀 셰이더 리소스 상태로의 전이를 할 수 없고, 그 상태를 전후 상태로 쓰는 배리어도 기록할 수 없습니다. 비동기 후보 패스는 계산 큐 합법 상태(SrvNonPixel/Uav/Copy*)만 선언해야 합니다. 계산 셰이더가 깊이를 읽어야 한다면 SrvNonPixel로 선언하고, 그 전이는 포크 앞 그래픽스 큐에서 이루어집니다.

    업스케일링과 동적 해상도

    관련 Phase: 48 · 살펴볼 곳: Renderer/UpscaleMath.h, Renderer/DynamicResolution.h, Engine/Shaders/TemporalAA.hlsl(PSResolveUpsample), Renderer/SceneRenderer.cpp(지터·밉 바이어스), Renderer/RendererConsoleVariables.cpp
    이 강의를 마치면
    • 내부 해상도와 출력 해상도를 나누는 이유와, 픽셀 수가 GPU 비용에 미치는 영향을 설명할 수 있습니다.
    • 시간 업샘플링(TAAU)이 지터와 이력 누적으로 해상도를 "되살리는" 원리와, 지터 표본 수를 늘려야 하는 이유를 압니다.
    • 어떤 패스가 내부 해상도이고 어떤 패스가 출력 해상도인지 나누는 규칙과 텍스처 밉 바이어스를 이해합니다.
    • 동적 해상도 제어기의 평활·히스테리시스·단계 설계와 그 대가(재할당 끊김)를 압니다.

    왜 필요한가픽셀 수는 비용이다

    현대 렌더러의 비용 상당 부분은 "픽셀마다" 드는 일입니다. 메인 패스의 조명 계산, SSAO, SSR, 안개, 레이 트레이싱 반사는 모두 화면 픽셀 수에 비례합니다. 1440p(2560×1440)는 약 369만 픽셀이고, 같은 화면을 67%로 그리면(1715×965) 약 166만 픽셀 — 면적은 0.67² ≈ 45%입니다. 비율이 아니라 비율의 제곱으로 줄어드는 것이 핵심입니다.

    문제는 그냥 작게 그려서 늘리면 흐릿하다는 것입니다. 쌍선형 확대는 없는 정보를 만들어 내지 못합니다. 그런데 20강의 TAA를 떠올려 보세요. TAA는 매 프레임 카메라를 픽셀 미만으로 살짝 흔들고(지터), 지난 프레임 결과(이력)와 섞어 여러 프레임에 걸친 표본을 모읍니다. 정지 화면이라면 8프레임 동안 픽셀 하나 안의 서로 다른 8곳을 본 셈입니다. 그렇다면 이력을 출력 해상도로 들고, 저해상도 프레임의 표본을 출력 픽셀 격자 위 정확한 위치에 누적하면 해상도를 되살릴 수 있지 않을까요? 이것이 TAAU(Temporal Anti-Aliasing Upsampling)이고, DLSS·FSR·XeSS 같은 업스케일러의 공통 바탕입니다.

    Phase 48 결정은 "업스케일러 = 자체 TAAU"였습니다. 외부 업스케일러 SDK 대신 이미 있는 TAA를 확장한 것입니다.

    핵심 개념TAAU — 지터된 저해상도 표본을 출력 격자에 모으기

    TAAU의 해석(resolve) 단계는 출력 해상도에서 돕니다. 출력 픽셀 하나를 계산할 때 하는 일은 이렇습니다.

    1. 이 출력 픽셀 중심이 이번 프레임의 지터된 내부 영상에서 어디에 해당하는지 계산합니다: InputPos = (UV + JitterUv) × InputSize.
    2. 그 주변 내부 픽셀 3×3을 읽고, 각 표본과 출력 픽셀 중심 사이 거리(출력 픽셀 단위)로 가우시안 가중치를 줍니다. 가까운 표본은 크게, 먼 표본은 작게. 이것이 "이번 프레임 값"입니다.
    3. 가장 큰 가중치를 신뢰도로 기억합니다. 이번 프레임에 이 출력 픽셀 바로 위에 떨어진 표본이 있으면 신뢰도가 높고, 없으면 낮습니다.
    4. 움직임 벡터로 이력을 재투영해 읽고, 3×3 이웃의 평균·분산 상자로 잘라(20강의 분산 클램프) 섞습니다. 섞는 비율에 신뢰도를 곱해 — 표본이 정확히 떨어진 픽셀만 이번 값을 많이 받아들입니다.
    const float2 InputPos = (Input.UV + JitterUv) * InputSize;
...
	const float2 DeltaInput  = float2(Base + int2(X, Y)) + 0.5f - InputPos; // 내부 픽셀 단위
	const float2 DeltaOutput = DeltaInput * UpsampleScale;                    // 출력 픽셀 단위
	const float  Sharp       = exp(-2.29f * dot(DeltaOutput, DeltaOutput));
	const float  Smooth      = exp(-2.29f * dot(DeltaInput, DeltaInput));
	SharpSum += Value * Sharp;  SharpWeight += Sharp;
	Confidence = max(Confidence, Sharp);
...
float Weight = lerp(CurrentWeight, ReactiveWeight, Reactive);
Weight = lerp(Weight, max(Weight, 0.25f), Fast);
Weight *= lerp(Confidence, 1.0f, max(Reactive, Fast));   // 표본 신뢰도
const float3 Result = lerp(Clipped, Current, Weight);

    Sharp와 Smooth 두 가중치가 있는 이유도 볼 만합니다. 이력이 없는 첫 프레임이나 화면 밖에서 들어온 픽셀은 누적할 과거가 없습니다. 이때는 출력 픽셀 단위의 날카로운 가중치를 쓰면 표본이 없는 자리에 구멍 같은 계단이 생기므로, 내부 픽셀 단위의 부드러운 가중치(Smooth)로 그냥 보간한 값을 씁니다. 반응형 마스크(파티클·반투명)와 빠른 움직임에서는 신뢰도 영향을 줄입니다 — 번지는 것보다 반응하는 쪽이 낫기 때문입니다. 지수 -2.29는 블랙맨-해리스 필터를 가우시안으로 근사한 값으로, FUpscaleMath::SampleWeight에 같은 식이 있고 테스트 UpscaleTests가 둘을 맞춥니다.

    네이티브 100%는 예전 경로 그대로 화면 비율이 100%일 때는 업샘플 셰이더(PSResolveUpsample)가 아니라 원래 TAA 해석(PSResolve)을 탑니다. TAAU 상수는 PSResolve가 읽지 않습니다. 그래서 Phase 48의 완료 기준은 "네이티브 비트 동일"이었고, CLAUDE.md에도 "네이티브 100%는 Phase 47 화면과 비트 동일해야 한다(PSResolve 경로 유지)"로 남았습니다. 새 기능을 넣을 때 "꺼져 있으면 예전과 비트 동일"을 보장하는 습관은 이 부 전체에서 반복됩니다.

    핵심 개념패스마다 해상도가 정해져 있다

    TAAU를 넣으면 프레임 안에 크기가 다른 버퍼 두 무리가 생깁니다. 어떤 패스가 어느 쪽인지 섞이면, 예를 들어 출력 크기 블룸 버퍼를 내부 크기 씬 컬러와 같은 UV로 읽으면 화면이 미묘하게 어긋납니다.

    규칙이 "크기는 SceneColor에서만 얻는다"인 이유는, 화면 비율이 프레임마다 바뀔 수 있기 때문입니다(동적 해상도). 창 크기를 들고 다니며 각자 비율을 곱하면 반올림이 패스마다 달라질 수 있습니다. 한 곳(FUpscaleMath::ComputeInternalDimension — 반올림, 1 이상, 출력 이하)에서 계산한 SceneColor 크기를 모두가 따르면 어긋날 일이 없습니다.

    오버레이 깊이는 재미있는 문제입니다. 에디터 그리드는 씬 깊이로 깊이 테스트를 해야 물체 뒤로 숨는데, 씬 깊이는 내부 해상도이고 지터되어 있습니다. 그래서 TAAU 단계에 PSUpscaleDepth를 두어 지터를 되돌리며 출력 해상도로 깊이를 옮깁니다. 평면 위에서 장치 깊이는 화면 공간에서 선형이라 쌍선형 보간이 정확하고, 윤곽(네 표본의 1/z 상대 차가 큼)에서는 보간하지 않고 가장 가까운 표본을 씁니다 — 물체 가장자리에 중간 깊이의 "유령 면"이 생기지 않게.

    핵심 개념텍스처 밉 바이어스

    GPU는 화면 픽셀 하나가 텍스처에서 몇 텍셀을 덮는지(화면 미분)로 밉을 고릅니다. 내부 해상도가 67%면 픽셀 하나가 덮는 텍스처 면적이 더 크니, GPU는 더 흐린 밉을 고릅니다. 하지만 TAAU는 결국 출력 해상도 영상을 만들어 내므로, 텍스처도 출력 해상도에서 본 것처럼 선명해야 합니다. 그래서 밉 선택을 한쪽으로 미는 바이어스를 줍니다.

    // 텍스처 밉 바이어스: 내부가 출력보다 작을 때만 log2(내부/출력) + Offset (Offset은 음수 쪽 = 더 선명).
// 같거나 크면 0 (네이티브와 비트 동일)
static float ComputeMipBias(uint32 InternalHeight, uint32 OutputHeight, float Offset)
{
	if (InternalHeight == 0 || OutputHeight == 0 || InternalHeight >= OutputHeight)
	{
		return 0.0f;
	}
	return std::log2(static_cast<float>(InternalHeight) / static_cast<float>(OutputHeight)) + Offset;
}

    67%라면 log2(0.67) ≈ −0.58에 보정 r.Upscale.MipBiasOffset(기본 −0.3)를 더해 약 −0.88밉 더 선명하게 읽습니다. 이 값은 PerFrame 상수 MaterialMipBias로 올라가고, 21강에서 본 MATERIAL_SAMPLE 매크로가 래스터 메시 패스에서 SampleBias(..., MaterialMipBias)가 됩니다. 머티리얼 코드가 .Sample을 직접 쓰지 않는다는 규칙 덕분에 모든 머티리얼에 한 번에 적용된 것입니다. 너무 음수로 밀면 이번에는 텍스처가 지글거리므로(20강), 보정값은 CVar로 열어 두었습니다.

    핵심 개념동적 해상도 — GPU 시간을 목표에 맞추는 제어기

    화면 비율을 고정하는 대신 부하에 따라 바꾸면 어떨까요? 장면이 무거울 때만 해상도를 낮추면 프레임 시간을 일정하게 지킬 수 있습니다. 이것이 동적 해상도이고, 본질은 제어 문제입니다. 입력은 측정된 GPU 시간, 출력은 화면 비율. 잘못 설계하면 해상도가 매 프레임 오르내리며(진동) 화면이 출렁입니다.

    //   - 지수 평활(Smoothing) 값으로 판단한다 (한 프레임 튐에 반응하지 않음)
//   - 예산 초과(평활 > 목표 × DecreaseThreshold)면 줄이고, 여유(평활 < 목표 × IncreaseThreshold)면 늘린다 (그 사이는 유지 = 히스테리시스)
//   - 새 비율 = 현재 × sqrt(목표 × Headroom / 평활) (GPU 비용 ∝ 픽셀 수 ∝ 비율²) → Step(%) 단위로 반올림 → [Min, Max]
//   - 바꾼 뒤 MinFramesBetweenChanges 동안은 다시 바꾸지 않는다 (타이머 지연 + 평활이 따라올 시간). 크게 넘으면(×UrgentThreshold) 1/3만 기다린다
//   - 바꿀 때 평활 값을 예측치(× (새/옛)²)로 옮겨 다음 판단이 옛 측정에 끌려가지 않게 한다
struct FDynamicResolutionSettings
{
	float  TargetGpuMs             = 16.6f;
	float  MinPercentage           = 50.0f;
	float  StepPercentage          = 5.0f;
	uint32 MinFramesBetweenChanges = 30;
	float  Smoothing               = 0.1f;
	float  DecreaseThreshold       = 1.0f;
	float  IncreaseThreshold       = 0.85f;
	float  Headroom                = 0.92f;
	float  UrgentThreshold         = 1.3f;
	...
};

    설계 요소를 하나씩 보면 모두 진동과 싸우는 장치입니다.

    • 측정 지연: GPU 시간은 타이머 쿼리로 재므로 몇 프레임 늦게 도착합니다. 바꾸자마자 다시 판단하면 아직 반영되지 않은 옛 측정으로 또 바꿉니다 → 대기 프레임(30).
    • 평활: 한 프레임 튐(셰이더 컴파일, 폭발 이펙트)에 반응하지 않도록 지수 평활(새 표본 비중 0.1).
    • 히스테리시스: 줄이는 문턱(목표 × 1.0)과 늘리는 문턱(목표 × 0.85)을 다르게 해 경계에서 왔다 갔다 하지 않게.
    • 모델 기반 점프: 비용이 비율의 제곱에 비례한다고 보고 √(목표/측정)를 곱해 한 번에 목표 근처로 갑니다. 목표의 92%(Headroom)를 노려 바로 다시 넘지 않게 합니다.
    • 이산 단계: 5% 단위로만 바꿉니다. 이유는 바로 다음 절의 비용입니다.

    함정과 교훈

    해상도를 바꾸는 순간의 끊김 동적 해상도는 기본으로 꺼 두었습니다. 단계가 바뀌는 프레임에 15~20ms 끊김이 생기기 때문입니다. 내부 해상도 리소스(씬 컬러, 깊이, 법선, 움직임 벡터, SSAO, SSR 이력 …)를 크기별로 다시 만들기 때문입니다. 해상도를 매끄럽게 바꾸려면 최대 해상도로 한 번 할당해 두고 그 안의 하위 사각형만 쓰거나(뷰포트만 바꾸기), 22강에서 미룬 placed 힙 별칭이 필요합니다 — Plans.md 후속 과제로 남아 있습니다. 5% 단계는 이 비싼 재할당이 너무 자주 일어나지 않게 하는 타협이기도 합니다.
    규칙: 내부 크기 버퍼의 이력은 스스로 버린다 시간 이력의 연속성은 출력 크기를 기준으로 판단합니다(출력 크기가 같으면 연속). 그런데 SSR·RT 그림자처럼 이력을 내부 크기 버퍼에 두는 효과는 해상도 단계가 바뀌면 버퍼가 새로 만들어지므로, 이전 이력을 그대로 섞으면 안 됩니다. CLAUDE.md: "내부 크기 버퍼에 이력을 두는 효과는 버퍼 재생성 때 스스로 버린다."

    마지막으로, 지터를 어디에 거느냐도 함정이었습니다. 지터는 씬 컬러에 그리는 패스(메시, 파티클)의 투영에만 겁니다. 그림자 캐스케이드, 클러스터, 컬링, LOD 선택은 지터 없는 카메라를 씁니다 — 그림자 맵이 매 프레임 반 픽셀씩 흔들리면 그림자 가장자리가 떨리기 때문입니다(SceneRenderer.cpp 주석).

    생각해 볼 문제

    Q1. 50%에서 지터 표본을 8개만 쓰면 정지 화면에서 어떤 무늬가 보일 수 있을까요? 내부 픽셀 하나가 출력 픽셀 4개를 덮으므로 8개 표본이면 출력 픽셀마다 평균 2개, 그것도 고르지 않게 떨어집니다. 표본이 거의 안 떨어지는 출력 픽셀은 신뢰도가 낮아 이웃 값에 의존하므로, 출력 격자에 맞물린 규칙적인 흐림·계단 무늬가 남을 수 있습니다. 그래서 면적비만큼(50%면 32개) 늘립니다.
    Q2. 동적 해상도에서 DecreaseThreshold와 IncreaseThreshold를 둘 다 1.0으로 하면 어떻게 될까요? 목표 근처에서 측정값이 조금만 흔들려도 줄였다 늘렸다를 반복합니다(진동). 매 변경마다 리소스 재할당 끊김(15~20ms)이 생기므로 오히려 프레임이 나빠집니다. 두 문턱 사이의 "유지 구간"이 이것을 막습니다.
    Q3. 새 화면 공간 효과가 창 크기에 화면 비율을 직접 곱해 자기 버퍼 크기를 정했습니다. 무엇이 문제일까요? 반올림 방식이 ComputeInternalDimension(반올림, 1 이상, 출력 이하)과 다르면 SceneColor와 1픽셀 차이가 나서 UV가 어긋나고, 동적 해상도가 비율을 바꾼 프레임에는 다른 패스와 다른 값을 볼 수도 있습니다. 규칙대로 크기는 RenderSceneColor의 Width/Height(SceneColor 크기)에서만 얻어야 합니다.

    핵심 개념산란과 투과율

    빛이 공기를 지나가면 두 가지 일이 일어납니다.

    • 소멸(extinction): 일부는 흡수되거나 옆으로 튕겨 나가 원래 방향의 빛이 줄어듭니다. 거리 d를 지난 뒤 남는 비율이 투과율 T = exp(−σt · d)입니다(비어-람베르트 법칙). σt는 소멸 계수(단위 1/km)이고, 밀도가 고도에 따라 변하면 지수 안이 ∫σt(x)dx — 이것을 광학 깊이라 부릅니다.
    • 내산란(in-scattering): 반대로 다른 방향에서 오던 햇빛이 이 점에서 튕겨 내 눈 방향으로 들어옵니다. 하늘이 밝은 이유는 바로 이것입니다. 대기가 없으면 하늘은 검습니다(달 표면처럼).

    핵심 개념LUT로 나누기 — Hillaire 2020

    그림 24-1의 적분을 픽셀마다 그대로 하면 시선 위 점 수십 개 × 각 점에서 태양까지 투과율(또 적분 수십 걸음)이라 너무 비쌉니다. 게다가 빛이 여러 번 튕기는 다중 산란까지 넣으면 더 커집니다. ProjectE는 Hillaire의 논문 "A Scalable and Production Ready Sky and Atmosphere Rendering Technique"(2020) 방식을 따라, 계산을 작은 표 세 장으로 나눕니다.

    1. 투과율 LUT: "고도 h에서 천정각 θ 방향으로 대기 끝까지 가면 얼마나 남나"는 태양 위치와 무관한 순수 기하라 한 번 계산해 두면 됩니다. 표 좌표는 Bruneton의 매개화(지평선 근처를 촘촘하게)를 씁니다.
    2. 다중 산란 LUT: 두 번 이상 튕긴 빛은 방향 정보가 흐려지므로 등방(모든 방향 같음)으로 근사하고, Hillaire의 식으로 무한 번 산란의 합을 기하급수 1/(1 − fms)로 닫습니다. 8×8 = 64 방향, 20걸음으로 적분합니다.
    3. 하늘 뷰 LUT: 카메라 고도에서 본 하늘 전체를 (시선 천정각, 태양 기준 방위)로 펼친 저해상도 표. 지평선 근처 색 변화가 급하므로 천정각 축을 지평선 쪽으로 촘촘하게 둡니다. 하늘 배경과 IBL 큐브는 이 표를 읽습니다.

    CPU 쪽 식도 같이 있습니다. 아래는 투과율의 정의 그대로입니다 — 광선을 구와 교차시켜 대기 끝(또는 지면)까지의 거리를 구하고, 걸음마다 그 고도의 소멸 계수를 더해 광학 깊이를 만든 뒤 exp(−광학 깊이).

    inline FVector3 ComputeTransmittanceToTop(const FParams& Params, float ViewHeight, float ViewZenithCos, uint32 Steps = TransmittanceSteps)
{
	const FVector3 Origin(0.0f, 0.0f, ViewHeight);
	const FVector3 Direction(std::sqrt(FMath::Max(1.0f - ViewZenithCos * ViewZenithCos, 0.0f)), 0.0f, ViewZenithCos);
	const float    TBottom = RaySphereIntersectNearest(Origin, Direction, Params.BottomRadius);
	const float    TTop    = RaySphereIntersectNearest(Origin, Direction, Params.TopRadius);
	...
	FVector3    OpticalDepth = FVector3::ZeroVector;
	const float Dt           = TMax / static_cast<float>(Steps);
	for (uint32 Step = 0; Step < Steps; ++Step)
	{
		const FVector3 P = Origin + Direction * ((static_cast<float>(Step) + 0.5f) * Dt);
		OpticalDepth += SampleMedium(Params, P.Length() - Params.BottomRadius).Extinction * Dt;
	}
	return Exp(-OpticalDepth);
}

    단위 경계: 대기 안은 km

    엔진의 단위는 1 = 1cm입니다. 그런데 대기 두께는 100km = 107cm, 행성 반지름은 6360km = 6.36 × 108cm입니다. float(유효 숫자 약 7자리)로 cm 단위 행성 좌표를 다루면 표면 근처의 cm 차이가 반올림에 먹힙니다. 그래서 대기 안은 km, 계수는 1/km로 계산하고, 엔진 월드와의 변환은 FAtmosphereMath::WorldToAtmosphere로만 합니다. 월드 Z = 0이 행성 표면이고 행성 중심은 원점 아래 6360km에 있습니다. 4강에서 본 "단위 변환은 경계에서만" 규칙(FUnits)을 그대로 따릅니다.

    공중 원근 (aerial perspective)

    먼 산이 파랗고 흐린 것은 산과 나 사이의 공기가 산의 빛을 줄이고(투과율) 하늘빛을 더하기(내산란) 때문입니다. 장면 크기(수 km 이하)에서는 행성의 곡률을 무시할 수 있으므로, ProjectE는 "평평한 지면 + 지수 밀도 + 카메라 고도의 태양 투과율 상수"로 놓고 닫힌 식으로 적분합니다(ComputeAerialPerspective). 이 식은 Fog.hlsli의 EvaluateFog 안에 들어갔고, 순서는 표면 → 공중 원근 → 높이 안개 → 볼류메트릭 안개입니다. 불투명(안개 적용 패스), 반투명, 파티클, 물, 구름이 모두 같은 함수를 부르므로 어떤 물체든 같은 거리에서 같은 공기감을 가집니다. 그래서 규칙: 새 반투명·볼륨 패스도 EvaluateFog를 쓴다.

    태양과 달

    씬의 첫 방향광이 태양입니다. FSkyAtmosphereRenderer::ApplyToDirectionalLight가 방향광 색에 "카메라 고도에서 태양 방향 투과율"을 곱하므로, 해가 낮아지면 그림자를 만드는 직사광 자체가 붉어집니다(bAffectSunLight). 태양이 지평선 아래로 지면 방향광은 태양 반대편의 달(MoonIntensity 0.25, 푸른 달빛 색)로 바뀌고, 밤하늘 최소 휘도(NightSkyColor)와 별이 더해집니다. 방향광을 읽는 새 코드는 원래 컴포넌트 값이 아니라 대기가 반영된 PerFrame.DirectionalLight를 읽어야 합니다.

    실시간 IBL

    하늘이 바뀌면 환경광도 바뀌어야 합니다. bRealtimeEnvironmentLighting이 켜져 있으면 대기(+구름)로 하늘 큐브를 다시 그리고 조도·프리필터 맵(17강)을 다시 적분합니다. 이것을 한 프레임에 다 하면 끊기므로 3단계로 시간 분산하고 이중 버퍼로 둡니다 — 새 결과가 완성될 때까지 셰이더는 이전 완성본을 읽습니다. FIblRenderer::GetLightingTable()이 이 덮인 표를 돌려주므로, 조명 표를 쓰는 패스는 항상 이 함수로 얻습니다. 26강의 DDGI도 빗나간 광선의 하늘빛을 여기서 읽습니다.

    핵심 개념볼류메트릭 구름 — 레이마칭

    구름은 표면이 없는 부피입니다. 삼각형으로 그릴 수 없으므로, 픽셀마다 시선 광선을 구름층 안에서 조금씩 전진(레이마칭)하며 각 점의 밀도를 노이즈로 계산하고, 그 점이 받는 햇빛과 남은 투과율을 누적합니다.

    식은 CloudMath.h(CPU 참조)와 VolumetricClouds.hlsl이 같고, 테스트 Cloud_*가 묶습니다. 핵심 부품은 이렇습니다.

    // 기본 모양 밀도: 모양 노이즈(펄린-워리 R + 워리 FBM) × 높이 기울기 → 덮임 잘라내기
inline float BaseDensity(float PerlinWorley, float WorleyFbm, float Gradient, float Coverage)
{
	const float Shape   = Saturate(Remap(PerlinWorley, WorleyFbm - 1.0f, 1.0f, 0.0f, 1.0f)) * Gradient;
	const float Covered = Saturate(Remap(Shape, 1.0f - Saturate(Coverage), 1.0f, 0.0f, 1.0f));
	return Covered * Saturate(Coverage);
}
// 비어-파우더: 광학 깊이 → 빛 투과 (가장자리 어두운 효과는 파우더 항)
inline float BeerPowder(float OpticalDepth, float PowderStrength)
{
	return std::exp(-OpticalDepth) * FMath::Lerp(1.0f, 1.0f - std::exp(-2.0f * OpticalDepth), Saturate(PowderStrength));
}
    • 덮임(Coverage) 잘라내기: Remap(Shape, 1 − 덮임, 1, 0, 1)은 "모양 값이 1 − 덮임보다 작으면 0". 덮임을 올리면 문턱이 내려가 더 많은 노이즈가 구름이 됩니다. 0 = 맑음, 1 = 흐림인 직관적 손잡이 하나.
    • 비어-파우더: 순수 비어 법칙(exp(−τ))만 쓰면 구름 가장자리가 너무 밝습니다. 실제 뭉게구름은 가장자리가 약간 어두운데(빛이 안쪽에서 여러 번 튕겨 나오는 효과), 이를 "파우더" 항 1 − exp(−2τ)로 흉내 냅니다.
    • 이중 로브 위상: 해를 등지고 보는 구름 가장자리의 은빛(silver lining)은 강한 앞쪽 산란(g = SilverLining 0.6)이고, 해를 등진 구름도 너무 어둡지 않게 뒤쪽 로브를 섞습니다.
    • 다중 산란 옥타브(Wrenninge 2013): 옥타브 i마다 소멸 ai, 산란 bi, 위상 이심률 ci로 줄여 더하면, 두꺼운 구름 안쪽이 새카맣게 되지 않습니다.

    레이마칭은 비싸므로 저해상도(내부 해상도 ÷ r.VolumetricClouds.Divisor, Plans.md 기록 1/4 해상도)로 추적하고, 프레임마다 Halton 지터로 시작점을 흔들어 재투영 누적합니다. 지터·노이즈는 시간 누적이 켜진 연속 프레임에만 쓰고, 크기가 바뀌면 이력을 버립니다. 합성은 메인 패스 뒤·안개 전에 하늘 픽셀에 합니다. 비용은 1440p에서 0.37~0.48ms였습니다.

    핵심 개념물 — 굴절, 흡수, 반사, 거품

    Phase 49의 물은 "소규모 물"입니다(사용자 결정: 수영장·분수·웅덩이·강 구간, 바다·부력 없음). FWaterBodyComponent는 엔티티 위치 중심 상자이고 수면은 상자 윗면입니다. 물은 메시 머티리얼 경로를 쓰지 않는 전용 패스로, 안개 적용 뒤·반투명 앞에서 그립니다. 이미 그려진 장면 색을 굴절 배경으로 읽어야 하기 때문입니다.

    constexpr float WaterF0 = 0.02f; // 물 굴절률 1.33
// 바닥(굴절) 색과 물 산란 색 섞기
inline FVector3 ApplyAbsorption(const FVector3& Behind, const FVector3& ScatterColor, const FVector3& AbsorptionPerMeter, float DistanceCentimeters)
{
	const FVector3 T = Transmittance(AbsorptionPerMeter, DistanceCentimeters);
	return Behind * T + ScatterColor * (FVector3::OneVector - T);
}
// 가장자리 거품 비중 (물 두께 cm 기준, 0 두께에서 1)
inline float EdgeFoam(float ThicknessCentimeters, float FoamDistance)
{
	...
	const float X = FMath::Clamp(1.0f - ThicknessCentimeters / FoamDistance, 0.0f, 1.0f);
	return X * X;
}

    물속 거리를 cm로 받아 경계에서 m로 바꾸는 점(FUnits::UnitsToMeters), 반사 비율이 수직으로 내려다볼 때 2%뿐이고 비스듬히 볼수록 급격히 커지는 점(슐릭 근사의 (1 − cos)5)을 보세요. 호수 가장자리를 멀리서 보면 하늘이 비치고 발밑은 투명한 이유입니다. 물속에 카메라가 들어가면 같은 흡수식을 "시선이 물 상자 안을 지나는 길이"(UnderwaterPathLength — 광선-상자 교차와 장면 깊이의 교집합)에 적용합니다. 반사도 20강의 교훈대로 확률적이 아닌 결정적 화면 반사를 씁니다. 물 3개의 비용은 1440p에서 0.23ms였습니다.

    함정과 교훈

    얕은 물이 회색 띠로 떠 보인 버그 물은 안개 적용 뒤에 그립니다. 그러니 굴절로 읽어 온 바닥 장면 색에는 이미 공중 원근과 안개가 들어 있습니다. 그런데 물 셰이더가 결과 전체에 다시 EvaluateFog를 걸자, 안개가 두 번 걸린 굴절 색 때문에 얕은 물(굴절 비중이 큰 곳)이 주변 땅보다 뿌옇게 — 회색 띠처럼 — 떠 보였습니다. 수정은 수면 안개를 물이 새로 더한 빛(산란·반사·거품)에만 거는 것입니다(Water.hlsl의 Direct). CLAUDE.md에 그대로 남아 있습니다: "굴절된 뒤 장면 색은 이미 안개가 낀 값이라 수면 안개는 산란·반사·거품 몫에만 건다." 합성 순서가 얽힌 효과에서는 "이 값에 무엇이 이미 들어 있나"를 항상 따져야 합니다.
    굽은 개울은 물 상자 하나로 데모 맵 Forest의 개울과 웅덩이에 대해 CLAUDE.md에 남은 기록입니다: 굽은 물을 여러 상자로 나누면 굽이에서 상자가 겹치거나 틈이 보이므로, "지형 전체를 덮는 물 상자 하나 + 파낸 바닥"으로 만든다. 물 상자는 요(Z) 회전만 되는 단순한 모델이라, 모양은 바닥 지형이 만들게 하는 편이 맞았습니다.

    Plans.md의 후속 과제는 이 모델의 한계를 정직하게 보여 줍니다: 높이 안개가 고정 색이라 해 질 녘 지평선이 하얗게 뜨고, 구름이 그림자를 드리우지 않고, 물이 깊이를 쓰지 않아 그리드·파티클이 수면 위로 보이며, 공중 원근은 수 km 이하 근사입니다. 그리고 하늘을 바꾸면 반사 캡처는 다시 구워야 합니다.

    HDR 디스플레이 출력도 같은 Phase 하늘처럼 밝기 범위가 큰 장면을 위해 Phase 49에서 HDR10/scRGB 출력도 넣었습니다. 씬 출력은 반드시 Rhi->GetSceneOutput(), UI·오버레이는 GetBackBufferOutput(HDR이면 SDR 겹침 층)으로 나누고, HDR 톤매핑 곡선은 HdrDisplayMath.h ↔ HdrDisplay.hlsli로 같은 식을 유지합니다.

    생각해 볼 문제

    Q1. 레일리 계수를 세 채널 모두 같게 하면 하늘은 어떻게 보일까요? 파장 의존이 사라지므로 산란된 빛이 햇빛 색 그대로라 하늘이 흰색/회색이 되고, 노을도 붉어지지 않습니다(긴 경로에서 모든 색이 같은 비율로 줄어듦). 하늘의 파랑과 노을의 빨강은 모두 "파랑이 더 잘 흩어진다"는 한 가지 사실에서 나옵니다.
    Q2. 대기 계산을 cm 단위 float로 하면 왜 문제가 될까요? 행성 반지름이 약 6.36 × 108cm라 float의 유효 숫자(약 7자리)로는 표면 근처 위치의 수십~수백 cm 차이가 반올림에 묻힙니다. 고도 계산(위치 길이 − 바닥 반지름)이 큰 수끼리의 뺄셈이 되어 정밀도가 크게 떨어집니다. km 단위로 두면 같은 계산의 절대 크기가 105배 작아집니다.
    Q3. 물 셰이더가 결과 전체에 안개를 다시 걸면 왜 얕은 물에서 특히 눈에 띌까요? 얕은 물은 투과율 T가 커서 결과의 대부분이 굴절된 바닥 장면 색입니다. 그 색에는 이미 안개가 들어 있으므로 안개가 두 번 걸린 효과가 가장 크게 드러납니다. 깊은 물은 결과의 대부분이 물이 새로 더한 산란 색이라 차이가 작습니다.

    왜 필요한가화면 밖의 것은 비칠 수 없다

    19~20강의 SSR(화면 공간 반사)은 이미 그려진 화면의 깊이 버퍼를 따라 광선을 행진합니다. 싸고 효과적이지만 근본적인 한계가 있습니다. 화면에 없는 것은 비출 수 없습니다. 카메라 뒤의 물체, 기둥에 가려진 물체, 화면 밖으로 나간 물체는 반사에서 사라지거나 가장자리에서 잘립니다.

    Plans.md Phase 40에 사용자 보고가 남아 있습니다: "파란 벽에 반사된 물체가 깜빡이고 모양이 이상하며 각도에 따라 안 보임." 분석 결과 상당 부분이 SSR 자체의 한계였고, 로드맵에서 "DXR 도입 결정, Phase 50 RT 반사로 해결"로 흡수되었습니다. Phase 50 결과: Reflections 데모의 카메라 뒤 물체가 반사되고, 정지 화면 깜빡임 최댓값이 11.8 → 6.5로 줄었으며, 1440p에서 RT 반사(5.15ms)가 SSR(5.78ms)보다 오히려 빨랐습니다.

    그림자도 비슷합니다. 그림자 맵(16강)은 해상도가 유한해 계단이나 흐림이 생기고, 캐스케이드 경계, 바이어스로 인한 떠 보임(피터 패닝) 같은 문제가 따라옵니다. 레이 트레이싱은 "이 점에서 해 쪽으로 쏜 광선이 막히는가"를 직접 묻습니다.

    핵심 개념질문의 방향을 뒤집기

    래스터화는 "이 삼각형은 화면의 어느 픽셀을 덮는가?"를 묻습니다. 삼각형을 하나씩 화면에 투영하므로 카메라에서 출발하는 시선에는 강하지만, 다른 방향(반사, 그림자, 간접광)의 질문에는 답할 수 없습니다. 레이 트레이싱은 반대로 "이 광선이 처음 맞는 삼각형은 무엇인가?"를 묻습니다. 광선의 출발점과 방향이 자유로우므로 반사·그림자·GI 모두 같은 질문 하나로 풀립니다.

    문제는 비용입니다. 장면에 삼각형이 수백만 개인데 광선마다 모든 삼각형과 교차 검사를 하면 끝나지 않습니다. 그래서 가속 구조가 필요합니다.

    BVH — 상자로 걸러내기

    BVH(Bounding Volume Hierarchy)는 삼각형들을 축 정렬 상자(AABB)로 묶고, 그 상자들을 다시 큰 상자로 묶은 트리입니다. 광선이 큰 상자를 빗나가면 그 안의 수천 개 삼각형을 한꺼번에 건너뜁니다. 상자 검사는 삼각형 검사보다 훨씬 싸므로, 광선 하나가 실제로 검사하는 삼각형은 로그 수준으로 줄어듭니다.

    2단계: BLAS와 TLAS

    장면 전체를 하나의 BVH로 만들면, 물체 하나만 움직여도 전체를 다시 만들어야 합니다. 그래서 DXR(DirectX Raytracing)은 두 단계로 나눕니다.

    • BLAS (Bottom-Level Acceleration Structure): 메시 하나의 삼각형에 대한 BVH. 메시의 로컬 공간에서 만들므로 물체가 움직이거나 회전해도 다시 만들 필요가 없습니다. 같은 메시를 쓰는 바위 100개는 BLAS 하나를 공유합니다.
    • TLAS (Top-Level Acceleration Structure): "인스턴스" 목록에 대한 BVH. 인스턴스 = (BLAS 포인터 + 월드 변환 행렬 + 마스크 + 플래그 + InstanceID). 인스턴스 수천 개짜리 TLAS는 매 프레임 새로 만들어도 빠릅니다.

    바인드리스 — 모든 것을 번호로

    래스터 패스는 그리기 호출마다 그 물체의 텍스처를 루트에 묶습니다. 하지만 광선은 어느 물체를 맞힐지 미리 모릅니다. 그래서 셰이더가 셰이더 가시 디스크립터 힙 전체를 배열로 봅니다: 공간 1의 Texture2D[], 공간 2의 ByteAddressBuffer[]. 히트 정보에는 정점/인덱스 버퍼의 힙 칸 번호가, 머티리얼 표에는 텍스처 테이블의 힙 칸 번호가 들어 있어, 맞힌 뒤 번호로 꺼내 읽습니다(NonUniformResourceIndex). 머티리얼 표(80B)는 매 프레임 Prepare가 다시 채웁니다 — 30강의 밉 스트리밍이 텍스처를 교체하면 칸 번호가 바뀌기 때문입니다.

    히트 머티리얼

    21강의 인터페이스가 여기서 빛을 발합니다. 고정 PBR은 MaterialDefault.hlsli를 E_MATERIAL_CUSTOM_RESOURCES로 include해 상수는 머티리얼 표, 텍스처는 바인드리스 테이블로 읽습니다. 그래프 머티리얼은 이번 프레임 TLAS에 들어간 그래프 셰이더들의 생성 함수를 해시 순 슬롯(RtGraphMaterial1, 2, …)으로 이어 붙인 변형을 만들고 슬롯 번호로 분기합니다(GetGraphVariant(), 최대 32 슬롯). 변형 컴파일이 실패하면 회색 근사로 떨어집니다. 텍스처 밉은 화면 미분 대신 광선 원뿔(거리에 따라 넓어지는 원뿔의 폭)로 LOD를 고르고, 밉 스트리밍에 필요 밉을 보고하지는 않습니다.

    핵심 개념움직이는 메시 — refit, 풀, 거리별 간격

    정적 메시의 BLAS는 한 번 만들면 끝입니다. 하지만 스킨 메시(캐릭터)는 매 프레임 정점이 움직입니다. BLAS를 매 프레임 처음부터 다시 빌드하면 비싸므로, DXR은 갱신(refit)을 제공합니다: 트리 구조(어떤 삼각형이 어떤 상자에 속하는지)는 그대로 두고 상자 크기만 새 정점에 맞춰 늘리고 줄입니다. 빠르지만, 포즈가 크게 바뀌면 상자가 부풀어 탐색 효율이 떨어집니다. 캐릭터 애니메이션처럼 위상이 같은 변형에는 잘 맞습니다.

    ProjectE의 스킨 경로(RayTracingScene.h 머리 주석)는 이렇습니다.

    1. 계산 셰이더 스키닝(RayTracingSkinning.hlsl): 프레임 본 팔레트(40강)로 월드 공간 정점을 만듭니다. 래스터는 정점 셰이더에서 스키닝하므로 결과가 메모리에 남지 않지만, BLAS 입력은 실제 정점 버퍼가 필요합니다.
    2. 모델 하나 = BLAS 하나: 스켈레톤(FSkinComponent::Joints[0]) + 양면·그림자 여부를 키로, 프리미티브마다 지오메트리 하나. 지오메트리별 OPAQUE 플래그라 Masked 프리미티브만 후보가 됩니다.
    3. 풀 하위 할당: 모든 스킨 정점은 큰 정점 풀 하나에, 모든 스킨 BLAS는 BLAS 풀 하나에 FRangeAllocator(오프셋 순 빈 칸 목록, 결정적 첫 맞춤, 해제 시 이웃 병합)로 나눠 넣습니다. 렌더 그래프 리소스는 엔티티 수와 무관하게 2개입니다(22강의 FindImported 교훈). 히트 정보의 BaseVertex가 풀 안 위치입니다.
    4. 서명이 같으면 refit, 다르면 다시 빌드: 멤버 순서·정점 위치·불투명 여부가 같으면 갱신.
    5. 거리별 갱신 간격: 아래.
    inline uint32 GetSkinnedRefitInterval(float Distance, float RefitDistance, uint32 MaxInterval)
{
	if (MaxInterval <= 1 || Distance <= RefitDistance || RefitDistance <= 0.0f)
	{
		return 1;
	}
	const float Steps = std::floor(Distance / RefitDistance);
	return std::min(MaxInterval, 1u + static_cast<uint32>(std::min(Steps, 1.0e6f)));
}

    먼 캐릭터의 반사나 그림자는 몇 프레임 늦어도 눈에 띄지 않습니다. 위상을 모델마다 다르게(피보나치 해시) 주는 이유는, 모두 같은 프레임에 갱신하면 4프레임마다 비용이 몰려 프레임 시간이 톱니처럼 튀기 때문입니다. 엇갈리면 매 프레임 비슷한 양을 갱신합니다.

    정적 BLAS에도 비용 관리가 있습니다. (메시 핸들, LOD) 키로 캐시하고 — LOD는 래스터와 같은 인스턴스 LOD여서 RT 그림자가 래스터 표면과 같은 면을 봅니다(자기 그림자 여드름 방지) — 프레임당 새 빌드는 32개 상한, 넘친 인스턴스는 다음 프레임으로 미룹니다. 빌드 후 몇 프레임 뒤 실제 크기를 읽어 압축(compaction) 복사합니다. 오래 TLAS에 들어가지 않은 BLAS는 해제합니다.

    ProjectE에서는RT 그림자와 반사 — 잡음을 결정적으로 거르기

    광선 한두 개로는 부드러운 그림자(태양 원반 크기의 반그림자)나 거친 표면의 흐린 반사를 표현할 수 없습니다. 픽셀마다 광선 수를 늘리면 비싸므로, 적은 광선 + 필터로 해결합니다. 여기서 20강의 교훈이 그대로 적용됩니다: 픽셀·프레임마다 흔드는 확률적 표본은 TAA가 거르지 못한다 → 결정적 필터를 먼저.

    RT 반사는 SSR과 같은 출력 형식을 내도록 만들어, 20강에서 다듬은 SSR 해석 경로(FScreenSpaceReflections::AddResolvePasses)를 그대로 재사용합니다. 히트 지점의 조명은 RayTracingLighting.hlsli의 EvaluateHitLighting이 합니다: 방향광 + RT 그림자 광선, 로컬 라이트 앞 16개(그림자 없음), IBL, 발광. 반투명과 물은 TLAS에 넣지 않습니다.

    함정과 교훈

    "RT를 켜면 첫 실행 화면이 다르다" — 재현되지 않은 1 LSB Plans.md Phase 51 기록: RT를 켠 첫 실행 화면 차이를 조사했지만 재현되지 않았고(1 LSB × 90픽셀), 드라이버 BVH의 동률 후보 때문으로 추정했습니다. 대신 결정성을 보강했습니다: 자동 검증·동기 로딩이면 BLAS 빌드 상한을 두지 않아 같은 프레임에 모두 빌드합니다. 상한 때문에 일부 BLAS가 한 프레임 늦게 들어가면 실행마다 첫 프레임들이 달라질 수 있기 때문입니다. 이후 RT 켬 Decals 3회 동일.
    스크래치 버퍼와 엔티티 수 BLAS 빌드에는 임시 작업 메모리(스크래치)가 필요합니다. 스킨 모델이 수백 개면 모두에게 스크래치를 따로 주면 메모리가 폭발하므로, 슬롯당 약 32MB 예산을 넘으면 처음부터 재사용하고 그 사이에 배리어를 넣습니다(FBuildOp::bScratchBarrier). 규모 문제는 "엔티티마다 무엇을 하나"를 먼저 의심해야 합니다.

    Plans.md의 후속 과제: RT 그림자 비용(반해상도 추적·필터 축소), 로컬 라이트 RT 그림자, 반사 히트에 안개/공중 원근 미적용, 반투명·물 TLAS 제외, 그래프 RT 변형의 런타임 컴파일 끊김과 패키지 쿠킹 미지원(회색 근사), RT 디버그 뷰는 내부 해상도 100%에서만.

    정리
    • 레이 트레이싱은 "이 광선이 무엇을 맞나"를 물어 화면 밖 반사·정확한 그림자를 얻는다.
    • BVH가 광선당 검사를 로그 수준으로 줄이고, BLAS(메시, 로컬) + TLAS(인스턴스, 매 프레임)로 나눠 갱신 비용을 줄인다.
    • ProjectE는 인라인 RayQuery(SM 6.5)로 기존 PSO·렌더 그래프를 그대로 쓰고, 추적은 전체 화면 픽셀 셰이더 + 바인드리스.
    • 히트 정보 번호 = InstanceID + GeometryIndex, 머티리얼은 21강의 EvaluateMaterial + 광선 원뿔 LOD.
    • 스킨은 계산 스키닝 + refit + 풀 2개 하위 할당 + 거리별 엇갈린 갱신 간격. 그림자·반사는 교차 표본 → 공간 → 시간의 결정적 필터.

    생각해 볼 문제

    Q1. 캐릭터가 걷는 애니메이션에 refit 대신 매 프레임 BLAS 재빌드를 하면 무엇이 좋고 무엇이 나쁠까요? 재빌드는 트리를 새 포즈에 맞게 다시 짜므로 탐색 효율이 가장 좋지만, 빌드 비용이 refit보다 훨씬 큽니다. 걷기처럼 삼각형의 이웃 관계가 크게 바뀌지 않는 변형은 refit으로 상자만 조정해도 탐색 효율 손실이 작아 refit이 유리합니다. 서명(멤버·불투명 여부)이 바뀌는 경우에만 재빌드합니다.

    왜 필요한가빛은 한 번에 끝나지 않는다

    창문으로 햇빛이 들어와 바닥을 비춥니다. 이것이 직접광입니다. 그런데 실제 방에서는 햇빛이 닿지 않는 천장도 밝습니다. 바닥에 맞은 빛이 튕겨 올라가 천장을 비추고, 다시 벽을 비추기 때문입니다. 이렇게 한 번 이상 표면에 튕긴 빛이 간접광이고, 직접광과 간접광을 모두 계산하는 것을 전역 조명(GI, Global Illumination)이라 합니다.

    Phase 51 이전 ProjectE의 간접광은 17강의 IBL — "모든 방향 하늘에서 들어오는 빛" — 뿐이었습니다. 실외에서는 그럴듯하지만, 실내에서는 벽과 천장이 하늘을 가리는데도 하늘빛을 받는 셈이라 구석이 밝고 평평해 보입니다.

    DDGI (Dynamic Diffuse Global Illumination)

    DDGI(Majercik 2019, NVIDIA RTXGI 방식)는 매 프레임 일부 프로브에서 레이 트레이싱으로 광선을 쏴 조도를 갱신하고, 시간에 걸쳐 누적합니다. 핵심 아이디어는 셋입니다.

    1. 옥타헤드럴 맵: 프로브의 "방향별 값"을 작은 정사각형 텍스처 타일에 저장.
    2. 거리 정보로 가시성 판정: 조도 외에 "방향별로 가장 가까운 벽까지의 거리"도 저장해, 벽 너머 프로브의 빛이 새는 것을 막음.
    3. 시간 누적(히스테리시스): 프레임당 광선은 적게, 대신 이전 값과 섞어 잡음을 평균.

    저장 형식은 DdgiMath.h 머리 주석에 있습니다. 조도 타일 값은 E/π(조도 ÷ π — 17강 하늘 확산 맵과 같은 규약이라 × 알베도 = 확산 반사광), 거리 타일 값은 (평균 거리, 거리 제곱의 평균) ÷ (1.5 × 프로브 간격)으로 정규화합니다. 프로브마다 상태 텍셀이 하나 더 있어 재배치 오프셋(xyz)과 상태(w: 0 아직 없음, 1 활성, 2 비활성 = 벽 속 + 4 × 갱신 횟수)를 담습니다. 볼륨 하나에 축마다 2~32개, 볼륨당 최대 8192, 전체 16384 프로브, 볼륨 8개까지.

    핵심 개념빛 새기와 체비셰프 가시성

    프로브 격자는 벽을 모릅니다. 벽 바로 안쪽 셰이딩 점의 주변 8개 프로브 중 일부가 벽 바깥(햇빛 쏟아지는 마당)에 있으면, 그냥 보간했을 때 실내 벽에 바깥 빛이 번집니다. 이것이 빛 새기(light leaking)로, 프로브 GI의 가장 고질적인 문제입니다.

    // 체비셰프 상한 (정규화 거리): 평균보다 가까우면 1, 멀면 (σ² / (σ² + Δ²))³ — 세제곱은 누수를 더 세게 자른다 (RTXGI)
inline float ComputeVisibility(float Distance, float Mean, float MeanSquared)
{
	if (Distance <= Mean) { return 1.0f; }
	const float Variance = FMath::Abs(MeanSquared - Mean * Mean);
	const float Delta    = Distance - Mean;
	const float Bound    = Variance / FMath::Max(Variance + Delta * Delta, 1.0e-8f);
	return FMath::Max(Bound * Bound * Bound, 0.0f);
}

    체비셰프 부등식은 "평균과 분산만 알 때, 값이 평균보다 Δ 이상 클 확률의 상한"을 줍니다. 여기서는 "프로브에서 그 방향으로 본 표면들 너머에 P가 보일 확률"의 상한으로 씁니다(분산 그림자 맵과 같은 아이디어). 적용 시에는 P를 법선·시선 쪽으로 살짝 밀고(NormalBias, ViewBias — 표면에 딱 붙은 점이 자기 표면에 가려지지 않게), 8개 프로브 각각에 삼선형 × 감싸기(법선 쪽 프로브 우대) × 가시성 가중치를 곱해 합으로 나눕니다.

    1차: "Demo_GI 화면 깜빡임" — 급변 감지가 잡음에 걸림

    원래 누적에는 "텍셀 값이 이전보다 30% 이상 급변하면 히스테리시스를 0.75 낮춰 빨리 따라가기"가 있었습니다(조명이 바뀔 때 빨리 반응하려고). 그런데 광선 몇백 개로 잰 값은 원래 잡음이 있어서 이 문턱에 자주 걸렸고, 히스테리시스가 0.22까지 떨어진 텍셀이 프로브 단위로 깜빡였습니다. 해결: 급변 감지를 기본 끔(r.DDGI.ChangeThreshold 1.0). 조명 변화는 GPU 값의 급변이 아니라 CPU에서 결정적으로 감지합니다 — 방향광 방향 2도, 복사·하늘 배율 10% 이상 바뀌면(ComputeLightChange) 30프레임 동안 히스테리시스 상한 0.7. 대가는 해 방향 급변 90% 추종이 20 → 약 36프레임으로 늘어난 것입니다.

    2차: "방 안에서 여전히 미세하게 깜빡임" — 확정 원인 셋

    원인 ① 재배치가 매 프레임 왕복 프로브가 벽 속에 들어가거나 벽에 너무 붙으면 고정 광선 결과로 프로브를 조금 옮깁니다(재배치). 규칙은 "가장 가까운 앞면이 MinFrontface보다 가까우면 밀고, 여유가 충분하면 격자 자리로 되돌아간다". 문제는 되돌아가는 문턱이 미는 문턱과 같았다는 것입니다. 고정 광선 32개의 "가장 가까운 거리"는 벽까지 수직 거리보다 길게 재지므로, 밀자마자 "여유 있음"으로 판정되어 되돌아가고, 다음 프레임에 다시 밀었습니다. 셰이딩 가중치가 프레임마다 바뀌니 창 쪽 벽·천장이 깜빡였습니다. 해결: 되돌아가는 문턱 = 미는 문턱 × 2(RelocationReturnScale) — 미는 한 걸음이 되돌아가기를 부르지 않도록 히스테리시스 간격을 둔 것입니다. 테스트 Ddgi_RelocationConvergesWithoutOscillation이 이 수렴을 지킵니다. 
    constexpr float RelocationReturnScale = 2.0f;
...
const float ReturnClearance = MinFrontfaceDistance * RelocationReturnScale;
if (Rays.BackfaceRatio > BackfaceThreshold)          // 벽 속: 가장 가까운 뒷면 너머로
{
	Full = Offset + Rays.ClosestBackfaceDir * (Rays.ClosestBackface + MinFrontfaceDistance * 0.5f);
}
else if (Rays.ClosestFrontface < MinFrontfaceDistance)  // 너무 가까움: 가장 먼 앞면 쪽으로
{
	...
}
else if (Rays.ClosestFrontface > ReturnClearance + 1.0f && OffsetLength > 1.0e-2f) // 여유: 격자 자리 쪽으로
{
	const float MoveBack = FMath::Min(Rays.ClosestFrontface - ReturnClearance, OffsetLength);
	Full                 = Offset - Offset * (MoveBack / OffsetLength);
}
// 결과가 간격 비율 MaxRelocation(0.45)을 넘으면 이전 오프셋 유지

    이 식은 CPU(DdgiMath.h)와 GPU(DdgiBlend.hlsl의 CSProbeData)가 같은 식으로 유지됩니다. 벽 속 판정(뒷면 히트 비율이 문턱 이상)은 뒷면 히트 거리를 줄여 음수로 저장해 두는 규약(BackfaceDistanceScale) 덕분에 가능합니다.

    원인 ② 16비트 누적의 치우침 조도 아틀라스는 원래 RGBA16F였습니다. 히스테리시스 h = 0.99면 프레임마다 값은 (1 − h) = 1%씩만 새 값 쪽으로 움직입니다. 반정밀도(유효 숫자 약 3자리)에서는 이 작은 걸음이 반올림에 먹혀, 특히 값이 올라가야 할 때 덜 올라가 어둡게 치우쳤습니다(h 0.99에서 −6%). 해결: 조도 아틀라스는 RGBA32F. CLAUDE.md 규칙: "누적 이력을 반정밀도로 두지 않는다." 거리 아틀라스는 정규화 덕분에 RG16F로 충분합니다.
    원인 ③ 광선 잡음은 수열을 바꿔도 줄지 않는다 누적 값의 프레임 간 잡음 표준편차는 대략 √((1 − h) / (1 + h) / 광선 수)에 비례합니다. 광선 회전 수열을 바꿔 봐도 줄지 않았습니다 — 줄이는 손잡이는 h와 광선 수뿐입니다. 실내 데모(Tests/GI)는 h 0.99 · 광선 512로 올렸습니다(0.99는 0.97 대비 잡음 0.58배). 그런데 h를 올리면 다중 반사가 h + (1 − h) · 반사율 비율로 수렴해 처음과 조명 변화 뒤 수백 프레임 어둡게 남습니다. 그래서 정착 구간을 두었습니다: 가속(0.7, 30프레임) → 정착(r.DDGI.SettleFrames 300프레임 동안 0.97) → 볼륨 값(0.99). ComputeFrameHysteresis가 이 상한을 고릅니다.

    측정 결과: 방 안 4시점에서 16×16 블록 평균의 시간 표준편차 99% 값이 0.40~0.59 → 0.15~0.17로, DDGI를 끈 화면(0.19~0.25)보다도 조용해졌습니다. 비용은 720p +0.3ms. 측정 방법 자체도 이때 정립되었습니다(20강): 화면 전체 평균은 국소 깜빡임을 놓치므로, 수렴 뒤 연속 32프레임의 화소별 시간 표준편차와 블록 평균 표준편차를 봅니다.

    ProjectE에서는RTAO — 프로브가 못 보는 가림

    세 번째 보고는 "실내 그림자 품질 형편없음"이었습니다. Tests/GI에 그림자 유형별 구조(창살, 계단, 테이블/의자, 선반, 알코브, 매단 상자 …)를 깔고 진단한 결론은 의외였습니다. 직접광 그림자(캐스케이드는 RT 그림자와 거의 같음)는 정상이었고, 원인은 간접광만 받는 곳의 가림 부재였습니다. 프로브 간격은 100cm라 테이블 밑, 선반 안쪽처럼 물체 크기의 가림을 담을 수 없고, SSAO(19강)는 거의 보이지 않았습니다.

    해결은 RT 앰비언트 오클루전(RTAO)입니다. 픽셀마다 짧은 광선을 반구로 쏴 "가까이에 무엇이 있나"를 재고, 그 가시도를 간접광에만 곱합니다.

    • 추적: 반해상도, 픽셀당 코사인 가중 광선 2개, Bayer 4×4 교차 표본(25강 그림자와 같음). 가장 가까운 히트 거리 t로 가림 w = (1 − t/반경)², 반경 기본 150cm(= 프로브 간격 × 1.5 — 프로브가 담는 규모와 이어지게).
    • 공간 필터: 5×5 텐트 — 주기 4 패턴의 칸마다 가중 합이 1이라 평평한 곳은 매 프레임 같은 값(결정적).
    • 시간 누적(0.1) → 결과는 SSAO와 같은 형식(R 가시도, G 뷰 깊이)이라 메인 패스 t16이 그대로 읽습니다.
    • 켜는 조건: r.RayTracing.AO −1(기본) = DDGI 볼륨이 활성인 프레임만.

    숫자로 정하기: 경로 추적 기준

    반경, 지수, 해상도 같은 값은 "보기 좋게"로 정하면 끝이 없습니다. 그래서 정답을 만들었습니다. r.RayTracing.AO.Reference N(--rtao-reference)은 정지 카메라에서 픽셀마다 광선 N개로 여러 번 반사까지 경로 추적한 간접 확산을 프레임마다 평균에 더하는 고비용 기준입니다. 이 기준과 --debug-view gi 화면의 rmse(평균 제곱근 오차)를 Tests/GI 8시점에서 쟀습니다.

    방식경로 추적 기준 대비 rmse (Tests/GI 8시점)
    DDGI만14.4
    DDGI + SSAO11.8
    DDGI + RTAO10.2

    비용은 1440p 0.63ms(SSAO 0.59ms를 대체하므로 실질 +0.04ms), 시간 표준편차는 master 이하였습니다.

    기준을 잘못 만들면 잘못된 답에 맞춘다 CLAUDE.md에 경고가 남아 있습니다: 기준을 "한 번 반사 + 히트 DDGI"로 만들지 말 것 — 히트 지점의 DDGI 조도도 접촉부에서 가려지지 않은 값이라 가림을 과소평가한 기준이 되기 때문입니다. 그래서 기준은 4번 반사·그림자 광선을 넣고 마지막 정점에서만 DDGI를 씁니다. 같은 이유로 "가려진 방향의 DDGI 조도를 히트 표면 빛으로 바꾸는" 조도 가중 RTAO도 시도했다가 버렸습니다(거의 어두워지지 않아 기준과 더 멀었음). 또 반해상도 추적을 씬 해상도로 업샘플하면 정지 화면 표준편차가 커져서 쓰지 않았습니다. 측정 기준을 만드는 것 자체가 설계의 일부입니다.

    남은 알려진 것: DDGI는 경로 추적 대비 간접 확산이 화면 평균 +7~16/255 밝게 나오고(프로브 보간), RT·DDGI가 없는 씬은 여전히 약한 SSAO입니다. 또 히트의 로컬 라이트에는 그림자가 없어 그림자 끈 등이 벽 너머로 샐 수 있습니다(Plans.md 후속).

    정리
    • 간접광 = 튕긴 빛. 하늘 IBL만으로는 실내가 평평하고 밝게 샌다.
    • DDGI = 프로브 격자 + 옥타헤드럴 조도(10×10)/거리(18×18) 타일 + 체비셰프 가시성 + 레이 트레이싱 갱신과 시간 누적. 이전 프레임 프로브로 다중 반사.
    • 깜빡임의 교훈: 잡음에 걸리는 GPU 급변 감지 대신 CPU 결정적 감지, 판정 경계에는 히스테리시스 간격, 누적 이력은 32비트, 잡음은 h와 광선 수로만 준다.
    • RTAO는 프로브가 못 담는 근거리 가림을 간접광에만 곱한다. 설계 값은 경로 추적 기준과의 rmse로 정했다(14.4 → 10.2).

    생각해 볼 문제

    Q1. 볼륨 상자를 방 크기에 딱 맞추면 벽 근처에서 무슨 일이 생길까요? 프로브는 상자 칸 가운데에 놓이므로 벽 바로 안쪽 점의 바깥쪽에 프로브가 없고, 상자 경계 반 칸은 경계 프로브로 고정되며 상자 끝에서 하늘 IBL로 페이드합니다. 그래서 벽 근처 셰이딩이 부정확하고 페이드 영역이 실내로 들어옵니다. 규칙대로 방·건물보다 조금 크게 잡아 바깥에도 프로브 층을 둡니다.
    Q2. 히스테리시스를 0.97에서 0.99로 올리면 잡음은 얼마나 줄고, 무엇을 잃을까요? 표준편차 ∝ √((1 − h)/(1 + h))이므로 √(0.01/1.99) / √(0.03/1.97) ≈ 0.58배로 줄어듭니다. 대신 새 정보가 프레임당 1%만 반영되어 조명 변화를 느리게 따라가고, 다중 반사가 차오르는 데 수백 프레임이 걸립니다. 그래서 처음과 조명 변화 뒤에는 정착 구간(0.97)을 둡니다.
    Q3. RTAO 가시도를 직접광에도 곱하면 어떻게 될까요? 직접광의 가림은 이미 그림자(그림자 맵/RT 그림자)가 정확히 계산했으므로 이중으로 어두워집니다. 햇빛이 정면으로 드는 구석도 AO만큼 어두워져 틀린 화면이 됩니다. AO는 "모든 방향에서 오는 빛 중 얼마나 가려졌나"이므로 방향이 퍼진 간접광에만 맞는 근사입니다.

    왜 필요한가세상의 조명은 점이 아니다

    핵심 개념면광원 = 다각형 위의 적분

    점광원에서는 셰이딩 점이 받는 빛이 "광원 하나의 방향 × 세기 ÷ 거리²"로 끝납니다. 면광원에서는 광원 면의 모든 점에서 빛이 오므로, 셰이딩 점에서 본 광원의 입체각 전체에 대해 BRDF를 적분해야 합니다.

    다행히 코사인 분포(람베르트 확산)를 다각형 위에서 적분하는 데는 오래된 정확한 식이 있습니다. 다각형 꼭짓점을 단위 구에 투영하고, 모서리마다 "두 꼭짓점 사이 각 × 방향" 항을 더하면 됩니다(형태 계수, form factor). 문제는 광택 반사입니다. GGX BRDF는 거칠기와 시선 각도에 따라 모양이 바뀌는 복잡한 분포라, 다각형 위 적분의 닫힌 식이 없습니다.

    핵심 개념LTC — 어려운 분포를 쉬운 분포로 바꾸기

    Heitz 등(2016)의 아이디어는 이렇습니다. 코사인 분포 Do에 3×3 행렬 M으로 방향을 선형 변환하면, 늘어나고 기울어진 새 분포가 생깁니다. 적당한 M을 고르면 그 모양이 GGX 분포와 거의 같아집니다. 이것이 선형 변환 코사인(LTC, Linearly Transformed Cosines)입니다. 그리고 결정적인 성질이 있습니다: 변환된 분포를 다각형 P 위에서 적분한 값은, 원래 코사인 분포를 역변환한 다각형 M−1P 위에서 적분한 값과 같습니다.

    셰이더가 하는 일은 그래서 단순합니다(AreaLightMath.h 머리 주석).

    1. 거칠기와 √(1 − N·V)로 표 1에서 M−1을 읽습니다(행렬 성분 4개, m11 = 1).
    2. 광원 꼭짓점을 셰이딩 점 기준 (T1, T2, N) 기저로 옮기고 M−1을 곱합니다.
    3. 단위 구에 투영해 모서리 적분 벡터를 더합니다 → 형태 계수 벡터 F.
    4. 스펙큘러 = L × 적분 × (F0 × 크기 + (1 − F0) × 프레넬)(표 2), 확산 = L × (단위 행렬로 같은 적분) × 알베도 × (1 − 금속).

    두 가지 세부가 우아합니다. 지평선 잘림: 광원 일부가 셰이딩 점의 표면 아래로 내려가면 원래는 다각형을 지평선에서 잘라야 하는데(꼭짓점 수가 바뀜), 대신 F를 "같은 형태 계수의 구"로 근사해 표 2의 4번째 채널에서 잘린 비율을 읽습니다(Heitz 2017). 꼭짓점 수와 무관한 비용입니다. 원판: 원형 광원은 다각형이 아니므로 넓이가 같은 정 8각형으로 근사합니다. 정 n각형 넓이 n/2 · r² · sin(2π/n)이 π r²가 되도록 꼭짓점 반지름에 1.05390736을 곱합니다(DiscPolygonScale). 타원(가로·세로 반지름이 다름)도 같은 경로로 됩니다.

    라이선스도 코드의 일부 LTC 표는 저자들이 공개한 selfshadow/ltc_code의 GGX 피팅 데이터입니다. BSD 라이선스이므로 LtcTables.cpp 옆에 LtcTables.LICENSE.txt를 둡니다. 외부 데이터를 가져올 때 출처와 라이선스 파일을 함께 두는 것은 Phase 47~53 야간 진행 결정("출처·라이선스 파일 동봉")에 적힌 규칙이기도 합니다.

    단위: 면을 키우면 더 밝아지나?

    Intensity는 "면 법선 방향 1m 거리의 조도"로, 18강 점광원과 같은 단위입니다. 그래서 멀리서 보면 같은 Intensity의 점광원과 면광원이 같은 밝기입니다. 면의 휘도는 L = Intensity × (100cm)² / 면적(cm²)이라, 면을 키우면 같은 총 빛이 더 넓게 퍼집니다(IntensityToRadianceScale). 렌더러는 L을 색에 미리 곱해 올립니다.

    문 덮개 (barn door)와 긴 면광원 버그

    무대 조명의 "문 덮개"처럼, 면광원 빛을 일정 각도 원뿔 안으로 제한하는 기능입니다. 처음에는 스포트라이트처럼 광원 가운데 → 표면 방향과 면 법선의 각도로 판정했습니다.

    "27m 코브 조명이 가운데 한 점만 밝다" (2026-10-04) 데모 맵의 긴 코브 간접 조명(27m × 20cm)을 면광원 하나로 만들었더니 빛이 가운데 근처에서만 나왔습니다. 원인은 그림 27-3의 왼쪽입니다. 면광원은 "면 전체"에서 빛이 나오는데, 가운데라는 한 점 기준의 원뿔로 잘랐으니 긴 면의 끝 쪽 표면이 모두 원뿔 밖이 된 것입니다. 데모는 우선 코브 조명을 칸마다 나눈 면광원 14개로 우회했고, 엔진은 판정을 면에서 가장 가까운 점 → 표면 방향으로 고쳤습니다. 이제 한 줄짜리 면광원도 같은 결과입니다. 감쇠 창(거리)도 같은 "면 최근접 거리"를 쓰고, 클러스터 경계 구 반지름은 영향 반경 + 면 반 대각선입니다. 
    // 문 덮개 원뿔에 넣는 코사인 = |면 법선 · (면에서 가장 가까운 점 → 표면 방향)| (양면 뒤쪽은 뒤집은 법선 기준).
//   가운데 → 표면 방향으로 재면 긴 면(27m × 20cm 코브 조명 등)의 끝 쪽 표면이 가운데에서 본 큰 각 때문에 원뿔 밖으로 잘려
//   빛이 가운데 한 점에서만 나왔다 (2026-10-04). 면 바로 앞(가장 가까운 점이 면 안)은 항상 1
inline float ComputeBarnDoorCos(LightMath::ELocalLightType Type, const FVector3& Local, float HalfWidth, float HalfHeight)
{
	const FVector3 Offset = ComputeAreaOffset(Type, Local, HalfWidth, HalfHeight);
	return FMath::Abs(Offset.X) / FMath::Max(std::sqrt(Offset.X * Offset.X + Offset.Y * Offset.Y + Offset.Z * Offset.Z), 1.0e-4f);
}

    이 수정은 셰이더(AreaLightBarnDoorCos)뿐 아니라 RT 히트와 볼류메트릭 안개의 "대표점 근사"에도 같은 코사인으로 들어갔습니다. 면광원 식이 래스터·지형·폴리지·RT 히트·안개에 공통이므로, 한 곳만 고치면 반사 속 조명과 화면 조명이 달라집니다.

    그림자: PCSS 64탭

    면광원 그림자는 스포트라이트식 그림자 맵 한 장(반각 = 문 덮개 각, 최대 80°)을 그리고, 반그림자는 PCSS(Percentage-Closer Soft Shadows)로 만듭니다.

    "구석 그림자가 얼룩덜룩" — 16탭 → 64탭 (2026-10-04) 처음에는 가림 탐색·PCF를 각 16탭으로 했습니다. 넓은 반그림자(최대 32텍셀)를 16개 표본으로 덮으니 표본 사이가 성겨 텍셀 계단 덩어리가 얼룩처럼 보였습니다. 64탭으로 늘리자 256탭 기준과의 rmse가 1.86 → 0.68로 줄었고, 대가는 720p 메인 패스 +0.4ms였습니다(Plans.md: 비용이 문제면 48/48). 두 가지 원칙이 함께 지켜졌습니다. 표본 위치는 고정 Vogel 원판 — 픽셀마다 흔들면 20강처럼 지글거립니다. 그리고 판단은 "고표본 기준과의 rmse·최대 오차 + 구석 4배 크롭"으로 — CLAUDE.md: "탭 수를 바꾸면 256탭 기준과 구석 크롭 비교". 자기 그림자 여드름은 수신 평면 기울기 바이어스로 막되, 픽셀마다 흔드는 표본은 쓰지 않습니다.

    IES 프로파일

    IES(LM-63) 파일은 조명 기구를 실측한 배광 표입니다: 수직 각 θ(0 = 천저, 빛 축)와 수평 각 φ마다 칸델라 값. FIesProfile::Parse는 LM-63-1986/1991/1995/2002를 읽습니다 — 머리 줄과 [키워드]를 건너뛰고, TILT 처리, 숫자 목록(램프 수, 칸델라 배율, 각 수 …)을 공백·쉼표·줄바꿈 아무렇게나 읽습니다. 수평 각은 대칭이 여러 종류(0 하나 = 회전 대칭, 0..90 = 4분면, 0..180 = 좌우 …)라 FoldHorizontalAngle이 접어서 찾습니다.

    struct FIesProfile
{
	std::vector<float> VerticalAngles;   // 도, 오름차순
	std::vector<float> HorizontalAngles; // 도, 오름차순
	std::vector<float> Candela;          // [수평 각 번호 × 수직 각 수 + 수직 각 번호] (배율 적용)
	float              MaxCandela  = 0.0f;
	...
	// 텍스트 파싱. 실패하면 false + OutError (Out은 비워진다)
	static bool Parse(std::string_view Text, FIesProfile& Out, std::string* OutError = nullptr);
	// 칸델라 (θ = 수직 각, φ = 수평 각, 도). 범위 밖 수직 각은 0, 수평 각은 대칭으로 접는다
	float Sample(float ThetaDegrees, float PhiDegrees) const;
	// 텍스처 굽기 (Width = θ 0..180, Height = φ 0..360, 칸 가운데 표본), 최대 1로 정규화
	std::vector<float> BakeTexture(uint32 Width, uint32 Height) const;
};

    순수 로직(GPU 없음)이라 테스트 Ies_*가 파싱·대칭 접기·굽기를 직접 검사합니다. 셰이더는 구운 결과만 봅니다.

    셰이더에서 매번 표를 보간하는 대신 θ 64 × φ 32 R32F 텍스처로 굽고(BakeTexture, 칸 가운데 표본, 최대값 1로 정규화), 조명 계산 때 라이트 공간 방향으로 한 번 샘플해 곱합니다. 축 규약은 0° = Forward, φ 0 = Right로 면광원과 같습니다. 면광원은 가운데에서 본 방향 하나로 곱합니다(근사). IES 밝기를 쓰면 최대 칸델라 × 0.01 = Intensity(1000cd ≈ 10)입니다. 파일은 FFileSystem으로 읽으므로 pak 패키지에서도 동작하고, 핫 리로드는 없습니다.

    쿠키

    쿠키는 빛에 곱하는 흑백(또는 색) 텍스처입니다. 광원 종류마다 투영 방식이 다릅니다.

    광원쿠키 투영
    스포트 / 면광원가운데에서의 원근 투영 (반각 = 외부 원뿔 / 문 덮개, 최대 80°)
    점광원위도-경도 (IES와 같은 θ, φ)
    방향광빛에 수직인 평면 좌표 (타일 크기로 반복 — 구름 그림자 흉내 등)

    uv = 투영 좌표 × Transform.xy + Transform.zw이고, ComputeCookieTransform이 크기 배율·오프셋·시간 패닝을 넣습니다. 시간은 CLAUDE.md의 "화면·시뮬레이션 시간 = 앱 프레임 시간" 규칙대로 실제 시계가 아니라 FFrameTime에서 얻어 자동 검증(--fixed-delta)이 재현됩니다. 쿠키 텍스처는 공개 LoadTexture(고정 = 항상 전체 밉 — 30강 밉 스트리밍 대상 밖)로 읽습니다.

    바인딩: 공간 3 무제한 표

    LTC 표 2장, 라이트마다 다른 IES·쿠키 텍스처를 어떻게 셰이더에 넘길까요? 라이트 데이터에 셰이더 가시 힙 칸 번호를 넣고, 메시·지형 루트 시그니처에 공간 3의 무제한 표(메시 루트 #26 RootParam_LightTextures)를 묶어 번호로 읽습니다. 25강의 바인드리스와 같은 발상입니다. 규칙: 새 메시 패스·루트 시그니처도 이 표를 묶는다.

    함정과 교훈

    "Demo_AreaLights 화면 엄청 깜빡임" — 데모 연출도 화면 안정성 대상 데모에서 깜빡이 쿠키를 천장 주 형광등에 걸었더니 방 전체가 0.1초 간격으로 깜빡였습니다(연속 프레임 평균 밝기 폭 19). 엔진 버그가 아니라 연출이 과했던 것이지만, 사용자에게는 "화면이 깜빡인다"로 보입니다. 깜빡임은 작은 벽등으로 옮기고, 쿠키 띠의 프레임마다 출렁이는 잡음을 없애고, 8초에 짧은 꺼짐 3번으로 바꿨습니다(폭 0.02). 규칙으로 남았습니다: "데모 깜빡임 연출은 작은 국소 광원에만, 쿠키 띠에 프레임마다 출렁이는 잡음 금지."
    발광 패널 메시는 광원보다 6cm 뒤에 면광원과 함께 빛나는 패널 메시를 놓으면, 패널이 자기 면광원의 그림자를 만들 수 있습니다. 면광원 그림자의 근평면이 5cm이므로 패널 메시는 광원 가운데보다 6cm 이상 뒤에 둡니다(CLAUDE.md, Scenes/Tests/AreaLights.escene).

    측정: 면광원 하나는 점광원 약 2.7배 비용(32개 메인 2.24ms @1440p). 면광원·IES·쿠키가 없는 씬은 비트 동일(Materials·Decals MD5). 후속 과제로 그래프 머티리얼 라이트 함수, 면광원 소스 텍스처 필터링, 80° 밖·양면 뒤쪽 그림자, .ies 핫 리로드, 아주 긴 면광원의 그림자는 가운데 기준 한 장이라 잘리는 문제가 남아 있습니다.

    정리
    • 면광원 조명 = 셰이딩 점에서 본 다각형 위 BRDF 적분. 코사인은 닫힌 식, GGX는 없다.
    • LTC: GGX ≈ M × 코사인. 다각형을 M−1로 되돌려 코사인 적분으로 계산. M은 64×64 표, 지평선은 구 근사, 원판은 같은 넓이 8각형.
    • 문 덮개·감쇠는 "면에서 가장 가까운 점" 기준 — 가운데 기준이면 긴 면광원 끝이 잘린다.
    • 그림자는 스포트식 한 장 + 결정적 PCSS 64탭(256탭 기준 rmse 1.86 → 0.68).
    • IES는 LM-63 파싱 → θ64×φ32 텍스처, 쿠키는 광원별 투영, 둘 다 공간 3 무제한 표로 바인드리스.

    생각해 볼 문제

    Q1. 면광원의 크기를 두 배로 키웠는데 Intensity는 그대로 두었습니다. 가까이 있는 바닥과 멀리 있는 벽의 밝기는 어떻게 될까요? Intensity가 1m 거리 조도 기준이므로 멀리 있는 벽은 대략 같은 밝기입니다. 휘도 L = Intensity × 1e4 / 면적이라 면적이 커지면 L이 줄어, 가까운 바닥은 빛이 더 넓게 퍼져 하이라이트가 더 넓고 덜 강렬해집니다. 총 빛의 양을 늘리고 싶다면 Intensity를 면적에 비례해 올려야 합니다.
    Q2. PCSS 표본 위치를 픽셀마다 무작위로 회전하면 16탭으로도 얼룩이 사라지지 않을까요? 공간적으로는 계단 덩어리가 잡음으로 바뀌어 덜 눈에 띌 수 있지만, 그 회전이 프레임마다 바뀌면 시간적으로 지글거리고, 고정이라도 픽셀마다 다른 잡음이 화면에 고정된 무늬로 남습니다. TAA는 이런 잡음을 잘 거르지 못합니다(20강). ProjectE는 결정적 Vogel 원판 + 충분한 탭 수를 택했고 고표본 기준과의 rmse로 확인했습니다.
    Q3. 원판 광원을 같은 넓이 8각형이 아니라, 원에 내접하는 8각형으로 근사하면 무엇이 틀릴까요? 내접 8각형은 원보다 넓이가 작아(약 90%) 같은 휘도에서 들어오는 빛이 체계적으로 약해집니다. 같은 넓이가 되도록 꼭짓점 반지름을 약 1.054배 키우면 총 빛(가까운 거리의 형태 계수)이 원과 거의 같아집니다.

    왜 필요한가모자이크가 아니라 도트

    3부 내내 우리는 "더 사실적으로"를 향해 달렸습니다. 이번 강의는 반대 방향입니다. 사용자 요청은 이랬습니다: "모자이크가 아니라 진짜 도트 게임처럼." 3D 장면을 픽셀 아트처럼 보이게 하는 가장 쉬운 방법은 완성된 화면에 모자이크(픽셀화) 후처리를 거는 것입니다. 하지만 그러면 도트 게임처럼 보이지 않습니다.

    • 도트가 반짝인다: 카메라가 1픽셀 움직이면 모자이크 칸 경계가 장면에 대해 움직여, 같은 물체의 도트 색이 매 프레임 바뀝니다(shimmering).
    • 외곽선·조명이 고해상도 기준: 얇은 선, 하이라이트, 그림자 경계가 고해상도로 계산된 뒤 평균되어 탁해집니다.
    • 비용: 고해상도로 다 그린 뒤 버리므로 이득이 없습니다.

    그래서 결정(2026-09-30 사용자 선택)은 "저해상도 렌더 + 확대(포스트 프로세스 모자이크 아님), 카메라에 직교 투영 추가, 설정은 씬 단위 컴포넌트, 범위 = 저해상도·정수 확대·스냅, 픽셀 외곽선, 팔레트/디더링 전부"였습니다.

    핵심 개념저해상도 + 여백으로 그리고, 최근접으로 확대

    도트 하나가 화면 픽셀 N×N이 되도록 장면을 (출력 ÷ N) 해상도로 그립니다. 확대할 때 쌍선형 보간을 쓰면 도트 경계가 흐려지므로 최근접(nearest) 표본을 씁니다 — 출력 픽셀이 속한 소스 텍셀 하나를 그대로 읽습니다. 이 모드에서는 TAA 지터(SceneRenderer.cpp 주석: "지터는 정수 격자 스냅과 충돌"), TAAU(23강), 레이 트레이싱(25강), DDGI(26강)가 꺼집니다. 지터는 도트를 흔들고, 업스케일은 도트 경계를 부드럽게 만들기 때문입니다.

    그런데 왜 사방에 1텍셀 여백(FPixelArtMath::Margin)을 둘까요? 바로 다음 절의 서브픽셀 보정 때문입니다. 확대 단계에서 소스를 최대 반 텍셀 밀어 읽으므로, 화면 가장자리 출력 픽셀이 소스 바깥을 읽지 않도록 여분을 그려 둡니다. 소스가 여백만큼 넓으므로 카메라 투영 범위도 그만큼 넓힙니다(GetSourceExtentScale).

    핵심 개념카메라 도트 스냅과 서브픽셀 보정

    도트가 반짝이는 근본 원인은 "카메라가 도트 크기보다 작게 움직일 때, 장면이 도트 격자에 대해 미끄러진다"는 것입니다. 오른쪽으로 0.3도트 움직이면 물체 가장자리가 도트 칸을 30% 건너 걸쳐, 어떤 도트는 물체 색이 되고 어떤 도트는 배경색이 됩니다. 다음 프레임에 0.6도트가 되면 또 다른 도트가 바뀝니다. 해결책은 두 단계입니다.

    1. 스냅: 직교 카메라 위치를 카메라 Right/Up 축 위 월드 원점 기준 도트 격자에 반올림합니다. 그러면 장면 렌더는 항상 도트 격자에 정확히 맞춰지고, 같은 물체는 매 프레임 같은 도트 패턴이 됩니다.
    2. 서브픽셀 보정: 그런데 스냅만 하면 카메라가 도트 단위로 뚝뚝 끊겨 움직입니다(PixelSize 4면 4픽셀씩). 그래서 반올림에서 버린 나머지(−0.5~0.5도트)를 기억해 두었다가, 확대 단계에서 소스를 읽는 좌표를 그만큼 밉니다. 화면에서는 도트들이 통째로 1픽셀 단위로 부드럽게 미끄러지고, 도트 내용은 바뀌지 않습니다.
    static FSnapResult SnapToTexelGrid(const FVector3& Position, const FVector3& Right, const FVector3& Up, float TexelWorldSize)
{
	...
	// 큰 좌표에서도 정밀도를 지키도록 격자 번호는 double로 계산
	const double AlongRight = static_cast<double>(FVector3::Dot(Position, Right)) / TexelWorldSize;
	const double AlongUp    = static_cast<double>(FVector3::Dot(Position, Up)) / TexelWorldSize;
	const double SnapRight  = std::round(AlongRight);
	const double SnapUp     = std::round(AlongUp);

	Result.Remainder       = FVector2(static_cast<float>(AlongRight - SnapRight), static_cast<float>(AlongUp - SnapUp));
	Result.IndexRight      = static_cast<int64>(SnapRight);
	Result.IndexUp         = static_cast<int64>(SnapUp);
	Result.SnappedPosition = Position - Right * (Result.Remainder.X * TexelWorldSize) - Up * (Result.Remainder.Y * TexelWorldSize);
	return Result;
}

    도트 하나의 월드 크기는 직교 높이 × PixelSize / 출력 세로(GetTexelWorldSize)입니다. 격자 번호를 double로 계산하는 주석에 주목하세요. 월드 좌표가 수만 cm인 큰 맵에서 float로 나누고 반올림하면, 같은 위치가 프레임마다 다른 격자 칸으로 떨어질 수 있습니다. 격자 번호(IndexRight/IndexUp)는 디더 무늬의 원점(mod 4)으로도 쓰여, 디더 무늬가 화면이 아니라 월드에 붙어 카메라와 함께 움직이게 합니다.

    확대 셰이더의 첫 줄이 이 보정을 그대로 씁니다: 출력 픽셀 위치 → (출력 중심 기준) ÷ PixelSize → 소스 중심에 맞춤 → + 서브픽셀 오프셋 → floor. 출력이 PixelSize로 나누어떨어지지 않아도 중심을 맞추므로 좌우 대칭입니다.

    // 1) 출력 픽셀 → 소스 텍셀 (SV_Position은 픽셀 중심)
const float2 SourcePosition = (Input.Position.xy - OutputSize * 0.5f) / PixelSize + float2(SourceSize) * 0.5f + SubPixelOffset;
const int2   Texel          = clamp(int2(floor(SourcePosition)), int2(0, 0), SourceSize - 1);
float3 Color = SourceColor.Load(int3(Texel, 0)).rgb;

    움직이는 물체 도트 스냅

    카메라를 스냅해도, 물체가 스스로 0.3도트씩 움직이면 그 물체 테두리는 여전히 반짝입니다. 2026-10-02 요청("카메라가 이동할 때 자글자글하지 않게, 옵션으로")으로 bSnapMovingObjects를 넣었습니다. 설계 규칙(PixelArtObjectSnap.cpp 머리 주석)이 섬세합니다.

    • 렌더 동안만: 씬 렌더 직전에 월드 행렬의 이동값만 바꾸고 렌더가 끝나면 정확히 되돌립니다. 게임·물리 위치는 그대로입니다. 그래서 CLAUDE.md는 "렌더 밖에서 스냅 값을 기대하지 않는다"고, 그리고 이 코드는 정확히 되돌리므로 트랜스폼 캐시 무효화(InvalidateWorldCache)가 필요 없다고 적어 둡니다.
    • 한 번이라도 움직인 최상위 루트만: 씬에 정적/이동 구분이 없으므로 위치 변화를 추적합니다. 정적 물체는 건드리지 않습니다 — 바닥 타일 하나하나를 각자 반올림하면 타일 사이에 이음새가 생기기 때문입니다. 멈춘 뒤에도 계속 스냅합니다(멈추는 순간 반 도트 튀지 않게).
    • 하위 트리 통째로: 루트의 이동량 하나를 자식 전체(스킨 뼈 포함)에 더합니다. 캐릭터의 팔다리가 따로 반올림되면 몸이 찢어집니다.
    • 소켓 부착: 손에 든 검은 계층 부모가 아니라 대상 모델의 최상위 루트 이동량을 따릅니다 — 들고 있는 물체가 캐릭터와 따로 떨지 않게.

    핵심 개념깊이로 그리는 외곽선과 하이라이트

    도트 게임의 물체는 보통 1px 어두운 외곽선을 가집니다. 저해상도 깊이 버퍼로 이것을 만듭니다: 이웃 4칸 중 깊이가 문턱(기본 25cm)보다 먼 칸이 있으면, 이 텍셀은 앞 물체의 가장자리입니다 — 외곽선은 앞 물체 쪽 1px에 생깁니다. 볼록 모서리(상자의 모서리, 계단 끝)에는 반대로 밝은 1px 하이라이트를 줍니다.

    // 축 방향 단면의 꺾인 각도(라디안, 앞뒤 이웃이 모두 같은 물체일 때만, 아니면 0). 볼록 능선이면 양수.
// 깊이 차 대신 각도로 재야 구 가장자리처럼 화면에 비스듬한 곡면이 모서리로 잘못 잡히지 않는다
float RidgeBend(int2 Texel, int2 Axis, int2 SourceSize)
{
	const float Center = GetViewPosition(Texel, SourceSize).z;
	const float Next   = GetViewPosition(Texel + Axis, SourceSize).z;
	const float Prev   = GetViewPosition(Texel - Axis, SourceSize).z;
	if (abs(Next - Center) >= DepthThreshold || abs(Prev - Center) >= DepthThreshold)
	{
		return 0.0f;
	}
	const float Texel1 = TexelWorldSize(Center);
	return atan((Next - Center) / Texel1) - atan((Center - Prev) / Texel1);
}

    양자화와 디더

    옛 게임기는 색 수가 적었습니다. ColorLevels(채널당 단계 수)를 주면 감마 공간에서 색을 단계로 자르고, 단계 사이 경계가 띠처럼 보이지 않도록 4×4 Bayer 행렬로 디더링합니다. Bayer 행렬은 0~15를 "가까운 칸끼리 값이 최대한 멀게" 배치한 표라, 문턱을 칸마다 달리 주면 중간 밝기가 규칙적인 점 무늬로 표현됩니다. 무늬 원점은 위에서 본 카메라 격자 번호(mod 4)라 카메라가 움직여도 무늬가 화면에 들러붙지 않습니다.

    함정과 교훈"여전히 자글거림"을 숫자로 잡기

    2026-10-02 사용자 보고: "에디터 플레이 중 카메라가 부드럽게 움직일 때 자글거림, 직교만." 카메라 스냅은 이미 있었는데 왜일까요? 여기서 이 강의의 가장 중요한 교훈 — 검증 방법 — 이 나옵니다.

    이론상 0이어야 하는 실험을 설계한다 카메라를 정확히 도트 N칸 옮긴 두 장면을 렌더하면, 스냅과 보정이 완벽할 때 두 번째 화면은 첫 번째를 N × PixelSize 픽셀 민 것과 완전히 같아야 합니다(가장자리 제외). 둘을 밀어 겹쳐 다른 픽셀 비율을 재면, 0이 아닌 만큼이 "카메라에 고정된 무언가"입니다. 정지 화면을 눈으로 보는 것으로는 판단할 수 없는 문제를 숫자로 바꾼 것입니다. 도트 사이 위치(0.25칸 = PixelSize/4 px)도 같은 방식으로 잽니다.
    1차: SSAO가 범인 — 0.48% → 0.105% 도트 5칸 이동 실험에서 수정 전 0.48%(기둥 테두리 전체 등)가 달랐습니다. SSAO만 끄면 0.22%. SSAO가 반해상도(도트 한 칸 이동에 반 칸씩 어긋남)이고 화면 고정 노이즈를 썼기 때문입니다. 카메라가 도트 단위로 움직이면 장면은 격자에 맞춰 움직이는데 노이즈 무늬는 화면에 붙어 있으니, 물체 위에서 노이즈가 흐릅니다. 수정: 픽셀 아트 렌더 동안 SSAO는 전체 해상도 + 월드 도트 격자 노이즈(GridCellNoise(픽셀 + GridOrigin), 카메라 스냅 격자 번호). 메인 패스 업샘플은 버퍼 폭으로 1/2 판별을 바꿔 → 0.105%(최대 밝기 차 148 → 31). 그래서 규칙: 화면 공간 효과를 추가·수정할 때 픽셀 아트에서는 화면 고정 노이즈·반해상도를 쓰지 않는다.
    2차: 하이라이트가 "0의 부호"에 기댔다 — 0.31% → 0.000% 사용자 재보고("여전히 자글거림"). 정수 도트 이동은 깨끗해졌지만 도트 경계를 넘을 때 테두리 0.31%가 바뀌었고, 외곽선/하이라이트만 끄면 0.000%. 원인은 원래 하이라이트 판정(깊이로 재구성한 노멀의 볼록 검사)이 같은 평면 이웃에서 정확히 0이 되는 식이었다는 것입니다. 이론상 0인 값에 부동소수점 오차가 붙으면 부호가 위치마다 달라져 모서리 전체가 켜졌다 꺼졌습니다 — 원래 보이던 하이라이트 선 상당수가 사실 이 오차의 산물이었습니다. 하이라이트를 그림 28-3의 깊이 능선(각도 30~60도, 큰 쪽 한 픽셀, 동률은 왼쪽/위 고정, 곡면은 문턱 아래)으로 바꾸자 도트 0.75/1/1.5/2.25칸 이동 모두 0.000%(런타임), 에디터 뷰포트도 정수 px 이동 0.000%가 되었습니다. 깊이 2차 차분으로 재면 구 가장자리가 금 간 것처럼 잡혀 각도로 바꿨다는 기록도 남아 있습니다.     3부를 마치며 사실적 렌더링(21~27강)과 픽셀 아트(28강)는 정반대 목표처럼 보이지만, 같은 교훈을 공유합니다. 화면에 고정된 무작위성은 움직임에서 드러나고, "이론상 0" 또는 "고표본 기준"과의 차이를 숫자로 재야 진짜 원인에 닿으며, 새 기능은 꺼져 있을 때 기존 화면과 비트 동일해야 안심하고 쌓을 수 있습니다. 4부에서는 이렇게 쌓은 화면을 예산 안에 넣는 성능 이야기를 합니다.

    Q1. 서브픽셀 보정을 확대 단계가 아니라 렌더 단계(카메라 위치)에 그대로 두면 어떻게 될까요? 그러면 스냅을 안 한 것과 같습니다. 카메라가 도트 미만으로 움직일 때마다 장면이 도트 격자에 대해 미끄러져 도트 색이 바뀌므로 반짝임이 돌아옵니다. 보정은 "이미 완성된 도트 그림 전체"를 화면 픽셀 단위로 미는 것이어야 도트 내용이 고정됩니다.
    Q2. 정적 바닥 타일들도 물체 스냅 대상에 넣으면 어떤 문제가 생길까요? 타일마다 자기 위치를 각자 반올림하므로, 원래 딱 붙어 있던 이웃 타일이 서로 다른 방향으로 최대 반 도트씩 밀려 틈이나 겹침(이음새)이 생깁니다. 그래서 한 번이라도 움직인 최상위 루트만 스냅하고, 정적 물체는 카메라 스냅만으로 격자에 맞춥니다.
    Q3. 새 화면 공간 효과(예: 화면 공간 그림자)를 만들며 블루 노이즈 텍스처를 화면 좌표로 타일링했습니다. 픽셀 아트 모드에서 어떻게 검증하고 고칠까요? 카메라를 정확히 도트 N칸 옮긴 두 프레임을 N × PixelSize px 밀어 비교해 차이 비율을 잽니다. 노이즈가 화면 고정이면 0이 아니게 나옵니다. 수정은 SSAO처럼 노이즈 좌표를 카메라 스냅 격자 번호(월드 도트 격자)에 고정하고, 효과 해상도를 도트 해상도 그대로(반해상도 금지) 두는 것입니다.
