    함께 플레이하기 — 네트워크

    한 대의 PC에서 돌던 게임 세계를 여러 대가 나눠 보게 만듭니다. 누가 진실을 정하는지, 무엇을 얼마나 자주 보내는지, 그리고 빛의 속도보다 느린 인터넷 위에서 "누르는 즉시 움직이는" 느낌을 어떻게 만드는지를 순서대로 봅니다.

    왜 필요한가두 대의 컴퓨터가 "같은 세계"를 보려면

    지금까지의 엔진은 프로세스 하나 안에서 세계 전체를 계산했습니다. 입력을 받고, 스크립트와 물리를 돌리고, 그 결과를 그렸습니다. 이제 친구와 같은 맵에서 놀고 싶다면 어떻게 될까요? 두 사람의 PC는 각자 자기 메모리에 세계를 들고 있고, 둘을 잇는 것은 느리고, 가끔 패킷을 잃어버리고, 순서도 뒤섞는 네트워크뿐입니다.

    그렇다고 매 프레임 세계 전체를 통째로 보낼 수는 없습니다. 씬에 엔티티가 수천 개 있고 각자 컴포넌트를 여러 개 갖고 있으니, 60fps로 통째로 보내면 회선이 버티지 못합니다. 또 두 PC가 각자 계산하면 부동소수점 오차나 입력 타이밍 차이로 조금씩 어긋나다가 결국 전혀 다른 세계가 됩니다. 멀티플레이 엔진은 이 두 질문에 답해야 합니다.

    1. 누가 진실을 정하는가? (둘의 결과가 다를 때 어느 쪽을 믿나)
    2. 무엇을, 얼마나 자주, 어떤 방식으로 보내는가? (회선과 지연의 제약 안에서)

    이 강의는 첫 번째 질문과, 두 번째 질문을 위한 "배관"(연결, 메시지, 버전 확인)을 다룹니다. 무엇을 보낼지는 56강, 지연을 숨기는 기술은 57~59강의 주제입니다.

    핵심 개념P2P와 클라이언트-서버, 그리고 권한 서버

    여러 기계가 통신하는 방식은 크게 둘입니다.

    • P2P(peer-to-peer): 모든 참가자가 서로 직접 연결됩니다. 서버가 필요 없지만, 누가 진실인지 정하기 어렵습니다. 대표적인 변형인 락스텝(lockstep)은 모두가 "입력만" 주고받고 같은 입력으로 같은 시뮬레이션을 돌립니다. 대신 시뮬레이션이 비트 단위로 결정적(deterministic)이어야 하고, 가장 느린 참가자의 입력이 올 때까지 모두가 기다려야 합니다. RTS 게임에서 많이 씁니다.
    • 클라이언트-서버(client-server): 한 기계(서버)가 세계를 시뮬레이션하고, 나머지(클라이언트)는 입력을 서버로 보내고 결과를 받아 그립니다. 통신은 별 모양(star)입니다.

    클라이언트-서버 구조에서 서버가 모든 판정을 내리면 이를 권한 서버(authoritative server)라고 합니다. "내 총알이 맞았다"를 클라이언트가 정하면 치트를 막을 수 없습니다. 클라이언트는 메모리를 조작할 수 있는 사용자의 PC에서 돌기 때문입니다. 서버가 판정하면 클라이언트는 기껏해야 "총을 쐈다"는 입력만 보낼 수 있고, 맞았는지는 서버가 정합니다. 언리얼 엔진도 같은 구조입니다.

    핵심 개념지연, 손실, 지터 — 네트워크가 게임에 주는 세 가지 고통

    네트워크 품질은 세 숫자로 요약됩니다.

    • 지연(latency): 패킷이 한쪽에서 다른 쪽까지 가는 시간. 보통 왕복 시간(RTT, round-trip time) 또는 핑(ping)으로 잽니다. 같은 도시 안이라도 수십 ms, 대륙을 건너면 100~200ms가 흔합니다. 빛의 속도라는 물리 한계가 있어 줄일 수 없는 부분이 있습니다.
    • 손실(loss): 보낸 패킷이 도착하지 않는 비율. 와이파이나 혼잡한 회선에서 몇 %씩 생깁니다.
    • 지터(jitter): 지연의 흔들림. 33ms 간격으로 보낸 패킷이 20ms, 50ms, 31ms 간격으로 도착하는 것. 순서가 바뀌어 도착하기도 합니다(재정렬).

    개발 중에는 대개 같은 PC나 같은 공유기 안에서 테스트하므로 지연이 거의 0입니다. 그래서 "내 PC에서는 잘 되는데"가 멀티플레이에서 가장 위험한 말입니다. ProjectE는 일부러 나쁜 망을 흉내 내는 디버그 기능을 둡니다. INetTransport::SetSimulation이 보내는 패킷에 지연과 손실을 넣고(GNS의 FakePacketLag/FakePacketLoss 설정), 앱 인자 --net-lag <ms> --net-loss <%>로 켭니다. 이후 강의에 나오는 측정은 대부분 "지연 100ms, 손실 5%" 같은 조건에서 한 것입니다.

    핵심 개념TCP와 UDP, 신뢰 채널과 비신뢰 채널

    인터넷의 전송 프로토콜은 대표적으로 둘입니다.

    TCPUDP
    전달 보장잃어버리면 다시 보냄없음 (보내고 끝)
    순서보낸 순서대로 전달도착한 순서 그대로
    단위바이트 스트림 (메시지 경계 없음)데이터그램 (메시지 하나 = 패킷 하나)
    게임에서의 문제패킷 하나가 빠지면 뒤의 모든 데이터가 재전송을 기다린다 (머리 막힘, head-of-line blocking)신뢰가 필요한 메시지는 직접 재전송·순서를 구현해야 한다

    게임 데이터에는 성격이 다른 두 종류가 섞여 있습니다.

    • 반드시 도착해야 하는 것: "플레이어 3 입장", "상자가 생성됨", "체력이 40이 됨", RPC 호출. 하나라도 빠지면 세계가 영원히 어긋납니다.
    • 최신 값만 의미 있는 것: 매 틱의 위치, 입력 상태. 100ms 전 위치가 지금 도착해 봐야 쓸모가 없고, 다음 패킷이 곧 새 값을 가져옵니다. 이것을 재전송하느라 새 값까지 기다리게 만드는 것이 TCP의 머리 막힘입니다.

    그래서 게임은 UDP 위에 "필요한 메시지만 신뢰성을 붙인" 자체 프로토콜을 씁니다. ProjectE에서는 이 선택이 ENetReliability 하나로 드러납니다.

    enum class ENetReliability : uint8
{
	Reliable,   // 순서 보장 + 재전송
	Unreliable, // 손실 가능 (최신 상태만 의미 있는 데이터)
};

    이 신뢰 계층을 직접 짜는 대신 ProjectE는 Valve의 GameNetworkingSockets(GNS)를 씁니다. Steam의 네트워크 라이브러리를 오픈소스로 공개한 것으로, UDP 위에 메시지 단위의 신뢰/비신뢰 전송, 암호화, 연결 품질 통계를 제공합니다. 0강의 기준("표준 해법이 있고, 직접 짜도 배울 것보다 시간이 더 드는 것")에 해당합니다. Plans.md Phase 17의 결정에는 "protobuf 때문에 빌드가 무거워도 GNS 유지"라고 적혀 있습니다. GNS가 의존하는 protobuf는 abseil에 의존하지 않는 마지막 버전(v21.12)으로 고정했습니다.

    규칙: GNS 헤더는 Network 모듈 .cpp에서만 GNS와 protobuf 헤더는 거대하고 매크로가 많습니다. 그래서 GnsTransport.cpp 안에만 넣고, 나머지 엔진은 아래의 INetTransport 인터페이스만 봅니다. 1강의 "공개 헤더에 Windows.h를 넣지 않는다"와 같은 원칙입니다.

    ProjectE에서는INetTransport — 전송 계층 추상화와 루프백 테스트

    네트워크 코드는 테스트하기 어렵기로 유명합니다. 실제 소켓을 열면 포트가 겹칠 수 있고, 타이밍이 매번 달라지고, 방화벽이 끼어듭니다(뒤에서 실제로 겪은 일을 봅니다). 그래서 ProjectE는 "메시지를 주고받는다"는 개념만 인터페이스로 뽑았습니다.

    // 메시지 단위 전송 계층 추상화. 구현: GameNetworkingSockets(CreateGnsTransport), 테스트용 루프백(FLoopbackTransport).
// 모든 함수는 메인 스레드에서 호출한다. 이벤트는 Poll에서만 나온다 (콜백 없음)
class INetTransport
{
public:
	// 서버: 모든 주소의 Port에서 접속 대기. GNS는 포트 0(자동 할당)을 받지 않는다

	virtual FNetConnectionId Connect(const std::string& Address) = 0;
	virtual bool Send(FNetConnectionId Connection, const void* Data, uint32 Size, ENetReliability Reliability) = 0;
	virtual void Disconnect(FNetConnectionId Connection, const std::string& Reason) = 0;
	// 쌓인 이벤트를 OutEvents 뒤에 붙인다 (매 틱)
	virtual void Poll(std::vector<FNetEvent>& OutEvents) = 0;
	...
	// 디버그: 보내는 패킷에 지연/손실을 흉내 낸다 (GNS: 프로세스 전역 설정). 0이면 끔
	virtual void SetSimulation(int32 LatencyMs, float LossPercent) {}
};

    두 가지 설계 결정이 보입니다. 첫째, 이벤트는 Poll에서만 나옵니다. 네트워크 라이브러리는 흔히 "메시지가 오면 이 콜백을 불러 줄게"라는 방식을 쓰는데, 콜백은 언제 어느 스레드에서 불릴지 모릅니다. 게임 루프는 매 틱 Poll로 쌓인 연결/끊김/메시지 이벤트를 꺼내 순서대로 처리하므로, ECS 순회 도중에 메시지가 끼어드는 일이 없습니다. 둘째, 인터페이스가 아는 것은 "연결 ID"와 "바이트 덩어리"뿐입니다. 메시지의 의미는 위층이 정합니다.

    루프백 구현은 아주 단순합니다. 같은 "허브" 객체를 공유하는 전송 계층끼리, 보낸 메시지를 상대의 대기열에 넣어 두었다가 다음 Poll에서 꺼내 줍니다.

    ProjectE에서는핸드셰이크와 NetProtocolVersion

    연결이 수립되었다고 바로 게임 메시지를 주고받으면 안 됩니다. 상대가 같은 게임, 같은 버전, 같은 맵인지 먼저 확인해야 합니다. 이 첫 대화를 핸드셰이크(handshake)라고 합니다. 모든 메시지는 [uint8 종류][본문] 형식이고, 처음 세 종류가 핸드셰이크용입니다.

    // 프로토콜을 바꾸면(메시지 추가/필드 변경) NetProtocolVersion을 올린다 — 버전이 다르면 접속을 거부한다
inline constexpr uint32 NetProtocolVersion = 12; // 2: 복제 메시지, 3: 트랜스폼 스냅샷, 4: RPC, 5: 입력 커맨드, ...
                                                 // 7: 캐릭터 무브/ack (예측), ... 12: 능력 발동 요청/결과
enum class ENetMessageType : uint8
{
	Hello   = 1, // 클라이언트 → 서버: 접속 요청 (버전/프로젝트/씬/이름)
	Welcome = 2, // 서버 → 클라이언트: 입장 허락 (플레이어 ID)
	Reject  = 3, // 서버 → 클라이언트: 거부 사유 (직후 연결을 닫는다)
	...
	GameBase = 32, // 입장 후 게임 메시지는 여기부터 (FNetDriver::OnGameMessage로 전달)
	...
};

{
	return std::format("네트워크 프로토콜 버전 불일치 (서버 {}, 클라이언트 {})", NetProtocolVersion, Hello.ProtocolVersion);
}

if (Hello.ProjectName != Session.ProjectName)     { ... "프로젝트 불일치 ..." }
if (Hello.SceneAsset != Session.SceneAsset)       { ... "씬 불일치 ..." }

    왜 이렇게 엄격할까요? 이후 강의에서 볼 메시지들은 모두 "상대도 나와 똑같이 해석한다"는 가정 위에 있습니다. 예를 들어 복제 메시지는 컴포넌트 값을 리플렉션 프로퍼티 선언 순서대로 바이트로 이어 붙입니다(56강). 한쪽 빌드에 프로퍼티가 하나 더 있으면 뒤의 모든 바이트가 엉뚱한 필드로 읽힙니다. 이런 문제는 크래시가 아니라 "가끔 이상한 값"으로 나타나서 찾기가 매우 어렵습니다. 그래서 입구에서 막는 것입니다.

    규칙: 메시지 형식을 바꾸면 NetProtocolVersion을 올린다 주석에 적힌 이력이 곧 8부의 목차입니다. 2(복제) → 3(트랜스폼 스냅샷) → 4(RPC) → 5(입력) → 7(캐릭터 무브/ack, 예측) → 11(루트 모션 무브) → 12(능력 발동 요청/결과). 병렬 트랙으로 작업할 때는 각 트랙이 필요하면 올리고 머지할 때 메인이 최종값을 정하는 규칙을 두었습니다(Plans.md Phase 23~26).

    씬 이름까지 같아야 하는 이유는 56강의 "정적 NetId" 때문입니다. 서버와 클라이언트가 같은 씬 파일을 로드해야 씬에 원래 있던 엔티티들이 같은 번호를 받습니다.

    LAN 탐색

    IP 주소를 입력하지 않고 같은 공유기 안의 방을 찾으려면 브로드캐스트를 씁니다. 네트워크 안의 모든 기계에 "여기 방 있나요?"를 외치고, 호스트가 "있어요(방 이름, 인원, 맵, 게임 포트)"라고 답하는 방식입니다. ProjectE의 FLanDiscovery는 Winsock UDP로 이를 구현합니다(탐색 포트 7778, 게임 포트 기본 7777). 질의는 브로드캐스트 주소와 127.0.0.1 두 곳에 보냅니다 — 브로드캐스트가 막힌 환경에서도 같은 PC의 서버는 찾게 하려는 것입니다. 런타임 --join-lan은 최대 2초 검색한 뒤 첫 세션에 접속하고, Lua에는 Net.FindSessions/GetSessions/Host/Connect가 있습니다.

    함정과 교훈방화벽 확인 창과 NetBindPolicy

    실제로 겪은 일 (2026-10-03, 사용자 보고: "개인/공용 네트워크에서 실행 허용 창이 자꾸 뜸") 작업 중 Windows 방화벽의 "이 앱이 네트워크에 접근하도록 허용하시겠습니까?" 창이 계속 떴습니다. 원인은 두 가지가 겹친 것이었습니다.
    1. Windows 방화벽은 프로그램이 모든 주소(0.0.0.0)에서 접속을 기다릴 때 허용 여부를 묻고, 그 허용은 exe 경로마다 따로 기억합니다.
    2. ProjectE는 병렬 작업용 git 워크트리를 여러 개 두므로, 같은 테스트 exe가 경로만 다르게 여러 벌 있었습니다. 그리고 실제 소켓을 여는 단위 테스트(GNS 서버·클라이언트, LAN UDP)가 0.0.0.0에 바인드했습니다.
    즉 워크트리를 하나 만들 때마다, 자동 검증을 돌릴 때마다 새 경로의 exe가 0.0.0.0을 열어 확인 창이 떴습니다.

    해결은 두 단계였습니다. 먼저 실제 소켓을 여는 단위 테스트 4곳은 환경 변수 E_TEST_SOCKETS=1(Build.ps1 -Test -SocketTests)일 때만 돌고, 기본은 건너뛰며 로그를 남기게 했습니다. 다음으로 "어느 주소에서 기다릴지"를 정하는 정책을 한 곳으로 모았습니다.

    // 서버 대기·LAN 응답 소켓을 어느 주소에 열지 정한다.
// Windows 방화벽 확인 창("개인/공용 네트워크에서 허용")은 모든 주소(0.0.0.0 / ::)에서 대기할 때 exe 경로마다 뜨고,
// 루프백(127.0.0.1)에서만 대기하면 뜨지 않는다.
//   루프백 전용 = 같은 PC 안의 접속만: 자동 검증(--exit-after) 실행, 에디터 네트워크 플레이와 그 자식 프로세스
//   공개 = 실제 LAN/인터넷: --host, 사람이 실행한 전용 서버 (처음 한 번 확인 창은 정상)
// 명령줄 --net-local(루프백 강제) / --net-public(공개 강제)이 앱의 기본값보다 우선한다
namespace NetBindPolicy
{
	void Configure(bool bDefaultLoopbackOnly);
	bool IsLoopbackOnly();
}
    SteamNetworkingIPAddr Address;
Address.Clear(); // 모든 주소 (IPv6 dual-stack)
if (NetBindPolicy::IsLoopbackOnly())
{
	Address.SetIPv4(0x7F000001, 0); // 127.0.0.1 — 같은 PC 전용 (방화벽 확인 창 없음)
}
Address.m_port = Port;

    LAN 방 알림(FLanDiscovery::StartHost)도 루프백 전용 실행이면 아예 열지 않습니다. 같은 PC 안에서는 방을 알릴 이유가 없고, 알림 소켓이 0.0.0.0을 열면 확인 창이 뜨기 때문입니다. 새 앱은 세션을 열기 전에 NetBindPolicy::Configure(IsAutomationRun())를 부르고, 0.0.0.0에 소켓을 여는 새 코드는 IsLoopbackOnly()를 따르는 것이 규칙이 되었습니다.

    교훈: "보안 정책도 실행 환경의 일부다" 코드는 정상이었습니다. 문제는 운영체제가 "모든 주소에서 대기"를 사용자에게 묻는 동작이었고, 개발 방식(워크트리 여러 개)이 그것을 증폭했습니다. 네트워크 코드는 기능뿐 아니라 "어느 주소에서, 어떤 실행에서 소켓을 여는가"까지 설계 대상입니다. 사람이 실행한 --host나 에디터 네트워크 플레이에서 처음 한 번 뜨는 확인 창은 실제 LAN을 위해 필요한 정상 동작으로 남겼습니다.

    마지막으로 검증 방법입니다. 멀티플레이 변경 뒤에는 .\Scripts\Verify.ps1 -Multiplayer가 전용 서버 하나와 런타임 클라이언트 둘을 띄워 입장 여부, 로그 오류, 클라이언트마다의 스크린샷을 확인합니다. -ExtraArgs "--net-lag 100 --net-loss 5"를 붙이면 불량 망에서 같은 확인을 합니다. 단위 테스트(루프백)는 로직을, 이 스크립트는 실제 소켓과 프로세스 경계를 검증합니다.

    정리
    • ProjectE는 권한 서버형 클라이언트-서버 구조다. 리슨 서버와 전용 서버를 모두 지원하고, Standalone은 "네트워크 없는 서버"로 취급한다.
    • 네트워크는 지연·손실·지터를 가진다. --net-lag/--net-loss로 일부러 나쁜 망에서 시험한다.
    • 게임은 UDP 위에서 신뢰(생성·상태·RPC)와 비신뢰(위치·입력) 채널을 나눠 쓴다. ProjectE는 GNS를 쓰고 ENetReliability로 고른다.
    • INetTransport가 GNS와 루프백을 감싸, 네트워크 로직을 소켓 없이 결정적으로 테스트한다. 이벤트는 Poll로만 나온다.
    • 핸드셰이크는 프로토콜·엔진 버전, 프로젝트, 씬이 모두 같을 때만 통과한다. 형식을 바꾸면 NetProtocolVersion을 올린다.
    • 자동 검증·에디터 플레이처럼 같은 PC 전용인 실행은 127.0.0.1에서만 대기한다(NetBindPolicy) — 방화벽 확인 창 문제의 해결.

    생각해 볼 문제

    Q1. 모든 메시지를 신뢰 채널로 보내면 구현은 단순해집니다. 위치 업데이트까지 신뢰 채널로 보내면 손실 5% 망에서 어떤 일이 생길까요? 손실된 위치 패킷 하나를 재전송하는 동안, 그 뒤에 보낸 더 새로운 위치들도 순서 보장 때문에 전달이 막힙니다(머리 막힘). 화면의 물체는 잠깐 멈췄다가 밀린 값들이 한꺼번에 도착하며 튑니다. 위치는 다음 패킷이 곧 최신 값을 가져오므로 잃어버려도 괜찮은 데이터이고, 그래서 ProjectE는 트랜스폼 변화를 비신뢰 스냅샷으로 보냅니다(56강).
    Q2. 핸드셰이크에서 엔진 버전과 프로토콜 버전을 둘 다 확인합니다. 프로토콜 버전만 확인하면 부족한 경우는 언제일까요? 복제 메시지는 컴포넌트의 리플렉션 프로퍼티를 선언 순서대로 씁니다. 메시지 "형식"(프로토콜)은 그대로인데 어떤 컴포넌트에 프로퍼티가 하나 추가되면, 바이트 배치가 달라집니다. 이런 변화는 NetProtocolVersion을 올리지 않으므로 엔진 버전과 프로젝트(게임 모듈이 등록한 타입) 확인이 함께 필요합니다. 그래도 빠지는 경우를 대비해 ReadComponent는 프로퍼티 개수가 다르면 그 컴포넌트를 거부합니다.
    Q3. 자동 검증 실행이 127.0.0.1에서만 대기하면, 다른 PC의 클라이언트는 접속할 수 없습니다. 이것이 문제가 되지 않는 이유는? 자동 검증(--exit-after)과 에디터 네트워크 플레이는 정의상 "같은 PC 안에서 서버와 클라이언트를 함께 띄우는" 실행입니다. 외부 접속이 필요 없으므로 루프백 전용이 맞고, 덕분에 방화벽 확인 창도 뜨지 않습니다. 실제 LAN이 필요하면 --net-public으로 강제할 수 있고, 사람이 실행한 --host/전용 서버는 기본이 공개 대기입니다.

    왜 필요한가서버의 세계를 클라이언트 화면에 옮기기

    55강에서 서버가 진실을 정한다고 했습니다. 그러면 클라이언트는 서버가 계산한 결과를 받아 자기 씬에 반영해야 합니다. 이것을 복제(replication)라고 합니다. 그런데 단순하게 생각하면 바로 막힙니다.

    • 모든 것을 보낼 수는 없다: 바닥 타일, 배경 나무, 조명 대부분은 게임 중에 바뀌지 않습니다. 클라이언트도 같은 씬 파일을 갖고 있으니 보낼 필요가 없습니다.
    • 매번 전부 보낼 수도 없다: 체력은 몇 초에 한 번 바뀌는데 매 틱 보낼 이유가 없습니다.
    • "그 상자"를 어떻게 가리키나: 서버의 엔티티 핸들(인덱스 + 세대)은 서버 메모리 안에서만 의미가 있습니다. 클라이언트의 같은 상자는 다른 핸들을 가집니다.
    • 도착 간격이 흔들린다: 위치를 받은 순간 그대로 적용하면, 지터 때문에 물체가 빨라졌다 느려졌다 하며 덜컥거립니다.

    이 강의는 이 네 문제를 ProjectE가 어떻게 풀었는지 봅니다.

    핵심 개념무엇을 보낼까 — 리플렉션 기반 컴포넌트 값 복제

    복제 대상은 엔티티 단위로 고릅니다. 에디터에서 ReplicatedComponent를 붙인 엔티티만 복제됩니다. 그리고 그 엔티티에서 무엇을 보낼지는 따로 적지 않습니다. 인스펙터와 직렬화가 이미 쓰는 리플렉션 정보(9강의 FTypeInfo/FPropertyInfo)를 그대로 씁니다. "인스펙터에 보이는 값 = 저장되는 값 = 복제되는 값"이 기본입니다.

    // 복제 대상 표시 (에디터에서 붙인다). 이 엔티티의 리플렉션 등록 컴포넌트 값을 서버 → 클라이언트로 보낸다.
// 제외: TF_NoReplicate 타입(계층/프리팹 연결 등), PF_NoReplicate 프로퍼티, 리소스 핸들(클라이언트가 경로로 다시 해석)
struct FReplicatedComponent
{
	int32 OwnerPlayerId = -1; // 소유 플레이어 (서버가 정한다, -1 = 서버 소유). 저장하지 않지만 복제는 된다
};

// 런타임 네트워크 ID (리플렉션 미등록 — 저장/복제/플레이 복제 대상 아님).
struct FNetIdComponent
{
	uint32 NetId = 0;
};

    이 방식의 장점은 새 컴포넌트가 공짜로 복제된다는 것입니다. 게임 모듈이 FTurretComponent를 리플렉션에 등록하면, 별도 코드 없이 그 값이 클라이언트에 도착합니다. 대신 "보내면 안 되는 것"을 표시하는 장치가 필요합니다.

    바뀐 것만, 컴포넌트 단위로

    서버는 각 복제 엔티티의 컴포넌트마다 마지막으로 보낸 바이트를 기억합니다. 전송 틱이 되면 컴포넌트를 다시 바이트로 쓰고, 지난번과 다르면 그 컴포넌트 전체를 보냅니다.

    FBinaryWriter Value;

    필드 단위로 더 잘게 비교할 수도 있지만, ProjectE는 컴포넌트 단위를 택했습니다. 비교가 바이트 배열 비교 한 번으로 끝나고, 이 상태 메시지는 신뢰 채널로 가므로 "지난번 값을 받았다"는 가정이 항상 성립합니다. 그래서 연결마다 따로 기록할 필요 없이 모든 연결이 같은 기준을 공유합니다. 새로 들어온 플레이어만 예외로, 입장할 때 모든 복제 엔티티의 현재 값을 한꺼번에(bFull) 받습니다.

    엔티티를 가리키는 프로퍼티(예: "타깃 엔티티")는 핸들을 그대로 쓰면 안 되므로, 쓸 때 NetId로 바꾸고 읽을 때 다시 엔티티로 바꿉니다(FEntityToNetId/FNetIdToEntity). 이것이 다음 절의 주제입니다.

    핵심 개념NetId — 두 기계가 같은 엔티티를 같은 이름으로 부르기

    NetId는 "네트워크 너머에서도 통하는 엔티티 번호"입니다. 두 종류가 있습니다.

    • 정적 NetId: 씬 파일에 원래 있던 복제 엔티티. 서버와 클라이언트가 같은 씬 파일을 로드했다면, 둘 다 같은 규칙으로 번호를 매겨 같은 결과를 얻습니다. 아무것도 주고받지 않고 합의하는 것입니다. 55강의 핸드셰이크가 씬 이름까지 확인하는 이유가 이것입니다.
    • 동적 NetId: 게임 중에 생성된 엔티티(총알, 접속한 플레이어의 폰). 서버만 번호를 매기고(DynamicNetIdBase = 1 << 20부터) 생성 메시지에 실어 보냅니다. 서브 씬(50강)은 서브 씬마다 1 << 26부터 16384개씩 구간을 나눠 씁니다.

    정적 NetId의 "같은 규칙"이 무엇이냐가 중요합니다. 처음에는 엔티티 인덱스 순서였는데, 버그가 나서 바뀌었습니다.

    void AssignStaticNetIds(FScene& Scene)
{
	// 순서 = ReplicatedComponent 풀에 추가된 순서(밀집 배열). 같은 씬 파일을 로드하면 양쪽이 같다.
	// 엔티티 인덱스 순서는 쓰지 않는다 — 씬을 비우고 다시 열면(세션 전환) 해제된 인덱스가 역순으로 재사용되기 때문
	FRegistry& Registry = Scene.GetRegistry();
	const TSparseSet<FReplicatedComponent>* Pool = Registry.TryGetPool<FReplicatedComponent>();
	if (Pool == nullptr) { return; }
	const std::vector<FEntity> Entities = Pool->GetEntities(); // 아래에서 다른 풀에 추가하므로 복사
	uint32 NextNetId = 1;
	for (const FEntity Entity : Entities)
	{
		Registry.GetOrEmplace<FNetIdComponent>(Entity).NetId = NextNetId++;
	}
}

    7강 ECS의 희소 집합(sparse set)을 떠올려 보세요. 컴포넌트 풀의 밀집 배열은 "추가된 순서"를 그대로 담고 있습니다. 엔티티 인덱스는 재사용되지만, 같은 파일을 위에서부터 읽어 컴포넌트를 추가하는 순서는 파일이 같으면 항상 같습니다. 이 순서에 기대므로 정적 NetId는 씬 로드 직후, 게임이 아무것도 생성하기 전에 매겨야 합니다(FReplicationServer::Begin/FReplicationClient::Begin). 에디터 네트워크 플레이가 플레이 씬을 "복제(clone)"하지 않고 저장된 같은 JSON(PIE.escene)에서 만드는 것도 같은 이유입니다.

    핵심 개념생성은 신뢰, 트랜스폼은 비신뢰 스냅샷

    서버는 게임플레이 틱마다 FReplicationServer::Tick을 부르고, SendRate(기본 30Hz)마다 한 번 실제로 보냅니다. 시뮬레이션은 60Hz지만 전송은 그 절반입니다 — 회선을 아끼고, 사이는 클라이언트가 보간으로 메웁니다.

//   ReplicationSpawn:   uint32 개수, [uint32 NetId, uint8 종류(1 엔티티, 2 프리팹), uint32 부모 NetId, string 이름,

    생성 메시지에 프리팹 경로가 있다는 점을 보세요. 플레이어 폰처럼 프리팹에서 생성된 엔티티는 "이 프리팹을 만들어라 + 그 안의 각 엔티티(링크 ID)는 이 NetId"만 보내면 됩니다. 클라이언트가 같은 프리팹 파일로 하위 트리를 통째로 만들고, 값이 다른 컴포넌트만 이어지는 상태 메시지로 받습니다.

    비신뢰 스냅샷에는 함정이 하나 있습니다. 물체가 멈추면 서버는 "바뀐 것이 없으니" 보내지 않습니다. 그런데 멈추기 직전의 마지막 스냅샷이 손실되었다면? 클라이언트의 물체는 멈추기 조금 전 위치에서 영원히 멈춥니다. 그래서 서버는 트랜스폼이 멈춘 뒤에도 RestResendSeconds(1초) 동안 계속 보냅니다. 손실 5%에서 30번 연속 손실될 확률은 사실상 0입니다.

    핵심 개념스냅샷 보간과 0.1초 지연

    클라이언트가 스냅샷을 받자마자 위치를 그 값으로 바꾸면 어떻게 될까요? 스냅샷은 30Hz(33ms 간격)로 오는데 화면은 60Hz 이상이므로, 물체는 두 프레임마다 한 번씩 순간이동합니다. 게다가 지터 때문에 간격이 흔들리고, 가끔 하나씩 빠집니다. 결과는 덜컥거리는 움직임입니다.

    해결책은 일부러 조금 과거를 보여 주는 것입니다. 클라이언트는 받은 스냅샷을 버퍼에 쌓아 두고, "추정한 현재 서버 시각 − 0.1초" 시점의 위치를 그 시각을 감싸는 두 스냅샷 사이에서 보간합니다. 0.1초 전이라면 보통 그 시점 양옆의 스냅샷이 이미 도착해 있으므로, 항상 매끄러운 선 위를 따라갈 수 있습니다.

    float InterpolationDelay = 0.1f; // 초. 스냅샷 간격(1/30초)의 3배 — 한두 개 손실돼도 보간할 두 점이 있다
    // 서버 시각 추정: 크게 어긋나면 맞추고, 아니면 조금씩 따라간다 (지연 변동에 흔들리지 않게)
if (!bClockValid || std::abs(Time - ServerClock) > 0.25f)
{
	ServerClock = Time;
	bClockValid = true;
}
else
{
	ServerClock += (Time - ServerClock) * 0.1f;
}
...
// Update: 매 프레임 시계를 진행하고 (현재 − 지연) 시점을 그린다
ServerClock += DeltaSeconds;
const float RenderTime = ServerClock - InterpolationDelay;
...
// Interpolate: RenderTime을 감싸는 두 스냅샷 사이 보간. 범위 밖이면 가장 가까운 끝 값 (외삽하지 않는다)
Result.Position = FVector3::Lerp(From->Position, To->Position, Alpha);
Result.Rotation = FQuat::Slerp(From->Rotation, To->Rotation, Alpha).GetNormalized();

    세 가지를 짚어 봅시다.

    1. 서버 시계 추정: 클라이언트는 서버 시각을 직접 알 수 없고, 스냅샷에 적힌 시각만 봅니다. 도착 시각이 지터로 흔들리므로 받을 때마다 그 값으로 맞추면 시계가 앞뒤로 튑니다. 그래서 평소에는 차이의 10%씩만 따라가고(저역 통과 필터), 0.25초 넘게 어긋날 때만 한 번에 맞춥니다. 그 사이에는 자기 프레임 시간으로 시계를 진행합니다.
    2. 늦게 온 스냅샷은 버린다: 버퍼의 마지막보다 시각이 이르면(재정렬) 무시합니다. 1초보다 오래된 것은 지웁니다.
    3. 외삽(extrapolation)하지 않는다: 그리는 시각이 마지막 스냅샷보다 뒤라면 "속도로 앞을 추측"하지 않고 마지막 값에 머뭅니다. 추측은 물체가 갑자기 멈추거나 방향을 바꿀 때 틀린 곳으로 갔다가 되돌아오는 출렁임을 만듭니다. 0.1초 여유를 두었으니 그런 일은 드뭅니다.
    대가: 다른 사람은 항상 조금 과거에 있다 이 방식에서 클라이언트가 보는 다른 플레이어와 물체는 "편도 지연 + 0.1초" 전의 모습입니다. 남이 움직이는 것을 볼 때는 문제가 없습니다. 하지만 내 캐릭터까지 이렇게 보이면 키를 누르고 한참 뒤에 움직이고(57강), 내가 민 상자는 더 늦게 반응합니다(58강). 다음 두 강의는 이 대가를 줄이는 이야기입니다.

    ProjectE에서는클라이언트 쪽 물리 — 복제 바디는 키네마틱

    클라이언트(EWorldRole::Client)는 게임 로직(서버 전용 스크립트, 게임 모듈, AI)을 돌리지 않지만 물리는 돌립니다. 클라이언트에만 있는 로컬 물체(연출용 파편 등)는 클라이언트가 시뮬레이션해야 하고, 그 물체가 복제된 상자에 부딪히려면 상자도 물리 세계 안에 있어야 하기 때문입니다. 대신 서버가 시뮬레이션하는 복제 바디는 스스로 움직이면 안 됩니다. 그래서 키네마틱(kinematic) — 힘이나 충돌로 움직이지 않고, 정해 준 위치로만 움직이는 바디 — 으로 바꿉니다.

    if (bClient)
{
	// 서버가 시뮬레이션하는 복제 엔티티(NetId 보유)는 키네마틱: 복제 트랜스폼을 따라가며 로컬 물체와 충돌.
	// 물리 예측 중인 바디만 동적으로 로컬 시뮬레이션한다 (바뀌면 FPhysicsSystem이 바디를 다시 만든다)
	Systems.Physics->SetKinematicOverride([this](const FScene& Target, FEntity Entity) {
		return Target.GetRegistry().Has<FNetIdComponent>(Entity) && !IsPhysicsSimulatedLocally(Entity);
	});
}

    키네마틱 바디는 보간된 복제 트랜스폼을 따라 움직이며, 그 이동에서 속도가 계산되므로 로컬 물체를 밀 수 있고 레이캐스트에도 잡힙니다. 속도를 따로 보내지 않아도 되는 것이 장점입니다. 코드 주석의 "물리 예측 중인 바디만 동적으로"는 58강에서 이 규칙에 예외를 만드는 이야기입니다.

    함정과 교훈

    • 정적 NetId는 "파일 내용만으로 정해지는 순서"여야 한다: 위 그림 56-1의 버그는 Phase 17-9b에서 Lua 세션 전환(Net.Connect — 씬을 비우고 다시 로드)을 만들면서 드러났습니다. 처음 로드한 서버와 다시 로드한 클라이언트가 같은 씬인데도 서로 다른 엔티티를 같은 번호로 불렀습니다. 같은 입력에서 같은 결과를 내야 하는 값은 "프로세스의 과거"(메모리 재사용 순서 등)에 의존하면 안 됩니다.
    • 프리팹 자식도 각자 ReplicatedComponent가 필요하다: 복제 단위는 엔티티입니다. 플레이어 프리팹의 루트에만 붙이면 자식(예: 몸 방향을 돌리는 메시 엔티티)의 값은 오지 않고, 클라이언트는 프리팹 기본값을 보여 줍니다(CLAUDE.md Phase 21 규칙).
    • 소유자는 늦게 올 수 있다: 클라이언트에서 ReplicatedComponent.OwnerPlayerId는 상태 메시지로 오므로, 스크립트 OnStart보다 늦게 도착할 수 있습니다. "이 폰이 내 것인가"는 OnStart에서 한 번 판정하지 말고, 확정될 때까지 매 프레임 확인합니다.
    • 클라이언트에서 트랜스폼을 직접 쓰지 않는다: 복제 엔티티의 트랜스폼은 매 프레임 보간 값으로 덮어씁니다. 클라이언트 스크립트가 위치를 바꿔도 다음 프레임에 사라집니다. 예외는 57·58강에서 볼 "예측" 대상뿐이며, 그것도 SetTransformFilter로 명시적으로 보간에서 뺍니다.
    • 알려진 제한: 생성 뒤 부모를 바꾸는 것은 복제되지 않습니다(Phase 17-5b 기록). 리슨 호스트는 렌더 보간된 물리 값을 보내 최대 한 스텝 늦습니다.
    정리
    • 복제 단위는 ReplicatedComponent가 붙은 엔티티, 내용은 리플렉션 등록 컴포넌트 값이다. 새 컴포넌트는 등록만 하면 복제된다.
    • 제외는 TF_NoReplicate/PF_NoReplicate/리소스 핸들. PF_Transient는 저장만 빼고 복제는 된다.
    • 정적 NetId = ReplicatedComponent 풀 추가 순서(양쪽이 같은 씬 파일을 로드했을 때 같음), 동적 NetId = 서버가 1<<20부터.
    • 30Hz 전송. 생성·파괴·바뀐 컴포넌트는 신뢰 채널(모든 연결 공통 기준), 트랜스폼 변화는 비신뢰 스냅샷(멈춘 뒤 1초 재전송).
    • 클라이언트는 (추정 서버 시각 − 0.1초)를 두 스냅샷 사이에서 보간하고 외삽하지 않는다.
    • 클라이언트의 복제 동적 바디는 키네마틱으로 보간 위치를 따른다.

    생각해 볼 문제

    왜 필요한가"원격 클라이언트 조작이 한발 느림"

    Phase 17이 끝났을 때 멀티플레이는 동작했습니다. 클라이언트가 매 틱 입력 상태를 서버로 보내고(PlayerInput), 서버의 스크립트가 그 입력으로 캐릭터를 움직이고, 결과가 스냅샷으로 돌아와 0.1초 지연 보간으로 그려졌습니다. 권한 서버 원칙에 충실한 구조입니다. 그런데 사용자 보고가 왔습니다. "원격 클라이언트 조작이 한발 느림" — Phase 22는 이 문장으로 시작합니다.

    3. 다음 전송 틱(30Hz)까지 대기

    5. 그리고 보간 지연 0.1초

    핵심 개념예측 — 서버가 할 계산을 미리 해 둔다

    해법의 아이디어는 단순합니다. 내 캐릭터가 어떻게 움직일지는 사실 내 입력이 거의 전부를 결정합니다. 서버의 답을 기다릴 필요 없이, 클라이언트가 서버와 똑같은 이동 계산을 자기 입력으로 미리 돌려 즉시 보여 주면 됩니다. 이것이 클라이언트 예측(client-side prediction)입니다. 권한은 여전히 서버에 있습니다. 클라이언트는 "서버도 아마 이렇게 계산할 것"이라고 예측할 뿐이고, 서버 답이 다르면 서버를 따릅니다.

    1. 같은 입력 → 같은 결과: 클라이언트와 서버가 같은 이동 함수를 같은 입력으로 돌리면 같은 위치에 도착해야 합니다. 그래야 대부분의 경우 "예측이 맞아서 아무 일도 없음"이 됩니다.
    2. 입력을 단위로 쪼개 이름표를 붙인다: 서버가 "몇 번째 입력까지 처리한 결과가 이것"이라고 알려 줘야, 클라이언트가 자기 기록의 어디와 비교할지 압니다.

    56강의 FReplicationClient::Update는 매 프레임 모든 복제 엔티티의 트랜스폼을 스냅샷 보간 값으로 덮어씁니다. 예측 캐릭터에도 이것이 적용되면, 클라이언트가 방금 예측한 위치를 0.1초 과거의 서버 위치가 덮어써서 예측이 무의미해집니다. 그래서 필터를 둡니다.

    // 거짓을 돌려주는 엔티티에는 스냅샷 보간 트랜스폼을 쓰지 않는다 (소유 클라이언트가 예측하는 캐릭터·물리 바디 — FGameWorld::IsPredicted)
void SetTransformFilter(std::function<bool(FEntity)> ShouldApply) { TransformFilter = std::move(ShouldApply); }

    런타임과 에디터의 클라이언트 앱은 SetTransformFilter(!World.IsPredicted(e))를 걸고, 새 클라이언트 앱도 반드시 같은 필터를 걸어야 합니다(CLAUDE.md 규칙). IsPredicted는 "클라이언트 모드 + 캐릭터 이동 컴포넌트 + 내가 조종 + 예측 옵션 켬"일 때 참입니다.

    return Mode == ENetMode::Client && ... &&
       Scene->GetRegistry().Has<FCharacterMovementComponent>(Entity) && GetOwner(Entity) >= 0 && IsLocallyControlled(Entity) &&
       UsesClientPrediction(Entity);

    예측은 끌 수 있습니다(사용자 요청). 컴포넌트의 bClientPrediction과 프로젝트 설정 네트워크의 "클라이언트 예측"이 둘 다 켜져 있어야 예측합니다. 끄면 소유 클라이언트는 무브를 보내기만 하고, 자기 캐릭터도 스냅샷 보간으로 보여 줍니다. 서버 쪽 코드는 똑같습니다. 이 스위치 덕분에 "예측 있음/없음"을 같은 빌드에서 바로 비교할 수 있습니다.

    검증은 루프백 테스트 CharacterPrediction_ImmediateMatchAndCorrection가 맡습니다. Plans.md 22-2에 적힌 확인 항목은 세 가지입니다: 틱 한 번에 클라이언트가 7.5cm 즉시 이동하고 서버는 아직 그대로인가, 1초 이동한 뒤 서버와 1cm 이내이고 보정이 0회인가, 서버가 캐릭터를 순간이동시키면 클라이언트가 300cm를 보정하는가. 실제 앱 측정(--hold-keys W)에서는 키를 누른 다음 프레임(약 20ms)에 이동이 시작되었습니다. 예측 전 약 130ms였습니다.

    함정과 교훈

    실제로 겪은 일: "같은 무브 → 같은 결과"의 경계 예측의 전제는 결정적 이동입니다. 그래서 스크립트가 이동을 직접 계산하던 구조를 버리고(PlayerCharacter.lua는 입력 → AddMovementInput/Jump와 시점·카메라만 남김), 이동은 C++ 순수 경로로 모았습니다. 그래도 남는 차이가 있었습니다. Plans.md 28-3에 기록된 것처럼 서버는 받은 무브를 한 프레임에 몰아서(0개~여러 개) 적용한 뒤 물리 스텝을 한 번 하고, 클라이언트는 무브 하나마다 스텝을 합니다. 그래서 무브가 몰려 도착하면(손실 재전송, 지연 변동) 상자를 미는 결과가 조금 달라지고, 1~5cm의 보정이 남습니다. 예측은 "차이를 없애는" 기술이 아니라 "차이가 드물고 작게 만들고, 생기면 부드럽게 흡수하는" 기술입니다.
    • 다시 적용 중에는 부수 효과를 끈다: 재조정은 "계산을 다시 해 보는 것"이지 "사건을 다시 일으키는 것"이 아닙니다. 상자 밀기처럼 세계에 흔적을 남기는 일은 다시 적용 중에 꺼야 합니다(SetCharactersPushBodies(false)).
    • 서버는 시간을 믿지 않는다: 무브 dt를 상한으로 자르는 것은 치트 방지의 시작일 뿐입니다. Plans.md는 "무브 dt 합 vs 실제 시간"으로 속도 조작을 막는 일을 후속 과제로 남겨 두었습니다.
    • 캐릭터를 따라가는 카메라는 OnLateUpdate에서: 예측·물리·트랜스폼 갱신이 끝난 뒤 카메라를 놓아야 한 프레임 늦게 따라가며 떨리지 않습니다(CLAUDE.md Phase 21 규칙).
    • 남이 보는 내 캐릭터는 여전히 과거다: 예측은 소유 클라이언트의 화면만 바꿉니다. 다른 클라이언트는 그 캐릭터를 스냅샷 보간으로 봅니다. 그래서 내가 미는 상자를 "나는 현재, 상자는 과거"에서 보게 되는 문제가 생기는데, 이것이 58강의 출발점입니다.
    정리
    • 예측 = 서버와 같은 이동 계산을 클라이언트가 자기 입력으로 미리 해 즉시 보여 주는 것. 권한은 여전히 서버.
    • 전제: 같은 무브 → 같은 결과. 이동을 스크립트에서 C++ 순수 경로(SimulateCharacter)로 옮겼다.
    • 클라이언트: 무브에 순번 → 즉시 시뮬레이션 → 기록 → 최근 8개를 겹쳐 비신뢰 전송.
    • 서버: 소유자 확인, 중복·비정상 거르기, dt·입력 제한, 순번 순서로 적용, ack(순번 + 상태).
    • 재조정: 확인된 무브 삭제 → 서버 상태로 되돌림 → 남은 무브 다시 적용(밀기 끔) → 1cm 넘게 다르면 보정.
    • 보정은 화면 오프셋으로 0.1초 시간 상수에 걸쳐 흡수, 150cm 넘으면 즉시. 예측 대상은 SetTransformFilter로 스냅샷 보간에서 뺀다.

    생각해 볼 문제

    Q1. 클라이언트가 무브 기록을 240개(4초)까지만 보관합니다. 서버 응답이 5초 동안 끊겼다가 돌아오면 어떻게 될까요? 오래된 무브는 이미 버려졌으므로, ack가 와도 "서버 상태 + 남은 기록"으로 지금 위치를 정확히 재구성할 수 없습니다. 재조정 결과가 크게 달라지고, 차이가 150cm를 넘으면 오프셋 없이 바로 서버 쪽으로 옮겨집니다. 상한은 메모리와 재조정 비용(다시 적용할 무브 수)을 제한하기 위한 것이고, 4초 넘게 응답이 없는 상황은 어차피 정상 플레이가 아닙니다.
    Q2. ack를 신뢰 채널로 보내면 더 안전하지 않을까요? ack는 "가장 최근 상태"만 의미가 있습니다. #5의 ack가 손실되어도 곧 #6, #7의 ack가 오고, 그것이 더 새로운 정답입니다. 신뢰 채널로 보내면 손실된 #5를 재전송하는 동안 #6 이후가 막혀 재조정이 늦어집니다. 그래서 ProjectE는 비신뢰로 보내고, 순서가 바뀌어 늦게 온 ack(Sequence <= LastAckSequence)는 버립니다.
    Q3. 재조정에서 차이가 생겼을 때 화면 오프셋 없이 시뮬레이션 위치만 천천히 서버 쪽으로 옮기면 어떤 문제가 생길까요? 시뮬레이션이 서버와 다른 위치에서 계속 진행되므로, 그 위에서 만든 새 무브의 예측도 계속 틀리고 다음 ack에서 또 보정이 생깁니다. 보정이 보정을 낳는 셈입니다. 시뮬레이션은 즉시 서버를 따르고, "보이는 것"만 천천히 따라가게 분리하는 것이 핵심입니다.

    왜 필요한가나는 현재에, 상자는 과거에

    57강의 예측으로 원격 클라이언트의 캐릭터는 즉시 움직이게 되었습니다. 그런데 새 사용자 보고가 왔습니다. "원격 클라이언트에서 물리 물체와 상호작용하면 드득거리고 반응이 늦음." Phase 28은 이 원인을 이렇게 정리합니다.

    //   문제: 예측 캐릭터는 "현재"(서버보다 왕복 지연만큼 앞)에 있는데 복제 동적 바디는 키네마틱으로 스냅샷 보간(편도 지연 + 0.1초 과거)을 따른다.
//     클라이언트에선 과거 위치의 밀리지 않는 상자에 막히고 서버에선 밀리므로 ack마다 캐릭터 보정이 생기고, 상자는 왕복 + 0.1초 뒤에야 움직인다.

    한 화면 안에 서로 다른 시간이 섞여 있는 것이 문제의 핵심입니다. 내 캐릭터는 예측 덕분에 "지금"에 있지만, 상자는 56강의 규칙대로 "과거"의 서버 위치를 키네마틱으로 따라갑니다. 키네마틱 바디는 밀어도 움직이지 않습니다. 그래서 클라이언트에서 캐릭터는 상자에 막혀 멈추는데, 서버에서는 같은 무브로 상자를 밀며 앞으로 갑니다. ack가 올 때마다 재조정이 "너는 앞으로 갔어"라고 캐릭터를 끌어당기고, 다시 과거의 상자에 막히고 — 이것이 "드득거림"입니다.

    Plans.md 28-1의 진단 측정은 이 설명을 숫자로 확인합니다. 물리 예측이 꺼진 상태에서 화면의 캐릭터 튐은 최대 1.3m, 불량 망에서 상자가 반응하기까지 0.25초가 걸렸습니다.

    핵심 개념대상 선정 — 반경, 빠른 물체, 접촉

    모든 복제 바디를 로컬 시뮬레이션하면 안 됩니다. 멀리서 다른 플레이어가 굴리는 공은 내가 영향을 줄 수 없고, 그것을 현재로 외삽하면 틀리기만 합니다. 그래서 "내가 영향을 줄 수 있는 것"만 고릅니다.

    //   대상 선정 (TickPhysicsPrediction, 스크립트 뒤·캐릭터 이동 전): 루트 엔티티이고 NetId + 동적 RigidBody + 콜라이더(바디)가 있는 복제 엔티티 중
//     로컬 예측 캐릭터(IsPredicted) 중심에서 PhysicsPredictionRadius 안에 중심이 있거나 캐릭터가 닿은 것.
//     반경 안이라도 서버 속도가 MaxEnterSpeed 이상이면(서버가 쏜 공처럼 내가 영향을 주지 않는 빠른 물체) 닿을 때만 — 현재로 외삽하면 크게 틀린다.
//     대상이 되면 키네마틱 오버라이드를 풀어(바디를 동적으로 다시 만든다) 로컬에서 현재 시간 기준으로 시뮬레이션한다.
//     진입 상태 = 화면 위치(보간 값) + 서버 속도(스냅샷 두 개의 차분)이고, 현재 시간과의 차이는 아래 수렴이 곧바로 줄인다 (진입 순간 튀지 않게).

    대상에서 빠지는 것도 규칙이 있습니다. 근처·접촉이 ReleaseDelaySeconds(1초) 동안 없고, 로컬과 서버 속도가 모두 RestSpeed(5cm/s) 미만이고, 위치 오차가 2cm 이내여야 키네마틱으로 돌아갑니다. 이때 화면 위치를 BlendOutSeconds(0.25초)에 걸쳐 스냅샷 보간 위치로 옮긴 뒤 보간에 넘깁니다. 멈춘 물체라 "과거 = 현재"이므로 이 이음새는 눈에 띄지 않습니다. 해제 판정 반경을 진입 반경의 1.25배로 넓게 잡은 것은 경계에 걸친 물체가 매 프레임 들어왔다 나갔다 하지 않게 하려는 히스테리시스(hysteresis)입니다.

    핵심 개념시각 맞추기 — 서버 스냅샷을 내 기록의 어디와 비교할까

    로컬 상자를 서버 쪽으로 수렴시키려면 "서버 상자와 내 상자가 얼마나 다른가"를 알아야 합니다. 57강의 재조정과 같은 문제가 여기도 있습니다. 서버 스냅샷은 과거의 상태이고 내 상자는 현재에 있으므로, 같은 시점끼리 비교해야 합니다. 그래서 클라이언트는 예측 바디의 위치를 매 프레임 기록(HistorySeconds 1.5초)해 두고, 스냅샷이 오면 그 스냅샷 시점에 해당하는 기록과 비교합니다.

    문제는 "서버 시각 Ts의 스냅샷이 내 로컬 시계로 언제인가"입니다. 여기서 ack가 다리 역할을 합니다.

    //   시각 맞추기: 서버는 무브 S를 적용한 프레임에 ack(S)를 보내고 같은 프레임 끝에 스냅샷을 보낸다. 그래서 스냅샷(서버 시각 Ts)의 바디 상태는
//     로컬이 무브 S를 시뮬레이션한 프레임의 물리 스텝 결과와 같은 시점이다. 오프셋 = (ack 무브의 로컬 시계) - Ts 를 감소하는 최댓값으로 유지한다
//     (ack 손실/재정렬은 오프셋을 작게만 만든다). 로컬 시각 = Ts + 오프셋.

    오프셋을 "감소하는 최댓값"으로 유지하는 이유도 재미있습니다. ack가 늦게 오거나 재정렬되면 잘못된(더 작은) 오프셋 표본이 생길 수 있습니다. 가장 큰 값을 기준으로 삼고 천천히(TimingDecayPerSecond 0.05) 내려가게 하면, 이상한 표본 하나에 흔들리지 않습니다. 지연이 실제로 크게 줄었을 때(새 표본이 0.5초 넘게 작을 때)만 다시 잡습니다.

    스냅샷이 올 때마다(ProcessBodySnapshot) 오차를 계산하고, 매 프레임(ApplyBodyCorrection) 그 오차의 일부를 바디에 더합니다.

...
if (SampleHistory(Body.History, LocalTime, HistoryPosition, HistoryRotation))

	Body.PositionError = Newest.Position - HistoryPosition;
	...
	// 속도도 같은 구간의 차분끼리

	Body.PositionError = Newest.Position + Body.ServerVelocity * Ahead - Local.Position;

    "같은 시점끼리 비교"의 힘을 보세요. 캐릭터가 상자를 미는 중이라 상자가 가속하고 있어도, 서버와 클라이언트가 같은 시뮬레이션을 했다면 같은 시점의 위치는 같으므로 오차는 0입니다. 현재 위치와 비교했다면 "현재 − 과거"만큼의 가짜 오차가 생겨, 보정이 상자를 계속 뒤로 끌었을 것입니다. 스냅샷에는 속도가 없으므로 서버 속도는 스냅샷 두 개의 차분으로 구하고, 비교 상대인 로컬 속도도 같은 구간의 기록 차분으로 구합니다. 같은 방식으로 잰 것끼리 비교해야 측정 방식의 차이가 오차로 둔갑하지 않습니다.

    const float    PositionAlpha = 1.0f - std::exp(-DeltaSeconds / PositionCorrectionSeconds); // τ = 0.15초
const FVector3 DeltaPosition = Body.PositionError * PositionAlpha;
Body.PositionError           = Body.PositionError - DeltaPosition;
...
Systems.Physics->CorrectBody(Entity, DeltaPosition, DeltaRotation, DeltaVelocity, DeltaAngular);
// 기록에도 같은 보정 (다음 스냅샷이 남은 오차만 보게). 속도 보정은 "처음부터 그 속도로 지금 상태에 왔다"로 과거를 옮긴다
for (FBodyHistorySample& Sample : Body.History)
{
	const float Before = Sample.Time - LastRecordTime; // 0 이하
	Sample.Position    = Sample.Position + DeltaPosition + DeltaVelocity * Before;
	...

    τ(타우) — 시간 상수 매 프레임 남은 오차의 1 − exp(−dt / τ)만큼을 고치면, 오차는 e−t/τ로 줄어듭니다. τ = 0.15초면 0.15초 뒤 37%, 0.45초 뒤 5%가 남습니다. 57강의 화면 오프셋(τ = 0.1초)과 같은 모양입니다. τ가 작으면 빨리 맞지만 보정이 눈에 띄고(밀리는 상자가 덜컥), 크면 부드럽지만 서버와 오래 어긋납니다. 위치·속도·회전 모두 0.15초입니다.

    보정을 바디에만 하고 기록에는 안 하면 어떻게 될까요? 다음 스냅샷이 오면 기록은 아직 보정 전이므로 같은 오차를 다시 보고, 이미 고친 만큼을 또 고칩니다. 오차를 두 번 세는 셈이라 과보정 → 반대쪽 오차 → 진동이 됩니다. 그래서 바디에 더한 보정을 기록 전체에도 똑같이 더해 "처음부터 그 위치·속도였던 것처럼" 만듭니다. 이 처리 덕분에 다음 스냅샷은 남은 오차만 봅니다. 그리고 CorrectBody는 렌더 보간 직전 상태(45강의 물리 보간)도 함께 옮겨, 보정 프레임에 화면이 끊기지 않게 합니다.

    위치 차이가 100cm(SnapDistance)를 넘으면 수렴을 포기하고 서버 상태를 현재로 외삽한 위치로 바로 옮깁니다. 그렇게 큰 차이는 "작은 계산 차이"가 아니라 서버에서 다른 일이 일어났다는 뜻이고, 천천히 끌면 상자가 벽을 뚫고 미끄러지는 이상한 장면이 됩니다. 회전은 스냅하지 않습니다 — 구르는 공은 회전이 쉽게 어긋나고, 충돌에는 위치가 더 중요하기 때문입니다.

    ProjectE에서는재조정 중의 바디 — PoseBodiesForReplay

    이제 상자도 로컬에서 움직이므로 57강의 캐릭터 재조정과 엮입니다. 재조정은 캐릭터를 서버 상태(과거)로 되돌려 남은 무브를 다시 적용하는데, 그동안 상자는 어디에 있어야 할까요? ProjectE는 전체 롤백을 하지 않으므로 상자는 재시뮬레이션하지 않습니다. 남는 선택지는 둘입니다.

    1. 상자를 지금 자리에 둔 채 다시 적용: 캐릭터는 과거에서 출발하는데 상자는 이미 밀려간 "현재" 자리에 있어, 밀기 중인 캐릭터가 상자의 현재 면에 걸립니다. 결과적으로 ack마다 1~8cm의 작은 보정이 생깁니다.
    2. 무브마다 상자를 그 무브를 처음 시뮬레이션할 때의 기록 위치로 잠시 옮겨 다시 적용(PoseBodiesForReplay), 끝나면 되돌림(RestoreBodiesAfterReplay): 충돌 상대만 "그때 자리"에 있으므로 상자 밀기는 원래 결과와 거의 같습니다.
    for (const auto& [Entity, Body] : PredictedBodies)
{
	...
	// 그 무브가 시뮬레이션될 때 바디가 있던 곳 = 그 프레임 전 기록 (기록은 프레임 끝 물리 스텝 결과).
	const auto After = std::lower_bound(Body.History.begin(), Body.History.end(), MoveTime, ...);
	const FBodyHistorySample& Sample = After == Body.History.begin() ? Body.History.front() : *(After - 1);
	Systems.Physics->PoseBody(Entity, Sample.Position, Sample.Rotation);
}

    그런데 2번에도 함정이 있었습니다. 서버와 결과가 갈린 경우(예: 가벼운 공에 올라탐), 2번의 결과 위치가 "지금" 바디와 겹쳐서, 바디를 되돌리는 순간 공을 튕겨 낼 수 있습니다. 그래서 ProjectE는 두 방식을 모두 계산해 지금 예측에 더 가까운 쪽을 쓰되, 2번 결과가 동적 바디에 1cm(MaxReplayPenetration) 넘게 묻혀 있으면 1번을 씁니다.

	if (!bPosedClear || FVector3::DistanceSquared(Posed.Position, Before) >= FVector3::DistanceSquared(Replayed.Position, Before))

		Systems.Physics->SetCharacterState(*Scene, Entity, Replayed);
	}
	else
	{
		Replayed = Posed;
	}
}

    생각해 볼 문제

    Q1. 반경 안의 모든 바디를 예측하지 않고 "빠른 물체는 닿을 때만"으로 예외를 둔 이유는? 예측 바디의 진입 상태는 "보간 위치 + 서버 속도"이고, 현재 시간과의 차이는 서버 상태를 현재로 외삽해 메웁니다. 서버가 쏜 빠른 공처럼 내가 영향을 주지 않는 물체는 외삽 거리가 크고, 그동안 서버에서 무엇에 부딪혔을지 모르므로 크게 틀립니다. 내가 영향을 줄 수 없는 물체를 굳이 현재로 끌어와 틀리느니, 과거 보간으로 정확히 보여 주는 편이 낫습니다. 닿는 순간에는 상호작용이 필요하므로 그때만 예측합니다.
    Q2. 로컬 기록 대신 "지금 로컬 위치"와 서버 스냅샷 위치를 비교하면, 일정한 속도로 밀리는 상자에서 어떤 일이 생길까요? 스냅샷은 과거 시점이므로, 상자가 v로 움직이면 "지금 위치 − 과거 위치 ≈ v × 시간 차"만큼의 가짜 오차가 항상 생깁니다. 보정이 이 오차를 없애려고 상자를 계속 과거 쪽으로 끌어, 밀리는 상자가 늦게 따라오는(사실상 예측 이전과 비슷한) 결과가 됩니다. 같은 시점의 기록과 비교하면 같은 시뮬레이션일 때 오차가 0입니다.
    Q3. 보정을 바디에 적용한 뒤 기록은 그대로 두면 어떤 현상이 생길까요? 다음 스냅샷이 와서 기록과 비교할 때, 이미 바디에 반영한 보정이 기록에는 없으므로 같은 오차를 다시 보게 됩니다. 결과적으로 오차를 두 번 이상 고쳐 과보정이 되고, 반대 방향 오차가 생겨 상자가 앞뒤로 흔들립니다. 그래서 ApplyBodyCorrection은 바디와 기록 전체에 같은 보정을 더합니다.

    • 능력(스킬) 발동을 예측 키로 미리 보여 주고, 서버 확인 시 합치고 거절 시 되돌리는 흐름을 설명할 수 있습니다.

    왜 필요한가"값"이 아니라 "사건"을 보내야 할 때

    56강의 복제는 상태를 맞춥니다. "체력이 40이다", "문이 열려 있다". 그런데 게임에는 상태로 표현하기 어색한 사건이 많습니다.

    • 클라이언트가 "문을 열고 싶다"고 서버에 요청하기 (입력 상태로 보내기엔 일회성이고 대상이 있음)
    • 서버가 특정 플레이어에게만 "퀘스트 완료 창을 띄워라"
    • 서버가 모두에게 "여기서 폭발 연출을 재생하라" (폭발은 상태가 아니라 한순간)

    이런 것을 위해 RPC(Remote Procedure Call, 원격 프로시저 호출) — "저쪽 기계에서 이 함수를 이 인자로 불러 줘" — 를 둡니다. 그리고 RPC로 발동 요청을 보내는 대표적인 기능이 스킬(능력)입니다. 하지만 스킬은 57강의 이동처럼 누르는 즉시 반응해야 하는데, 요청을 보내고 서버 답을 기다리면 다시 왕복 지연이 생깁니다. 이 강의 후반부는 능력 발동을 예측하고, 서버가 거절하면 되돌리는 방법을 다룹니다.

    핵심 개념RPC 세 종류와 라우팅

    // 네트워크 RPC — Lua(entity:CallServer 등)와 게임 모듈 C++(IGameNet::CallRpc)이 같은 경로를 쓴다.
// 받는 쪽: 대상 엔티티 스크립트의 Server_/Client_/Multicast_<이름> 메서드 + 게임 모듈 IGameModule::OnRpc(서버에서만)
enum class EGameRpcKind : uint8
{
	Server,    // 클라이언트 → 서버 (대상 엔티티 소유자만). 서버에서 부르면 바로 로컬 실행
	Client,    // 서버 → 대상 엔티티 소유 클라이언트 (호스트 소유면 로컬)
	Multicast, // 서버 → 서버 자신 + 모든 클라이언트
};

    Lua에서는 엔티티 메서드로 부릅니다. entity:CallServer("Fire", 목표)를 부르면 서버에서 그 엔티티 스크립트의 Server_Fire(목표)가 실행됩니다. 접두사로 받는 쪽 메서드를 정하는 방식이라, 등록 절차가 따로 없습니다. 인자는 nil/bool/숫자/문자열/Vector3/에셋/엔티티를 지원하고, 엔티티는 NetId로 바꿔 보냅니다(복제되지 않은 엔티티는 받는 쪽에서 무효).

    라우팅은 FGameWorld::RouteRpc 한 곳에 있습니다.

    핵심 개념능력 예측 — 예측 키, 예측 창, 확인과 거절

    51강의 능력 시스템(언리얼 GAS식)에서 플레이어가 "화염구"를 누르면 무슨 일이 일어나야 할까요? 마나가 줄고, 쿨다운이 시작되고, 시전 애니메이션이 재생되고, 투사체가 날아갑니다. 이 모든 것을 서버 답을 기다려 보여 주면 57강 이전의 이동처럼 끈적합니다. 하지만 이동과 달리 능력은 서버가 거절할 수 있습니다. 클라이언트는 마나가 충분하다고 봤지만, 서버에서는 방금 받은 데미지 효과로 상태가 달라졌을 수 있습니다.

    그래서 능력 예측에는 세 가지 장치가 필요합니다.

    1. 예측 키(prediction key): 발동마다 붙이는 이름표. 엔티티마다 1부터 늘어나는 번호입니다. 클라이언트가 미리 적용한 모든 변화에 이 키를 붙여 두면, 나중에 "키 7의 결과를 되돌려라" 또는 "키 7까지는 서버 값에 들어 있다"를 정확히 처리할 수 있습니다.
    2. 예측 범위: 무엇을 미리 해도 되는가. 되돌릴 수 있는 것만 예측합니다.
    3. 확인/거절 처리: 서버 답이 왔을 때 예측과 서버 값을 합치거나 되돌리는 규칙.
    // 예측 (소유 클라이언트, 능력 bPredicted)
//   키: 엔티티마다 1부터 늘어나는 예측 키. 발동 요청(AbilityActivate 메시지)에 실어 보낸다.
//   예측 범위: 발동 검사, 비용(기본값 변화량), 쿨다운·ActivationEffects·스크립트가 예측 창에서 자기에게 건 효과(예측 효과), 발동 태그,
//     능력 스크립트 로컬 실행(몽타주 등 연출). 예측 창 = OnActivate가 처음 대기(ctx:Wait 등)에 들어가기 전. 그 뒤 자기 효과·커밋은 서버만.
//   예측하지 않음: 다른 대상 효과·데미지·투사체·스폰(서버만, ctx:HasAuthority), 주기 실행, 효과 제거, Health/메타 속성.
//   서버: 같은 키로 발동하고 예측 창 안에서 적용한 효과에 그 키를 붙인다. 처리한 최대 키를 RepPredictionKey로 복제한다
//     (복제 문자열과 같은 컴포넌트라 "이 키까지의 결과가 이 값에 들어 있다"가 항상 맞다). 거절이면 AbilityResult(거절, 이유)를 소유자에게.
//   합치기: RepPredictionKey >= 키가 오면 그 키까지의 예측 효과·변화량을 버린다 → 서버 값만 남아 중복 적용이 없다.
//   거절: 그 키의 예측 효과·변화량을 즉시 되돌리고 로컬 인스턴스를 취소(OnEnd cancelled) + AbilityFailed("Rejected:<이유>").
//   서버가 예측 발동을 취소로 끝내면 AbilityResult(취소) → 로컬 인스턴스 취소. 3초 넘게 처리되지 않은 예측은 버린다(경고).

    예측 창 — 능력 스크립트의 "첫 대기 전"

    능력 스크립트(Lua)는 OnActivate(ctx)를 코루틴으로 실행합니다. 소유 클라이언트는 예측 능력이면 같은 스크립트를 로컬로 돌립니다. 그런데 스크립트 전체를 예측하면 안 됩니다. 시간이 지날수록 서버와 클라이언트의 상황이 갈라지기 때문입니다. 그래서 예측 창을 "OnActivate가 처음 대기(ctx:Wait 등)에 들어가기 전"으로 짧게 잡았습니다.

    남에게 데미지를 주거나 투사체를 만드는 일을 예측하지 않는 이유는 간단합니다. 되돌리기가 어렵거나 불가능합니다. 클라이언트가 미리 적에게 데미지를 줬다가 서버가 거절하면, 적의 체력바가 줄었다 늘어나는 이상한 장면이 됩니다. 투사체를 미리 만들었다가 서버가 다른 위치에 만들면 둘이 됩니다. 그래서 스크립트 규칙은 이렇습니다. "다른 대상 효과·스폰·데미지는 if ctx:HasAuthority() then ... end 안에 둔다. 클라이언트에서 ApplyEffectToTarget은 아무것도 하지 않고 false."

    확인(합치기)과 거절(되돌리기)

    정리
    • RPC는 상태가 아닌 사건을 보낸다. Server(클라→서버, 소유자만) / Client(서버→소유자) / Multicast(서버→서버 자신+모두). 신뢰 채널, Standalone은 즉시 로컬.
    • 서버는 받는 순간 소유권을 검사한다. 클라이언트 쪽 검사는 보안이 아니다.
    • Lua와 C++ 게임 모듈은 Scene/GameRpc.h 한 경로를 공유한다. 받는 쪽 = 스크립트 Server_/Client_/Multicast_이름 + 서버의 OnRpc.
    • 능력 예측: 예측 키 → 예측 창(첫 대기 전) 안에서 자기 비용·쿨다운·효과·연출만 예측 → 서버가 같은 키로 발동.
    • 확인 = RepPredictionKey(상태와 같은 컴포넌트) ≥ 키 → 예측분 버림. 거절 = AbilityResult → 그 키만 되돌리고 인스턴스 취소.
    • 거절 경로는 ability.ClientSkipChecks로 일부러 일으켜 불량 망 Verify로 검증한다.

    생각해 볼 문제

    Q1. 클라이언트 2가 클라이언트 1 소유 캐릭터에 CallClient를 부르면 어떻게 될까요? RouteRpc에서 Client/Multicast는 서버에서만 부를 수 있으므로, 클라이언트에서 부르면 예외(Lua 오류)가 납니다. 만약 수정된 클라이언트가 그런 메시지를 강제로 보내도, 서버의 ReceiveRpc는 클라이언트로부터 Server 종류만 받고 소유자도 검사하므로 경고 로그만 남기고 버립니다.
    Q2. 서버가 처리한 예측 키를 능력 컴포넌트가 아니라 별도의 "확인" 메시지로 보냈다면 어떤 문제가 생길 수 있을까요? 확인 메시지와 상태 복제가 서로 다른 메시지로 오면 도착 순서가 어긋날 수 있습니다. "키 7 확인"이 먼저 와서 예측분(마나 −20)을 버렸는데 복제 값은 아직 옛 값(100)이면, 마나가 잠깐 100으로 튀었다가 80으로 내려갑니다. 반대 순서면 잠깐 60(이중 차감)이 보입니다. 같은 컴포넌트에 넣으면 둘이 항상 한 번에 도착합니다.
    Q3. 화염구 스크립트가 ctx:Wait(0.4) 뒤에 자기에게 "시전 후 이동 속도 감소" 효과를 겁니다. 이 효과는 예측될까요? 예측되지 않습니다. 예측 창은 첫 대기 전까지이므로, 대기 뒤의 자기 효과는 서버만 적용하고 클라이언트는 복제로 받습니다. 즉시 반응이 필요한 효과라면 첫 대기 전에 걸도록 스크립트를 짜야 합니다. 예측 창을 짧게 둔 것은, 시간이 지날수록 서버와 클라이언트의 상황이 갈라져 예측이 틀릴 가능성이 커지기 때문입니다.
